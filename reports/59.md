## 原因

1. **#59 卡住：** tracing-core 在 `LOCKED_DISPATCHERS` 讀鎖下 upgrade 每個 subscriber 的 Weak。若此時測試 T 放掉 guard，別的執行緒手上那份就成了最後一份引用；它在鎖內 drop，OTel 的 `SdkTracerProvider`/`SdkLoggerProvider` 跟著 shutdown，發出 `otel_debug!`（`internal-logs` feature），這是首次命中的 callsite，要再拿讀鎖，卻排在等寫鎖的 `set_default` 後面 → 死結，4 個測試執行緒全卡。
2. **PR #62 flake：** 只登記一個 dispatcher 時，tracing-core 用「命中執行緒」的預設 subscriber 決定 callsite 的 interest，沒有 subscriber 的執行緒先命中就會把 `never` 快取給所有執行緒。
3. **#61：** `REBUILD_FAIL_NEXT`、`REBUILD_CHECKOUT_FAIL_NEXT`、`REBUILD_DOC_META_FAIL_NEXT` 是行程全域，別的測試的 rebuild 會吃掉別人布置的失敗。

## #93（只做診斷；修正草稿在 `lane-93`，未開 PR）

### 結論

- **不是 #86 造成的，也不是 tracing。** PR #91 的 CI run（41198577862）測的是 GitHub 的 merge commit b8c085e1（baa4ed76 併入 f9cd90c1，已含 #86），和 main 的 dc8a6ccc 是**同一棵 tree**（`22a8dd49`）。同一棵 tree 一次通過、一次失敗，所以是跟負載有關的間歇失敗，不是 #86 的回歸。
- **真正原因：graph 操作逾時。** `ExtractGraphContextNode` 用 `graph_operation_timeout_ms` 包住 graph 查詢，預設 2424 ms（`engine/src/config.rs:420`）。逾時的話，節點只加一個 `GRAPH_TIMEOUT` notice 然後回 `Ok`，`graph_traversal` span 上的 `graph_augmentation` 永遠不會被 record。查詢仍然以 `NO_EVIDENCE` 成功，所以測試的 `NO_EVIDENCE` assert 通過，下一行 `captured` 是 `[]`，正是 CI 的 `left: [] right: ["attempted_and_failed"]`（src/tests.rs:7580）。4 CPU 的 CI runner 跑整套 lib 時，這個 graph 呼叫（開一個被換成檔案的 `entity_edges.lance`）偶爾超過 2.4 秒。

### 重現

- origin/main cc10774e，本機（12 CPU Windows）：單跑該測試通過；整套 lib `--test-threads=4` 5/5 通過，本機負載不夠讓它逾時。
- **確定性重現**（暫時改動，未 commit）：在該測試把 `graph_operation_timeout_ms` 設成 1 ms：
  ```text
  REPRO93 notices: ["GRAPH_TIMEOUT", "NO_EVIDENCE"]
    left: []
   right: ["attempted_and_failed"]
  ```
  用預設 2424 ms：notices 是 `["GRAPH_DEGRADED", "NO_EVIDENCE"]`，測試通過。和 CI 的失敗完全一樣。
