# Phase 06.1: Code Review Report

**Reviewed:** 2026-08-23T00:00:00Z
**Depth:** standard
**Files Reviewed:** 14
**Status:** issues_found

## Summary

Plan 06.1-01 (index rebuild-and-swap, CorpusStore snapshot isolation) is the substantive delta in this phase. Its BM25-side isolation is implemented correctly: `CorpusSnapshot` is an immutable `Arc`, swapped atomically under a short write-lock, and both the dense and BM25 ports for a given request are built from the same `Arc<CorpusSnapshot>` read once at request admission. That half of the "same-snapshot pinning" claim holds.

The dense-retrieval half does not. The pinning mechanism for the LanceDB `nodes` table relies on `Table::checkout(version)`, which the codebase invokes on a `.clone()` of a single, long-lived `Table` handle shared by every in-flight `QueryRAG` request *and* by the periodic rebuild task. `lancedb::Table` is `#[derive(Clone)]` over `Arc<dyn BaseTable>`; cloning it does not create an independently-versioned handle, it creates a second reference to the same `Arc<Mutex<DatasetState>>` that holds the checked-out version. `checkout()`/`checkout_latest()` therefore mutate state that is shared across every clone, not state private to the caller. This is confirmed against the vendored `lancedb` 0.31.0 source (`src/table.rs`, `src/table/dataset.rs`) and directly contradicts the reasonable assumption a reader would form from the crate's own doc comment on `checkout()` ("Other table instances will not be affected") — that guarantee holds for table instances opened independently (e.g. two calls to `DatabaseManager::nodes_table()`, which is what the new `test_checkout_clone_isolated_from_live_writes` test actually exercises), not for `.clone()`s of one instance.

Plans 06.1-02 (BU-01/BU-02 deterministic proofs) and the Python live-evidence harness changes look correct and are well covered by the added tests; no findings there beyond one minor dead-variable note.

## Critical Issues

### CR-01: `rebuild_and_swap` un-pins every concurrently in-flight query's checked-out version

**File:** `engine/src/ingest.rs:1454-1459`
**Issue:**
```rust
let nodes_latest = nodes.clone();
let _ = nodes_latest.checkout_latest().await;
let nodes_version = nodes_latest
    .version()
    .await
    .map_err(|err| format!("failed to read nodes table version: {err}"))?;
```
`nodes` here is the single `Table` value constructed once in `main.rs` (`database.nodes_table().await?`) and shared, via `.clone()`, with `LancetServiceImpl.nodes` (`main.rs:131-142`) and every `ProductionDenseRetrievalPort` built per request (`service.rs:82-88`). Because `Table::clone()` shares the underlying `Arc<Mutex<DatasetState>>` (verified in `lancedb-0.31.0/src/table.rs:727-732` and `src/table/dataset.rs:18-26`), `checkout_latest()` here does not create a private "latest" view for the rebuild task — it resets `pinned_version` to `None` on the *same* shared state that a concurrent request may have just pinned to an older version via `ProductionDenseRetrievalPort::retrieve_dense` (`service.rs:533-539`). Neither `checkout()` (via `as_time_travel`, `dataset.rs`) nor `get()` (`dataset.rs:111-117`) holds the shared mutex across an `.await` point — each acquires it, reads or writes `pinned_version`, and releases it immediately. There is therefore no mutual exclusion between one task's `checkout(v)` and a concurrent task's dataset read inside `DenseRetriever::query` (`engine/src/retrieval/dense.rs`): on a multi-threaded Tokio runtime (the default `#[tokio::main]` scheduler used in `main.rs`), two requests' calls into this shared state can interleave on different OS threads at any point, so a request pinned to `v` can observe whichever version last won the race, not `v`. This directly defeats the "same-snapshot pinning" guarantee this plan sets out to deliver, and it fires on every rebuild-and-swap cycle while any query is in flight, not just under contrived timing.

The `let _ =` also discards any error from `checkout_latest()` outright: if it fails for an unrelated transient reason, the function proceeds to read `.version()` and build the BM25 index from whatever version happens to be currently pinned (possibly stale, possibly the value another concurrent caller most recently checked out), and reports the rebuild as fully successful (`rebuild_degraded: false`) rather than failing closed.

**Fix:** Do not share a stateful `Table` handle across the request/rebuild boundary. `LancetServiceImpl` already holds `pub database: DatabaseManager`; have `rebuild_and_swap` (and `spawn_rebuild_debounce_task`) take `&DatabaseManager` and open an independent handle per rebuild:
```rust
pub async fn rebuild_and_swap(
    database: &DatabaseManager,
    corpus_store: &CorpusStore,
    bm25_settings: Bm25Config,
) -> Result<Arc<CorpusSnapshot>, String> {
    let nodes_latest = database.nodes_table().await.map_err(|e| e.to_string())?;
    // nodes_latest is now a genuinely independent Table instance (own Arc<Mutex<DatasetState>>),
    // so checkout_latest() here cannot affect any other in-flight handle.
    let nodes_version = nodes_latest.version().await.map_err(|err| ...)?;
    ...
}
```
and propagate the `checkout_latest()` error instead of discarding it (`.map_err(...)?` rather than `let _ =`).

### CR-02: Per-request dense-retrieval snapshot pinning races against concurrent checkouts on the same shared `Table`

**File:** `engine/src/service.rs:82-88`, `engine/src/service.rs:499-540`
**Issue:** `build_production_workflow` constructs `ProductionDenseRetrievalPort { nodes: self.nodes.clone(), nodes_version: snapshot.nodes_version, ... }` for every `QueryRAG` request, cloning `LancetServiceImpl.nodes` — the same shared `Table` described in CR-01. Inside `retrieve_dense`:
```rust
let nodes = self.nodes.clone();
nodes.checkout(self.nodes_version).await.map_err(...)?;
let dense_retriever = DenseRetriever::new(nodes);
dense_retriever.query(query_embedding, &query_req, &self.retrieval_settings).await...
```
Two concurrent `QueryRAG` requests that read `corpus_store` on either side of a `rebuild_and_swap` (a routine occurrence — the whole point of the debounced rebuild is to run while queries are being served) will hold different `nodes_version` values but call `checkout()` on clones sharing one mutable pinned-version cell. Whichever request's `checkout()` call is most recent when the *other* request's query actually executes wins for both. This means dense-retrieval results for a request can silently be drawn from a different LanceDB version than the one recorded in that request's own `RetrievalSnapshot.index_generation` (`workflow/nodes/retrieve.rs:230-242`), and than the BM25 candidates fused alongside it in the same request — the opposite of the "unified CorpusSnapshot makes cross-generation mixing unreachable" property asserted in `workflow_phase5.rs`'s notice-reachability rationale table.

**Fix:** Same root fix as CR-01 — do not hold a long-lived shared `Table` for dense retrieval. Give `ProductionDenseRetrievalPort` a `database: DatabaseManager` handle and open a fresh `Table` per query before calling `checkout`:
```rust
pub struct ProductionDenseRetrievalPort {
    pub database: DatabaseManager,
    pub nodes_version: u64,
    pub retrieval_settings: retrieval::RetrievalSettings,
}
// in retrieve_dense:
let nodes = self.database.nodes_table().await.map_err(|err| NodeError::new(..., err))?;
nodes.checkout(self.nodes_version).await.map_err(...)?;
```
This is the same pattern the passing `test_checkout_clone_isolated_from_live_writes` test (`engine/src/tests.rs:7706`) already validates — it works precisely because that test compares two independently-opened `Table`s, not two clones of one.

Note this field-shape change also touches this phase's own `retrieve_dense_on_freshly_initialized_table_does_not_panic` test (`engine/src/tests.rs:563-591`, added by 06.1-01), which constructs `ProductionDenseRetrievalPort { nodes: nodes_pinned, nodes_version, retrieval_settings }` directly — that call site will need updating to pass a `DatabaseManager` instead of a pre-checked-out `Table` clone.

## Warnings

### WR-01: New "atomicity"/"isolation" tests do not exercise the shared-checkout race, creating false confidence

**File:** `engine/src/tests.rs:8045` (`rebuild_swap_generation_atomicity`), `engine/src/tests.rs:7706` (`test_checkout_clone_isolated_from_live_writes`)
**Issue:** `rebuild_swap_generation_atomicity` spawns 10 concurrent workflow queries against `s.build_production_workflow(snapshot.clone())` alongside a concurrent `rebuild_and_swap`, but its only assertion per task is `assert!(ret_snap.index_generation.starts_with("lance-"))`. `index_generation` is a string the `RetrieveHybridNode` was constructed with (`snapshot.generation.clone()` at construction time, `retrieve.rs:230-242`) — it is never cross-checked against what the dense port actually scanned, so this test would pass unchanged even if CR-01/CR-02 silently mixed versions. `test_checkout_clone_isolated_from_live_writes` genuinely proves isolation, but only between two independently-opened `Table`s (`database.nodes_table()` called twice), which is not the code path production traffic exercises (`service.rs` clones one shared handle). Neither test would fail under the race described in CR-01/CR-02.
**Fix:** Add a test that clones one `Table`, checks it out to version A, and — before the pinned clone's query executes — checks out a second clone (sharing the same underlying handle) to version B; assert whether the first clone's subsequent query still observes version A. Given the current implementation this should fail, and is the regression test CR-01/CR-02's fix should be validated against.

### WR-02: `rebuild_and_swap` swallows `checkout_latest()` failures independent of the shared-state issue

**File:** `engine/src/ingest.rs:1455`
**Issue:** `let _ = nodes_latest.checkout_latest().await;` discards the `Result` unconditionally. Even after fixing CR-01 by opening an independent `Table` per rebuild, a genuine I/O failure here would still be silently ignored, and the function would proceed to build a "successful" (non-degraded) BM25 snapshot from whatever version the table happens to be pinned to (its just-opened default, if this is otherwise addressed as part of CR-01) rather than the actual latest version, without emitting the `IndexRebuildFailed` degraded-notice path that this plan otherwise correctly wires up for the `Bm25Index::from_table` failure branch two lines below.
**Fix:** Treat a `checkout_latest()` failure the same as the `Bm25Index::from_table` failure arm two lines below (`ingest.rs:1462-1479`) — actually take the degraded-snapshot branch, not just log and continue:
```rust
if let Err(err) = nodes_latest.checkout_latest().await {
    tracing::error!("nodes checkout_latest failed during rebuild: {err}");
    let prior = { let guard = corpus_store.read().await; Arc::clone(&*guard) };
    let degraded_snapshot = Arc::new(crate::workflow::ports::CorpusSnapshot {
        bm25: Arc::clone(&prior.bm25),
        generation: prior.generation.clone(),
        nodes_version: prior.nodes_version,
        rebuild_degraded: true,
    });
    let mut write_guard = corpus_store.write().await;
    *write_guard = degraded_snapshot;
    return Err(format!("nodes checkout_latest failed during rebuild: {err}"));
}
```
A fix that only logs and falls through (as `let _ =` already effectively does) does not address this finding.
