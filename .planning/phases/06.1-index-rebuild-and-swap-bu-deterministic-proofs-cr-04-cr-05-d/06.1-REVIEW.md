## Summary

This is a re-review of `engine/src/ingest.rs`, `engine/src/main.rs`, `engine/src/service.rs`,
`engine/src/tests.rs`, and `scripts/engine-test-targets.sh` after gap-closure commit `6d1273d`
("feat(06.1-04): isolate Table checkout handles and propagate checkout_latest failure to
degraded snapshot"). I read every file in full, diffed the gap-closure commit in isolation
(`git show 6d1273d -- <files>`) to separate what actually changed from pre-existing code, traced
`DatabaseManager::nodes_table()`/`open_table()` in `engine/src/db/mod.rs` to confirm each call
returns an independently-constructed `lancedb::Table` (not a `.clone()` of a cached handle), read
the gap-closure plan's `must_haves`/acceptance criteria (`06.1-04-PLAN.md`) to scope what this
specific commit committed to, and ran the actual test suite rather than trusting that tests exist:
the full `engine` lib suite (369 passed / 1 ignored / 0 failed), the 5 tests specific to this
gap-closure plan individually, and `scripts/engine-test-targets.sh` itself (all 7 invariants
green, 407 total).

**All four carried-over findings (CR-01, CR-02, WR-01, WR-02) are closed as scoped by the plan**,
verified by ID below. No new BLOCKER/critical issues were introduced by the fix. Three
WARNING-level issues were found: two adjacent failure exits inside `rebuild_and_swap` that still
bypass the degraded-snapshot path the same way the original WR-02 bug did (the plan explicitly
scoped WR-02/SC4 to the `checkout_latest` failure only, so this isn't a broken acceptance
criterion, but it is the same failure class left open two call sites away); a vestigial `Table`
field left on `LancetServiceImpl` that reintroduces the shared-handle shape the fix was meant to
eliminate; and a test-flakiness risk from three pieces of global mutable state (two `AtomicBool`
fault-injection flags plus an `AtomicUsize` invocation counter) shared across concurrently-run
`#[tokio::test]` functions that all call the same `rebuild_and_swap` function.

## Verification of Prior Findings (by ID)

**CR-01 (critical, `rebuild_and_swap` shared-checkout race) — CLOSED.**
`rebuild_and_swap` (`engine/src/ingest.rs:1441`) no longer takes `nodes: &Table` and no longer
calls `.clone()` on a long-lived handle. It now takes `database: &DatabaseManager` and calls
`database.nodes_table().await` (line 1468-1471) to obtain a table handle that is opened fresh —
`DatabaseManager::nodes_table()` (`engine/src/db/mod.rs:128-134`) calls
`self.connection.open_table("nodes").execute().await` on every invocation, which is a brand-new
`Table` object, not a cache lookup or a clone of a stored handle. `spawn_rebuild_debounce_task`
(`engine/src/ingest.rs:1548`) was updated correspondingly to take `database: DatabaseManager`
instead of `nodes: Table`, and `main.rs:99-106` passes `database.clone()` (a cheap
`Connection`-wrapping clone, not a `Table` clone) instead of `nodes.clone()`. Proven by test
`independent_nodes_table_checkout_stays_isolated` (`engine/src/tests.rs:7763-7811`), which opens
two independent `nodes_table()` handles, pins one to version 1 and the other to latest, and
asserts the first retains version 1 — this test passes (`cargo test ... independent_nodes_table_checkout_stays_isolated` → ok).

**CR-02 (critical, `ProductionDenseRetrievalPort::retrieve_dense` shared-checkout race) — CLOSED.**
`ProductionDenseRetrievalPort` (`engine/src/service.rs:500-504`) now holds `database:
DatabaseManager` instead of `nodes: Table`. `retrieve_dense` (line 532) calls `self.database
.nodes_table().await` to open a fresh table per call, then checks it out to `self.nodes_version`
(line 538) — the same independent-handle guarantee as CR-01. `build_production_workflow`
(`engine/src/service.rs:82-87`) constructs the port with `database: self.database.clone()`
instead of `nodes: self.nodes.clone()`. Companion demonstrator test
`shared_table_clone_checkout_mutates_sibling_pin` (`engine/src/tests.rs:7710-7761`) proves the
underlying vulnerability class is real for `Table::clone()` (two clones of one `Table` share the
`pinned_version` cell — checking out one clobbers the other's observed version), and
`independent_nodes_table_checkout_stays_isolated` proves the fixed pattern (`nodes_table()` called
twice) does not exhibit that coupling. Both tests pass.

**WR-01 (warning, no regression test proving isolation) — CLOSED.**
Both tests above were added by this gap-closure plan (new in commit `6d1273d`, confirmed via `git
show 6d1273d -- engine/src/tests.rs`) and both pass under the real test suite run. This is not a
tautological pair — `shared_table_clone_checkout_mutates_sibling_pin` demonstrates the failure
mode would exist if the code still used `.clone()`, and `independent_nodes_table_checkout_stays_isolated`
proves the actual fixed code path does not exhibit it. `scripts/engine-test-targets.sh`'s lib test
count invariant was bumped from 367 to 370 to account for these two tests plus one more (see
WR-02), and the script's own assertions pass against the current code (`LIB_COUNT: 370`,
`TOTAL: 407`, verified by running the script directly).

**WR-02 (warning, `checkout_latest()` error discarded via `let _ = ...`) — CLOSED, as scoped by
this plan.** `rebuild_and_swap` (`engine/src/ingest.rs:1473-1499`) now captures `checkout_res`
and, on `Err`, logs the error, builds a `CorpusSnapshot` with `rebuild_degraded: true` carrying
forward the prior snapshot's `bm25`/`generation`/`nodes_version`, swaps it into `corpus_store`
under a write lock, and returns `Err(...)` — it no longer silently discards *this specific*
failure and reports success. Proven by new test `rebuild_checkout_latest_failure_degrades_not_fails`
(`engine/src/tests.rs:8056-8141`), which arms a `#[cfg(test)]`-only checkout-failure injection hook
(`REBUILD_CHECKOUT_FAIL_NEXT`), asserts the call returns `Err`, asserts `rebuild_degraded` is set
and the prior generation/version/`Arc`-identical `bm25` are preserved, asserts a downstream
`RetrieveHybridNode` run emits an `INDEX_REBUILD_FAILED` warning notice, and asserts a subsequent
successful rebuild clears the degraded flag. This test passes. **Caveat:** the plan
(`06.1-04-PLAN.md` must_haves SC4, Task 2 acceptance criteria) explicitly scoped this fix to the
`checkout_latest` failure only, mirroring the pre-existing `Bm25Index::from_table` degrade arm —
it did not commit to covering every failure exit inside `rebuild_and_swap`. Two other exits in the
same function still discard their error without degrading; see WR-05 below, which is a new finding
in the same class, not a re-opening of WR-02 against its own stated scope.

## Narrative Findings (AI reviewer)

### WR-05: Two more failure exits in `rebuild_and_swap` bypass the degraded-snapshot path — the same defect class as WR-02, left open at two adjacent call sites

**File:** `engine/src/ingest.rs:1468-1471` (`database.nodes_table()` open failure);
`engine/src/ingest.rs:1501-1504` (`nodes_latest.version()` failure)
**Issue:** `rebuild_and_swap` has four distinct failure points. Two of them (`checkout_latest()`
and `Bm25Index::from_table()`) correctly route through the degrade-and-swap block: log at error
level, retain the prior snapshot with `rebuild_degraded: true`, return `Err`. The other two use a
bare `?`:
```rust
let nodes_latest = database
    .nodes_table()
    .await
    .map_err(|err| format!("failed to open nodes table: {err}"))?;   // no degrade, no tracing::error!
...
let nodes_version = nodes_latest
    .version()
    .await
    .map_err(|err| format!("failed to read nodes table version: {err}"))?;  // no degrade, no tracing::error!
```
If either of these fails (e.g. a transient LanceDB manifest read error, disk I/O failure, or a
version read racing a concurrent compaction), `rebuild_and_swap` returns `Err` without touching
`corpus_store` at all and without a `tracing::error!` call. The sole production caller,
`spawn_rebuild_debounce_task` (`engine/src/ingest.rs:1601`), does `let _ =
rebuild_and_swap(&database, &corpus_store, bm25_settings.clone()).await;` — it discards the
`Result` outright. So on either of these two failure modes: `rebuild_degraded` stays at its
previous value (typically `false`), no `INDEX_REBUILD_FAILED` notice is ever surfaced to a query
via `RetrieveHybridNode`, nothing is logged, and the only observable symptom is that the corpus
silently stops advancing to newer ingested content — this is exactly the failure signature WR-02
described for `checkout_latest`, just triggered by a different LanceDB call inside the same
function. This is not a violation of the 06.1-04 plan's stated acceptance criteria (Task 2 scoped
the fix narrowly to the `checkout_latest` Err arm), so it is filed as a new warning rather than a
re-opened WR-02, but it is the same defect shape and worth closing in the same pass that already
built the degrade-block plumbing for the other two exits.
**Fix:** Route both of these `?` sites through the same degrade-and-swap helper proposed in IN-01
(read prior snapshot, build `CorpusSnapshot { rebuild_degraded: true, .. }`, write-swap, return
`Err`), with a `tracing::error!` call matching the other two arms, so all four failure exits in
`rebuild_and_swap` behave identically.

### WR-03: `LancetServiceImpl.nodes: Table` is a vestigial long-lived handle that reintroduces the exact shape CR-01/CR-02 eliminated

**File:** `engine/src/service.rs:51` (field declaration); `engine/src/main.rs:30-31,135` (construction)
**Issue:** The gap-closure plan removed every *production* use of a stored, cloneable `Table`
handle for dense retrieval and rebuild (`ProductionDenseRetrievalPort` and `rebuild_and_swap` both
now open fresh tables via `DatabaseManager`). However, `LancetServiceImpl` still declares `pub
nodes: Table` (`service.rs:51`), and `main.rs` still opens it once at startup
(`let nodes = database.nodes_table().await?;`, line 30) and stores it on the service
(`main.rs:135`). Grepping the whole crate confirms this field is never read by any production code
path — `ProductionDenseRetrievalPort` and `rebuild_and_swap` both use `self.database`/`database`
now, not `self.nodes`. Its only surviving reader is a test helper
(`engine/src/tests.rs:3979`, `DenseRetriever::new(service.nodes.clone())`), and because
`LancetServiceImpl` derives `Clone` and tonic clones the service per request, this stale `Table`
handle gets cloned on every RPC for no purpose. Because it is a `pub` field on a `pub` struct, the
Rust compiler's `dead_code` lint does not flag it as unused — nothing will warn a future
maintainer away from reaching for `self.nodes.checkout(...)` (which is precisely how CR-01/CR-02
were introduced in the first place) instead of the now-correct `self.database.nodes_table().await`
pattern. (Note: the 06.1-04 plan's own task description explicitly permits this — "LancetServiceImpl.nodes
may remain for non-checkout consumers" — so this is filed as a maintainability warning, not a
deviation from plan.)
**Fix:** Remove the `nodes: Table` field from `LancetServiceImpl` and the corresponding
construction in `main.rs`/`configured_service`/`reranker_query_fixture` test helpers; have the one
remaining test that needs an unpinned nodes handle call `database.nodes_table().await` directly
instead of reading it off the service struct. If a transitional reason exists to keep it, mark it
`#[cfg(test)]`-only or document inline why production code must not read it.

### WR-04: Three pieces of global mutable test state create cross-test flakiness risk for `rebuild_and_swap`'s own regression suite

**File:** `engine/src/ingest.rs:1394-1399` (`REBUILD_COUNTER`), `1405-1417` (`REBUILD_FAIL_NEXT`),
`1419-1431` (`REBUILD_CHECKOUT_FAIL_NEXT`); consumed at `engine/src/tests.rs:8005`, `8082`, `8163-8189`
**Issue:** `REBUILD_CHECKOUT_FAIL_NEXT` (new in this gap-closure commit) follows the same pattern
as the pre-existing `REBUILD_FAIL_NEXT`: a single process-wide `static AtomicBool`, armed with
`.store(true, ...)` in one test and consumed with a one-shot `.swap(false, ...)` inside
`rebuild_and_swap`. A third piece of global state, `REBUILD_COUNTER` (a `static AtomicUsize`,
pre-existing), is incremented unconditionally on every `rebuild_and_swap` call and is used for an
exact-count assertion in `debounce_coalesces_burst` (`engine/src/tests.rs:8163-8189`):
`reset_rebuild_invocation_count()`, then, after a ~560ms window (5×10ms sends plus a 350ms settle
sleep), `assert_eq!(rebuild_invocation_count(), 1, "burst of 5 notifications must coalesce into
exactly 1 rebuild")`. `rebuild_and_swap` itself is called from at least five different
`#[tokio::test]` functions (`test_rebuild_swap_updates_generation_label`,
`rebuild_failure_degrades_not_fails`, `rebuild_checkout_latest_failure_degrades_not_fails`,
`rebuild_swap_generation_atomicity`, and indirectly via `spawn_rebuild_debounce_task` in
`debounce_coalesces_burst`/`debounce_task_terminates_on_shutdown_signal`). Neither this crate nor
the workspace configures `cargo test` with `--test-threads=1`, and no `serial_test`-style
annotation exists anywhere in `tests.rs` (confirmed by grep) — so by default `cargo test` runs
these functions concurrently on separate OS threads. Two concrete failure shapes follow:
1. If `rebuild_checkout_latest_failure_degrades_not_fails` arms `REBUILD_CHECKOUT_FAIL_NEXT`
   (`tests.rs:8082`) at the same moment another concurrently-scheduled test's `rebuild_and_swap`
   call races in and consumes the flag via `.swap(false, ...)` first, the arming test's own
   subsequent call sees no injected failure and `assert!(res.is_err(), ...)` (`tests.rs:8090`)
   fails spuriously — or the innocent concurrent test gets an unexpected `Err`/degraded snapshot
   it never asked for and one of *its* assertions fails instead.
2. `debounce_coalesces_burst`'s 560ms window is wide open to any other concurrently-scheduled test
   calling `rebuild_and_swap` during that time — each such call increments the same
   `REBUILD_COUNTER`, which would make `assert_eq!(rebuild_invocation_count(), 1, ...)` fail even
   though the coalescing logic under test behaved correctly.
A full local run of the suite passed cleanly in this review (369 passed / 1 ignored), so none of
this is a reproduced failure — it is a structural hazard that can manifest intermittently under
different scheduling, machine load, or thread counts (e.g., in CI), and it directly undermines
confidence in the tests that are supposed to prove CR-01/CR-02/WR-01/WR-02/SC4 stay fixed.
**Fix:** Scope the fault-injection flags and the invocation counter to the calling test instead of
process-global state — e.g. thread an injectable fault hook and a counter through
`rebuild_and_swap` (an `Option<&dyn Fn() -> bool>` parameter or a `#[cfg(test)]`-only struct passed
per-call) rather than `static`s, or gate all `rebuild_and_swap`-calling tests with a shared
`Mutex`/`serial_test::serial` guard so they cannot interleave with one another.

### IN-01: Duplicated degraded-snapshot construction in `rebuild_and_swap`

**File:** `engine/src/ingest.rs:1448-1466`, `1484-1499`, `1509-1524`
**Issue:** The same ~14-line pattern (read `prior` snapshot under a read lock, build a new
`CorpusSnapshot` with `rebuild_degraded: true` carrying forward `prior.bm25` /
`prior.generation` / `prior.nodes_version`, swap it in under a write lock) is written out three
separate times in `rebuild_and_swap`: once for the `#[cfg(test)]` injected-failure branch, once
for the `checkout_latest()` failure branch, and once for the BM25-rebuild-failure branch (and
would become four with WR-05's fix). Independent copies of the same invariant-preserving logic
increase the chance that a future edit to one branch (e.g. adding a new `CorpusSnapshot` field) is
applied to only some of the copies.
**Fix:** Extract a small helper, e.g. `async fn degrade_snapshot(corpus_store: &CorpusStore) ->
Arc<CorpusSnapshot>`, that performs the read-prior/build-degraded/write-swap sequence once, and
call it from all failure branches (see also WR-05).

### IN-02: `scripts/engine-test-targets.sh` hardcodes a developer-specific cargo path

**File:** `scripts/engine-test-targets.sh:7`
**Issue:** The `cargo` discovery fallback hardcodes `/mnt/c/Users/user3/.cargo/bin` and
`/c/Users/user3/.cargo/bin`. This is pre-existing (unchanged by the 06.1-04 gap-closure commit —
only the numeric test-count assertions in this file were touched), but since the file is in this
review's scope: it only works on this one developer's machine/username and silently falls through
(via the `command -v cargo.exe` check afterward) rather than failing with an explicit "cargo not
found" message on any other machine or CI runner where cargo isn't already on `PATH`.
**Fix:** Drop the hardcoded username path, or derive it from `$USERPROFILE`/`$USER` instead of a
literal `user3`, and add an explicit error message if `cargo`/`cargo.exe` still cannot be located
after the fallback.
