## Plan 06.1-01 — Index rebuild-and-swap

### Summary

The plan's architectural instinct (bundle BM25 + generation + LanceDB version into one atomically-swapped `CorpusSnapshot`) is correct and reuses a proven primitive (`ports.rs:13`, `Bm25IndexStore = Arc<RwLock<Arc<Bm25Index>>>`). But three defects, all independently verified against the current source, would let this plan's own tests pass while the phase goal (DEBT-RAG-04's "no mixed evidence") stays unmet.

### Strengths

- **Startup fail-closed is already correct and needs no new code.** `main.rs:28-31`: `Bm25Index::from_table(&nodes, ...).await.map_err(...)?` propagates out of `async fn main`, and `engine/tests/config_startup.rs:339-395` (`initial_bm25_failure_blocks_readiness`) already proves nonzero exit + no readiness line. Task 1's plan to treat this as regression-only is correct.
- **The fail-closed config template exists and is copy-ready.** `config.rs:652-664` (`ALLOW_MODEL_ONLY_ANSWERS`) is a genuinely different code shape from the silent-ignore pattern at `config.rs:642-645` (`PROMPT_TIMEOUT_MS`) — verified both blocks exist as described. `engine/tests/config_startup.rs:678-722` is the exact integration-test template to copy for the new debounce key.
- **`Table::checkout` precedent for the rollback direction is real** (`ingest.rs:532-541`, `restore_version`), giving the dense-pinning design a concrete API shape to imitate, even though the *usage* (checkout on a shared handle then restore) is the opposite of what read-pinning needs (checkout on a clone, never restore).

### Concerns

- **CRITICAL — D-26's proposed generation source (`staged_documents` MAX) is empty in steady state.** I verified this directly: `ingest.rs:814-816` deletes the staging row inside `replace_document_with_faults` after a successful add, and `:649-653` deletes it on the empty-chunk branch too. There is no code path that leaves a row behind after `Completed`. A corpus-wide `MAX(generation)` scan of that table therefore returns `None` on any healthy corpus, which the plan's own fallback rule (`"gen-0" when None`) turns into a *constant* label across every rebuild and every restart. Every downstream proof that depends on the generation being discriminating — the D-21 "exactly one generation" test, the D-24 "dense and BM25 share the same generation" test — becomes a comparison of `"gen-0"` against `"gen-0"` and proves nothing. This is a **must-fix-before-Task-1** issue: `nodes.version(): u64` (already available via `Table::version()`, used elsewhere in this file at `ingest.rs:610`) is the durable, restart-surviving, monotonic replacement that actually satisfies D-26's *intent* ("derived at startup from persisted LanceDB state... no stored counter") even though it departs from D-26's literal "staging generation" wording.

- **HIGH — The query path as specified still mixes generations, contradicting the plan's own D-24 prohibition.** I verified `ProductionBm25RetrievalPort::retrieve_bm25` (`service.rs:543-588`) re-reads the live `Bm25IndexStore` on *every call* (`:573-576`: `let guard = self.bm25_index.read().await; Arc::clone(&*guard)`), not a value captured once per query. If Task 1 pins `ProductionDenseRetrievalPort` to a fixed `nodes_version` at query start but leaves BM25 retrieval reading whatever is live at call time, a swap landing between dense construction and the BM25 call produces exactly the mixed-generation candidate set DEBT-RAG-04 exists to prevent — while `RetrievalSnapshot.index_generation` (a single string stamped from one source, `retrieve.rs:216`) reports only one of the two real sources. The fix requires constructing `ProductionBm25RetrievalPort` with the specific `Arc<Bm25Index>` from the same `CorpusSnapshot` used for the dense checkout version, not with a live view of the store.

- **HIGH — `build_production_workflow` is synchronous; the plan never resolves how it reads an async `RwLock`.** Verified: `pub fn build_production_workflow(&self) -> (...)` at `service.rs:69` has no `async` keyword, and `Bm25IndexStore`/the proposed `CorpusStore` both use `tokio::sync::RwLock` (`ports.rs:1-2`), whose `.read()` returns a future that must be awaited from an async context. `query_rag` (`service.rs:826`) calls `self.build_production_workflow()` without `.await` today, and this function is also called from many `cfg(test)` sites. Neither task text specifies capturing the `Arc<CorpusSnapshot>` in the async caller before invoking the (still-sync) builder, converting the builder to `async fn`, or switching to `std::sync::RwLock`. Without one of these, this either fails to compile or an executor reaches for `.blocking_read()` inside a Tokio worker thread, which is its own hazard.

- **MEDIUM — Degraded-notice lifecycle is entirely unspecified.** Verified `RetrieveHybridNode` (`retrieve.rs:14-48`) carries only two `String` fields (`index_generation`, `embedding_model`) with no degraded flag or constructor parameter. Task 2's plan text says a "degraded indicator" lets `RetrieveHybridNode` emit `IndexRebuildFailed`, but no field, no constructor change, and — critically — no clear-on-success rule is named anywhere in the plan. Without an explicit clear rule, one transient rebuild failure silently marks every subsequent query as degraded forever, which is a worse UX than the fail-closed alternative it's replacing.

- **MEDIUM — Two sources of truth for "the generation" survive side by side.** Verified `config.rs:452-454`: `new_index_generation() -> format!("gen-{}", Uuid::new_v4())`, consumed at `config.rs:511` into `EffectiveRagSettings.index_generation`, and validated non-empty at `:564-566`. `config.rs` is not in Task 1's `files` list. If this field isn't retired (or at minimum documented as dead on the query path), a reader of the codebase finds two plausible "the generation" values, one a random per-process UUID that D-26 explicitly forbids ("no second source of truth").

- **MEDIUM (corroborating, not independently re-verified) — the notice-manifest test cannot fail.** Both prior reviews cite `workflow_phase5.rs:3758-3773`/`:3766-3773` asserting only `!rationale.is_empty()`. I did not read that file directly this pass, but the citation is specific and consistent across two independent reviewers, and it matches the general pattern in this codebase (`retrieve.rs:87-91`, `:231-235`) of centralizing notice construction through one `notice()` helper — I'd flag this as **very likely correct** rather than fully independently confirmed.

- **LOW — Construction ordering in `main.rs` isn't addressed.** Verified `main.rs:67-74` spawns the ingestion worker *before* `LancetServiceImpl` is constructed at `:99-110`. If `CorpusStore` is meant to be shared between the worker's rebuild trigger and the service's query path, the plan needs to say explicitly that `CorpusStore` construction moves before `spawn_worker`, since today nothing exists yet for the worker to notify.

### Suggestions

- Add a Task 0 (or fold into Task 1, before any test is written): derive the corpus generation from `nodes.version()`, not `staged_documents`. Record this as a documented, deliberate departure from D-26's literal wording — its *intent* is fully preserved.
- Construct `ProductionBm25RetrievalPort` with the `Arc<Bm25Index>` pulled from the *same* `CorpusSnapshot` Arc used for the dense `nodes_version` checkout, per query — not a live view of the shared store.
- Decide explicitly (and state in the plan) whether `build_production_workflow` becomes `async fn`, or whether `query_rag` captures the snapshot before calling it. Add a unit test proving no `.await` is attempted inside a sync fn.
- Add a `rebuild_degraded: bool` (or similar) to whatever carries snapshot metadata into `RetrieveHybridNode`, with an explicit test proving it clears on the next successful rebuild.

### Risk Assessment

**HIGH.** Three of the plan's own load-bearing claims (discriminating generation, single-source BM25+dense pinning, sync/async correctness) are currently false against the codebase as read. All three are cheaply fixable in planning, but if executed as written the plan can complete "green" while none of D-21/D-24's actual guarantees hold.

### Concerns

- **CRITICAL — the plan's own BU-01 timestamps trip the wrong check first.** I traced this directly: `validate_evidence` calls `validate_challenge(challenge, now=now)` at `:336`, *before* the run-window `require` at `:376`. `validate_challenge:292` requires `current - issued_at <= MAX_CHALLENGE_AGE` where `MAX_CHALLENGE_AGE = 30min` (`:130`). With `issued_at = 00:00`, `generated_at = 00:36`, `now = 00:40` (the fixture named in the plan's `must_haves` and in `06.1-VALIDATION.md`'s test description), `now - issued_at = 40min > 30min` — the function raises `"challenge.issued_at is stale"` before ever reaching line 376, and `assertRaisesRegex(..., r"^complete run window exceeded$")` fails. Since `MAX_RUN_WINDOW` (35min) is strictly larger than `MAX_CHALLENGE_AGE` (30min), and `generated_at - issued_at` must exceed 35min to exercise the target branch, `now` (which must be `>= generated_at`) is *arithmetically forced* past the 30-minute challenge-staleness bound whenever `issued_at` is the only free variable held near "now". This isn't a minor off-by-a-few-minutes bug — it needs a genuinely different fixture shape (e.g., a challenge `issued_at` far enough in the past that challenge staleness would already fire on its own, deliberately establishing that the run-window check is reached only via a controlled `now` that stays within 30 minutes of `generated_at` — meaning `issued_at` must be set close to the *outer* edge of what's still valid, not simply "36 minutes before generated_at" as a standalone construction).

- **HIGH — Task 2's success and post-upload-failure scenarios cannot be reached by a loopback HTTP mock alone.** I traced the full gate sequence in `verify-ingestion.sh`: `OPENROUTER_API_KEY` non-empty (`:86`), challenge file must equal the exact phase-local path `${phase_dir}/.02-LIVE-CHALLENGE.json` (`:80-82`, enforced by string equality, not just existence) — and that exact path is one of two paths `assert_not_real_runtime_path` (`test_phase02_live_evidence.py:35-38`) explicitly forbids test code from writing to. Even past that, success requires `docker compose exec ... psql` (`:167`) and `cargo run ... inspect_lancedb` (`:168`) — neither of which a Python `http.server` substitutes for. A mock gateway alone gets nowhere near the upload call at `:154`.

- **MEDIUM — mock JSON schema doesn't match what the script actually reads.** Verified directly from `verify-ingestion.sh` itself (not from the Go source): `:155` reads `json.load(sys.stdin)["ID"]`, `:159` reads `["Status"]`, `:166` reads `["ChunkCount"]` — capitalized keys, not `job_id`/`status`. And `sample_file` is a bare positional argument (`:72`: `*) sample_file="$1"; shift ;;`), not a `--sample` flag. Any mock built around `job_id`/`status`/`--sample` will not integrate with the real script even where the live-service gates are bypassed.

- **LOW — `phase02_live_evidence.py` doesn't need the change `files_modified` implies.** The `now=` parameter already exists and is unused by any test today; listing this file as modified risks an executor "helpfully" adding a second clock mechanism.

### Suggestions

- Rework the BU-01 fixture so `validate_challenge`'s staleness check and the target run-window check don't compete for the same `now`. One approach: keep `issued_at` recent enough that `now - issued_at` stays under 30 minutes, while making `run_started_at`/`generated_at` violate the 35-minute *run* window relative to `issued_at` — this requires `generated_at - issued_at > 35min` while `now - issued_at <= 30min`, which is only possible if `now < generated_at`... but `validate_evidence` also requires `generated_at <= now` (implicitly via `MAX_EVIDENCE_AGE`, `:374-375`). Given the fixed 30/35-minute constants, this is genuinely tight — the plan should verify a concrete satisfying tuple exists before committing to specific timestamps, and if none does, treat "challenge staleness shadows the run-window check for large excesses" as a documented finding rather than silently picking a fixture that happens to work.
- For BU-02, do not attempt to drive `verify-ingestion.sh` end-to-end for success/post-upload scenarios. Extract the `sample_owned` cleanup semantics into a small, directly-testable shell function or standalone harness script and exercise three terminal outcomes against *that*, matching 06.1-RESEARCH.md's own Assumption A4 fallback.
- Keep `test_caller_sample_preservation_on_early_failure` unmodified and add siblings rather than combining/replacing it.

### Risk Assessment

**HIGH for Task 2, MEDIUM-HIGH for Task 1** — Task 1's headline fixture as specified will not pass and needs real arithmetic work, not a cosmetic timestamp tweak. Task 2 as specified cannot be implemented against the real gating script. Neither risks production code, so blast radius is confined to this phase's closure claim for DEBT-BU-01/02.
