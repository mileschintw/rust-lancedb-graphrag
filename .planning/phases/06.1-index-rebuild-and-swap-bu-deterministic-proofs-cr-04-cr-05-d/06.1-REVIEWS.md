# Cross-AI Plan Review — Phase 06.1

## Consensus Summary

Both independent AI reviewers (**Claude** via Opus and **Cursor** via Grok 4.6) completed source-grounded code reviews against the repository at `D:/Repos/lancet`. Both reviewers reached unanimous consensus on critical defects in Plan 01 and Plan 02, alongside factual corrections required for Plan 03. Overall phase risk is classified as **HIGH** due to foundational design gaps in generation derivation, test harness reachability, and concurrency plumbing that would cause green tests to pass without satisfying the underlying safety guarantees.

### Agreed Strengths

- **Plan 01 Atomic Snapshot Architecture:** Reusing `Bm25IndexStore` (`Arc<RwLock<Arc<Bm25Index>>>` at `engine/src/workflow/ports.rs:13`) and wrapping it alongside `nodes_version` and `generation` in an atomic `CorpusSnapshot` is unanimously affirmed as the correct pattern for D-21/D-24.
- **Plan 01 Startup & Config Contracts:** Fail-closed startup on initial BM25 failure (`engine/src/main.rs:28-30`) and fail-closed environment parsing for `LANCET_ENGINE__WORKFLOW__REBUILD_DEBOUNCE_MS` matching `config_startup.rs` conventions are properly recognized and preserved.
- **Plan 02 Direct Evidence Validation Seam:** Invoking `validate_evidence` directly with an injectable `now` parameter (`scripts/phase02_live_evidence.py:332-377`) correctly decouples BU-01 from machine wall-clock time and subprocess shells.
- **Plan 03 Scope & Timeout Facts:** The documented-only boundary (0 production diffs) and the factual audit of `gateway/main.go:702-709` (`ReadTimeout: 60s`, `ReadHeaderTimeout: 10s`, omitted `WriteTimeout`/`IdleTimeout`) accurately reflect shipped reality.

### Agreed Concerns

1. **CRITICAL (Plan 01) — Generation Derivation from `staged_documents` is Vacuous (D-26 Defect):**
   - *Mechanism & Evidence:* `staged_documents` is an ephemeral table emptied after every successful ingestion (`engine/src/ingest.rs:814-816`, `scripts/phase02_live_evidence.py:358`). In steady state, `get_max_corpus_staged_generation` returns `None`, defaulting to constant `"gen-0"`.
   - *Impact:* Generation-stamped assertions (D-21/SC2) and cross-index generation agreement (D-24/SC3) become tautological comparisons (`"gen-0"` vs `"gen-0"`), providing false-positive verification.
   - *Consensus Fix:* Derive corpus generation from persistent, monotonic LanceDB state (`nodes.version(): u64` or `nodes` table metadata), maintaining D-26's "no stored counter" requirement without relying on an empty staging table.

2. **CRITICAL (Plan 02) — BU-01 Timestamp Fixture Shadowed by Challenge Staleness:**
   - *Mechanism & Evidence:* `validate_evidence` invokes `validate_challenge(challenge, now=now)` (`phase02_live_evidence.py:336`) before testing run windows (`:376`). Setting `issued_at = 00:00` and `now = 00:40` triggers `MAX_CHALLENGE_AGE` (30m) staleness on line 292, failing the expected `r"^complete run window exceeded$"` regex assertion.
   - *Consensus Fix:* Re-derive synthetic timestamps using `fixture_pair()` and ensure challenge staleness checks do not shadow the target window validation error.

3. **CRITICAL (Plan 02) — BU-02 Harness Blocked by Live Integration Constraints:**
   - *Mechanism & Evidence:* `verify-ingestion.sh` enforces hard checks for `OPENROUTER_API_KEY` (`:86`), canonical live challenge file existence (`:80-87`), postgres docker execution (`:167`), and cargo inspection (`:168`). A loopback Python `http.server` mock cannot satisfy these gates, and the mock JSON schema (`job_id`/`status` vs `ID`/`Status`) disagrees with gateway handlers (`gateway/main.go:456, 519`).
   - *Consensus Fix:* Adopt the PATH-shim / inspector pattern already established in `test_phase02_live_evidence.py:543-638` or extract a dedicated hermetic harness for sample cleanup testing.

4. **HIGH (Plan 01) — Notice Manifest Verification & Emission Holes:**
   - *Mechanism & Evidence:* `IndexStale` and `IndexGenerationMismatch` have no reachable production triggers under a unified `CorpusSnapshot`. The existing test `test_notice_published_enum_reachability_or_reservation` (`workflow_phase5.rs:3766-3773`) asserts non-empty strings rather than validating code reachability.
   - *Consensus Fix:* Maintain reservation status for unused notice codes with explicit rationale, and specify the exact lifecycle/clearing rules for `IndexRebuildFailed`.

5. **MEDIUM (Plan 03) — Factual Inaccuracy in Upload Body Bound:**
   - *Mechanism & Evidence:* The plan claims `http.MaxBytesReader` bounds uploads to 32MB. The actual codebase limits uploads to `maxUploadBytes+(1<<20)` = **11 MiB** (`gateway/main.go:40, 361`) and limits `/rag/query` bodies to `maxRAGQueryBodyBytes = 32 << 10` = **32 KiB** (`:41, 534`).
   - *Consensus Fix:* Correct the documented review to cite 11 MiB upload and 32 KiB query body bounds.

6. **LOW (Cross-Plan) — Wave 2 Over-Serialization:**
   - *Observation:* Plans 02 (Python) and 03 (Markdown) declare `depends_on: [06.1-01]` despite having zero file overlap with the Rust engine plan. Both reviewers recommend removing this false dependency.

### Divergent Views

- **Plan 01 Synchronous Workflow Builder Seam:** Cursor noted that `build_production_workflow` (`engine/src/service.rs:69`) is currently synchronous while `tokio::sync::RwLock::read()` is async, requiring either capturing the snapshot in `query_rag` before invoking the builder, converting the builder to async, or using `std::sync::RwLock`. Claude did not flag this sync/async signature mismatch explicitly.
- **Plan 01 BM25 Port Wiring:** Cursor pointed out that Task 1 specifies passing `snapshot.nodes_version` and `snapshot.generation` into nodes, but omits passing `snapshot.bm25` directly into `ProductionBm25RetrievalPort`, which currently holds a live reference to the store and re-reads on every call.

# Cross-AI Plan Review — Phase 6.1

## Plan 06.1-01 — Index rebuild-and-swap

### 1. Summary
The plan correctly identifies the existing seams (`Bm25IndexStore` at `engine/src/workflow/ports.rs:13`, the single startup build at `engine/src/main.rs:28-31`/`:104`, the pre-declared notice codes at `engine/src/pb/lancet/v1/lancet.v1.rs:339-341`), and its `CorpusSnapshot` single-swap-unit design is the right answer to the atomicity requirement. But it inherits, without checking, 06-CONTEXT.md D-26's claim that the corpus generation can be derived from "max staging generation across the corpus" — and in this codebase that table is **empty in steady state**, which makes the derived generation constant and silently voids SC2/SC3's proof value. Two of the three notice codes it promises to wire have no described emission logic, and one Wave-0 prerequisite (the counted rebuild seam) is owned by no task.

### 2. Strengths
- **Correct swap-unit choice.** Bundling `{bm25, generation, nodes_version}` into one `Arc`-swapped struct resolves 06.1-RESEARCH.md Open Question 1 in favour of option (b) and is what actually makes D-21 provable. Reading it once per query in `build_production_workflow` (`engine/src/service.rs:69-90`) is the right insertion point — that function already runs per request from `query_rag` (`service.rs:826`), so no new lifetime problem is introduced.
- **Fail-closed startup is preserved by construction, not re-implemented.** `main.rs:28-30` uses `?` on `Bm25Index::from_table`, and `engine/tests/config_startup.rs:339-395` already asserts nonzero exit, a BM25-naming diagnostic, and `assert_not_listening(grpc_addr)`. The plan correctly treats D-25's startup half as regression-only.
- **The fail-closed config pattern is correctly identified.** Task 3 points at the right template: `config.rs:652-664` (`ALLOW_MODEL_ONLY_ANSWERS`) returns `ConfigError::Message`, versus the silent-ignore shape at `config.rs:642-645` (`PROMPT_TIMEOUT_MS`). The integration-test template (`config_startup.rs:678-722`) asserts both the key name and the offending value — copying it is exactly right.
- **Test-count gate is respected.** `scripts/engine-test-targets.sh` hard-asserts `TOTAL=392`/`LIB=357`; Task 3 requires updating it in the same commit, matching the script's own "never lower a value to make the gate pass" comment.

### 3. Concerns

- **HIGH — D-26's generation source is empty in steady state; the derived generation will be constant.** `staged_documents` rows are deleted on every successful ingestion: `engine/src/ingest.rs:814-816` (`ReplacementMutation::StagingDelete` with `document_id = '…'`) and `:649-653` on the empty-chunk path. `persist_raw_with_boundary` additionally deletes all `generation <= old_max` (`ingest.rs:483-491`). The Phase 02 evidence contract even *asserts* the table is empty after success — `scripts/phase02_live_evidence.py:358`: `require(evidence["staged_document_rows"] == 0, ...)`. So `get_max_corpus_staged_generation` returns `None` on a healthy corpus, and Task 1's rule "`gen-0` when None" makes the generation label a **constant across restarts and across rebuilds**. Consequences: SC2's "query concurrent with a swap returns results from exactly one generation" becomes vacuous (both generations are the string `gen-0`); `RetrievalSnapshot.index_generation` gains no cross-index meaning (D-24); `IndexStale` can never be computed. `nodes.version()` (already captured in the snapshot, and durable/monotonic in LanceDB) is the obvious correct source. This needs resolving *before* Task 1, since every downstream test depends on the generation being discriminating.
- **HIGH — `IndexStale` and `IndexGenerationMismatch` are promised but never designed.** Task 2's behavior block and acceptance criteria both claim all three codes get "real production emission sites," but the only emission logic anywhere in the plan is `IndexRebuildFailed`. Worse, under the plan's own design a mismatch is *impossible by construction* (one snapshot read supplies both the BM25 `Arc` and the dense `nodes_version`), so `generation_agreement_dense_bm25`'s "deliberately-mismatched pair is rejected/falls back" clause has nothing to exercise. Either the two codes stay reserved (and Task 2's acceptance criterion is rewritten), or the plan must specify where they fire.
- **HIGH — the notice-manifest "verification" cannot fail.** `engine/src/tests/workflow_phase5.rs:3766-3773` asserts only `!rationale.is_empty()` and `!n.code.is_empty()`. Task 2's automated verify is `cargo test … test_notice_published_enum_reachability_or_reservation` — that command passes identically whether the entries read `"reserved for Phase 6.1"` (current, `:3758-3763`) or a real path. 06.1-RESEARCH.md flagged this explicitly ("assertion needs strengthening"), but the plan only changes the strings. The acceptance criterion is unenforced.
- **MEDIUM — `Table::checkout` clone-independence is assumed, not verified.** The prohibition ("checkout must only be called on a per-query clone", `verification: source`) is a grep — it cannot prove that `nodes.clone()` yields an independent handle. If `lancedb::Table` clone shares an `Arc<dyn BaseTable>` with interior mutability, `checkout` on the "clone" pins *every* holder, including the ingestion writer path (`ingest.rs:603-611` reads `nodes` and mutates it). 06.1-RESEARCH.md logs this as assumption A2 (MEDIUM) and recommends a focused isolation test *before* building D-24 on top; the plan drops that step. I could not read the vendored `lancedb ~0.31` source in this environment, so I'm reporting this as an unverified risk rather than a confirmed defect.
- **MEDIUM — the degraded-notice plumbing is unspecified.** `RetrieveHybridNode` receives only two `String`s today (`with_snapshot_metadata`, `engine/src/workflow/nodes/retrieve.rs:40-48`, called at `service.rs:134-137`). Task 2 says a "degraded indicator" is set "so RetrieveHybridNode can attach `NoticeCode::IndexRebuildFailed`", but neither Task 1 nor Task 2 specifies the field, the constructor change, or how the indicator is cleared after a later successful rebuild. Without a clear-on-success rule, one transient failure marks every subsequent query degraded forever.
- **MEDIUM — two sources of truth for the generation survive.** `EffectiveRagSettings.index_generation` is populated by `new_index_generation()` (random UUID, `config.rs:452-453,511`) and validated non-empty at `config.rs:564-566`. Task 1 changes `main.rs` and `service.rs` to use the snapshot value but never retires the config field, leaving a live-looking random UUID in the settings struct — precisely the "no second source of truth" D-26 forbids. `config.rs` is not even in Task 1's `<files>` list (it appears only in Task 3, for the debounce key).
- **MEDIUM — two Wave-0 prerequisites are unowned.** 06.1-VALIDATION.md:74-78 lists a "counted/observable rebuild-invocation seam" (needed by `debounce_coalesces_burst`) and a "seeded-LanceDB `staged_documents` fixture helper" (needed by `startup_generation_derived_from_lancedb` and `generation_agreement_dense_bm25`). No task `<action>` creates either. Task 3 assumes both exist.
- **LOW — `<verify>` in Task 1 names a test the `<action>` never creates.** `cargo test … -- test_corpus_snapshot_initialization` has no counterpart in Task 1's action text (which only names `get_max_corpus_staged_generation` and a `RetrieveHybridNode` snapshot-label test).
- **LOW — estimate looks thin.** 85k tokens / 3 tasks for 9 files, a new type threaded through both retrieval ports, a background task, a config knob, and 11 new tests. Task 3 alone carries six named tests plus an integration test.

### 4. Suggestions
- Insert a Task 0: pick the durable generation source. Recommend `nodes.version(): u64` — already needed for `checkout`, monotonic, restart-durable, and it collapses the "two values must agree" problem into one value. Record the deviation from D-26's literal wording in the SUMMARY (D-26's *intent* — derived, no stored counter, survives restart — is satisfied; its *named column* is not viable).
- Add a `<precondition>`-style probe task for A2: one `#[tokio::test]` that checks out a clone to version N, writes through the live handle, and asserts the clone still reads N. Gate Task 1 on it.
- Strengthen `test_notice_published_enum_reachability_or_reservation` so non-reserved entries must match `^engine/src/.*\.rs(:\d+)?$` (or grep the cited file for the code), then update the three entries. Otherwise drop the acceptance criterion as unverifiable.
- Either scope `IndexStale`/`IndexGenerationMismatch` out of this plan explicitly (keeping their reservation strings, retargeted) or specify their trigger conditions.
- Specify the degraded-flag lifecycle: an `AtomicBool`/field on `CorpusSnapshot` cleared by the next successful swap is the simplest correct shape, and it rides the same atomic swap.
- Split Task 3: config knob + its integration test is one commit; the five concurrency/atomicity tests plus the gate update is another.

### 5. Risk Assessment
**HIGH.** The generation-source defect is load-bearing for three of the four D-20…D-26 success criteria and will not surface as a red test — it will surface as green tests that prove nothing. Combined with the unverifiable notice-manifest gate and the unverified `checkout` isolation semantics, this plan can complete "successfully" while leaving SC2/SC3 unmet.

## Plan 06.1-02 — DEBT-BU-01 / BU-02 deterministic proofs

### 1. Summary
Task 1 (BU-01) is precise, correctly grounded, and will work as written. Task 2 (BU-02) is not executable as specified: `verify-ingestion.sh` cannot reach the upload — let alone success — with only a fake HTTP gateway, because it hard-validates a challenge file at an exact repo path that the test suite's own guard forbids creating, and the success path additionally requires docker, cargo, and a write to a second forbidden runtime path.

### 2. Strengths
- **BU-01's mechanism is verified correct.** `validate_evidence(value, challenge, now=None)` at `scripts/phase02_live_evidence.py:332-334` already takes an injectable clock, and `:376` raises exactly `"complete run window exceeded"` — distinct from `:377`'s `"run start delay exceeded"` and `:375`'s staleness message. The plan's proposed timestamps genuinely isolate the target branch: `issued_at→run_started_at` = 5min (under `MAX_RUN_WINDOW` 35min, `:131`), `issued_at→generated_at` = 36min (over), `now−generated_at` = 4min (under `MAX_EVIDENCE_AGE` 30min, `:129`), ordering preserved for `:373`. Note `validate_evidence` also calls `validate_challenge(challenge, now=now)` at `:336`, whose `:292` staleness check is satisfied by `now−issued_at` = 40min... **wait — that is 40 minutes, exceeding `MAX_CHALLENGE_AGE` of 30 minutes (`:130`).** See Concerns.
- **The direct-import pattern already exists.** `scripts/test_phase02_live_evidence.py:24-27` does the `sys.path.insert` + `from phase02_live_evidence import …`, so Task 1 needs no new machinery.
- **Correctly diagnoses that the existing "overlong run" subtest is insufficient** (`test_phase02_live_evidence.py:290-292` shells out via `run_helper("validate-gate", …)`, and the `validate-gate` CLI has no `--now` flag — `phase02_live_evidence.py:748-750`).

### 3. Concerns

- **HIGH — Task 1's chosen `now` trips the wrong assertion first.** `validate_evidence` calls `validate_challenge(challenge, now=now)` on line 336, *before* reaching the run-window check on 376. `validate_challenge:292` requires `current − issued_at <= MAX_CHALLENGE_AGE` (30 min). With `issued_at = 00:00` and `now = 00:40`, that's 40 minutes → the test raises `"challenge.issued_at is stale"`, and `assertRaisesRegex(ValidationError, r"^complete run window exceeded$")` **fails**. The window is tight: `now` must satisfy `generated_at ≤ now ≤ min(issued_at+30min, generated_at+30min)`, but `generated_at = issued_at+36min` already exceeds `issued_at+30min` — so **no valid `now` exists** for the stated fixture. The fixture must lower `MAX_RUN_WINDOW`-crossing by making `issued_at→generated_at` exceed 35min while keeping `now−issued_at ≤ 30min`, which is arithmetically impossible. The test must therefore call `validate_evidence` with a challenge whose `issued_at` is recent enough *or* bypass `validate_challenge` — this needs a design decision the plan does not make. This is the single most important issue in this plan and it is invisible from the plan text alone.
- **HIGH — Task 2's success and post-upload-failure scenarios are unreachable with an HTTP mock alone.** `verify-ingestion.sh` gates, in order: `OPENROUTER_API_KEY` non-empty (`:86`), then `[[ -f "$challenge_file" && ! -L … ]]` (`:87`) where `challenge_file` is *forced* to equal `.planning/phases/02-ingestion-chunking-vector-storage/.02-LIVE-CHALLENGE.json` by the equality check at `:80-82` (the `--challenge-file` flag cannot point elsewhere). Only after that does it curl the gateway (`:154`). So:
  - The **existing** early-failure test (`test_phase02_live_evidence.py:640-655`) passes because it dies at `:86`/`:87`, **not** because "the gateway is unreachable" as the plan's Task 2 behavior block and 06.1-RESEARCH.md both state.
  - Reaching the upload requires writing that exact challenge path — which `assert_not_real_runtime_path` (`test_phase02_live_evidence.py:35-38`, with `REAL_CANONICAL_PATHS` at `:29-32`) explicitly raises on.
  - The **success** path further needs `docker compose exec … psql` (`:167`), `cargo run … inspect_lancedb` (`:168`), and an `mv` onto the second forbidden runtime path `02-LIVE-EVIDENCE.json` (`:83-85`, `:176`).
  The plan's mock-HTTP-server design covers none of this. The existing `PATH`-shim precedent (`test_phase02_live_evidence.py:543-638`) shims `cargo`/`docker` for `verify-live-evidence.sh`, not for this script's runtime-path constraints.
- **MEDIUM — the plan will delete existing coverage.** Task 2 says "Combine existing `test_caller_sample_preservation_on_early_failure` into this comprehensive suite." If the new suite is blocked by the above, the working test is lost with nothing replacing it. Combining should be strictly additive.
- **LOW — `scripts/phase02_live_evidence.py` is declared modified but needs no change.** It's in `files_modified` and in `artifacts` ("Evidence validation logic supporting injectable now datetime") — that already ships at `:333`. Listing it invites an unnecessary edit to a fail-closed validator.
- **LOW — false dependency.** `depends_on: [06.1-01]` serializes Python-only work behind a large Rust plan with zero file overlap.

### 4. Suggestions
- Re-derive the BU-01 fixture arithmetic against `MAX_CHALLENGE_AGE` before writing the test. The cleanest fix: assert on the *specific* branch by calling the run-window predicate path with a challenge issued recently and `generated_at` pushed past 35min while `now` stays within 30min of `generated_at` — which requires `run_started_at`/`issued_at` ordering to still hold, so `issued_at` must be ~36min in the past and the challenge-staleness check must be acknowledged. If both bounds genuinely conflict, the honest resolution is to note that `validate_challenge`'s staleness check *shadows* the run-window branch on this input and either (a) test the branch by calling a narrower helper, or (b) record the shadowing as a finding of its own. Do not paper over it with `assertRaises(ValidationError)` without a message match — that would reproduce exactly the non-discriminating-test failure mode Phase 6 spent three plans fixing.
- For BU-02, prefer the fallback 06.1-RESEARCH.md already anticipated (Assumptions Log A4): extract `verify-ingestion.sh`'s sample-ownership/cleanup logic into a directly-invocable shell function (or replicate the `sample_owned` trap in a small harness script under `scripts/fixtures/`) and drive *that* through three terminal outcomes. It satisfies D-07's substance — three scenarios, deterministic, no live services — without fighting the runtime-path guard.
- If you keep the end-to-end approach, add an explicit env override to `verify-ingestion.sh` for the challenge/evidence paths guarded to temp dirs only, and state that as a scoped deviation.
- Keep `test_caller_sample_preservation_on_early_failure` and add siblings.

### 5. Risk Assessment
**HIGH.** Task 1 as specified will not pass; Task 2 as specified cannot be implemented. Both are discoverable only by reading the script and the validator — which is exactly what this review is for. Neither issue threatens production code, so the blast radius is contained to the phase's own closure claim.

## Plan 06.1-01 — Index rebuild-and-swap

### Summary

The plan correctly reuses the existing swap cell (`Bm25IndexStore = Arc<RwLock<Arc<Bm25Index>>>` at `engine/src/workflow/ports.rs:13`), startup-only `Bm25Index::from_table` (`engine/src/main.rs:28-31`), clone-then-read BM25 lock (`engine/src/service.rs:573-576`), and `Table::version`/`checkout` already used for ingest rollback (`engine/src/ingest.rs:607-611`, `532-540`). `CorpusSnapshot` is the right atomic unit for D-21/D-24. It will not close DEBT-RAG-04 as written: generation is derived from `staged_documents`, which successful ingest **empties**; query wiring never pins BM25 from the same snapshot as dense checkout; `build_production_workflow` is synchronous and cannot `await` a tokio `RwLock`; and `IndexStale`/`IndexGenerationMismatch` are promised as live emission sites with no trigger design.

### Strengths

- Reuses the real swap primitive and the existing “clone `Arc` under read lock, then retrieve without holding the lock” pattern (`engine/src/service.rs:573-576`; lock-release test at `engine/src/tests/workflow_phase5_production.rs:1634-1677`).
- Clone-before-`checkout` matches rollback’s `Table::checkout` usage (`engine/src/ingest.rs:532-536`) and the plan’s safety prohibition.
- Debounce after **successful** completion (`engine/src/ingest.rs:1501-1509`) is the right trigger; failed jobs already delete staging (`:1511-1520`) and should not rebuild.
- Fail-closed debounce env parsing is specified against the Phase 6 boolean pattern (`engine/src/config.rs:652-678`) and the `model_only_answers_invalid_env_fails_closed` harness (`engine/tests/config_startup.rs:678-719`), not the silent-ignore timeout parsers (`:622-650`).
- Default `2000` ms debounce is documented (research Open Question 2). Startup BM25 failure already fail-closes (`engine/src/main.rs:28-30`); D-25’s startup half is already true.

### Concerns

- **HIGH — D-26 source is empty after every successful ingest.** `get_max_staged_generation` is document-scoped (`engine/src/ingest.rs:391-419`). Staging rows are deleted on success (`:814-816`), empty-chunk success (`:649-653`), and indexing failure (`:1512-1520`). Phase 02 evidence **requires** `staged_document_rows == 0` (`scripts/phase02_live_evidence.py:358`). A corpus-wide scan therefore returns `None` in steady state; Task 1’s `"gen-0" when None` makes the label constant across rebuilds and restarts. D-21’s “exactly one generation” test becomes tautological (`gen-0` vs `gen-0`). D-24’s “cross-index meaning” for `RetrievalSnapshot.index_generation` never materializes. Durable alternatives already exist: `nodes.version()` (`ingest.rs:610`) and the live table head `ProductionDenseRetrievalPort` already queries (`service.rs:528`).

- **HIGH — Query path can still mix generations.** Task 1 says: one `CorpusStore` read, pass `snapshot.nodes_version` into dense, pass `snapshot.generation` into `RetrieveHybridNode::with_snapshot_metadata`. It does **not** pass `snapshot.bm25` into `ProductionBm25RetrievalPort`. Today that port holds the live store and re-reads on every call (`service.rs:543-576`). Dense can be pinned to version N while BM25 clones the post-swap Arc. That is exactly the D-24 prohibition the plan marks `status: resolved`. `index_generation` on the snapshot is only a label (`retrieve.rs:19-47`, `:216`); it does not bind candidate sets.

- **HIGH — `build_production_workflow` cannot await `corpus_store.read()`.** The method is sync (`service.rs:69-71`) and is called from async `query_rag` (`:826`) plus many tests. Tokio `RwLock::read()` is async. The plan never makes the builder async, never captures the snapshot in `query_rag` before spawn, and never switches the cell to `std::sync::RwLock`. Executors will stall on this seam.

- **HIGH — `IndexStale` and `IndexGenerationMismatch` have no production design.** Proto variants exist (`proto/lancet/v1/lancet.proto:96-98`; allowlist `workflow_phase5.rs:3758-3763`). Task 2 requires all three manifest rows to cite real emission sites, but the only specified emit is `IndexRebuildFailed` via an unspecified “degraded indicator.” Under a single `CorpusSnapshot`, dense/BM25 disagreement is impossible if BM25 is taken from that snapshot, so `IndexGenerationMismatch` cannot fire. `IndexStale` would fire on in-flight queries still holding the previous Arc — which D-22 **requires**. Task 2’s acceptance criterion will either invent notices that contradict D-22/D-24 or leave the reachability test as a comment-only lie (the current test only asserts `!rationale.is_empty()`, `:3766-3770`).

- **MEDIUM — Degraded-notice plumbing is unspecified.** `RetrieveHybridNode` takes two strings today (`retrieve.rs:40-47`). Notices are attached via `ctx.add_notice` on retrieval errors (`:87-91`, `:140-145`). Task 2 never adds a field, constructor arg, or clear-on-success rule. A sticky flag would mark every later query `INDEX_REBUILD_FAILED` forever after one failed rebuild.

- **MEDIUM — `spawn_worker` signature change is under-scoped.** Task 2 adds a `watch::Sender<u64>` (or handle) to `spawn_worker` (`ingest.rs:1394-1410`). `engine/src/tests.rs` has **9** `spawn_worker(` call sites; `spawn_worker_with_boundary` is the real loop (`:1413+`). `files_modified` omits `engine/src/tests.rs`. In `main.rs` the worker is spawned **before** `LancetServiceImpl` (`:67-74` vs `:99-110`), so `CorpusStore` must be created first and shared; the plan never specifies that construction order.

- **MEDIUM — Rebuild must not hold the write lock during `from_table`.** If `corpus_store.write()` is held across `Bm25Index::from_table`, in-flight `retrieve_bm25` waits on the write lock (`service.rs:574`) and D-22 / `query_never_blocks_on_rebuild` fail. The action text *lists* build then replace, but does not forbid holding the write guard across the build.

- **MEDIUM — LanceDB checkout isolation (research A2) is not tested.** Rollback calls `checkout` on the **shared** handle then `restore` (`ingest.rs:532-540`). Query pinning needs the opposite: clone, checkout, leave the live ingest handle at head. No named test proves a checked-out clone is isolated from concurrent writes. `lancedb = "~0.31"` (`engine/Cargo.toml:17`).

- **MEDIUM — Config surface is three types, not one.** Env overlay mutates `WorkflowConfigSettings` (`config.rs:147-177`, deny_unknown_fields). Runtime uses `WorkflowSettings` (`:211-229`) via `to_workflow_settings` (`:195-207`). Task 3 only names `WorkflowSettings`. Missing the config struct, default fn, and copy in `to_workflow_settings` either fails compile or silently drops the knob. `u64` parse accepts `0`; the error string says “positive integer.”

- **LOW — Tests parked in `workflow_phase5.rs` for ingest/LanceDB behavior.** `get_max_corpus_staged_generation` belongs with ingest fixtures in `engine/src/tests.rs` / `db`. The lib test module can import `ingest` (`lib.rs:9`, `:19-21`), but this is the wrong home and inflates the pinned lib count in `scripts/engine-test-targets.sh`.

- **LOW — Task 3 requires `cargo fmt --check`.** STATE.md already records that gate as pre-existing red after plan 06-01. A new plan should not inherit a known-red fmt gate as an acceptance criterion without a baseline exception.

### Suggestions

- Derive corpus generation from durable LanceDB state that survives ingest: `nodes.version()` (and/or max generation on **nodes** rows), not `staged_documents`. Keep D-26’s “no stored counter” without using an ephemeral table.
- Capture `Arc<CorpusSnapshot>` once per query (in async `query_rag`), pass `snapshot.bm25` (not `CorpusStore`) into `ProductionBm25RetrievalPort`, and checkout dense on a clone using `snapshot.nodes_version`.
- Keep `IndexStale` / `IndexGenerationMismatch` reserved (update the allowlist rationale) unless you specify real, D-22-compatible triggers. Only `IndexRebuildFailed` needs emission this phase.
- Create `CorpusStore` in `main` before `spawn_worker`; do not change `spawn_worker`’s signature unless `tests.rs` is in `files_modified`. Drive debounce from a completion `watch` owned by `main`.
- Build the new BM25 index **outside** the write lock; swap only the `Arc<CorpusSnapshot>`.
- Add an early A2 test: concurrent ingest/write on the live `Table` vs vector search on a checked-out clone.
- Add `rebuild_debounce_ms` to `WorkflowConfigSettings`, `WorkflowSettings`, and `to_workflow_settings`; reject `0` if the contract is “positive.”

### Risk Assessment

**HIGH** — without a durable generation and a single snapshot feeding both retrievers, DEBT-RAG-04’s “no mixed evidence” goal is not met even if every named test is green.

## Plan 06.1-02 — DEBT-BU-01 / DEBT-BU-02 proofs

### Summary

BU-01 is almost ready: `validate_evidence(..., now=)` already exists (`scripts/phase02_live_evidence.py:332-377`), windows are `MAX_RUN_WINDOW = 35m` and `MAX_EVIDENCE_AGE = 30m` (`:129-131`), and the dedicated message is `"complete run window exceeded"` (`:376`). The stated timestamps (issued 00:00, start 00:05, generated 00:36, now 00:40) correctly isolate that clause from start-delay, staleness, ordering, and future-skew. BU-02 as specified will not prove the post-upload or success paths: it drives the full `verify-ingestion.sh`, which is not a gateway-only client, uses a nonexistent `--sample` flag, mocks the wrong JSON shape, and hits OpenRouter/challenge/docker/cargo gates before fixture preservation on those paths can be observed.

### Strengths

- BU-01 calls `validate_evidence` directly with injected `now` — not the CLI and not `datetime.now`. That matches D-07 and avoids Pitfall 3.
- Discriminating timestamps are arithmetically correct against `phase02_live_evidence.py:372-377`.
- Early-failure preservation already has a template (`scripts/test_phase02_live_evidence.py:640-655`) asserting existence and exact bytes (hash can be added).
- `sample_owned` cleanup only deletes script-created temps (`verify-ingestion.sh:41`, `:48-54`, `:149-152`); caller files are already intended to survive.

### Concerns

- **HIGH — Success and post-upload scenarios cannot be hermetic via `http.server` + `verify-ingestion.sh`.** After optional managed startup, the script always `curl`s upload (`:154`), then polls (`:157-164`), then `docker compose exec` Postgres (`:167`) and `cargo run ... inspect_lancedb` (`:168`). A loopback mock does not stop docker/cargo. The script also requires `OPENROUTER_API_KEY` (`:86`) and a pre-issued untracked challenge at the phase-local path (`:80-87`) **before** curl. Research already recommended the PATH-shim pattern used in `test_captured_inspector_arguments_explicit_path` (`test_phase02_live_evidence.py:543-638`). The plan ignores it.

- **HIGH — Mock protocol does not match the gateway.** Upload/get handlers serialize `db.Document` (`gateway/main.go:456`, `:519`) with exported fields `ID`, `Status`, `ChunkCount` (`gateway/db/models.go:11-16`). The script reads `["ID"]` and `["Status"]` (`verify-ingestion.sh:155-159`). The plan’s mock bodies use `job_id` / `status` and invent `--sample`. The sample is a positional argument (`verify-ingestion.sh:72`), not `--sample`.

- **MEDIUM — BU-01 “valid base evidence” is a full schema, not timestamps.** `validate_evidence` also requires matching challenge identity, `schema_version == 1`, `success_sentinel`, UUID document id, `provider == "openrouter"`, locked embedding model, agreeing counts, `staged_document_rows == 0`, `document_rows == 1`, `generation_count == 1`, boolean hygiene flags, etc. (`phase02_live_evidence.py:335-368`). The plan does not say to reuse `fixture_pair()` (`test_phase02_live_evidence.py:62`). A naive dict will fail before the window assertion. That is fixable; it is not specified.

- **MEDIUM — `files_modified` lists `scripts/phase02_live_evidence.py` with no required production change.** `now=` is already implemented. Harmless unless an executor “implements” a second clock.

- **LOW — `depends_on: [06.1-01]` is a false code dependency.** Research states the three workstreams share no code. Wave 2 serialization delays BU proofs for no technical reason.

- **LOW — Full-suite verify includes `verify-live-evidence.sh --self-test`.** Fine as extra, not required by D-07.

### Suggestions

- Keep BU-01 as unit tests; construct evidence via `fixture_pair()` then overwrite timestamps; assert `^complete run window exceeded$`.
- For BU-02 success/post-upload: either (a) PATH-shim `curl`/`docker`/`cargo` like the existing inspector test, with correct `ID`/`Status`/`ChunkCount` JSON, positional sample path, and a throwaway challenge fixture, or (b) extract a small “upload+poll+cleanup” function and test that — do not pretend `verify-ingestion.sh` is gateway-only.
- Drop `depends_on: 06.1-01` (and Wave 2 blocking) unless process policy requires it.
- Remove `phase02_live_evidence.py` from `files_modified` unless a real helper change is planned.

### Risk Assessment

**HIGH** for BU-02 as written (tests will fail closed on challenge/API key, or pass vacuously without exercising poll/success cleanup). **LOW** for BU-01 if fixtures are complete.

## Plan 06.1-03 — DEBT-CR-04 / DEBT-CR-05 documented review

### Summary

Scope matches D-06: no production code, loopback test, timeout audit, CR-04 disambiguation. The empirical line numbers for `formatListenAddr` / `newHTTPServer` are correct (`gateway/main.go:695-708`; `TestGatewayAddressIsLoopback` at `gateway/main_test.go:1788-1793`). The plan then reintroduces the exact Pitfall 2 it cites: Task 2 records upload bounding as **32MB** and treats both `MaxBytesReader` sites as the same control. They are not.

### Strengths

- Documented-only; `files_modified` is only `06.1-CR-REVIEW.md`.
- Loopback proof is a real test (`main_test.go:1788-1793`) of `formatListenAddr("8080")` → `127.0.0.1:8080` (`main.go:695-699`).
- Read timeouts match code: `ReadTimeout: 60s`, `ReadHeaderTimeout: 10s`, no `WriteTimeout`/`IdleTimeout` (`main.go:702-708`). `TestHTTPServerReadTimeouts` already locks this (`main_test.go:1616-1622`).
- D-03 disambiguation table is the right CR-04 split (network auth vs `DEBT-CR-04-EXT` insecure gRPC dial at `main.go:734` vs VER-20 evidence helper).
- `go test ./...` as a no-diff regression check is appropriate.

### Concerns

- **HIGH (accuracy of the artifact, not runtime) — 32MB claim is false.** `maxUploadBytes = 10 << 20` (10 MiB) (`gateway/main.go:40`). Upload `MaxBytesReader` is `maxUploadBytes+(1<<20)` (11 MiB) (`:361`) plus `ParseMultipartForm(maxUploadBytes)` (`:362`) and `header.Size > maxUploadBytes` (`:372`). Line 534 is **RAG query** body: `maxRAGQueryBodyBytes = 32 << 10` (32 KiB) (`:41`, `:534`). Task 2’s “`http.MaxBytesReader` (32MB) bounds upload payload size” collapses those two sites. D-06 and Pitfall 2 exist so this review does **not** copy stale CONTEXT prose; 32MB is a new error.

- **MEDIUM — Loopback is not absolute.** `formatListenAddr` returns `port` unchanged if it contains `:` (`main.go:696-698`). `TestGatewayAddressIsLoopback` only checks `"8080"` and `"127.0.0.1:9090"`. A config of `0.0.0.0:8080` bypasses the guardrail. The review should record that, not claim “binds strictly to 127.0.0.1.”

- **MEDIUM — `depends_on: [06.1-01]` is unnecessary.** Documented review does not need `CorpusSnapshot`.

- **LOW — Task 1 `files: gateway/main.go, gateway/main_test.go` with “no modifications.”** Fine if executors treat it as read-only; easy to accidentally “fix” timeouts.

- **LOW — Insecure gRPC dial (`main.go:734`) is correctly out of scope as `DEBT-CR-04-EXT`,** but the review should cite the line so it is not silently folded into DEBT-CR-04.

### Suggestions

- In `06.1-CR-REVIEW.md`, table the real bounds: upload 10 MiB (+1 MiB reader slack); RAG body 32 KiB; ReadTimeout 60s; ReadHeaderTimeout 10s; Write/Idle unset; no upload semaphore.
- Document the colon bypass in `formatListenAddr` and that `TestGatewayAddressIsLoopback` does not cover `0.0.0.0:port`.
- Drop `depends_on: 06.1-01`.
- Keep Task 1 files out of `files_modified` (already true at plan level).

### Risk Assessment

**LOW** for shipping (no code). **MEDIUM** for the phase goal: a wrong-byte-size review would fail D-06’s “record empirical code facts” must-have and Pitfall 2.
