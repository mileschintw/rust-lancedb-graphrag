### Locked Decisions — Section C: Index lifecycle & recovery (DEBT-RAG-04, Phase 6.1)

- **D-20:** **Rebuild-and-swap after ingest.** When an ingestion batch completes, BM25 is rebuilt
  from the nodes table and swapped into the existing `Arc<RwLock<Arc<Bm25Index>>>`
  (`engine/src/workflow/ports.rs:13`). The swap mechanism already exists and is only ever built
  once at startup (`engine/src/main.rs:3250` in the CONTEXT.md's line numbering — see Existing
  Code Insights below for the current, post-restructure line) — Phase 6.1 wires a trigger to it.
  No incremental IDF/doc-length bookkeeping.
- **D-21:** **Atomicity is proven by generation stamping plus assertion tests.** Results carry
  the index generation (`RetrievalSnapshot.index_generation` already exists on the wire), and a
  test asserts that a query concurrent with a swap returns results from **exactly one**
  generation. No fault-injection seam required for this property.
- **D-22:** **Queries never block on a rebuild.** Startup readiness gating is unchanged (the
  first build must complete before serving); post-startup rebuilds run off to the side and
  in-flight queries keep serving the previous generation until the instantaneous swap.
- **D-23:** The rebuild is **triggered by the Rust ingestion worker** on batch completion,
  **debounced/coalesced** so a burst of documents causes one rebuild rather than N. No new API
  surface; index lifecycle stays inside the component that owns LanceDB.
- **D-24:** **A single corpus generation covers both representations.** Dense and BM25 results
  must agree on the generation or the query is served entirely from the previous one. This gives
  `RetrievalSnapshot.index_generation` real cross-index meaning and is what actually delivers
  "no mixed evidence" during replacement. — **Reversibility:** costly — the generation becomes a
  precondition threaded through both retrieval paths and the fusion step.
- **D-25:** **Rebuild failure: fatal at startup, degraded after ingest.** A failed startup build
  stops the engine (fail-closed, preserving build-before-readiness). A failed post-ingest
  rebuild keeps the previous generation serving, emits a warning notice on affected queries, and
  logs/spans at error level — the same one-path-degraded contract as D-13.
- **D-26:** **The corpus generation is derived at startup** from persisted LanceDB state (max
  staging generation across the corpus) — no stored counter, no second source of truth, survives
  restart by construction.

## Summary

Phase 6.1 is almost entirely a **greenfield wiring exercise on top of already-provisioned
scaffolding**, not new infrastructure. Three independent workstreams, none of which share code:

1. **Index rebuild-and-swap (D-20–D-26, RAG-03/DEBT-RAG-04).** The atomic-swap primitive
   (`Bm25IndexStore = Arc<RwLock<Arc<Bm25Index>>>`) and the build function (`Bm25Index::from_table`)
   already exist and are exercised once at startup (`engine/src/main.rs:26-31,104`). Nothing in
   `engine/src` today triggers a rebuild after startup — grepping for `rebuild|debounce|coalesce`
   in `engine/src` returns zero hits. The three protobuf notice codes 6.1 needs
   (`INDEX_REBUILD_FAILED`, `INDEX_STALE`, `INDEX_GENERATION_MISMATCH`) were **pre-declared in
   Phase 6's wire-contract consolidation** (D-74) and already round-trip in the generated Rust
   `NoticeCode` enum — a test (`workflow_phase5.rs:3758-3763`) currently allowlists them as
   "reserved for Phase 6.1" with no real emission site, which is the seam 6.1 must close. The
   hardest sub-problem is D-24/D-26: today `index_generation` is a random UUID minted once per
   process (`config.rs:452-453,511`) and carries no real cross-index meaning; dense retrieval reads
   the live LanceDB `nodes` table directly with no version pinning
   (`service.rs:81-85`, `ProductionDenseRetrievalPort { nodes: self.nodes.clone(), .. }`). Making
   the generation real requires (a) deriving it from the corpus-wide max of the `staged_documents`
   table's existing `generation` column at rebuild time (adapting the existing
   `get_max_staged_generation` in `engine/src/ingest.rs:391-420`, which today is scoped to one
   `document_id` and must be widened to scan the whole table), and (b) pinning dense reads to the
   LanceDB table version that generation corresponds to via `Table::checkout(version)` — a method
   already used elsewhere in this codebase for rollback (`ingest.rs:532-540`) and confirmed by the
   official LanceDB Rust docs to be a per-handle "detached head" that does not affect other `Table`
   clones, which is exactly the isolation 6.1 needs.

2. **DEBT-BU-01/BU-02 deterministic proofs (D-07).** Both debts live entirely in
   `scripts/phase02_live_evidence.py` (a stdlib-only Python module, no new dependencies) and its
   test file `scripts/test_phase02_live_evidence.py`. BU-01's exact machinery already exists:
   `validate_evidence(value, challenge, now=None)` accepts an injectable clock and already raises
   the distinct message `"complete run window exceeded"` (line 376) when `generated_at - issued_at`
   exceeds `MAX_RUN_WINDOW` (35 min) — separately from `"run start delay exceeded"` (line 377). No
   test today calls this function directly with a controlled `now`; the existing "overlong run"
   subtest goes through the CLI subprocess, which has no `--now` flag and therefore depends on the
   real wall clock at test-run time. BU-02's fix (`sample_owned` flag preventing deletion of a
   caller-supplied fixture) already ships in `verify-ingestion.sh`, and one deterministic test
   (`test_caller_sample_preservation_on_early_failure`) already proves the *early*-failure case.
   D-07 requires *also* proving success and post-upload-failure preservation without a live run —
   which needs a local fake HTTP stub standing in for the gateway (the pattern of faking `cargo`/
   `docker` via a `PATH`-shimmed script already exists in this test file and is directly reusable).

3. **DEBT-CR-04/CR-05 documented review (D-06).** No code changes. The loopback guardrail
   (`formatListenAddr` returning `"127.0.0.1:" + port`, `gateway/main.go:695-699`, proven by
   `TestGatewayAddressIsLoopback` in `gateway/main_test.go:1788-1793`) still holds. One factual
   correction against the CONTEXT.md prose: `gateway/main.go:702-709` **already sets**
   `ReadTimeout: 60 * time.Second` and `ReadHeaderTimeout: 10 * time.Second` on the `http.Server` —
   only `WriteTimeout` and `IdleTimeout` (which would break SSE streaming) and the bounded upload
   semaphore are genuinely absent. The review task must record this accurately rather than restate
   the CONTEXT.md's "ships without ReadTimeout" line as fact.

**Primary recommendation:** Treat this phase as three independent, narrowly-scoped plans (index
lifecycle in Rust; BU-01/BU-02 in Python; CR-04/CR-05 as a documentation-only task with one
grep-and-record step), landing the index-lifecycle plan first since it is the only one with real
design risk (the dense/BM25 generation-agreement mechanism in D-24).

### Pattern 1: Debounced/coalesced rebuild trigger (D-23)

**What:** After each document completes ingestion, notify a rebuild task; if another
notification arrives before the debounce window elapses, reset the window instead of firing
twice.
**When to use:** Any burst-collapsing trigger in a single-process Tokio service with no existing
debounce dependency.
**Example (idiomatic Tokio pattern, not yet in the codebase — illustrative only):**
```rust
// Illustrative pattern — not sourced from a file in this repo (no rebuild code exists yet;
// verified via `grep -r "rebuild|debounce|coalesce" engine/src` returning zero matches).
// Tag: [ASSUMED] as an implementation sketch, not a verified in-repo pattern.
use tokio::sync::watch;
use tokio::time::{sleep, Duration};

// Ingestion worker side: cheap "something completed" signal, coalesced by watch semantics
// (a watch channel only ever holds the latest value — sends are never queued).
let (rebuild_tx, rebuild_rx) = watch::channel(0u64);
// on each successful completion (ingest.rs:1501-1509 today):
let _ = rebuild_tx.send(rebuild_tx.borrow().wrapping_add(1));

// Separate task: debounce by resetting a sleep future on every new value.
tokio::spawn(async move {
    let mut rx = rebuild_rx;
    loop {
        rx.changed().await.ok();
        // Debounce window: race the next change against a timer.
        tokio::select! {
            _ = sleep(Duration::from_millis(debounce_ms)) => {
                // quiet period elapsed — perform the rebuild
            }
            _ = rx.changed() => continue, // another completion arrived — restart the wait
        }
    }
});
```

### Pattern 2: Corpus-wide generation derivation, reusing an existing per-document query shape (D-26)

**What:** `get_max_staged_generation` already computes `MAX(generation)` from the
`staged_documents` LanceDB table, but is scoped to one `document_id` via a `WHERE` predicate.
**When to use:** At startup (deriving the initial corpus generation) and at each successful
rebuild (deriving the post-ingest generation) — same query, no `only_if` predicate.
**Example:**
```rust
// Source: engine/src/ingest.rs:391-420 (existing, verified this session).
// The corpus-wide variant simply omits the `.only_if(&pred)` call and its predicate string:
pub async fn get_max_staged_generation(
    table: &Table,
    document_id: &str,
) -> Result<Option<i64>, String> {
    let pred = format!("document_id = '{}'", escape_sql_literal(document_id));
    let batches: Vec<RecordBatch> = table
        .query()
        .only_if(&pred)          // <- drop this line (and `pred`) for the corpus-wide scan
        .execute()
        .await
        .map_err(|e| format!("query failed: {e}"))?
        .try_collect()
        .await
        .map_err(|e| format!("collect failed: {e}"))?;

    let mut max_g: Option<i64> = None;
    for batch in &batches {
        if let Some(col) = batch.column_by_name("generation") {
            let gen_arr = col
                .as_any()
                .downcast_ref::<Int64Array>()
                .ok_or_else(|| "invalid generation column type".to_string())?;
            for i in 0..batch.num_rows() {
                let g = gen_arr.value(i);
                max_g = Some(max_g.map_or(g, |current| current.max(g)));
            }
        }
    }
    Ok(max_g)
}
```

### Pattern 3: Dense-side generation pinning via `Table::checkout` (D-24)

**What:** Clone the `nodes: Table` handle per query (or per rebuild) and call
`.checkout(version)` on the clone before querying, so the query reads exactly the LanceDB version
that corresponds to the generation stamped at the last successful rebuild — without affecting any
other `Table` handle (the live ingestion writer, other in-flight queries, etc).
**When to use:** Anywhere a read must be pinned to a specific historical version while writers
continue to advance the table.
**Example:**
```rust
// Existing precedent for `.checkout()` in this codebase (rollback use, not read-pinning):
// Source: engine/src/ingest.rs:532-540 (verified this session).
pub async fn restore_version(table: &Table, version: u64) -> Result<(), String> {
    table
        .checkout(version)
        .await
        .map_err(|error| format!("checkout rollback version {version}: {error}"))?;
    table
        .restore()
        .await
        .map_err(|error| format!("restore rollback version {version}: {error}"))
}

// For D-24's read-pinning (new code — clone first, never checkout the shared handle):
// [CITED: https://docs.rs/lancedb/latest/lancedb/table/struct.Table.html] — "Checkout is a
// read-only operation that turns the table into a sort of 'view' or 'detached head', with
// other table instances not being affected."
async fn retrieve_dense_pinned(
    nodes: &Table,
    pinned_version: u64,
    /* query params */
) -> Result<Vec<Candidate>, String> {
    let pinned = nodes.clone();          // do NOT call checkout on the shared `self.nodes` handle
    pinned.checkout(pinned_version).await.map_err(|e| e.to_string())?;
    // ... run the existing dense query against `pinned` instead of `nodes` ...
    Ok(vec![])
}
```

### Pattern 4: Generation-stamped concurrency assertion test (D-21)

**What:** Prove a query concurrent with a swap sees exactly one generation, without a
fault-injection seam.
**When to use:** Directly against the shared cell in a `#[tokio::test]`, not an end-to-end
subprocess test.
**Sketch:** hold two `RetrievalSnapshot`s from two queries issued around a manually-triggered
swap (call the rebuild function directly in the test rather than waiting on the debounce timer);
assert each snapshot's `index_generation` is one of exactly two known values, and that no snapshot
mixes dense candidates from one generation with BM25 candidates from the other (assert the
generation label used to build the workflow matches the LanceDB version actually checked out for
that same query, e.g. by asserting `nodes.version()` on the pinned handle equals the recorded
`nodes_version` for that generation). This exercises the shared-cell swap directly and needs no
`cfg(test)` fake beyond what already exists.

### Anti-Patterns to Avoid

- **Checkout on the shared/live `Table` handle:** calling `.checkout()` on `self.nodes` (the
  handle also used for potential future writes or other concurrent reads) would silently pin
  *every* subsequent read through that handle to a stale version — clone first, always.
- **Copy-pasting the existing silent-ignore env-parsing pattern for the new debounce key:** several
  existing `LANCET_ENGINE__WORKFLOW__*_TIMEOUT_MS` keys silently ignore an unparseable value
  (`config.rs:642-650`) — D-84 requires the *new* debounce key to fail closed instead, following
  the `ALLOW_MODEL_ONLY_ANSWERS`/`CITATION_REPAIR_ENABLED` pattern (`config.rs:652-679`) that
  returns `Err(::config::ConfigError::Message(...))`.
- **Treating "batch completion" as a literal batch abstraction:** the ingestion worker processes
  one document per job in a serial loop (`ingest.rs:1422-1548`) — there is no batch object to hook.
  "Batch completion" for D-23 means "after each document's success, notify the debounced rebuild
  trigger" — the debounce mechanism itself is what collapses a burst of documents into one rebuild.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Debounce/coalesce timing | A custom timer-management struct with manual cancellation bookkeeping | `tokio::sync::watch` (coalesces by construction — only the latest value survives) + `tokio::select!` racing a `sleep` against the next change | `watch` channels already collapse redundant notifications; no crate, no custom data structure needed |
| Version-pinned reads | Filtering by `ingested_at` timestamp or a custom row-visibility flag | `Table::checkout(version)` (LanceDB-native, already used for rollback in this codebase) | Timestamp-based pinning is subject to clock skew and doesn't compose with the existing generation-numbering protocol; checkout is exact |
| SHA-256 fixture hashing (BU-02) | A hand-rolled hash comparison | `hashlib.sha256` (already imported in `phase02_live_evidence.py:8`) | Stdlib, already a dependency, already used elsewhere in the same file for evidence/attestation hashing |
| Controlled clock for BU-01 | A new clock-abstraction layer or mocking library | The existing `now: dt.datetime | None = None` parameter on `validate_evidence` (`phase02_live_evidence.py:332-333`) | Already present and unused by any test — no new machinery needed, just a test that imports and calls the function directly instead of going through the CLI subprocess |

**Key insight:** every piece of "new" infrastructure this phase seems to need (debounce, version
pinning, clock injection, SHA-256 comparison) already has either a direct precedent in this
codebase or an already-exposed extension point. The design risk in this phase is *architectural
wiring* (getting D-24's generation-agreement precondition threaded correctly through both
retrieval paths), not missing tooling.

## Common Pitfalls

### Pitfall 1: Silent env-var parse failure on the new debounce key

**What goes wrong:** A mistyped `LANCET_ENGINE__WORKFLOW__REBUILD_DEBOUNCE_MS=abc` gets silently
ignored, and the engine starts with the *default* debounce window instead of failing loudly.
**Why it happens:** The dominant existing pattern for numeric `_TIMEOUT_MS` keys in
`engine/src/config.rs` is exactly this silent-ignore shape:
```rust
// engine/src/config.rs:642-645 (verified this session)
if let Ok(value) = std::env::var("LANCET_ENGINE__WORKFLOW__PROMPT_TIMEOUT_MS") {
    if let Ok(val) = value.trim().parse::<u64>() {
        settings.engine.workflow.prompt_timeout_ms = val;
    }
}
```
This is precisely the shape DEBT-P3-WARN-SETTINGS complains about ("invalid numeric env overrides
silently ignored") and D-84 explicitly says existing keys keep this behavior *but new keys must
not*.
**How to avoid:** Follow the boolean-key fail-closed pattern already introduced for Phase 6's own
new knobs instead:
```rust
// engine/src/config.rs:652-664 (verified this session) — same shape, adapted to a numeric parse:
if let Ok(raw) = std::env::var("LANCET_ENGINE__WORKFLOW__ALLOW_MODEL_ONLY_ANSWERS") {
    let trimmed = raw.trim();
    if !trimmed.is_empty() {
        settings.engine.workflow.allow_model_only_answers = match trimmed {
            "true" | "1" => true,
            "false" | "0" => false,
            other => {
                return Err(::config::ConfigError::Message(format!(
                    "LANCET_ENGINE__WORKFLOW__ALLOW_MODEL_ONLY_ANSWERS must be true/false, got {other:?}"
                )))
            }
        };
    }
}
```
For a numeric key, the equivalent is `value.trim().parse::<u64>()` inside the same `if
!trimmed.is_empty()` guard, returning `Err(::config::ConfigError::Message(...))` on parse failure
instead of silently falling through.
**Warning signs:** A test resembling `model_only_answers_invalid_env_fails_closed`
(`engine/tests/config_startup.rs:678-722`) not existing for the new key — that test's shape
(spawn the real binary via `spawn_engine_full`, assert nonzero exit, assert the diagnostic names
both the env var key and the offending value) is the exact template to copy.

### Pitfall 3: BU-01's existing "overlong run" test proves nothing about a controlled clock

**What goes wrong:** Treating `test_all_structured_failures_are_rejected_under_optimized_isolated_python`'s
existing `"overlong run"` subtest (`scripts/test_phase02_live_evidence.py:290-292`) as already
satisfying D-07's "controlled/injected clock" requirement, and closing DEBT-BU-01 without new work.
**Why it happens:** That subtest does trigger the "complete run window exceeded" branch, but by
offsetting `challenge["issued_at"]` 36 minutes into the *real* past
(`overlong_run["issued_at"] = timestamp(-36 * 60)`) and running through the CLI subprocess, which
calls `validate_evidence(evidence, challenge)` with `now=None` → real wall clock. This is
deterministic in the sense that the test always fails the same way, but it is **not** an injected
clock — it depends on the machine's real time, and the CLI (`validate-gate` subcommand) has no
`--now` flag to inject one even if you wanted to.
**How to avoid:** D-07 wants a test that `import`s `phase02_live_evidence` directly and calls
`validate_evidence(evidence, challenge, now=<fixed datetime>)`, fully decoupled from the real clock
— e.g. `issued_at = 2020-01-01T00:00:00Z`, `run_started_at` 1 minute later (within the 35-minute
window so only the run-window check trips), `generated_at` 36 minutes after `issued_at` (exceeds
the window), `now` a few minutes after `generated_at` (stays within the 30-minute staleness bound)
— and asserts the raised `ValidationError` message is exactly `"complete run window exceeded"`
(not `"run start delay exceeded"` or a staleness message), proving the *specific* classification
D-07 names.
**Warning signs:** A new BU-01 test that still shells out to the CLI (`run_helper("validate-gate",
...)`) instead of importing and calling `validate_evidence` directly.

### Pitfall 4: BU-02's existing test only covers the early-failure branch

**What goes wrong:** Declaring DEBT-BU-02 closed after adding one more assertion to the existing
`test_caller_sample_preservation_on_early_failure` test.
**Why it happens:** That test (`scripts/test_phase02_live_evidence.py:640-655`) runs
`verify-ingestion.sh` with no managed services and no gateway listening, so the very first `curl
--fail` against `${gateway_url}/documents` fails immediately — this is exactly one of D-07's three
required scenarios (early failure) but not the other two (success, post-upload failure).
**How to avoid:** D-07 explicitly requires "successful plus representative early and post-upload
failures" and explicitly forbids a live run. This means standing up a local, deterministic fake
HTTP responder bound to loopback (Python's `http.server` in a background thread, or a
`PATH`-shimmed fake `curl`-reachable service) that can be parameterized to (a) accept the upload
and report `Status: "completed"`, or (b) accept the upload but report `Status: "failed"` on
subsequent polls — exercising `verify-ingestion.sh`'s cleanup path in both outcomes, still with a
`sample_owned=false` caller-supplied fixture, asserting the fixture's bytes and SHA-256 survive in
all three cases (success, early failure, post-upload failure). The existing fake-`cargo`/fake-
`docker` `PATH`-shim pattern in `test_captured_inspector_arguments_explicit_path`
(`scripts/test_phase02_live_evidence.py:543-638`) is the template for building a fake responder
without a live OpenRouter/engine/gateway process.
**Warning signs:** A BU-02 closure claim that does not name three distinct scenarios (success,
early, post-upload) each with an assertion on both file existence and byte/hash equality.

### Pitfall 5: Reserved notice codes look "already wired" but are not emitted anywhere

**What goes wrong:** Assuming `NoticeCode::IndexRebuildFailed` / `IndexStale` /
`IndexGenerationMismatch` are production-ready because they exist in the generated Rust enum and
round-trip via `as_str_name()`.
**Why it happens:** They were pre-declared in Phase 6's D-74 wire-contract consolidation
(`proto/lancet/v1/lancet.proto:95-98`, `engine/src/pb/lancet/v1/lancet.v1.rs:339-341,364-366`)
specifically so 6.1 wouldn't need a second protobuf change — but no emission site exists yet. A
test in `workflow_phase5.rs:3758-3763` currently allowlists all three with the literal rationale
string `"reserved for Phase 6.1"`, which will silently keep passing even if 6.1 ships without
wiring them, because the test only asserts the rationale string is non-empty
(`workflow_phase5.rs:3766-3773`), not that it names a real file/line.
**How to avoid:** Treat updating those three allowlist entries to real `"engine/src/....rs:NNN
emission site"` strings as part of the phase's acceptance criteria (mirrors how Phase 6 itself
retired the `"Phase 6 plan 06-08/06-09/06-10/06-11 emission site"` entries for its own new codes).
**Warning signs:** `git diff` for this phase touching zero lines in `workflow_phase5.rs`'s
`published_manifest` table.

## Open Questions

1. **Where exactly should the shared `{generation, nodes_version}` state live?**
   - What we know: `Bm25IndexStore` already provides the exact atomic-swap shape needed
     (`Arc<RwLock<Arc<T>>>`); D-24 needs the BM25 index, the generation label, and the LanceDB
     version-to-checkout to move together as one unit so a single swap updates all three
     consistently.
   - What's unclear: whether to (a) widen `Bm25Index` itself to carry `generation`/`nodes_version`
     fields, (b) wrap it in a new small struct (e.g. `CorpusSnapshot { bm25: Bm25Index, generation:
     String, nodes_version: u64 }`) and swap that instead, or (c) keep three separate cells updated
     in careful sequence (riskier — reintroduces the "not really atomic" problem D-21 exists to
     rule out).
   - Recommendation: option (b) — a small wrapper struct swapped as a single `Arc` — keeps
     `Bm25Index` itself unchanged (still testable/constructible in isolation, as today's unit tests
     do) while satisfying D-21's single-swap atomicity requirement. The plan should make this an
     explicit design decision in its first task, not leave it implicit.

2. **Exact debounce window value.**
   - What we know: D-23 requires "debounced/coalesced" behavior; 06-CONTEXT.md's Claude's
     Discretion list explicitly leaves the window value open, "provided it is documented."
   - What's unclear: no numeric default is suggested anywhere in the decision record or the
     codebase's existing timeout conventions (which range from hundreds of ms to tens of seconds
     depending on the node).
   - Recommendation: pick a value in the low-single-digit-seconds range (e.g. 2–5s) as a starting
     default, configurable via the new fail-closed env key, and document the reasoning (balances
     "burst of documents → one rebuild" against "user waits too long after a single-document
     upload to see it in BM25 results") directly in the plan.

3. **Does the D-21 concurrency assertion test need real concurrency (two Tokio tasks racing) or is
   a sequential "swap between two calls" test sufficient?**
   - What we know: D-21 explicitly says "No fault-injection seam required for this property," and
     the existing `Bm25IndexStore` type is already `RwLock`-based, which makes a genuinely
     concurrent read-during-write race straightforward to construct in a `#[tokio::test]` using
     `tokio::join!` around one query future and one swap future with a controlled ordering
     (e.g. a oneshot channel gating the swap until the query has read the snapshot Arc but before
     it finishes using it).
   - What's unclear: whether "exactly one generation" is best proven by true interleaving or by a
     simpler before/after snapshot comparison, given D-21 explicitly disclaims needing a
     fault-injection seam.
   - Recommendation: default to the simpler before/after form (query, trigger a manual rebuild
     call directly — not via the debounce timer — then query again, assert the two snapshots carry
     different but individually-consistent generations) unless the plan-checker or verifier flags
     it as insufficiently rigorous; escalate to true task-interleaving only if that objection is
     raised, since D-21's own text signals the simpler form was anticipated as sufficient.
