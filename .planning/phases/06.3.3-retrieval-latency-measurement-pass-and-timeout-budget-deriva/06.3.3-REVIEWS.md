# Cross-AI Plan Review — Phase 06.3.3

## Cursor Review

### Summary

The four plans can achieve the phase goal: they put store truth before
measurement, commit decision inputs before seeing data, refuse to treat clipped
percentiles as true tails, keep production writes behind a disposition gate, and
close on a blocking spend decision. Wave order and the explicit supersession of
`06.3.3-PATTERNS.md`'s `is_usable` filter are sound. Two instrument holes would,
however, recreate the original defect if execution follows the plans literally:
node-timer expiry never writes a duration, while inner `graph_operation` expiry
completes the node with a `GRAPH_TIMEOUT` notice; and the live SSE query path has
a hardcoded 300-second read timeout that is not lifted by
`EvalSettings.gateway_timeout_secs`.

### Strengths

- The 2026-09-03 failure is correctly diagnosed. `config/config.toml:44-49`
  records the nested 4,000 ms graph operation and 15,000 ms graph node budgets.
  Plan 01's strict inequality is intentionally stronger than the equality
  accepted by `engine/src/config.rs:321-329`.
- A distinct measurement record is necessary because `RunRecord` forbids extra
  fields (`eval/src/lancet_eval/journal.py:45-48`) and resume identity currently
  keys only `(corpus, question_id, graph_arm)` (`journal.py:70-72,99-100`).
- Two adjacent arms expose the otherwise uninstrumented inner graph budget.
  `ExtractGraphContextNode::run` embeds and then early-returns for graph-off
  (`engine/src/workflow/nodes/graph_context.rs:72-105`), while graph-on proceeds
  through `query_graph` under the inner timeout (`graph_context.rs:107-120`).
- Environment-only raised budgets match the settings stack:
  `engine/src/config.rs:658-731` applies base config, eval overlay, then workflow
  timeout environment overrides, and `engine/src/service.rs:113-128` threads the
  resolved values into the runner and graph node.
- The dedicated measurement run directory avoids `resolve_run_dir`'s
  date/corpus glob (`eval/src/lancet_eval/cli.py:224-225`) and remains committable
  under `.gitignore:62-63`.
- Removing `is_usable` from latency/trend analysis is required because
  `eval/src/lancet_eval/usability.py:16-40` drops error outcomes and hard node
  failures—the clipped retrieval population this phase needs to inspect.
- Store inspection is correctly ordered before timeout work. The inspector
  currently only accepts `--document-id`
  (`engine/src/bin/inspect_lancedb.rs:342-357`), while table-open failures are
  already fail-closed (`engine/src/db/mod.rs:130-151`).
- Provider generation-budget derivation is executable:
  `engine/src/config.rs:333-344` requires twice the provider timeout, currently
  30 seconds in `config/config.toml:89`.
- Production config writes remain behind an explicit disposition gate, and the
  phase does not seed spend from the historical `$0.0199` figure.

### Concerns

- **HIGH — The specified censoring detector cannot see all engine clips.**
  `NodeCompletedEvent` carries `duration_ms`
  (`proto/lancet/v1/lancet.proto:207-211`), but `NodeFailedEvent` does not
  (`lancet.proto:213-218`). Node timer expiry returns `NodeError::timeout`
  (`engine/src/workflow/runner.rs:386-388`) and emits only `node_failed`
  (`runner.rs:467-480`), so a clipped node appears as a missing timing, not
  `duration >= ceiling`. Inner graph timeout is different again:
  `graph_context.rs:117-119,162-180` emits `NoticeCode::GraphTimeout` and returns
  success. `eval/src/lancet_eval/dimensions.py:11,492-499` already recognizes
  this notice.
- **HIGH — Raising `gateway_timeout_secs` does not lift the live SSE ceiling.**
  `eval/src/lancet_eval/client.py:207-216` hardcodes
  `httpx.Timeout(..., read=300.0, ...)` on `connect_sse`; `run.py:205-208`
  independently hardcodes the client timeout. The per-request value wins.
  `question_deadline_secs` is applied (`run.py:224`,
  `client.py:243-245`), but `gateway_timeout_secs` only reaches preflight paths
  such as `preflight.py:628`.
- **MEDIUM — Inner-budget derivation is under-specified.** Pooling node
  percentiles across graph-on and graph-off, then independently taking inner
  percentiles, can violate `graph_node >= query_embedding + graph_operation`
  (`engine/src/config.rs:321-329`). The plan does not define how to resolve that
  conflict or how an inner timeout pile-up is classified.
- **MEDIUM — Spend fallback undercounts embedding cost.** The proposed
  `workflow_meta.prompt_tokens` and `completion_tokens`
  (`eval/src/lancet_eval/journal.py:40-41`) cover generation, while every query
  also pays for the embedding model in `config/config.toml:82-83`.
- **MEDIUM — Span corroboration is not available from the journal.**
  `embedding_request` is not one of the retained graph span names
  (`engine/src/telemetry/mod.rs:45-47`), and OTLP export is optional.
- **MEDIUM — Canary gold data contains no graph entity IDs.** The canary file has
  questions and `require_graph_node`, while gold records carry fact text.
  `fetch_neighborhood` rejects non-UUID seeds
  (`engine/src/graph/mod.rs:351-356`), so Plan 02 must define name-to-entity
  matching rather than imply direct ID lookup.
- **MEDIUM — Neighbourhood inspection risks implementing a second BFS.**
  Production calls `graph::fetch_neighborhood`
  (`engine/src/service.rs:328-329`,
  `engine/src/graph/mod.rs:345-350`). The inspector should reuse it and state
  that a structural degree probe is not a replay of query-time semantic seeding.
- **MEDIUM — The planned sample size may empty analysis strata.** Several
  hundred records split by two arms, question type, segment, and early/late
  windows can leave cells too small for the declared bootstrap analysis.
- **MEDIUM — Plan 02/04 verification commands conflict with repository policy.**
  `AGENTS.md` documents pre-existing `--all-targets` clippy and format findings;
  those commands cannot be treated as regression gates without a scoped
  baseline.
- **LOW — Plan 03 is marked autonomous despite engine restarts and paid API
  spend.** The mechanics are careful, but the operational blast radius remains
  material.

### Suggestions

1. Define censoring as the union of timings at/above a ceiling, timeout-kind
   `node_failures`, and typed `GRAPH_TIMEOUT` notices. A timeout failure is a
   lower bound at the ceiling; an unrelated missing timing remains a separate
   instrumentation failure.
2. Name `eval/src/lancet_eval/client.py:207` in Plan 01 and derive the actual
   `connect_sse` read timeout from recorded settings.
3. Pin graph derivation strata: graph-on for outer graph-node observations,
   graph-off for query embedding, paired on-minus-off for graph operation, with
   timeout pairs excluded or censored and an explicit nesting-conflict policy.
4. Require spend accounting to include embeddings, not only generation tokens.
5. Reuse `graph::fetch_neighborhood`; define case-folded entity-name lookup for
   canary evidence and record entity ID hits/misses.
6. Compute the required N after thresholds land so every arm/type/segment/window
   cell meets the bootstrap minimum.
7. Treat span corroboration as optional and do not claim `embedding_request` is
   retained unless telemetry configuration is changed.
8. Scope clippy/format regression checks to touched targets and update all
   `scripts/engine-test-targets.sh` count pins together.
9. State whether decay joins measurement records to gold metadata or stores
   `question_type` directly.

### Risk Assessment

**MEDIUM.** The design is unusually well aligned with the phase goal, but the
node-failure/notice censoring paths and hardcoded SSE ceiling can still produce a
confident, reproducible budget from censored data. Close those before Wave 2.

## Antigravity Review

### Summary

The phase presents a rigorous experimental and statistical methodology for
resolving the 2026-09-03 run in which retrieval observations piled up at the
configured ceiling. The plans establish store truth, build a censoring-aware
stdlib analysis spine, run a two-segment/two-arm measurement pass under raised
environment ceilings, and derive production budgets behind a blocking spend
decision. The main operational hazards are mutation from Plan 01's live
calibration run before the Plan 02 baseline, a canary deadlock when the surviving
store lacks required graph entities, and incomplete coverage of Rust code
defaults and tests when Plan 04 writes new production budgets.

### Strengths

- Censoring is explicitly detected and propagated instead of being treated as a
  true percentile; environment workflow overrides are supported at
  `engine/src/config.rs:698-732`.
- Paired graph arms match the early-return control flow in
  `engine/src/workflow/nodes/graph_context.rs:72-105` and give a practical input
  for inner-budget decomposition.
- Statistical thresholds are committed before measurement, preventing post-hoc
  selection.
- Read-only store verification precedes timeout derivation and records graph
  population/degree evidence.
- Strict non-zero nesting slack improves on the equality accepted by
  `engine/src/config.rs:321-330`.
- Cheap-model generation latency is correctly prevented from setting the
  production generation-node timeout, which is tied to
  `engine/src/config.rs:333-344`.
- The analysis avoids adding NumPy/SciPy and stays within the dependency posture
  visible in `eval/pyproject.toml:10-19`.

### Concerns

- **HIGH — The live calibration micro-pass can perturb the as-is baseline.**
  Plan 01 drives real queries, while workflow execution persists checkpoints
  (`engine/src/workflow/runner.rs:328-343`,
  `gateway/db/schema.eval.hcl:138-172`). Plan 02 is scheduled in parallel to
  record starting checkpoint counts, and Plan 03 requires those counts to remain
  unchanged. Execution order can therefore contaminate the baseline or make its
  later invariant fail.
- **HIGH — Required graph canaries can deadlock the phase after an empty-store
  finding.** Two canaries require a graph node
  (`eval/corpora/multihop_rag/canary.jsonl:5-6`) and
  `eval/src/lancet_eval/preflight.py:548-560` fails when none is returned. Plan 02
  permits suspending graph questions when the graph is unpopulated, while Plan
  03 still makes canary success an unconditional prerequisite.
- **MEDIUM — Plan 04 omits code defaults and a production test.**
  `engine/src/tests/workflow_phase5_production.rs:37-47` hardcodes current
  default node timeouts, sourced from default functions in
  `engine/src/config.rs:125-145`. Leaving those defaults untouched creates
  config divergence; updating them without adding the production test to Plan
  04 breaks the test suite.
- **MEDIUM — Ordinal requirements need to distinguish journal order from
  logical order.** `eval/src/lancet_eval/run.py:213-225` uses a thread pool, so
  completion order can differ from dispatch order. Analysis should sort by the
  recorded ordinal, then reject duplicates/gaps, rather than require physical
  journal lines to be monotonic.
- **LOW — Test count accounting must update both pins.**
  `scripts/engine-test-targets.sh:51-58` computes and pins `TOTAL`; raising only
  `BIN_INSPECT_COUNT` still fails the gate.

### Suggestions

1. Mock the Plan 01 tracer path or run it against scratch state; do not issue
   calibration queries against the live evaluation database before the baseline.
2. Carry Plan 02's graph-population disposition into Plan 03 preflight so an
   explicitly suspended graph question does not create an impossible canary
   prerequisite.
3. Add `engine/src/config.rs` and
   `engine/src/tests/workflow_phase5_production.rs` to Plan 04 if the production
   defaults are intended to change together.
4. Sort parsed records by ordinal before checking uniqueness, gaps, and segment
   continuity.
5. Update both `BIN_INSPECT_COUNT` and `TOTAL` in the engine test target script.

### Risk Assessment

**MEDIUM.** The statistical and systems design directly addresses the historical
failure, but baseline mutation and graph-canary coupling can block or invalidate
the pass unless the plans make their ordering and disposition flow explicit.

## Consensus Summary

Both source-grounded reviewers rate the plan set **MEDIUM risk** and agree that
its architecture is fundamentally sound: store truth precedes derivation,
measurement is paired and two-armed, censoring is treated explicitly, thresholds
are pre-committed, graph timeout nesting is stricter than the engine's current
validation floor, environment overrides avoid accidental committed budget
changes, and production writes remain gated.

The reviews also expose a key distinction: the plans have the right *policy* for
censoring, but the implementation contract must name the engine's actual timeout
signals. A robust revision should incorporate both reviewers' operational
findings before execution rather than treating them as post-run analysis notes.

### Agreed Strengths

- Store inspection is correctly ordered before timeout derivation.
- Two adjacent graph arms are the correct observable basis for inner graph
  decomposition.
- Pre-committed thresholds and censoring-aware outputs directly address the
  historical clipped-percentile failure.
- Strict graph-budget nesting and provider-derived generation constraints are
  stronger than ad hoc constants.
- Raised measurement ceilings remain process-local until an explicit production
  disposition.

### Agreed Concerns

1. **Canary/store coupling is incomplete.** Missing canary entities need a
   defined name-to-entity lookup and the Plan 02 suspension result must flow into
   Plan 03 preflight; otherwise an empty or mismatched graph can deadlock the
   measurement pass.
2. **Timeout-default updates need a complete source/test sweep.** Plan 04 must
   settle whether Rust code defaults change with `config.toml`, update the
   hardcoded production timeout test accordingly, and use verification commands
   compatible with the repository's documented pre-existing findings.
3. **Engine test count pins must move together.** Adding inspector tests requires
   updating both the target-specific count and aggregate total.
4. **The derivation contract needs tighter strata and ordering language.**
   Recorded ordinals—not journal line order—are authoritative, and graph-on,
   graph-off, inner-timeout, and node-timeout populations cannot be pooled
   without explicit rules.

### Divergent Views

- Cursor found two additional **HIGH** call-path defects: timeout failures and
  graph notices are not represented by `duration >= ceiling`, and the SSE
  measurement path hardcodes a 300-second read timeout. Antigravity praised the
  censoring policy but did not trace those mechanisms. The source evidence makes
  Cursor's findings blockers before Wave 2.
- Antigravity found a separate **HIGH** ordering collision: Plan 01's live
  calibration can mutate PostgreSQL checkpoint state before or during Plan 02's
  baseline. Cursor did not flag this. The plans should make calibration
  state-isolated or sequence it before a fresh baseline.
- Antigravity recommends changing Rust in-code defaults with production config;
  Cursor focuses on config and existing literal assertions. Plan 04 must state
  the intended source-of-truth relationship rather than leave the two default
  surfaces ambiguous.

### Recommended Planning Disposition

Revise the plans before execution:

1. Amend Plan 01/03 censoring to consume timeout-kind node failures and
   `GRAPH_TIMEOUT` notices, and lift/record the actual SSE read timeout.
2. Isolate the calibration micro-pass from the surviving eval database or move
   the authoritative baseline after calibration.
3. Flow the store-baseline graph disposition into canary preflight and define
   entity-name resolution.
4. Define graph derivation strata, nesting-conflict handling, spend coverage,
   and sample-size minima.
5. Complete Plan 04's Rust default/test/config sweep and correct the test-count
   and scoped lint gates.
