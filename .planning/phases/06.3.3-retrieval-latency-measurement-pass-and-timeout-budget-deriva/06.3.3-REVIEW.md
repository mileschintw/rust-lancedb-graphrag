# Phase 06.3.3: Code Review Report

**Reviewed:** 2026-09-07T00:00:00Z
**Depth:** standard
**Files Reviewed:** 20
**Status:** issues_found

## Summary

This phase derives six production workflow timeout budgets from a measured-latency
harness and wires them into `config.toml` / `config.example.toml` / `engine/src/config.rs`.
The three files stay numerically in sync for the six budgets that changed
(`query_embedding_timeout_ms`, `retrieve_timeout_ms`, `graph_operation_timeout_ms`,
`graph_node_timeout_ms`, `prompt_timeout_ms`, `generation_node_timeout_ms` — verified
identical across all three sources, and the nesting-invariant arithmetic documented in
the comments checks out: `645 + 38595 = 39240 < 45674` with 6434ms slack, `645 < 16647`
with 16002ms slack).

However, the measurement/derivation pipeline in `eval/src/lancet_eval/measure.py` and
`eval/src/lancet_eval/decay.py` has real, unguarded gaps in exactly the area this review
was asked to scrutinize: whether censoring can silently corrupt the numbers that get
baked into production config. Both `run_measurement_pass()` (the library entry point
behind `lancet-eval measure`) and `analyze_decay()` compute a proper 5-label censoring
taxonomy but then fail to actually apply it before deriving percentiles/budgets or
before pairing ordinals with latencies for trend detection. Separately,
`EffectiveRagSettings::validate()` in `engine/src/config.rs` never calls the
already-implemented `validate_against_provider()` guard, so the engine can start with a
`generation_node_timeout_ms` that violates the very provider-contract invariant this
phase's design (and its own tests) assert must hold.

None of these three issues are exercised by the existing test suites (`test_measure.py`,
`test_decay.py`, `tests.rs`), so they will not surface until real censored data or a
provider-timeout misconfiguration is encountered in production.

## Critical Issues

### CR-01: `run_measurement_pass()` derives budgets from raw durations without excluding censored (timed-out) observations

**File:** `eval/src/lancet_eval/measure.py:437-463`

**Issue:** `run_measurement_pass()` computes a proper censoring census:

```python
census = compute_censoring_census(analysis_records, ceilings)
durations = extract_node_durations(analysis_records)
```

`compute_censoring_census` correctly classifies each `(record, node)` observation into
`OBSERVED`, `CENSORED_AT_CEILING`, `CENSORED_NODE_TIMEOUT`, `NOT_REACHED`, or
`INSTRUMENT_GAP` (see `lancet_eval/latency.py:53-130`). But `extract_node_durations`
(same file, `latency.py:174-185`) pulls every `duration_ms` value straight off
`node_timings` with no reference to the census — including durations for observations
the census itself just labeled `CENSORED_AT_CEILING` (a node that hit/exceeded its
timeout ceiling and would have run longer had it not been cut off).

Those raw, right-censored durations then flow straight into the percentile/budget
derivation:

```python
pct = percentile_with_ci(
    vals, p=thresholds.derivation_percentile, seed=thresholds.bootstrap_seed
)
if pct.is_available:
    p_rec = derive_budget(cfg_key, pct, thresholds=thresholds)
```

`percentile_with_ci` is never told about the censored count (it defaults to
`censored_count=0`), so `is_lower_bound` is always `False` and `censored_status` in the
resulting `ProposedBudgetRecord` always reads `"clean"` — even when a meaningful
fraction of the sample sat at the timeout ceiling. This is exactly the scenario the test
fixture in `eval/tests/conftest.py:26-34` documents as having actually happened
("904 of 1000 retrieval observations ... sat at the 10000ms retrieve_timeout_ms
ceiling"). If that data were fed through this code path, the resulting p95 would be
clamped at the ceiling and the derived budget would be silently too low — mislabeled as
clean, uncensored data.

**Fix:** Cross-reference the census with `durations` before calling
`percentile_with_ci`, e.g. only include a duration if
`census.node_counts[node]["OBSERVED"]` covers it, or (simpler) have
`extract_node_durations` accept the ceiling map and drop/count any value
`>= ceiling_ms`, then pass the resulting drop count into
`percentile_with_ci(vals, ..., censored_count=dropped)` so `is_lower_bound` /
`censored_status` reflect reality instead of always reporting `"clean"`.

### CR-02: `analyze_decay()` silently misaligns ordinals and latencies when a record is dropped without being classified as censored

**File:** `eval/src/lancet_eval/decay.py:489-521`

**Issue:**

```python
for r in sorted_records:
    ord_val = int(r.ordinal)
    ordinals.append(ord_val)          # appended unconditionally
    ...
    if f is not None and getattr(f, "error_kind", None) == 1:
        censored_count += 1
        continue

    if t is not None and getattr(t, "duration_ms", None) is not None:
        dur = float(t.duration_ms)
        latencies.append(dur)         # only appended when timing present
        ...
```

`ordinals` gets one entry per record; `latencies` only gets an entry when the node has
a completed timing. A record is only excluded from `latencies` *and* counted via
`censored_count` when its own failure has `error_kind == 1` (node timeout). Any other
reason for a missing timing on the analyzed node — a non-timeout failure on that node,
an upstream failure that prevented the node from running at all (e.g. `ReformulateQuery`
failing with a validation error before `RetrieveHybrid` starts), or a transport-level
exception in `measure_one`'s `except Exception` branch (`measure.py:267-280`, which
produces a `MeasurementRecord` with empty `node_timings` **and** empty `node_failures`)
— drops the record from `latencies` while leaving `censored_count` at 0 and leaving the
record's ordinal in `ordinals`.

Downstream, the trend prong does:

```python
trend_res = compute_theil_sen_trend(
    ordinals[: len(latencies)],
    latencies,
    thresholds=thresh,
    censored_count=censored_count,
)
```

Because `censored_count` is 0 in this scenario, `compute_theil_sen_trend` does not take
its early-refusal path — it proceeds to pair `ordinals[i]` with `latencies[i]` for
`i in range(len(latencies))`. But `ordinals[:len(latencies)]` is just a truncated prefix
of the full ordinal sequence, not the ordinals of the records that actually contributed
to `latencies`. Once any qualifying gap occurs before the last record, every subsequent
`(ordinal, latency)` pair fed into the Theil-Sen slope and Mann-Kendall statistic is
mismatched against the wrong query index. This can flip the sign/significance of the
reported decay trend without any error, warning, or `is_censored` flag — the exact
"silently misleading numbers" failure mode called out for this review.

**Fix:** Build `ordinals` and `latencies` as one parallel structure (e.g. append
`(ord_val, dur)` tuples only when a usable latency exists, then unzip), or track a
"dropped for reasons other than a timeout" counter and fold it into
`censored_count`/the refusal path so misaligned pairs are never sent into
`compute_theil_sen_trend`.

### CR-03: Provider-contract timeout invariant is implemented but never enforced at engine startup

**File:** `engine/src/config.rs:333-344, 590-649`

**Issue:** `WorkflowSettings::validate_against_provider()` exists specifically to check
the invariant this phase's derivation logic depends on and documents
(`generation_node_timeout_ms >= 2 * generation_timeout_secs * 1000`, matching
`derive_provider_contract_budget()` in `eval/src/lancet_eval/latency.py:372-398`
and the config comment "generation_node (provider contract: 2×30s + 5s slack)"). It is
exercised only in tests (`engine/src/tests.rs:395,480` call it directly). It is **never
called from `EffectiveRagSettings::validate()`**:

```rust
pub fn validate(&self) -> Result<(), String> {
    self.workflow.validate()?;          // nesting invariant only
    self.retrieval.validate()...
    ...
    if self.generation_timeout_secs == 0 { ... }
    ...
    Ok(())
}
```

and `main.rs` only calls `EffectiveRagSettings::try_from_settings(&settings)`, which
calls this `validate()`. So the guard that ties `generation_node_timeout_ms` to
`openrouter.generation_timeout_secs` is dead at runtime: the engine will start
successfully with, for example, `generation_timeout_secs` raised to 40s (via
`LANCET_OPENROUTER__GENERATION_TIMEOUT_SECS`-style env override, which is unvalidated
elsewhere too) while `generation_node_timeout_ms` stays at 65000 — violating the
`2 * 40 * 1000 = 80000 > 65000` contract this phase's own derivation logic is built
around, without any startup error. In production this manifests as the workflow-level
timeout firing mid-retry on the provider path, silently discarding otherwise-successful
generations.

**Fix:** Call `self.workflow.validate_against_provider(self.generation_timeout_secs)?`
from inside `EffectiveRagSettings::validate()` (or from `try_from_settings` right after
constructing `effective`), so the check that already exists and is asserted by tests is
actually enforced on every settings load, not only in `engine/src/tests.rs`.

## Warnings

### WR-01: Two of the "six derived budgets" are never actually derived from measured data, but are reported as if they were

**File:** `eval/src/lancet_eval/measure.py:426-473`

**Issue:** `WORKFLOW_NODE_ORDER` (imported from `latency.py`) only contains the five
top-level runner nodes (`ReformulateQuery`, `ExtractGraphContext`, `RetrieveHybrid`,
`AssemblePrompt`, `GenerateAnswer`) — there is no per-record instrumentation for the two
*inner* sub-timers, `query_embedding_timeout_ms` and `graph_operation_timeout_ms`.
Consequently the derivation loop can only ever populate
`proposed_budgets["graph_node_timeout_ms"]` (from `ExtractGraphContext`'s outer
duration), never the two inner keys. The fallback path:

```python
if "query_embedding_timeout_ms" not in proposed_budgets:
    proposed_budgets["query_embedding_timeout_ms"] = effective_cfg.get(
        "query_embedding_timeout_ms", 10000
    )
if "graph_operation_timeout_ms" not in proposed_budgets:
    proposed_budgets["graph_operation_timeout_ms"] = effective_cfg.get(
        "graph_operation_timeout_ms", 4000
    )
```

always fires for these two keys — they are simply carried forward from whatever is
already configured (or a hardcoded default), never measured. The resulting
`proposed_budgets`/`nesting_rep.resolved_budgets` dict is reported under the CLI command
whose docstring says "derive proposed timeout budgets" without distinguishing which
entries are measured vs. pass-through, which is misleading for anyone reading the
summary JSON and assuming all six numbers reflect fresh measurement.

**Fix:** Mark the two inner-budget entries in `proposed_records`/the summary with an
explicit `"rule": "carried_forward_unmeasured"` (mirroring the existing
`is_invariant_driven` / `rule` fields already used elsewhere in this module) so
consumers of the JSON can tell measured values apart from pass-through values.

### WR-02: `run_measurement_pass()`'s self-description contradicts its own behavior and the CLI's advertised purpose

**File:** `eval/src/lancet_eval/measure.py:486-489`, `eval/src/lancet_eval/cli.py:770`

**Issue:** The function embeds this note in every summary it writes:

```python
"calibration_note": (
    "This micro-pass is calibration of the instrument only and "
    "is not an input to any derived budget."
),
```

but the same function computes and writes `proposed_budgets` via `derive_budget()` calls
just a few lines earlier, and the CLI command that calls it
(`measure_latency` in `cli.py`) is documented as: `"""Run two-armed latency measurement
pass and derive proposed timeout budgets."""`. One of these three statements is wrong;
as written, a caller reading the summary JSON is told the numbers it just computed don't
count, while the CLI help text says the opposite.

**Fix:** Decide which claim is authoritative and make the other two match — either strip
`derive_budget` calls from this micro-pass path entirely (if it's truly calibration-only)
or drop/rephrase the `calibration_note`.

### WR-03: `settings_path()` in the inspect tool does not honor `LANCET_CONFIG_DIR`, unlike the engine's main config loader

**File:** `engine/src/bin/inspect_lancedb.rs:312-330`

**Issue:** `engine/src/config.rs::load_settings()` resolves the config base path with
explicit `LANCET_CONFIG_DIR` handling (`config.rs:659-672`). `inspect_lancedb.rs`'s own
`settings_path()` (used to find `engine.lancedb_path` when `--lancedb-path` is not
passed) only checks `../config/config.toml` existence vs. `config/config.toml`, with no
`LANCET_CONFIG_DIR` awareness at all. Running the inspection binary from a directory
layout that relies on `LANCET_CONFIG_DIR` (as the main engine binary supports) will
silently resolve to the wrong config file or fail to find one, instead of honoring the
same override the rest of the system supports.

**Fix:** Reuse `LANCET_CONFIG_DIR` resolution logic (or better, share a single helper
between `main.rs`/`config.rs` and `inspect_lancedb.rs`) so both entry points agree on
where config lives.

## Info

### IN-01: `check_provider_allowance` and other duplicated request/record-building blocks between `measure.py` and `drive_measurement_pass.py`

**File:** `eval/scripts/drive_measurement_pass.py:244-326` vs `eval/src/lancet_eval/measure.py:196-280`

**Issue:** The per-query execution + `MeasurementRecord` construction logic in
`drive_pass()` (roughly 80 lines) is a near-verbatim duplicate of `measure_one()` in
`measure.py`, differing only in how the `except` branch is inlined instead of factored
into a shared helper. `drive_measurement_pass.py` already imports `measure_one` indirectly
via `MEASUREMENT_ARMS`/`MeasurementRecord`/`check_provider_allowance`/`compute_spend`
from `lancet_eval.measure`, but stops short of reusing `measure_one` itself.

**Fix:** Have `drive_pass()` call `measure_one()` directly instead of re-implementing its
body, to avoid the two copies drifting (e.g. `dropped_node_timings` handling, or field
lists) as the schema evolves.

### IN-02: `NodeFailed` events are appended to `node_failures` in `client.py` with no cap, while `node_completed` events are capped at 64

**File:** `eval/src/lancet_eval/client.py:287-295`

**Issue:** `node_completed` frames are explicitly capped (`if len(node_timings) < 64: ...
else: dropped_node_timings += 1`) to bound memory/record size, but `node_failed` frames
(`case "node_failed": node_failures.append(...)`) have no equivalent cap. A pathological
stream emitting many `node_failed` events (e.g. a retry storm) has no bound on
`node_failures` list growth for a single record.

**Fix:** Apply the same cap-and-count pattern used for `node_timings` to `node_failures`,
or document why an unbounded list is acceptable for this field specifically.
