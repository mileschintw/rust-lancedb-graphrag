<objective>
Establish what is actually in the surviving eval store before anything measures it, and record the
starting state the measurement pass will consume.

Purpose: the graph arm of the 2026-09-03 run produced 494 timeouts at the inner graph budget and
essentially no facts. That is consistent with a slow graph, and equally consistent with a graph
that was never populated — and those two findings send the phase in opposite directions. One is a
budget to derive; the other is an ingest defect and the graph-yield question is not a query
question at all. The roadmap makes this ordering explicit: population is verified before any
timeout work. Separately, the measurement pass consumes the store's "as-is" condition by running
against it, so the starting row counts must be captured while they still describe the original
state.

Output: a store-wide graph-population mode and a bounded neighbourhood mode on the existing
`inspect_lancedb` tool, and `06.3.3-STORE-BASELINE.md` recording population, degree distribution,
a hand-run traversal, the starting PostgreSQL checkpoint rows, and the canary-entity confirmation
06.3.2-03 deferred to this phase.
</objective>

  <behavior>
    - **Population counts:** invoked in graph-population mode against a store, the tool emits row counts for the nodes, edges, entities, entity-edges, documents and staged-documents tables in one machine-readable object.
    - **Degree distribution:** the same output carries the entity degree distribution — minimum, median, upper percentile and maximum degree — computed over the union of the entity-edge source and target columns.
    - **Isolated entities counted:** entities appearing in neither entity-edge column are counted and reported as an explicit isolated-entity count, not dropped from the distribution.
    - **Empty store:** run against a store whose entity and entity-edge tables are empty, the tool emits zero counts, an explicitly empty distribution and a stated marker that the graph is unpopulated — it does not error and does not omit the fields.
    - **Neighbourhood:** invoked with a seed entity UUID, the tool emits that seed's incident edges out to the stated hop bound, with the relation type and the neighbour identifier on each, by delegating to `graph::fetch_neighborhood`.
    - **Non-UUID seed:** a seed that is not a parseable UUID is rejected with a message saying so and naming the seed, and the message points at the entity-name mode as the way to obtain one — rather than surfacing `fetch_neighborhood`'s raw bridge error.
    - **Entity-name lookup:** invoked with a name, the tool case-folds it and returns every `entities` row whose `name` case-folds to the same value, emitting the `entity_id` and `entity_type` of each, ordered by identifier ascending.
    - **Name miss:** a name matching no entity emits an explicitly empty result echoing the queried name, exit status success — a miss is a finding, not an error.
    - **Name ambiguity:** a name matching more than one entity emits all matches rather than picking one, so an ambiguous canary entity is visible as ambiguous.
    - **Seed with no edges:** a seed present in the entities table with no incident edge emits an explicitly empty neighbourhood echoing the seed, not an error.
    - **Seed absent:** a seed not present in the entities table is reported as absent, naming the seed, distinctly from a seed that is present but isolated.
    - **Stable order:** two invocations against an unchanged store emit byte-identical output, because results are ordered by a stated key.
    - **Hop bound honoured:** raising the hop bound cannot return fewer edges, and the emitted result states the bound that produced it.
    - **Read-only:** every mode opens tables, counts and reads; no invocation creates, writes, compacts or deletes.
    - **Existing mode unchanged:** the document-scoped invocation produces exactly the output it produces today.
    - **Usage:** an invocation naming no mode, or naming two, exits non-zero with a usage message listing every mode.

  <action>
    Extend `inspect_lancedb` with two additional read-only modes. Keep the existing document-scoped
    mode exactly as it is; this is additive, and the tool is the sanctioned path for this inspection
    because it is the one D-05 names and the one that already opens the store through the validated
    database manager.

    Rework `main`'s argument loop so it selects among modes rather than requiring a document
    identifier. Today an unrecognised argument returns a usage error and `--document-id` is
    mandatory; both need to change, and the usage message must list every mode. Exactly one mode
    per invocation — reject zero and reject two, so an operator never has to guess which one ran.

    The graph-population mode takes no target and reports the whole store. Emit row counts for the
    six tables, the entity degree distribution, and the isolated-entity count, in one serialisable
    object printed as the existing mode prints its inspection. Compute degree over the union of the
    entity-edge source and target columns, since the relation is stored once per edge and an
    entity's degree is its appearances on either side. Count entities that appear on neither side
    explicitly: an isolated entity is a real structural fact about a graph built from sparse
    extraction, and dropping it from the distribution would make a mostly-disconnected graph read
    like a healthy one. When the entity or entity-edge table is empty, emit zeros, an empty
    distribution and an explicit marker that the graph is unpopulated — the caller needs the shape
    of the answer to be the same whether or not the graph exists, because an empty result here is a
    finding rather than an error.

    The neighbourhood mode takes a seed entity UUID and an optional hop bound with a stated
    default, and **delegates to `graph::fetch_neighborhood(db, seed, hop_cap, bidirectional)`**
    (`engine/src/graph/mod.rs:345-350`) rather than writing a second breadth-first expansion. That
    function is what production calls at `engine/src/service.rs:329`, it already enforces
    `clamp_hop_cap`, `MAX_FRONTIER_SIZE` and `MAX_TOTAL_EDGES`, and it already returns the bridged
    entities and entity-edges batches. A parallel implementation here would be a second definition
    of "neighbourhood" that could silently drift from the one under investigation — and an
    inspection whose traversal differs from production's is evidence about the inspector, not about
    the store. Emit each returned edge with its relation type and the neighbour it reaches.

    Distinguish four outcomes clearly: a seed that is not a parseable UUID, a seed that is absent
    from the entities table, a seed that is present with no incident edges, and a seed with a
    neighbourhood. `fetch_neighborhood` rejects a non-UUID seed at `graph/mod.rs:351-356` with a
    bridge error; catch that and report it as a usage problem naming the seed and pointing at the
    entity-name mode, rather than letting a raw `GraphSpikeError` surface. The present-but-isolated
    case is not an error — a sparsely-extracted entity legitimately has no edges — and conflating
    it with absence would make an inspection unable to tell "the entity was never extracted" from
    "the entity was extracted but connects to nothing", which is exactly the distinction this phase
    needs.

    Add a third mode: **entity-name lookup**. This exists because of a gap the cross-AI review
    surfaced and that would otherwise stall task 2. The canary set carries questions, gold fact
    text and `require_graph_node` flags — and no entity identifiers anywhere — while
    `fetch_neighborhood` accepts nothing but a UUID. Without a name-to-identifier bridge there is
    literally no way to run task 2's canary-entity confirmation. So: take a name, case-fold it,
    match against the non-nullable `name` column in `entities_schema` (`engine/src/db/mod.rs:249-262`),
    and emit every matching row's `entity_id` and `entity_type`, ordered by identifier ascending.
    Case-folding matters because extracted entity names carry the casing of whatever sentence they
    were pulled from, so an exact-match lookup would report false absences. Emit all matches rather
    than picking one, so an ambiguous name reads as ambiguous. A name matching nothing emits an
    explicitly empty result echoing the queried name at exit status success — a miss is one of the
    two findings this whole confirmation exists to produce.

    Record explicitly, in the tool's own output and in the record task 2 writes, that this
    structural probe is **not** a replay of query-time semantic seeding. Production does not look an
    entity up by name at all: `query_graph` (`engine/src/service.rs:469-520`) reaches
    `matched_entity_id` through embedding similarity gated by `seed_match_min_score`. So a healthy
    structural neighbourhood found here proves the graph contains the entity and its edges; it does
    not prove a real query would ever have reached it. Stating that boundary is what stops this
    inspection being over-read later.

    Order every emitted collection by a stated key so two runs against an unchanged store produce
    identical bytes. A recorded traversal that cannot be reproduced is not evidence.

    Bound the expansion. Give the hop bound a small default and a hard ceiling, and cap the total
    edges returned, so a hub entity in a dense region cannot make the tool run unbounded against a
    store this phase is not allowed to modify.

    Emit structural facts only: identifiers, types, counts, relation types and degrees. Never chunk
    content, entity or edge summaries, document raw content, or any embedding vector. The output
    goes into a committed phase record.

    Add tests in the existing test module following its fixture idiom, one per behavior bullet, and
