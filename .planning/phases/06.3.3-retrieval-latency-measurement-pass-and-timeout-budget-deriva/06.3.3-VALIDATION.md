# Phase 06.3.3 — Validation Strategy

> Per-phase validation contract for feedback sampling during execution.
> Seeded from `06.3.3-RESEARCH.md` § Validation Architecture.

> **Read this first.** This phase is planned at `--granularity coarse` and its acceptance
> criteria are **procedural, not value-bearing** — the numbers it depends on are produced by
> the measurement pass this phase itself runs. Validation therefore tests **the derivation
> machinery and its invariants**, never a specific millisecond value. A test asserting
> `retrieve_timeout_ms == 8000` would be wrong here; a test asserting *"the written budget
> equals the recorded p95 × the recorded multiplier, and the nesting invariant holds"* is right.

## Manual-Only Verifications

| Behavior | Requirement | Why Manual | Test Instructions |
|----------|-------------|------------|-------------------|
| The measurement pass reproduces original conditions | OBS-05 (D-22) | "Starting from the store and PostgreSQL checkpoint rows **as-is**" is an operator precondition, not an assertable state — re-seeding would destroy the very condition under test. | Before the pass, record store table row counts and PostgreSQL checkpoint row counts. Confirm no re-seed or compaction ran between recording and the pass. |
| Mid-run restart actually happened at the planned boundary | OBS-05 (D-21) | Restarting the engine process is an operator action outside the harness. | Record the wall-clock time and query ordinal of the restart; confirm it falls between the two segments in the journal. |
| Budget-blowing nodes were investigated as defects first | OBS-05 (D-16) | "Is this a defect or is it genuinely slow" is an engineering judgement, not an assertion. | For each node that blew a budget, record the investigation and its conclusion before widening. A widened budget with no disposition entry fails this check. |
