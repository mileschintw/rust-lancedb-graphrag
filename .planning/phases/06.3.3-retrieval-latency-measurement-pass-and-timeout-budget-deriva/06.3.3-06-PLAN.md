<objective>
Close VERIFICATION.md gap 3: the provider-attempt invariant that this phase's
`generation_node_timeout_ms = 65000` derivation rests on is dead code at runtime, and
`06.3.3-BUDGETS.md`'s own closing record claims otherwise.

Purpose: `WorkflowSettings::validate_against_provider` is correct in isolation and is exercised by
two unit tests, but nothing on the engine's startup path ever calls it.
`EffectiveRagSettings::validate()` calls `self.workflow.validate()` (the nesting invariant) and a
series of unrelated field checks; `try_from_settings()` calls `validate()` and nothing else. The
written value satisfies the invariant today (65000 >= 60000), so no user-visible defect exists yet —
but raising `generation_timeout_secs` past 32.5 s via `LANCET_OPENROUTER__GENERATION_TIMEOUT_SECS`
would start the engine successfully in violation of the provider contract, silently discarding
otherwise-successful generations mid-retry in production. That is exactly the class of silent
mis-sizing this phase exists to prevent.

Output: the guard wired into the startup path, every configuration in the repository made coherent
with it, a new regression test that fails if the wiring is removed again, and a corrected
"Engine startup proof" section.

**The fix is four sites, not one line — this is the plan's central finding.** VERIFICATION.md
prescribes a one-call addition to `validate()`. Direct source read during planning confirms that
addition, applied alone, turns the repository red and breaks the verify environment's ability to
boot:

1. `config/config.verify.toml` pairs `generation_timeout_secs = 30` with
   `generation_node_timeout_ms = 7000`. Required is 60000. The overlay violates the invariant.
2. `verify-ingestion.sh:105` exports `LANCET_ENV=verify` and line 133 starts the engine binary. With
   the guard live and the overlay unchanged, the engine refuses to start and the script cannot run.
3. `engine/src/tests/workflow_phase5_production.rs:670` loads config.toml + config.verify.toml
   through `try_from_settings` and `.expect(...)`s success.
4. `engine/src/tests.rs:404-462` overrides `generation_node_timeout_ms` to 8888 via environment and
   `.expect(...)`s `try_from_settings` success at line 454; `tests.rs:353` and `tests.rs:397-400`
   assert the verify overlay's 30 s / 7000 ms pair as a fact.

The verify overlay's incoherence is deliberate — the test wants the node timer to fire fast against
a slow generator — but it is incoherent nonetheless: a 7000 ms node budget cannot contain even ONE
30 s provider attempt. It is made coherent here, not exempted. `SlowLiveProvider`
(`workflow_phase5_production.rs:626-648`) hardcodes a 30 s sleep and never reads
`generation_timeout_secs`, so lowering the overlay's provider budget preserves everything the test
measures. This is recorded so a later reviewer reads it as a deliberate coherence repair rather than
collateral damage.

There is no spine to trace. Task 1 is itself the whole vertical path (settings load → validate →
refuse), which is as close to a tracer as this scope admits, so forcing the label would add ceremony
without information.
