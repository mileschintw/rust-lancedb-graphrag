The measurement pass produces the observed latencies; the planner applies the rule to derive the final values.

## Architecture Patterns

### Measurement Pass Structure (D-20, D-21)

**Entry Point:** `uv run --project eval lancet-eval measure --corpus multihop_rag --sample-size N --budget-multiplier MULT [--cheap-model MODEL]`

The pass must:
1. **Warm-up phase:** 5–10 queries to stabilize connection pools and embedding caches before recording begins.
2. **Measurement segment 1 (before restart):** Query count M₁ (e.g., 250–400 queries).
3. **Mid-run engine restart:** Stop the engine, wait for clean shutdown, restart it (captures D-21's process-state reset).
4. **Measurement segment 2 (after restart):** Query count M₂ = N − M₁.
5. **Persist to journal:** Every record must carry:
   - `question_id`, `question`, `graph_arm` (graph-on/off),
   - Wire diagnostics per D-01: `node_timings[]` (per-node `duration_ms`), `workflow_meta` (metadata),
   - Wall-clock `started_at_ms`, `completed_at_ms`,
   - `segment` (1 or 2, for D-21 discrimination),
   - `total_duration_ms`.
6. **Exit:** Clean completion or human-visible failure (D-10 preflight gate).

### Decay Detection Methodology

**Hypothesis pair (D-18):**
- **Budget hypothesis:** Flat-but-high latency across the pass, peak ≤ the original timeout values. ⟹ Budgets were too tight; widen them symmetrically.
- **Exhaustion hypothesis:** Upward trend in `total_duration_ms` with query ordinal. ⟹ Process or store state accumulates; restart discriminates.

**Detection strategy:**

1. **Ordinal trend (monot. decay pattern from 2026-09-03):** Use Mann–Kendall test on full run; Theil–Sen slope to estimate rate-of-change. Report significance *p*-value and 95% CI on slope.
   - **Confound 1:** Question difficulty varies across ordinal. **Mitigation:** Stratify by gold `question_type` (exists in corpus, currently unused). Trend should hold within each type.
   - **Confound 2:** Graph-on/off arm alternates every ~1 position (D-41 verified in 2026-09-03: median 1 apart, max 9). **Mitigation:** Stratify by arm; compare segment-1 graph-on vs segment-2 graph-on, not across arms.
   - **Confound 3:** OS page-cache state persists across engine restart; embedding-model server-side caching varies. **Mitigation:** Compare segment-1 tail (last ~50 queries before restart) vs segment-2 head (first ~50 after restart) and report the delta. If segment-2 head is higher, restart failed to reset retrieval latency (process state intact or fresh connection cost).

2. **Early-vs-late windowing (D-19):** Divide segment 1 into early (first 25%) and late (last 25%) windows. Compare p95 latency (or p99 if n ≥ 30 per window). Report as: "early p95 = XXms, late p95 = YYms, delta = ZZms" and *t*-test *p*-value on per-query differences between windows.

3. **Segment-boundary analysis (D-21):** Compare segment-1 tail vs segment-2 head per node type (`RetrieveHybrid`, `AssemblePrompt`, `GenerateAnswer`, etc.). If all node types reset latency in segment 2, ⟹ process state. If `RetrieveHybrid` stays elevated, ⟹ store state. Report per-node latency delta with 95% CI.

4. **Censoring check:** Count records at or above each budget threshold. If any budget was hit ≥5 times in the pass, report it as "censored" — the observed p95/p99 is a **lower bound**. Flag for D-16 investigation (is it a real bug or an insufficient budget?).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Percentile confidence bounds at n<30 | Custom formulas | Order-statistic / binomial / bootstrap CIs (e.g., `scipy.stats.binom_test`, or hand-rolled method from Devore) | Small n makes normal approx invalid; parametric methods are correct and published. |
| Trend detection on skewed, potentially auto-correlated data | Ad-hoc slope regression | Mann–Kendall + Theil–Sen (nonparametric, robust to outliers and heteroscedasticity) | Residuals in retrieval latency are non-normal due to p99 outliers; rank-based tests don't assume shape. |
| Significance testing for segment-boundary latency delta | Welch's *t*-test (assumes equal variance) | Permutation / bootstrap CI or Wilcoxon signed-rank (paired within arms, non-parametric) | Segment 1 vs 2 within the same arm (paired measures) and potentially unequal variance. |
| Multiplier choices | Picked intuitively ("5 seems safe") | Literature / domain justification + explicit false-timeout rate | Multiplier = 1.5 → ~13.4% false timeout rate at Gaussian; = 2.0 → ~2.3%. Domain trade-off: must be stated. |

## Common Pitfalls

### Pitfall 1: Censoring at Tight Budgets Hides the True Tail

**What goes wrong:** A budget of 10ms that fires on 50 queries reports p95 = 10ms exactly (the queries that timed out report ceiling latency). The true p95 is unknown (could be 12ms, could be 50ms). A multiplier applied to 10ms derives a too-tight budget for the re-drive.

**Why it happens:** The measurement apparatus makes timeouts unobservable by design — they're hard faults, not datapoints.

**How to avoid:** Before running the pass, set budgets **above** the suspected maximum (e.g., 2× the current broken value). Report any censoring (count of records at/above ceiling per node). If censored records exist, flag them in the journal and note in the planner's decision: "p95 is a lower bound; true max unknown."

**Warning signs:** Count histogram of `node_timings[*].duration_ms` shows a spike at the budget ceiling. Example: `retrieve_timeout_ms = 10000` original, you set it to `20000` for the pass, but histogram shows 120 records at 20000ms exactly. ⟹ Retrieve latency distribution extends beyond 20ms; investigate as D-16 bug candidate.

### Pitfall 2: Decay Signal Confounded by Question Difficulty or Arm Imbalance

**What goes wrong:** Segment 2 shows higher p95 latency, but that segment happened to draw harder questions (lower retrieval yield), not because of state accumulation.

**Why it happens:** Random sampling without stratification can produce arm imbalance across segments or type imbalance.

**How to avoid:** Report latency stratified by (`segment`, `graph_arm`, `question_type`). A true exhaustion signal must hold within stratum.

**Warning signs:** Segment-2 p95 is elevated, but segment-2's average `graph_node_count` is lower than segment-1, suggesting harder questions. Cross-tabulate before concluding decay.

### Pitfall 3: Restart Doesn't Reset Because Connection Pool Survives

**What goes wrong:** Engine restarts, but connection to PostgreSQL (eval checkpoint table) or embedding-model server are pooled elsewhere or cached. Segment-2 latency stays elevated, masking whether *database* state (not process state) is the culprit.

**Why it happens:** Modern async libraries and OS-level connection pooling survive process restarts; only client-side process state is cleared.

**How to avoid:** After the restart, run a standalone `lancet-eval probe` query (preflight, single question) to verify the path is clean before segment 2. Record that probe's latency and compare to segment-1 baseline.

**Warning signs:** Segment-2 head (`first 10 records`) latency is not lower than segment-1 tail, even though all engine memory should be fresh.

### Pitfall 4: Derived Budget Is Production-Ready Without D-16 Verification

**What goes wrong:** Plan derives p95 × 1.5 and installs it to `config.toml`. The re-drive (06.3.4) immediately hits the new budget on a different query distribution or setup.

**Why it happens:** Budgets derived from one run and applied to another assume stable latency distribution; real systems drift.

**How to avoid:** D-16 mandates: "A blown budget is investigated as a bug before it is widened." Use this pass to investigate *current* defects (D-16 scope), not just to measure latency. If a node times out in the measurement pass, stop and diagnose before moving to re-drive.

**Warning signs:** A budget fires repeatedly in the measurement pass but the node completes successfully in preflight. ⟹ Budget is real constraint, not a defect; derive conservatively.

## Code Examples

### Percentile Estimation at Small n

```python
# eval/src/lancet_eval/latency.py — compute p95/p99 with CI

from statistics import mean
import math

def percentile_with_ci(data: list[float], p: float, ci: float = 0.95) -> dict[str, float]:
    """
    Compute percentile and bootstrap CI.
    
    Args:
        data: measured latencies (ms)
        p: percentile (0.95 for p95, 0.99 for p99)
        ci: confidence level (0.95 for 95% CI)
    
    Returns:
        {"percentile": value_ms, "ci_low": lo, "ci_high": hi, "n": sample_size}
    """
    n = len(data)
    if n < 2:
        return {"percentile": data[0] if data else 0.0, "ci_low": 0.0, "ci_high": float('inf'), "n": n}
    
    sorted_data = sorted(data)
    # Order-statistic index for p-th percentile
    idx = int(math.ceil(p * n)) - 1
    percentile_val = sorted_data[idx]
    
    # Bootstrap CI: resample n items with replacement, compute percentile each time
    import random
    bootstrap_percentiles = []
    random.seed(42)  # Deterministic for reproducibility
    for _ in range(10000):
        resample = [random.choice(sorted_data) for _ in range(n)]
        resample.sort()
        idx_boot = int(math.ceil(p * n)) - 1
        bootstrap_percentiles.append(resample[idx_boot])
    
    bootstrap_percentiles.sort()
    alpha = (1 - ci) / 2
    ci_idx_low = int(math.ceil(alpha * len(bootstrap_percentiles)))
    ci_idx_hi = int(math.floor((1 - alpha) * len(bootstrap_percentiles)))
    
    return {
        "percentile": percentile_val,
        "ci_low": bootstrap_percentiles[ci_idx_low],
        "ci_high": bootstrap_percentiles[ci_idx_hi],
        "n": n,
    }

# Usage
segment_1_latencies = [...]  # list of total_duration_ms from segment 1
result = percentile_with_ci(segment_1_latencies, p=0.95, ci=0.95)
print(f"p95 = {result['percentile']}ms, 95% CI [{result['ci_low']}, {result['ci_high']}]")
```

**Source:** Bootstrap percentile CI from Efron & Tibshirani (1993), *An Introduction to the Bootstrap*, §13.

### Trend Detection (Theil–Sen)

```python
# eval/src/lancet_eval/decay.py — detect upward trend in latency

def theil_sen_slope(x: list[int], y: list[float]) -> dict[str, float]:
    """
    Estimate slope of upward trend using Theil–Sen (resistant to outliers).
    
    Args:
        x: query ordinal (1, 2, 3, ..., n)
        y: total_duration_ms per query
    
    Returns:
        {"slope_ms_per_query": value, "intercept": value, "n_pairs": count}
    """
    n = len(x)
    slopes = []
    
    for i in range(n):
        for j in range(i + 1, n):
            if x[j] != x[i]:
                slope = (y[j] - y[i]) / (x[j] - x[i])
                slopes.append(slope)
    
    if not slopes:
        return {"slope_ms_per_query": 0.0, "intercept": 0.0, "n_pairs": 0}
    
    slopes.sort()
    median_slope = slopes[len(slopes) // 2]
    
    # Intercept: median of (y - slope * x)
    intercepts = [y[i] - median_slope * x[i] for i in range(n)]
    intercepts.sort()
    median_intercept = intercepts[len(intercepts) // 2]
    
    return {
        "slope_ms_per_query": median_slope,
        "intercept": median_intercept,
        "n_pairs": len(slopes),
    }

# Usage
ordinals = list(range(1, len(latencies) + 1))
result = theil_sen_slope(ordinals, latencies)
print(f"Trend slope: {result['slope_ms_per_query']:.4f} ms/query")
if result['slope_ms_per_query'] > 0:
    print(f"  → upward trend detected (decay signal)")
```

**Source:** Theil–Sen estimator from Sen (1968), *Estimates of Regression Coefficient Based on Kendall's tau*.

## Open Questions

1. **What is the threshold for "clear positive slope" in D-19?**
   - *What we know:* D-19 defines decay as "a clear positive slope, or a late-window p95 materially above the early-window p95."
   - *What's unclear:* How to quantify "clear" (significance threshold) and "materially" (delta threshold). Slope of 0.1ms/query over 500 queries adds 50ms tail latency; is that material?
   - *Recommendation:* Planner must decide: (1) Mann–Kendall *p* < 0.05? (2) Theil–Sen 95% CI doesn't include 0? (3) Late p95 − Early p95 > K ms (specify K)? State choice explicitly so a reader can reproduce the decay verdict.

2. **Should `reformulate_timeout_ms` be included in D-15's six budgets?**
   - *What we know:* D-15 names six budgets; the codebase implements seven, including `reformulate_timeout_ms = 5000` at line 32 of `config.toml`.
   - *What's unclear:* Is `reformulate` a pass-through node in v1 (per ORCH-05), and therefore its timeout is immaterial? Or does it need to be measured and derived?
   - *Recommendation:* Planner to resolve: measure it anyway (data is free once the pass runs) and defer the derivation decision to the re-drive phase, or explicitly exempt it from D-15 and leave it at current 5000ms?

3. **Can the `inspect_lancedb.rs` tool support hand-traversal for D-05?**
   - *What we know:* The tool is read-only diagnostic; it queries table counts and chunk integrity.
   - *What's unclear:* D-05 says "hand-run traversal from a known entity." The tool may not expose graph-traversal APIs (Cypher, BFS). Manual inspection of the LanceDB `nodes`/`edges` tables via `lancectl` or similar may be required.
   - *Recommendation:* Planner to verify: does `inspect_lancedb` output degree distribution and support a point-query on a known entity? If not, document the manual steps (or defer to a follow-up tool).

4. **What is the empirical multiplier literature standard for timeout budgets?**
   - *What we know:* Various systems use 1.5×, 2.0×, or adaptive percentiles (p95 vs p99 vs p99.9).
   - *What's unclear:* Is there guidance for a RAG system specifically, or for latency-sensitive network services?
   - *Recommendation:* Planner to adopt: state the multiplier as a rule (e.g., "budget = p95 × 1.5 + 500ms") and document the false-timeout rate it implies (e.g., "assuming Gaussian, 1.5× implies ~13.4% false timeout").

5. **How to handle OpenRouter rate limits if the cheap model hits quota during the pass?**
   - *What we know:* D-47 caps spend per stage; D-20 uses a cheap model to preserve concurrency economically.
   - *What's unclear:* If the model is rate-limited (429 with `Retry-After`), should the measurement pass backoff and retry, or should the planner pre-authorize higher quota?
   - *Recommendation:* Planner to decide: (1) use tenacity backoff (already in harness) to retry, or (2) cap the pass at a lower QPS, or (3) purchase additional quota. Record the choice in `D-47` spend cap documentation.
