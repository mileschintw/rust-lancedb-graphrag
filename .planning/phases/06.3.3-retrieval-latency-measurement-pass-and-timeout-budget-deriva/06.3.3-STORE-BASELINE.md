## 7. Stated Boundaries of Evidence

1. **Structural Presence vs. Query-Time Semantic Seeding**:
   Case-folded name lookup and graph neighborhood expansion confirm that these entities and relations structurally exist in LanceDB tables.
   However, this does **NOT** prove that a live RAG query will seed or traverse them. In production, `query_graph` (`engine/src/service.rs`) discovers seed entities via vector embedding similarity gated by `seed_match_min_score`, not exact name matching. A query may fail to activate an entity if the semantic distance between the query phrase and entity embedding exceeds the threshold.

2. **Population vs. Latency**:
   A populated, dense graph store establishes that data is present, but does **NOT** establish retrieval speed. Traversal across thousands of entity edges, community hierarchy lookups, and graph filtering contribute non-trivially to execution time. Deriving timeout budgets (`graph_operation_timeout_ms` and `graph_node_timeout_ms`) requires the live timing measurements conducted in 06.3.3-03 and derived in 06.3.3-04.

3. **As-Is Condition Consumption**:
   Running the live measurement pass in Phase 06.3.3-03 consumes this baseline condition — new checkpoint records will be inserted and store fragments may advance. Because re-seeding is out of scope per D-05, this committed record serves as the permanent reference baseline for all Phase 06.3.3 retrieval analyses.
