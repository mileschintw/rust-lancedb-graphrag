the engine against it rather than by arguing about arithmetic, and close the phase on the paid-spend
decision.

size, and whether the observation was censored. A number without that trail is a guess wearing the
costume of a measurement.

nesting documentation, `06.3.3-BUDGETS.md` carrying the full derivation trail, and a recorded

    Derive first, write second, and prove third.

    Run the containment check before anything else. Take the set of nodes whose budget this
    derivation widens and the set of nodes carrying a disposition in the measurement record, and
    require the first to be contained in the second. A budget widened for a node nobody investigated
    is exactly the failure the roadmap's fifth criterion names, and checking it after the write
    turns a gate into a formality.

    Derive the four directly-measured node budgets — retrieve, prompt, graph node, and the graph
    node's inner graph operation — from their recorded percentiles under the committed rule, and
    keep the record of each: the percentile value, the sample size, the censoring status, the
    multiplier, the additive allowance and the rule. Each written value must recompute from that
    record alone, using nothing outside it.

    Derive the query-embedding and graph-operation budgets from the arm-difference decomposition the
    measurement record carries, and state in the derivation record that they rest on an estimate
    rather than a direct measurement, with the corroborating span evidence where it exists. These
    two have no per-node wire instrument, and the graph-operation budget is the one that fired 494
    times in the recorded run, so its true latency was fully censored there. Whatever number it gets,
    the record must state the strength of the evidence behind it rather than presenting it with the
    same confidence as a directly-measured node total.

    Derive the generation node budget from the provider contract, not from this pass. The engine
    already carries the rule: the node budget must accommodate the provider's attempt count times
    its per-attempt timeout, plus inter-attempt slack. Use that rule, record the slack, and mark the
    provenance as the provider contract. Report the measured generation latency beside it and mark
    it explicitly non-derivable from this pass, because the cheap model that made the pass
    affordable is not the model production runs. That is how the requirement to re-derive all six
    together and the constraint that generation latency is unusable are both honoured, rather than
    one being quietly dropped.

    Leave the reformulate budget alone. Report its measured latency in the derivation record and
    state that it is deliberately not derived: the stated success criterion names six budgets and
    does not name this one, and deriving a seventh would exceed it. Record it as an open input for a
    later decision rather than as an oversight.

    Handle any node for which the pass produced no usable observations by retaining its current
    value, stating the retention with the observation count that produced it, and carrying the gap
    forward as an open input. A retained value with a stated reason is honest; a value derived from
    an empty sample is not, and silently omitting the row is worse than either.

    Now check the invariants before writing, using the nesting report rather than the engine's own
    floor. The engine requires only that the graph node budget be at least the sum of the budgets
    nested inside it — a set that passes that check can still have an outer budget that can never
    fire, which is precisely the incoherence the family documented and which the recorded run
    confirmed with 494 timeouts at the inner budget and none at the outer. Require strict inequality
    with recorded slack, and for each nesting group state which budget is expected to fire first and
    why. Also state the worst-case sum of the node budgets against the harness read timeout and
    per-question deadline, so a query can never reach the harness wall before its own node budget
    fires. If the derived set cannot satisfy both the nesting invariant and the harness ceiling,
    that is a finding to record and resolve deliberately, not a reason to shave a number until it
    fits.

    Then write the six values into `config/config.toml` and `config/config.example.toml`, keeping the
    two files in step. Refresh the nesting documentation in both. Sibling 06.3.1-03 wrote comments
    into these files describing the nesting relationship as it stood, including the specific
    incoherence at the old values; those comments become stale the instant the numbers change, and a
    stale comment beside a changed number is worse than no comment. Rewrite them to describe the
    relationship the new set actually has, and to name which budget fires first in each group.

    Leave `config/config.eval.toml` overriding only the store path. Adding a budget override there
    would mean benchmarking a configuration nobody runs, which is the whole reason these values land
    in the production file. Leave `config/config.verify.toml` alone as well: it is a test fixture
    with literal assertions bound to it, not an operator default, and changing it would break tests
    for no gain.

    Finally, sweep the Rust tests for arithmetic that encodes the superseded set. The overlay
    contract test carries free-standing assertions written as literals of the old values; they will
    still pass after the change because they are self-contained arithmetic, which is exactly the
    problem — they become true statements about numbers nobody uses any more, sitting in a test
    named as though it validated the current contract. Find every one, and either rewrite it to
    assert the relationship against the values actually loaded from the configuration, or update the
    literals and say in the summary which you did and why. Then run the full suite and the test
    target script; if any pinned count moved, raise it in the same commit as the change that moved
    it, never the other way.

    Prove the result by starting the engine against the committed configuration. The invariants
    checked here are the same ones the engine enforces at startup plus stricter ones on top, and an
    engine that starts is the only evidence that does not depend on having reasoned correctly.
