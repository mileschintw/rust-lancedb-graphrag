## 1. System Classification

**System Type:** Hybrid (RAG pipeline formalization / workflow orchestration — not a new agent-framework adoption)

**Description:**
This phase formalizes Lancet's existing linear RAG query pipeline (validate -> reformulate -> hybrid retrieve -> graph-augment -> assemble prompt -> generate) into a typed Rust state machine that streams per-node workflow-progress events (not token-level streaming) from the Rust engine through the Go gateway to an SSE client, while adding per-node timeouts, a single generation-only retry, native cancellation propagation, and durable PostgreSQL-backed checkpoints. It is orchestration/reliability infrastructure sitting underneath an existing RAG answer-generation capability (the generation/structured-output contract was locked in Phase 3 and is unchanged) — it does not change *what* the system answers, only how faithfully and visibly it reports what happened while producing that answer. There are two user populations: (a) the developer building on or debugging Lancet's engine, who consumes workflow events and checkpoint rows to understand pipeline behavior, and (b) the end-user of whatever RAG application is built on top of Lancet, who sees streamed progress and either a cited answer or an honest failure state. "Good" here means: every node's success or failure is truthfully and distinguishably reported (typed error categories, not generic strings), no failure is silently swallowed or masked as success, no answer is fabricated when generation genuinely fails twice, and the state trail (events + checkpoints) is detailed enough that a developer can reconstruct what happened in a given query without re-running it.

**Critical Failure Modes:**
<!-- The 3-5 behaviors that absolutely cannot go wrong in this system -->
1. A node failure (retrieval, graph, generation, timeout, cancellation) is silently swallowed or misreported under the wrong error category, leaving the developer unable to diagnose why a query failed or degraded (violates D-22's typed `NodeFailed` taxonomy).
2. Generation is retried more than the single permitted attempt, retried with an altered request, or a fabricated/unvalidated answer is substituted once the retry is exhausted — presenting an ungrounded answer as if it were legitimate (violates D-12/D-13's "no fabricated answer" contract).
3. Cancellation or a timeout leaves a checkpoint or downstream write half-committed (e.g., an in-flight node future dropped mid-poll by `tokio::select!` with no cleanup path), corrupting state that a developer or a later query might read (violates the cancellation-safety requirement in Section 3 pitfall #2).
4. A fire-and-forget checkpoint/event send blocks or stalls the hot query path when its channel backpressures, meaning a debugging side-channel failure degrades or fails a user's actual query (violates D-27).
5. The zero-evidence early-return path (D-03, a valid successful completion) is misreported as a failure, or conversely a genuine retrieval failure is misreported as the benign zero-evidence path — either direction misleads whoever reads the `NodeFailed`/`WorkflowCompleted` trail about what actually happened.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Developer tooling / RAG infrastructure reliability. Lancet is a general-purpose, local-first RAG/GraphRAG demo system (per `PROJECT.md`), not a system built for a regulated vertical (healthcare, legal, finance). This phase specifically formalizes the orchestration/streaming/retry/checkpoint layer around an already-shipped RAG pipeline — its "domain" is orchestration correctness and debuggability for infrastructure engineers, not a business-vertical subject matter.

**User Population:** Two populations, neither end-consumer-facing in the regulated sense: (1) the engineer building on or debugging Lancet's RAG engine — reads `NodeStarted`/`NodeCompleted`/`NodeFailed` events and Postgres checkpoint rows to understand what happened inside a query; (2) the end-user of whatever application is layered on top of Lancet — receives streamed workflow progress and either a cited answer or a visible, honest failure/degraded state. In v1, both are effectively the same person (single-user local demo, per 05-CONTEXT.md D-23/PROJECT.md), but the rubric below evaluates the orchestration contract each role depends on separately.

**Stakes Level:** Medium. No regulated data, no multi-tenant blast radius, no revenue/safety exposure (Low would understate it) — but orchestration correctness stakes are real: a silently swallowed failure or a fabricated post-retry answer directly undermines the system's core credibility claim (cited, debuggable RAG answers), and this is also the project's interview-facing demonstration of engineering judgment (per `PROJECT.md`'s "Core Value"), so visible reliability bugs have outsized signal cost relative to a typical internal tool.

**Output Consequence:** Workflow events and checkpoint rows are consumed directly by a developer debugging pipeline behavior (deciding whether to trust, retry, or investigate a given answer) and indirectly shape end-user trust in the answer itself. A node failure that gets silently swallowed, or a fabricated answer served after generation fails twice, both propagate downstream as a confidently-presented but untrustworthy result — exactly the "confidently wrong because the model faithfully reasoned over degraded/absent context" failure mode documented in production RAG postmortems (see Known Failure Modes below).

### What Domain Experts Evaluate Against

```
Dimension: Failure visibility (no silent swallowing)
Good: A failed node (retrieval, graph, generation, timeout, cancellation) always surfaces as a distinguishable NodeFailed event with a typed category (D-22) — a developer can tell "the graph query timed out" from "the LLM call failed schema validation" without reading server logs.
Bad: A node failure is swallowed, silently retried beyond the documented single-retry policy, or reported as a generic "something went wrong" string that gives no actionable signal.
Stakes: Critical
Source: D-22's typed NodeFailed taxonomy; production RAG observability practice — teams "can't detect retrieval degradation... without stage-by-stage traces" when failures aren't surfaced distinctly (industry research, see Research Sources).

Dimension: No fabrication on exhausted retry
Good: When generation fails twice (initial attempt + the one permitted retry, D-12), the workflow transitions to Failed and reports it as such — the end-user sees an honest failure rather than a plausible-looking, ungrounded answer.
Bad: The system substitutes a fabricated or unvalidated answer to avoid showing a failure state, or returns a partially-formed/unvalidated ModelOutput.
Stakes: Critical
Source: D-13 (no fabricated answer after exhausted retry, consistent with Phase 3 D-31) — matches the broader production-RAG finding that a confidently-wrong answer over degraded context is worse than a visible failure.

Dimension: Degrade-vs-fail honesty
Good: When graph extraction fails or finds no match, the pipeline degrades to chunk-only evidence and completes successfully (D-09) — but the checkpoint/event trail records that the degradation happened, so a developer inspecting a "successful" answer can tell it ran without graph context.
Bad: A degraded-mode answer is indistinguishable from a fully-evidenced answer in the trail — no signal that a supporting retrieval path failed.
Stakes: High
Source: D-09 (silent degrade unchanged from 04.1 D-32) combined with the checkpoint/event design (D-22/D-28) — "silent" is scoped to mean "doesn't fail the query," not "invisible to anyone debugging it."

Dimension: Bounded latency / no hung node
Good: Every node has an enforced timeout (D-17) distinct from cancellation, so a stalled downstream call (e.g., a slow provider response) cannot hang the whole query indefinitely; the client sees NodeFailed{Timeout} within the budgeted window, and a client-initiated cancel is never misreported as a server-side Timeout.
Bad: A node blocks past its documented timeout budget, or timeout and cancellation are conflated in the error trail, sending a developer chasing the wrong root cause.
Stakes: High
Source: The tokio::select! timeout-vs-cancellation distinction (Section 3 pitfalls #2/#3 of this AI-SPEC); industry retry/timeout guidance on allocating explicit wall-clock budgets and propagating cancellation cleanly to avoid orphaned work (see Research Sources).

Dimension: Debuggable state trail (checkpoint fidelity)
Good: Each node-boundary checkpoint captures the full accumulated WorkflowContext snapshot at that point (D-28), so a developer reproducing a bad answer can see exactly what evidence/graph context/prompt state existed when generation ran, without re-running the query.
Bad: Checkpoints are incremental diffs or omit populated fields, forcing reconstruction of pipeline state by replaying events instead of reading one row.
Stakes: Medium
Source: D-23/D-28 (durable, full-snapshot Postgres checkpoints) — matches production RAG observability guidance that traces should capture query, retrieval candidates, fused scores, generation prompt, response, and per-stage latency.
```

### Known Failure Modes in This Domain

1. **Silent retrieval/embedding-pipeline degradation.** Industry pattern: ingestion or retrieval issues typically don't surface as errors, they surface as subtly worse answers over time (stale index, embedding drift, retrieval-threshold creep). This phase doesn't add ingestion-side monitoring, but the checkpoint/event design is the mechanism that would let a future eval pass detect this class of failure per-query rather than only in aggregate — the rubric above depends on that trail existing and being trustworthy.
2. **Confidently-wrong answers from faithfully reasoning over degraded context.** The generation node can produce a well-formed, schema-valid `ModelOutput` even when upstream retrieval or graph context was degraded or empty — the answer "looks" successful. D-22's typed `NodeFailed` categories and D-09's degrade signal are the only guardrails preventing this from masquerading as an ordinary successful query.
3. **Orphaned or half-committed work on cancellation.** Durable-execution literature flags that naive cancellation can leave child work (in-flight sub-calls, partially-written checkpoints) running or half-committed after the parent request is abandoned. This phase's own Section 3 pitfall #2 documents exactly this risk (`CancellationToken` drops the in-flight node future mid-poll without an async cleanup step) — mitigated only by requiring nodes to avoid state that needs async cleanup on cancel.
4. **Timeout/retry budget miscalibration silently disabling the retry.** Section 3 pitfall #3 of this AI-SPEC identifies a real arithmetic tension: if the node-level timeout is read as covering both the first generation attempt and D-12's retry, the retry can never actually run — "retry exists on paper but never fires" is a domain-specific failure mode distinct from generic hallucination, and is the kind of bug that would be invisible without a state trail precise enough to show retry-attempt counts.

**Selected Framework:** None — native Rust/tokio hand-rolled state machine (`Node` trait + `WorkflowRunner`)

**Version:** Rust 2021 edition, tokio ~1.53, tonic ~0.14 + prost ~0.14 (existing engine dependencies)

**Rationale:**

It is not a new LLM-orchestration framework decision: the model-provider/generation contract (OpenRouter, structured JSON-schema output, single retry) was locked in Phase 3 (D-01) and is explicitly unchanged this phase. `REQUIREMENTS.md`'s Out of Scope section directly excludes "Full LangGraph, Dify, or generic workflow-engine clone — limits scope to fixed RAG path needed for this project." No framework in the AI framework decision matrix (LangGraph, CrewAI, LlamaIndex, OpenAI Agents SDK, etc.) offers Rust bindings — all target Python, TypeScript, Java, or .NET. A hand-rolled `Node` trait + `WorkflowRunner` gives direct control over the async timeout/retry/checkpoint shape (D-11, D-17, D-23) this phase's coarse, fixed-sequence pipeline needs.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|

### Entry Point Pattern
Async-fn-in-trait is not `dyn`-compatible, and `async-trait` is **not** a Cargo.toml
dependency — the codebase's existing house style avoids it. `generation/mod.rs`
already solved this for `Generator` with a hand-rolled `BoxFuture` alias
(`generation/mod.rs:22`, used by `openrouter.rs`'s `impl Generator for
OpenRouterGenerator` at `openrouter.rs:617-636`). `Node` should mirror that shape
exactly rather than inventing a different one or pulling in `async-trait`:

```rust
// engine/src/workflow/node.rs
pub type BoxFuture<'a, T> = Pin<Box<dyn Future<Output = T> + Send + 'a>>;

/// One pipeline step (ReformulateQuery, RetrieveHybrid, ExtractGraphContext,
/// AssemblePrompt, GenerateAnswer). Mirrors `generation::Generator`'s
/// object-safe-via-BoxFuture shape (generation/mod.rs:22) — NOT async-trait.
pub trait Node: Send + Sync {
    /// Node identity used for NodeStarted/NodeCompleted/NodeFailed events (D-20)
    /// and as the timeout-config lookup key (D-17).
    fn name(&self) -> &'static str;

    /// Runs the node against the accumulated WorkflowContext (plan doc §2),
    /// observing `cancel` for D-16 cancellation propagation (see pitfall #2 below
    /// for why `cancel` is fan-out, not disconnect detection).
    fn run<'a>(
        &'a self,
        ctx: &'a mut WorkflowContext,
        cancel: &'a CancellationToken,
    ) -> BoxFuture<'a, Result<(), NodeError>>;
}

// engine/src/workflow/runner.rs
pub struct WorkflowRunner {
    nodes: Vec<Box<dyn Node>>,
    timeouts: Vec<Duration>, // parallel to `nodes`, sourced from D-17 config keys
    events: mpsc::Sender<WorkflowEvent>, // fire-and-forget; see pitfall #4
}

impl WorkflowRunner {
    pub async fn run(
        &self,
        mut ctx: WorkflowContext,
        cancel: CancellationToken,
    ) -> Result<WorkflowContext, NodeError> {
        for (node, node_timeout) in self.nodes.iter().zip(&self.timeouts) {
            let _ = self.events.send(WorkflowEvent::NodeStarted {
                node: node.name().into(),
            }).await;

            // tokio::select!, not `timeout()` alone — the plain `tokio::time::timeout`
            // wrapper cannot distinguish D-22's `Timeout` from `Cancelled`. Racing the
            // node future against `cancel.cancelled()` inside select! preserves that
            // distinction (see pitfall #2).
            let outcome = tokio::select! {
                biased;
                _ = cancel.cancelled() => Err(NodeError::cancelled()),
                res = timeout(*node_timeout, node.run(&mut ctx, &cancel)) => match res {
                    Ok(inner) => inner,
                    Err(_) => Err(NodeError::timeout(node.name())),
                },
            };

            match outcome {
                Ok(()) => {
                    let _ = self.events.send(WorkflowEvent::NodeCompleted {
                        node: node.name().into(),
                    }).await;
                }
                Err(err) => {
                    let _ = self.events.send(WorkflowEvent::NodeFailed {
                        node: node.name().into(),
                        category: err.category(), // D-22 typed taxonomy
                        message: err.to_string(),
                    }).await;
                    return Err(err);
                }
            }
        }
        Ok(ctx)
    }
}
```

### Key Abstractions
| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `Node` trait | `BoxFuture`-returning trait (mirrors `Generator`, `generation/mod.rs:22`) — one pipeline step owns its own domain logic | Implemented once per fixed-sequence step: `ReformulateQuery`, `RetrieveHybrid`, `ExtractGraphContext`, `AssemblePrompt`, `GenerateAnswer` (plan doc §3, D-06 order) |
| `WorkflowRunner` | Drives the fixed `Vec<Box<dyn Node>>` sequence, applies per-node timeout + D-11/D-12 generation-only retry, emits `WorkflowEvent`s | One instance per `query_rag` call, constructed after `ReceiveQuery` validation (D-04) |
| `WorkflowContext` | Single mutable struct threaded through every node (`session_id`, `trace_id`, `original_query`, `reformulated_query`, `vector_results`, `bm25_results`, `graph_context`, `assembled_prompt`, `answer` — plan doc §2) | Passed `&mut` into every `Node::run`; the D-28 checkpoint payload is a snapshot of this struct's populated fields at each node boundary |
| `WorkflowEvent` (proto `oneof`) | Wire type streamed over the new server-streaming `QueryRAG` RPC (D-18): `NodeStarted`/`NodeCompleted`/`NodeFailed`/`AnswerChunk`/`FinalAnswer`/`WorkflowCompleted` | One `mpsc::Sender<WorkflowEvent>` per request, wrapped in `tokio_stream::wrappers::ReceiverStream` as the tonic response stream |
| `CancellationToken` | tokio-util fan-out primitive — NOT the disconnect detector itself (see pitfall #2) | `cancel.child_token()` per in-flight node future; raced via `tokio::select!` inside `WorkflowRunner::run` and inside any node that awaits a cancellable sub-call |

### Common Pitfalls
1. **`async fn` in a `dyn`-usable `Node` trait won't compile without `async-trait` (not a dependency).** The fixed sequence naturally wants `Vec<Box<dyn Node>>`, but async-fn-in-trait is not object-safe. The codebase already solved this for `Generator` with a hand-rolled `BoxFuture<'a, T> = Pin<Box<dyn Future<Output = T> + Send + 'a>>` (`generation/mod.rs:22`) returned from an ordinary (non-async) method. Mirror that shape for `Node` exactly — do not add `async-trait` as a new dependency for this.
2. **`CancellationToken` is the fan-out mechanism, not the disconnect detector.** D-16 says cancellation is native connection-close propagation. In a tonic server-streaming handler the actual detector is the response-stream `mpsc::Sender` failing to send (client dropped its receiving half) or `tx.closed().await` resolving — that is where the *gateway-side* Go context cancellation surfaces on the Rust side once the gRPC stream context is torn down. `CancellationToken` only carries that already-detected signal into an in-flight node's `tokio::select!` so the node can stop early and the runner can emit `NodeFailed{category: Cancelled}` (D-22) instead of misreporting it as `Timeout`. Wire `CancellationToken::cancelled()` to fire only from a `Sender::send().is_err()` / stream-drop check — never treat `cancelled()` itself as detecting the drop. **Also note what cancellation does to the node future itself:** the runner's `select! { biased; _ = cancel.cancelled() => ..., res = timeout(...) => ... }` shape means that as soon as `cancelled()` resolves, `select!` drops the *other* branch — the in-flight `node.run(...)` future — mid-poll, without awaiting it to completion. This is intended (fast cancellation), but it means no node may hold state that requires an explicit async cleanup step on cancellation (e.g. no "start a LanceDB write, cancel mid-write, rely on a later `await` in the same future to roll it back" pattern) — any such cleanup must happen via `Drop` (sync only) or be structured so a half-sent checkpoint/event is simply dropped and re-derivable, not left half-committed.
3. **Node-level 30s timeout (D-17) vs. D-12's "exactly 1 retry, no backoff" is arithmetically tight — resolve explicitly, don't leave implicit.** `openrouter.rs`'s existing `Generator::generate` (lines 617-636) already wraps `execute_one_call` in `tokio::time::timeout(self.config.timeout, ...)` with `GENERATION_TIMEOUT = Duration::from_secs(30)` (`openrouter.rs:24`) — that is a **per-attempt** budget, and `execute_one_call` itself makes two HTTP round trips per attempt (`check_supported_parameters()` at line 376, then the chat completion call). If `GenerateAnswer`'s D-17 node-level timeout is read as 30s **total** (covering both the first attempt and the D-12 retry), the retry can never run — it becomes dead code, since one attempt alone can already consume the full budget. Section 4 below resolves this as: **D-17's 30s is the existing per-attempt `Generator::generate` timeout, unchanged; the `GenerateAnswer` *node's* wall-clock budget is a new, separate outer bound (≈ 2× the per-attempt timeout + slack) that wraps up to two `generate()` calls.** Do not silently collapse these into one 30s figure — the planner must size the node-level timeout config key distinctly from `GENERATION_TIMEOUT`.
4. **Fire-and-forget checkpoint/event sends (D-27) must not be allowed to block the pipeline if the channel fills.** `mpsc::Sender::send(...).await` backpressures when the receiving side (the gateway-facing stream consumer, or Go's Postgres writer per D-26) is slow — an unbounded `.await` on a full channel would violate D-27's "never stalls the user's actual query." Use a bounded channel sized generously and `try_send` (dropping/logging on `Full`) for the checkpoint path specifically, or spawn the checkpoint emission as a detached `tokio::spawn` fire-and-forget task rather than `.await`-ing it inline in the hot node-execution path. The `let _ = sender.send(...).await` shown in the Entry Point Pattern above is illustrative of "ignore the Result," not a statement that the `.await` itself is free of backpressure risk — verify the concrete channel sizing/backpressure choice in planning.
5. **Do not declare `tokio-util`'s `"full"` feature out of habit.** Verified against the crate's `lib.rs` source: `pub mod sync;` (containing `CancellationToken`) carries no `#[cfg(feature = ...)]` gate, so it compiles with tokio-util's default (empty) feature set — none of the 15 opt-in features (`codec`, `compat`, `io`, `net`, `rt`, `time`, `full`, ...) are needed. `tokio-util = "~0.7"` with no `features = [...]` list is correct; adding `"full"` (or guessing `"rt"`) pulls in unrelated codec/net/io machinery for no benefit.

### Structured Outputs with Pydantic (N/A as literally named — Rust serde equivalent, unchanged this phase)

Pydantic is a Python library; this is a Rust codebase, and per D-01 the generation/structured-output contract is **explicitly locked in Phase 3 and not touched this phase**. Rather than fabricate a Pydantic example that doesn't exist in this stack, this documents the actual, already-shipped Rust equivalent (`engine/src/generation/openrouter.rs` and `engine/src/generation/mod.rs`) so the planner knows what "structured output" means here and confirms nothing new is needed:

```rust
// engine/src/generation/mod.rs:57-68 — the closed, provider-neutral output contract.
// `#[serde(deny_unknown_fields)]` is the Rust equivalent of Pydantic's `extra="forbid"`.
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct ModelOutput {
    pub answer: String,
    #[serde(default)]
    pub cited_evidence_ids: Vec<String>,
    pub answer_basis: AnswerBasis,   // enum, see below — closed set
    #[serde(default)]
    pub notices: Vec<String>,
    #[serde(default)]
    pub warnings: Vec<String>,
    #[serde(default)]
    pub usage: Option<ModelUsage>,
}

// generation/mod.rs:27-31 — closed enum; note the wire schema (openrouter.rs:416-419)
// currently only allows ["retrieval", "mixed"] via response_format's json_schema
// "enum", deliberately excluding "model_only" — consistent with DEBT-RAG-01
// (degraded/model_only response contract) staying out of scope until Phase 6.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum AnswerBasis { Retrieval, Mixed, ModelOnly }
```

**How the framework integrates:** OpenRouter's `response_format: { type: "json_schema", json_schema: { strict: true, schema: {...} } }` (`openrouter.rs:401-464`) is the provider-side enforcement — the model is constrained at generation time, not just validated after the fact. The Rust side still validates independently: `serde_json::from_str::<ModelOutput>(content_str)` (`openrouter.rs:549`) deserializes with `deny_unknown_fields`, and a separate `validate_grounding_with_limits` call (`openrouter.rs:608-611`) checks `cited_evidence_ids` against the actually-packed evidence IDs and enforces `GroundingLimits` token ceilings — this is the semantic-grounding check a bare JSON-Schema validator can't express, analogous to a Pydantic `@field_validator`.

**Retry logic:** `GenerationErrorKind::SchemaValidation` (`openrouter.rs:514-598`, covering wrapper-JSON parse failure, wrong `choices` count, non-`stop` `finish_reason`, `ModelOutput` deserialize failure, and grounding/budget violations) is one of the failure classes D-12's single generation retry (Section 4) covers — the retry replays the identical request rather than attempting repair/reprompting. If the retry also fails schema validation, the workflow transitions to `Failed` (D-13) — **no fabricated/patched answer is substituted**, consistent with Phase 3 D-31. Log the `GenerationErrorKind` variant and message on both the first failure and the retry's outcome (surfaced to the client via `NodeFailed{category: LlmGenerationFailed, message}`, D-22) so failures are distinguishable in the checkpoint/event trail without adding new tracing spans (D-31 defers per-node spans to Phase 6).

### Async-First Design

Rust's async is not "hidden" the way it is in most Python frameworks — every `Node::run` is an explicit `Future`, and the runner drives it with `tokio::select!` rather than a framework event loop. Key points for this pattern:
- **The one common mistake:** blocking the executor thread inside a `Node` — e.g. calling a synchronous/CPU-bound routine (tokenization, large JSON parsing, graph traversal over an in-memory structure) directly inside an `async fn`/`BoxFuture` without `tokio::task::spawn_blocking`. On the `rt-multi-thread` runtime (`Cargo.toml:7`) this doesn't panic, it just silently stalls other in-flight requests' progress on that worker thread — much harder to notice than Python's `asyncio.run()`-inside-a-running-loop `RuntimeError`, because Rust gives no error, only degraded concurrency. Any node doing non-trivial CPU work (e.g. `ExtractGraphContext`'s traversal, `AssemblePrompt`'s token counting via `tiktoken-rs`) should be checked for this during planning.
- **The `tokio::time::timeout` + `tokio::select!` distinction (ties to Section 3 pitfall #3):** `tokio::time::timeout(dur, fut).await` alone cannot distinguish "the node ran out of time" from "the client cancelled" — both just produce `Elapsed`. `WorkflowRunner::run`'s `tokio::select! { _ = cancel.cancelled() => ..., res = timeout(...) => ... }` shape (Section 3 Entry Point Pattern) is required specifically so D-22's `Timeout` and `Cancelled` categories stay distinguishable in `NodeFailed` events.
- **Stream vs. await, mapped to D-01/D-02:** the `WorkflowEvent` stream (`NodeStarted`/`NodeCompleted`/`NodeFailed`/checkpoints) is genuinely streamed — pushed to the client as soon as each node boundary is crossed, for UX/progress visibility (D-20's coarse per-node granularity). The `answer` itself is **awaited in full** inside `GenerateAnswer` before a single `AnswerChunk` event is emitted (D-01 — "streaming" here means workflow progress, not token streaming) — `ModelOutput` must be fully deserialized and grounding-validated before anything is sent, because a partial/unvalidated JSON fragment cannot satisfy the closed schema. Do not attempt to stream partial `answer` text incrementally in this phase; that is the "costly, one-way" reversal D-01 explicitly calls out.

## 5. Evaluation Strategy

> **Why no LLM judge appears anywhere in this section:** this phase's evaluable surface is deterministic orchestration behavior — event ordering, timeout enforcement, retry counts, cancellation categorization, checkpoint shape. Every dimension below has a mechanically checkable correct answer; there is no subjective quality judgment (tone, reasoning quality, faithfulness) in scope. The one LLM call site (`GenerateAnswer`) is a black box to this phase's eval — its *output quality* (faithfulness, hallucination, answer relevance) is Phase 3's locked, unchanged generation contract (D-01) and is evaluated there, not here. Applying an LLM judge to "did `NodeFailed` fire in the right order" would be strictly worse than a deterministic assertion. This is a deliberate scoping decision, not an omission.

**Testability requirements this eval strategy imposes on the implementation** (must hold before these evals can run — flagged for planning, not optional):
- Every per-node timeout value (D-17: 5s/10s/15s/2s/~65s) must be overridable via the existing TOML+env convention down to sub-second values for tests. Without this, a Tier 1 timeout-enforcement test (dimension 5) literally waits out a 65s budget per test case.
- The `Generator` port and the graph-query port each need an injectable test double that can stall past a given duration or fail on the Nth call. Retry-count (dimension 2) and timeout (dimension 5) scenarios must be deterministic, not dependent on real OpenRouter latency/flakiness.

**Explicitly out of scope for this phase's eval tooling:** Arize Phoenix, RAGAS, Langfuse, Promptfoo. Two reasons: (1) no Python/TS AI framework fronts this Rust state machine for OTel auto-instrumentation to attach to; (2) D-30/D-31 explicitly defer workflow-metadata collection and per-node tracing spans to Phase 6's `OBS-01` OpenTelemetry work. If Phase 6 adds OTel spans per node, Arize Phoenix (self-hosted, OTel-native) becomes the natural production-tracing choice at that point — noted here for forward continuity only, not adopted now (see Section 7).

### Reference Dataset

**Size:** 15 scenarios (within the 10-20 guideline; each scenario is one deterministic fault-injection or happy-path test case, not a generation example). Scenario 4 is a placeholder — its concrete assertion can only be written once dimension 4's open design question (graph-timeout vs. D-09) is resolved during planning; the other 14 are fully specified now.

**Composition:**
1. Happy path — all 5 nodes succeed, full evidence, single `AnswerChunk`+`FinalAnswer`, `WorkflowCompleted(success)`.
2. Zero-evidence early return (D-03) — `RetrieveHybrid` empty → `Complete`, `AssemblePrompt`/`GenerateAnswer` never started, zero `AnswerChunk`.
3. Graph degrade, non-timeout (D-09) — `ExtractGraphContext` logical failure/no-match → query still completes, checkpoint shows `graph_context` empty.
4. Graph timeout — exercises dimension 4's open question directly; written once planning resolves whether D-09's "mandatory but non-required" framing covers the timeout sub-case.
5. Generation transient failure + successful retry (D-12) — attempt 1 fails (mock 5xx), attempt 2 (identical request) succeeds → `WorkflowCompleted(success)`.
6. Generation double failure (D-13) — both attempts fail → `WorkflowCompleted(failed)`, zero `AnswerChunk`/`FinalAnswer`, no fabricated answer.
7. Retry-vs-timeout arithmetic (Section 3 pitfall #3) — node-level timeout sized so attempt 1 consumes most of the per-attempt budget; assert attempt 2 still fires (retry isn't silently dead).
8. Per-node timeout, non-generation node (parametrized across `ReformulateQuery`/`RetrieveHybrid`/`AssemblePrompt`) — stub stalls past the test-shortened budget → `NodeFailed{Timeout}`, `WorkflowCompleted(failed)`.
9. Client cancellation during a fast node (e.g. `AssemblePrompt`) — simulated receiver drop → `NodeFailed{Cancelled}`, no further nodes start.
10. Client cancellation during `GenerateAnswer`, between attempt 1 and the retry — verifies cancellation is checked between attempts, not just within a single attempt.
11. Malformed/invalid request (D-04) — pre-stream validation failure → real gRPC `Status`/HTTP 4xx, no stream opens, zero `WorkflowEvent`s emitted.
12. Checkpoint full-snapshot fidelity — assert the checkpoint after node N restates all fields populated by nodes 1..N-1 (Tier 1); confirm the same shape lands in Postgres (Tier 2).
13. `trace_id`/`correlation_id` consistency — one query, assert every event and checkpoint row shares one `trace_id`, established from the first event and checked against every subsequent event/checkpoint row (dimension 8).
14. Checkpoint/event backpressure isolation (D-27, Critical Failure Mode #4) — attach a never-draining event/checkpoint receiver, run a full happy-path query, assert `FinalAnswer` still arrives within the normal per-node latency envelope and no node's measured duration inflates.
15. `RetrieveHybrid` hard error, not zero-evidence (D-22, Critical Failure Mode #5) — force `RetrieveHybrid`'s underlying LanceDB/BM25 call to return an error (not empty results) → `NodeFailed{RetrievalFailed}` → `WorkflowCompleted(failed)`; must be distinguishable in the event trail from scenario 2's zero-evidence success.

**Labeling:** No external/domain-expert labeling process in the LLM-judge-calibration sense. Per Section 1b's Domain Expert Roles, Lancet's own engineer/maintainer defines the expected event sequence and checkpoint shape for each scenario directly as Rust/Go test assertions — the "label" is the assertion itself, not a separate dataset file. This is appropriate because every dimension in this section is code-measurable; there is no subjective quality judgment in this phase's evaluable surface requiring calibration (that work belongs to Phase 3's generation-quality evals, unchanged here per D-01).

**Creation timeline:** Build Tier 1 scenarios incrementally alongside each node's implementation. Specifically, the timeout-injection stub (scenario 8) and the mock-`Generator` retry-counting harness (scenarios 5-7) should exist **before** `GenerateAnswer`'s retry logic is written — D-12/D-13 correctness is very hard to verify after the fact without deterministic fault injection already in place. Tier 2 scenarios (9's Go-side variant, 12's Postgres half) follow once the Go gateway's streaming rewrite (D-18/D-19) lands.

## 6. Guardrails

> The items below are runtime invariants **this phase's own control flow implements** (the `WorkflowRunner`'s `tokio::select!` timeout/cancel race, the `GenerateAnswer` node's retry ceiling, D-27's `try_send` backpressure policy) — not a separate enforcement layer bolted on top. The eval's job (Section 5) is to assert these invariants hold under fault injection; it does not add new invariants beyond what D-11 through D-27 already specify.

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| Retry-count ceiling | `GenerateAnswer` about to issue a 3rd `generate()` call for one query | **Block** — hard-fail to `NodeFailed{LlmGenerationFailed}` → `WorkflowCompleted(failed)`. Implemented as the node's own loop bound (D-12), not external policy; dimension 2 asserts the ceiling holds. |
| No-fabrication-on-failure | A success-shaped terminal event (`AnswerChunk`/`FinalAnswer`/`WorkflowCompleted(success)`) about to fire after both generation attempts failed | **Block** — the `WorkflowRunner`'s control flow (Section 3: `Err(err) => emit NodeFailed; return Err(err)`) structurally prevents this by construction; dimension 2/7 assert no code path bypasses it (e.g., no catch-and-substitute-empty-`ModelOutput` shortcut). |
| Per-node timeout enforcement | Node execution exceeds its D-17 configured budget | **Block** — `tokio::select!` races the node future against `timeout()`; emits `NodeFailed{Timeout}`, drops the node future in place (Section 3 pitfall #2's intended-fast-cancellation shape). |
| Timeout-vs-Cancelled disambiguation | Both a timeout deadline and a client disconnect could plausibly explain a terminated node | **Flag** — the `select! { biased; ... }` ordering plus the D-16 fan-out design must resolve this deterministically to exactly one category, never both or neither; misclassification sends a developer chasing the wrong root cause (Section 1b). |
| Checkpoint-channel backpressure | The fire-and-forget checkpoint/event channel is full | **Flag, not Block** — `try_send` drops-and-logs rather than blocking the hot query path (D-27, Section 3 pitfall #4). This is the one guardrail that deliberately favors query availability over checkpoint completeness — the query itself must never degrade to protect a debugging side-channel. |

### Offline (Flywheel)

This table is intentionally thin. With single-user local traffic (Section 1b's User Population/Stakes framing; PROJECT.md's avoid-speculative-hardening constraint), there is no production sample stream to batch-analyze — building sampling infrastructure for a demo with no real callers would itself be the speculative hardening the project scopes out. What would be "offline flywheel" metrics in a multi-user product are instead **deterministic Tier 1/2 regression scenarios re-run on every change** (Section 5's 15-example reference dataset), not sampled production data.

| Metric | "Sampling" Strategy | Action on Degradation |
|--------|------------------|----------------------|
| Retry-fire rate (attempt-2 calls / attempt-1 injected failures) | Not sampled — deterministic scenarios #5/#7 re-run every change; no production traffic exists in v1 to aggregate from | If attempt-2 never fires in the injected-failure scenario, the node-level timeout is mis-sized (Section 3 pitfall #3 realized) — fix the timeout config before merging |
| `NodeFailed` category distribution across the reference dataset | Full dataset (15 scenarios), not sampled | If a scenario's expected category doesn't match the emitted category (e.g. everything collapsing to `Internal`, or scenario 15's `RetrievalFailed` collapsing into scenario 2's zero-evidence shape), the D-22 taxonomy mapping has a gap in that node's error classification |
| Checkpoint payload completeness (full-snapshot vs. diff) | Full dataset (scenario #12), not sampled | Any field silently dropped from a later checkpoint vs. an earlier one is a regression against D-28 — block merge |
| Degraded-mode signal presence (dimension 4's checkpoint-diff proxy) | Full dataset (scenario #3), not sampled | If a degraded completion's checkpoint stops distinguishing itself from a full-evidence one, file it as a regression against D-09/D-28 before Phase 6 builds explicit `degraded_mode` metadata on top of it |
| Hot-path isolation under checkpoint backpressure | Full dataset (scenario #14), not sampled | If `FinalAnswer` latency measurably degrades when the checkpoint channel is starved, D-27's fire-and-forget contract is broken — block merge |

## 7. Production Monitoring

**Tracing Tool:** None in v1. D-30 (workflow metadata: `started_at`/`completed_at`, counts, `degraded_mode`) and D-31 (per-node tracing spans) are both explicitly scoped to Phase 6's `OBS-01` OpenTelemetry work — this phase adds zero new tracing instrumentation beyond the pre-existing `tracing::info_span!("query_rag", ...)` span. "Production monitoring" in v1 means direct inspection of two artifacts this phase already makes durable/observable: the `WorkflowEvent` stream (ephemeral, visible only to a connected client, not independently persisted) and the PostgreSQL checkpoint rows (durable, D-24 no TTL, D-25 no fetch API — `psql` or a local script is the only v1 access path). When Phase 6 lands OTel spans per node, Arize Phoenix (self-hosted, OTel-native, the `ai-evals.md` default for RAG/multi-agent tracing) is the natural next step — noted here for continuity, not adopted in this phase.

**Key Metrics to Track** (all derivable today from checkpoint rows + structured `NodeFailed` logs, without any new instrumentation):
1. `NodeFailed` rate by category, per node — SQL aggregation over checkpoint rows' terminal event field (or log grep keyed on `correlation_id`/`trace_id`) — surfaces which node/category degrades first.
2. Generation retry-fire rate — fraction of `GenerateAnswer` completions where a 2nd `generate()` call occurred — the production-traffic counterpart to Section 6's offline scenario #5/#7, validating D-12's retry is reachable in practice, not just under injected test failures. **Artifact note:** no checkpoint field or `WorkflowEvent` carries an explicit attempt count (D-15 forbids a "retrying" event, D-20 keeps granularity coarse, and D-28's context-snapshot field list has no attempt counter) — this metric is derivable only from the attempt-1-failure log line Section 4b's retry-logic guidance mandates (`GenerationErrorKind` + message logged on both the first failure and the retry's outcome). Do not assume this is queryable from checkpoint rows alone; it requires a log-based count.
3. `WorkflowCompleted(failed)` rate as a fraction of total queries — the top-line reliability signal a developer checks first when debugging a bad session.
4. Per-node wall-clock duration (`NodeStarted`-to-terminal-event timestamp delta, derivable from checkpoint row timestamps) — early-warning signal for a node trending toward its D-17 budget before it starts actually timing out.
5. Degraded-mode rate (checkpoint rows where `graph_context` is empty but `vector_results`/`bm25_results` are populated — dimension 4's proxy) — visibility into how often the graph path silently degrades.

**Alert Thresholds:** None. This is a single-user, local-first demo (Section 1b Stakes: Medium, no multi-tenant blast radius, no on-call per `PROJECT.md`) — there is no paging pipeline to configure, and building one would itself be the speculative hardening `PROJECT.md`'s scope discipline rules out. The dev-facing equivalent: any `NodeFailed{Internal}` occurrence (the catch-all category, D-22) or any `WorkflowCompleted(failed)` observed during Verify-phase manual testing is a stop-and-investigate signal before considering the phase done — a manual gate, not an automated threshold.

**Smart Sampling Strategy:** Not applicable in the "weight toward concerning production signals" sense (`ai-evals.md`'s guidance assumes real user volume to sample against) — with single-user local traffic there is no production stream to sample from. The v1 equivalent is exhaustive, not sampled: every scenario in Section 5's 15-example reference dataset runs on every change (Tier 1 in CI on every commit; Tier 2 gated to gateway/checkpoint changes) rather than a subset being spot-checked. If Lancet gains real multi-user traffic in a later phase, revisit this section to add signal-weighted sampling (retries, timeouts, unusual latency) per `ai-evals.md`'s Monitor Phase guidance — explicitly not built now.
