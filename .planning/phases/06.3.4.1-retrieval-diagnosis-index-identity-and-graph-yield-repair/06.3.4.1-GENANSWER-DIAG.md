# 06.3.4.1 GenerateAnswer diagnosis and stage-cap accounting (plan 06.3.4.1-23)

Gap G4 of `06.3.4.1-PASSA-GAPS.md` (D-86, D-91). Section 1 fixes the cost estimator that every later paid stage is
capped on. The later sections diagnose pass A's 135 `GenerateAnswer` failures from existing artifacts only and design
the capped probe (06.3.4.1-25). No paid call was made in this plan.

## Stage-cap cost accounting (06.3.4.1-23)

### Why the cap under-counted

`compute_spend` prices only wire tokens (`WorkflowWireMeta.prompt_tokens` / `completion_tokens`) plus a per-record
embedding estimate. A record whose `GenerateAnswer` node failed validation or parsing carries zero wire tokens, but the
provider billed the generation. `run.drive` and `measure.run_measurement_pass` both enforce `--stage-cap` on
`compute_spend`, so a cap authorised under D-86 meant roughly three times its figure whenever generations failed.

### User decision (recorded 2026-09-28, via the orchestrator)

The corrected stage-cap estimator is **approved as planned**:

- failed generations are charged at the per-attempt ceiling (classes the engine retries are charged twice);
- successful records are charged exactly as before (their own wire tokens times the per-token prices, plus the per-record
  embedding estimate);
- a `FAILED_GENERATION_CHARGE_MULTIPLIER` is added **only if** the corrected pass-A estimate falls below the $0.2178
  billed, and it is applied to the failed-generation charge only.

### Charge rules (in `compute_spend`, so `run.py` needs no change)

| Record shape | Attempts charged |
|---|---|
| any wire token reported | 0 (the token formula already prices it) |
| `GenerateAnswer` failed, class retried by the node (Timeout node kind, or an engine timeout / `OpenRouter request failed:` / body-read / HTTP 5xx or 429 message) | 2 |
| `GenerateAnswer` failed, any other class (all seven pass-A classes) | 1 |
| `AssemblePrompt` completed, no `GenerateAnswer` failure or timing, zero tokens (harness deadline / read timeout) | 1 |
| never reached `AssemblePrompt` | 0 |

The retried set comes from `generate.rs` `is_retryable` (Timeout and ProviderError only). The node reports every
provider error as kind 3 with `retryable=false`, the same kind as `SchemaValidation`, so the retried classes are
matched on the engine's literal messages (`openrouter.rs`). No committed journal holds a `GenerateAnswer` timeout or
provider-error message (2026-09-03, 2026-09-09, 2026-09-06 and pass A were searched), so those five patterns are pinned
against the engine literals, not journal text. The classes the node retries were not seen in any run, which is why the
retry rule is untested against real traffic.

The corrected estimate is 1.47 times the bill, so pass A is covered and **no multiplier is added**
(`FAILED_GENERATION_CHARGE_MULTIPLIER = 1.0`). The multiplier hook exists and is tested to scale the failed-generation
charge only (successes and embeddings are never scaled).

### Guards

- Monotonic: for every record set the new estimate is at least the old formula at the same price constants
  (`test_new_estimate_never_below_old_for_any_mix`, including all 324 pass-A records).
- Successful-only fixtures: old and new are identical, also with a multiplier set.
- Discriminating cap test (`test_stage_cap.py::test_cap_counts_failed_generations_and_stops_earlier_than_the_old_estimator`):
  a mocked drive whose records fail generation stops at the third record on a $0.005 cap. The old estimator charged
  $0.0000144 of embeddings per record and never reached the cap in 20 units. It failed on the old `compute_spend`
  (commit `a15da015`, RED) and passes on the new one.

### Use by later D-86 checkpoints

Every later paid checkpoint proposes its `--stage-cap` from this corrected estimator's **all-at-max** figure: one
ceiling attempt plus the embedding estimate per record, that is $0.00181664 x records (a record of a retried class
would charge two ceilings, $0.0036 each). The stages are the probe, confirmation and preflight of 06.3.4.1-25/-26/-27,
drive 1 (06.3.4.1-12), pass B (06.3.4.1-18) and drive 2 (06.3.4.1-19). The figure is far above what a run spends when
generations succeed (pass A billed $0.00067 per record), so a cap proposed from it is a hard ceiling, not an expected
cost.

### Caveats a checkpoint must carry

- **`drive --retries N`.** `run.drive_one` re-runs a failed query up to N more times but journals only the last attempt,
  so a journaled failure can stand for N+1 billed generations while `compute_spend` sees one record. The corrected
  estimator does not see this. D-67 pins drive 1 to `--retries 0`; if any stage runs with retries, its all-at-max figure
  must be multiplied by N+1 before a cap is proposed. `measure` never retries.
- **Widening the engine's retry rule.** If a later plan makes `SchemaValidation` retryable (fix candidate below),
  `_generation_error_is_retried` in `measure.py` is the single place that must change, or failures of those classes stay
  under-charged at one attempt.
- **Ceiling versus listing.** The 8192-token prompt ceiling is 3.8 times pass A's largest successful prompt (4,322
  tokens). The estimate is an upper bound by construction.

### Method and evidence limits

- Classes are keyed by the engine's own message. `trailing characters at line L column C` is one class: L and C are kept
  as numeric fields (`parse_error_line`, `parse_error_column`) and only the stable prefix is the key. Counts are exactly
  52 / 44 / 22 / 11 / 3 / 2 / 1 = 135, checked by the task's verify command over
  `diagnostic/genanswer/passA_failures.jsonl`. The 4 warm-up records are inside the 324 (one of them, ordinal 2, failed
  with the `mixed` message), so the file carries `ordinal` and `warm_up`.
- Checkpoint join: journal `correlation_id` = `workflow_checkpoints.trace_id`, `node_name = 'post_assembleprompt'`;
  324 of 324 matched. Features were computed **inside PostgreSQL** (`length()`, `jsonb_array_length()`, `position()`,
  `md5()`), so no prompt, evidence or article text left the database. Only `SELECT` was run
  (`docker compose exec db psql`, no DDL or DML). The committed feature file has no field longer than 200 characters
  (checked in the acceptance step).
- Features per failed record: `prompt_chars`, `evidence_block_count`, `evidence_text_chars`,
  `suspicious_block_count`, `graph_fact_count`, `graph_context_chars`, `question_chars`,
  `d71_sentences_present` (0 to 4 of the four D-71 sentences found by `position()`), `duration_ms`, plus
  `paired_arm_class`.
- What these artifacts cannot show: **the raw model output.** The journal keeps only `error_message`, `answer: ""` and
  zero tokens, and no checkpoint exists past `post_assembleprompt` for a failed request. Everything below about why the
  model wrote what it wrote is a hypothesis, each tied to an observation in 06.3.4.1-25's probe.

### Where the failures are raised (checked in the code, and it corrects RESEARCH section A)

`OpenRouterGenerator::execute_one_call` runs `validate_output_shape_with_limits` on the model's **raw** output
(`openrouter.rs:836`) before it returns, so the GenerateAnswer node's citation repair (`generate.rs:288-390`, which
rebuilds the citation set from inline markers and, by its own comment, "never from `cited_evidence_ids` alone") only
sees outputs that already passed the shape check. RESEARCH section A describes only the node site and concludes that
what the model put in `cited_evidence_ids` "is irrelevant on this path". That holds for the node site, not for the
provider site that runs first. The same message can therefore come from two places:

| Message | Site 1: provider, raw output (`openrouter.rs:836`, `generation/mod.rs:195-`) | Site 2: node, after repair (`generate.rs:384`) |
|---|---|---|
| `answer basis 'mixed'/'retrieval' requires at least one cited evidence ID` (`mod.rs:226`) | the model's own `cited_evidence_ids` array is empty, whatever the answer text holds | the answer text held no resolvable `[n]` marker |
| `ModelOnly answer basis is not supported ...` (`mod.rs:202`) | the model reported `answer_basis: "model_only"` | `total_drop`: markers existed and none resolved (clone forced model-only) |
| `Model answer text must not be empty or blank` (`mod.rs:209`), `notice length exceeds limit 1024` (`mod.rs:265`) | raw output | not reached first |
| `trailing characters`, `finish_reason 'length'` | provider only (`openrouter.rs:749`, `:726`) | none |

Plan 22's `generation_output_rejected` event tells the two sites apart: a provider event carries `finish_reason`
(`"stop"`) and `model_cited_ids` and no `markers_found`; a node event carries no `finish_reason` and carries
`markers_found`, `markers_resolved` and `total_drop`. Every confirm/refute line below uses these fields.

### Findings that apply to every class

1. **The failures are largely stochastic at temperature 0.** `config.toml` sets `temperature = 0.0`, `top_p = 1.0`.
   Grouping pass A's 324 records by the `md5` of the stored assembled prompt gives 221 distinct prompts and 101 groups of
   byte-identical prompts (204 records: 100 pairs and one group of four). Of those 101 groups, 38 are all-success,
   27 are all-failure (24 with the same class, 3 with different classes) and **36 mix success and failure on the same
   prompt**. The clearest case is ordinal 2 (warm-up, graph-on), which failed with `mixed` while ordinals 1, 5 and 6 (same
   question, byte-identical prompt) succeeded. When both records of a group failed, the class agreed 24 of 27 times, so
   the propensity to fail and the kind of failure look prompt-dependent, while whether a given draw fails is not.
   (The stored prompt is `AssemblePrompt`'s output; the adapter re-packs the same evidence with the same function, so it
   is a proxy for the wire prompt, not a proof of byte-identical wire bodies.)
2. **The retries difference can by itself explain most of the rate gap.** The baseline and the replay journal the last of
   up to three attempts (`--retries 2`), pass A a single attempt. If per-attempt failures were independent at pass A's
   non-null rate (33.6%), three attempts would leave 0.336^3 = 3.8% failing, against 4.5% (baseline) and 7.6% (replay).
   Independence is only approximate (finding 1 shows prompt-dependent propensity), so this bounds the effect rather than
   measuring it: the single-attempt baseline rate is unknown and at least 12.1%. The artifacts cannot separate "D-71
   raised the per-attempt failure rate" from "the earlier runs hid it behind retries". The probe can bound it, see the
   design below.
3. **Abstention questions almost always fail, in every run** (69%, 93%, 93%), and 41 of the 44 pass-A null records fail
   (all 22 graph-on, 19 of 22 graph-off). So D-69's residual, an abstention with nothing to cite, predates D-71. What is
   new in pass A is the non-null failure rate: 4.5% and 7.6% before, 33.6% now.
4. **Input shape does not separate failing from succeeding records.** All 324 assembled prompts hold exactly 8 evidence
   blocks. Failing versus succeeding (n = 189) class means, leaving out the single `notice` record: prompt characters 6.8k to
   7.6k versus 7.1k, evidence characters 2.1k to 2.5k versus 2.4k, question characters 270 to 331 versus 289. The only feature contrast is duration (below).
5. **Duration separates the short-output classes.** Failing `modelonly` and `trailing` records finish in about 2.6 s and
   2.5 s against 4.5 s for successes (mean; median 4.1 s), so the model wrote a short reply. `mixed` (4.0 s) and
   `retrieval` (4.2 s) look like ordinary-length answers. The two `length` failures took 17.1 s and 22.8 s.
6. **Graph-on fails more, on identical prompts too.** Non-null failure is 54 of 140 graph-on against 40 of 140
   graph-off; nulls fail 22 of 22 against 19 of 22. In 110 question pairs whose two arms carry equal prompt and evidence
   sizes and no graph facts (so the prompts are almost certainly the same), 38 pairs split (one arm fails, the other does
   not), 42 succeed in both and 30 fail in both. Together with finding 1, the arm effect is not explained by the prompt.

### Class 1: `answer basis 'mixed' requires at least one cited evidence ID` (52)

- **Counts and splits.** graph-on 29, graph-off 23. Null 4, non-null 48 (inference 20, comparison 16, temporal 12, null 4).
  1 warm-up. Paired arm: 27 succeeded, 22 also `mixed`, 2 `trailing`, 1 `retrieval`. Baseline had 25 (20 on null
  questions); pass A has 48 on non-null questions. That contradicts RESEARCH B's account of this class as "mostly
  abstentions on null questions".
- **Plan-08 lines it could interact with.** `prompt.rs:212` ("shortest answer"), `:213` ("keep citing ... with [n]
  markers"), `:215` (insufficient evidence, still name blocks). The validator lines are unchanged since `33e774bd`.
- **Hypotheses.**
  - **H-mixed-provider** (Site 1): the model writes an answer that may hold `[n]` markers but leaves its JSON
    `cited_evidence_ids` array empty; the provider shape check rejects it before repair could rebuild the set. Confirmed
    by events with `stage = "validate"`, `finish_reason = "stop"` and `model_cited_ids = 0`; and, to call it a valid
    output rejected, `[n]` markers visible in `raw_head`'s `answer` string. Refuted if `model_cited_ids > 0`.
  - **H-mixed-node** (Site 2): the D-71 "shortest answer" instruction shrinks the explanation until no inline marker
    remains. Confirmed by node events (no `finish_reason`) with `markers_found = 0` and `answer_basis = "mixed"`.
    Refuted if `markers_found > 0`.
  - **H-mixed-stochastic**: the same prompt sometimes passes (finding 1). Read from the probe's per-question
    agreement, not from a single event.
- **Fix candidates.**
  - Run the emptiness check on the citation set repair produces, or skip it at the provider when
    `citation_repair_enabled` (removes Site 1's rejection of outputs the node would accept): **`bug/regression`** only if
    H-mixed-provider is confirmed with markers present (the design says citations come from markers); otherwise
    **`contract change (decision)`**. Reversibility: moderate (engine change plus tests; reverting restores fail-closed).
  - Reword D-71's sentence at `prompt.rs:212-213`: **`bug/regression`** if H-mixed-node is confirmed (a plan-08
    regression); reversibility **costly** (CONTEXT D-71: changes shipped answer text and makes scored runs
    non-comparable).
  - Retry a `SchemaValidation` failure once in the node: **`contract change (decision)`**, reversibility moderate;
    doubles the billed attempts of failing records (see the estimator caveat).

### Class 2: `ModelOnly answer basis is not supported on Phase 03 QueryRAG path` (44)

- **Counts and splits.** graph-on 22, graph-off 22. Null 28, non-null 16 (null_query 28, temporal 9, comparison 7).
  0 warm-up. Paired arm: 32 also `modelonly`, 8 succeeded, 3 `trailing`, 1 `retrieval`. Baseline 10 (8 null); replay 53
  (39 null, 14 non-null); this class is 28 of the 41 failing null records in pass A.
- **Plan-08 lines.** `prompt.rs:215` ends abstentions with "Answer: Insufficient information"; `allow_model_only_answers
  = false` (`config.toml:59`) makes any self-reported `model_only` fatal.
- **Hypotheses.**
  - **H-modelonly-report** (Site 1): on abstentions the model sets `answer_basis: "model_only"` itself. Confirmed by an
    event with `answer_basis = "model_only"` at the provider `validate` stage (`finish_reason = "stop"`); the null share
    of the class (28 of 44) is the feature-file prediction.
  - **H-modelonly-drop** (Site 2): `total_drop`, all markers unresolvable (a marker naming a block outside 1 to 8, or a
    bracketed number the grammar reads as a marker). Confirmed by node events with `total_drop = true`,
    `markers_found > 0`, `markers_resolved = 0`. Refuted if none exist.
  - **H-modelonly-abstain**: the reply is an abstention. Confirmed by `raw_head`/`raw_tail` holding the
    "Insufficient information" line and `completion_tokens` small (this class runs 2.6 s).
- **Fix candidates.**
  - Accept a self-reported abstention as grounded-by-absence (no citation required): **`contract change (decision)`**
    (changes the validator's acceptance rule and D-72's null semantics); reversibility moderate.
  - Drop or reword `prompt.rs:215`'s abstention clause: **`bug/regression`** only if H-modelonly-report shows the
    clause is what flips the basis on answerable questions (16 non-null records); reversibility **costly** (D-71).
  - Nothing in the validator is a bug on this evidence: it rejects `model_only` as designed.

### Class 3: `failed to deserialize ModelOutput schema: trailing characters` (22)

- **Counts and splits.** graph-on 17, graph-off 5. Null 7, non-null 15 (inference 8, null_query 7, comparison 6,
  temporal 1). 0 warm-up. Paired arm: 9 succeeded, 8 also `trailing`, 3 `modelonly`, 2 `mixed`. **New:** 0 in the
  baseline (355 reached), 0 in the replay (350); the baseline held one `invalid type: integer` parse error in the
  2026-09-03 run and the replay one `duplicate field`.
- **Position evidence in hand.** `serde_json` reports the position of the first non-whitespace character after a complete
  value. 21 of 22 errors are at column 1 of line 2, 8, 10, 12, 13 or 14 (12 x6, 8 x5, 13 x5, 2 x3, 14, 10), i.e. the
  trailing text starts at the beginning of a line after a complete multi-line JSON object; one is at line 1 column 1235
  (trailing text on the same line). That fits a valid `ModelOutput` object followed by extra text. It cannot say what
  the text is.
- **Plan-08 lines.** `prompt.rs:212` says the answer must "end with exactly one final line ... Answer: ..." and does
  not say that line belongs inside the JSON `answer` string; the response format is strict JSON
  (`openrouter.rs:553-616`). The class did not exist before `af23ab97`.
- **Hypotheses.**
  - **H-trailing-answerline**: the model emits the JSON object and then a literal `Answer: <short>` line outside it.
    Confirmed by `stage = "parse"` events whose `raw_head` is a complete `ModelOutput` object and whose `raw_tail` (or
    the remainder after the object when `raw_chars <= 2000`) starts with `Answer:`. Refuted if the text after the
    object is not that line.
  - **H-trailing-repeat**: a repeated or looping generation (a second object, duplicate fields; the replay's
    `duplicate field` error points the same way). Confirmed by trailing text beginning `{`, and `completion_tokens`
    near 2048 or `raw_chars` far above one object.
  - The graph-on skew (17 of 22) is unexplained by prompt shape (finding 6) and is left as an observation to re-test.
- **Fix candidates.**
  - State in the prompt that the Answer line goes inside the `answer` string: **`bug/regression`** if
    H-trailing-answerline is confirmed (plan 08's wording caused it); reversibility **costly** (D-71).
  - Parse the first complete JSON value and ignore trailing text: **`bug/regression`** only if the events show a complete
    valid `ModelOutput` rejected for text that carries no answer content; otherwise **`contract change (decision)`**;
    reversibility moderate. It also risks accepting a model that ignores the strict-schema contract, which is why it is
    not pre-decided here.

### Class 5: `Model answer text must not be empty or blank` (3)

- **Counts and splits.** graph-off 2, graph-on 1. All non-null (comparison 2, temporal 1). Paired arm: succeeded in all

- **Hypotheses.**
  - **H-empty-field**: the model returned `answer: ""` (or whitespace) with content placed elsewhere in the object

### Class 6: `OpenRouter completion incomplete: finish_reason 'length'` (2)

- **Counts and splits.** Both graph-on, both non-null comparison questions; both paired arms succeeded. Durations 17.1 s
  and 22.8 s, an order of magnitude above every other class.
- **Hypotheses.**
  - **H-length-runaway**: repetitive, non-terminating generation until the 2048-token cap. Confirmed by a
    `stage = "finish_reason"` event with `finish_reason = "length"`, `completion_tokens = 2048` and a repeating pattern
    in `raw_tail`.
  - **H-length-legit**: a genuinely long answer to a comparison question. Confirmed by an orderly `raw_tail` and no
    repetition.
- **Fix candidates.** Raising `[openrouter] max_output_tokens` is a **`contract change (decision)`** (also raises the
  estimator's pinned `FAILED_GENERATION_COMPLETION_TOKENS`); reversibility moderate. Both records fall in the class the
  estimator charges at the ceiling, and a `length` stop means the completion hit the cap, so these two are presumably
  the failed records billed closest to it.

### Class 7: `notice length exceeds limit 1024` (1)

- **Counts and splits.** graph-off, non-null comparison; the paired arm succeeded; a small evidence set (1,070
  characters, 5,614-character prompt). Never seen in earlier runs.
- **Hypotheses.** **H-notice-answer**: the model wrote its explanation into a `notices` entry. Confirmed by a provider
  `validate` event with a `raw_head` whose `notices` string is longer than 1024 characters. Refuted if `notices` is
  short and another notice is the long one.
- **Fix candidates.** Truncating or dropping an oversized notice is a **`contract change (decision)`** (the validator
  is fail-closed on notice length by design); reversibility moderate. One record does not justify it.

## Probe design (for 06.3.4.1-25)

- **Prefix rule (checked in the code).** `run_measurement_pass` selects `corpus.questions[:sample_size]` (sorted by id,
  fixed sample; `measure.py`), so `measure --sample-size N` replays a true prefix of pass A's question order, after 4
  warm-up records (the first two questions, both arms). Pass A's first `2N + 4` ordinals are therefore exactly what a
  probe of size N replays. Pass A's ordering matches `corpus.questions[:160]` (checked).
- **Sample N.** Failures of each class inside the first `2N + 4` pass-A ordinals:

  | N | records | mixed | modelonly | trailing | retrieval | empty | length | notice | every class with >= 10 in pass A has >= 3 |
  |---|---|---|---|---|---|---|---|---|---|
  | 40 | 84 | 12 | 18 | 8 | 0 | 0 | 0 | 0 | no (retrieval 0) |
  | **60** | **124** | 18 | 19 | 9 | **3** | 0 | 0 | 0 | **yes** |
  | 80 | 164 | 20 | 27 | 11 | 6 | 0 | 0 | 0 | yes |
  | 100 | 204 | 21 | 27 | 13 | 8 | 0 | 0 | 0 | yes |
  | 120 | 244 | 27 | 32 | 16 | 10 | 1 | 0 | 0 | yes |
  | 160 | 324 | 52 | 44 | 22 | 11 | 3 | 2 | 1 | yes |

  **Proposed N = 60** (smallest that satisfies the rule): **expected records 2N + 4 = 124**.
  Two flags for the checkpoint: (a) `retrieval` sits exactly on the threshold (3), and finding 1 says a re-draw will not
  reproduce pass A's records, so N = 80 (164 records, `retrieval` 6) is the safer choice if the class matters; (b) the
  three classes with fewer than 10 records (`empty` 3, `length` 2, `notice` 1) fall almost entirely beyond ordinal 244,
  so a probe below N = 160 cannot test them. They are not dropped: plan 22's capture stays on for every later run, so
  they can be diagnosed from drive 1's events, or the user can choose N = 160 to cover all seven classes.
- **Cost.** All-at-max estimate from Task 1, one ceiling attempt plus the embedding estimate per record:
  124 x $0.00181664 = **$0.2253** (N = 80: $0.2979; N = 100: $0.3706; N = 160: $0.5886). **Proposed cap =
  max($0.25, 2.5 x $0.2253) = $0.5632.** That is a hard ceiling. At pass A's realised $0.00067 per record the N = 60
  probe would bill about $0.08. The estimator now charges failures at the ceiling, so `--stage-cap` stops the probe at
  about the same total whether generations fail or succeed.
- **Completeness check.** Every failed journal record (a `GenerateAnswer` node failure) must match **exactly one**
  `generation_output_rejected` event by correlation ID (`journal.correlation_id` = the event's `correlation_id`).
  A missing match is an uncaptured rejection site and stops the diagnosis; two matches per record would mean a repeat
  attempt (the node retries Timeout and ProviderError only). A provider `validate` event and a node `validate` event for
  one request cannot both occur (the provider error aborts before the node repair), so exactly one is the invariant.
- **Reproducibility reading.** Per-question class agreement with pass A, on `(question, arm)`: the share of pass-A
  failures the probe reproduces with the same class, and the share of pass-A successes that now fail. The reference is
  finding 1: byte-identical pass-A prompts agree on success/failure in 65 of 101 groups (64%) and on the class in 24 of 27
  when both fail. A reproduction near 100% means failures are deterministic in (question, prompt) and a prompt or
  validator edit can be judged on a small sample. A reproduction near the same-prompt reference means failures are
  largely per-draw noise, and any fix must be judged on rates, not on the pass-A records. The 4 warm-up repeats and the
  probe's own byte-identical arm pairs (about a third of pairs, no graph facts) give a second same-prompt reading inside
  the probe.
- **What the probe cannot separate.** D-71's effect from the retries difference (finding 2). A clean split needs the
  same questions run under the pre-D-71 prompt with retries 0, which needs a prompt change; that is a decision for
  06.3.4.1-25/-26, not this plan. The probe still bounds the single-attempt rate under the D-71 prompt, and the raw
  outputs decide each class's mechanism.
- **The brief's alternative (replay stored `post_assembleprompt` prompts directly).** The prompt is recoverable for all
  324 requests, and a direct replay would skip retrieval and cost the same per call. It is not chosen because it needs a
  new provider-calling tool, bypasses the engine's own request wrapper (the fixed system message, the strict
  `json_schema` response format, `reasoning: none`, temperature and token limits, the parser and both validation sites),
  so its outputs would not necessarily be the outputs the engine sees, and it has no `generation_output_rejected`
  correlation. The `measure` prefix uses the same path as pass A, the same capture, existing capped tooling with the
  corrected estimator, and no new provider-calling tool.
- **Preconditions this plan did not check** (they belong to 06.3.4.1-25's checkpoint): an engine built at a HEAD that
  contains plan 22's capture, the `log_filter` and `build_profile` on its startup line, a reachable log sink for the
  `engine::` INFO events, and the user's authorisation of the cap under D-86.
