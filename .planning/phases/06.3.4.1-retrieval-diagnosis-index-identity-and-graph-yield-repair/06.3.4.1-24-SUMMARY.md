## Task 2 decision (verbatim, user, 2026-09-29)

Reply: `inner=other:2000,10000; prompt=floor:65; preflight=authorise-0.05; noise=accept`

Rationale the user chose, dated 2026-09-29: **"Tight embedding, loose graph."** (a) An embedding timeout (`graph_context.rs:80`) fails the node and the runner cancels the whole query. The engine never retries it; only the eval harness's `--retries` re-runs the whole query (`run.py:181-195`), which is cheap because generation has not started. (b) A graph-operation timeout (`graph_context.rs:117-186`) silently degrades to chunk-only context with a `GraphTimeout` notice and records a success, so nothing retries and graph yield would drop invisibly. Hence `query_embedding_timeout_ms` 2000 and `graph_operation_timeout_ms` 10000. The user considered and declined `toml` 15000 / 40000 (too loose), `config-rs` 645 / 38595, and tight-both 2000 / 4000.

- **Prompt floor:** 65 ms for `prompt_timeout_ms` only, 1.5x pass A's 43 ms maximum. This is a dated user amendment for that node; the committed p95 x 1.5 rule (which writes 11 ms) is unchanged.
- **Preflight:** $0.05 authorised (D-86). Eight generating queries by code; the all-at-max estimate is $0.0145 (9-query margin $0.0163, all-retried worst case $0.0326). Preflight has no in-process cap, so 06.3.4.1-27 meters it by the OpenRouter account delta.
- **Noise:** accepted. 0 of 121 windows fire, escalation flag false, nearest misses 89.4% (slope) and 72.2% (window). D-89's numbers (658, 0.25, 25 ms) are unchanged.

## Deviations from Plan

### Documented deviations from the plan text

**1. [Plan text error] The rule writes 294 ms for RetrieveHybrid, not 299 ms**
- **Found during:** Task 1 (first derivation run).
- **Issue:** The plan says "p95 199 ms x 1.5 -> 299 ms" and treats that as a mismatch with the brief's 294 ms. The rule's nearest-rank p95 over all 320 records is 196 ms, giving 294 ms, so the brief and the rule agree. 199 ms is the early-window p95 (n = 80) of the D-89 reading, and BUDGETS' older "Observed node latency" table lists 199 for RetrieveHybrid's p95, which coincides with it.
- **Fix:** Reported in `budget-hazards.json` (`brief_mismatch`) and in the BUDGETS section; the rule's output governs (G2). The older BUDGETS table is history and was not edited.
- **Committed in:** `cf168407`, `eecafab3`

**4. [Correction to the decision's rationale, ratios only] The embedding prelude runs inside `ExtractGraphContext`, not `RetrieveHybrid`**
- **Found during:** Task 2 resume, reading `graph_context.rs:72-90` and `retrieve.rs:188`.
- **Issue:** The rationale bounds the embedding by RetrieveHybrid's 403 ms maximum ("about 5x"). The code runs the embedding prelude in `ExtractGraphContext`, before the graph-ablation early return, so on both arms, and `RetrieveHybrid` reads the precomputed embedding. Pass A's bound on the embedding is therefore `ExtractGraphContext`'s 1438 ms maximum (embedding plus graph operation on graph-on records), so 2000 ms is about 1.4x that bound and 10000 ms about 7.0x it.
- **Fix:** Stated in the BUDGETS decision section. The decision stands as the user made it and no value changed. Pass A carries no separate timing for either inner operation, so no record can be shown above either inner budget or below it.
- **Committed in:** `0a738931`
