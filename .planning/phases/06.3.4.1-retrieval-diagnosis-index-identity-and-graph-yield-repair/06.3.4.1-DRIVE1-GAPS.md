## How the answer path works

These facts were checked while writing this brief.

- **Structured output:**
  - The engine asks OpenRouter for strict `json_schema` output, set in `engine/src/generation/openrouter.rs` around lines 540 to 620. The schema is named `model_output`, and its required fields are `answer`, `cited_evidence_ids`, `answer_basis`, `notices` and `warnings`.
  - The prose answer, including the D-71 final line, lives inside the JSON string `answer`. A line break there is an escaped `\n` that the model has to emit itself.
- **The final-line instruction:** it is in `engine/src/prompt.rs` (lines 212, 215, 722, 729 and 743): "end with exactly one final line in this form: Answer: ...".
- **The extractor:** `eval/src/lancet_eval/metrics.py` `extract_final_answer`, with the regex `_ANSWER_LINE` at about line 63, is multiline and anchored at line start. It reads only an `Answer:` that begins a line. The last match wins.
- **What the engine drops from the response:** `OpenRouterChatResponse` (`openrouter.rs` about line 963) deserialises only `choices` and `usage`. OpenRouter's response `id`, `model` and `provider` fields are dropped.
- **What the engine logs:** the `llm_attempt` span carries only `gen_ai.request.model`.
- **No generation IDs were kept.** A search of `data/oi02-evidence/drive1-2026-09-30*` and the run directory for OpenRouter `gen-...` IDs finds none.

- Nothing else moves at the onset: token counts, error rates and both arms change together.
- Format map, one character per record: L = line-start `Answer:`, i = inline only, n = none, `.` = no answer.

  ```
  LLLLL.LL.LLLiLLLiLLLL.LLL.nL.LLLLLLLLLLLLLL..LLLLL.LLiiiiiiiiiiiiiiininiiiii.niiniininniiniiiiinnniiiininiiiiiiiiiiiiiiininniininiiiniiininiiniiiiiiiniinininniiiiiiiiniiiiiiiiiniiiiniiiiiiiiiiiiiiinii
  ```

**Required:**

- The drive-2 final answer is recoverable whether or not the served model emits line breaks.
- The fix is committed and tested **before** any drive-2 data.
- Prefer a fix that does not depend on the provider's whitespace.

**Options.** The user chooses at plan time, through a blocking `checkpoint:decision`; the planner must not pick.

- **(a) Extractor.** `extract_final_answer` also accepts the last `Answer:` that is not at line start, under a strict rule. For example:
  - the last `Answer:` token in the text, preceded by sentence-ending punctuation or whitespace;
  - running to the end of the text.

  Consequences:
  - This changes the D-70 metric definition. It needs its own committed literal or rule name, tests (line-start, inline, several `Answer:` tokens, `Answer:` inside a quotation, no `Answer:`), and a note in DRIVE1 or BUDGETS.
  - Drive 1 is **not** re-scored as a pass (D-87a). If drive 1 is re-read under the new rule, the result is labelled post-hoc.
  - The 12 answers per 146 with no `Answer:` at all stay missing.
- **(b) Engine / schema.**
  - Option b1: add a required short `final_answer` field to the strict `model_output` schema. The model then returns the short answer as its own JSON value, and the engine carries it into the final-answer event and the journal. The extractor prefers the field and falls back to the line rule.
  - Option b2: the engine normalises the last `Answer:` onto its own line.

  Consequences:
  - Option b1 changes the engine and gateway response contract and the prompt. That means Rust tests, `scripts/engine-test-targets.sh` raised to measured counts, a release rebuild, and possibly gateway and proto work if the field crosses the gRPC boundary.
  - It also removes the dependence on free-text format, including the 12-per-146 case with no `Answer:`.
- **(c) Prompt only.** Reword the D-71 instruction, for example "the answer text must contain a newline before `Answer:`".
  - This is the cheapest, but it still depends on whatever the served backend does with whitespace. It is the weakest option against the observed failure.

**The orchestrator's recommendation to put to the user:**

- (a) is the minimum, because it is eval-only and needs no rebuild.
- (b1) is the more robust option if the user accepts the Rust, contract and proto scope.
- (c) alone is not recommended.
- Whatever is chosen, the plan also records the per-stratum constant-Yes baselines unchanged.
