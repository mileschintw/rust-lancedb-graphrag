# 06.3.4.1-03: OI-02 RetrieveHybrid Profile

Read-only, API-free `retrieval_soak` (release build) drove 300 iterations per arm against the
live `./data/lancedb-eval` store (`LANCET_ENV=eval`, engine and gateway both stopped for the
entire run). Query vectors/text: a SplitMix64-seeded (`seed=5494759071201636403`, recorded on
every header line) sample of 300 `nodes` rows for R/RP and 300 `entities` rows for RG/RGT/W (an
entity's own `name_vector` is used as the query embedding for the graph-touching arms, which
guarantees `attempt_graph_augmentation`'s seed match trivially succeeds — see
`retrieval_soak.rs`'s `Arm::uses_entity_seed` doc comment). All five headers report
`build_profile: "release"` and `collector_reachable: false` (no local OTel collector running,
as expected). Process sampling: PowerShell `Get-Process` every 1s (not the plan's stated 5s —
see Methodology Note below) into `soak/<arm>-proc.csv`.

`censored_count=0` and `unusable_dropped_count=0` on every arm — no RetrieveHybrid failures,

**R and RP formally fail the machine flatness verdict, but not for a practically meaningful
reason.** Both fire only the Mann-Kendall slope prong (window prong never fires on any arm —
every window delta is 2.5-32.9ms against the 500ms materiality threshold). At n=300,
Mann-Kendall has enough statistical power to flag a slope of 0.02ms/query (R) or 0.011ms/query
(RP) as "significant" (p=0.002, p=0.013) even though the total drift implied over the whole run
is 6.1ms (R) and 3.4ms (RP) — smaller than the noise band visible in the slice medians
themselves (which swing by ~2-13ms between consecutive 50-iteration blocks with no consistent
direction). This is large-n statistical sensitivity, not decay: applying the same instrument
production-side (paid drive 1, 06.3.4.1-12) at n≈500 records per arm should be read the same
way — a "fired" slope prong with a sub-millisecond-per-query slope is not what OI-02 is looking
for.

RGT's graph augmentation timed out on **300/300 iterations** (`graph_ms` observed 200.3-215.1ms
against the 200ms timeout — this store's graph seed lookup + neighborhood fetch + two Cypher
executions consistently take just over 200ms), so RGT is not a weak reproduction of the
segment-1 abandoned-future condition — every iteration genuinely abandons a real in-flight
`attempt_graph_augmentation` future exactly as `tokio::time::timeout` drops it in production.

## Named accumulator

**Inconclusive at this soak's scale.** No arm reproduces RetrieveHybrid latency growth of any
practical magnitude — R and RP's statistically-significant slopes amount to single-digit
milliseconds of total drift over 300 queries, RG/RGT/W show no significant slope at all, and no
arm's window prong fires. This does not match 06.3.4's observed growth (RetrieveHybrid median
5.0s -> 29.3s over seven 50-record slices) or 06.3.3 segment 1's growth (2.97s -> 10.83s over
four 40-record slices) in either direction or magnitude.

### What was reproduced

- **A real, deterministic abandoned-future condition** (RGT, 300/300 timeouts) with zero
  measurable effect on `alive_tasks`/`global_queue_depth` (both flat at 3 tasks / 0 queue depth
  across every sample, every arm) and no measurable effect on subsequent `RetrieveHybrid`
  iterations' `retrieve_ms`.
- **Per-query `open_table`/`checkout` state**: flat and tiny throughout (`open_table_ms`
  ~1.0-2.1ms, `checkout_ms` ~0.12-0.23ms, all five arms, ordinal 1 through 300 — no drift).
- **Process-level counters** (working set, private bytes, handle count, thread count): all four
  rise sharply in the first 2-3 process samples (~1-3s of wall time — process/runtime/thread-pool
  warm-up: `target/release/retrieval_soak.exe`'s own startup, tokio worker + Lance
  `spawn_cpu`/blocking-pool thread spin-up, first LanceDB dataset opens), then **plateau** for
  the remainder of the run. RGT (guaranteed abandonment on every iteration) plateaus at 46
  threads / ~233 handles / ~187MB working set after its first ~3 samples and stays there for the
  following ~105 one-second samples. RG, R, RP and W show the same shape.

### What was not reproduced, and why that is a real discriminator, not a soak defect

- **The ~15-20x baseline gap between this soak (release, ~55-110ms median `retrieve_ms`) and
  production (06.3.3 segment 2's flat baseline: ~1.6-1.7s; 06.3.4's starting point: ~5.0s) is
  substantially a build-profile confound, not evidence the soak under-reproduces the store's real
  cost.** `06.3.3-BUDGETS.md`'s own "Engine startup proof" section records the only documented
  live-binary launch command for that phase: `cargo run --manifest-path engine/Cargo.toml
  --locked --bin engine` — no `--release` flag, i.e. a **debug** build. A supplementary
  exploratory run of this same soak bin in debug mode (`cargo run` without `--release`, arm R,
  50 iterations, not part of the committed `soak/` artifact set —
  `header.build_profile: "debug"`) measured `retrieve_ms` at **377-529ms** (median 439ms) against
  the release build's 76-136ms range for the same arm — roughly a 4-5x gap from the optimization
  level alone, with **no growth** over those 50 debug-mode iterations either (first-5/last-5
  medians ~445ms/~450ms). That still leaves an unexplained ~3-4x gap to production's observed
  1.6-5s baseline (real network/gRPC/HTTP round-trip overhead absent from this in-process soak,
  a possibly warmer-vs-colder store state, and production's per-request node construction are
  candidate remaining contributors, not measured here).
- **Sustained, unbounded resource growth over hundreds of queries at soak speed.** Every
  process-level counter plateaus within a few seconds of warm-up and does not continue climbing
  through the remaining ~15-140 seconds of wall time each arm's 300 iterations took (RG/RGT/W
  ran 130-140 one-second samples after warm-up with flat readings). If class 2/3 (allocator or
  Lance session-cache growth) is the true accumulator, either it requires materially more
  iterations/wall-time than 300 release-speed queries provide to become visible, or it requires
  concurrent/production request patterns this single-threaded sequential soak does not generate.
- **The harness/gateway path.** This soak never leaves the engine process — no gRPC, no SSE
  streaming, no gateway checkpoint dispatch. A slope that depends on that path (candidate 5,
  lowest-ranked in RESEARCH, and any HTTP/connection-pool-side accumulation) is invisible here by
  construction.

## Methodology note (deviation from the plan's literal "every 5s")

The plan's Task 2 action says to sample the soak process "every 5 s". At soak speed
(55-140ms/iteration, 300 iterations complete in 15-140s depending on arm) a 5s cadence would
have produced only 3-28 samples per arm — too few to see the warm-up/plateau shape this profile
relies on. Samples were taken every 1s instead (still satisfying "sample ... externally"; the
5s figure in the plan was written against production's much slower per-query cost, where 5s
easily captures many queries per sample). 42-140 samples were collected per arm. Recorded here
as a deviation, not silently changed.

## Conclusion

The accumulator class OI-02 is investigating is **not named by this pass** — no arm reproduces
practically meaningful RetrieveHybrid growth, and process-level counters plateau rather than
climb. The pass does, however, rule out per-query `open_table`/`checkout` state (class 4) and
finds no evidence of unbounded task/queue accumulation on the main tokio runtime even under
guaranteed real abandonment (weakening, not confirming, class 1 as tested — with the explicit
caveat that Lance's own blocking pool is invisible to those two counters and only partially
visible via thread count, which itself plateaus). It surfaces a concrete, evidenced alternative
explanation for a large share of the previously-unexplained baseline gap between 06.3.3/06.3.4's
production numbers and this soak's release-mode numbers: those drives' only documented engine
launch command omits `--release`. That is a build-profile confound in the *comparison*, not
proof that growth itself doesn't happen in production — a debug-mode soak run showed a higher
but still flat baseline over 50 iterations, not growth.

This profile does not attempt to decide between the checkpoint's three options; it supplies the
evidence for that decision (Task 3).
