## CR-02 ruling: latent defect outside the SC-1 wording, not a goal gap

**What the code does (read, and reproduced offline).**
- `evaluate_sc1` (`eval/src/lancet_eval/unpark_gates.py:78-160`) checks that the header `partial` flag equals `not completeness_comparison(...)`. It also checks that `report.json` is absent for a partial run and present for a non-partial run.
- I built a 40-of-200-record journal in the scratchpad, with the header set to `partial: true` and no `report.json`. `evaluate_sc1` returned `PASS`, with `missing_units` 160. The reviewer is right about the behaviour.
- `main` (`:1274-1401`) computes SC-2, D-69, SC-3, SC-4 and SC-5 over whatever records exist, and none consults `completeness_comparison`. SC-5 rule (a) has no minimum `n`.

**Why it is not a goal gap.**
1. SC-1's two clauses are: (a) "Journal completeness metadata matches reality (`partial: true` if incomplete)" and (b) "No score/report of a halted run as complete". An honestly labelled partial journal with no report satisfies both clauses literally. The SC-1 gate is a metadata-honesty gate, which is what D-87a and the `evaluate_sc1` docstring define. A `PASS` there does not mean "the run is complete". Clause (a) names `partial: true` as the correct state for an incomplete journal.
2. Clause (b) is enforced where scoring and reporting happen, not in the gate table:
   - `score.py:1586-1594` defaults `effective_partial = True` and flips it only when the header says `false` and `completeness_comparison` independently agrees.
   - `score.py:1663-1667` writes `report.json` only when `not effective_partial`.
   - `report.py:164-166` and `:206-208` refuse to render a partial report. `cli.py:691` does the same.
   - `run.py:279` writes the header as `partial=True`, and `run.py:389-390` calls `reconcile_header` in a `finally`, so every `drive()` exit path, including a cap stop or an exception, ends with a measured header.
   - Wired tests pass: `test_journal_reconcile.py` (including `test_drive_header_staged_mid_run_and_publishable_on_completion`, `test_score_run_publishable_header_with_missing_units_resolves_incomplete` and `test_score_run_staged_header_with_complete_records_trusted_as_incomplete`), `test_report.py::test_partial_run_refuses_to_render` and `test_report_cli_refuses_partial_run`. I ran `test_journal_reconcile.py test_report.py test_stage_cap.py test_unpark_gates.py` and 115 passed.
3. The decisive check is on outputs, not code. I enumerated every journal under `eval/runs/` and asked whether any incomplete journal was ever scored, reported or gated:
   - `2026-09-09-multihop_rag` (the halted 658/1000 run) has `partial: true`, no `report.json`, and a `SUPERSEDED.md`.
   - The measure journals (`2026-09-06`, `passA`, `genprobe`, `genconfirm`, `passB`) have no header `partial` field, no gates file and no report.
   - `drive1`, `drive1b` and `drive2` each have 200 of 200 units, `partial: false`, a `report.json` and a gates file.
   - `eval/runs/smoke_test` (untracked, dated 2026-08-29, pre-phase) has `partial: true` and a `report.json`. It is a legacy artifact from before the fail-closed path existed. It is not tracked in git, was not produced by this phase, and does not affect any claim.
   - No incomplete journal in this phase has a gate table or report beside it, so a halted run was never scored or reported as complete.
4. The run of record satisfies SC-1 on independent evidence, not merely on the gate's say-so. `journal.jsonl` has 200 distinct `(corpus, question_id, graph_arm)` keys, the header is `partial: false`, and `report.json` has `metadata.partial: false`.

**Why it still matters (WARNING, not dismissed).** ROADMAP layer constraint 1 says "This phase must not publish a false-complete report", and the unpark gates are described as "all required". A future operator who runs `unpark_gates --stage drive2` on a halted journal gets an SC-1 `PASS` beside SC-2 to SC-5 readings computed on a thin population, and the table does not say the journal is incomplete. That is a fail-open in the gate tool, not in the run of record. SC-3 also shrinks its denominator for non-D-69 errors without disclosing it (WR-04). The recorded drives are unaffected. This must be fixed or explicitly deferred before the next gated drive and before the 6.4 unpark. It is listed in Human Verification Required.

CR-01 (`measure` ignores the stage cap when `workers > 1`) and CR-03 (retries drop billed attempts) are likewise latent. All three drives of record ran `--workers 1 --retries 0` with complete journals. CR-03 intersects the prohibition about retrying a timeout away. See that item.
