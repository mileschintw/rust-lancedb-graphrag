### G6: the first query on a fresh engine times out in AssemblePrompt (D-93)

- Evidence: preflight `corpus_generation` failed ("No index_generation observed in
  preflight query snapshot"). The engine's first query (correlation
  `f2493e90-06fe-4588-b81b-ce050ee1dda8`) ended after RetrieveHybrid; the Jaeger
  `prompt_assembly` span ran 78.6 ms with `node AssemblePrompt failed: timeout` against
  `prompt_timeout_ms` 65. Earlier fresh-engine first queries: 55 and 74 ms (pass A
  warm-ups, excluded from the derivation), 41 ms (25 probe), 46 ms (26 confirmation);
  steady state about 1 ms. Suspected source: the lazy `tiktoken_rs::cl100k_base_singleton()`
  build on the first `prompt.rs` call (`engine/src/prompt.rs:371`, `:649`); not isolated.
- Required (D-93, both):
  1. Build the prompt tokenizer at engine start, before the server accepts requests (the
     same singleton the prompt path uses, so the first query reuses it). Test-first where
     it can be tested; the startup ordering must be checkable (for example a startup log
     line or event stating the tokenizer is ready, emitted before the serving line).
  2. Raise `prompt_timeout_ms` from 65 to 120 in the config trio, in one commit, updating
     the agreement test and any test pinning 65. The other six values are unchanged.
     Record 120 as the D-93 amendment to the 06.3.4.1-24 decision in `06.3.4.1-BUDGETS.md`
     (the 24 SUMMARY is not rewritten). Recheck nesting and harness ceilings (prompt has
     no inner budget; the worst-case sum rises by 55 ms).
- After the restart, the preflight record must show the first query's AssemblePrompt
  duration (from Jaeger or the engine's events), so the warm-up's effect is measured, not
  assumed.
