### Graph repair (OI-01, layer 5)

- **D-75:** **Seed step: mention extraction + per-mention match, with NO
  query-time LLM call.** Extract candidate entity mentions from the question
  (e.g. capitalized spans / n-grams), match exact/alias against entity names
  first, then per-mention `name_vector` top-k. Allow multiple seeds. This
  replaces `nearest_to(full-question embedding).column("name_vector").limit(1)`
  at `engine/src/service.rs:242-273`.
- **D-76:** **Graph contribution: seed-to-seed paths (≤ 2 hops) + chunk boost.**
  Find short paths that *connect* seeds (the bridge relation). Inject only
  path facts, not unfiltered 1-hop neighbourhoods (the source of 06.3.4's
  -0.0024 F1). Use the source chunks of path entities (`source_chunk_ids`) to
  boost or add retrieval candidates, so the graph visibly changes retrieval
  composition.
- **D-77:** **Traversal cost is bounded by a degree cap on hub expansion + a
  cap on the injected path/fact count.** Values are derived from the
  post-reconcile degree distribution (D-62) and recorded with the derivation
  (current store: max degree 724, p95 10). `graph_operation_timeout_ms` is
  re-derived with the other budgets (D-66) after this lands.
- **D-78:** **Ships as the production default; the old seeding path is
  removed.** No config flag, no eval-only mode. graph-off remains the ablation
  arm. If the result is negative, it is reported per D-49, not toggled off.
  — **Reversibility:** costly — removes the old seeding code path and changes
  production graph behaviour. Undo means re-implementing or restoring from git,
  and re-measuring.
- **D-79:** **Column (d) "graph seed hit" = at least one seed entity sourced from
  a gold evidence document** (via entity → `source_chunk_ids` → document). Also
  record the seed count and whether a seed-to-seed path was found.
- **D-80:** **D-31 canaries are re-validated under the new seeding and
  extended.** Add at least one canary whose gold answer needs a seed-to-seed
  path. The canaries stay hard preflight gates (`check_canary_floors`).

## Summary

This is a four-layer diagnosis-then-repair phase over a stack that already exists. No new framework or dependency is needed.

**Layer 1 is closed.** T-06.3.4-19/24/25/43 are closed. Consume the fail-closed `score_run` (`score.py:1464-1545`) and the measured `reconcile_header`/`completeness_comparison` (`journal.py:144-239`). Do not modify them.

**The identity problem is smaller and better understood than the ROADMAP states** (MEDIUM, inferred):
- The 4 extra LanceDB documents (350 − 346) are all duplicate ingestions of *mapped* articles. They are the alias `0370301a…` plus three unmapped IDs that leak into retrieval: `f9992c53…` (Best Buy price-matching), `fa85cb0e…` (Moneyline Betting) and `3aadce3b…` (The people who ruined the internet). The source is `seed_corpus`'s 5-attempt retry loop (`seed.py:337-401`): each retry POSTs a new gateway document.
- The 21 extra PostgreSQL rows (367 − 346) are not identified. Their IDs must be listed by a query before deleting.
- Every one of the 1,185 gold evidence facts appears verbatim (whitespace/case-normalized) in its article body, and within a single paragraph. So column (b) should be "yes" for nearly all questions. A (b)=no most likely comes from chunk splitting of long paragraphs, not from missing content. D-59 re-ingest will probably be small or empty.
- Ingestion does not rewrite text. All **1,048** distinct non-truncated retrieved-chunk excerpts in the 06.3.3 and 06.3.4 journals are verbatim (normalized) substrings of their article body: 0 mismatches. The odd "below. 500" is in the source body itself. So Recall@4 is not depressed by any chunk-text transformation. (b) must still be computed on stored `nodes.content`, not on the body.

**The OI-02 accumulation is process-wide, not a RetrieveHybrid-local handle problem.** The journals show:
- (1) RetrieveHybrid grew identically in both arms (graph-off 5.0 → 29.4 s, graph-on 4.8 → 29.2 s).
- (2) AssemblePrompt, which is pure CPU (tiktoken + string packing), also doubled (453 → 1,046 ms).
- (3) In 06.3.3, after the restart, segment 2 stayed **flat for 160 records**: RetrieveHybrid medians 1.73/1.56/1.61/1.72 s and graph-on ExtractGraphContext ~1.8 s, with 0 GRAPH_TIMEOUT. Segment 1 grew (RetrieveHybrid 3.0 → 10.8 s; graph-on ExtractGraphContext 9.8 → 30.4 s).
- (4) The store was last written 2026-09-02 (all `_versions` mtimes), so store growth is ruled out.

A flat process is therefore reproducible, and the plan needs a profiling step that reproduces *both* segment conditions before naming a fix.

**The D-71 change is safe on the validator side, with one correction to the AI-SPEC.**
- The citation rule is per-answer.
- On the production path (`citation_repair_enabled = true`, `config/config.toml:60`) the engine **discards the model's `cited_evidence_ids` and rebuilds citations from the `[n]` markers in the answer text** (`generate.rs:258-359`), so set-equality holds by construction.
- An uncited `Answer:` line is neutral.
- A marker on that line is added if it resolves, or stripped with a `CITATION_DROPPED` notice if it does not. It is never "rejected".
- The real D-69 risk is the model dropping *all* inline markers when it is pushed toward short answers. That produces the existing "requires at least one cited evidence ID" message.

### A. D-71 grounding validator (answers required before planning)

**How the validator actually runs in production** (verified `[VERIFIED: engine/src/workflow/nodes/generate.rs:216-455]`):

1. The model returns strict JSON `ModelOutput { answer: String, cited_evidence_ids: Vec<String>, answer_basis: AnswerBasis, notices, warnings, usage }`.
   - Struct: `[VERIFIED: engine/src/generation/mod.rs:57-71]`.
   - Enum `AnswerBasis { Retrieval, Mixed, ModelOnly }`, serialized snake_case `"retrieval" | "mixed" | "model_only"`: `[VERIFIED: engine/src/generation/mod.rs:27-44]`.
   - JSON-schema enum and strict flag `[VERIFIED: engine/src/generation/openrouter.rs:568-571,589-590,611-617]`, verbatim:
     ```
     "answer_basis": {
         "type": "string",
         "enum": ["retrieval", "mixed", "model_only"]
     },
     ...
     "required": ["answer", "cited_evidence_ids", "answer_basis", "notices", "warnings"],
     "additionalProperties": false
     ...
     json_schema: JsonSchemaWrapper {
         name: "model_output".into(),
         strict: true,
     ```
2. **Branch taken in production:** `allow_model_only_answers = false` (`config/config.toml:59`), so the model-only branch at `generate.rs:218-243` is skipped. `citation_repair_enabled = true` (`config/config.toml:60`) and grounding limits are set (`service.rs:153-163`), so the **repair branch** `generate.rs:244-393` runs.
3. In the repair branch:
   - `markers = citations::extract_markers(&output.answer)` (`generate.rs:260`). The widened `[ ws? digits ws? ]` scan is at `citations.rs:82-118`.
   - Each marker is resolved against the packed evidence IDs, which are `"[1]".."[N]"` (`prompt.rs:35-36`: `let id = format!("[{}]", index + 1);`). The outcome is Unchanged, Repaired or Dropped; a drop removes the marker text (`generate.rs:268-314`).
   - `repaired_citations` is rebuilt **only from markers found in the text**. The model's `cited_evidence_ids` is not used. The design comment at `generate.rs:252-257` reads: *"never from `cited_evidence_ids` alone"*.
   - If markers existed but none survived (`total_drop`, `generate.rs:319`), the clone is forced `into_model_only()`.
   - Validation then runs on the clone (`generate.rs:321-348`): `validate_grounding_with_limits`, which is `validate_output_shape_with_limits` followed by `validate_marker_grounding` (`generation/mod.rs:376-383`).

**Answers:**

1. **Per-answer or per-line?** Per-answer. The rule is `if self.cited_evidence_ids.is_empty() && (!limits.allow_model_only || self.answer_basis != AnswerBasis::ModelOnly)` and returns `"answer basis '{}' requires at least one cited evidence ID"` `[VERIFIED: engine/src/generation/mod.rs:209-219]`. On the repair path, "cited evidence IDs" means "resolvable `[n]` markers anywhere in the answer text".

2. **Would an uncited final line add rejections?** No. It adds no markers, so the rebuilt citation set is unchanged.
   - The whole-answer set-equality check (`generation/mod.rs:349-371`) compares `repaired_citations` with the markers in `repaired_answer`. Both come from the same text, so they are equal by construction.
   - `citation_marker_mismatch` is structurally unreachable on the production path. It can only fire when `citation_repair_enabled = false` (`generate.rs:394-410`).
   - A marker placed *on* the Answer line is either added to the citation set (if it resolves) or stripped with a `CITATION_DROPPED` notice (`generate.rs:292-305`). It is not a rejection.
   - Hazard: a bracketed number on the Answer line, such as `Answer: [2023]`, matches the marker grammar, fails to resolve, and is **stripped from the answer**. This corrupts the extracted line. The prompt must forbid square brackets on that line.

3. **Structured output and `answer_basis`:**
   - The answer is a JSON object, and the Answer line lives **inside the `answer` string** (newlines are allowed in a strict-schema string). No new key or proto change is needed.
   - `answer_basis` is a separate enum field that the model chooses. The engine only ever weakens it (D-18 conservative-wins, `workflow/mod.rs:191-221`).
   - **Placement correction:** `base_system_policy()` (`prompt.rs:205-212`) is embedded at the top of the **user** message by `pack_evidence_and_graph_prompt` (`prompt.rs:364-373`). The OpenRouter adapter sends a fixed system message `"You are a precise technical RAG engine."` (`openrouter.rs:295-296`). The instruction therefore belongs in `base_system_policy()`, which is the single source for both callers of `pack_evidence_and_graph_prompt` (AssemblePrompt `assemble_prompt.rs:82` and the adapter `openrouter.rs:269`).

4. **Could it raise D-69's rate?** Yes, through model behaviour, not the validator:
   - (a) If the model shortens its explanation to nothing, it writes no inline markers, which triggers "requires at least one cited evidence ID".
   - (b) If an abstention prompt nudges the model toward `answer_basis: model_only`, that triggers "ModelOnly answer basis is not supported…" (`generation/mod.rs:188-193`).
   - Both are measurable in drive 1 by splitting classes by null/non-null.
   - **Baseline caveat:** the 06.3.4 baseline (43/355) was recorded under `--retries 2`. `drive_one` journals only the *last* attempt (`run.py:87-215`), so first-attempt D-69 failures that later succeeded are invisible. The single-attempt rate under D-67's `--retries 0` is ≥ 43/355 and may already exceed the AI-SPEC's 0.159 tripwire *without any prompt change*. Disclose this at the drive-1 checkpoint.

**Recommended instruction** (append to `base_system_policy()`; keep every existing sentence verbatim) `[ASSUMED wording; placement VERIFIED]`:

```
After your full cited answer, end with exactly one final line in this form:
Answer: <the shortest answer: yes, no, an entity name, or a short phrase>
Keep citing evidence with [n] markers in the explanation above that line. Do not put citation markers or any square brackets on the Answer line.
If the evidence is insufficient, still name the evidence blocks you checked with their [n] markers, then end with: Answer: Insufficient information.
```

**Extraction rule** (harness, `metrics.py`):
- Take the **last** line matching `(?im)^[ \t>*_-]*answer[ \t*_]*:[ \t]*(?P<a>.+?)[ \t]*$`.
- Remove `\[\s*\d+\s*\]` markers.
- Remove `*` and `_` characters. Do **not** delete text between `**…**`.
- Apply `squad_normalize` (`metrics.py:43-59`).
- If nothing matches, or the result is empty after cleanup, set `final_answer_missing = True`, which scores a miss and stays in the denominator (D-74).
- Golden cases: `Answer: Yes`, `**Answer:** Yes`, `**Answer**: **Yes**`, `Answer: Yes [1]`, two Answer lines (the last wins), no line at all, and `Answer:` followed by nothing.

**Optional, not a D-69 fix (planner's choice):** keep the error-message prefixes byte-stable so harness classification by substring still works, but append a diagnostic suffix, e.g. `" (answer text contained 0 [n] markers; model listed k cited_evidence_ids)"` and `" (all N markers dropped)"`. Today the journal cannot tell a self-reported `model_only` from a `total_drop` (the failure returns before notices are added, `generate.rs:339-348`).

    - Runs a **flat** KNN over `name_vector` with `limit(1)` (`service.rs:256-273`). No ANN index exists on any table: `_indices` is empty for every `.lance` dir.

  - Dense: `database.nodes_table()` runs `connection.open_table("nodes")` **per query** (`service.rs:571`, `db/mod.rs:120-123,163-165`), then `nodes.checkout(nodes_version)` per query (`service.rs:577`), then a **flat** KNN `nearest_to(...).column("embedding").limit(32)` over 19,210 × 2,048-float rows in 350 fragments (`dense.rs:56-101`).

  - Then weighted RRF (`fusion.rs:87-195`) and `NoOpReranker` (`main.rs:146`).
- **AssemblePrompt / GenerateAnswer:** `tiktoken_rs::cl100k_base()` rebuilds the full BPE on **every** call (`prompt.rs:362`). It is called twice per query: `assemble_prompt.rs:82` and `openrouter.rs:269`. `tiktoken-rs 0.12` ships `cl100k_base_singleton()` (`singleton.rs:44`).

**Ranked candidate accumulators** (none confirmed; each has a discriminator):

1. **Abandoned CPU work that outlives a timed-out or cancelled future (process-wide contention).**
   - Mechanism: `tokio::time::timeout` drops the graph or node future (`graph_context.rs:117`, `runner.rs:386`), but lance flat-KNN `spawn_cpu` closures and DataFusion tasks continue.
   - A larger per-query in-flight load then feeds back into more timeouts.
   - For: segment 2 had 0 timeouts and was flat. Everything CPU-bound slows.
   - Against: in both runs the slope starts before the first GRAPH_TIMEOUT. The mechanism would need other abandonment, such as harness-side SSE disconnects or retries, or slow-but-not-timed-out graph ops overlapping the next query.
   - Discriminator: tokio `Handle::current().metrics().num_alive_tasks()` and `global_queue_depth()` (both stable in tokio 1.53.1: `runtime/metrics/runtime.rs:74,100`; no new dependency), plus process thread count, sampled per query. If they rise with ordinal, this is the cause.
2. **Memory / allocator degradation from large per-query allocations** on the Windows system allocator.
   - Allocations per query: ~157 MB of `embedding` columns in the dense flat scan; ~229 MB of `name_vector` in the graph-on flat scan; two full cl100k BPE rebuilds.
   - Discriminator: working set and private bytes vs ordinal (external PowerShell `Get-Process` sampling).
   - Fix options:
     - Remove the allocations. This needs no new dependency and is recommended regardless: the tiktoken singleton; caching the opened `nodes` table per `CorpusSnapshot` instead of per query; D-75 replacing the whole-table entity scan.
     - mimalloc (M-MIMALLOC-APPS). Package gate: `OK`, 1.2M weekly downloads. It is a **new crate**, so it needs a `checkpoint:decision` against the AI-SPEC §2 lock.
3. **Lance session cache growth.**
   - The `lancedb::connect(path)` default `Session` has a 1 GiB metadata cache and a 6 GiB index cache (`lance-8.0.0/src/dataset.rs:151,155`).
   - Each query opens new `Dataset` objects via `open_table`.
   - If any cache key is per-open rather than per-file, memory grows to 1 GiB and eviction costs rise.
   - Discriminator: the soak loop with a small explicit session versus the default.
4. **Per-query `open_table` + `checkout` state.**
   - `DatasetConsistencyWrapper` is `Lazy` (`read_consistency_interval: None`) with no background refresh (`lancedb-0.31.0/src/table/dataset.rs:57-77`). This makes it unlikely to grow, but it is a cheap fix anyway: open the table once per snapshot.
   - Discriminator: per-sub-stage timing of `open_table`, `checkout` and `execute+collect`.
5. **PostgreSQL checkpoint growth / gateway backpressure.** Ruled out by the 06.3.3 restart discriminator and the async dispatcher. Keep it as a sanity metric only.

**Cascade specification** (one Rust bin, e.g. `engine/src/bin/reconcile_eval_store.rs`, default `--dry-run`; `--apply` requires `--snapshot-dir` to exist). The allow-list is `document_map.json` `entries` keys; aliases are NOT allowed.

### F. D-75/D-76/D-77 graph repair design

**Primitives that exist:**

| Primitive | Location | Fit for this design |
|---|---|---|
| lance-graph Cypher (`CypherQuery::new(...).with_config(...).with_parameter(...).execute(datasets, None)`) | `graph/mod.rs:146-326` | Runs over an **in-memory** already-narrowed RecordBatch. Variable-length `*1..hop_cap` with `hop_cap ≤ 3`; `r` cannot be projected (`graph/mod.rs:202-265`). Directed only, so the codebase runs it forward and reversed (`graph/mod.rs:598-647`). | Bounded BFS `fetch_neighborhood(db, seed, hop_cap, bidirectional)` | `graph/mod.rs:345-533` | **Errors** (does not truncate) when `seen_edge_ids > MAX_TOTAL_EDGES = 500` or the next frontier > `MAX_FRONTIER_SIZE = 200` (`graph/mod.rs:336-337,411-458`). Hubs such as Google (552 edges) and the degree-724 entity fail (06.3.3-STORE-BASELINE §3). In 06.3.4 these errors never surfaced (0 `GRAPH_DEGRADED` notices) because the 40 s timeout fired first. |

| Multi-vector KNN | `lancedb-0.31.0/src/query.rs:1115` `add_query_vector` | One flat scan for all mention vectors, instead of N scans. |
| Distance semantics | `service.rs:308-313` + `dense.rs:162-164` | `score = 1/(1+L2 distance)` with the default L2 metric. `seed_match_min_score = 0.5` (`config.rs:94-96`; no `[engine.graph]` in `config.toml`, so the default applies). |

**Recommendation: do path search in Rust set operations over `entity_edges`, not Cypher.** It is simpler, bounded, and can return the bridge node and relation. Keep Cypher-backed `QueryGraph` untouched.

1. **Seeds (D-75)** — for each question:
   - Extract mentions: maximal capitalized spans (allow inner `of|and|&|de|the|-|.|'`), strip leading stop-words (`Does|Which|What|Who|Between|Considering|The|A|…`), strip possessive `'s`/`’s`.
   - Also emit a sub-span without a leading "The".
   - This yields a median of 5 mentions/question on the sample (p10 2; 1 question with 0) `[VERIFIED: computed this session over questions.sample.jsonl]`.
   - Match order: case-folded exact name (hash map) → normalized form (strip punctuation/articles) → `name_vector` top-k (k=3) **only** for unmatched mentions. Batch all unmatched mentions into **one** embedding call (`get_embeddings(&[...])` takes a slice, `service.rs:439-442`) and **one** multi-vector KNN.
   - Accept a vector match only at `score ≥ seed_match_min_score` (keep 0.5 unless the offline probe says otherwise).
   - Cap seeds at ~6.
   - **Publisher attributions** ("article from TechCrunch", "The Verge"): 461/500 questions name a source. These typically match hub entities. Do not special-case the eval corpus in production. Let the degree cap and a specificity weight `1/ln(2+degree)` (HippoRAG-style) demote them.
2. **Precompute per corpus generation** (immutable, lives in `CorpusSnapshot`, rebuilt at the same trigger as BM25, `ingest.rs:1604-1660`):
   - a `name_casefold → [entity_id]` map
   - `degree[entity_id]`
   - `entity_id → source_chunk_ids`

   This is **not** an unbounded query-time cache (AI-SPEC §3 Pitfall 4 is right about that), and it removes the per-query flat `entities` scan that is a leading OI-02 cost.
3. **Paths (D-76):**
   - For each seed pair (≤ 15 pairs): a direct edge A–B = 1-hop path.
   - 2-hop A–X–B = `N(A) ∩ N(B)`, where `N()` comes from one `entity_edges` scan with `source_node_id IN (seeds) OR target_node_id IN (seeds)`, the same predicate style as `graph/mod.rs:371-375`.
   - **Exclude intermediates X with `degree[X] > DEGREE_CAP`.** Seeds themselves are never "expanded" beyond this one scan, so hubs cannot blow up.
   - Emit path facts `A –rel→ X –rel→ B`, capped at `MAX_PATH_FACTS`, ranked by `Σ weight × specificity`.
4. **Chunk boost (D-76) — use RRF injection, not score boost:**
   - ExtractGraphContext runs *before* RetrieveHybrid, so it can put `ctx.graph_chunk_candidates: Vec<(chunk_id, score)>` (the source chunks of path entities) into the context.
   - RetrieveHybrid fetches those rows from the pinned `nodes` version (`chunk_id IN (...)`) and adds them as a **third RRF list** in `fuse_candidates` (`fusion.rs:87-195`). It needs a new `VariantProvenanceSource::Graph` (`fusion.rs:21-27`) and weight `graph_rrf_weight`, a **new** retrieval setting. Do **not** reuse `graph_weight`, which is D-30's prompt-packing multiplier (`generation/mod.rs:454-459`).
   - Injection both **adds** chunks that neither dense nor BM25 found and **boosts** chunks already present (RRF sums). A pure score boost can only reorder.
   - graph-off early-returns (`graph_context.rs:95-105`), so its retrieval is unchanged, which preserves ablation invariance.
   - Mark each fused candidate that has Graph provenance, and surface it as a new additive `StructuredCitation` field (§ wire changes) for D-81's composition measure.
   - Cap the injected list at `final_limit` (8).
5. **Config keys** (all in `GraphSettings`/`GraphConfigSettings`, `config.rs:94-123`; plus one retrieval key; defaults in `config.rs` equal to `config.toml` and `config.example.toml`):
   - `max_seeds`, `mention_vector_top_k`, `degree_cap`, `max_path_facts`, `max_graph_chunk_candidates`
   - `retrieval.graph_rrf_weight`
   - D-78 forbids an on/off flag. These are tuning values, not a mode switch.
6. **Deriving the caps (D-77):** run on the post-reconcile distribution from §D.
   - `DEGREE_CAP` = degree at the **p99** of the post-reconcile entity-degree distribution, rounded up and recorded with the full sorted-degree histogram. Rationale: p95 = 10 would exclude mid-size real entities (SBF 44, FTX 257, Apple 361); max 724 admits hubs.
   - `MAX_PATH_FACTS` = `floor(0.10 × (evidence_token_budget − answer_budget) / tokens_per_fact)`, with `tokens_per_fact` measured as the cl100k p95 over the rendered path facts in the offline probe. For example 0.10 × 6144 / ~25 ≈ 24; round down to ≤ 16 `[ASSUMED]`.
   - `graph_operation_timeout_ms` is re-derived in budget pass B (D-66/D-77).
7. **De-risk before paid drive 2 (strongly recommended):** an **offline seed/path probe** over the diagnostic sample, free except one batched mention-embedding call per question (< $0.01). It emits seed count, (d) seed hit, path found, candidate chunk IDs and composition-change-vs-dense for every question. Concern: comparison questions (179/447) pair entities from unrelated articles, and many inference questions name only publishers plus the answer clue. So *seed-to-seed paths may be rare*, and D-76's literal "path entities only" chunk boost could leave SC-4/SC-5 near zero. ### Pattern 1: Additive wire fields end-to-end
**What:** Every new per-record field (`graph_seed_count`, `graph_path_found`, `graph_boosted_chunk_count`, per-chunk `graph_boosted`) goes through all of the following:
- proto (`lancet.proto:126-136,237-252`)
- `buf generate`
- engine population
- gateway explicit map (`sse.go:112-135` and the snapshot/chunk DTOs)
- harness `client.WorkflowMetadata` (`extra="ignore"`)
- `journal.WorkflowWireMeta` (`extra="forbid"`, `journal.py:28-42`), with an optional default like `graph_prompt_fact_count: int | None = None`
- the `run.py:123` mapping

**When:** D-79 and D-81. D-71's "no proto change" scopes to the answer only.
**Current tags** `[VERIFIED: proto/lancet/v1/lancet.proto:126-136,237-252]`:
- `StructuredCitation` ends at `string content_type = 9;`, so the next free tag is 10.
- `WorkflowMetadata` ends at `uint32 graph_prompt_fact_count = 11;`, so the next free tag is 12.

New fields must take tags ≥ these and be additive only (the `bb9d2086` precedent). The field names above are `[ASSUMED]` proposals.

### Pattern 2: Immutable per-generation structures, not caches
**What:** Build the name index, degree map and chunk provenance once per `CorpusSnapshot` (`ports.rs:19-38`). Swap them atomically with BM25 on rebuild.
**Why:** It removes per-query full scans without introducing an OI-02-style accumulator.

### Pattern 3: One-way store change behind a decision checkpoint
**What:** Dry-run output (IDs, row counts per table, entities to rewrite/delete) is committed first. Then a `checkpoint:decision`. Then `--apply` with snapshot directory + recorded versions + pg_dump. Then the engine restart and generation probe.

### Anti-Patterns to Avoid
- **Hand-writing `index_generation`** in `document_map.json`. Always probe the restarted engine.
- **Pruning provenance by extra-doc prefix only.** Prune by the surviving-chunk allow-list.
- **Running `optimize`/compaction/`cleanup_old_versions` during reconcile.** It destroys the version-restore rollback.
- **A diag corpus with a copied `document_map.json`.** Two maps drift.
- **Raising budgets or restarting the engine to make drive 1 flat.** D-64 forbids both. So does leaving `LANCET_ENGINE__WORKFLOW__*` env overrides set.
- **Scoring (e) on full-answer containment.** A yes/no gold is "contained" in most explanations. Use the extracted line only.

## Common Pitfalls

### Pitfall 1: Scoring refuses the run of record because a duplicate doc leaked
**What goes wrong:** `score_run` raises `Unmapped document_id` (`score.py:255-274`) when any retrieved chunk comes from `f9992c53…`/`fa85cb0e…`/`3aadce3b…`.
**How to avoid:** Reconcile before any scored drive; the D-61 gate enforces it.

### Pitfall 2: The engine is not restarted after the reconcile
**What goes wrong:** Dense retrieval checks out the startup `nodes_version` (`service.rs:577`) and BM25 is a startup snapshot. The deletes are invisible and `index_generation` stays `lance-701`.
**Warning sign:** the preflight probe still reports `lance-701`.

### Pitfall 3: `check_corpus_generation` fails after the reconcile
**What goes wrong:** The map's `index_generation` is stale (`preflight.py:220-229`).
**How to avoid:** Refresh it from the probe, never by hand.

### Pitfall 4: The D-69 tripwire fires from the retry change, not the prompt
**What goes wrong:** The 43/355 baseline hides first-attempt failures because of `--retries 2` (`run.py:87-215`). Drive 1 runs `--retries 0`.
**How to avoid:** State this at the drive-1 checkpoint. Split classes by null/non-null.

### Pitfall 5: Square brackets on the Answer line
**What goes wrong:** `[2023]` matches the marker grammar and is stripped by repair (`citations.rs:82-118`, `generate.rs:309-314`). The extracted answer becomes empty.
**How to avoid:** Prompt rule plus a golden test.

### Pitfall 6: Flatness reads "not present" when it is actually unavailable
**What goes wrong:** One RetrieveHybrid timeout censors the set (`decay.py:522-524`).
**How to avoid:** Require `is_available` on both prongs. Never read `verdict_decay_present` alone.

### Pitfall 7: The window prong at small n
**What goes wrong:** The late-25% p95 minus the early-25% p95 must stay under 500 ms (`decay.py:232-306`). With ~50-record windows, p95 is a single high observation, and noise alone can fire it on a ~2 s node.
**How to avoid:** Report the 50-record-slice medians beside the verdict. This is a committed threshold; do not relax it.

### Pitfall 8: `measure` defaults to a $5 cap
**What goes wrong:** `--stage-cap` defaults to 5.0 (`cli.py:872-877`).
**How to avoid:** Always pass the authorised figure.

### Pitfall 9: The hard-coded canary manifest counts
**What goes wrong:** 7 rows / 6 IDs is enforced (`preflight.py:345-365`). Adding a canary without changing it fails preflight.

### Pitfall 10: The engine test-count gate
**What goes wrong:** `scripts/engine-test-targets.sh` asserts exact counts.
**How to avoid:** Every Rust test added must update it in the same commit.

### Pitfall 11: Drive 1 still has the old graph path
**What goes wrong:** If the accumulator lives there, the OI-02 fix must cover it (§C).

### Pitfall 12: Seed-to-seed paths may be rare on this corpus
**What goes wrong:** Comparison questions pair unrelated articles, and 461/500 questions name a publisher. SC-4/SC-5 may miss with a "paths only" boost.
**How to avoid:** Run the offline probe first.

### Pitfall 14: A staged row replays at restart
**What goes wrong:** Any `staged_documents_v2` row is re-ingested when the engine starts (`main.rs:114-121`). That means paid extraction, and the generation changes mid-drive, which gets the journal rejected for mixed generations.
**How to avoid:** Gate on 0 staged rows before every restart.

### Pitfall 13: Proto regeneration needs network
**What goes wrong:** `buf.gen.yaml` uses remote plugins.
**How to avoid:** Plan for it. If it is offline, regeneration blocks.

### Final-answer extraction (harness)
```python
import re
from lancet_eval.metrics import squad_normalize

_ANSWER_LINE = re.compile(r"(?im)^[ \t>*_-]*answer[ \t*_]*:[ \t]*(?P<a>.+?)[ \t]*$")
_MARKER = re.compile(r"\[\s*\d+\s*\]")

def extract_final_answer(answer: str) -> str | None:
    matches = list(_ANSWER_LINE.finditer(answer or ""))
    if not matches:
        return None
    text = _MARKER.sub("", matches[-1].group("a")).replace("*", "").replace("_", " ")
    norm = squad_normalize(text)
    return norm or None
```
