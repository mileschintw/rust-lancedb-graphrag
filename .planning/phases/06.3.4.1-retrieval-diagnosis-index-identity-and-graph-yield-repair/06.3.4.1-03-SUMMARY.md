## Decisions Made

- **Checkpoint resolved diagnose-in-drive-1**, not fix-named-class or mimalloc: three independent soak passes (build profile, iteration count/wall-time at soak speed, and 2.5 real hours of production-paced wall-clock time) all failed to reproduce practically meaningful `RetrieveHybrid` growth. Neither remaining option is available without a named accumulator class, and none was named.
- **Production ran `--workers 1`**, ruling out concurrency as an explanation for the already-observed 06.3.4 growth episode specifically (though concurrent load in general remains untested by this soak's single-threaded design).
- **Query embedding and generation happen outside the `RetrieveHybrid` span**, so provider network latency cannot explain growth measured inside that span.
- **The eval store was not written to during the 06.3.4 drive** (newest `_versions` 2026-09-02; drive ran 2026-09-09/10), ruling out store mutation as a candidate for that episode.
- **Class 3 (Lance session cache growth) is a watch item, not a named cause**: the one counter across all three passes that grows continuously (if decelerating) rather than plateauing, but its growth does not correlate with this soak's own retrieval latency.
- **D-64 root-cause identification moves to paid drive 1**, via the P1 tracing and flatness adapter already built here, with no restart workaround and no raised timeout budget as a substitute.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `tracing_subscriber` fmt layer redirected from stdout to stderr**
- **Found during:** Task 1, building `retrieval_soak.rs`
- **Issue:** `engine::telemetry::init`'s console-only and OTel-diagnostics fmt layers wrote to stdout by default. `retrieval_soak.rs` (like `inspect_lancedb.rs` before it) uses stdout as its structured-output interface (one JSON header line, one JSON line per iteration, per M-LOG-NOT-PRINT's inspect-bin exception) -- process-global tracing output on stdout would interleave with and corrupt that output.
- **Fix:** `tracing_subscriber::fmt::layer().with_writer(std::io::stderr)` on both the console-only and OTel-diagnostics fmt layers in `telemetry/mod.rs`. `main.rs`'s own stdout is not consumed by anything today, so this is behavior-neutral for production.
- **Files modified:** `engine/src/telemetry/mod.rs`
- **Verification:** Soak bin's stdout output is clean JSON only, no interleaved tracing lines; engine lib test suite passes unchanged.
- **Committed in:** `784b8972` (Task 1 commit)

**2. [Rule 3 - Blocking] `CARGO_BUILD_JOBS=4` required for release/debug builds**
- **Found during:** Extended profiling rounds 2 and 3
- **Issue:** Building `retrieval_soak` at full machine parallelism exhausted local resources (established in an earlier round of this phase, reconfirmed here).
- **Fix:** `CARGO_BUILD_JOBS=4` used for every build in rounds 2 and 3.
- **Files modified:** none (build-invocation only)
- **Verification:** All builds completed cleanly at this job count.
- **Committed in:** n/a (build-time environment variable, not a code change)

### Scope Extensions (user-directed via the checkpoint)
