## Accomplishments

- **Snapshot and index (Task 1).** `CorpusSnapshot.graph_index: Arc<GraphIndex>`. `main.rs` builds it before the first snapshot; `rebuild_and_swap` builds it next to BM25 off the write lock and swaps both inside one new snapshot. A build failure keeps the whole prior snapshot (BM25, graph index, generation) with `rebuild_degraded` set, so a query never sees a new BM25 index beside an old graph index. A query holding the old `Arc<CorpusSnapshot>` keeps the old index.
- **Settings (Task 2).** `max_seeds` 6, `mention_vector_top_k` 3, `degree_cap` 33, `max_path_facts` 8 and `max_graph_chunk_candidates` 8, each with a doc-commented `default_*` function that references the library constant (`DEFAULT_MAX_SEEDS`, `DEFAULT_MENTION_VECTOR_TOP_K`, `DEGREE_CAP`, `MAX_PATH_FACTS`, `default_final_limit()`). `config.toml` gains `[engine.graph]` (it had none); both files carry the D-77 comments. Startup rejects a zero `max_seeds`, `degree_cap` or `max_path_facts`. `config/config.eval.toml` is untouched.
- **Cutover (Task 3).** `attempt_graph_augmentation(database, graph_index, question, embedder, settings)` runs `extract_mentions`, `match_seeds` (with `LanceMentionVectorSearch`) and `find_seed_paths`, and returns the outcome plus a `GraphAugmentationReport`. An empty index or no mention returns `NoMatchFound` before any embedding call or store read. Every error is `AttemptedAndFailed`. The old single nearest-entity query over `name_vector`, its one-hop `fetch_neighborhood` and `narrow_via_cypher` narrowing are deleted from the augmentation path (`fetch_neighborhood`, `narrow_via_cypher` and the QueryGraph RPC stay for their other callers). `grep -c 'limit(1)' engine/src/service.rs` is 0.
- **Node and context.** The port takes the original question and returns a `GraphQueryOutput`. The node records the five D-79 fields on every completed query (so seeds that found no path are visible), takes `graph_node_count` and `graph_edge_count` from the path entities and hops, and leaves every field at its default for graph-off, a failure or a timeout. The `graph_traversal` span records `lancet.graph.seed_count` and `lancet.graph.path_found` (declared `Empty` and recorded), and no question text or entity name.
- **Two-hop text settled.** See Decisions Made.

## Decisions Made

- **Two-hop text (the question plan 13 left to this plan).** The user's instruction was to keep the clean `PathFact.rendered` text with arrow directions. The prompt body of a path fact is now that text: the packer uses `PrecomputedSemantics`, which renders a fact's `edge_summary` when it has one and the plain triple when it does not (existing facts with no summary render byte-identically). The relation attribute stays the chain `r1->X->r2` of the measured shape, one `GraphFact` per path, but each arrow now points the way its hop is stored (`ASSOCIATED_WITH←Sherrone Moore→SUBSTITUTE_FOR` for the path `Penn State ←ASSOCIATED_WITH— Sherrone Moore —SUBSTITUTE_FOR→ Jim Harbaugh`). Plan 13's chain used a forward arrow for both hops, which told the model that a hop stored against the path pointed along it, and the first cut of this plan left that contradiction between the attribute and the body of one block. A two-fact rendering was not adopted: it was not measured and would reopen the user-confirmed cap.
- **Confirmed cap still holds, on a limited check.** The new block was compared with the block as measured (forward arrows in the chain, the chain as the body) on two sample paths, `Penn State/Moore/Harbaugh` and `The Verge/Snap/TechCrunch`: **0 extra tokens per fact**. `derive_max_path_facts(8192, 2048, 69 + 0)` is still 8, and it stays 8 while the p95 is at or below 76. This is not a re-measurement over the 338 probe paths (no paid call was allowed); deliverable D5 is marked for human judgment for that reason.
- **Paths-only, enforced.** Seeds with no path: `Succeeded` with empty facts, `graph_path_found = false`, empty `graph_chunk_candidates`, the seed count and `graph_seed_document_ids` still recorded.
- **Presence counters changed meaning.** `graph_node_count` and `graph_edge_count` are the distinct entities and the hops on the kept paths and are non-zero only when a path exists. The 9.8% graph presence figure of the old seeding (which counted any 1-hop neighbourhood) is not comparable with the new one.
- **Failure injection by a builder value.** `rebuild_and_swap_with_graph_builder` takes the graph index builder as a function value, so the new tests inject a failure without a process-global flag that a parallel rebuild test could consume. `rebuild_and_swap` keeps its signature and passes `GraphIndex::build`.

## Issues Encountered

- **Stale-index risk in tests.** Test helpers that build a service before adding entities see an index without them. `configured_service` builds the real index from the store at construction, as `main.rs` does; a test that adds entities afterwards must rebuild.
- **Isolation covers the index only.** The mention vector search and the edge scan read the live tables, not a pinned version. Vector hits for an entity that is not in the snapshot's index are dropped by `match_seeds`; edges are not pinned to the snapshot's generation.
- **`seed_document_ids` is unbounded.** A hub seed such as `Google` (543 edges) can contribute many document IDs. Plan 16 may need to cap it for the wire.

## Cost and latency notes for plans 17, 18 and 19

- **A new per-query outbound call.** A graph-on question with at least one mention that no entity name matches now makes one more embedding request (one batch for all such mentions) inside `graph_operation_timeout`, which stays at 10000 ms. In the offline probe 19.4% of seeds came from that fallback. `graph_operation_timeout` is for plan 18 to re-derive; the call is included in what it must cover.
- **Index memory and startup.** One scan each of `entities` and `entity_edges` at startup and at every rebuild (27,855 entities and 45,052 edges on the eval store), held in memory per snapshot generation.
