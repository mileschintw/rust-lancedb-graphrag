# Phase 06.3.4.1 Plan 15: The graph's chunks as a third RRF list in retrieval (D-76, D-81) Summary

**Graph-on retrieval now includes the source chunks of the entities on seed-to-seed paths: RetrieveHybrid reads them once per query at the snapshot's `nodes` version, merges them into fusion as a third RRF list weighted by the new `graph_rrf_weight` (1.0), and flags every chunk the graph contributed to, while graph-off fusion and node output stay byte-identical to what was recorded before the change.**

## Accomplishments

- **Third RRF list (Task 1).** `fuse_cross_variant_candidates(variant_lists, graph_candidates, settings)` merges the per-variant lists as before, then merges the graph list once into that result. Each graph candidate at rank `r` adds `graph_rrf_weight / (rrf_k + r)` and a `graph` provenance entry (variant 0): a chunk dense or BM25 found gains the contribution and keeps its first canonical copy, a chunk only the graph found is appended with that contribution as its whole score. The list is de-duplicated, bounded by `candidate_limit`, rejected on a non-finite score, and ignored at weight `0.0`. The result is re-sorted by score with a stable sort, so ties keep the D-51 order the earlier passes gave them. An empty list or a zero weight returns before any sort. `fuse_candidates` is unchanged.
- **Setting (Task 1).** `graph_rrf_weight` is in `RetrievalSettings` (validated like `graph_weight`, outside the vector+bm25 non-zero rule), `RetrievalConfigSettings` with `default_graph_rrf_weight()` (documented derivation: equal to `vector_weight`), `config/config.toml` and `config/config.example.toml`, with the agreement checked by a unit test and by the existing example-contract test. `graph_weight` (D-30) is untouched and a test pins that it never reaches fusion.
- **Graph fetch at the pinned version (Task 2).** `DenseRetrievalPort::fetch_chunks_by_id(ids, cancel)`. The production port opens `nodes`, checks out `self.nodes_version` (the snapshot's), and calls `DenseRetriever::fetch_by_chunk_ids`, which validates every ID with `is_valid_chunk_id`, escapes them, runs `chunk_id IN (...)`, and returns the rows in request order, skipping IDs the generation lacks. It does not write the dense sub-stage timings. `is_valid_chunk_id` requires a UUIDv4 in its canonical lower-case hyphenated form (so upper-case, simple, braced and `urn:uuid:` spellings fail), and an unsigned decimal `i32` with no sign, no leading zero and no whitespace.
- **Node (Task 2).** `RetrieveHybridNode::fetch_graph_candidates` runs once per query before the variant loop. It does nothing for an empty list, a zero `graph_rrf_weight` or no dense port. It drops malformed IDs (one warning with a count, no ID text), de-duplicates, applies the request's `DocumentFilter`, degrades a failed read to no graph list (warning with the error kind only, plus the graph path-failure metric), and propagates cancellation. The count `ctx.graph_boosted_chunk_count` is reset at the start of every run and set over `evidence_blocks`, which is after the final limit. `graph_fetch_ms` joins the sub-stage report and its tracing event.
- **Flag (Task 2).** `FusedCandidate::graph_boosted()` reads the provenance. `EvidenceBlock.graph_boosted` carries it to the retrieved-chunk representation that plan 16 puts on the wire; it is never rendered into the prompt and is omitted from the checkpoint JSON when false.

## Decisions Made

See `key-decisions` above. Two points of method:

- **The cross-variant pass is where the independence comes from.** With two or more variants the pass keeps only each chunk's rank in each list. A graph block placed in variant 0 would therefore shift a chunk's rank in one list, and its effect on the final score would depend on what the other variants ranked. Merging after the pass makes the contribution exactly `graph_rrf_weight / (rrf_k + rank)` whatever the variant count, which `the_graph_contribution_does_not_scale_with_the_variant_count` checks for a graph-only chunk and for a chunk already found by dense and BM25.
- **The pins are recorded, not derived.** The fusion golden was produced by running the fusion code at 8899b6b5, before any change, over seven scenarios (one variant, three variants, exact ties, empty inputs), with every float as its bit pattern. The node pins were recorded after Task 1's fusion change and before any change to `retrieve.rs`; that is a fair pin because Task 1's change is inert without a graph list, which the fusion golden proves from 8899b6b5. The node pins are not recorded at 8899b6b5.

## Issues Encountered

- **Limitation: non-canonical document IDs.** Ingest's `validate_document_id` accepts upper-case, simple and braced UUID spellings and stores the string as given, so a store written that way would have its chunks dropped from the boost by the canonical-form check. The drop is counted in the warning. Every chunk ID in the planning documents is lower-case hyphenated and the gateway generates lower-case IDs, so this is not blocking; it is worth a glance when the live store is next read.
- **`scripts/engine-test-targets.sh` printed zeros once** (TOTAL 0) right after a formatter run changed a file; the next run printed the measured counts. Not reproduced.
- **Isolation covers the chunk read only.** As in plan 14, the mention vector search and the edge scan read the live tables; only the graph chunk fetch is pinned to the snapshot's `nodes` version.

## Cost and latency notes for plans 17, 18 and 19

- **One more `nodes` read per graph-on query:** an open, a checkout and a `chunk_id IN (...)` read of at most 8 IDs. `chunk_id` has no scalar index on the table, so this is likely a scan of the pinned version.
- **It runs inside `retrieve_timeout_ms` (2500), which this plan did not change.** A slow read is not caught by the fetch's own degrade path; it trips the runner's node timeout and fails RetrieveHybrid instead of degrading. Plan 18 must include this read when it re-derives the budget, next to the extra mention-embedding call plan 14 recorded for `graph_operation_timeout_ms`.
- **`graph_fetch_ms`** is now in the sub-stage event, so the cost is measurable on the next soak or drive without new instrumentation.
