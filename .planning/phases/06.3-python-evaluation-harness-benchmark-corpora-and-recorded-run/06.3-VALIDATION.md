# Phase 06.3 — Validation Strategy

> Per-phase validation contract for feedback sampling during execution.

---

## Test Infrastructure

This phase spans two test stacks. The Python harness is new (`eval/` does not exist in the
repository today); the Rust engine suite already exists and is only extended.

| Property | Python half (`eval/`) | Rust half (`engine/`) |
|----------|-----------------------|-----------------------|
| **Framework** | pytest + pytest-httpx, run under `uv` | `cargo test` (built-in harness) + local mock HTTP server |
| **Config file** | `eval/pyproject.toml` — **none today; Wave 0 (`06.3-01` Task 1) creates it** | `engine/Cargo.toml` — exists |
| **Quick run command** | `uv run --project eval pytest {test_file} -v` | `cargo test --manifest-path engine/Cargo.toml --locked {filter} -- --nocapture` |
| **Full suite command** | `uv run --project eval pytest` then `uv run --project eval ruff check --preview src tests` then `uv lock --project eval --check` | `cargo test --manifest-path engine/Cargo.toml --locked` then `sh scripts/engine-test-targets.sh` |
| **Estimated runtime** | ~10–30 s (fully offline: synthetic SSE fixtures, no gateway, no network, no `OPENROUTER_API_KEY`) | ~120–180 s warm (~cold build longer) |
| **Network required** | No — offline is an asserted invariant, not a convenience | No — every mock server binds `127.0.0.1:0` |

*Runtimes are projections; confirm and correct them when Wave 0 lands (`06.3-01` Task 1).*

---

## Sampling Rate

- **After every task commit:** run that task's `<automated>` command(s) — the per-task quick
  command from the map below.
- **After every plan wave:** run the full suite for the half that wave touched. Waves 2–6 are
  Python-only; wave 1 touches both halves.
- **Before `/gsd-verify-work`:** both full suites must be green, and `uv lock --project eval --check`
  must report no drift.
- **Max feedback latency:** 30 s for the Python half (plans 01, 03–07 — every task); 180 s for the
  Rust half (plan 02 only, Task 2's whole-crate run).

## Wave 0 Requirements

There is no separate Wave 0 plan. **`06.3-01` Task 1 (the tracer) is the Wave 0 bootstrap** — `eval/`
does not exist in the repository, so no Python test infrastructure exists yet and Task 1 stands up its
own harness before asserting against it. Every other Python plan (`06.3-03` … `06.3-07`) declares
`depends_on: ["06.3-01"]`, so the bootstrap is strictly upstream of everything that consumes it.

- [ ] `eval/pyproject.toml`, `eval/uv.lock`, `eval/.python-version` — the uv project itself; no pytest
      framework is installed anywhere in this repo today. Created by `06.3-01` Task 1.
- [ ] `eval/tests/conftest.py` — shared fixtures: repo-root path anchoring, synthetic SSE fixture
      loading, and environment isolation so the suite runs with no `OPENROUTER_API_KEY`. Created by
      `06.3-01` Task 1.
- [ ] `eval/tests/fixtures/sse/*.txt` — the six byte-exact synthetic SSE streams (happy,
      degraded-terminal-only, node-failed-then-success, duplicate-final-answer, missing-terminal,
      stream-error) every offline contract test drives. Created by `06.3-01` Task 1.
- [ ] `eval/tests/test_client_contract.py` — the first executable test. `06.3-01` Task 1's own
      `<automated>` command cannot run until that same task creates this file; that is expected for a
      bootstrap task, not a gap.
- [x] Rust half: **no Wave 0 work required.** `engine/src/generation/tests.rs` and
      `scripts/engine-test-targets.sh` both already exist, so `06.3-02` extends existing infrastructure
      and its `<automated>` commands are runnable today.

## Manual-Only Verifications

Seven `<human-check>` blocks exist across the phase. Each sits **alongside** an `<automated>` command
in the same task — none replaces automated coverage; each covers behaviour that only the live stack,
live quota, or a human judgement can exhibit.

| Behavior | Requirement | Why Manual | Test Instructions |
|----------|-------------|------------|-------------------|
| `06.3-01-03` — `probe` drives the running gateway once end to end and renders a report | OBS-02 | The tracer's whole point is proving the live path; a synthetic SSE fixture proves the parser, not the wiring | With PostgreSQL, the engine and the gateway running (any store), run `lancet-eval probe --question ... --gold-fact ... --out ./tmp-probe`; confirm exit 0, one retrieval row plus the OBS-04 skipped row in `report.md`, and a `correlation_id` in `report.json`. A 0.0 retrieval score is a valid outcome |
| `06.3-04-01` — uploaded rows land in the `lancet_eval` schema and not in `public` | OBS-02 | Schema placement is only observable by direct query against a live PostgreSQL, and the Atlas branch (env/flag override vs. `psql` pre-create) is chosen at execution time by live probe | Run the eval-schema creation and Atlas invocation for the chosen branch, start engine + gateway with `LANCET_ENV=eval` and the eval DSN, upload one small file, then query both schemas. Record the branch taken and both query results in the SUMMARY |
| `06.3-04-02` — seeding through the real `/documents` ingestion path, and the document map it produces | OBS-02 | Seeding embeds every chunk against the live free-tier allowance; the map's completeness and the observed quota pressure cannot be simulated | Run `lancet-eval seed --corpus multihop_rag` to completion; confirm one `document_map.json` entry per subset article, a non-empty `index_generation` header, and a matching row count. Re-run and confirm it uploads nothing. Record wall-clock time and rate-limit pressure |
| `06.3-04-03` — preflight passes against a live stack and fails actionably against a stopped one | OBS-02 | Observing the failure path requires stopping a real service mid-flight | Run `preflight --corpus multihop_rag` and `... --judged`; confirm every named check prints a pass line, exit 0, and the judged form prints the remaining daily allowance. | `06.3-05-02` — two-armed run, partial stamping, and resume after a real interruption | OBS-02 | Resume correctness after a genuine mid-flight interrupt (truncated trailing line, in-flight stream) cannot be faithfully reproduced offline | Run `run --corpus multihop_rag --limit 3`; confirm six journal lines each with `index_generation` and `correlation_id`, and a partial-stamped header.
