## 1. System Classification

**System Type:** RAG / GraphRAG **evaluation harness** — an external, black-box HTTP/SSE client.

> Note on classification: the *system under evaluation* is multi-hop RAG + knowledge graph, already
> shipped in Rust (engine) and Go (gateway) through Phase 5. The artifact **this phase builds** is
> not itself an AI system — it is an integration harness plus a scorer that drives the shipped
> system as a real client would (D-48). The only LLM call the harness makes on its own behalf is
> the confined groundedness/faithfulness judge (D-50).

**Description:**
A Python project living in `eval/`, managed by `uv` with a committed lockfile (D-49), that drives
the gateway's `/rag/query` HTTP/SSE endpoint over a sampled MultiHop-RAG question set (~500
questions, committed fixed seed) and scores the responses. Metrics are split in two: a
**deterministic half** — retrieval recall@k, context precision, MRR/nDCG, answer EM/F1 — computed
from the benchmark's own gold labels with **no LLM and no API key at all**, and a **judged half** —
groundedness and faithfulness only — using a pinned judge model distinct from the generator at
temperature 0, with judgements cached by a `(question, answer, evidence)` hash (D-50, D-52, D-62).
Graph capability is measured by **ablation**: the same question set run with graph context on and
off via a per-request flag against one running engine, scored as its own dimension and kept
strictly distinct from the model-only opt-in (D-46, D-47). The eval store is fully isolated — its
own LanceDB path and its own PostgreSQL schema created by the existing Atlas migrations — seeded
once through the real ingestion path over a documented reduced document subset (D-55, D-56, D-57).
Output is a committed, dated Markdown report plus machine-readable JSON, **advisory only with no
pass/fail gate**, reported per corpus with full run metadata and no cross-corpus aggregate (D-54,
D-60, D-61). The audience is the project's own maintainers and readers of the README: "good" is a
number a reviewer can trace back to a specific commit SHA, judge model, sample size and index
generation, and recompute offline from the committed run journal.

**Critical Failure Modes:**

1. **A fabricated or silently-wrong number.** Any metric that reports a value it did not actually
   measure. Concretely: OBS-04's placeholder must return an explicit `skipped` status with a reason,
   never a simulated score (D-51); a failed, truncated or contract-violating SSE stream must surface
   as a typed error, never be scored as zero (D-65); a dimension that could not run must say so.
2. **Evidence-ID mismatch corrupting recall.** MultiHop-RAG labels evidence at source/article
   granularity while the response returns `chunk_id` + `document_id`. If the
   `document_id → corpus article ID` map is not captured at seed time and persisted with the corpus
   config, recall@k / context precision / MRR / nDCG are all quietly wrong while looking plausible.
   This is the single highest-risk defect in the phase.
3. **Non-reproducible results.** An unpinned model, an uncommitted lockfile, an unseeded or
   wrong-generation eval store, or a lost sampling seed makes a recorded run uninterpretable and
   breaks the D-61 trajectory claim.
4. **Eval/dev store contamination.** The eval store sharing a LanceDB path or PostgreSQL schema
   with the dev store — or one corpus contaminating the other — invalidates every number (D-56).
   The existing seeder is recorded as non-idempotent (DEBT-P3-WARN-DX).
5. **The deterministic half acquiring an LLM or API-key dependency.** D-50's guarantee is that the
   free, instant, reproducible half runs with no key. Any library or code path that breaks this
   collapses the phase's central design property.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** **Developer tooling / infrastructure.** Lancet has no end-user vertical —
no healthcare, legal or finance deployment exists to research. The domain that actually governs
this phase is **multi-hop QA benchmark evaluation and retrieval-augmented generation measurement
methodology**. Its "domain experts" are IR/RAG evaluation practitioners and benchmark authors, and
the question they ask is not "is the answer good?" but **"is this reported number trustworthy, and
does it mean what its name says it means?"**

**User Population:** The project's own maintainers, README readers and technical reviewers
assessing whether Lancet's RAG/GraphRAG claims are substantiated. Nobody consumes these numbers to
make a clinical, legal or financial decision. This is a portfolio/demonstration system, so a
number's **credibility and traceability matter more than its absolute magnitude** — a modest
recall@10 a reviewer can recompute from a committed journal is worth more than a high one they
cannot.

**Stakes Level:** **Medium** — argued, not defaulted. There is no patient, financial or safety
harm downstream; D-54 makes the report explicitly advisory with no pass/fail gate, so no CI job and
no release is blocked by it. The failure mode that actually bites is **credibility**: an evaluation
report is a claim about one's own work, and a wrong claim is worse than no claim. One sub-case is
genuinely **High** — a fabricated, mis-defined or unreproducible number that gets **cited in the
README** (D-66) and enters the committed trajectory (D-61). That is the specific outcome D-51,
D-54, D-60, D-61 and D-65 exist to prevent, and it is the sub-case the rubrics should weight.

**Output Consequence:** Numbers land as a dated, committed Markdown + JSON record stamped with
commit SHA, judge model, sample size, corpus and index generation (D-61), reported **per corpus
with no cross-corpus aggregate** (D-60). Old runs stay in the repo, so successive runs form a
visible trajectory a reader can diff. The README cites the latest (D-66). Nothing gates on them
(D-54) — their whole value is as evidence, which is exactly why a number that cannot be traced
back to what produced it has negative value.

**Refinement of Section 1's Critical Failure Mode #2 (evidence only — Section 1 not edited, no
decision re-opened):** the mismatch is sharper, and in one respect *better*, than "article
granularity vs `chunk_id`". The benchmark's own matching rule is *gold-fact-sentence containment in
retrieved chunk text*, and `gateway/main.go`'s `structuredCitationDTO` **does** carry text —
`excerpt` and `is_truncated`, alongside `chunk_id`, `document_id`, `title`, `section_path`, `score`,
`rank`, `content_type`. Since the 512-char excerpt cap exceeds the 500-char default chunk, the
excerpt *is* the chunk at default settings, so **the reference rule can be replicated exactly from
the response** — article-level matching is a choice, not a necessity, and it is the weaker choice.

The residual risk moves elsewhere: **gold facts straddling a chunk boundary.** Gold facts are
median 161 chars and p90 257 chars, while `defaultChunkOverlap` is **50** — far smaller than a
typical fact. A fact split across two 500-char chunks is therefore contained in *neither* chunk, and
containment matching records a miss on a retrieval that was in fact perfect. This is a systematic
downward bias on recall, not a random one. Three mitigations are available to the planner and one
should be chosen and documented: raise `chunk_overlap` for the eval corpus above the maximum gold
fact length (538 chars); relax matching to a normalised sub-span / longest-common-substring
threshold; or fall back to article-level matching with the comparability caveat below. D-44/D-50 say
nothing about chunking or the matching rule, so this is a planning input, not a conflict.

### What Domain Experts Evaluate Against

**Dimension: Evidence coverage on answerable questions**
- **Good:** Recall is computed only over the 2,255 answerable questions, with the denominator stated
  as *number of gold evidence items* (6,084) or *number of queries with ≥1 hit* — explicitly, one or
  the other. Reported at the benchmark's own cut-offs, K=4 and K=10, so it sits next to published
  baselines.
- **Bad:** The 301 `null_query` items are left in the retrieval denominator. They have empty
  `evidence_list`, so they can never be "hit"; including them silently deflates recall by up to
  ~11.8% and the deficit is invisible in the report.
- **Stakes:** Critical
- **Source:** MultiHop-RAG reference scorer `retrieval_evaluate.py` (commit `33d3ad0`) explicitly
  `continue`s on `question_type == 'null_query'`; counts verified against the dataset.

**Dimension: Evidence-match rule fidelity**
- **Good:** The report states the matching rule in one sentence, and it is one of: (a) **replicate the
  reference** — whitespace-normalised containment of the gold `fact` in the citation `excerpt`
  (which equals the full chunk at the default 500-char chunk / 512-char cap), with the
  chunk-boundary mitigation chosen above applied and named; or (b) **article-level** — map
  `document_id` (or citation `title`) to the article `url`, **labelled in the report as a strictly
  looser criterion whose numbers are not comparable to the published baselines.** Under (a), a
  citation arriving with `is_truncated == true` (only possible if chunk size is raised above 512) is
  recorded as *undecidable*, never silently as a miss.
- **Bad:** A number named `recall@k` whose matching rule is undocumented; or article-level matching
  reported as if it were the benchmark's metric. Article-level counts any chunk from a gold article
  as a hit even when that chunk contains none of the gold fact (inflation), and collapses the gold
  denominator for the 7.5% of queries drawing two or more facts from one article (further inflation).
  The opposite error deflates recall: running strict containment at `chunk_overlap = 50` against gold
  facts of median 161 / p90 257 chars, so every boundary-straddling fact scores as a miss on a
  perfect retrieval — and reporting the resulting number as the system's recall rather than as an
  artefact of the chunking parameters.
- **Stakes:** Critical — this is Section 1's highest-risk defect, made concrete.
- **Source:** `retrieval_evaluate.py` matching logic (commit `33d3ad0`); `gateway/main.go`
  `structuredCitationDTO` and `defaultChunkSize/Overlap = 500/50`;
  `engine/src/prompt.rs::bounded_unicode_excerpt` with `excerpt_max_chars = 512`; the 168/2,255 and
  fact-length figures measured from the dataset.

**Dimension: Ranking quality under multi-evidence questions**
- **Good:** Because **every** answerable question has 2–4 gold facts, a rank-aware metric that
  accounts for *all* of them is reported, not just the first hit — and its formula is stated.
  Two acceptable routes: (a) implement **the reference scorer's own metric**, which is what the
  published baselines used; or (b) implement textbook MAP@10 / nDCG@k — nDCG with the ideal-DCG
  denominator built from `min(|gold|, k)` gold items under binary gain — and state that these are
  **not** the benchmark's numbers. MRR@10 may appear **beside** either, never instead of it.
- **The trap, verified in code and by worked example:** the reference scorer's `MAP@10`
  **is not textbook MAP.** Standard AP accumulates *cumulative* relevant-found over rank; the
  reference accumulates only the count of gold facts **newly matched at that exact rank**, divided
  by that rank:

  ```python
  count = <# gold facts first matched at THIS retrieved item>   # normally 1
  precision_at_rank = count / rank
  ...
  map_at_10_list.append(average_precision_sum / min(len(gold), 10))
  ```

  It therefore reduces to **the mean, over all gold facts, of the reciprocal rank at which each fact
  first appears**, normalised by `min(|gold|, 10)` — conceptually "MRR averaged over every gold
  item", not MAP. Worked example, gold A at rank 1 and gold B at rank 3, `|gold| = 2`:
  reference = `(1/1 + 1/3)/2` = **0.667**; textbook AP = `(1/1 + 2/3)/2` = **0.833**. Both computed
  and confirmed against the fetched source. A planner who implements textbook MAP will report
  **systematically higher** numbers than the paper and have no visible reason why. (This also makes
  the reference metric the *right* companion to MRR@10 on this corpus, since it is precisely the
  all-gold-items generalisation of it.)
- **Bad:** MRR@10 reported alone as "ranking quality". MRR credits only the reciprocal rank of the
  *first* relevant chunk, so a system that finds 1 of 4 gold facts at rank 1 scores a perfect 1.0 —
  identical to one that finds all 4. On this corpus that describes 100% of scorable questions.
  Equally bad: a textbook MAP@10 published as "MAP@10, cf. MultiHop-RAG paper"; or an nDCG whose
  ideal DCG is normalised against the retrieved list rather than the gold set, which prevents nDCG
  from falling below its ceiling and drifts it toward 1.0.
- **Stakes:** High
- **Source:** Measured — 0 of 2,255 answerable queries have a single gold item.
  `retrieval_evaluate.py` at commit `33d3ad0`, read directly; the 0.667 vs 0.833 divergence computed
  from its logic.

**Dimension: Answer correctness under span normalisation**
- **Good:** EM/F1 uses a stated normalisation (D-50 specifies SQuAD v1.1: lowercase, strip
  punctuation and articles, collapse whitespace), and the report states plainly that these numbers
  are **not comparable to the MultiHop-RAG paper's reported accuracy**, because the reference scorer
  uses a far looser criterion. Gold answers are short spans — `"Yes"`, `"OpenAI"`,
  `"Sam Bankman-Fried"` — so a `The answer is …` preamble must be handled by extraction or F1, not
  left to sink EM.
- **Bad:** Quoting a Lancet EM/F1 next to a published MultiHop-RAG accuracy as though they were the
  same measurement. The reference `has_intersection` scores a prediction correct if it shares **any**
  whitespace-split lowercased token with the gold answer, which over-credits partial matches on
  multi-token gold answers. Verified instance using two strings that are *both* gold answers in this
  dataset: gold `"Sam Bankman-Fried"` → `{"sam", "bankman-fried"}`, prediction `"Sam Altman"` →
  `{"sam", "altman"}`; the intersection `{"sam"}` is non-empty, so **a wrong-person answer is scored
  correct**. SQuAD-normalised EM will be dramatically lower on identical output — that is the metric
  working, not a regression. Also bad: SQuAD normalisation being treated as sufficient — it does not
  resolve aliases, numeric formatting or date phrasings, which is a known ceiling on this metric.
- **Stakes:** High
- **Source:** `qa_evaluate.py` at commit `33d3ad0` (`has_intersection`, and a comment noting
  precision/recall/F1/accuracy collapse to one value); gold-answer strings sampled from the dataset;
  SQuAD v1.1 normalisation (Rajpurkar et al. 2016).

**Dimension: Abstention on unanswerable questions**
- **Good:** The 301 `null_query` items are scored by their **own** abstention criterion and reported
  as a separate line — did the system decline, and does the decline surface through the intended
  channel (a `NO_EVIDENCE`/degraded notice, or an explicit "insufficient information" answer)? A
  fabricated confident answer to a null query is the single behaviour this slice exists to catch.
  Because Lancet's degraded path emits a notice and can legitimately produce **zero** `final_answer`
  frames (Section 2), the abstention check must read the notice, not just the answer text.
- **Bad:** Running EM/F1 across a sample that includes null items. The gold answer is the literal
  string `"Insufficient information."` for all 301; a `NO_EVIDENCE` notice or a differently-worded
  refusal will never string-match it, so **correct abstention is scored as wrong** — the harness
  punishes precisely the behaviour it should reward, and a system that hallucinated a plausible
  entity might even score higher by accident. Equally bad: dropping null queries entirely, which
  discards the benchmark's only hallucination probe.
- **Stakes:** Critical — this is the direct benchmark analogue of D-51's "never a fabricated number",
  applied to the system under test rather than to the harness.
- **Source:** Measured — all 301 null items have `evidence_list == []` and answer
  `"Insufficient information."`; the benchmark's stated purpose for the null category is to test
  whether an LLM hallucinates when the retrieved set is irrelevant (Tang & Yang 2024).

**Dimension: Groundedness/faithfulness judging that a reader can discount correctly**
- **Good:** The judge is a **different model family from the generator** (D-62), pinned, at
  temperature 0, and the report carries judge model, prompt version, judged `n` and judge-error count
  next to the score. Before any judged number is published, a small hand-scored slice (~20 items) is
  compared against the judge so the report can state an observed agreement rather than implying the
  score is ground truth. Judged scores are presented as *advisory* (D-54) and never averaged with
  deterministic metrics into one headline figure.
- **Bad:** Judge and generator from the same family — self-recognition drives measurable
  self-preference, and MT-Bench measured self-enhancement of roughly +10% (GPT-4) to +25% (Claude-v1)
  win rate when a model judged its own output. Also bad: a judged mean published with no agreement
  check and no error count, so a reader cannot tell 4.1-over-100 from 4.1-over-94-with-6-failures; a
  small free-tier judge's scores presented with the same confidence as a deterministic metric; and
  pairwise/positional judging without order swapping (MT-Bench measured only 65% consistency under
  answer-order swap with the default prompt, rising to 77.5% with a few-shot judge).
- **Stakes:** High
- **Source:** Zheng et al. 2023 (MT-Bench / Chatbot Arena) — 65% position consistency, 8.7% vs 91.3%
  verbosity-attack failure, +10%/+25% self-enhancement, 85% GPT-4–human agreement vs 81% human–human;
  Panickssery et al. 2024 — self-recognition capability linearly predicts self-preference bias,
  argued causally. Both directly justify D-62's different-model rule.

**Dimension: Graph-ablation attribution validity**
- **Good:** Both arms are driven against **one running engine** over the **same question set**, at
  the **same index generation**, differing only in the per-request graph flag (D-46/D-47), and the
  report shows both arms' numbers with the delta rather than the delta alone. A near-zero or negative
  delta is reported as-is — the graph literature's own headline finding is that GraphRAG frequently
  underperforms vanilla RAG, so a null result is a legitimate result, not a bug to hide.
- **Bad:** Arms compared across separate runs, restarts, reseeds or different `index_generation`
  values, which confounds the graph flag with index drift; the graph flag conflated with the D-10/D-12
  model-only opt-in, which answers a different question ("without evidence" ≠ "without graph"); a
  delta computed from judged scores whose judge prompt version differs between arms; or an ablation
  delta reported without the sample size and per-arm error counts that make it interpretable.
- **Stakes:** High
- **Source:** D-46/D-47 (one engine, per-request flag, kept distinct from the model-only opt-in);
  GraphRAG-Bench / "When to use Graphs in RAG" (arXiv 2506.05690) — GraphRAG frequently underperforms
  vanilla RAG on real-world tasks, which is why an honest null delta must be publishable.

**Dimension: Run traceability and reporting hygiene**
- **Good:** Every reported number is traceable to the exact inputs that produced it — commit SHA,
  corpus and its document subset, sampling seed, sample size, index generation, and for judged
  dimensions the judge model **and prompt version** (D-60/D-61). Sample size appears next to the
  number, not in a footnote (D-53). Dimensions that could not run appear as `skipped`/`error` with a
  reason (D-51); a failed or truncated stream is a typed error, not a zero (D-65). Results are
  reported per corpus with no cross-corpus aggregate (D-60).
- **Bad:** A metric table with no run metadata; a judged score whose prompt version is unrecorded, so
  a later trajectory movement cannot be attributed to the system rather than to a prompt edit; sample
  size changing silently between runs so the D-61 trajectory compares incomparable points; a `0.0`
  standing in for "did not run"; or a single headline figure averaged across MultiHop-RAG and
  GraphRAG-Bench, whose label schemas measure different things.
- **Stakes:** Critical
- **Source:** D-51, D-53, D-54, D-60, D-61, D-65; standard IR reporting practice — a metric without
  its cut-off, denominator and judgment set is not interpretable.

### Known Failure Modes in This Domain

1. **Evidence-ID granularity mismatch producing plausible-but-wrong recall.** The benchmark labels
   evidence as a *fact sentence* attached to an article; the response returns `chunk_id`,
   `document_id`, `title` and a chunk `excerpt`. Article-level matching and fact-containment matching
   both yield numbers in a believable range and disagree by large margins — one biased up, one biased
   down. Nothing in the pipeline errors; the report is simply wrong. The two measured mechanisms are
   the 7.5% of queries drawing multiple facts from one article (article-level inflation) and
   `chunk_overlap = 50` being far below the median 161-char gold fact, so boundary-straddling facts
   are unmatchable by containment (fact-level deflation).
2. **Rewarding fabrication on unanswerable questions.** Scoring the 301 null queries with the same
   EM/F1 path as answerable ones inverts the incentive: a correct refusal never matches the literal
   gold string `"Insufficient information."`, while a confidently hallucinated answer can accidentally
   share a token with it. The benchmark's designated hallucination probe becomes a hallucination
   *reward*.
3. **Metric-name drift — reporting a quantity other than the one the name implies.** "Recall@10" that
   is actually a per-query hit rate; MRR standing in for multi-evidence ranking quality; nDCG
   normalised against the retrieved list instead of the gold set; EM/F1 quoted beside a published
   accuracy computed by token intersection. Each is individually defensible and collectively makes
   the report non-comparable to anything, including its own earlier runs.
4. **Judge self-preference and judge instability.** A judge from the generator's family inflates its
   own work by a measurable margin; a judge whose prompt changes between runs moves the trajectory
   for reasons unrelated to the system; a small free-tier judge's scores carry less signal than their
   decimal places imply. All three are invisible unless judge model, prompt version and an agreement
   check are recorded.
5. **Scoring an infrastructure failure as a quality result.** A 429, a dropped SSE stream, a
   contract-violating frame sequence or a judge that never returned valid JSON being folded in as
   `0.0`. This is the domain's most common silent corruption because it always moves the number in a
   direction that looks like a real regression, and D-51/D-65 exist specifically to forbid it.
6. **Silent sample-size and index-generation drift.** `--sample N` changing between runs, or the eval
   store having been reseeded at a different generation, makes two committed runs incomparable while
   both look like points on one trajectory. D-64's preflight (store seeded at the *expected* corpus
   generation) is the control.
7. **Corpus contamination and store cross-talk.** Eval and dev sharing a LanceDB path or PostgreSQL
   schema, one corpus's documents leaking into the other's retrieval pool, or a non-idempotent
   reseed leaving duplicates — all invalidate recall in a way no metric surfaces (D-56;
   DEBT-P3-WARN-DX). Distinct from, but often confused with, **training-data contamination**: the
   MultiHop-RAG corpus is real news from 2023 and is very likely inside the generation model's
   pretraining data, so answer-quality numbers partly measure recall-from-weights rather than
   retrieval. This is unfixable here and should be *disclosed*, which is one of the reasons D-46's
   graph ablation (holding the generator fixed) is a better capability signal than raw answer
   accuracy.
8. **Averaging across incompatible label schemas.** MultiHop-RAG (fact-sentence evidence, short-span
   answers) and GraphRAG-Bench (tiered tasks up to summarisation and creative generation) do not
   share a scale. A combined mean is a number with no referent — which is precisely why D-60 forbids
   the cross-corpus aggregate.

**No regulatory regime applies.** No personal data, no protected health or financial information, no
automated decision affecting a person. GDPR/HIPAA/FCA and the EU AI Act's high-risk categories are
all out of scope for an offline benchmark harness run by a maintainer against public news articles.

### Domain Expert Roles for Evaluation

This is a solo-maintainer project. There is no staffed eval team, and pretending otherwise would be
the same category of error as a fabricated metric. The honest framing is **three distinct
responsibilities worn by one person**, named so that each has an owner and a moment at which it must
be discharged.

| Role (responsibility, not headcount) | Responsibility in Eval |
|---|---|
| **Benchmark-label steward** | Owns the evidence-matching rule and the `document_id`/citation-`title` → article-`url` map captured at seed time and persisted with the corpus config. Decides and *documents* whether matching is fact-containment or article-level, and whether the resulting numbers are claimed comparable to published baselines. Owns the null-query exclusion from retrieval scoring and the reduced-subset selection record (D-55). |
| **Judge-prompt calibrator** | Before any judged number is published, hand-scores a ~20-item slice for groundedness/faithfulness and compares against the judge, recording the observed agreement in the report. Owns the judge prompt as a **versioned artifact** and re-runs the calibration slice whenever it changes. Confirms judge ≠ generator family (D-62). |
| **Run-record reviewer** | Before committing a run (D-61), checks: metadata complete (commit SHA, judge model + prompt version, sample size, corpus, index generation); every dimension `ok`/`skipped`/`error` with a reason; no dimension reporting a value it did not measure; no cross-corpus aggregate; sample size unchanged from the previous committed run, or the change called out. |
| **Reference-set spot-checker** *(periodic, low cost)* | Reads ~10 scored items end-to-end — question, retrieved citations, answer, gold facts, computed score — and confirms the score matches what a human sees. This is the only control that catches a matching-rule bug producing a plausible number, which is Critical Failure Mode #2. |

## 2. Framework Decision

**Selected Framework:** **No AI/RAG framework.** A standalone `uv`-managed Python project at
`eval/`: `httpx` + `httpx-sse` (contract-asserting SSE client), Pydantic v2 (config, results, run
metadata, JSON report schema), hand-rolled deterministic IR + EM/F1 metrics, and a thin raw-`httpx`
OpenRouter judge. Scaffolding: `typer` + `rich` (CLI/preflight), `jinja2` (report), `pytest` +
`pytest-httpx` (tests), `tenacity` (judge retries), `ruff`.

**Version:** Python `>=3.13,<3.14`; `httpx>=0.28` (verified 0.28.1), `httpx-sse>=0.4.3`,
`pydantic>=2.11`, `pydantic-settings>=2.7`, `typer>=0.15`, `rich>=13`, `jinja2>=3.1`,
`tenacity>=9.1`, `pytest>=8`, `pytest-httpx>=0.35`.
(`tenacity>=9.1` — **not** `>=9`: `tenacity.wait_exception`, the primitive that lets a retry honour
a `Retry-After` header, does not exist in 9.0.0. Verified directly. The resolver lands on 9.1.4;
there is no 9.1.0 on PyPI. Resolved versions from a real `uv` build on Windows 11 / CPython 3.13.3:
httpx 0.28.1, httpx-sse 0.4.3, pydantic 2.13.4, pydantic-settings 2.15.0, typer 0.27.1, rich 15.0.0,
jinja2 3.1.6, tenacity 9.1.4, pytest 9.1.1, pytest-httpx 0.36.2, ruff 0.16.3.)
`pyproject.toml` declares compatible **ranges**; the committed `eval/uv.lock` is the actual pin
(D-49). Dependencies are added with `uv add`, not transcribed by hand; `uv lock --check` verifies
the lock is current. Dev tooling lives in a PEP 735 `[dependency-groups]` block so the
no-API-key runtime path stays lean.

**Rationale:**
- **D-48 forecloses the RAG-framework question entirely.** The retrieval, graph and generation
  stack is already shipped in Rust and Go. The harness is an *external client* of `/rag/query`; a
  RAG framework here would build a second, different system and measure that instead.
- **D-50 is the discriminating constraint on the metrics layer.** The deterministic metrics must
  run with no LLM and no API key. Nearly every purpose-built eval framework assumes an LLM in the
  loop for its headline retrieval metrics, and their non-LLM variants score *string similarity*
  rather than MultiHop-RAG's gold evidence IDs — which is a different measurement, not a cheaper
  one. Recall@k / context precision / MRR / nDCG over gold evidence IDs is ~120 lines with zero
  runtime dependencies; EM/F1 follows SQuAD v1.1 normalization. Hand-rolling also keeps the lock
  lean and avoids native-toolchain risk on Windows (D-68 requires Windows native **and** Linux/WSL).
- **D-65 wants a thin client that asserts a sequence, not a framework.** `httpx-sse` supplies only
  frame parsing (and correctly handles BOM / multi-line `data:` edge cases); the load-bearing part
  — terminal event present, **at most one** `final_answer`, notices attached, `stream_error`
  raised as a typed failure rather than scored as zero — is Lancet-specific and hand-written.
  (Two contract facts verified against `gateway/main.go` and corrected here: the assertion is
  **at most one** `final_answer`, not exactly one — `queryRAG` can emit `workflow_completed` as the
  first frame carrying `notices` and no `final_response`, so a legitimately degraded answer has
  **zero** `final_answer` frames, and hard-asserting exactly-one would fire D-65 on precisely the
  responses D-51 wants classified as degraded. And `node_failed` is neither terminal nor fatal — it
  carries `retryable` and the workflow can still succeed — so blanket-raising on it would discard
  valid runs and bias every metric downward. See Section 3 for the tested implementation.)
- **D-52/D-62 want a pinned, cached, auditable judge**, not a provider abstraction. A raw `httpx`
  POST to OpenRouter's `/chat/completions` mirrors the engine's existing integration. The cache is
  a **plain-text `judge_cache.json`** keyed by SHA-256 of `(question, answer, evidence)` —
  deliberately not a binary store, because D-52's stated purpose is that the cache file makes the
  reported numbers auditable.
- **Pydantic v2 makes D-51 unrepresentable-if-wrong.** `DimensionResult.status:
  Literal["ok","skipped","error"]` with a required reason on non-`ok` means a fabricated number
  cannot typecheck. It also emits `report.schema.json` via `model_json_schema()` for D-54's
  machine-readable output, and models the corpus config D-59 requires.
- **Corpus config in TOML via stdlib `tomllib`** matches the repo's existing `config.toml`
  convention (Phase 2 D-26–D-30) and needs no dependency.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| **RAGAS 0.3.x + `arize-phoenix-evals`** (strongest alternative) | Puts an LLM in the loop for its headline context-precision/recall metrics; the non-LLM variants score string similarity, not gold evidence IDs — breaks D-50's "no LLM at all, no API key". Drags a `langchain-core` tree into a repo that deliberately has no Python manifest (D-49), and has churned its API across 0.1/0.2/0.3. |
| LlamaIndex / LangChain / Haystack / DSPy | Build a RAG system; the RAG system already exists in Rust + Go. Directly contradicts D-48. |
| DeepEval | Nearly every metric is LLM-backed; telemetry on by default. Fails D-50. |
| TruLens | Feedback functions require a provider — no free deterministic path. Fails D-50. |
| promptfoo | Node/TS. Violates D-48's Python decision and D-49's `uv` project. |
| `ranx` | numba JIT — native-toolchain and version-lag risk on Windows (D-68); JIT is pure overhead at ~500×8 scoring operations. |
| `pytrec_eval` / `ir_measures` | C++ build on Windows native / requires Java. Fails D-68. |
| HuggingFace `evaluate` | Drags `datasets` and a large transitive tree for EM/F1 that is ~30 lines. |
| `sseclient-py` | `requests`-based, known chunk-boundary bugs, unmaintained — the wrong foundation for D-65. |

**Vendor Lock-In Accepted:** **No — deliberately minimal.** Nothing in the metrics layer, the
report layer or the data model is tied to a vendor. The only external coupling is OpenRouter's
OpenAI-compatible `/chat/completions` for the judge, which is one function behind a pinned-model
config and already the engine's own provider (D-62). Models are pinned in config and reported in
every run's metadata; swapping a judge model is a config edit plus a cache invalidation, and
switching provider is one function. `uv` is a build-tool commitment, not a runtime one — the
project remains a standard PEP 621 `pyproject.toml`.

### Entry Point Pattern

The contract-asserting SSE consumer (D-65). **This exact code passes 8 `pytest-httpx` tests**
covering: happy path, terminal-only degraded response, `node_failed` followed by success,
duplicate `final_answer`, missing terminal event, `stream_error` frame, and a pre-stream
plain-text 400, and an exceeded per-question wall-clock deadline.

Grounded in `gateway/main.go`: event names come from `writeWorkflowEventSSE`
(`node_started`, `node_completed`, `node_failed`, `answer_chunk`, `final_answer`,
`workflow_completed`) plus `writeStreamErrorSSE` (`stream_error`); payload fields come from
`queryRAGResponseDTO` / `structuredCitationDTO` / `noticeDTO` / `retrievalSnapshotDTO`.

```python
# src/lancet_eval/client.py
from __future__ import annotations
import time
from typing import Literal

import httpx
from httpx_sse import SSEError, connect_sse
from pydantic import BaseModel, ConfigDict, Field


# ── wire models: extra="ignore" so a gateway ADDING a field never breaks a run.
#    (Removing/renaming one still fails loudly, which is the regression we want.)
class StructuredCitation(BaseModel):
    model_config = ConfigDict(extra="ignore")
    chunk_id: str
    document_id: str              # ← joins to the corpus article ID via the seed-time map
    title: str = ""
    excerpt: str = ""
    score: float = 0.0
    rank: int = 0                 # ← the ranked list MRR / nDCG / recall@k consume


class Notice(BaseModel):
    model_config = ConfigDict(extra="ignore")
    code: str
    message: str
    severity: int


class RetrievalSnapshot(BaseModel):
    model_config = ConfigDict(extra="ignore")
    index_generation: str         # ← D-64 preflight + D-60 run metadata
    embedding_model: str
    result_hash: str


class RagAnswer(BaseModel):
    """gateway `queryRAGResponseDTO`."""
    model_config = ConfigDict(extra="ignore")
    answer: str = ""
    citations: list[str] = Field(default_factory=list)
    session_id: str = ""
    answer_basis: int = 0
    structured_citations: list[StructuredCitation] = Field(default_factory=list)
    notices: list[Notice] = Field(default_factory=list)
    snapshot: RetrievalSnapshot | None = None


class NodeFailed(BaseModel):
    model_config = ConfigDict(extra="ignore")
    node_name: str
    error_kind: int
    error_message: str
    retryable: bool


class WorkflowCompleted(BaseModel):
    model_config = ConfigDict(extra="ignore")
    success: bool
    total_duration_ms: int = 0
    error_kind: int = 0
    error_message: str = ""
    final_response: RagAnswer | None = None      # present on the success path
    notices: list[Notice] = Field(default_factory=list)  # present when it is NOT


class StreamErrorFrame(BaseModel):
    model_config = ConfigDict(extra="ignore")
    code: str        # STREAM_EOF_WITHOUT_TERMINAL | GRPC_RECV_ERROR
    message: str


# ── typed failures. NONE of these is ever scored as zero (Critical Failure Mode #1).
class HarnessStreamError(Exception): ...
class PreStreamError(HarnessStreamError): ...      # non-SSE 4xx/5xx before streaming
class StreamAborted(HarnessStreamError): ...       # stream_error frame / no terminal
class ContractViolation(HarnessStreamError): ...   # D-65 sequence broken
class StreamDeadlineExceeded(HarnessStreamError): ...  # wall-clock budget for one question


class QueryOutcome(BaseModel):
    model_config = ConfigDict(extra="ignore")
    status: Literal["ok", "degraded"]
    answer: RagAnswer | None
    completion: WorkflowCompleted
    notices: list[Notice] = Field(default_factory=list)
    node_failures: list[NodeFailed] = Field(default_factory=list)
    session_id: str = ""
    correlation_id: str = ""
    duration_ms: int = 0


# httpx's 5s default applies to EVERY phase and is fatal for first-token latency on
# a multi-hop RAG query. `read` is per-chunk inactivity, NOT a total budget.
EVAL_TIMEOUT = httpx.Timeout(connect=10.0, read=300.0, write=30.0, pool=10.0)


def run_query(client: httpx.Client, *, query: str, session_id: str = "",
              deadline_s: float = 600.0) -> QueryOutcome:
    # `client` already carries base_url; the path is relative on purpose.
    started = time.monotonic()
    body: dict[str, object] = {"query": query, "session_id": session_id}
    # NOTE: the graph-ablation flag (D-47) goes here — but the gateway DTO uses
    # DisallowUnknownFields(), so sending it today is a hard 400. See Section 4 / D-74.

    try:
        with connect_sse(client, "POST", "/rag/query",
                         json=body, timeout=EVAL_TIMEOUT) as event_source:
            resp = event_source.response
            if resp.status_code != httpx.codes.OK:
                resp.read()                       # required: the body was not streamed yet
                raise PreStreamError(f"HTTP {resp.status_code}: {resp.text[:500]!r}")

            # Free trace correlation with the Phase 6 OTel work — persist in the journal.
            session     = resp.headers.get("X-Lancet-Session-ID", "")
            correlation = resp.headers.get("X-Lancet-Correlation-ID", "")

            final_answer_count = 0
            answer: RagAnswer | None = None
            completion: WorkflowCompleted | None = None
            node_failures: list[NodeFailed] = []

            for sse in event_source.iter_sse():
                # httpx's `read` timeout is per-chunk inactivity, so a gateway that
                # keeps trickling node_started frames never trips it. This is the
                # only total budget that exists. See pitfall 1.
                if time.monotonic() - started > deadline_s:
                    raise StreamDeadlineExceeded(f"exceeded {deadline_s}s")
                # Dispatch on the SSE `event:` NAME. The payloads carry no type tag,
                # so a Pydantic discriminated union has nothing to key on.
                match sse.event:
                    case "final_answer":
                        final_answer_count += 1
                        answer = RagAnswer.model_validate_json(sse.data)
                    case "workflow_completed":
                        completion = WorkflowCompleted.model_validate_json(sse.data)
                    case "node_failed":
                        # NOT terminal and NOT fatal — the workflow may still succeed.
                        # Recorded as a diagnostic; the verdict comes from the terminal event.
                        node_failures.append(NodeFailed.model_validate_json(sse.data))
                    case "stream_error":
                        f = StreamErrorFrame.model_validate_json(sse.data)
                        raise StreamAborted(f"{f.code}: {f.message}")
                    case "answer_chunk" | "node_started" | "node_completed":
                        pass          # UX-only. The scorer reads final_answer.answer,
                                      # never the concatenation of answer_chunk.chunk_text.
                    case other:
                        raise ContractViolation(f"unknown SSE event {other!r}")
    except SSEError as exc:
        # handlePreStreamError writes plain text with no SSE headers; httpx-sse's
        # _check_content_type() raises SSEError on the first iter_sse() call.
        raise PreStreamError(str(exc)) from exc

    # ── D-65 sequence assertions ────────────────────────────────────────────
    if completion is None:
        raise StreamAborted("stream ended without workflow_completed")
    if final_answer_count > 1:
        raise ContractViolation(f"{final_answer_count} final_answer frames, expected <= 1")
    if answer is None:
        # PRECEDENCE, stated deliberately: `final_answer` WINS. `workflow_completed`
        # .final_response is only consulted when no final_answer arrived. They come
        # from different proto fields and are not guaranteed byte-identical; picking
        # one and never mixing is what keeps EM/F1 deterministic.
        answer = completion.final_response
    if completion.success and answer is None:
        raise ContractViolation("workflow_completed.success with no answer payload")

    notices = answer.notices if answer is not None else completion.notices
    return QueryOutcome(
        status="ok" if completion.success else "degraded",
        answer=answer, completion=completion, notices=notices,
        node_failures=node_failures, session_id=session,
        correlation_id=correlation, duration_ms=completion.total_duration_ms,
    )
```

> **The assertion is "AT MOST ONE `final_answer`", not "exactly one".** Verified against
> `main.go`: `queryRAG` can receive `workflow_completed` as the **first frame**
> (`firstFrame.GetWorkflowCompleted() != nil`), and when it carries no `final_response` it carries
> `notices` instead. A legitimately degraded answer therefore has **zero** `final_answer` frames.
> Hard-asserting exactly-one would fire D-65 on exactly the responses D-51 wants classified as
> `degraded`. The invariant that actually holds: a terminal event is present, **at most one**
> `final_answer`, and `success == true` implies an answer payload reached the scorer from
> *either* `final_answer` *or* `workflow_completed.final_response`. Count the **event name** —
> the DTO itself can legitimately arrive twice.

### Common Pitfalls

1. **httpx's default timeout is 5 seconds on *every* phase — and there is no total-request
   timeout at all.** Official docs confirm: "raise a `TimeoutException` after 5 seconds of network
   inactivity", applied *per operation*, not as one budget for the whole response. Two consequences.
   (a) First-token latency on a multi-hop RAG query will blow 5s routinely, so you **must** pass
   `httpx.Timeout(connect=10.0, read=300.0, write=30.0, pool=10.0)`. (b) Because `read` is
   *inactivity between chunks*, a gateway that keeps trickling `node_started` frames can hang a
   worker **forever** — `read` never fires. The harness therefore needs its **own wall-clock
   deadline** per question (checked inside the `iter_sse` loop), and `timeout=None` is never
   acceptable. Set it on the `connect_sse` call, not only on the client, since the sane default
   for the judge's POST is much shorter.

2. **`locale.getpreferredencoding()` is not UTF-8 on Windows — measured `cp950` on this machine.**
   Every bare `open(p)` / `Path.read_text()` / `Path.write_text()` decodes with the ANSI codepage.
   MultiHop-RAG articles are full of curly quotes, em dashes and accented names, so the *same*
   corpus yields *different* EM/F1 on Windows than on Linux — silently, with no traceback. This is
   the concrete way D-68 ("verify on Windows native **and** Linux/WSL") gets violated. Mitigations,
   apply all three: pass `encoding="utf-8"` at **every** call site; add `newline="\n"` on writes so
   committed reports and JSONL don't churn to CRLF (verified: without it Python translates `\n` to
   `\r\n` on Windows); and enable ruff's `PLW1514` — **which needs `preview = true`**, verified:
   without it ruff prints `Selection 'PLW1514' has no effect because preview is not enabled`.
   Belt-and-braces: export `PYTHONUTF8=1` in the eval entry point (verified to flip
   `getpreferredencoding()` to `utf-8`).

3. **`uv run --project eval` executes with cwd = the *repo root*, not `eval/`** (verified:
   `os.getcwd()` printed the parent). Every relative path — `templates/report.md.j2`, `corpora/`,
   `runs/`, `judge_cache.json` — resolves against wherever the operator stood. Anchor packaged
   assets to the module (`Path(__file__).parent / "templates"` or `importlib.resources.files()`)
   and make every data path an explicit, config-driven, `.resolve()`d absolute path. A silently
   wrong `corpora/` root is a whole run scored against the wrong gold labels.

4. **`stream_error` and a pre-stream error are two different failure surfaces, and the HTTP status
   tells you nothing once streaming has started.** `handlePreStreamError` writes `400`/`502` with a
   **plain-text** body and no SSE headers, so `httpx-sse` raises `SSEError` from
   `_check_content_type()` on the first `iter_sse()` — an exception type that looks nothing like an
   HTTP error. In-stream failures arrive as **HTTP 200** plus a `stream_error` frame
   (`STREAM_EOF_WITHOUT_TERMINAL`, `GRPC_RECV_ERROR`) because the header was already flushed.
   Catch `SSEError` and check `response.status_code` *before* iterating; map both to typed
   exceptions. And do **not** call `resp.raise_for_status()` or touch `resp.text` on a streaming
   response without `resp.read()` first — httpx raises `ResponseNotRead`.

5. **`node_failed` is not terminal and is not a run failure.** It carries `retryable`, and the
   workflow can recover and still emit `workflow_completed{success: true}` (verified as a passing
   test case). Blanket-raising on `node_failed` throws away valid results and quietly biases every
   metric downward. Record `node_failed` frames into the journal as diagnostics; take the verdict
   from the terminal event's `success` field alone.

6. **The `/rag/query` DTO rejects unknown fields — the graph-ablation flag returns HTTP 400
   today.** `gateway/main.go:677` calls `dec.DisallowUnknownFields()` and `:687` re-decodes into
   `&struct{}{}` to reject trailing content. `ragQueryRequestBody` (`:662`) has only `query`, `session_id`
   and `filter`. Any harness code that "just adds" the D-47 flag fails hard and immediately. This
   is a genuine cross-phase precondition (D-74), not an assumption — D-64's preflight must probe
   the field and fail fast naming D-74, and the ablation arm cannot be exercised before it lands.

7. **Score `final_answer.answer`, never the concatenation of `answer_chunk.chunk_text`.** Both are
   emitted; they are produced by different code paths and are not guaranteed identical. Pick one,
   state it, and never mix — an EM/F1 delta caused by whitespace between chunks is
   indistinguishable from a real regression.

8. **`tomllib.load()` requires a *binary* file object** — `open(path, "rb")`, not `"r"`; text mode
   raises `TypeError: File must be opened in binary mode`. (`tomllib.loads()` does take a `str`,
   but reading that string still needs `encoding="utf-8"` — see pitfall 2.) `tomllib` is read-only:
   the harness reads corpus config from TOML and writes results as JSON/JSONL.

9. **Pydantic v2: `model_dump()` is not JSON.** It returns Python objects — `Path`, `datetime`,
   `float('nan')` — so `json.dumps(m.model_dump())` raises or writes invalid JSON. Use
   `model_dump_json()` for the journal and report, or `model_dump(mode="json")` when you need a
   dict. For the JSONL journal, `model_dump_json()` per line is both correct and fastest.

## 4. Implementation Guidance

**Model Configuration:**

The harness **reads** model pins; it never chooses one. All three D-62 roles are declared in the
corpus/run config, resolved once at startup, echoed by `preflight`, and copied verbatim into every
run's `metadata.json` and report header (D-60/D-61). A run whose pins cannot be resolved does not
start — a report that cannot name its models is uninterpretable.

| Role | Where it lives | Value | Params | Harness's job |
|---|---|---|---|---|
| **Generation** | the **engine's** config, not the harness's | `dots-studio/dots-3-note-preview:free` | engine-owned | **Read only.** Preflight *reports* what the engine says it is running; the harness must never override it, or it stops measuring the shipped system (D-48). |
| **Embedding** | engine config; also echoed on the wire | `nvidia/llama-nemotron-embed-vl-1b-v2:free` (per `scripts/phase02_live_evidence.py`) | engine-owned | Read from `snapshot.embedding_model` on a live response — free, authoritative, no config drift. |
| **Judge** | the **harness's** config | a pinned free model **≠ the generator** (D-62) | `temperature: 0`, `max_tokens: 400`, `seed` if the provider honours it | Owned by the harness. Enforce distinctness *in code*: if `judge_model == generation_model`, preflight fails. A judge grading its own generator's work is not a measurement. |

**Core Pattern — journal-first, score-offline:**

The single most important structural decision in the harness: **driving is not scoring**. `run`
produces a JSONL journal and nothing else; `score` reads the journal and produces numbers. This is
what actually delivers D-50's "deterministic metrics need no API key and no gateway" — re-scoring
a committed journal touches neither. At ~1000 free-tier requests, **partial failure is the expected
case, not the exception**, so `--resume` is a first-class feature, not a convenience.

```python
# src/lancet_eval/run.py  (structure; the SSE call is client.run_query from Section 3)
import json, random
from concurrent.futures import ThreadPoolExecutor
from pathlib import Path

def sample_questions(all_q: list[dict], n: int, seed: int) -> list[dict]:
    # The ~500-question corpus selection drawn from MultiHop-RAG's full set with the
    # committed fixed seed (D-53), and COMMITTED as questions.sample.jsonl. Distinct
    # from `score --sample N`, which sub-samples the *judged* slice from this same set
    # using the same function and the same seed.
    # Sort first: dict/JSON iteration order must never decide the sample, or "same
    # seed" stops meaning "same questions".
    rng = random.Random(seed)
    ordered = sorted(all_q, key=lambda q: q["question_id"])
    return sorted(rng.sample(ordered, min(n, len(ordered))), key=lambda q: q["question_id"])


def journal_key(corpus: str, question_id: str, graph_arm: str) -> str:
    return f"{corpus}\x1f{question_id}\x1f{graph_arm}"


def load_done(journal: Path) -> set[str]:
    """--resume: everything already durably recorded is skipped. Tolerates a
    half-written last line from a killed process."""
    done: set[str] = set()
    if not journal.exists():
        return done
    with journal.open("r", encoding="utf-8") as fh:
        for line in fh:
            try:
                r = json.loads(line)
            except json.JSONDecodeError:
                continue                      # truncated tail — will be re-driven
            done.add(journal_key(r["corpus"], r["question_id"], r["graph_arm"]))
    return done


def drive(cfg, questions, journal: Path) -> None:
    done = load_done(journal)
    # Both ablation arms against ONE running engine, interleaved, no restart (D-47).
    units = [(q, arm) for q in questions for arm in ("on", "off")
             if journal_key(cfg.corpus, q["question_id"], arm) not in done]

    limits = httpx.Limits(max_connections=cfg.max_workers,          # SSE holds a
                          max_keepalive_connections=cfg.max_workers)  # conn per query
    with journal.open("a", encoding="utf-8", newline="\n") as fh, \
         httpx.Client(base_url=cfg.gateway_url, limits=limits) as http, \
         ThreadPoolExecutor(max_workers=cfg.max_workers) as pool:   # DEFAULT 1 — see 4b
        futures = [pool.submit(drive_one, http, cfg, q, arm) for q, arm in units]
        # as_completed + submit (NOT pool.map): with map, one escaping exception
        # re-raises at consumption time, aborts the loop, and DISCARDS every
        # already-completed-but-unwritten result. Against a 1,000 req/day cap that
        # is unrecoverable quota. Nothing may be lost that was already paid for.
        for fut in as_completed(futures):
            record = fut.result()          # drive_one never raises — see below
            # Append + flush per record. A killed run loses at most one question.
            fh.write(record.model_dump_json() + "\n")
            fh.flush()


def drive_one(http, cfg, q, arm) -> RunRecord:
    """MUST NOT RAISE. A work unit that escapes takes its siblings' unwritten
    results with it. Every failure becomes a durable `outcome="error"` record."""
    try:
        out = run_query(http, query=q["question"])   # graph arm flag: blocked on D-74
        return RunRecord(corpus=cfg.corpus, question_id=q["question_id"], graph_arm=arm,
                         outcome="ok", answer=out.answer, notices=out.notices,
                         node_failures=out.node_failures, duration_ms=out.duration_ms,
                         session_id=out.session_id, correlation_id=out.correlation_id,
                         index_generation=(out.answer.snapshot.index_generation
                                           if out.answer and out.answer.snapshot else None))
    except Exception as exc:
        # Deliberately broad. HarnessStreamError is NOT enough: httpx.ReadTimeout is a
        # TransportError, and a malformed frame raises pydantic.ValidationError —
        # both are expected events against a rate-limited free-tier gateway, and
        # neither is in the HarnessStreamError hierarchy.
        # NEVER scored as zero (Critical Failure Mode #1): recorded as an error with
        # its type and message; the dimension reports status='error' with an n.
        return RunRecord(corpus=cfg.corpus, question_id=q["question_id"], graph_arm=arm,
                         outcome="error", error_type=type(exc).__name__, error=str(exc))
```

(`from concurrent.futures import ThreadPoolExecutor, as_completed`.) The **only** thing allowed to
propagate out of `drive()` is a deliberate operator abort (`KeyboardInterrupt`), and even then the
journal is already flushed up to the last completed unit.

The CLI is five typer sub-commands with a strict dependency order:

| Command | Needs gateway? | Needs API key? | Writes |
|---|---|---|---|
| `preflight` | yes | only if `--judged` | nothing |
| `seed` / `reseed` | yes | no (engine uses its own) | eval store, `document_map.json`, corpus generation |
| `run --corpus X [--resume] [--limit N]` | **yes** | no | `runs/<date>-<corpus>/journal.jsonl` |
| `score --run <dir> [--sample N] [--no-judge]` | **no** | only for the judged half | `report.json`, `judge_cache.json` |
| `report --run <dir>` | no | no | `report.md`, `report.schema.json` |

> **`--sample N` lives on `score`, not on `run` — this is D-53, read precisely.** D-53 says the
> sample is a smaller **judged** slice while *"deterministic metrics always run over the full set
> (they are free)"*. If `--sample` reduced the drive, the journal would hold only N questions and
> the deterministic half **could not** cover 500 — which is exactly the
> `sample_size_deterministic` / `sample_size_judged` split `CorpusReport` already models. So:
> `run` always drives the full committed set × both arms; `score --sample N` selects which
> journal records get sent to the judge, **deterministically, by the same committed seed**, so
> re-scoring judges the same N and the judge cache hits instead of thrashing.
> `run --limit N` exists only as a smoke-test knob, and a journal produced with it must be
> stamped `partial: true` and is **not publishable** — the report generator should refuse it.

`score --no-judge` on a committed journal is the D-50 guarantee made executable: it runs offline,
in seconds, on a laptop with no key and no services, and any reviewer can reproduce the
deterministic half of a published number from what is in the repo.

**Tool Use:**

- **`POST /rag/query` (HTTP + SSE) is the sole integration surface.** No gRPC, no direct LanceDB
  or PostgreSQL reads for scoring — the harness measures the whole stack as a user experiences it
  (D-48), and reading the store directly would measure a different system. Everything the
  deterministic half needs is already on the wire (verified at `gateway/main.go:895-936`):
  `structured_citations[].chunk_id` / `.document_id` / `.score` / `.rank` for recall@k, context
  precision, MRR and nDCG; `answer` for EM/F1; `snapshot.index_generation` and `.result_hash` for
  run metadata and the D-64 generation check; `notices[]` for degraded-path accounting.
- **Graph ablation (D-46/D-47) is a per-request field that does not exist yet.** Blocked on D-74.
  Until it lands, `run` must refuse `--arm on` with a message naming D-74 rather than silently
  driving both arms against identical behaviour and reporting a spurious ~0 ablation delta — which
  is precisely a fabricated number (Critical Failure Mode #1).
- **Seeding goes through the real ingestion path** — `POST /documents` upload → chunk → embed →
  graph extract (D-56). Not a fixture loader, not a direct vector insert: the eval must exercise
  the chunker and the entity extractor, since those are what MultiHop-RAG's full-article corpus was
  chosen to stress (D-44).
- **Schema creation is one Atlas invocation against a different schema** (D-57) — identical DDL,
  no second definition to drift. Practically: point the eval `search_path`/schema at
  `lancet_eval` and run the existing migration command; `reseed` drops the schema and the eval
  LanceDB directory, then replays.
- **OpenRouter `/api/v1/chat/completions`** — one raw `httpx` POST for the judge only, behind the
  `tenacity` retry from Section 3. `Authorization: Bearer $OPENROUTER_API_KEY`, read from the
  environment via `pydantic-settings`, **never** written to the journal, cache, report or logs.

**State Management:**

Five pieces of state, in order of how badly they hurt when wrong:

1. **`document_map.json` — `document_id` → corpus article ID, captured AT SEED TIME.** This is
   Critical Failure Mode #2 and it is load-bearing. MultiHop-RAG labels evidence at
   source/article granularity; the wire returns `chunk_id` + `document_id`. Without the map,
   recall@k / context precision / MRR / nDCG are *quietly wrong while looking plausible* — the
   worst possible failure. Rules: (a) the seeder emits the map as it uploads, from the upload
   response, and it is **committed with the corpus config**; (b) the map records the
   `index_generation` it was built at; (c) `score` **fails loudly** on any `document_id` in a
   response that is absent from the map — an unmapped ID must never be silently treated as a miss,
   because "not in the gold set" and "not in my map" are different facts; (d) a round-trip
   assertion in `tests/` proves map ∘ response reproduces a known article ID.
2. **The isolated eval store** (D-56): its own LanceDB directory and its own PostgreSQL schema,
   both distinct from dev. `preflight` asserts the configured paths differ from the dev config and
   refuses to run otherwise — DEBT-P3-WARN-DX records the existing seeder as non-idempotent, so a
   partial re-seed into a shared store is unrecoverable and silently corrupting.
3. **Corpus generation tracking** (D-64): the corpus config records the expected
   `index_generation`; `preflight` issues one throwaway query and compares
   `snapshot.index_generation`. Mismatch → fail fast with "reseed required", not 40 minutes in.
   Every journal record also stamps the generation it observed, so a mid-run reseed is detectable
   after the fact rather than producing a silently mixed run.
4. **The run journal** (`journal.jsonl`) — append-only, flushed per record, keyed
   `(corpus, question_id, graph_arm)`. It is the durable record of paid-for work and the input to
   all scoring. Never rewritten in place; `--resume` reads it, `score` reads it, a reviewer reads it.
5. **`judge_cache.json`** — plain-text, `sha256`-keyed, sorted-key pretty-printed JSON (D-52).
   Auditability is the stated point: a reviewer opens the file and sees the exact verdicts behind
   the reported groundedness number. Written atomically (temp file + `os.replace`) so a killed
   process cannot truncate it.

**D-58 (checkpoints):** checkpoints stay **enabled** during eval runs so that path is exercised
under load — a ~500-question run writes roughly 2,500 checkpoint rows carrying full accumulated
snapshots (Phase 05 D-28). They are not scored and not read by the harness; they are dropped with
the schema on reseed, which is exactly why the isolated schema is what makes this affordable.
Phase 05 D-24's no-TTL decision for the real system is untouched.

**Context Window Strategy:**

For this harness "context window" means one thing only: **the judge prompt**. Nothing else the
harness does involves a model. Four rules, in priority order:

1. **Bound the evidence, deterministically.** Take `structured_citations` in the ranked order the
   gateway returned, truncate each `excerpt` to a fixed character budget, and accumulate to a fixed
   total budget (`PER_PASSAGE_CHAR_BUDGET = 1_500`, `EVIDENCE_CHAR_BUDGET = 12_000` — roughly 3k
   tokens, comfortable for any free-tier context and cheap to re-run). Fixed order + fixed cuts =
   byte-identical evidence for identical inputs. Verified by test: two calls produce the same
   string and therefore the same cache key.
2. **Never truncate silently.** Overflow appends an explicit
   `[TRUNCATED: N further passages omitted]` marker. The judge is told it may be seeing a subset,
   and the marker is *inside* the hashed evidence, so a budget change invalidates cleanly.
3. **Hash the post-truncation evidence, plus `judge_prompt_version` and `judge_model`.** Hashing
   the pre-truncation evidence would let a budget change reuse verdicts computed on different
   input — a stale-cache bug that looks like a metric drift. See 4b.
4. **`max_tokens: 400` on the judge, always set.** The verdict is a small JSON object; an unbounded
   completion on a free-tier model is a rate-limit and latency liability with no upside, and a
   rambling model that runs to the context edge produces truncated JSON that fails validation and
   burns a re-ask.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.

### Structured Outputs with Pydantic

Two distinct jobs, and conflating them is a mistake: **(a)** making a fabricated number
unrepresentable in the harness's own output, and **(b)** getting trustworthy JSON back out of a
free-tier judge that may not honour `response_format` at all.

**(a) `DimensionResult` — D-51 enforced by the type system.** Every dimension, including OBS-04's
placeholder, returns this. The cross-field validator makes "a score without a measurement" and
"a skip without a reason" **fail at construction**, so the failure surfaces in a unit test rather
than in a published report. **Verified: all four negative cases below were executed and rejected.**

```python
# src/lancet_eval/dimensions.py
from typing import Annotated, Literal, Self
from pydantic import BaseModel, ConfigDict, Field, model_validator


class DimensionResult(BaseModel):
    model_config = ConfigDict(extra="forbid")

    name: str
    status: Literal["ok", "skipped", "error"]
    score: float | None = None
    detail: dict[str, float] = Field(default_factory=dict)
    reason: str | None = None
    n: int = 0

    @model_validator(mode="after")
    def _no_fabricated_numbers(self) -> Self:
        if self.status == "ok":
            if self.score is None:
                raise ValueError(f"dimension {self.name!r}: status 'ok' requires a score")
        else:
            if self.score is not None or self.detail:
                raise ValueError(
                    f"dimension {self.name!r}: status {self.status!r} must not carry a score")
            if not (self.reason or "").strip():
                raise ValueError(
                    f"dimension {self.name!r}: status {self.status!r} requires a reason")
        return self


# D-51's OBS-04 placeholder. Same interface as every other dimension.
# A `0.0` here would be a fabricated number; the model makes it impossible.
OBS_04_PLACEHOLDER = DimensionResult(
    name="community_summary_quality",
    status="skipped",
    reason="requires community summaries, Phase 999.1",
)
```

Verified rejections (`ValidationError` raised, message quoted):

| Attempted | Rejected with |
|---|---|
| `status="skipped", score=0.0, reason="r"` | `dimension 'x': status 'skipped' must not carry a score` |
| `status="skipped"` (no reason) | `dimension 'x': status 'skipped' requires a reason` |
| `status="ok"` (no score) | `dimension 'x': status 'ok' requires a score` |
| `status="error", reason="  "` | `dimension 'x': status 'error' requires a reason` |

**D-54's committed schema** falls straight out (verified — 3,085 bytes of JSON Schema, `$defs`
containing `DimensionResult`):

```python
Path("report.schema.json").write_text(
    json.dumps(CorpusReport.model_json_schema(), indent=2) + "\n",
    encoding="utf-8", newline="\n")      # encoding+newline: see Section 3 pitfall 2
```

Commit `report.schema.json` and add a test asserting it is byte-identical to a freshly generated
one — the schema then becomes a reviewable diff whenever the report shape changes.

**(b) The judge envelope + bounded re-ask.** There is **no framework** here — no `instructor`, no
`.with_structured_output()`, no `openai` SDK. Just `Model.model_validate_json()` on the completion
text, and a re-ask that feeds the validation errors back.

```python
# src/lancet_eval/judge.py
Score5 = Annotated[int, Field(ge=1, le=5)]

class JudgeVerdict(BaseModel):
    model_config = ConfigDict(extra="ignore")
    groundedness: Score5
    faithfulness: Score5
    unsupported_claims: list[str] = Field(default_factory=list, max_length=10)
    rationale: str = Field(max_length=600)


def judge_once(client, *, model, question, answer, evidence, max_reasks: int = 1):
    """Returns JudgeVerdict | None. None becomes DimensionResult(status='error'),
    NEVER a 0 — a judge that failed to answer is not a judge that scored zero."""
    messages = [
        {"role": "system", "content": JUDGE_SYSTEM},
        {"role": "user",
         "content": f"QUESTION:\n{question}\n\nANSWER:\n{answer}\n\nEVIDENCE:\n{evidence}"},
    ]
    for attempt in range(max_reasks + 1):
        raw = _post(client, {                       # _post carries the tenacity retry
            "model": model, "messages": messages,
            "temperature": 0, "max_tokens": 400,
            # Best-effort ONLY. Phase 05's WARN-NEW-01 exists precisely because free-tier
            # models' structured-output support is unverified. json_object (not json_schema)
            # is the weaker, more widely honoured request; the Pydantic validation below
            # is the actual guarantee.
            "response_format": {"type": "json_object"},
        })["choices"][0]["message"]["content"]
        try:
            return JudgeVerdict.model_validate_json(_strip_fences(raw))
        except ValidationError as exc:
            if attempt == max_reasks:
                return None                         # give up → status='error' + reason
            messages += [
                {"role": "assistant", "content": raw},
                {"role": "user", "content":
                    "That did not validate against the required schema:\n"
                    f"{exc.errors(include_url=False)}\n"
                    "Reply with ONLY the corrected JSON object."},
            ]
    return None
```

`_strip_fences()` is not optional — free-tier chat models routinely wrap JSON in a ```` ```json ````
fence even when asked not to, which `model_validate_json` rejects outright.

**Retry policy — two independent layers, do not confuse them:**

| Layer | Trigger | Budget | Logged | Surfaced as |
|---|---|---|---|---|
| **Transport** (`tenacity`) | HTTP 429 / `httpx.TransportError` | 5 attempts, `wait_exception` honouring `Retry-After` + `wait_random(0, 2)` jitter, `reraise=True` | attempt no., status, `Retry-After`, `X-RateLimit-Remaining` | exception → `status="error"` |
| **Semantic** (re-ask) | `ValidationError` on the completion | **1 re-ask, then stop** | question id, raw completion (truncated), the `exc.errors()` list | `None` → `DimensionResult(status="error", reason="judge did not return valid JSON after 1 re-ask")` |

One re-ask, not three: a free-tier model that fails the schema twice at `temperature=0` will fail
it a third time — the completion is deterministic — and each attempt burns scarce daily quota.
Record the count of judge failures in the report next to the judged `n`, so a reader can see
*"groundedness 4.1 over 94 of 100 judged; 6 judge errors"* rather than a silently shrunken sample.
**Cache the failures too**, keyed identically, so a re-run does not re-burn quota on the same
hopeless items.

### Async-First Design

**Decision: synchronous `httpx` plus a bounded `ThreadPoolExecutor`, `max_workers` a config knob
defaulting to `1`.** No `asyncio`, no `aiohttp`, no `aconnect_sse`.

The justification is a ceiling, not a preference. OpenRouter's documented free-tier limit is
**20 requests/minute**, enforced **server-side, per account**. Client concurrency cannot move a
server-side ceiling — 8 async workers and 1 sync worker complete 1000 requests in the same ~50
minutes, except the async version also collects 429s. What async *would* buy is real cost:
`async` colouring through every call site, a concurrent journal writer, and interleaved failure
handling — against a benefit of zero. `max_workers` stays a knob because a future paid tier, or a
locally hosted model, would change the ceiling; `1` stays the default because it makes the journal
strictly ordered and a failing run trivially reproducible.

**The one mistake to avoid here is not `asyncio.run()` inside a running loop** — there is no loop.
It is **sharing one `httpx.Client` across threads without bounding the connection pool.** `httpx.Client`
*is* thread-safe and should be shared (one client, one pool, connection reuse), but its default pool
allows 100 connections; with SSE, every in-flight query holds a connection open for its entire
lifetime. Bound it explicitly and make the bound match the worker count:

```python
limits = httpx.Limits(max_connections=cfg.max_workers,
                      max_keepalive_connections=cfg.max_workers)
with httpx.Client(base_url=cfg.gateway_url, limits=limits, timeout=EVAL_TIMEOUT) as http:
    ...
```

The second mistake: **the journal writer must not be concurrent.** `ThreadPoolExecutor.map`
yields results in the main thread — write there, and no lock is needed. Interleaved
`fh.write()` from workers can tear a line and corrupt `--resume`.

**Stream vs. await, for this harness:**

- **Streaming is mandatory, not a UX choice.** `/rag/query` is SSE-only; there is no
  request/response form of it. `connect_sse` must stay a context manager for the whole iteration —
  touching `.text` or `.json()` on a streaming response raises `httpx.ResponseNotRead`, and
  `resp.read()` on a live SSE stream buys you a hang, not a body.
- **But the harness consumes the stream synchronously to completion before scoring.** It is not a
  UI; there is no value in partial answers. Frames are drained, the D-65 contract is asserted, one
  `QueryOutcome` is produced, one journal line is written. Streaming is how the wire works;
  the harness's unit of work is the completed response.
- **The judge is a plain non-streaming POST.** Structured output must be validated as a whole
  document; streaming a JSON object you are about to parse in one shot is pure complexity.

### Prompt Engineering Discipline

The harness owns exactly **one** prompt — the judge's. That makes discipline cheap and its absence
inexcusable.

**System vs. user separation.** The *system* message carries the invariant contract: the role
("grade this answer against the evidence given, and nothing else"), the explicit prohibition on
outside knowledge (a judge that "knows" the answer stops measuring groundedness and starts
measuring agreement), the 1–5 scale definitions, and the output shape. The *user* message carries
only the three per-item variables — `QUESTION`, `ANSWER`, `EVIDENCE` — under fixed, uppercase,
unambiguous delimiters. Nothing per-item ever leaks into the system message; that is what keeps
the prompt a constant and the cache meaningful.

**Evidence is untrusted input.** It is corpus text the harness did not write, being fed to a model.
Delimit it explicitly, label it as data to be graded, and never interpolate it into the system
message. A MultiHop-RAG article containing text that reads like an instruction must not become one.

**Versioning is not optional, and the version belongs in the cache key.**
`judge_prompt_version = "v1"` is bumped on **any** edit — wording, scale, ordering, whitespace.
It is recorded in run metadata *and* hashed into the cache key. Recording it only in metadata is
the trap: an edited prompt would silently reuse verdicts produced by the old one, which is exactly
the corruption the versioning exists to prevent. Two runs with different `judge_prompt_version`
values are **not comparable** and the report must say so.

**No few-shot examples in v1.** Reasons, in order: every example is tokens spent on all ~200–1000
judge calls against a hard daily quota; hand-picked examples anchor the judge toward the picker's
priors, and D-45 already defers human-reviewed items; and with no calibration set (D-45), there is
no way to demonstrate the examples *help* rather than merely change the numbers. If judge variance
proves unacceptable, add few-shot as an explicit `judge_prompt_version = "v2"` with both runs
committed side by side — that is a measurement, not a tweak.

**Token budget, explicit at both ends.** Input: `EVIDENCE_CHAR_BUDGET = 12_000` (~3k tokens) plus a
short question and answer. Output: `max_tokens = 400`, always set — never unbounded. `temperature = 0`
with `unsupported_claims` capped at 10 and `rationale` at 600 characters keeps the completion
small, the latency low, and the verdict reproducible.

### Context Window Management

RAG-evaluation-specific, and narrower than it sounds: the only context window in play is the
judge's. See Section 4's Context Window Strategy for the mechanism; the discipline that matters:

- **Truncate in ranked order, never re-rank.** The harness must not reorder
  `structured_citations` — the rank *is* part of what is being measured. Truncation drops from the
  tail (lowest rank) so the judge sees what the system considered most relevant. Re-ranking inside
  the harness would make groundedness measure the harness's reranker, not the system's retriever.
- **Cap per passage before capping in total.** One pathologically long article would otherwise
  evict every other passage and make the judge's view unrepresentative of what the system retrieved.
- **Overflow is marked, not silent** — `[TRUNCATED: N further passages omitted]` inside the hashed
  evidence.
- **The cache key survives a budget change, correctly.** Hash the **post-truncation** evidence
  string together with `judge_prompt_version` and `judge_model`. Changing
  `EVIDENCE_CHAR_BUDGET` therefore changes the evidence, changes the key, and produces a clean
  miss — new verdicts, no stale reuse. Hashing the pre-truncation evidence would silently serve
  verdicts computed on different input, which reads as unexplained metric drift.
- **Truncation must be deterministic across platforms.** Character counts on `str` (not bytes),
  no locale-dependent collation, no `set`/`dict` iteration in the ordering. Verified by test:
  two calls on identical input produce identical strings and identical keys.
- **If evidence is empty, do not call the judge at all.** A degraded response with no citations
  yields `DimensionResult(status="skipped", reason="no evidence returned; groundedness undefined")` —
  a 1/5 there would be a fabricated number about a question that was never asked.

### Cost and Latency Budget

**Monetary cost: $0.** All three roles are `:free` models (D-62). Deliberate — the design property
being protected is reproducibility, not spend. The real currency is **quota**.

**The quota arithmetic, and it changes the plan.** Fetched from OpenRouter's limits page on
2026-08-19:

| Limit | Value |
|---|---|
| Free-model requests/minute | **20 RPM** |
| Free-model requests/day, **< $10 lifetime credit purchased** | **50 RPD** |
| Free-model requests/day, **≥ $10 lifetime credit purchased** | **1,000 RPD** |
| 429 response headers | `Retry-After`, `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` |

Against that, a full run:

| Stage | Free-tier calls | Wall-clock floor at 20 RPM |
|---|---|---|
| Drive: 500 questions × 2 ablation arms | **~1,000** generation calls, made by the **engine** on its **own** key | **~50 min** |
| Judge: 500 × 2 arms, if fully judged | **~1,000** judge calls | **~50 min** |
| Deterministic scoring from the journal | **0** | seconds, offline |

**The binding constraint is requests/day, not requests/minute.** A full 500×2 drive consumes the
*entire* 1,000 RPD allowance in one sitting — leaving nothing for the judge — and on an account
that has never purchased credit the cap is **50 RPD**, which makes a full run a *twenty-day*
proposition. Three planner-level consequences:

1. **`score --sample N` (D-53) is structural, not a convenience.** Deterministic metrics run over
   the full journal because they are free; the **judged** slice is a seeded sub-sample, its size
   printed prominently in the report. A realistic v1: full 500×2 deterministic, ~100 judged.
   Note this is a knob on `score`, never on `run` — see the CLI table in Section 4.
2. **The journal + `--resume` are how a run survives the daily cap.** A run that stops at the
   ceiling resumes the next day without re-paying for completed work. Design for this; do not treat
   it as an error path.
3. **Budget the drive and the judge separately, and consider separate keys.** If the engine and the
   judge share one OpenRouter account, they share one daily cap and the judge starves. Preflight
   should report remaining quota (`X-RateLimit-Remaining`) and warn when the planned run exceeds it —
   before 40 minutes are spent.

**Precision on D-50, which is worth stating exactly.** "No LLM, no API key" is a guarantee about
**scoring**, not about **driving**. Producing the journal requires the gateway *and* the engine's
own generation calls against the same free-tier quota. What D-50 actually buys — and it is a lot —
is that **`score --no-judge` on a committed journal needs no key, no network and no services**, so
any reader can recompute the deterministic half of a published number from the repo alone. Write
it that way in the docs; "the deterministic metrics are free" is true of re-scoring and misleading
about the run.

**Caching:**

- **Exact-match only, and that is the right call.** `sha256(judge_prompt_version, judge_model,
  question, answer, post-truncation evidence)` → verdict, in a plain-text `judge_cache.json`
  (D-52). Semantic/embedding caching is explicitly rejected: it would need an embedding model
  (burning the quota it was meant to save), and a near-miss returning a *different question's*
  verdict is a fabricated number by another name.
- **What re-runs actually cost.** Re-scoring after a metrics bug fix: **free** (journal + cache,
  offline). Re-running after an engine change: the drive re-pays, and the judge cache misses on
  every question whose *answer* changed — which is correct, and is the signal. Re-running after a
  judge prompt edit: full judge cost, by design.
- **Auditability is the point** (D-52): sorted keys, `indent=2`, `ensure_ascii=False`, UTF-8,
  `newline="\n"`, atomic replace. A reviewer opens the file and reads the verdicts behind the
  number. Store the plaintext `question`/`answer`/`evidence` alongside the hash for exactly that
  reason — never the API key.

**Cheaper models for sub-tasks: not applicable, and deliberately so.** Everything except
groundedness and faithfulness is deterministic Python — recall@k, context precision, MRR, nDCG and
EM/F1 need no model at all (D-50). There is no classification, routing or summarisation step to
downgrade. The judge is already the smallest model that can do the job, pinned, and pinned
*distinct* from the generator (D-62) — a constraint that overrides any cost consideration.

## 5. Evaluation Strategy

> **Two things are being measured, and they must not be confused.** Dimensions **1–8** measure
> **the shipped Lancet RAG/GraphRAG stack** — that is the evaluation. Dimensions **9–11** and all of
> Section 6 are **the harness measuring itself and its inputs** — whether a published number is
> entitled to be believed (9 = the wire contract the harness depends on; 10 = a dimension declaring
> it did not run; 11 = the provenance of every number). Section 1b's framing governs: the question
> is not "is the answer good?" but *"is this reported number trustworthy, and does it mean what its
> name says it means?"*
>
> **Every number in this section is advisory (D-54).** No threshold anywhere gates a build, a
> release or a commit. Where a bound is stated it is *informational* — a value a reader should
> notice, never a value that fails something.

### Dimensions

Priorities mirror Section 1b's own stakes labels rather than inventing a second scale.

|-----------|--------------------------|---------------------|----------|

#### Normative note — the matching rule (applies to dimensions 1, 2 and 3)

Dimensions 1–3 are meaningless until the evidence-match rule is fixed and **stated in the report in
one sentence**. Section 1b establishes that the reference rule is *whitespace-normalised containment
of the gold `fact` inside the retrieved chunk's text*, and that Lancet **can replicate it exactly
from the SSE response** — `structuredCitationDTO.excerpt` is capped at 512 characters against a
500-character default chunk, so the excerpt **is** the chunk and no store lookup is needed.

- **Preferred: fact-containment**, replicating the reference. The **chunk-boundary mitigation must
  be chosen and named in the report** — `defaultChunkOverlap = 50` is far below the median 161-char
  (p90 257, max 538) gold fact, so a fact straddling a boundary is contained in *neither* chunk and
  containment records a miss on a retrieval that was in fact perfect. This is a **systematic
  downward bias**, not noise. The three available mitigations (raise the eval corpus's
  `chunk_overlap` above 538; relax matching to a normalised sub-span / longest-common-substring
  threshold; fall back to article-level) are a planning input — one must be picked, applied and
  written into the report.
- **Fallback: article-level** via the seed-time `document_id → article url` map, **labelled in the
  report as a strictly looser criterion whose numbers are not comparable to published baselines** —
  it counts any chunk from a gold article as a hit even when that chunk contains none of the gold
  fact, and it collapses the gold denominator for the **168 / 2,255 (7.5%)** of queries drawing two
  or more facts from one article. Both errors inflate.
- A citation arriving with `is_truncated == true` (only possible if chunk size is raised above 512)
  is recorded as **undecidable**, never silently as a miss.
- **Never report a deflated recall as if it were clean.** If the chosen mitigation leaves residual
  boundary loss, the report says so next to the number.

#### Normative note — ranking-metric convention (applies to dimension 3)

The MultiHop-RAG reference scorer's `MAP@10` **is not textbook MAP**. It accrues
`count_of_gold_facts_newly_matched_at_this_rank / rank`, which reduces to the mean reciprocal
*first-appearance* rank across gold facts, normalised by `min(|gold|, 10)`. Worked example, gold A
at rank 1 and gold B at rank 3: reference = `(1/1 + 1/3)/2` = **0.667**; textbook AP =
`(1/1 + 2/3)/2` = **0.833**. A textbook implementation therefore reports **systematically higher**
numbers than the paper with no visible reason why.

**Lancet reports `ndcg@k` (gold-set ideal DCG) and `mrr@10`, per D-50, and states that neither is
the paper's `MAP@10`.** *Optional, additive, ~5 lines:* the reference-convention number may also be
computed and published under the explicit label `reference_convention_map@10 (comparability with
Tang & Yang 2024)` — it is the only path to a directly comparable retrieval figure, and it is the
natural all-gold-items companion to MRR@10 on this corpus. It is **additive**: it never substitutes
for D-50's named metric list.

#### Judge rubric (dimensions 6 and 7) — the actual text the judge is scored against

The judge sees **only** `QUESTION`, `ANSWER` and the bounded `EVIDENCE` (per-passage 1,500 chars,
total 12,000 chars, ranked order preserved, overflow marked `[TRUNCATED: N further passages
omitted]` *inside* the hashed evidence). It **never sees the gold answer** — a judge that "knows"
the answer stops measuring groundedness and starts measuring agreement. Evidence is untrusted corpus
text: it is delimited and labelled as data to be graded, never interpolated into the system message.

**Groundedness — is every claim traceable to the evidence supplied?**

| Score | Anchor |
|---|---|
| **5** | Every factual claim in the answer is directly supported by a specific supplied excerpt. Nothing requires the reader to take the model's word for it. |
| **3** | The core claim is supported, but at least one supporting or connective detail (a date, a name, a causal link) appears in the answer without any excerpt backing it. |
| **1** | Central claims have no support anywhere in the supplied evidence — the answer would read the same if the evidence had been blank. |

**Faithfulness — does the answer distort, contradict or go beyond the evidence?**

| Score | Anchor |
|---|---|
| **5** | No claim contradicts or overstates any excerpt; no outside knowledge is injected; hedges and qualifiers in the evidence survive into the answer. |
| **3** | The answer is broadly consistent with the evidence but overstates certainty, drops a qualifier, or generalises past what the excerpts actually say. |
| **1** | The answer states something the evidence contradicts, or answers from the model's own priors while citing evidence that does not say it. |

**Judging discipline (all of it load-bearing, all of it from Section 1b / 4b):** judge pinned and
**≠ the generator's family** — preflight fails in code if `judge_model == generation_model`;
`temperature = 0`, `max_tokens = 400`; verdicts cached by
`sha256(judge_prompt_version, judge_model, question, answer, post-truncation evidence)` in a
plain-text auditable `judge_cache.json` (D-52); one bounded re-ask on a `ValidationError`, then
`status="error"` — **never a score**; **if evidence is empty, the judge is not called at all**
(`status="skipped", reason="no evidence returned; groundedness undefined"` — a 1/5 there would be a
fabricated number about a question that was never asked); no few-shot in `v1`, and any prompt edit
is a `judge_prompt_version` bump that lands in the cache key, making two differently-versioned runs
**explicitly not comparable**.

**On D-45 and the calibration slice — a scope clarification the planner must not get wrong.**
D-45 defers **LLM-generated supplementary Q/A items** (and the D-17 evidence-vs-priors metric with
them). It does **not** forbid hand-scoring ~20 *existing benchmark items* to measure judge
agreement. Section 4b's "with no calibration set (D-45)" refers to the absence of a *generated*
set; the ~20-item human calibration slice is in scope, is cheap, and is the only thing that lets
the report state an observed agreement rather than implying the judge is ground truth.

|---|---|---|---|
| Drive: 500 questions × 2 ablation arms | **~1,000** generation calls | the **engine's** | ~50 min |

## 6. Guardrails

> **Scope statement, and it changes the shape of this section.** The artifact Phase 6.3 builds is an
> **offline advisory harness**, not a production request path. It has no users, serves no traffic and
> makes no decision on anyone's behalf. Inventing online guardrails for it would be the same category
> of error as a fabricated metric. What genuinely applies here is a different thing wearing the same
> name: **the integrity checks that stop a wrong number from being published.**
>
> **The distinction that keeps this section compatible with D-54:** D-54 forbids gating on
> **scores** — no metric value fails a build, blocks a release or blocks a commit. It does **not**
> forbid refusing to publish a run whose **provenance** is invalid. Corpus-generation mismatch, an
> unmapped `document_id`, a changed judge-cache key, sample-size drift, a `partial: true` journal —
> these are provenance checks, not quality thresholds. Nothing below reads a metric value and
> decides whether it is good enough.

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| **None — N/A by design.** | — | — |

**Reasoned N/A, not an omission.** Three independent reasons:

1. **There is no online.** The harness runs as a maintainer-invoked CLI over a committed question
   set. `run` is a batch drive; `score` and `report` run offline from a committed journal with no
   network at all. There is no request path on which a real-time check could sit.
2. **Every guardrail-shaped concern here is already a hard failure, not a filter.** D-64's preflight
   *fails fast before the run starts* (gateway reachable, engine reachable, eval store seeded at the
   expected `index_generation`, API key present when judged dimensions are requested, judge ≠
   generator, eval store paths ≠ dev store paths). D-65's contract assertions raise typed exceptions
   mid-stream. Pydantic's `DimensionResult` validator rejects a fabricated number *at construction*.
   These are preconditions and type invariants — stronger than a guardrail, and they belong to the
   mechanisms already specified in Sections 3, 4 and 4b.
3. **The real online guardrails belong to the system under test, and this phase measures them
   rather than adding them.** Lancet's own request-path protections — `NO_EVIDENCE` and degraded
   notices, citation repair/drop, graph-unavailable notices, generation retry — ship in Phase 6.
   Dimension 5 (abstention) and dimension 9 (wire-contract conformance) are how Phase 6.3 checks
   they work. Adding a second, harness-side copy would measure the harness instead of the system,
   which is exactly what D-48 forbids.

### Offline (Flywheel)

Every row is a **publication precondition or a quality signal about the measurement**, never a
threshold on a measured value. "Action on Degradation" means *what stops a wrong number reaching the
committed record*, and each row traces to a Section 1 Critical Failure Mode (CFM) or a Section 1b
known failure mode (KFM).

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| **Corpus-generation match** — configured expected `index_generation` vs. `snapshot.index_generation` (CFM #3, KFM #6) | `preflight` issues one throwaway query before the run; **every journal record additionally stamps the generation it observed**, so a mid-run reseed is detectable after the fact | Preflight **fails fast with "reseed required"** rather than 40 minutes in. A journal containing mixed generations is **refused for publication** — the run is not a point on D-61's trajectory. |
| **`document_id → article ID` map coverage** — every `document_id` in every scored response resolves in the seed-time map (CFM #2 — *the single highest-risk defect in the phase*; KFM #1) | Every scored record, every run — 100%, not sampled | `score` **fails loudly** on any unmapped `document_id`. An unmapped ID is **never** silently treated as a miss: "not in the gold set" and "not in my map" are different facts and conflating them is how recall goes quietly wrong while looking plausible. A `tests/` round-trip assertion proves map ∘ response reproduces a known article ID. |
| **Judge-cache key integrity** — the cache key hashes `judge_prompt_version`, `judge_model` and the **post-truncation** evidence (KFM #4) | Every judge call | A prompt edit, a model change or an `EVIDENCE_CHAR_BUDGET` change produces a **clean cache miss and fresh verdicts**, never stale reuse. Two runs with different `judge_prompt_version` are marked **not comparable** in the report. Judge failures are cached too, keyed identically, so a re-run does not re-burn scarce quota on hopeless items. |
| **Sample-size drift between committed runs** — `sample_size_deterministic` and `sample_size_judged` vs. the previous committed run (KFM #6) | Every run-record commit, by the *run-record reviewer* | The report **must call out the change explicitly**; an uncalled-out change makes two committed runs incomparable while both look like points on one trajectory. Sizes print **next to the numbers**, never in a footnote. |
| **Contract-violation and infrastructure-error counts** — `ContractViolation` / `StreamAborted` / `PreStreamError` / `StreamDeadlineExceeded` / transport / `ValidationError`, counted by type (CFM #1; KFM #5) | Every driven record; counts surfaced per dimension alongside `n` | **Surfaced, never absorbed.** A 429, a dropped stream or a malformed frame becomes a durable `outcome="error"` record and a `status="error"` dimension with a reason — **never `0.0`**. This is the domain's most common silent corruption precisely because it always moves the number in a direction that looks like a real regression. |
| **Judge-error count and judge–human agreement** — errors beside judged `n`; agreement from the ~20-item hand-scored slice (KFM #4) | Before **any** judged number is published; re-scored on every `judge_prompt_version` bump | If agreement is not measured, judged numbers are **withheld or published explicitly as uncalibrated**. The report reads *"groundedness 4.1 over 94 of 100 judged; 6 judge errors"*, never a silently shrunken sample. |
| **Null-slice integrity** — the 301 `null_query` items are excluded from every retrieval denominator and scored only by dimension 5 (KFM #2) | Asserted by unit test on the golden vectors **and** re-asserted per run from the sample composition | A retrieval denominator that includes null items is a **build-time test failure**, not a runtime surprise. Without this the harness rewards fabrication on exactly the benchmark's hallucination probe. |
| **`partial: true` journal detection** — any journal produced with `run --limit N` | Every report render | The report generator **refuses to publish**. A smoke-test journal is not a recorded run. |
| **Reference-set spot-check** — ~10 scored items read end-to-end: question → returned citations → answer → gold facts → computed score (CFM #2) | Per recorded run, **weighted** toward records carrying notices, `node_failures`, `outcome="error"`, zero citations, judge errors, and EM=0-with-high-F1 | A human/score mismatch **blocks publication** and triggers a matching-rule fix. This is the **only** control that catches a matching-rule bug producing a plausible number. |
| **Cross-corpus aggregate absence** (D-60; KFM #8) | Every report render | The report model has **no field** for a combined figure. MultiHop-RAG and GraphRAG-Bench do not share a scale; a combined mean is a number with no referent. |
| **Store-isolation assertion** (D-56; KFM #7) | `preflight`, every invocation | Refuses to run if the configured eval LanceDB path or PostgreSQL schema matches the dev config. DEBT-P3-WARN-DX records the seeder as non-idempotent, so a partial re-seed into a shared store is unrecoverable and silently corrupting. |

**Two things this section deliberately does not do.** It does not set a floor on recall, EM, F1,
nDCG or any judged score — that would be the threshold gate D-54 removed. And it does not alert:
there is no on-call and nowhere to route a page (D-40; `06-CONTEXT.md` `<domain>` out-of-scope names
"alerting rules"). The flywheel here feeds a **human reviewer before a commit**, which is the only
consumer that exists.

## 7. Production Monitoring

> **Honest framing first.** There is no production deployment of Lancet and no production traffic to
> monitor. What "production monitoring" means for Phase 6.3 is two concrete things: **(a)** the
> telemetry Lancet emits about *itself*, which Phase 6.2 lands and this phase consumes rather than
> replaces, and **(b)** the one thing 6.3 genuinely adds — **correlating an eval question to the
> trace and the index state that produced its number**, so a metric in a committed report can be
> opened up and looked at rather than merely believed.

**Tracing Tool: the Phase 6.2 OpenTelemetry stack. Arize Phoenix is explicitly overridden.**

Detection was run before defaulting. **No eval or tracing SDK exists in the project tree** — the
only `langfuse|langsmith|arize|phoenix|braintrust|promptfoo|ragas` matches in the repo are GSD
agent-definition files under `.claude/worktrees/`, not project code. What *does* exist is the
telemetry stack, and it wins:

| Layer | What ships | Decision |
|---|---|---|
| Instrumentation | OTel across **Go and Rust** — `tracing` + `tracing-opentelemetry` and the OTel Meter API in the engine; `otelhttp` + `otelgrpc` + `otelzap` in the gateway | D-36, D-37 |
| Transport | Both services export **OTLP → OpenTelemetry Collector** | D-34 |
| Backends | **Jaeger** (traces) + **Prometheus** (metrics) + **Loki** (logs), correlated in **Grafana** by `trace_id` | D-34 |
| Already running | **Jaeger 2.19.0** in `docker-compose.yml` with OTLP receivers bound on **`127.0.0.1:4317` (gRPC)** and **`4318` (HTTP)** | verified in-repo |
| Compose shape | `core` profile (PostgreSQL only) / `observability` profile (Collector, Jaeger, Prometheus, Loki, Grafana); pipelines, scrape config, datasources and dashboards **committed and auto-provisioned, no manual UI state**, dashboards generated from typed code | D-39, D-40 |
| Ordering | D-75 fixes the sequence **module graph → wire contract → behavior → telemetry → eval → docs**, so **6.2 lands before 6.3** and this stack is a dependency, not a proposal | D-75 |

**Arize Phoenix: considered and unnecessary.** Two reasons, either sufficient. It would be a
**second tracing backend for a system already exporting OTLP** to a Collector that already fans out
to Jaeger — duplicated infrastructure with no signal Jaeger does not carry. And Phoenix instruments
the *Python* process, whereas this harness's only LLM call is the judge; the interesting spans —
retrieval fusion, graph traversal, each LLM attempt, the whole SSE stream — are emitted by the Rust
engine and the Go gateway, which Phoenix does not see. Adding `arize-phoenix` would also add a
`phoenix` + `opentelemetry-sdk` dependency tree to a lockfile Section 2 deliberately keeps lean.
**No new dependency is introduced by this section.**

**Key Metrics to Track**

*From Phase 6.2, observed during an eval run — read, not defined here (D-35):*

1. **Query latency histogram by outcome** — an eval run is the only sustained load this system sees;
   the p50/p95 under a 500-question drive is the phase's one realistic latency signal.
2. **Retrieval-path failure counter** (dense / BM25 / graph, by kind) — distinguishes a low recall
   caused by *ranking* from one caused by a retrieval path being *down*, which no metric in
   Section 5 can tell apart on its own.
3. **Degraded-answer counter by `answer_basis`** — the operational twin of dimension 5. On the 301
   null queries a *rising* degraded count is the system working correctly.
4. **Corpus generation gauge and index-rebuild duration** — the telemetry-side view of the same
   `index_generation` the harness stamps on every journal record.
5. **Generation retry counter** — free-tier 429 pressure, visible while the drive is running rather
   than inferred afterwards from a truncated journal.

*Added by Phase 6.3, per run record (harness-side, no new backend):*

6. `correlation_id`, `session_id`, `index_generation`, `result_hash`, `duration_ms`, `outcome`,
   `error_type`, notice codes and `node_failures` — recorded on **every** journal line.

**The correlation mechanism, stated precisely so the planner does not assume a link the wire does
not carry.** The gateway sets exactly two response headers — `X-Lancet-Session-ID` and
`X-Lancet-Correlation-ID` (`gateway/main.go:725-728`, `:786-789`). **There is no trace-ID response
header.** Per D-27 the **OTel trace ID is authoritative and `correlation_id` is retained as a span
attribute** for continuity. So the honest join is:

> harness reads `X-Lancet-Correlation-ID` off the streaming response (before iterating frames, inside
> the `connect_sse` context) → persists it on the journal record → a reviewer searches **Jaeger on
> that span attribute** to land on the ~8–10 spans for that exact question.

That is a free, real capability and it is worth building deliberately: **any number in a committed
report can be walked back to the trace of the query that produced it.** Alongside it,
`snapshot.index_generation` + `snapshot.result_hash` on each record tie the number to a **specific
index state** — the difference between "recall moved" and "the index moved underneath the run".
D-43's `service.version` (git SHA) closes the loop from a trace back to the exact build.

**Alert Thresholds: N/A — no alerting, by decision, on both sides.**

- **D-40, verbatim:** *"**No alert rules and no recording rules** — there is no on-call and nowhere
  to route them."* That governs the Phase 6.2 metrics backend.
- `06-CONTEXT.md` `<domain>` **Out of scope** names *"threshold-gated eval, alerting rules, CI"*
  explicitly.
- **D-54** removes the only thing 6.3 could have alerted on: the report is advisory, so no metric
  value is an alarm condition.

The substitutes, and they are the right ones for a solo-maintainer project: **D-64's preflight**
(fails *before* the run, with guidance, rather than paging after it), **Section 6's publication
preconditions** (a wrong number never reaches the record), and **D-38's silent degradation to
stdout** (a missing collector never fails a service). If any bound is written into the report at
all, it is labelled **informational** — a value a reader should notice, never a value that fails
something.

**Smart Sampling Strategy** — which journal records get human eyes, given that ~1,000 records is far
past what anyone reads. Two consumers, both from Section 1b's expert-role table, both signal-weighted
rather than random:

| Consumer | Volume | Signal-based selection |
|---|---|---|
| **Reference-set spot-checker** (per run) | ~10 records read end-to-end: question → returned citations → answer → gold facts → computed score | Weighted toward: records carrying **notices** (any `NO_EVIDENCE` / degraded / citation-repair code); records with **`node_failures`**; `outcome="error"`; **zero citations returned**; **`EM = 0` with high `F1`** (the alias / numeric-formatting / date-phrasing ceiling Section 1b names — the highest-yield place to find a *scoring* bug rather than a system bug); and records where the **two ablation arms disagree most**. Plus 2–3 uniformly-random records so the weighting cannot hide a systematic problem in the boring majority. |
| **Judge-prompt calibrator** (before any judged number publishes; re-run on every `judge_prompt_version` bump) | ~20 records hand-scored for groundedness and faithfulness | Stratified across query type (comparison / inference / temporal), deliberately including **judge-error items** and **low-evidence** records, since those are where a small free-tier judge is least reliable. Observed agreement is printed in the report. |

**Signal–metric divergence — the one thing worth watching across committed runs.** D-61 makes
successive runs a visible trajectory in the repo. The early-warning pattern to look for is a
deterministic metric moving while the *signals* do not — recall shifting with no change in
`index_generation`, no change in retrieval-path failures and no change in sample size means the
**measurement** moved, not the system. Section 1b's failure modes #1 (matching-rule granularity),
#3 (metric-name drift) and #6 (sample-size / generation drift) all present exactly that way, and the
run metadata stamped on every record is what makes the divergence visible instead of invisible.
