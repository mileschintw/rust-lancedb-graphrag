<objective>
Add the retrieval result set to the wire. Today `/rag/query` exposes `structured_citations` — the subset of evidence the generator chose to cite — and nothing else that identifies what retrieval actually returned. Every "retrieval recall@k / context precision / MRR / nDCG" number Phase 6.3 publishes would therefore measure generator citation behaviour, not retrieval. This plan adds an additive `retrieved_chunks` field to `RetrievalSnapshot`, populates it at the one seam where the true ranked retrieval result set still exists, and threads it through the gateway's SSE DTO so the Python harness can consume it.

Purpose: ROADMAP SC3 requires deterministic retrieval metrics computed "over the full set with no LLM", and D-50 promises the deterministic half is free of any LLM dependency. Neither is achievable while the only retrieval-shaped field on the wire is downstream of a generation call. This is the structural fix; renaming the metrics to `cited_evidence_recall_at_k` was the alternative and was rejected because it narrows what the phase can claim.
Output: proto field 12 on `RetrievalSnapshot`, its population in `RetrieveHybridNode`, its excerpt budget wired from the same config value the citation path uses, the gateway DTO field, and wire-compatibility plus population tests on both sides with both test-count invariant gates raised.

**Plan number 08, wave 1.** This plan is numbered after the existing six but executes *first*: 06.3-01's Python wire models mirror the gateway DTO field-for-field and 06.3-03's metric module computes over `retrieved_chunks`, so both must see the field already landed. The number is sequential-by-authoring-order; the `wave` field is what execution reads. Nothing was renumbered, so every existing `depends_on`, SUMMARY reference and back-reference in this phase stays valid.
</objective>

## Reversibility

<reversibility rating="costly">
Adding proto field number 12 to `RetrievalSnapshot` spends that number permanently — protobuf field numbers are never recycled, so this cannot be undone, only superseded. That is the costly half. It is **not** a one-way door, and no `checkpoint:decision` gates it, for three reasons verified against the repository:

1. **There is no external consumer.** Both generated surfaces live in this repo (`engine/src/pb/lancet/v1/lancet.v1.rs` via the neoeinstein-prost plugin, `gateway/proto/lancet/v1/lancet.pb.go` via protocolbuffers/go, both emitted by one `buf generate` from `buf.gen.yaml`). Engine and gateway ship together from one commit; there is no independently-versioned client whose deploy could skew.
2. **The change is purely additive and proto3-compatible in both directions.** An old peer skips tag 12 as an unknown field; a new peer decoding an old message gets an empty vector. The existing `retrieval_snapshot_variant_provenance_wire_contract` test already encodes exactly this discipline for tags 10 and 11, and this plan extends it rather than replacing it.
3. **The behaviour is trivially retractable.** Stopping population is a one-line change in `retrieve.rs`; consumers then see an empty array, which the harness already has to handle as "retrieval returned nothing".

The direction that *would* be one-way — renaming or renumbering an existing field, or reusing a number below 12 — is forbidden outright by this plan's prohibitions. Given the reviewer separately flagged this phase for human-gate density (five blocking gates already), adding a sixth for a retractable additive field would cost more than it protects.
</reversibility>
