<objective>
Give the evaluation its own store and its own front door: an isolated PostgreSQL schema created by the existing Atlas migrations, an isolated LanceDB directory, a seeder that uploads the reduced document subset through the real ingestion path, and a preflight that fails fast with guidance instead of forty minutes into a run.

Purpose: eval/dev store contamination invalidates every number and no metric surfaces it (AI-SPEC Critical Failure Mode #4), and the existing seeder is on record as non-idempotent (DEBT-P3-WARN-DX), so a partial reseed into a shared store is unrecoverable. The `document_id` → article map captured at seed time is the single highest-risk artifact in the phase: without it, recall is quietly wrong while looking plausible.
Output: an Atlas eval environment, `config/config.eval.toml`, `seed` / `reseed` / `preflight` commands, and the committed `document_map.json`.
</objective>

## Atlas branch: single point of failure (replan pass, REVIEWS.md MEDIUM-5 / Cursor HIGH)

Both reviewers independently flagged this as the weakest joint in the phase, and the planner re-verified the mechanics: `gateway/atlas.hcl` declares exactly one `env "local"` whose `src` is `file://db/schema.hcl`, and `gateway/db/schema.hcl` opens with `schema "public"` as a **literal label** with every table hanging off `schema.public`. Atlas resolves the source's target schema from that label, so Branch 1 (appending `search_path=lancet_eval` to the URL) is unlikely to work and Branch 2 requires parameterising a block referenced dozens of times. Branch 3 is the probable outcome and was the least-specified of the three.

**Why this matters beyond one task:** plans 06.3-05, 06.3-06 and 06.3-07 all block on this plan, so an unresolved probe stalls four plans and every one of the phase's live human gates sits downstream of it. The reviewer's suggestion was to run Probe A out of band before planning. That is not available to the planner — the probe needs a live PostgreSQL and the `atlas` CLI, neither of which exists at planning time, and guessing the outcome is exactly what the probe-before-asserting design forbids.

**What this replan does instead**, in three parts: (1) Branch 3 is now fully specified, including its concrete regeneration command, so the probable outcome is no longer the least-prepared one; (2) the branch choice is promoted to an explicit `checkpoint:decision` (Task 0 below) so it is resolved deliberately at the top of the wave rather than discovered mid-task; (3) `user_setup` now names the Atlas CLI install as a precondition, so a missing tool surfaces before the wave starts rather than at the probe.
