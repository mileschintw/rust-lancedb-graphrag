## Ruling: what the retrieval metrics are computed over (replan pass, REVIEWS.md HIGH-1)

**The retrieval dimensions are computed over `snapshot.retrieved_chunks`, never over `structured_citations`.** This reverses what the original plan specified and it is the single most consequential change in this replan.

The reviewers traced, and this planner re-verified against the code, that `ctx.structured_citations` is assigned in `engine/src/workflow/nodes/generate.rs` from `resolve_citations_with_max_chars(&ctx.citations, &ctx.evidence_blocks, ...)`, where `ctx.citations` is the post-repair set of markers *the model emitted*; `engine/src/prompt.rs` emits a `StructuredCitation` only for an evidence block whose id matches one of those markers. So `structured_citations` is the cited subset, and before this replan the HTTP surface exposed no retrieved-chunk list at all. Every number the original plan would have published as `evidence_recall_at_4`, `context_precision_at_k`, `mrr_at_10` or `ndcg_at_k` would have measured *generator citation behaviour conditioned on retrieval*, downstream of a generation call — which also made D-50's "no LLM" guarantee and ROADMAP SC3's "with no LLM" requirement unsatisfiable as written.

Plan **06.3-08** fixes the surface: `RetrievalSnapshot` gains `retrieved_chunks`, populated in `engine/src/workflow/nodes/retrieve.rs` from the post-fusion, post-rerank, `final_limit`-truncated result set, before `AssemblePromptNode` narrows `ctx.evidence_blocks` to the prompt's token budget and independently of anything the generator does. This plan consumes that field. The entries have the same nine-field shape as `structured_citations`, so no metric implementation changes shape — only its input list does.

**Consequences, all binding:**

- Every retrieval-named dimension reads `outcome.snapshot.retrieved_chunks`. A retrieval-named number computed from `structured_citations` is forbidden by this plan's prohibitions and asserted against by test.
- `snapshot` absent and `retrieved_chunks` empty are different facts. Absent means the retrieval node never ran: every retrieval dimension is `skipped` with a reason. Present-but-empty means retrieval ran and returned nothing: an honest measured zero that stays in the denominator. `retrieve.rs` assigns `ctx.snapshot` before its zero-evidence notice branch, which is what makes the distinction observable.
- A response with zero `structured_citations` no longer forces recall to zero. That was the shape `allow_model_only` produces by design, and scoring it as a retrieval failure was the concrete defect the review named.
- **Citation-conditioned variants are an explicit non-goal.** No `cited_evidence_recall_at_k` companion dimension is built. Publishing both doubles the metric table and invites the reader to compare two numbers whose difference is a generator property this phase does not set out to measure. Decided, not forgotten. If a later phase wants it, the wire already carries both lists.
- **Judged** dimensions still key off `structured_citations`: groundedness and faithfulness ask whether the answer is supported by the evidence the model actually cited, so the cited subset is the correct input there. The split is deliberate — retrieval metrics over retrieval, grounding metrics over citations.

## Ruling: gold facts longer than a chunk (replan pass, REVIEWS.md Cursor HIGH)

This is a **separate defect from HIGH-1 and is not fixed by the wire change.** AI-SPEC §1b records a maximum gold-fact length of 538 characters; the gateway's `defaultChunkSize` is 500 characters and chunking is character-based (`engine/src/chunker/mod.rs` operates on `chars.len()`). A gold fact longer than the chunk size cannot appear verbatim inside any single chunk's text, at any retrieval quality, with any overlap setting permitted by the `chunk_overlap >= chunk_size` rejection. Under the primary containment rule those facts are guaranteed misses.

They are also **not** caught by `boundary_attributable_misses`, whose anchored prefix/suffix rule requires the fact to straddle a chunk edge. So without a separate control, headline recall would silently mix "the retriever failed" with "the gold sentence is longer than the chunker's window", and a reader would attribute the second to the first.

**The ruling:**

- Compute `gold_fact_longer_than_chunk` per corpus at load time by comparing each gold fact's character length against the corpus config's declared chunk size (a new `chunk_size` key on the corpus TOML's `[documents]` table, set to 500 for MultiHop-RAG to match the shipped default the seeder relies on).
- **Exclude those facts from the recall denominator** and report the excluded count. Excluding is right rather than counting them as misses: a metric whose denominator contains items no retriever could ever satisfy is not measuring the retriever. Keeping them in would understate recall by a fixed, corpus-determined amount that varies with chunk size and is therefore not comparable across runs.
- Carry the excluded count in every affected dimension's `detail` map under the key `gold_facts_longer_than_chunk`, and print it beside the recall figure in the report so the exclusion is visible rather than silent. Plan 06.3-07 carries the matching caveat sentence.
- The exclusion applies to recall and nDCG's ideal-DCG gold length. It does **not** apply to `context_precision_at_k`, whose denominator is retrieved chunks rather than gold facts.

## Ruling: the evidence-match rule (planner decision, D-50 discretion)

06.3-AI-SPEC.md §1b and 06.3-RESEARCH.md Pitfall 7 both leave the chunk-boundary mitigation as an explicit planner input. It is decided here, once, and the executor implements it as stated.

**Primary source finding that corrects RESEARCH's recommendation.** RESEARCH names "raise the eval corpus's `chunk_overlap` above 538" as the *preferred* mitigation. That option self-destructs, verified in this repo's own code:

1. `gateway/main.go` rejects any upload where `chunk_overlap >= chunk_size`. Reaching an overlap of 538 therefore forces a `chunk_size` above 538.
2. `config/config.toml` `[engine.retrieval] excerpt_max_chars = 512`, and the citation `excerpt` is a bounded prefix of the chunk. A chunk larger than 512 characters makes `is_truncated` true on effectively every citation.
3. 06.3-AI-SPEC.md §5's normative note classifies a citation with `is_truncated == true` as **undecidable** for matching.

So the mitigation intended to make containment matching work is precisely the change that makes containment matching impossible. It is rejected.

**The rule, as it will be stated in the report in one sentence:**

> *A retrieved citation matches a gold evidence fact when the fact's whitespace-normalised text appears verbatim inside the citation's whitespace-normalised excerpt.*

**Decisions that follow, all binding on the executor:**

- **The eval corpus is seeded at the shipped chunking defaults** (`chunk_size = 500`, `chunk_overlap = 50`), with no per-upload override. Three converging reasons: the collision above; D-44 chose this corpus *because* full news articles exercise structure-aware chunking as shipped; and D-48 says the harness measures the shipped system. Plan 06.3-04's seeder sends no `chunk_size` or `chunk_overlap` form field.
- **The primary rule is used identically by recall@k, context precision@k, MRR@10 and nDCG@k.** One function, `fact_matches_excerpt()`. Divergence between them would make the metrics non-composable.
- **Residual boundary loss is measured, not hidden.** `defaultChunkOverlap = 50` is far below the median 161-character gold fact, so a fact straddling a chunk edge is contained in neither chunk and records a miss on a retrieval that was in fact perfect. This is a systematic downward bias. It is quantified by a **diagnostic that no headline metric consumes**: `boundary_attributable_misses`, computed by an anchored partial match — a normalised prefix of the fact of length at least `max(60, ceil(0.5 * len(fact)))` equal to the tail of the excerpt, or a normalised suffix of the same minimum length equal to the head of the excerpt. The 60-character floor is chosen because it exceeds the shipped 50-character overlap, so an overlap-window coincidence cannot trigger it. The report prints this count next to the strict recall figure.
- **Article-level matching is rejected** as the primary rule. It counts any chunk from a gold article as a hit even when that chunk contains none of the gold fact, and it collapses the gold denominator for the 7.5% of queries drawing two or more facts from one article — both errors inflate. The `document_id` → article map (plan 06.3-04) stays load-bearing for the coverage guardrail, not for scoring.
- **Undecidable is a third state, and it fails loud rather than printing quietly.** A retrieved chunk with `is_truncated == true` is neither a hit nor a miss, the anchored diagnostic does not fire on it, and the count of undecidable entries is reported. At the shipped 500/512 parameters this count should be zero — plan 06.3-08 wires the retrieved-chunk excerpt budget from the same `citation_excerpt_max_chars` value (512) the citation path uses, deliberately not from `resolve_citations()`'s 200-character default, so the truncation path is not reachable at shipped settings. But a non-zero rate means the chunking parameters moved and the numbers are not comparable to the previous run, and printing a count next to a still-published number lets a reader miss that. **When the undecidable rate over a scored set exceeds 1%, every retrieval dimension is emitted as `status='error'` with a reason naming the observed rate and the parameters, and no retrieval score is published for that run.** The threshold is 1% rather than 0 so a single pathological oversized chunk does not void an otherwise valid run, and it is far below any rate a real parameter change would produce.
