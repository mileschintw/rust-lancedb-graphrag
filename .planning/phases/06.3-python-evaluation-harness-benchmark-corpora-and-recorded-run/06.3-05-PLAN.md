<objective>
Turn one-question probing into a resumable, two-armed recorded drive plus an offline deterministic scorer: `run` produces a JSONL journal and nothing else, `score --no-judge` reads that journal and produces numbers with no network at all.

Purpose: driving and scoring are separate concerns, and separating them is what actually delivers D-50's guarantee that any reader can recompute the deterministic half of a published number from the repository alone. It is also what makes a run survive the free-tier daily ceiling — at roughly 1,000 generation calls for a full two-armed drive, partial completion is the expected case, not the exception, so `--resume` is load-bearing infrastructure rather than a convenience.
Output: the append-only journal with resume, the two-armed driver, the graph-ablation dimension with its provenance check, and the offline `score --no-judge` path.
</objective>

## User Story (MVP mode)

**As a** Lancet maintainer, **I want to** drive the whole question set across both graph arms and resume where I left off when the daily quota runs out, **so that** a multi-day run produces one coherent journal I can score offline as many times as I like.

Write `journal.py` with `RunRecord` (a Pydantic model with `extra="forbid"`), `Journal`, `journal_key()` and `load_done()`. Records are appended one compact JSON line at a time with an explicit UTF-8 encoding and an LF newline, flushed per record. `load_done()` tolerates a half-written trailing line from a killed process by skipping unparseable lines, so that unit is re-driven rather than silently treated as done. `RunRecord` carries `corpus`, `question_id`, `graph_arm`, `outcome`, the answer payload, `notices`, `node_failures`, `duration_ms`, `session_id`, `correlation_id`, `index_generation`, `partial`, and on failure `error_type` and `error`.

Write `run.py` with `drive()` and `drive_one()`, following the AI-SPEC's reference implementation rather than improvising. `drive()` builds the work units as the cross product of questions and the confirmed arm labels, filters out anything already in `load_done()`, and executes them through a `ThreadPoolExecutor` whose `max_workers` comes from config and defaults to one. Share a single `httpx.Client` across the workers — it is thread-safe — but bound its connection pool explicitly to the worker count, because an SSE query holds a connection open for its entire lifetime and the default pool of one hundred would let that run away.

Use `submit` plus `as_completed`, never `map`. With `map`, one escaping exception re-raises at consumption time, aborts the loop and discards every already-completed-but-unwritten result — against a daily request ceiling that is unrecoverable quota. Write journal lines from the main thread only, so no lock is needed and no interleaved write can tear a line and corrupt `--resume`.

`drive_one()` must not raise. Catch broadly and deliberately: `HarnessStreamError` alone is not enough, because an httpx read timeout is a transport error and a malformed frame raises a pydantic validation error, and both are expected against a rate-limited free-tier gateway while neither is in the harness's own exception hierarchy. Every failure becomes a durable `outcome="error"` record naming the exception type. A failed stream is not a measurement of zero; it is an absence of measurement, and the distinction is the difference between an honest report and a silently corrupt one.

`node_failed` frames are recorded as diagnostics and never treated as a run failure — the workflow carries a `retryable` flag and can still complete successfully, and blanket-failing on them would bias every metric downward.

Wire the `run` sub-command with `--corpus`, `--resume` and `--limit`. `--limit` exists only as a smoke knob: it stamps `partial: true` on the journal header and on every record, and plan 06.3-07's report generator refuses to publish such a journal. `--sample` is deliberately **not** a flag on `run`; it belongs to `score`, because reducing the drive would leave the journal holding fewer questions than the deterministic half is supposed to cover. Record that split in `eval/README.md` alongside the resume workflow and the free-tier arithmetic that makes a full drive a multi-day or credit-gated activity.

Write `tests/test_journal.py` and `tests/test_run_arms.py` against `pytest-httpx`, covering every behaviour above.

  <action>
Register the `graph_ablation_delta` dimension in `dimensions.py`. It consumes the scored records of both arms and returns a `DimensionResult` whose `detail` map holds each arm's metric value, each arm's sample size and each arm's error count alongside the delta — never the delta alone, because a delta without its arms and their sizes is not interpretable. A near-zero or negative delta is published as-is: the graph literature's own headline finding is that graph-augmented retrieval frequently underperforms vanilla retrieval, so an honest null result is a result, and suppressing it would be the fabrication D-51 exists to prevent.

Implement the provenance check the engine's own tests already assert: on the `graph-off` arm the response must carry a notice whose typed code is the graph-ablation value, and must not carry the graph-unavailable typed code attributable to the ablation. Bind on the typed enum ordinal rather than the string spelling, keeping the string only as a human-readable fallback, so a future rename of the string cannot silently break the check. A `graph-off` response failing that check means the flag did not do what the harness believes it did; record it as an error and exclude it from the arm, never score it as if the ablation had applied.

Guard the comparison's validity structurally: `score` refuses a journal containing more than one distinct non-empty `index_generation`, naming both, because arms compared across a reseed are confounded by index drift rather than by the graph flag. It also refuses on any `document_id` absent from `document_map.json`, naming the id — "not in the gold set" and "not in my map" are different facts, and conflating them is how recall goes quietly wrong while looking plausible.

Implement `score` with `--run`, `--no-judge` and `--sample`. Under `--no-judge` it touches no network at all and needs no API key: it reads the committed journal, the committed corpus sample and the committed document map, and writes `report.json`.
