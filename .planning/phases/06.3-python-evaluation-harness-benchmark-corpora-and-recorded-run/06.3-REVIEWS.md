# Cross-AI Plan Review — Phase 06.3 (7 plans)

## 1. Summary

This is an unusually rigorous plan set. The decision-coverage map, the explicit NOT-BUILDING dispositions for D-45/D-58, the "make an illegal state unconstructable" `DimensionResult`, the structural (raise-not-convention) null-query exclusion, and the type-level absence of a cross-corpus aggregate field are all above the norm. Plan 06.3-02's drift anchor and plan 06.3-03's chunk-overlap ruling both *correct* the upstream RESEARCH.md using primary-source evidence, and I confirmed both corrections are right against the code. **However, the plan set rests on one unexamined assumption that invalidates its headline numbers:** `structured_citations` on the `/rag/query` wire is the *model-cited subset*, not the retrieval result set, and the HTTP/SSE surface exposes no retrieved-chunk list at all. Every "retrieval recall@k / context precision / MRR / nDCG" number these plans publish would actually measure generator citation behavior. That is a phase-goal-level defect (ROADMAP SC3), and none of the seven plans mentions it. Secondary issues: a k-slicing contradiction between plans 01 and 03, several `read_first` symbols that don't exist, and a mislabeled `autonomous: true`.

## 3. Concerns

### HIGH — `structured_citations` is the model-cited subset, not the retrieval result set; the retrieval metrics measure the wrong thing

This is the finding that matters. Trace:

- `engine/src/workflow/nodes/generate.rs:364-371` builds citations via `resolve_citations_with_max_chars(&ctx.citations, &ctx.evidence_blocks, max_chars)`, then assigns `ctx.structured_citations = resolved_citations...` at `:372`.
- `ctx.citations` is the **post-repair model marker set** — the comment at `generate.rs:351-356` says so explicitly ("`cited_evidence_ids` the post-repair set").
- `engine/src/prompt.rs:596-604` only emits a `StructuredCitation` for an evidence block whose `id`/`chunk_id` matches a cited marker. Uncited retrieved blocks produce nothing.

So `structured_citations` = *evidence the LLM chose to cite*, a sparse subset of retrieval. Meanwhile the wire exposes **no retrieved-chunk list anywhere else**: `RetrievalSnapshotDTO` (`gateway/internal/sse/dto.go:47-57`) carries only `index_generation`, weights, limits and `result_hash`; `workflow_completed.metadata` (`gateway/internal/sse/sse.go:110-121`) carries `vector_count`/`bm25_count` but no ids.

Consequences, none of which any of the seven plans acknowledges:

- `evidence_recall_at_4`, `context_precision_at_4/10`, `mrr_at_10`, `ndcg_at_4/10` and `reference_convention_map_at_10` (06.3-03 Task 3) all measure *generator citation behavior conditioned on retrieval*, not retrieval. Publishing them under those names is exactly the metric-name drift 06.3-03's own prohibition forbids ("MUST NOT label a Lancet metric as the MultiHop-RAG paper's metric").
- 06.3-03's own "empty" edge resolution bakes the defect in: "an answerable question whose response returns zero citations contributes zero hits and stays in the recall and precision denominators." Under the real semantics that records recall 0 for a query whose retrieval may have been perfect and whose model simply answered without markers — and the model-only path (`allow_model_only`) produces exactly that shape by design.
- The `graph_ablation_delta` (06.3-05) inherits the confound: a delta between arms could be entirely a change in how many markers the model emitted.
- ROADMAP SC3 requires "retrieval recall@k, context precision, MRR/nDCG — run over the full set with no LLM." As specified, these numbers **cannot** be LLM-free — they are downstream of a generation call. That contradicts D-50's central guarantee, which 06.3-05 then mechanically "proves" with a zero-HTTP-request test over a journal whose contents were already LLM-shaped.

This needs resolving before 06.3-03 executes, and the resolution is a wire/scope decision, not a harness detail — D-48 says drive HTTP like a real client, but the HTTP surface does not carry what SC3 asks to measure.

### HIGH — Plans 01 and 03 specify contradictory top-k selection

- 06.3-01 Task 3 and its inlined helper: score "over the citations in the order the wire returned them" and (per the `<action>`) the tracer's containment check walks `structured_citations[:k]`; the pattern in RESEARCH.md is likewise `structured_citations[:k]`.
- 06.3-03 Task 2 `<action>`: "`recall_at_k` counts distinct gold facts matched **within rank <= k**", and the `<behavior>` for `context_precision_at_k` says "the number of citations actually returned **at rank <= k**".

With a sparse cited subset these are materially different — a response citing blocks at retrieval ranks 3 and 9 yields two candidates under `[:4]` slicing and one under `rank <= 4`. 06.3-03 additionally asserts *both* "preserves the wire order" **and** "uses the response's own `rank` field as the authoritative position" in the same must-have without reconciling them. The executor of 06.3-03 will silently change what 06.3-01's committed tracer test asserted.

### MEDIUM — `read_first` names symbols that do not exist, and the key_link doesn't cover the terminal frame

06.3-01 Task 1 `<read_first>` tells the executor to read `writeWorkflowEventSSE`, `writeStreamErrorSSE` and `handlePreStreamError` in `gateway/main.go`. Only the third exists (`gateway/main.go:787`). The writers are `sse.WriteWorkflowEvent` and `sse.WriteStreamError` in `gateway/internal/sse/sse.go:24,43`; `main.go:765` has a thin `writeWorkflowEvent` method that only intercepts checkpoints.

More consequentially, the plan's key_link says "client.py wire models mirror `gateway/internal/sse/dto.go` field-for-field; a renamed or removed gateway field must surface as a red test." But the `workflow_completed` payload — the terminal frame D-65 is built around — is **not** in `dto.go`. It is an inline `map[string]any` at `sse.go:82-136` (`success`, `total_duration_ms`, `error_kind`, `error_message`, `final_response`|`notices`, `metadata`). A rename there would not be covered by the stated mechanism. Same for `stream_error`'s `{code, message}` at `sse.go:25-28` and `node_failed`'s `{node_name, error_kind, error_message, retryable}` at `sse.go:67-72`.

### MEDIUM — `final_response` and top-level `notices` are mutually exclusive on the terminal frame; the plan's fallback rule doesn't say so

`sse.go:89-106`: `wcPayload["final_response"]` is set **only if** `GetFinalResponse() != nil`, `else` `wcPayload["notices"]` is set. So a terminal frame never carries both, and `sse_test.go:199` pins that ("must not carry a top-level notices list alongside final_response"). 06.3-01's must-have — "a terminal-only degraded response with zero `final_answer` frames produces `status='degraded'` with notices attached" — happens to be satisfiable, but only via the `else` branch, and the plan's separate rule ("when no `final_answer` arrived fall back to `workflow_completed.final_response`") plus "success with no answer payload raises `ContractViolation`" describes a state space the executor has to infer. State the disjunction explicitly or the `ContractViolation` will fire on legitimate degraded responses.

### MEDIUM — preflight conflates gateway-down with engine-down

06.3-04 Task 3 makes `check_gateway()` call `GET /health` and `check_engine()` read the engine block from the same response. But `gateway/main.go:361-364` returns **HTTP 503** with `{"status":"error","engine":{"status":"unreachable"}}` when the engine ping fails. A `check_gateway()` that fails on non-200 (the shape PATTERNS.md models at its `check_gateway_reachable`) will report "gateway not reachable" for a running gateway with a dead engine — precisely the misdirection D-64's "fails fast **with guidance**" exists to prevent. The fix is one sentence (treat a parseable 503 body as gateway-reachable, engine-failed), but the plan doesn't contain it.

### MEDIUM — 06.3-04 is labeled `autonomous: true` but carries three blocking live human-checks

Its frontmatter says `autonomous: true`, yet Task 1 requires an operator to run Atlas, start both services under `LANCET_ENV=eval`, and query two Postgres schemas; Task 2 requires a full live seed against real OpenRouter quota; Task 3 requires stopping the gateway and re-running. Compare 06.3-05 and 06.3-07, which correctly set `autonomous: false` for less. This will route the plan to a Pattern-A single-subagent dispatch that cannot satisfy its own verification.

### MEDIUM — the Atlas branch is a wave-3 single point of failure, and the likely-correct branch is the least-specified

I confirmed the risk is real, not hypothetical: `gateway/atlas.hcl` has exactly one `env "local"` with `src = "file://db/schema.hcl"`, and `gateway/db/schema.hcl:1` declares `schema "public"` as a literal label with every table hanging off `schema.public`. Atlas resolves the source's schema by that label, so Branch 1 (append `search_path=lancet_eval` to the URL) is unlikely to work, and Branch 2 requires parameterizing a schema block that is referenced ~dozens of times. Branch 3 (generated `schema.eval.hcl` + staleness check) is the probable outcome and gets one sentence with no generator command named. Since waves 4–6 all block on 06.3-04, an unresolved probe stalls four plans. Consider pre-resolving this probe now rather than at execution time.

### LOW — `resolve_citations`' 200-char default is a live footgun the ruling depends on not firing

`engine/src/prompt.rs:583` defaults `max_chars` to **200**, and `generate.rs:370` takes that branch when `citation_excerpt_max_chars` is `None`. Production is safe — `engine/src/config.rs:557` reads `excerpt_max_chars = 512` and `engine/src/service.rs:156` threads it in — so 06.3-03's claim that the undecidable count "should be zero at the shipped 500/512 parameters" is **verified correct**. But the whole retrieval metric set collapses to `undecidable` if any path ever takes the 200 branch, and no preflight check asserts the observed excerpt budget. Cheap insurance: have `check_corpus_generation()`'s throwaway query also assert `is_truncated == false` on its citations.

### LOW — scale and human-gate density

Seven plans, ~465k estimated tokens, all with `confidence: low`, plus at least five blocking human gates (06.3-04 ×3 live, 06.3-05 Task 1 decision, 06.3-05 human-check, 06.3-06 Task 3 hand-scoring 20 items, 06.3-07 Task 3 multi-day run). 06.3-06 Task 3 (calibration worksheet + agreement + prompt-version binding) is defensible under AI-SPEC §5 but is the one item I'd cut if the phase needs to land — D-52/D-62 do not require it, and it adds a human loop to an already human-heavy phase.

## 4. Suggestions

1. **Resolve the retrieval-visibility question before 06.3-03 executes.** Three options, in my order of preference: (a) add an additive `retrieved_chunk_ids` (or a full ranked list) to `RetrievalSnapshot` — a one-message proto change consistent with the D-74 additive pattern, and the only option that makes SC3's metrics mean what they say and satisfies D-50's no-LLM guarantee; (b) keep the current surface but **rename every affected dimension** to `cited_evidence_recall_at_k` etc., and state in the report that these are joint retrieval+citation metrics not comparable to any IR baseline; (c) narrow SC3 with an explicit recorded decision. Option (b) is the zero-code path but should not be taken silently — it changes what the phase claims.
2. **Pick one k-rule and pin it in 06.3-01's must-haves**, so the tracer test and the full metric module cannot diverge. Given the sparse cited set, `rank <= k` is the defensible one; delete the conflicting "preserves wire order" phrasing or demote it to a tie-break-only statement.
3. **Fix 06.3-01 Task 1's `read_first`**: replace `writeWorkflowEventSSE`/`writeStreamErrorSSE` with `gateway/internal/sse/sse.go` `WriteWorkflowEvent` / `WriteStreamError`, and add `gateway/internal/sse/sse_test.go` (it already pins the exact frame shapes the fixtures must reproduce). Extend the key_link to name `sse.go`'s inline terminal/stream_error/node_failed payloads, not just `dto.go`.
4. **Add one must-have to 06.3-01**: a `workflow_completed` frame carries `final_response` XOR top-level `notices`, never both; a `final_answer` frame and a `final_response` are never merged.
5. **Flip 06.3-04 to `autonomous: false`** and add the 503-body-parsing rule to `check_gateway()`/`check_engine()`.
6. **Run 06.3-04's Atlas Probe A now**, out of band, and rewrite Task 1 around the branch that actually works — including the concrete regeneration command if Branch 3 wins.
7. **Add an excerpt-budget assertion to preflight** (`is_truncated == false` on the throwaway query's citations) so the ruling's core assumption is checked once per run rather than assumed.

## 5. Risk Assessment

**HIGH.**

Execution risk is low-to-moderate — the plans are precise, the tests are well-specified, and I could verify nearly every code claim they make. The risk is *outcome* risk: the phase would very likely execute green and produce a committed, beautifully attributed, advisory-only report whose headline retrieval numbers do not measure retrieval. Every guard the plan set builds — the unconstructable fabricated score, the provenance checks, the publication preconditions, the ten-item spot-check — protects against *dishonest* numbers, and none of them protects against *correctly-computed numbers of the wrong quantity*. Given that this phase exists to make quality claims in a resume-oriented artifact, and that the README (Phase 6.4, D-73) will cite these numbers, a mislabeled recall figure is the single worst failure mode available here. Downgrade to MEDIUM once finding HIGH-1 has an explicit recorded resolution and the k-rule contradiction is closed; the remaining items are ordinary plan-hygiene fixes.

### Strengths
- Field-for-field mirror of `StructuredCitationDTO` / `NoticeDTO` / `RetrievalSnapshotDTO` (`gateway/internal/sse/dto.go:19–57`): `is_truncated`, `typed_code`, `index_generation`.

Treating "zero `final_answer`" as `status="degraded"` will classify **failed** workflows as degraded measurements unless the client also keys off `success`.
- **MEDIUM — notices on success are on `final_answer`, not the terminal.** `sse.go:91–99` omits top-level `notices` when `final_response` is present. A client that only reads notices from `workflow_completed` will see empty notices on every successful (including retrieval-degraded) run.

### Suggestions
- Map `QueryOutcome.status` from `workflow_completed.success` first; use missing `final_answer` only as a fallback after that.
- Collect notices from `final_answer` (and from the terminal only when `final_response` is absent).
- Freeze one arm-label vocabulary in `client.py` now, or add `client.py` to 06.3-05.

### Risk Assessment
**LOW** for the tracer itself; **MEDIUM** if the degraded/notice rules ship unchanged into scoring.

## 06.3-03 — Corpus config, sample, deterministic metrics

### Summary
Best plan in the set: one `fact_matches_excerpt` rule, nulls out of retrieval denominators, no LLM on `metrics` import, corpus-agnostic TOML. The overlap-538 mitigation is correctly rejected against this code: `chunk_overlap >= chunk_size` is 400 (`gateway/main.go:50–51, 417–418`), `excerpt_max_chars = 512` (`config/config.toml:52`), and `is_truncated` is set by `bounded_unicode_excerpt` (`engine/src/prompt.rs:607–608`).

Chunk windows are **characters**, not tokens (`engine/src/chunker/mod.rs:189–207`: `chars.len()`, `start + target_size`). Default 500/50 with excerpt 512 means typical citations are **not** truncated — the plan's "undecidable count should be ~0 at shipped params" is right for that reason.

### Strengths
- Shared matching rule + `rank` as wire order (`StructuredCitationDTO.rank`, never re-sort) matches D-50 and the SSE DTO.
- `NOTICE_CODE_NO_EVIDENCE = 1` (`proto/lancet/v1/lancet.proto`) is the right abstention bind.
- Boundary diagnostic floor 60 > overlap 50 is a real discriminator, not a comment.

### Concerns
- **HIGH — gold facts longer than a chunk are unmatchable and are not the boundary diagnostic.** AI-SPEC max fact length 538 > `defaultChunkSize` 500. Those facts cannot appear verbatim in any excerpt, even with perfect retrieval and no straddle. They will inflate **misses**, not `boundary_attributable_misses` (that rule needs a prefix/suffix anchored on a chunk edge). Headline recall will mix "retriever failed" with "gold sentence longer than the chunker."
- **MEDIUM — `is_truncated => undecidable` is correct at 500/512, but any future raise of `chunk_size` above 512 silently zeros retrieval metrics.** The report should treat a non-zero undecidable count as "numbers not comparable," which 06.3-07 already wants; 03 should fail-loud or skip retrieval dimensions when undecidable rate exceeds a tiny epsilon, not only print a count.
- **MEDIUM — GraphRAG-Bench TOML with no questions/documents artifact.** `files_modified` has `graphrag_bench.toml` but no stub JSONL. If `load_corpus()` requires the questions path to exist, the D-59 proof test is one missing file from red.

### Suggestions
- Add a diagnostic `gold_fact_longer_than_chunk` (fact length > 500) next to boundary misses; exclude those facts from the recall denominator or report them separately.
- Ship a minimal `graphrag_bench` fixture file so `load_corpus("graphrag_bench")` is offline-true.

### Risk Assessment
**MEDIUM.** Rule is honest; unmeasured long-fact misses will make MultiHop-RAG recall look like a retriever bug.
