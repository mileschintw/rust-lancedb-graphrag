# Phase 06.3: Code Review Report

**Reviewed:** 2026-08-29T00:00:00Z
**Depth:** standard
**Files Reviewed:** 69 (Rust engine + Go gateway wiring for `retrieved_chunks` wire field, plus the full new Python evaluation harness `eval/`)
**Status:** issues_found

## Summary

The Rust/Go/proto side of this phase (adding `RetrievalSnapshot.retrieved_chunks` end-to-end, the chunker empty-region fix, the embedding client retry/backoff retune, and the associated generated code / test-count assertions) is small, well-tested, and internally consistent — wire-contract tests for the new protobuf field exist on both the Rust and Go sides and agree with each other.

The bulk of this phase is the new `eval/` Python package. It is generally well structured (fail-closed `pydantic` settings, atomic cache/map writes, an append-only resumable journal, a byte-identical JSON-schema regression test, an explicit API-key-leak test). However, the review surfaced two genuine correctness gaps in destructive/config-critical code paths, a documentation-vs-implementation mismatch that ships inside every generated evaluation report, and one confirmed orphaned test fixture (the specific item flagged for investigation in this review's scope).

**On `eval/tests/fixtures/journal_fixture.jsonl`:** confirmed orphaned/dead test data. A repo-wide grep (outside `.planning/`) finds zero references to the filename anywhere in `eval/tests/*.py` or `eval/tests/conftest.py`. `conftest.py` only defines a loader fixture for `fixtures/sse/*` (`load_sse_fixture`); there is no equivalent loader for journal fixtures. Every test that needs a journal (`test_journal.py`, `test_run_arms.py`, `test_score_deterministic.py`, `test_score_judged.py`, `test_secrets.py`) builds `tmp_path / "journal.jsonl"` and writes its own inline `RunRecord`/JSON content rather than reading this file. It was committed in the 06.3-07 feat commit but never wired to anything — see WR-01.

## Critical Issues

### CR-01: `reseed` never touches the PostgreSQL eval schema despite being documented and advertised as a full clean-store reset

**File:** `eval/src/lancet_eval/seed.py:271-303` (also `eval/src/lancet_eval/cli.py:183-212`, `eval/README.md:126`)
**Issue:** `reseed_corpus()` only (1) `shutil.rmtree()`s the LanceDB directory and (2) deletes the local `document_map.json`. It never issues any request or SQL against the isolated `lancet_eval` PostgreSQL schema. But:
- `eval/README.md`'s CLI table describes `lancet-eval reseed` as: *"Drop and recreate isolated evaluation store schema"*.
- `cli.py`'s `reseed` command help text says: *"Reseed evaluation store with clean schema."*
- `seed.py`'s own docstring says: *"Drop the eval store and re-seed from scratch."*

None of these promises are kept for the relational side. After a `reseed --confirm`, the `documents`, `workflow_checkpoints`, and `document_reconciliation_intents` rows for every previously-seeded article remain in Postgres (with stale `status`, `chunk_count`, etc.), while the vector/graph data backing them has just been deleted from LanceDB. Re-seeding then creates brand-new gateway `document_id`s for the same corpus articles (since `document_map.json` was deleted and corpus-id dedup only checks the in-memory map, not the DB), so repeated reseeds strictly accumulate orphaned rows in the "isolated" store rather than recreating it. `test_seed.py::test_reseed_requires_confirmation_and_isolation_check` only exercises the confirmation guard — there is no test proving Postgres state is actually reset.
**Fix:** Either implement the documented behavior (e.g., have `reseed_corpus` call a gateway/admin endpoint or issue `TRUNCATE ... CASCADE` against the `lancet_eval` schema tables before re-seeding), or correct the documentation/CLI help/docstrings to state plainly that `reseed` only resets the LanceDB store and document map, and that the Postgres schema must be reset manually (e.g. via `atlas schema clean --env eval` or a `DROP SCHEMA ... CASCADE; CREATE SCHEMA ...`) before running it.

### CR-02: `question_deadline_secs` config knob is validated but never wired into the primary `run` command path

**File:** `eval/src/lancet_eval/run.py:38-43`, `eval/src/lancet_eval/config.py:49`, `eval/src/lancet_eval/client.py:149-156`
**Issue:** `EvalSettings.question_deadline_secs` is defined, validated (`config.py:84-88`), and covered by a dedicated negative-value test (`test_client_contract.py:323`), but it is only ever read in the `probe` CLI command (`cli.py:570`). The actual benchmark driver, `drive_one()` → `run_query()` (`run.py:39-43`), never passes `deadline_s`, so `run_query`'s default of `600.0` (`client.py:155`) always applies for the `lancet-eval run` command regardless of what an operator configures via `LANCET_EVAL__QUESTION_DEADLINE_SECS` or `eval/config.toml`. A user who lowers this to guard against runaway/hung queries during a full benchmark run gets silent no-op behavior with no warning.
**Fix:** Thread `EvalSettings` (or just `question_deadline_secs`) through `drive()` → `drive_one()` → `run_query(..., deadline_s=eval_settings.question_deadline_secs)`, matching how `probe` already does it.

## Warnings

### WR-01: Orphaned test fixture `journal_fixture.jsonl` committed with no consumer

**File:** `eval/tests/fixtures/journal_fixture.jsonl` (all 5 lines), `eval/tests/conftest.py:8-23`
**Issue:** Confirmed dead test data — see Summary. It was added in the 06.3-07 feat commit alongside `journal.py`/`run.py`/`score.py` work, but no test file, fixture, or `conftest.py` helper references it, and its own plan's SUMMARY.md never mentions it either. It silently rots (e.g. it lacks the `retrieved_chunks` fields other later fixtures/tests use, and predates the `snapshot.embedding_model`/`title`/`section_path` conventions used elsewhere), so if it were ever wired up later it would likely fail current model validation.
**Fix:** Either delete the file, or add the loader/test it was clearly intended for (e.g. an integration-style `score_run()` test driven from a realistic on-disk journal, analogous to the `load_sse_fixture` pattern already used for SSE fixtures).

### WR-02: Published "Evidence Matching Rule" in the report template does not match the implemented scoring rule

**File:** `eval/src/lancet_eval/templates/report.md.j2:47`, `eval/src/lancet_eval/metrics.py:62-94`, confirmed by `eval/tests/test_metrics.py:78-92`
**Issue:** Every generated `report.md` states under "Methodological Caveats":
> "A retrieved chunk matches a gold fact if and only if the chunk's normalized text contains the fact's normalized text as a contiguous substring **or the fact's normalized text contains the chunk's text** (for facts truncated at passage boundaries)."

This describes a bidirectional-containment match rule. The actual scoring function `fact_matches_excerpt()` only implements one direction (`norm_fact in norm_excerpt`); the second ("boundary straddle") case is handled by a separate function `boundary_attributable()` that is explicitly diagnostic-only — `test_metrics.py:85-86` proves a boundary-straddling case still resolves to `MatchVerdict.MISS` from `fact_matches_excerpt`, and is merely counted in the `boundary_attributable_misses` detail field, never promoted to a HIT. The doc text therefore overstates recall/precision/MRR/nDCG for anyone reading a published report and taking the stated methodology at face value.
**Fix:** Correct the template wording to state that boundary-straddling facts are excluded from the recall/precision numerator and only surfaced via the `boundary_attributable_misses` diagnostic count, not counted as matches.

### WR-03: `EvalSettings.sample_seed` is a dead configuration field

**File:** `eval/src/lancet_eval/config.py:62`
**Issue:** `EvalSettings` declares `sample_seed: int = 42`, and it is included in the settings' documented field inventory (asserted by `test_client_contract.py`'s `expected_fields` set), but it is never read anywhere in `eval/src/lancet_eval/*.py` (`grep` confirms zero uses of `settings.sample_seed`/`self.sample_seed` from an `EvalSettings` instance). The actual sampling seed used throughout `corpus.py`/`score.py` comes exclusively from each corpus's TOML file (`CorpusConfig.sample_seed`, `corpus.py:131`). An operator setting `LANCET_EVAL__SAMPLE_SEED=...` would get no error and no effect, silently believing they changed determinism.
**Fix:** Either remove the field, or wire it in as the fallback default for `CorpusConfig.sample_seed` when a corpus TOML omits `sample_seed`.

### WR-04: `embed_with_retry` silently substitutes a zero vector for empty/whitespace-only text with no test coverage or diagnostic

**File:** `engine/src/client/mod.rs:234-238`
**Issue:** The new short-circuit (`if trimmed.is_empty() { return Ok(vec![0.0; expected_dimension]) }`) bypasses the OpenRouter call and returns an all-zero embedding for empty input, silently, with no log/notice and no accompanying unit test (searched `engine/src/client/tests.rs` — no test exercises this path). A zero vector is a "valid" embedding as far as downstream cosine-similarity code is concerned, so any upstream bug that produces empty chunk text (or an empty user query) now degrades silently into a permanently near-zero-similarity vector instead of surfacing as an error, and no test exists to pin the intended behavior (e.g. what happens for a fully-blank query embedded at request time vs. an already-filtered chunk).
**Fix:** Add a regression test asserting the exact contract (zero-vector short-circuit for blank input) and consider emitting a debug-level log or workflow notice when this path fires, since it indicates a data-quality condition further upstream (especially now that `chunker::append_region`/`split_window` were just changed in this same commit to filter out blank chunks — this guard may be masking a upstream contract that should already guarantee non-empty text reaches the embedder).

### WR-05: `max_workers` config setting is disconnected from the primary `run` command's concurrency knob

**File:** `eval/src/lancet_eval/config.py:61`, `eval/src/lancet_eval/cli.py:248-255`, `eval/src/lancet_eval/run.py:80-138`
**Issue:** `EvalSettings.max_workers` is validated (`config.py:89-90`) and used to size `httpx.Limits` in the `probe` command (`cli.py:557-559`), but the `run` command — the harness's main workhorse — takes its own independent `--workers`/`-w` CLI option (default `1`, `cli.py:248-255`) that is passed straight to `drive(..., workers=workers)` and never cross-checked against or defaulted from `settings.max_workers`. Two different, disconnected concurrency knobs exist for two different commands, which is confusing and easy to misconfigure (e.g. setting `LANCET_EVAL__MAX_WORKERS` and expecting it to also bound `run`'s concurrency).
**Fix:** Either default `run`'s `--workers` option from `settings.max_workers` when not explicitly passed, or rename/document the two settings so it's clear they are unrelated.

## Info

### IN-01: `DIMENSION_REGISTRY` / `register_dimension` builder-pattern is effectively unused

**File:** `eval/src/lancet_eval/dimensions.py:49,67-69,79`
**Issue:** The registry infrastructure (`DIMENSION_REGISTRY: dict[str, DimensionBuilder]`, `register_dimension()`) is built out generically but only ever populated with a single entry, `community_summary_quality` (the placeholder). `score.py`, the actual dimension producer for the other 11 registered dimension names, constructs `DimensionResult` objects directly and never touches the registry. This is speculative generality for a single caller.
**Fix:** Either use the registry to drive dimension construction generically in `score.py`, or drop the registry abstraction and keep only the flat `REGISTERED_DIMENSIONS` name list (which is genuinely used by tests as the canonical dimension-name set).

### IN-02: `retrieval_skipped_count` computed per-arm but never surfaced

**File:** `eval/src/lancet_eval/score.py:198,212-214,260`
**Issue:** `arm_metrics[arm]["retrieval_skipped"]` is accumulated whenever a success record has `snapshot is None`, but this count is never read anywhere after being stored in `arm_metrics` — it doesn't feed any `DimensionResult`'s `detail` dict, nor the markdown/JSON report. Dead accounting that looks like it should inform "Failed Query Snapshot Exclusion" (caveat #6 in `report.md.j2`) but currently doesn't.
**Fix:** Surface `retrieval_skipped` in the relevant dimensions' `detail` (e.g. `retrieval_evidence_coverage`), or remove the dead accumulator.

### IN-03: `probe` command hardcodes model-pin strings instead of sourcing them from configuration or the live response

**File:** `eval/src/lancet_eval/cli.py:680-682`
**Issue:** `RunMetadata(generation_model="dots-studio/dots-3-note-preview:free", embedding_model="text-embedding-3-small", judge_model="meta-llama/llama-3.3-70b-instruct:free", ...)` are all string literals, disconnected from `settings.judge_model`, the corpus config's `judge_model`, or `snapshot.embedding_model` (which `score.py` does source dynamically, `score.py:719-724`). If the shipped models are ever repinned, `probe` reports will keep claiming stale model pins even though `test_client_contract`/`generation/tests.rs` enforce the pin elsewhere.
**Fix:** Source these from `load_settings()`/`load_corpus(corpus).judge_model` and `outcome.answer.snapshot.embedding_model` where available, matching `score.py`'s approach.

### IN-04: Local dev/eval Postgres URLs embed the well-known `postgres:postgres` credential pair

**File:** `gateway/atlas.hcl:1-9`, `gateway/db/schema.eval.hcl` (comment header), `eval/src/lancet_eval/config.py:51,53-55`
**Issue:** Default connection strings use `postgres://postgres:postgres@127.0.0.1:5432/...` throughout the Atlas config and `EvalSettings` defaults. This matches the pre-existing project convention (same pattern already present for the dev schema before this phase) and is scoped to local-only default configs (real deployments override via env), so this is informational rather than a new vulnerability introduced by this phase — flagging only because it's touched in this diff (`gateway/atlas.hcl` is new in this phase).
**Fix:** No action required beyond continuing to ensure these defaults are always overridden for any non-local environment (already the case per `.gitignore`'s exclusion of `config/config.prod.toml`/`config/config.dev.toml`).
