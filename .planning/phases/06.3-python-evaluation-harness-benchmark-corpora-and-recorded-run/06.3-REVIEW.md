# Phase 06.3: Code Review Report

**Reviewed:** 2026-09-03T22:55:51Z
**Depth:** standard

## Summary

This review covers the union of two gap-closure plans (06.3-09: uncommitted MultiHop-RAG benchmark run; 06.3-10: under-seeded document_map.json) and an interleaved Quick Task migrating the paid model stack (voyageai/voyage-4-large embeddings, deepseek/deepseek-v4-flash-0731 generation) with new concurrency knobs.

The Python evaluation harness changes (seed.py's schema-isolated reset path, cli.py's run-directory resolution) are well-guarded: SQL identifiers passed to `psql` are validated with a strict regex before being embedded in DDL, subprocess calls never use `shell=True`, and the isolation guards (`assert_schema_isolated`, `assert_admin_dsn_targets_eval_database`) are exercised by targeted negative tests (`test_reset_refuses_non_identifier_schema_name`, `test_reset_refuses_dsn_with_foreign_host_or_dbname`) that assert `subprocess.run` is never invoked for a rejected identifier/DSN. No injection vector was found in the schema-reset path.

The most significant defect is in the Rust engine, not the eval harness: `DatabaseManager::get_or_create_table` (introduced in this diff to back `documents_table()`, `nodes_table()`, `entities_table()`, `edges_table()`, `entity_edges_table()`, `staged_documents_table()`) treats *any* error from `open_table()` as "table missing" and silently creates a fresh empty table in its place. This method backs the live, per-query graph-augmentation path (`service.rs::attempt_graph_augmentation` calls `entities_table()` on every request) as well as the ingestion mutation path, so a transient or partial storage failure — not just a genuinely absent table — is masked by silently replacing existing data with an empty table instead of failing closed. The test the author added to force a genuine failure (`graph_augmentation_attempted_and_failed_is_observable_end_to_end`) had to go further than "delete the directory" (which no longer forces a failure under the new fallback) and additionally write a corrupted non-directory file at the same path — direct evidence that the intended "real table-open failure" scenario is now silently healed rather than surfaced.

The remainder of the findings are lower-severity robustness/consistency gaps: a dead fallback branch in `seed.py`'s schema-reset command selection, an unwrapped `subprocess.TimeoutExpired`, a newly-plumbed per-question `deadline_s` config value that is silently capped below its own default by a hardcoded httpx read timeout, and a couple of naming/duplication nits.

## Critical Issues

### CR-01: `get_or_create_table` masks real LanceDB failures as "table missing," risking silent data loss on the live query path

**File:** `engine/src/db/mod.rs:111-129`
**Issue:**

```rust
async fn get_or_create_table(&self, name: &str) -> Result<Table, String> {
    match self.connection.open_table(name).execute().await {
        Ok(tbl) => Ok(tbl),
        Err(_) => {
            let schemas = table_schemas();
            if let Some((_, expected)) = schemas.into_iter().find(|(n, _)| *n == name) {
                let tbl = self
                    .connection
                    .create_empty_table(name, expected)
                    .execute()
                    .await
                    .map_err(|error| format!("failed to create LanceDB table {name}: {error}"))?;
                Ok(tbl)
            } else {
                Err(format!("unknown LanceDB table {name}"))
            }
        }
    }
}
```

This function backs `documents_table()`, `staged_documents_table()`, `nodes_table()`, `edges_table()`, `entities_table()`, and `entity_edges_table()` (all previously simple `open_table().await.map_err(...)` calls that surfaced the underlying error verbatim). The `Err(_)` arm now treats **any** failure to open the table — corruption, a transient IO error, a permissions problem, a concurrent process holding a lock, or a genuinely deleted directory — identically to "table does not exist yet," and reacts by silently creating a brand-new **empty** table at that name.

This method is called on the hot path, not just at startup:
- `service.rs:247` — `attempt_graph_augmentation()` calls `database.entities_table()` on every RAG query. If the entities table becomes transiently unreadable (e.g. a concurrent index rebuild, a filesystem hiccup, an accidentally-deleted directory), the very next query will not fail with `AttemptedAndFailed` as designed — it will silently swap in an empty entities table, permanently discarding graph augmentation for the corpus generation with no error signal.
- `ingest.rs:613-615, 999` — the ingestion mutation path opens `documents_table()`, `nodes_table()`, `edges_table()`, and `entities_table()` this way too, so the same masking applies to document/entity persistence.

The `DatabaseManager::open_and_validate` path (used for read-only startup validation, `db/mod.rs:35-62`) deliberately keeps the old fail-closed behavior (checks `table_names()` and errors if a required table is absent), and `validate_schema`'s own error message states the project's explicit design intent: *"schema reconciliation is fail-closed by design."* `get_or_create_table` violates that stated design principle for the live-serving `DatabaseManager` used by `main.rs`.

The regression is corroborated by the test suite itself: `engine/src/tests.rs:7139-7177` (`graph_augmentation_attempted_and_failed_is_observable_end_to_end`) still carries the stale comment *"delete the entities table's on-disk LanceDB directory ... so entities_table() genuinely fails to open"*, but the diff for this phase had to add an extra step beyond deletion:

```rust
std::fs::remove_dir_all(&entities_dir)
    .expect("remove entities.lance to force a real table-open failure");
std::fs::write(&entities_dir, b"corrupted non-directory file")
    .expect("write corrupted file in place of entities.lance");
```

Mere directory removal is no longer sufficient to force the failure the test wants to exercise — `get_or_create_table` now silently heals a missing directory by recreating it empty, so the author had to write a *non-directory file* at the path to make both `open_table` and the subsequent `create_empty_table` fail. This is the masking behavior manifesting in the test itself; it will manifest identically in production for the (far more likely) "directory transiently missing/unreadable" case.

**Fix:** Only fall back to creation when the table is genuinely absent (mirror the pattern already used in `initialize_tables()` / `open_and_validate()`, which lists `table_names()` first), and propagate all other open errors unchanged:

```rust
async fn get_or_create_table(&self, name: &str) -> Result<Table, String> {
    let existing = self
        .connection
        .table_names()
        .execute()
        .await
        .map_err(|error| format!("failed to list LanceDB tables: {error}"))?;

    if existing.iter().any(|n| n == name) {
        return self
            .connection
            .open_table(name)
            .execute()
            .await
            .map_err(|error| format!("failed to open LanceDB table {name}: {error}"));
    }

    let schemas = table_schemas();
    if let Some((_, expected)) = schemas.into_iter().find(|(n, _)| *n == name) {
        self.connection
            .create_empty_table(name, expected)
            .execute()
            .await
            .map_err(|error| format!("failed to create LanceDB table {name}: {error}"))
    } else {
        Err(format!("unknown LanceDB table {name}"))
    }
}
```

## Warnings

### WR-01: Dead/unreachable fallback branch in `reset_eval_schema` produces an unhandled crash instead of a clear error

**File:** `eval/src/lancet_eval/seed.py:106-143`
**Issue:**

```python
if shutil.which("psql"):
    psql_cmd = [...]
    cmd_cwd = gateway_dir
elif shutil.which("docker"):
    psql_cmd = [...]
    cmd_cwd = repo_root()
else:
    psql_cmd = [
        "psql",
        settings.dev_database_url,
        "-v", "ON_ERROR_STOP=1",
        "-c", drop_create_sql,
    ]
    cmd_cwd = gateway_dir
```

The `else` branch is only reached when `shutil.which("psql")` already returned `None`, yet it unconditionally builds a command that re-invokes `"psql"`. `subprocess.run(["psql", ...])` will raise `FileNotFoundError` (not a `SeedError`, and not something callers catch specifically) when neither `psql` nor `docker` is on `PATH`, producing an opaque Python traceback instead of the clear, actionable `SeedError` messages this function otherwise provides (e.g. for bad schema names or DSN mismatches).

**Fix:** Raise a clear `SeedError` when neither tool is available instead of duplicating the `psql`-unavailable branch:

```python
else:
    raise SeedError(
        "Neither 'psql' nor 'docker' found on PATH; install the PostgreSQL "
        "client or Docker to reset the eval schema."
    )
```

### WR-02: `subprocess.TimeoutExpired` is not translated to `SeedError` in the schema-reset path

**File:** `eval/src/lancet_eval/seed.py:145-167`
**Issue:** `subprocess.run(psql_cmd, ..., timeout=30.0)` and the subsequent `atlas schema apply` call (`timeout=60.0`) can each raise `subprocess.TimeoutExpired`. Every other failure mode in `reset_eval_schema` (non-zero return code) is wrapped in a descriptive `SeedError`, but a hang (e.g. `psql` prompting for a password, or a stuck connection) surfaces as a raw `TimeoutExpired`, which is inconsistent with the rest of the module's error-handling contract and is not covered by `test_seed.py`'s isolation-guard tests.
**Fix:** Wrap both `subprocess.run` calls in a `try`/`except subprocess.TimeoutExpired` that re-raises as `SeedError` with the elapsed timeout and command context.

### WR-03: Newly-plumbed per-question `deadline_s` is silently capped by a hardcoded 300s httpx read timeout, and ignores `gateway_timeout_secs`

**File:** `eval/src/lancet_eval/run.py:124-135`
**Issue:** This diff threads `eval_settings.question_deadline_secs` (default `600.0`, see `config.py:65`) through `drive()` → `drive_one()` → `run_query(..., deadline_s=...)` so that a per-question wall-clock deadline can be configured. However, the `httpx.Client` constructed in `drive()` uses a hardcoded read timeout well below that default:

```python
eval_client = client or httpx.Client(
    base_url=eval_settings.gateway_url,
    limits=limits,
    timeout=httpx.Timeout(connect=10.0, read=300.0, write=30.0, pool=10.0),
)
```

If the gateway goes more than 300s without emitting a chunk on the SSE stream (plausible for a slow multi-hop/graph-augmented generation, which is exactly the scenario a 600s deadline is meant to accommodate), `httpx` raises `ReadTimeout` at 300s — well before the configured 600s `deadline_s` check inside `run_query`'s event loop ever gets a chance to fire. The other call sites in this same codebase (`cli.py:571`, `preflight.py:314`, `seed.py:303`) correctly source their client timeout from `settings.gateway_timeout_secs`; `run.py` instead hardcodes a value that happens to coincide with the *default* of that same setting, so raising `gateway_timeout_secs` or `question_deadline_secs` above 300s in configuration has no effect here.
**Fix:** Derive the read timeout from `eval_settings.gateway_timeout_secs` (or `question_deadline_secs`, whichever is intended to be authoritative) instead of a hardcoded literal, e.g. `read=max(eval_settings.gateway_timeout_secs, eval_settings.question_deadline_secs)`.

### WR-04: `MAX_CONCURRENCY` constant name is misleading — it is a default, not an enforced ceiling

**File:** `engine/src/client/mod.rs:11-12, 97-106`
**Issue:**

```rust
pub const DEFAULT_EMBEDDING_CONCURRENCY: usize = 2;
const MAX_CONCURRENCY: usize = DEFAULT_EMBEDDING_CONCURRENCY;
...
pub fn new_with_concurrency(
    model: impl Into<String>,
    endpoint: impl Into<String>,
    max_concurrency: usize,
) -> Result<Self, String> {
    let mut config = Self::new(model, endpoint)?;
    config.max_concurrency = max_concurrency;
    config.validate()?;
    Ok(config)
}
```

`MAX_CONCURRENCY` reads as an enforced upper bound, but `new_with_concurrency` (used by `main.rs` with `effective_settings.embedding_concurrency`, defaulting to `12` per `config.rs::default_embedding_concurrency`) freely overrides it with no upper-bound check — `validate()` only rejects `0`. Functionally this is fine (the field is genuinely meant to be configurable), but the name will mislead the next reader into assuming there's a hard cap of 2 concurrent embedding requests, when production actually runs at 12.
**Fix:** Rename the constant to `DEFAULT_EMBEDDING_CONCURRENCY_FALLBACK` (or just drop the redundant `MAX_CONCURRENCY` alias and reference `DEFAULT_EMBEDDING_CONCURRENCY` directly), or add an explicit upper-bound check in `validate()` if a real ceiling is intended.

### WR-05: Path-traversal-shaped inputs are not validated for `--corpus` before being used to build filesystem paths

**File:** `eval/src/lancet_eval/seed.py:209-211`, `eval/src/lancet_eval/cli.py:214-231`
**Issue:** `get_document_map_path(corpus_name)` (`repo_root() / "eval" / "corpora" / corpus_name / "document_map.json"`) and `resolve_run_dir(corpus, ...)` (`root / f"{today}-{corpus}"`) both interpolate the `--corpus` CLI value directly into a filesystem path with no validation (no allowlist of known corpora, no rejection of `..`/absolute-path segments). `corpus.py`'s `CorpusConfig.__init__` will fail closed later with `CorpusError` if `eval/corpora/<corpus>.toml` doesn't exist, but `seed.py`'s document-map read/write path and `cli.py`'s run-directory resolution are reached before or independently of that check in some flows (e.g. `load_document_map` in `test_secrets.py`, `resolve_run_dir` in `run_benchmark`). Since this is a local operator-invoked CLI (not a network-facing service) the practical exploitability is low, but a corpus name like `../../../../tmp/evil` would let `save_document_map_atomic` write outside `eval/corpora/`.
**Fix:** Validate `corpus_name` against an allowlist (or a conservative `^[A-Za-z0-9_-]+$` pattern) at the CLI boundary before it reaches path-construction helpers.

## Info

### IN-01: Probe-query fallback logic is duplicated verbatim between `seed.py` and `preflight.py`

**File:** `eval/src/lancet_eval/seed.py:408-413`, `eval/src/lancet_eval/preflight.py:155-161`
**Issue:** Both files independently implement the identical "pick a title from the doc map, else use a hardcoded fallback question" block:
```python
probe_query = "What hospital program helps teenage patients in Nebraska?"
if doc_map.entries:
    first_entry = next(iter(doc_map.entries.values()))
    if first_entry.title:
        probe_query = first_entry.title
```
**Fix:** Extract a shared `pick_probe_query(doc_map: DocumentMap) -> str` helper (e.g. in `corpus.py` or a small shared module) to avoid the two copies drifting apart.

### IN-02: `resolve_run_dir` glob pattern is not robust to corpus names containing glob metacharacters

**File:** `eval/src/lancet_eval/cli.py:214-231`
**Issue:** `root.glob(f"????-??-??-{corpus}")` interpolates `corpus` directly into a glob pattern. A corpus value containing `*`, `?`, or `[` (unlikely but not rejected anywhere) would silently change the resume-matching semantics rather than raising a clear error.
**Fix:** Escape `corpus` with `glob.escape()` before interpolating into the pattern, or validate `corpus` against a restricted character set at the CLI layer (see WR-05).

### IN-03: `default_generation_model()` in `config.rs` was not updated as part of the model migration

**File:** `engine/src/config.rs:59-61, 507`
**Issue:** This diff updates `default_embedding_model()` to `"voyageai/voyage-4-large"` and the eval harness defaults to `"deepseek/deepseek-v4-flash-0731"` (`preflight.py`, `cli.py probe`, `score.py`), but `config.rs::default_generation_model()` / `OpenRouterSettings::default().generation_model` remains `"openai/gpt-4o-mini"`. This is presumably intentional (the actual production model is set via `config/config.toml`, which is out of this review's scope), but it leaves the in-code default inconsistent with the rest of the migration and could confuse a reader relying on `Settings::default()` (e.g. in tests) to reflect the currently-shipped model.
**Fix:** If `openai/gpt-4o-mini` is intentionally retained as a safe code-level fallback distinct from the deployed `config.toml` value, add a short comment noting that; otherwise update it to match the migration.
