# Phase 06.3: Code Review Report

**Reviewed:** 2026-09-04T14:49:43Z
**Depth:** standard

## Summary

Reviewed the gap-closure fix from plan 06.3-11: the calibration-worksheet candidate
selector in `score.py` was changed to require that each candidate resolve to a
`JudgeCacheEntry` in `judge_cache.json` with a non-null `verdict`, in addition to
having non-empty `structured_citations`, before it is written to the calibration
worksheet. `judge.py` was read as the contract anchor (`JudgeCacheEntry`,
`cache_key()`, `truncate_evidence()`); it was not itself modified by this plan.

The verified-selection branch itself (`score.py:466-489`, the `if not no_judge and
judged_qids:` path) is correct and matches its contract: it filters on
`structured_citations`, recomputes the cache key identically to how the judging
pass wrote it, and requires `entry.verdict is not None`. The two new/modified tests
covering it (`test_worksheet_rows_are_drawn_from_the_judged_subset`,
`test_worksheet_excludes_judge_errored_records`) each pass with the current code.

However, that verified branch is only reachable when `no_judge=False`. `no_judge`
defaults to `True` on the CLI (`cli.py:317-323`), and `judged_qids` is populated
*only* inside the `if not no_judge:` block (`score.py:290`, `292`) — so whenever
`no_judge=True`, the `else` branch at `score.py:489` fires unconditionally and
emits the first 20 primary-arm records into the calibration worksheet with **no**
citation check and **no** cache-verdict check at all. This is exactly the failure
mode the fix was supposed to close, reachable via the CLI's default flag combination.
See CR-01.

I also found a test-coverage gap in the exact scenario the scoping note asked me to
check (mixed cited/uncited/judge-errored records within one run), plus three
pre-existing issues encountered while reading these files that are unrelated to
this specific fix but worth recording for awareness (WR-02, WR-04, IN-01, IN-02
below are explicitly out-of-scope-for-06.3-11 and should not be attributed to this
plan's diff).

## Narrative Findings (AI reviewer)

### Critical Issues

#### CR-01: Calibration-worksheet selector's cache verification is bypassed on the default `no_judge=True` path

**File:** `eval/src/lancet_eval/score.py:464-489`

**Issue:**
The new verified-selection logic is gated by `if not no_judge and judged_qids:`
(line 465). `judged_qids` is declared as an empty set at line 290 and is only ever
assigned a non-empty value inside the `if not no_judge:` block (lines 292-374).
Consequently, whenever `no_judge=True` — which is the CLI's documented default
(`--no-judge/--judge`, default `True`, see `cli.py:317-323`) — the condition at
line 465 is always false, and the `else` branch at line 489 runs instead:

```python
else:
    selected_records = p_records[:20]
```

`selected_records` here is not filtered for `structured_citations` and no
`cache.get(k)`/`entry.verdict is not None` check is ever performed for it. The
records then flow straight into the worksheet-building loop (lines 491-519),
which happily writes `evidence: ""` for any record lacking citations and writes a
freshly-computed `cache_key` regardless of whether that key exists in
`judge_cache.json` or has a verdict at all.

Concretely reachable paths:
1. A user runs `lancet-eval score --run X --emit-calibration-worksheet ws.jsonl`
   without also passing `--judge` (an easy, plausible mistake since `--no-judge`
   is the default) — the emitted worksheet can contain uncited and/or never-judged
   records with no error or warning.
2. A more insidious variant: run 1 uses `--judge` and populates
   `judge_cache.json` with 30 verified entries; run 2 (e.g. a later re-score to
   just regenerate `report.json`) omits `--judge` and re-uses
   `--emit-calibration-worksheet`. The worksheet is silently rebuilt from the
   *first 20 records in journal order*, not the *verified* 20, even though a
   fully populated, verified cache sits right next to it on disk.

No test in `test_score_judged.py` exercises `score_run(..., no_judge=True,
emit_calibration_worksheet=...)`, so this path is untested as well as unguarded.
This defeats the entire purpose of the 06.3-11 fix in the code path it is most
likely to be hit through (the CLI default).

**Fix:**
Drop the `no_judge`-based branch and always apply the same cache-verified
selection (it degrades safely to an empty list when nothing has been judged),
or fail loudly instead of silently emitting an unverifiable worksheet — this file
already fails loud on comparable input problems (e.g. `score.py:401-404`,
`414-416`, `426-429`):

```python
if emit_calibration_worksheet is not None and no_judge:
    raise ScoreError(
        "--emit-calibration-worksheet requires --judge; a calibration "
        "worksheet cannot be built from unverified, unjudged records"
    )

...

if judged_qids:
    selected_records = []
    for r in p_records:
        ...
else:
    selected_records = []
```

### Warnings

#### WR-01: No test exercises "good records still get through" when errored/uncited records are mixed in the same worksheet emission

**File:** `eval/tests/test_score_judged.py`

**Issue:**
The scoping note for this review specifically asks whether the new tests exercise
"mixed cited/uncited/judge-errored records in a single judged sample." They do
not, in the way that actually pins the selector's discriminating behavior:

- `test_worksheet_rows_are_drawn_from_the_judged_subset` mixes 2 uncited + 30
  cited-successful records and asserts `len(data_rows) == 20`. All 30 candidates
  are valid, so a selector that dropped a handful of good records for the wrong
  reason would still hit the cap of 20 and pass.
- `test_worksheet_excludes_judge_errored_records` has exactly 1 record, which
  errors, and asserts `len(data_rows) == 0`. A selector that (bug) excludes
  *everything* unconditionally would also pass this test — there is no
  companion successful record in the same run to prove good records survive
  alongside the errored one.

Neither test proves the property that actually matters for this fix: **when
successful, errored, and uncited records all coexist in one run, the errored and
uncited ones are dropped while the successful ones are still emitted.** A
regression that made the selector too aggressive (e.g. accidentally excluding
records adjacent to an error, or an off-by-one in the cache-key recomputation
that causes a mismatch for otherwise-valid records) would not be caught by either
existing test.

**Fix:** Add a test with, in one run: N (e.g. 3) cited-successful records, 1
cited record that fails judging (mock a non-reusable error response ordered
*before* the reusable success response), and 1 uncited record. Assert the
emitted worksheet has exactly N rows and that neither the errored nor the
uncited `question_id` appears among them.

#### WR-02: Duplicate `(question_id, arm)` records in the journal are not de-duplicated by the selector or the judging pass

**File:** `eval/src/lancet_eval/score.py:318-374` and `466-489`

**Issue:** `Journal.append()` (`journal.py:99-104`) is a pure append with no
uniqueness check, and `run.py`'s de-duplication against `done_keys` only applies
when the caller passes `--resume` (`run.py:110-116`). Re-running `lancet-eval run`
against an existing, non-empty journal file without `--resume` appends a second
full set of `(question, arm)` records for every question. `score_run` does
nothing to collapse these: `p_records` (and therefore `judged_qids`, the main
judging loop at 318-374, and the worksheet selector at 466-489) iterate every
record, including duplicates. Two duplicate records for the same question produce
the same `cache_key` (same question/answer/evidence) and both independently pass
`entry.verdict is not None`, so:
- Both are appended to `groundedness_scores`/`faithfulness_scores`, double
  weighting that question in the `answer_groundedness`/`answer_faithfulness`
  dimension means.
- Both can be selected into the calibration worksheet (or, if only one fits under
  the 20-row cap, at least one duplicate can still occupy a slot that should have
  gone to a distinct question), and if a human grades both worksheet rows, the
  calibration ingestion loop (`score.py:432-441`) counts the same cache entry's
  agreement/MAD twice, skewing `calibration_exact_match`/`calibration_mad`.

**Fix:** De-duplicate `p_records` by `question_id` before building `judged_qids`
and before the worksheet selection loop (e.g. keep only the last record per
`question_id`, matching journal replay/resume semantics), or raise `ScoreError`
if duplicate `(question_id, arm)` pairs are detected in the journal, consistent
with this module's existing strict-validation posture (mixed index generations,
unmapped document ids, etc. all raise rather than silently proceed).

#### WR-03 (pre-existing, outside 06.3-11 scope): `primary_arm` fallback always resolves to `"graph-on"` regardless of which arm has data

**File:** `eval/src/lancet_eval/score.py:274-278`

**Issue:**
```python
if "graph-on" in arm_metrics and arm_metrics["graph-on"]["total"] > 0:
    primary_arm = "graph-on"
else:
    primary_arm = next(iter(arm_metrics.keys()))
```
`arm_metrics` is built by iterating `records_by_arm.items()`, and
`records_by_arm` is initialized as `{"graph-on": [], "graph-off": []}`
(`score.py:182`), so `arm_metrics` always has `"graph-on"` as its first key
regardless of record counts. `next(iter(arm_metrics.keys()))` in the `else`
branch therefore always evaluates to `"graph-on"` again — the fallback to
`"graph-off"` (or to whichever arm actually has data) never executes. If a
journal contains only `graph-off` records (e.g. a graph-off-only debugging run),
`primary_arm` is still `"graph-on"`, `p_data = arm_metrics["graph-on"]` is all
empty lists/zero totals, and every primary-arm-driven dimension
(`retrieval_evidence_coverage`, `context_precision_at_k`, `answer_exact_match`,
etc.) reports `status: skipped` / `n: 0` instead of scoring the graph-off data
that is actually present.

This is unrelated to plan 06.3-11 (it predates the calibration-worksheet
selector fix and sits in the arm-selection code above it) — flagging for
awareness only, not as part of this fix's diff.

**Fix:** `primary_arm = max(arm_metrics, key=lambda a: arm_metrics[a]["total"])`,
or explicitly check `arm_metrics.get("graph-off", {}).get("total", 0) > 0` before
falling back to `next(iter(...))`.

#### WR-04 (pre-existing, outside 06.3-11 scope): silent config-read failures fabricate provenance data and can mask the judge/generator safety check

**File:** `eval/src/lancet_eval/score.py:64-74`, `296-300`, `748-753`

**Issue:** `_get_engine_generation_model()` swallows every exception from reading
`config/config.toml` and returns `""`:
```python
except Exception:
    return ""
```
Two downstream consequences:
1. At lines 296-300, the safety guard that aborts when the judge model equals the
   generation model (`if gen_model and judge_model and gen_model.strip() ==
   judge_model.strip(): raise ScoreError(...)`) is silently skipped whenever the
   config read fails for *any* reason (missing file is handled explicitly and
   correctly via `cfg_path.is_file()`, but a malformed/unreadable TOML hits this
   bare `except` and disables the check without any indication to the caller).
2. At line 749, `gen_model_name = _get_engine_generation_model() or
   "deepseek/deepseek-v4-flash-0731"` — and similarly `emb_model =
   "voyageai/voyage-4-large"` at line 753 when no snapshot carries an
   `embedding_model` — write a hardcoded, possibly-wrong model name into
   `RunMetadata`, which is part of the persisted `report.json` provenance record.
   In an eval harness the report *is* the audit artifact; fabricating
   `generation_model`/`embedding_model` values when the real value is unknown is
   misleading to anyone reading the report later, with no notice recorded
   anywhere that a fallback was used.

Pre-existing, unrelated to the 06.3-11 selector fix — flagging for awareness.

**Fix:** Log or re-raise on config parse failure instead of swallowing it
silently, and record `null`/`"unknown"` (not a plausible-looking real model
name) in `RunMetadata` when the actual value cannot be determined, so a reader
of `report.json` can tell fallback data was used.

### Info

#### IN-01: Comment claims query-type stratification the code doesn't perform

**File:** `eval/src/lancet_eval/score.py:464`

**Issue:** The comment `# Select up to 20 representative items across query
types` describes stratified sampling by `question_type`, but the actual
implementation just takes the first 20 qualifying records in `p_records`
(journal) order — there is no grouping or balancing by `gold.question_type`
anywhere in the loop. This could mislead a future maintainer into believing the
calibration sample is diversified across query types when it is actually
whatever order the journal happened to record them in.

**Fix:** Either implement stratification by `question_type`, or correct the
comment to describe the actual first-N-in-order behavior.

#### IN-02: `JudgeCache` silently discards corrupted or schema-mismatched cache data

**File:** `eval/src/lancet_eval/judge.py:209-222`

**Issue:** `JudgeCache._load()` wraps the entire file read/parse in a bare
`except Exception: pass`, and wraps each entry's validation in its own
`except Exception: continue`. A corrupted `judge_cache.json` (partial write,
manual edit, schema drift after a `JudgeCacheEntry`/`JudgeVerdict` field change)
silently degrades to "cache is empty" with zero warning — the caller has no way
to know previously-paid-for judge verdicts were dropped, and re-running will
silently re-spend API calls to rebuild them (and, per the auditability comment
on the class, could also silently discard human-relevant audit history).

**Fix:** Log a warning (e.g. via `logging`/`print` to stderr) when the whole
cache fails to parse or when individual entries are dropped, so silent cost/data
loss is at least visible.
