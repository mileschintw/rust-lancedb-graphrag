## Known Issue Outside Phase Scope (flagged for visibility, not a 06.3 must-have failure)

A cross-AI code review of the diff since the last review (`06.3-REVIEW.md`, committed `82879f7`) found 1 Critical finding in `engine/src/db/mod.rs`'s `get_or_create_table` (lines 111-129, confirmed present at those lines in this session): on **any** `open_table()` error — not just "table doesn't exist" — the function silently falls through to `create_empty_table`, masking transient failures or corruption as silent data loss rather than failing closed. This function backs `documents_table`, `staged_documents_table`, `nodes_table`, `edges_table`, `entity_edges_table` — i.e. every live RAG query and every ingestion call. This landed in the same window as 06.3's gap-closure work (interleaved with an unrelated paid-model-migration Quick Task) and is on the same branch, but is not part of any 06.3 plan and is explicitly out of this phase's scope by the additive-round fence in 06.3-09/06.3-10.

An anomaly observed directly in this verification needs a root-cause hypothesis, and the more likely one is not this Critical finding: the committed run's own report shows only 16-17 of 500 questions per arm producing a valid retrieval snapshot, and only 34 of 1000 total records (3.4%, `run_traceability`) carrying any structured citations at all — the direct cause of Truth 10's thin judged sample (n=2). The **leading hypothesis** is the generation-model swap confirmed above under SC9: `deepseek/deepseek-v4-flash-0731` replaced `dots-studio/dots-3-note-preview:free` as the shipped model during this same window, and its structured-output/citation-emission behaviour against this specific prompt was never validated by an evaluation run before this one — a newly-swapped model readily stops reliably emitting `[1]`-style citations even when retrieval itself is healthy. There is a pointed irony here: SC9's drift-guard test exists precisely to catch a shipped-model mismatch, and it passed cleanly, which rules out "the pin drifted from the test" but says nothing about whether the *newly pinned* model's citation behavior was itself validated against this specific prompt template before being used for a benchmark run.

A **secondary, unproven** hypothesis is `get_or_create_table` above: if a table hit a transient `open_table()` error mid-drive, it would silently reset to empty and produce exactly this kind of "found nothing" pattern. This verification session did not inspect engine logs from the actual drive, so neither hypothesis is confirmed — the model-swap explanation is simply more likely on the evidence at hand (it directly touches citation emission; a silently-emptied table would also fail `wire_contract_conformance`, which instead reports `1.000` with 0 errors, indicating retrieval requests were completing normally, just usually without evidence). Either way, the user should see both candidate causes before shipping, independent of 06.3's own verdict.

Both gaps from the prior verification round are genuinely closed: the corpus is fully seeded (346/346, real ingestion path), and a real, byte-verifiable, git-tracked run record is committed with all required metadata including a resolvable commit SHA. All 6 CR/finding items dispositioned in 06.3-09/06.3-10 (CR-01 PostgreSQL isolation, CR-02 deadline forwarding, WR-02 matching-rule caveat, commit-SHA provenance, gateway-down remedy, resume-glob date-anchoring) are implemented in code and confirmed present by direct inspection, not merely by SUMMARY claim.

One gap remains, and it is new (not present as a distinct item in the prior round, though it is the direct mechanism behind closing Human Verification item 3 from that round): the judge-calibration slice was never actually hand-scored. The root cause is a code defect in the calibration-worksheet row selector (`score.py:464-470`), which selects rows by "was this question sampled for judging" rather than "does this row actually have a cached judge verdict to compare against." Against this run's real data — where 98% of the 100 sampled questions produced answers with zero structured citations and were therefore never sent to the judge at all — the naive first-20 slice yielded only 1 scoreable row out of 20. The executor correctly detected this via the exact check the plan specified and correctly declined to hand a human an unusable worksheet, which is the right behavior, but it leaves 06.3-06-03 permanently undischarged until the selector is fixed and the worksheet/scoring steps are re-run.

This is reported as a genuine, code-level gap rather than an operational/timing issue: no amount of "come back and try again" fixes it without a code change, because the underlying citation rate (34/1000 records) makes the current selection logic near-certain to fail the pairing check again on a re-run with the same code.

**This does not look like an intentional deviation.** The plan's own instructions anticipated exactly this failure mode and specified the correct fallback behavior (stop, don't ask a human to score unusable rows) — which is what happened — but did not anticipate that the underlying selector bug (not merely "insufficient judge quota") was the actual cause, so no override is appropriate; a small code fix plus a re-run is the correct path to closure.
