# Phase 06.3.1: Code Review Report

**Reviewed:** 2026-09-05T20:00:00Z
**Depth:** standard
**Files Reviewed:** 23

## Summary

This phase adds an additive proto surface (`NOTICE_CODE_RETRIEVAL_FAILED = 19`, `WorkflowMetadata.graph_prompt_fact_count`, `WorkflowCompletedEvent.partial_snapshot`), closes a fail-open hole in `DatabaseManager::get_or_create_table` (D-24: only recreate on `TableNotFound`, propagate every other error), adds a `GraphSpanRetainingSampler` that force-samples two named graph spans regardless of the configured ratio, and wires provenance-on-failure plus graph-influence counting end-to-end from `RetrieveHybridNode` / `AssemblePromptNode` through `WorkflowRunner::emit_terminal_once` into the gateway SSE payload (`sse.go` / `dto.go`).

I traced every new field and code path across the Rust/proto/Go boundary (proto tag numbers, generated Rust and Go structs, `notice()` string derivation, the `derive_degraded_mode` match arm, the `RetrieveHybridNode` pre-retrieval snapshot seed vs. the post-fusion overwrite, `AssemblePromptNode`'s two branches — packed-evidence vs. model-only-early-return — and the real `OpenRouterGenerator::pack_openrouter_messages` model-only branch that independently confirms graph facts never leak into the model-only prompt even though `GenerateAnswerNode` unconditionally forwards `ctx.graph_facts`). All of these are wired correctly and are consistent with the accompanying test suite (`workflow_phase5.rs` Case A/B/C graph-influence matrix, the partial-snapshot provenance test, the SSE precedence tests, and the `get_or_create_table` classifier tests). The two per-language test-count invariant scripts (`engine-test-targets.sh`, `gateway-test-targets.sh`) were re-derived by hand from the actual test files and match the committed expected totals (498 / 114).

No blocking defects were found in the shipped behavior. Three issues weaken regression protection for exactly the guarantees this phase set out to add, and one pre-existing config gap undercuts the phase's headline metric operationally; none of them describe incorrect behavior in code that runs today.

## Warnings

### WR-01: The `get_or_create_table` fail-closed regression test never executes, and the test-count gate can't tell

**File:** `engine/src/db/tests.rs:348-370`, `scripts/engine-test-targets.sh:17-19`
**Issue:** Plan 06.3.1-02's stated purpose is to close a fail-open hole where `get_or_create_table` previously recreated (and thereby wiped) a table on *any* `open_table` error, not just `TableNotFound` (D-24 — a data-loss-risk class of bug). The fix itself, in `engine/src/db/mod.rs:111-130`, is simple and I confirmed by inspection it is correct: `Err(err) if is_table_not_found(&err) => { ...create... }` vs. `Err(err) => Err(format!(...))` for everything else. However, the only test written to exercise the real `Err(err) => Err(...)` branch against a live LanceDB failure — `get_or_create_table_fails_closed_on_non_missing_table_error` — carries a blanket `#[ignore = "Windows file-locking non-determinism during on-disk directory corruption; covered by is_table_not_found_discriminates_missing_from_non_missing"]`. The `#[ignore]` attribute is unconditional (not `#[cfg_attr(windows, ignore)]`), so this test does not run on any platform in a normal `cargo test` invocation, including CI on Linux/macOS where the stated Windows file-locking non-determinism would not apply.
The referenced "coverage" (`is_table_not_found_discriminates_missing_from_non_missing`, `engine/src/db/tests.rs:311-346`) only proves the pure classifier function (`is_table_not_found`) categorizes `lancedb::Error` variants correctly. It does not exercise `get_or_create_table` itself, so the actual wiring of the fix has zero executing end-to-end regression coverage.
This is compounded by `scripts/engine-test-targets.sh`, whose header explicitly states "lowering a value to make the gate pass is never the correct response to a red gate" — but the gate counts tests via `cargo test --list`, which enumerates ignored tests in the total right alongside tests that actually run. The 488→498 invariant (10 tests added by plans 01–04) reads fully green even though only 9 of those 10 ever execute; the gate cannot distinguish "added and passing" from "added and permanently skipped" for the one code path plan 02 exists to protect.
**Fix:** Either (a) make the ignored test deterministic and runnable everywhere by injecting a fake/mock connection or a non-filesystem error instead of corrupting an on-disk Lance directory (avoids the Windows locking issue entirely), or (b) scope the `#[ignore]` to Windows only (`#[cfg_attr(windows, ignore)]`) so it at least runs on Linux/macOS CI, or (c) add a lighter-weight integration test that triggers a `Runtime`/`Io`-class error without relying on filesystem race conditions. Separately, consider having the test-count script report ignored-test counts alongside the total so a gate like this one can't go green on a permanently-skipped addition.

### WR-02: `partial_snapshot` drops variant identity at the wire, undercutting the failure-provenance goal

**File:** `gateway/internal/sse/dto.go:46-58, 81-115`, `engine/src/workflow/nodes/retrieve.rs:94-107`
**Issue:** `RetrievalSnapshot` (proto) carries 12 fields, including `variant_count` (tag 10) and `variant_identities` (tag 11). `RetrieveHybridNode::execute` deliberately populates both of these into the pre-retrieval seed snapshot (`ctx.snapshot`) before any await point specifically so that a failed/timed-out query's `partial_snapshot` is "still attributable" (D-33, the comment at `retrieve.rs:87-93`) — and query-reformulation variants are exactly the kind of provenance an operator would want when diagnosing a failed retrieval. But `RetrievalSnapshotDTO` in `dto.go` only has 10 fields; `ToRetrievalSnapshotDTO` silently drops `variant_count`/`variant_identities` with the comment "deliberately omitted to preserve the exact 10-key payload contract asserted across gateway tests." That contract predates this phase's `partial_snapshot` field and was never revisited for it: the one consumer of the new failure-provenance field (the gateway SSE client) cannot see which query variants were in flight on a failed run, even though the engine went out of its way to seed them.
No test in this phase's set exercises this gap either: `workflow_phase5_retrieve_timeout_emits_partial_snapshot_with_provenance` (`engine/src/tests/workflow_phase5.rs:6896-7012`) asserts 7 provenance discriminators and does not check `variant_count`/`variant_identities`; `TestWorkflowCompletedCarriesPartialSnapshotAndGraphInfluence` (`gateway/internal/sse/sse_test.go:598-708`) only checks `index_generation` on the Go side.
**Fix:** Decide deliberately whether variant identity belongs in the client-facing snapshot DTO. If it does (it is explicitly part of what D-33 says a failed query should be attributable to), add `VariantCount`/`VariantIdentities` to `RetrievalSnapshotDTO` and update the "exact 10-key" assertions in `gateway/main_test.go:2915-2917` and the corresponding `sse_test.go` key-set tests to 12 keys in the same commit. If it deliberately does not, document why in `dto.go` next to the existing omission comment so the next reader doesn't have to re-derive that this was a conscious call made against the new field, not an oversight carried over from before `partial_snapshot` existed.

### WR-03: `derive_degraded_mode` "11 degrading codes" enumeration test is stale after this phase added a 12th degrading code

**File:** `engine/src/tests/telemetry_query.rs:1111-1143`
**Issue:** `test_derive_degraded_mode_11_degrading_codes_return_true` enumerates 11 `NoticeCode` values and asserts each degrades the mode. `derive_degraded_mode`'s actual match arm in `engine/src/workflow/mod.rs:255-266` now has 12 degrading codes — this phase (06.3.1-01) added `NoticeCode::RetrievalFailed` to that arm — but the `telemetry_query.rs` enumeration was never updated to include it, and the test/function name ("11 degrading codes") is now inconsistent with the implementation it claims to pin down. Behavior for `RetrievalFailed` *is* separately covered by `derive_degraded_mode_includes_retrieval_failed_regardless_of_position` in `engine/src/tests/workflow_phase5.rs:6867-6894`, so this is not a functional gap — but a maintainer scanning `telemetry_query.rs` in isolation (its docstring reads as an exhaustive pinning table, mirrored by the sibling `test_derive_degraded_mode_6_non_degrading_codes_return_false`, whose 6+12=18 total does account for every `NoticeCode` variant) would reasonably believe the 11-item list is the complete degrading set and miss that a 12th code exists elsewhere.
**Fix:** Add `NoticeCode::RetrievalFailed` to the `degrading_codes` array in `test_derive_degraded_mode_11_degrading_codes_return_true` and rename the test (and its doc comment) to reflect 12 codes, e.g. `test_derive_degraded_mode_12_degrading_codes_return_true`. This keeps one authoritative, exhaustive enumeration test per notice-code addition instead of splitting coverage silently across two files.

## Info

### IN-01: `config/config.toml` doesn't set or document `graph_weight`, the exact knob this phase's headline metric depends on

**File:** `config/config.toml:62-73`
**Issue:** This is **pre-existing** and was not touched by any 06.3.1 commit — I confirmed via `git show` on all four phase commits that every change to `config/config.toml` and `config/config.example.toml` in this phase's range was comment-only (the D-17 budget-nesting documentation block), so this is not a regression introduced here. Flagging it anyway because it directly affects operability of this phase's new metric: `workflow_phase5_graph_facts_reaching_prompt_are_counted` (Case B, `workflow_phase5.rs:7101-7180`) proves `graph_weight = 0.0` is what drives `graph_prompt_fact_count` to 0 while graph presence counters (`graph_node_count`/`graph_edge_count`) stay positive — that is precisely the graph-ablation signal this phase exists to make measurable. `config/config.toml` never sets `[engine.retrieval].graph_weight` (it silently falls back to the serde default of `1.0`) and has no `[engine.graph]` section at all, while `config/config.example.toml` documents both. An operator trying to run a graph-ablation arm from `config.toml` alone has no visible knob for it.
**Fix:** Not a blocker for this phase and should not be attributed to it in any fix-up pass, but worth a follow-up: add `graph_weight` (and the `[engine.graph]` section) to `config/config.toml` with the same `# unit=...; range=...` documentation style already used in `config.example.toml`, so the two files stay in sync for every knob relevant to the ablation measurement this phase enables.
