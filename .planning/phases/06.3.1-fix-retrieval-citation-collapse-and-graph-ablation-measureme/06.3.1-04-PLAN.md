<objective>
Make a failed query attributable, and make graph contribution measurable, then close the phase's
test-count invariants.

Three things land here, all building on the proven wire path from plan 01:

1. **Provenance on failure (D-33, SC-2).** Seed the retrieval snapshot with everything known
   *before* retrieval runs, so a node killed mid-flight still reports which index generation,
   embedding model and retrieval parameters produced the failure. 966 of 1000 records in the
   recorded run carried a blank index generation and cannot be attributed to anything — an audit
   failure for a benchmark.
2. **Graph influence at prompt assembly (D-06, SC-4).** Count graph-derived facts that actually
   reached the assembled prompt, reported separately from graph presence. Without both, a
   near-zero ablation delta cannot distinguish "the graph found nothing" from "the graph found
   things the model ignored" — which is the measurement sibling 06.3.2 depends on.
3. **The phase's test-count invariants**, updated once, at the end, for all four plans.

Output: a partial snapshot on every failed terminal, a graph-influence counter on
`WorkflowMetadata`, both surfaced through the gateway SSE contract, and green invariant gates.
</objective>

<critical_findings>
1. **Why seeding the snapshot early works.** `engine/src/workflow/runner.rs:386` wraps
   `node.run(ctx, cancel)` in `tokio::time::timeout`. On expiry the node future is **dropped**,
   but `ctx` is owned by `run_workflow` and only mutably borrowed by that future — so every
   mutation applied to `ctx` **before** the drop persists and is visible to
   `emit_terminal_once`. Assigning `ctx.snapshot` at the top of the node body is therefore the
   correct and only reliable mechanism for D-33. Anything written after an await point inside
   the node is unreachable on the 904 records this exists to fix.
2. **Today's snapshot is built at the very end.** `engine/src/workflow/nodes/retrieve.rs:287-300`
   constructs `ctx.snapshot` after dense retrieval, per-variant BM25, cross-variant fusion and
   reranking have all completed — which is why a timeout leaves it `None`.
3. **The success flag is already correct; do not "fix" it.** Verified during planning:
   `run_workflow` (`runner.rs:512`) sets `overall_err` on any node `Err` and breaks, and
   `emit_terminal_once` (`runner.rs:665-676`) emits `success = false` with `final_response: None`.
   `gateway/internal/sse/sse.go:91` emits a top-level `notices` list **only** when
   `final_response` is nil, and all 904 `RetrieveHybrid`-timeout records in
   `eval/runs/2026-09-03-multihop_rag/journal.jsonl` carry one — proving they took the failure
   branch. The existing test `workflow_phase5_retrieve_timeout_ten_seconds`
   (`engine/src/tests/workflow_phase5.rs:956-1024`) already asserts `!completed_event.success`.
   **The false green came entirely from the harness** (`eval/src/lancet_eval/run.py:58` hardcodes
   `outcome="success"` for every non-exception result) — 06.3.2's D-27/D-01 work. See
   `<out_of_scope_deferrals>`. This plan pins the engine half and adds no eval-mode switch.
