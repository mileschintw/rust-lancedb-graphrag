## Phase Boundary

**What this family delivers:** a trustworthy evaluation signal, and the corrected
recorded run that Phase 6.4 documents for v1 milestone closure.

Phase 6.3's recorded MultiHop-RAG run (`eval/runs/2026-09-03-multihop_rag`) is
unusable. This family root-causes why, fixes the defects that caused it, makes
the failure mode impossible to miss again, corrects the ablation methodology, and
re-drives.

**In scope:** engine node-timeout budgets and the defects behind them; the
missing total-retrieval-failure notice; provenance on failed records; the
`get_or_create_table` fail-open; the resource-exhaustion/decay investigation and
its fix; eval-harness capture of wire diagnostics; new per-path and graph scored
dimensions; paired graph-ablation refactor; denominator convention; a preflight
canary; the four open `06.3-REVIEW.md` findings; the corrected re-drive with
human calibration; root-cause documentation.

**Out of scope:** graph-RAG *quality* work — traversal tuning, fan-out/depth
parameters, reranking, redesign. The bar for the graph is "it runs, and outright
bugs are fixed" (D-03), not "it performs well". Re-seeding the eval corpus is
also out (D-05).

## Implementation Decisions

### Diagnostics and instrumentation

- **D-01:** **Wire data is the primary diagnostic instrument.** Extend the eval
  client to persist `NodeCompletedEvent.duration_ms` and
  `WorkflowCompletedEvent.metadata` (`graph_node_count`, `graph_edge_count`,
  `vector_count`, `bm25_count`, `reformulation_used`, `degraded_mode`, token
  counts) into every journal record. The engine already emits all of it and
  `client.py:218` discards it in a single `pass` arm — this is a harness fix,
  not an engine change.
- **D-02:** **Graph-path health becomes a first-class scored dimension** in
  `report.md`, not a sidecar. `graph_ablation_delta` already sits in the report
  and is the dimension currently lying; "did the graph even run" belongs next to
  it. This widens the report contract Phase 6.4 documents.
  — **Reversibility:** costly — removing a published dimension breaks
  comparability across committed runs and forces a 6.4 docs revision.
- **D-03:** **Graph scope is "make it run + fix outright bugs".** Fix whatever
  prevents the graph path executing (budgets, genuine defects the diagnostics
  expose — unbounded traversal, missing index, per-chunk query). No tuning, no
  redesign, no new traversal strategy.
- **D-04:** **If graph traversal is inherently too slow for any sane budget,
  raise the budget and accept slow graph queries.** Set the graph budget to what
  the measured p95 needs so the arm completes; record the latency cost in 6.4's
  honest-limitations section. Do not silently ship a degraded graph.
- **D-05:** **Verify graph population before blaming query-time behavior.**
  Inspect the surviving `data/lancedb-eval/` store — node/edge/entity_edge
  counts, degree distribution, a hand-run traversal from a known entity — using
  the existing `engine/src/bin/inspect_lancedb.rs`. Re-seeding is NOT in scope.
- **D-06:** **"Graph contributed" is measured as presence AND influence,
  reported separately.** Presence = `graph_node_count`/`graph_edge_count` > 0
  (already populated at `graph_context.rs:127-148`). Influence = graph-derived
  context actually landed in the assembled prompt — needs a new counter at
  `AssemblePrompt`. Without both, a zero delta cannot distinguish "graph found
  nothing" from "graph found things the model ignored".
- **D-07:** **Retention: raw SSE stream on failures plus a sampled subset.** Full
  raw events for any query with non-empty `node_failures`, plus a fixed sample of
  successes as baseline. Bounded committed-artifact size; failures are where
  forensics goes.
- **D-08:** **OTel span retention is turned on for the graph node specifically.**
  Refines, does not reverse, D-01: wire capture remains primary for all queries;
  graph-path spans are retained additionally so Phase 6's existing Cypher-level
  instrumentation (`graph_traversal` span, `service.rs:475`) becomes usable.
- **D-09:** **Instrumentation covers vector, BM25 and graph symmetrically.**
  `vector_count`/`bm25_count` are already in `WorkflowMetadata`, so per-path
  yield and latency is nearly free. Without symmetry a near-zero ablation delta
  cannot distinguish "graph adds nothing" from "the baseline arm is equally
  broken" — which is exactly what happened.

### Guards

- **D-10:** **The preflight gains query-path checks.** The existing preflight
  (store isolation, gateway/engine reachable, corpus generation, OpenRouter,
  model differentiation) passed clean on a fully dead run because none of its
  checks touch retrieval. Add checks that probe the query path so it fails loud.
  A mid-run abort threshold was considered and **not** selected.
- **D-11:** **The preflight check runs a committed canary set with fixed
  expectations** — corpus questions checked into the repo with known-good floors
  (each returns >= 1 retrieved chunk; graph-on returns >= 1 graph node; per-node
  duration under budget). Deterministic, reviewable, diffable.
- **D-12:** **The canary is also what locks the timeout fix in.** No config-value
  floor test and no node-timeout behavior test — the canary fails loud on a dead
  query path for any reason, testing the symptom rather than a proxy.

### Timeout budgets

- **D-13:** **Corrected budgets land in production `config/config.toml`.**
  `config.eval.toml` overrides only `lancedb_path`, so the budgets that broke the
  run are production defaults. An eval-only overlay would mean benchmarking a
  configuration nobody runs.
  — **Reversibility:** costly — changes shipped production defaults that Phase 6
  stabilised and that 6.4 documents.
- **D-14:** **Budgets are derived from measured p95/p99 with a stated
  multiplier**, not guessed. Sequences the fix behind instrumentation and gives
  6.4 a defensible number.
- **D-15:** **All six budgets are re-derived together** — `query_embedding`,
  `retrieve`, `graph_operation`, `graph_node`, `prompt`, `generation_node`. The
  measurement pass produces latency for every node anyway; no un-examined budget
  is left to fire during the re-drive.
- **D-16:** **A blown budget is investigated as a bug before it is widened.**
  `AssemblePrompt` exceeding 2s, or retrieve latency scaling with candidate
  count, points at a defect rather than a tight budget.
- **D-17:** **Budget nesting is documented, not enforced.** Record in
  `config.toml`/`config.example.toml` which budgets nest inside which. Known
  incoherence to document: `graph_operation_timeout_ms = 4000` nests inside
  `graph_node_timeout_ms = 15000`, so the outer budget can never fire. Startup
  validation was considered and **not** selected.

### The decay signature (see `<code_context>` for the evidence)

- **D-18:** **Budgets and resource exhaustion are both live hypotheses; the
  measurement pass is the discriminator.** Flat-but-high latency => budgets.
  Latency climbing with query ordinal => exhaustion.
- **D-19:** **"Decay confirmed" means retrieval latency trends upward with query
  ordinal** — a statistically clear positive slope, or a late-window p95
  materially above the early-window p95. Measures the phenomenon directly and
  works even when no query times out at raised budgets.
- **D-20:** **The measurement pass drives full end-to-end queries against a cheap
  generation model.** Preserves real concurrency and connection behavior at a
  fraction of the spend. Consequence: generation latency from this pass is **not**
  usable for setting `generation_node_timeout_ms`. No judge is involved, so the
  model-differentiation preflight does not constrain the model choice.
- **D-21:** **The measurement pass includes a mid-run engine restart.** Latency
  resetting to baseline => process state (leaked handles, connection pool,
  memory). Staying elevated => accumulated store state (checkpoint growth per
  D-58, LanceDB versions/fragments). Two segments; a third checkpoint-truncation
  segment was considered and not selected.
- **D-22:** **The pass starts from the store as-is**, reproducing the original
  conditions — the surviving `data/lancedb-eval/` and the existing PostgreSQL
  eval-schema checkpoint rows. Record starting row counts so the baseline is
  interpretable. No re-seed, no checkpoint truncation.
- **D-23:** **The decay fix stays in this family's scope.** *(Supersedes an
  earlier decision in this same discussion that routed it to a conditional
  inserted phase and held 06.3.1 open until that landed — see D-46, which
  replaces that arrangement with a deliberate four-way split.)* The measurement
  pass still discriminates budgets from decay; it no longer decides which phase
  the fix lands in.

### `get_or_create_table` fail-open

- **D-24:** **Fix to the ROADMAP's shape: fail closed on every `open_table`
  error except `lancedb::Error::TableNotFound`,** propagate the rest, plus a
  regression test. Post-create `validate_schema` and removing lazy creation from
  the accessor path were both considered and **not** selected.
  — **Reversibility:** reversible — contained to one function.
- **D-25:** **Correction to the ROADMAP text:** the function backs **six**
  accessors, not five — `documents`, `staged_documents_v2`, `nodes`, `edges`,
  `entities`, `entity_edges`.
- **D-26:** **This defect is exonerated as the cause of the 2026-09-03 collapse**
  but stays in scope as a genuine latent data-loss risk on the hot path. It is
  fixed here, not dropped.

### Failure visibility

- **D-27:** **The false-green is fixed in both the engine and the harness.**
  Engine: a workflow with a hard node failure that produced no evidence should
  not read as healthy. Harness: the client holds `node_failures` at the moment it
  decides and must not trust the flag blindly. Defence in depth.
- **D-28:** **A new notice code is added at the free tag** (e.g.
  `NOTICE_CODE_RETRIEVAL_FAILED = 19`), emitted when the retrieval node *fails*
  rather than completes, and included in `derive_degraded_mode`. Keeps "found
  nothing" (`NO_EVIDENCE`, a designed outcome) semantically distinct from "died
  trying". Additive tag, the kind D-76 anticipated.
  — **Reversibility:** one-way — a published proto enum value cannot be reused or
  withdrawn once clients observe it; it also enters 6.4's documented notice
  vocabulary (SC 5).
- **D-29:** **`success = false` on total failure — but only for the non-graph
  path, and only in eval/test.** **Graph failure of any kind — timeout,
  unavailable, `NoMatchFound` — stays a non-fatal degradation** with a notice and
  `degraded_mode = true`.

  **Predicate — implement it as the node-failure condition, NOT as a conjunction
  of the per-path notices.** The trigger is: `RetrieveHybrid` failed (D-28's new
  notice present / non-empty `node_failures` for that node) **and** no snapshot
  was produced. It is **not** "`RETRIEVAL_DEGRADED_DENSE` and
  `RETRIEVAL_DEGRADED_BM25` both present" — those two notices are emitted *inside*
  `retrieve.rs` at the end of `run`, exactly like `NO_EVIDENCE` (:305), so they
  never fire on a node timeout. Implementing the conjunction would silently
  reproduce the original bug: the condition would evaluate false on precisely the
  966 records it must catch.
  **Rationale (mechanism, not caution):** vector/BM25 are ranking operations — over
  a non-empty index there is always a nearest neighbour, so zero results means
  broken. Graph traversal is conditional: `GraphAugmentationOutcome::NoMatchFound`
  (`service.rs:487`) is a first-class designed outcome, and a query whose entities
  were never extracted legitimately returns nothing. Zero graph results does not
  imply a broken graph, and requiring otherwise would mark healthy production
  queries as failures.
- **D-30:** **The stricter `success = false` semantics are scoped to eval/test.**
  Production keeps current semantics; the shipped API contract Phase 6 stabilised
  is not broken this close to v1 closure.
- **D-31:** **A canary-only conditional graph guarantee.** The committed canary
  set carries hand-picked questions whose entities are *known* to be in the graph;
  those must return facts or preflight fails. A real graph regression guard that
  never asserts the graph must return something for arbitrary queries.
- **D-32:** **MultiHop-RAG carries a corpus-scoped expectation with a provisional
  floor.** The corpus is constructed so answering requires linking facts across
  documents, so widespread `NoMatchFound` on *this corpus* is a defect signal,
  not background noise. Measure and publish graph yield / `NoMatchFound` rate,
  and state a provisional floor which, if missed, triggers investigation before
  results are published in 6.4. Note: the broken run gave 494 `GRAPH_TIMEOUT` and
  only 4 `GRAPH_UNAVAILABLE`, so **the true `NoMatchFound` rate is currently
  unknown** — the corrected run establishes it for the first time.
- **D-33:** **A failed retrieval still emits a partial snapshot** — the
  provenance known before retrieval runs (`index_generation`, `embedding_model`,
  weights, `rrf_k`, candidate/final limits, active filter) with an empty chunk
  list. 966 records currently carry `index_generation: ""` and are unattributable
  to any index generation, which is an audit failure for a benchmark.
- **D-34:** **Infrastructure-failed records are excluded from all denominators
  and reported separately**, with an explicit unusable-record count and rate.
  Makes the convention consistent: the run already excluded snapshot-less records
  from *retrieval* denominators (caveat 6, hence `n=16`) while *answer*
  dimensions counted them as zeros — which is what produced the headline
  `answer_exact_match = 0.000`.
- **D-35:** **`wire_contract_conformance` is redefined to include
  self-contradiction checks.** A response claiming success while carrying a hard
  node failure, a null snapshot and an empty answer *is* a contract violation —
  the contract is not just field shapes but that the fields agree. It would have
  read 0.034 instead of 1.000.
  — **Reversibility:** costly — redefines a published dimension; the
  2026-09-03 value becomes non-comparable and 6.4's methodology must say so.
- **D-36:** **All four open `06.3-REVIEW.md` findings close before the
  re-drive:** CR-01 (calibration-worksheet verification bypassed on the
  `no_judge=True` CLI default), WR-02 (duplicate journal records never
  de-duplicated), WR-03 (`primary_arm` always resolves to `graph-on`; the
  `next(iter(...))` fallback is unreachable), WR-04 + IN-02 (silent config-read
  and judge-cache failures that fabricate provenance and discard paid verdicts).

### Ablation pairing

- **D-37:** **Unpaired questions are dropped and pairing coverage is reported
  explicitly** next to the delta. Consistent with D-34: an unpaired question
  usually means one arm's retrieval died, which measures the environment, not
  graph capability. Low coverage then visibly discredits the delta instead of
  hiding inside it.
- **D-38:** **The delta is always reported, with a paired confidence interval** —
  no minimum-pair-count suppression. A wide interval is the signal.
- **D-39:** **Pairing covers recall plus the deterministic answer metrics** —
  `retrieval_evidence_coverage` (as the ROADMAP specifies) and additionally exact
  match, F1, context precision and ranking quality. No extra API spend; answers
  "does the graph change the answer", not only "does it change what was
  retrieved". Judged dimensions are **not** paired (would double judged spend).
- **D-40:** **The delta is stratified by gold `question_type` and reported in
  aggregate.** This is the measurement that tests the graph's premise: on a
  multi-hop corpus the graph should help most on types requiring traversal. An
  aggregate near zero could be hiding a real effect on the subset that matters.
  (`question_type` exists in gold data and is currently unused — review finding
  IN-01.)
- **D-41:** **Arm adjacency is documented, not enforced.** Verified in the
  recorded run: a question's two arms ran a median of 1 position apart (max 9)
  for all 500 questions, so D-47's interleaved design already protects pairing
  from drift — and this is a second argument for paired comparison, since both
  arms of a pair experience near-identical system state and the delta is
  therefore robust to the decay. Runtime enforcement was considered and not
  selected.
- **D-42:** **The ablation reports cost alongside benefit: paired latency delta
  and paired prompt-token delta** next to the quality deltas. Turns "does the
  graph help" into "what does the graph cost for what it gives" — the actual v1
  decision, and direct input to 6.4's honest-limitations section. Both are nearly
  free given D-01. Note the arms differ structurally in cost: graph-off
  early-returns at `graph_context.rs:96` before the graph query, so it never pays
  the graph budget that graph-on does.
- **D-43:** **`graph_ablation_delta` is redefined in place, and the 2026-09-03
  value is marked non-comparable.** Same dimension name, paired computation, with
  an explicit statement in the methodology and in 6.4's docs that the old `0.010`
  must not be cited.

- **D-45:** **The 2026-09-03 run is kept, marked superseded, and cited as
  evidence.** The corrected drive gets a new dated run directory. Every number in

  6.4's narrative unsupported.
- **D-46:** **Phase 06.3.1 is split into four sibling phases before planning,
  sharing this CONTEXT.md** (the D-77 pattern). *(This supersedes the earlier
  arrangement of a single conditional 06.3.2 carved off for decay — the split is
  now a deliberate decomposition of the whole phase, cut along the dependency
  graph.)* Proposed seams for `/gsd-phase`:
  1. **Engine & config** — new notice code, partial snapshot on failure,
     eval-scoped success semantics, graph-influence counter at `AssemblePrompt`,
     `get_or_create_table` fail-closed, proto regeneration in both trees +

  2. **Harness** — wire capture, raw-stream retention, new per-path and graph

  **Seam-1 assignments not obvious from the list above:** D-08 (OTel graph-span
  retention) belongs to seam 1 alongside the other engine/telemetry work.
  **D-50** (register the new evaluation-fidelity requirement, and replace this

  **Back-edge — resolve it forward, never by reopening a closed sibling.** Seam 1
  closes before seam 3 runs, yet three decisions send work backwards: D-16

  "the diagnostics expose"), and D-13/D-14 (the corrected budget *values* land in

- **D-47:** **Spend is bounded by per-stage caps, with no overall phase ceiling.**
  Each stage (measurement pass, staged drive, full drive, judging) is capped

- **D-48:** **Fresh human calibration, explicitly sized to what the user will

- **D-49:** **If the corrected paired comparison shows the graph makes things

## Existing Code Insights

### The forensic findings (from `journal.jsonl`, 1000 records)

**Retrieval collapse, not citation collapse.** The ROADMAP's framing — "root-cause
the near-zero structured-citation rate" — describes a symptom two layers down from
the cause, and its hypothesis (generation-model swap / prompting) is wrong.

| Signal | graph-on | graph-off |
|---|---|---|
| Records | 500 | 500 |
| `outcome: "success"` | 500 | 500 |
| Non-null retrieval snapshot | 16 | 18 |
| Non-empty citations | 16 | 18 |
| Empty answer string | 484 | 482 |

The set of records with retrieved chunks and the set with citations are
**identical** — verified as set equality, not just equal counts (34 = 34, both
differences empty). `run_traceability = 0.034` is a perfect mirror of retrieval
success.

**Cause, from `node_failures` — which the harness records and no dimension reads:**

```
 904  RetrieveHybrid       kind=1 retryable=False  Node 'RetrieveHybrid' timed out
  47  AssemblePrompt       kind=1 retryable=False  Node 'AssemblePrompt' timed out
   6  ExtractGraphContext  kind=1 retryable=False  Query embedding timed out
   9  GenerateAnswer       kind=3 (basis / schema errors)
```

Timeouts bound the *node*, not the query: the workflow continues past the dead
node through AssemblePrompt and GenerateAnswer and returns empty — which is why
failures show a 14.6s median while successes (retrieval completed, generation ran
on real evidence) show 19.8s.

**The decay signature** — successes by journal position:

| Range | Successes |
|---|---|
| 1–11 | 10 |
| 12–200 | 13 |
| 201–500 | 4 |
| 501–564 | 3 |
| **565–1000** | **0** |

Monotonic decay to zero, then 436 consecutive failures. Records 12–1000 ran in a
single process after the `--resume`, so degradation occurred *within* one process
lifetime. A uniformly-too-tight budget would fail uniformly from query 1. This is
why D-18 keeps both hypotheses live.

**Graph arm, fully broken down:** 494/500 timed out at
`graph_operation_timeout_ms = 4000` (not the 15s node budget), 4 returned
`GRAPH_UNAVAILABLE`, leaving ~2 queries where the graph returned any facts.
Graph timeout is non-fatal and degrades correctly, so **the graph is not what
caused the empty answers** — `RetrieveHybrid` is. Two independent defects that
co-occurred.

**No retrieval notice was emitted anywhere in 1000 records** despite 904
`RetrieveHybrid` failures. Only `GRAPH_ABLATION` (496), `GRAPH_TIMEOUT` (494),
`MODEL_NOTICE` (41), `MODEL_WARNING` (34) and `GRAPH_UNAVAILABLE` (4) appear.

**Ablation disjointness:** the reported `graph_ablation_delta = 0.010` at "n=33"
came from 16 graph-on and 18 graph-off scores sharing only **8 questions** — 8
graph-on and 10 graph-off scores had no counterpart at all. Under proper pairing,
the entire 500 x 2 drive supports **8 pairs (1.6% coverage)**.

**Arm interleaving is healthy:** all 500 questions had their two arms a median of
1 journal position apart (max 9). D-47's design works; this protects paired
comparison from the decay (D-41).

**False greens produced by the above:** `wire_contract_conformance = 1.000`
(counts explicit errors; every record said success with a null error),
`answer_exact_match = 0.000` and `answer_f1 = 0.001` (empty answers scored as
zeros in answer denominators while retrieval denominators excluded them).
