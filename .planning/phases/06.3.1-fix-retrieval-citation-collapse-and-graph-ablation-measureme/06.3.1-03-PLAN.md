<objective>
Make the graph path legible in two independent ways that need no measurement to land:

1. **Retain the graph span (D-08, SC-6).** Phase 6 already instruments the Cypher-level
   `graph_traversal` span with node/edge counts, but it is subject to the global sampling ratio
   like everything else. Retain graph spans specifically so that instrumentation becomes usable
   for 06.3.3's investigation without raising the global ratio for the whole service.
2. **Document budget nesting (D-17, SC-8).** Record in both operator-facing TOML files which
   budgets nest inside which, and the known incoherence that
   `graph_operation_timeout_ms = 4000` sits inside `graph_node_timeout_ms = 15000` so the outer
   budget can never fire for the graph operation.

Purpose: 494 of 500 graph-arm queries in the recorded run died at the inner 4000 ms budget while
the outer 15000 ms budget sat unused and unexplained, and nobody could read the Cypher spans to
see why.

Output: a composite sampler that retains graph spans regardless of the configured ratio, a unit
test proving retention under an off sampler, and a nesting comment block in both TOML files.

**Values are documented, never changed.** Sibling 06.3.3 derives all six budget values.
</objective>

<critical_findings>
1. **The mechanism for D-08 is the planner's to choose; this plan chooses a composite sampler.**
   `06.3.1-PATTERNS.md:539` reports no analog and suggests deferring or asking the user.
   CONTEXT.md leaves the mechanism to downstream judgment (the policy — graph spans retained
   additionally, wire capture stays primary — is what is locked). **Do not defer it.**
2. **The `ShouldSample` trait is the seam.** `opentelemetry_sdk 0.32.1`
   (`src/trace/sampler.rs:88`) declares
   `pub trait ShouldSample: CloneShouldSample + Send + Sync + std::fmt::Debug`, with
   `fn should_sample(&self, parent_context: Option<&Context>, trace_id: TraceId, name: &str, span_kind: &SpanKind, attributes: &[KeyValue], links: &[Link]) -> SamplingResult`.
   `SdkTracerProvider::builder().with_sampler` (`src/trace/provider.rs:375`) accepts
   `impl Into<Box<dyn ShouldSample>>`, and `impl<T: ShouldSample + 'static> From<T> for Box<dyn ShouldSample>`
   exists — so a custom type is accepted directly. `CloneShouldSample` is satisfied by deriving
   `Clone`. The custom sampler therefore needs `#[derive(Clone, Debug)]`.
3. **Today's default is already always-on.** `engine/src/telemetry/mod.rs:195-201` maps
   `sampler_ratio >= 1.0` to `Sampler::AlwaysOn`, and `config/config.toml` ships `1.0`. The
   retention wrapper is therefore a **no-op at the shipped default** and only takes effect when
   an operator lowers the ratio. Say so in the doc comment; it is the reason the change is safe.
4. **`config/config.example.toml` is guarded by a strict adjacency test.**
   `engine/src/tests.rs:230-315` (`config_example_matches_effective_rag_contract`) asserts that
   for every key in `[engine.workflow]` the **immediately preceding line** is a comment
   containing that key's exact annotation marker (`unit=milliseconds; range=>0`), and that the
   section contains **exactly** the documented key set. A multi-line block inserted directly
   above a key breaks this test. Place the D-17 block **immediately after the
   `[engine.workflow]` section header and before the first key's annotation comment.**
5. **`config/config.verify.toml` is pinned by exact-value string assertions**
   (`engine/src/tests.rs` around line 350: `graph_operation_timeout_ms = 4000`,
   `graph_node_timeout_ms = 15000`, `generation_node_timeout_ms = 7000`, and others). Do not
   touch it. `config/config.eval.toml` is likewise out of scope here.
6. **The nesting facts, verified from source:**
   - Runner-level (top-level) budgets, applied by `WorkflowRunner::timeout_for_kind`
     (`engine/src/workflow/runner.rs:298-306`): `reformulate_timeout_ms`,
     `graph_node_timeout_ms`, `retrieve_timeout_ms`, `prompt_timeout_ms`,
     `generation_node_timeout_ms`.
   - Inner budgets, applied inside `ExtractGraphContextNode::run`:
     `query_embedding_timeout_ms` at `engine/src/workflow/nodes/graph_context.rs:78`, and
     `graph_operation_timeout_ms` at `:117`. **Both nest inside `graph_node_timeout_ms`.**
   - `10000 + 4000 = 14000 < 15000`, so the outer graph-node budget can only fire in the narrow
     residual window, never for the graph operation itself. An existing assertion in
     `engine/src/tests.rs` already encodes this inequality; D-17 asks for it in prose where an
     operator will read it.
   - The inner graph-operation expiry is **non-fatal** (`graph_context.rs:162-188` emits
     `GRAPH_TIMEOUT` and returns `Ok`), which is why 494 records showed a graph timeout and none
     showed a graph-node timeout.
</critical_findings>
