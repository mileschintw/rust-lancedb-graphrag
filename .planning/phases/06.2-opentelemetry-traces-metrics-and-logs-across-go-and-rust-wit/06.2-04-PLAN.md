<objective>
Extend the proven span mechanism to the ingestion path: one trace per document from upload through graph extraction, carried across the ingestion queue, plus an observable `index_rebuild` span linked to the documents that triggered it.

Purpose: SC3 of the phase, and the thing that makes Phase 6.1's debounced rebuild-and-swap visible. Today the two most interesting ingestion behaviours — that graph extraction happens after the document span has already closed, and that a burst of documents coalesces into one rebuild — are invisible.
Output: a document-scoped ingest span with the existing stage spans nested inside it, a graph-extraction span with a leaf span at every real external call it makes (per LLM attempt, graph read, entity-name embedding, graph write), queue-crossing trace context, and a linked rebuild span.
</objective>

<scope_rationale>
Three tasks split at the real seams in this work: the synchronous document path (admission through graph extraction, one trace, context carried across a channel), the asynchronous coalesced rebuild (a many-to-one relationship that needs links rather than parenting), and the leaf spans at the external calls graph extraction itself makes (a different file, `engine/src/graph/extraction.rs`, and a different failure mode — an unattached leaf rather than a mis-parented trunk). Task 3 runs last because its leaves parent to the `graph_extraction` span Task 1 creates and because it owns the plan's test-count re-pin. Wave 3 because it edits `engine/src/service.rs`, which Plan 02 owns in wave 2, and `engine/src/ingest.rs`, which Plan 05 will extend in wave 4; `engine/src/graph/extraction.rs` is owned by no other plan in this phase.

Estimate note, stated rather than left for a checker to flag: at 135k this plan's projection sits above the smart-zone target, and that is a deliberate, acknowledged choice rather than an oversight. The number is carried almost entirely by Tasks 1 and 2, which were already 105k for two tasks before this round — Task 1's worker-branch restructure and Task 2's fifteen-call-site signature change are the expensive work. Task 3's marginal cost is small: four additive spans wrapped around awaits that already exist, five tests, no signature changes, no control-flow changes, and one file (`engine/src/graph/extraction.rs`) that no other task in the phase touches. Re-slicing Task 3 into its own plan was considered and rejected: its leaves must parent to the `graph_extraction` span Task 1 creates, so a separate plan would inherit a hard dependency on this one and land in wave 4 or 5 alongside Plan 05's `engine/src/ingest.rs` edits — trading an advisory size warning for a real file-ownership conflict and a seventh plan whose only content is four spans. Keeping the work where its dependency already lives is the better trade; the executor should expect a long plan, not a surprising one.
</scope_rationale>
