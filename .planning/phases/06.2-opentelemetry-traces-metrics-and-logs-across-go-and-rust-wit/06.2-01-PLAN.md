## Phase User Story

**As a** developer running and demoing Lancet, **I want to** follow one real RAG query as a single correlated trace, metric and log across the Go gateway and the Rust engine, **so that** I can explain and diagnose the system's behaviour instead of inferring it from prose.

<objective>
Land the telemetry foundation as one production-quality end-to-end slice: a single W3C trace identity crossing HTTP → gRPC → the Rust workflow, all three signal providers in both services, one real metric, one real correlated log site, fail-closed telemetry configuration, and a Collector the whole thing actually exports to.

Purpose: this is the tracer. Every later plan in Phase 6.2 expands a mechanism proven here rather than introducing one. The three architecturally risky seams — the tonic parent installation (RESEARCH Pitfall 4), the `otelzap` request-context seam (RESEARCH Pitfall 5 / assumption A4), and the false-Collector-fallback trap (RESEARCH Pitfall 3) — are all resolved in this plan, on the agent's best early-context tokens.
Output: `engine/src/telemetry/*`, a real `gateway/internal/telemetry` package, telemetry configuration in both services, a committed Collector config, an `observability` Compose profile, and updated count gates.
</objective>

`telemetry/mod.rs` also owns the process's ONE subscriber registry composition, layering: the existing `tracing_subscriber::fmt` layer (unconditional, so console output never depends on OTLP health), the `tracing_opentelemetry` layer bound to a tracer from the tracer provider, and the `OpenTelemetryTracingBridge` layer bound to the logger provider.
