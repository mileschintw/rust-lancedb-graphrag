# Phase 06.2: Code Review Report

**Reviewed:** 2026-08-24T00:00:00Z
**Depth:** standard
**Files Reviewed:** 46
**Status:** issues_found

## Summary

Phase 06.2 wires OpenTelemetry traces, metrics, and logs across the Go gateway and Rust engine: SDK init, W3C propagation, node/leaf span instrumentation, Prometheus/Loki/Grafana deploy scaffolding, ingestion span binding + rebuild-link buffering, operational metrics, and log/degraded-mode correlation. The bulk of the instrumentation code (span creation, field recording, metric emission) is consistent, well-tested, and follows the bounded-cardinality discipline the project documents in `metrics.rs`.

However, the review surfaced four BLOCKER-level defects that undermine the very observability guarantees this phase exists to deliver: two span attributes report a hardcoded (and in one case simply *wrong*) model name instead of the actually-configured model; the OTel Collector's Prometheus exporter config will silently double-prefix every metric name so none of the shipped Grafana dashboard queries or the checked-in Prometheus scrape config will ever return data; the Go gateway accepts and validates `https://` OTLP endpoints but the exporter always forces plaintext (`insecure`) transport, so a configured "https" endpoint is *not honored* — telemetry travels in cleartext regardless of intent; and a 3.3MB compiled Windows executable (`dashboard_gen.exe`) was committed directly into version control and is not referenced by any script or CI step.

Additional warnings cover a dead/vestigial state variable in the gateway's per-request span-status logic, a fragile string-sniffing approach to classifying retrieval failure kind for metrics, incomplete test isolation around shared global rebuild-fault-injection state, hardcoded default Grafana admin credentials in `docker-compose.yml`, span-name cardinality from unbounded URL paths in `otelhttp`, and a startup path where the telemetry handle is never flushed on early-return error exits.

## Critical Issues

### CR-01: `dashboard_gen.exe` is a committed compiled binary, unused by any script or CI step

**File:** `deploy/grafana/dashboard_gen/dashboard_gen.exe`
**Issue:** This is a 3.3MB PE32+ Windows console executable committed directly to the git blob store (confirmed via `git cat-file -t/-s`, `file`), introduced in commit `1dda665` ("feat(observability): provision prometheus, loki, grafana and typed operations dashboard (06.2-03)"). It is not covered by `.gitignore` (only `gateway/gateway.exe` and `/bin/` are ignored). The phase's own regeneration gate, `scripts/generate-dashboards.sh`, invokes `go run main.go -output ...` — it never builds or calls this `.exe`. A `grep` across the repository confirms nothing references `dashboard_gen.exe` by name. This is a stray local build artifact that should never have been staged: it bloats the repository, is platform-specific (useless on Linux/macOS CI runners and to any contributor not on Windows), and its committed bytes will silently rot out of sync with `main.go` since nothing regenerates or verifies it.
**Fix:**
```
git rm deploy/grafana/dashboard_gen/dashboard_gen.exe
```
Add to `.gitignore`:
```
deploy/grafana/dashboard_gen/*.exe
deploy/grafana/dashboard_gen/dashboard_gen
```

### CR-02: OTel Collector's Prometheus `namespace: lancet` double-prefixes every metric name, breaking every dashboard query and the Prometheus scrape contract

**File:** `deploy/collector/otel-collector-config.yaml:27-29`
**Issue:** The Prometheus exporter is configured with `namespace: lancet`. The `prometheusexporter` component in `otelcol-contrib` prepends `<namespace>_` to every already-sanitized metric name (dots → underscores). All of the engine's metric names already begin with the `lancet.` prefix (e.g. `lancet.rag.query.duration`, `lancet.ingest.documents`, `lancet.index.rebuild.duration` — see `engine/src/telemetry/metrics.rs`), which sanitizes to `lancet_rag_query_duration`, `lancet_ingest_documents`, etc. Applying the collector's `namespace: lancet` on top of that yields `lancet_lancet_rag_query_duration_ms_count`, `lancet_lancet_ingest_documents_total`, and so on for every single metric emitted by the engine and gateway.

Every panel query in `deploy/grafana/dashboards/lancet-rag-operations.json` / `deploy/grafana/dashboard_gen/main.go` (e.g. `sum by (outcome) (rate(lancet_rag_query_duration_ms_count[5m]))`, `lancet_index_corpus_generation`) targets the single-prefixed name and will therefore never match anything scraped through the collector — every dashboard panel will render "No data" against a live stack. The `prometheus.yml` scrape job (`targets: ["collector:8889"]`) scrapes exactly the endpoint the double-prefixing applies to, so this is not a test-only concern; it will reproduce in the docker-compose observability profile exactly as shipped.
**Fix:** Remove the collector-level namespace (the metric names are already namespaced at the source):
```yaml
exporters:
  prometheus:
    endpoint: 0.0.0.0:8889
    # namespace: lancet   <- remove; metric names already carry the lancet. prefix
```
Then verify end-to-end against a live collector (`docker compose --profile observability up`, curl `collector:8889/metrics`) that the exported names match the dashboard/scrape expectations before merging.

### CR-03: `gen_ai.request.model` span attributes are hardcoded and diverge from the actually-configured model

**File:** `engine/src/service.rs:431`, `engine/src/workflow/nodes/generate.rs:122`, `engine/src/workflow/nodes/generate.rs:178`
**Issue:** Three span-attribute sites hardcode a literal model name instead of reading the actually configured model:
- `service.rs:431` (`ProductionEmbeddingPort::embed_variant_zero`) sets `gen_ai.request.model = "nvidia/llama-nemotron-embed-vl-1b-v2:free"` as a string literal, even though `self.embedder: Arc<dyn EmbeddingProvider>` exposes `.model_id()` (see `client/mod.rs:190`, which returns the real configured `embedding_model`). The sibling code path in `engine/src/ingest.rs:1143` gets this right: `gen_ai.request.model = %embedder.model_id()`. If an operator overrides `embedding_model` via config or `LANCET_OPENROUTER__EMBEDDING_MODEL`, every `embedding_request` span will report the wrong model.
- `generate.rs:122` and `generate.rs:178` (both `llm_attempt` spans, attempt 1 and attempt 2) hardcode `gen_ai.request.model = "google/gemini-2.5-flash"`. This value does not match *any* configured default anywhere in the repo — `config.example.toml`'s default is `openai/gpt-4o-mini` and `config.toml`'s dev default is `dots-studio/dots-3-note-preview:free`. `GenerateAnswerNode` (see struct definition, `generate.rs:14-20`) never stores a model name at all, and the `Generator` trait (`engine/src/generation/mod.rs:563`) exposes no `model_id()`-style accessor for the node to use. This means the `llm_attempt` span attribute is wrong on every single generation call, in every environment, regardless of configuration — not merely an edge case triggered by an override.

This directly undermines the phase's own stated purpose (D-43 resource/attribute accuracy) — anyone using traces to attribute cost or latency by model, or routing APM alerts by `gen_ai.request.model`, will get systematically incorrect data. The existing test (`engine/src/tests/telemetry_query.rs:608`, `leaf_span_embedding_request_wraps_real_http_call`) only asserts the attribute is *present*, not that its value matches the configured model, so this gap is not caught by the test suite.
**Fix:** Thread the actual configured model into the span. For the embedding span:
```rust
// service.rs, ProductionEmbeddingPort::embed_variant_zero
let span = tracing::info_span!(
    "embedding_request",
    gen_ai.request.model = %self.embedder.model_id(),
);
```
For generation, either add a `model_id()`-style method to the `Generator` trait (mirroring `EmbeddingProvider::model_id()`) or store the configured `generation_model` string on `GenerateAnswerNode` via `with_settings`, and use it in place of the literal in both `llm_attempt` spans.

### CR-04: Gateway OTLP exporter always forces insecure (plaintext) transport, silently ignoring `https://`-configured endpoints

**File:** `gateway/internal/telemetry/telemetry.go:115-124,151-154,171-174`; contrast with `gateway/internal/config/config.go:100-106`
**Issue:** `config.go`'s `Load()` validates `gateway.telemetry.otlp_endpoint` as an "absolute http or https URL" (`u.Scheme != "http" && u.Scheme != "https"` fails validation) — implying `https://` is a legitimately supported, TLS-secured configuration. But `telemetry.Init()` unconditionally strips *both* `http://` and `https://` prefixes from the endpoint and then calls `otlptracegrpc.WithInsecure()` / `otlpmetricgrpc.WithInsecure()` / `otlploggrpc.WithInsecure()` on every exporter, with no branch that ever uses TLS credentials. A operator who configures `otlp_endpoint = "https://collector.example.com:4317"` expecting an encrypted channel to a remote collector will instead have the gateway attempt (and typically fail, or — if the collector tolerates plaintext on that port — silently succeed) a plaintext gRPC connection. Either the intended TLS protection never actually applies (telemetry, including trace/log content that may carry query text, session IDs, and correlation IDs, travels in cleartext), or the export simply fails silently (per the `Init()` doc comment, `Init` "never returns an error" and only logs a bounded startup warning if *exporter construction* fails — connection-time TLS handshake failures during actual export are swallowed by the batch processor's own error handling and are not surfaced to the operator at all).

This is a real functional/security gap: validation accepts a scheme that the implementation cannot honor, and there's no code path connecting the parsed scheme to the exporter's security mode.
**Fix:** Branch on the parsed scheme and only strip `WithInsecure()` for `http://`; for `https://` configure TLS credentials instead:
```go
useTLS := strings.HasPrefix(endpoint, "https://")
cleanEndpoint := strings.TrimPrefix(strings.TrimPrefix(endpoint, "http://"), "https://")
opts := []otlptracegrpc.Option{otlptracegrpc.WithEndpoint(cleanEndpoint)}
if useTLS {
    opts = append(opts, otlptracegrpc.WithTLSCredentials(credentials.NewClientTLSFromCert(nil, "")))
} else {
    opts = append(opts, otlptracegrpc.WithInsecure())
}
traceExp, err := otlptracegrpc.New(ctx, opts...)
```
Apply the same pattern to the metric and log exporters. Add a test asserting an `https://` endpoint does not set `WithInsecure`.

## Warnings

### WR-01: `streamEndedNormally` is a dead/vestigial variable — the "stream ended unexpectedly" fallback is effectively unreachable

**File:** `gateway/main.go:574-649` (deferred span-status handler in `queryRAG`)
**Issue:** `streamEndedNormally` is only ever set `true` inside the branch `else { streamEndedNormally = true }` at the EOF-handling site (main.go, around line 745), which executes when `sawWorkflowCompleted == true` OR `r.Context().Err() != nil`. In both cases, the deferred handler's earlier checks (`if completedEvent != nil { ... return }` and `if r.Context().Err() != nil { ... return }`) already fire and return *before* the final `if !streamEndedNormally { ... }` fallback is ever evaluated — because `sawWorkflowCompleted` and `completedEvent` are always set together, and a non-nil `ctx.Err()` is handled by the earlier branch. Tracing through `TestRootSpanStatusSetOnEveryExitPath`'s "success terminal" case in `gateway/main_test.go` confirms this: the span status is set via the `completedEvent != nil` branch, never via `streamEndedNormally`.

This makes `streamEndedNormally` write-only dead code today, but it is a maintenance foot-gun: a future refactor that adds a new early-return path in the receive loop (without also updating `completedEvent`/`streamErrorCode`/context state) will silently fall into the "stream ended unexpectedly" `Error` status regardless of whether the stream actually ended normally, because the variable meant to guard that case has no actual effect.
**Fix:** Either remove the dead variable and the unreachable branch, or restructure the deferred handler so `streamEndedNormally` is checked *before* the `completedEvent`/context-error branches (so it can actually gate behavior), whichever matches the intended semantics.

### WR-02: Retrieval failure `kind` metric classification relies on substring-matching the error message text

**File:** `engine/src/workflow/nodes/retrieve.rs:107-114`, `engine/src/workflow/nodes/retrieve.rs:171-178`
**Issue:** Both the dense and BM25 failure-classification sites do:
```rust
let kind = match err.kind {
    NodeErrorKind::Timeout => crate::telemetry::metrics::KIND_TIMEOUT,
    _ if err.message.to_lowercase().contains("unavailable") => crate::telemetry::metrics::KIND_UNAVAILABLE,
    _ => crate::telemetry::metrics::KIND_ERROR,
};
```
Bucketing the `lancet.rag.retrieval.path_failures{kind}` metric on whether the free-text error message happens to contain the substring "unavailable" is fragile: any refactor of an error message (e.g. rewording "LanceDB table unavailable" to "LanceDB table not ready") silently reclassifies failures from `unavailable` to `error` with no compile-time or test signal, corrupting the dashboard's "Retrieval Path Failures" breakdown by `kind` (`deploy/grafana/dashboard_gen/main.go` panel `p2`) without anyone noticing.
**Fix:** Classify on a typed error variant/kind instead of string content — e.g. extend `NodeErrorKind` (or the underlying retrieval error kind already available as `RetrievalErrorKind`) with an explicit `Unavailable` variant that call sites construct deliberately, and match on that instead of `message.to_lowercase().contains(...)`.

### WR-03: Shared global rebuild-fault-injection test state is only partially guarded by the new `REBUILD_TEST_MUTEX`

**File:** `engine/src/ingest.rs:1451` (new `REBUILD_TEST_MUTEX`); `engine/src/tests.rs:8001-8072` (`rebuild_failure_degrades_not_fails`), `engine/src/tests.rs:8075-8160` (`rebuild_checkout_latest_failure_degrades_not_fails`); contrast with `engine/src/tests.rs:8163`, `engine/src/tests.rs:8218` (the two tests that do take the new lock)
**Issue:** This phase introduces `pub static REBUILD_TEST_MUTEX: tokio::sync::Mutex<()>` and acquires it in the two new/modified debounce tests (`debounce_coalesces_burst`, `debounce_task_terminates_on_shutdown_signal`) before touching `rebuild_and_swap`/the debounce task. However, two pre-existing tests — `rebuild_failure_degrades_not_fails` and `rebuild_checkout_latest_failure_degrades_not_fails` — call `engine::ingest::arm_rebuild_fail_next()` / `arm_rebuild_checkout_fail_next()` and then `rebuild_and_swap()` directly, mutating the same process-global `REBUILD_FAIL_NEXT` / `REBUILD_CHECKOUT_FAIL_NEXT` / `REBUILD_COUNTER` statics, *without* acquiring `REBUILD_TEST_MUTEX`. Since `cargo test` runs `#[tokio::test]` functions concurrently by default, if either of these two unprotected tests runs at the same time as one of the two now-protected debounce tests, the shared global fault-injection flags can be armed/consumed by the wrong test, producing intermittent, hard-to-reproduce CI flakiness (e.g., a debounce test's background `rebuild_and_swap()` unexpectedly failing because an unrelated concurrently-running test armed `REBUILD_FAIL_NEXT`).
**Fix:** Acquire `REBUILD_TEST_MUTEX` at the top of `rebuild_failure_degrades_not_fails` and `rebuild_checkout_latest_failure_degrades_not_fails` as well, so all tests that touch the shared fault-injection statics are mutually exclusive.

### WR-04: Hardcoded default Grafana admin credentials in the committed observability compose stack

**File:** `docker-compose.yml:88-91`
**Issue:**
```yaml
environment:
  GF_SECURITY_ADMIN_USER: admin
  GF_SECURITY_ADMIN_PASSWORD: admin
```
The Grafana service ships with the well-known default `admin`/`admin` credential pair hardcoded directly in the committed compose file, rather than sourced from an environment variable or `.env` file with a documented "change me before any non-local use" callout. While the service is bound to `127.0.0.1:3000` and gated behind the `observability` compose profile (reducing but not eliminating exposure — anyone with local port-forwarding access, a misconfigured bind, or reuse of this compose file in a shared/staging environment inherits the default credential), this is a pattern the project itself would likely flag if found elsewhere (`config/config.toml` explicitly comments "never commit a real DSN" for the database URL, showing awareness of this class of issue).
**Fix:** Source from environment variables with no committed default value, e.g.:
```yaml
environment:
  GF_SECURITY_ADMIN_USER: ${GRAFANA_ADMIN_USER}
  GF_SECURITY_ADMIN_PASSWORD: ${GRAFANA_ADMIN_PASSWORD}
```
and document the required `.env` entries in a local dev README.

### WR-05: `otelhttp` span-name formatter includes raw, unbounded URL path segments

**File:** `gateway/main.go:912-918`
**Issue:**
```go
otelHandler := otelhttp.NewHandler(
    routesHandler,
    "lancet-gateway",
    otelhttp.WithSpanNameFormatter(func(operation string, r *http.Request) string {
        return fmt.Sprintf("%s %s", r.Method, r.URL.Path)
    }),
)
```
For routes like `GET /documents/{id}`, this produces a distinct span name per document UUID (e.g. `GET /documents/3fa85f64-5717-4562-b3fc-2c963f66afa6`) rather than a route-template name (`GET /documents/{id}`). Unlike Prometheus metric labels, this doesn't cause a cardinality *cost* problem in the trace backend itself, but it directly conflicts with the bounded-dimension discipline the phase otherwise follows carefully for metrics (`engine/src/telemetry/metrics.rs` doc comment: "bounded dimensions only (D-35, D-42)"), and it degrades APM tooling that groups/aggregates by span name (Jaeger's operation view, latency-by-endpoint dashboards, etc.), since every request to `/documents/{id}` becomes its own unique "operation."
**Fix:** Use the matched chi route pattern instead of the raw path, e.g. via `chi.RouteContext(r.Context()).RoutePattern()` inside the formatter, falling back to `r.URL.Path` only when no route matched (e.g. 404s).

### WR-06: Engine telemetry handle is not flushed on early-return startup error paths

**File:** `engine/src/main.rs:23-161`
**Issue:** `telemetry_handle.shutdown()` is only called on the last line of `main()`, after `Server::builder()....serve_with_shutdown(...).await?`, `worker.await?`, and `debounce_worker.await?` all succeed. `telemetry::init()` is called near the top of `main()` (line 26), well before database initialization, embedding/generation client construction, and the OPENROUTER_API_KEY check. Any `?`-propagated error from those steps (e.g., a bad `lancedb_path`, a missing `OPENROUTER_API_KEY`, a malformed `grpc_addr`) exits `main()` without ever calling `telemetry_handle.shutdown()`, so any spans/logs/metrics buffered by the batch exporters during startup (including the startup failure's own `tracing::error!`/log output, if any were emitted) are dropped rather than flushed to the collector. This weakens exactly the class of diagnostic signal (early startup failures) that telemetry is most useful for capturing.
**Fix:** Wrap the fallible startup sequence so `telemetry_handle.shutdown()` runs on every exit path, e.g. restructure into an inner `async fn run(settings, telemetry_handle) -> Result<...>` and call `shutdown()` unconditionally after it returns, or use a small RAII guard around `TelemetryHandle` that flushes on `Drop`.

## Info

### IN-01: Per-call OTel instrument construction instead of cached/static instruments

**File:** `engine/src/telemetry/metrics.rs:70-165`
**Issue:** Every `record_*` function calls `meter().u64_histogram(...).build()` / `meter().u64_counter(...).build()` / `meter().u64_gauge(...).build()` fresh on every invocation, rather than constructing the instrument once (e.g., via `OnceLock`/`LazyLock`) and reusing the handle. The OTel SDK aggregates by instrument name/unit/description so this is not a correctness bug, but it is inconsistent with the "reuse allocations, avoid needless per-call construction" guidance the project's own Rust guidelines emphasize for hot paths, and every one of these functions is invoked on the request-serving path (query duration, retrieval failures, generation retries).
**Fix:** Not required for this phase, but consider caching instrument handles behind `std::sync::OnceLock` keyed per metric if these calls become hot-path-sensitive.
