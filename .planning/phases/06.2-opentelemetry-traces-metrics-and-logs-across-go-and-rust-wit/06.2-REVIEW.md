## Summary

This is a gap-closure re-review covering plans 06.2-10, 06.2-11, 06.2-12 (gap_ids
G-06.2-1 Loki↔Jaeger trace-log correlation, G-06.2-2 duration-panel PromQL shape,
G-06.2-4 unbounded OTel exporter error noise). `engine/src/telemetry/metrics.rs` and
`scripts/generate-dashboards.sh` were included as contract anchors, not because they
changed in this delta — `metrics.rs` defines the instrument names the dashboard PromQL
and Rust test stems assert against, and `generate-dashboards.sh` is the verifier (not
regenerator) that keeps `dashboard_gen/main.go` and the committed dashboard JSON in
sync.

**Finding-ID note:** this document carries forward still-open findings from the stale
2026-08-24 `06.2-REVIEW.md` **at their original IDs** (WR-01, WR-04, WR-06, WR-10,
IN-01, IN-02, IN-03) so that any prior cross-reference to those IDs still resolves
correctly. New findings from this round are numbered starting at WR-11 / IN-04.
Findings from the prior pass that pertained to files outside this round's scope
(`WR-02` throughput/duration panel, `WR-03`/`WR-05`/`WR-07`/`WR-09`, in `service.rs`,
`generation/mod.rs`, `telemetry_query.rs`, `verify-collector-prom-export.sh`) are not
re-litigated here since those files were not reviewed this round.

**Verification against `06.2-REVIEWS.md`'s pre-execution concerns for plans 10–12** (all
confirmed against the actual shipped code, not just plan intent):

1. **[HIGH, plan 10] Loki→Jaeger derived-field regex** — confirmed fixed.
   `datasources.yaml` now uses `matcherType: label` / `matcherRegex: trace_id` instead of
   the old `matcherRegex: "trace_id=([0-9a-fA-F]+)"` body regex. This is genuinely
   correct Grafana semantics for this deployment: `matcherType: label` (Grafana ≥10.3,
   this stack pins `grafana/grafana:11.5.2`) resolves `matcherRegex` as an exact
   label/structured-metadata field name rather than a regex against the log line body.
   The Collector ships logs to Loki via `otlphttp/loki` (Loki 3.4.2's native OTLP
   ingestion path), which surfaces a log record's trace ID as Loki structured metadata
   keyed `trace_id` — exactly what `matcherType: label` + `matcherRegex: trace_id`
   targets. The old body-regex approach would never have matched because the trace ID
   never appears as literal `trace_id=<hex>` text in the log line body under OTLP
   ingestion. `engine/src/tests/telemetry_metrics.rs::grafana_traces_to_logs_maps_no_span_tag`
   pins both the removed `tags:` mapping on the Jaeger side and the new label-matcher
   shape on the Loki side.
2. **[MEDIUM, plan 10] Triple-nested Python quoting → `jq -e`** — confirmed addressed at
   the plan-authoring level (`06.2-10-PLAN.md` Task 2 now specifies `jq -e` one-line
   polls with `curl`/`jq` PATH preconditions, replacing the earlier Python-quoting
   design). The `jq`-based live poll scripts themselves are not part of this review's
   file list (they live inline in the plan/SUMMARY, not as a committed script), so this
   is reported as confirmed-at-the-source-of-truth-available rather than independently
   re-executed.
3. **[MEDIUM, plan 12] Error-suppression cap "for the whole process lifetime"** —
   confirmed addressed, not just relabeled. Both `boundedErrorHandler` (Go,
   `telemetry.go:38-78`) and `BoundedOtelDiagnostics` (Rust, `mod.rs:58-108`) re-arm
   after a 5-minute window (`windowStart`/`window_start` reset when
   `now - start >= window`), verified by both `TestOTelErrorHandlerBoundsRepeatedExportErrors`
   (advances a fake clock past the window and asserts a new error line appears) and Rust's
   `otel_internal_diagnostics_are_bounded` (Property 3). The cap is per-5-minute-window,
   not a single line for the process's entire lifetime — this is a materially different
   (and correct, D-38-conformant) design from what was flagged. See WR-13 below for a
   related but distinct defect in how the window is *communicated* in the printed
   message.
4. **[MEDIUM, plan 11] Fail-first git stash/checkout ceremony leaving index residue** —
   no residue found. `git status --porcelain` is clean and `git stash list` is empty at
   time of review; the current `telemetry_metrics.rs` and dashboard files show no signs
   of partial/leftover edits.
5. **[LOW] Duration panels unitless** — confirmed fixed. Both `main.go`'s "RAG Query
   Duration" (p1) and "Index Rebuild Duration" (p9) builders now chain `.Unit("ms")`,
   and the committed `lancet-rag-operations.json` reflects `"unit": "ms"` in both
   panels' `fieldConfig.defaults`.
6. **[LOW] WR-01 fold-in not done** — confirmed. `TestOTLPExportersFollowEndpointSecurity`
   (`telemetry_test.go:448-462`) is byte-for-byte unchanged from the stale review: it
   still only asserts non-empty option slices for both TLS branches and still refers in
   its own comment to a "`WithInsecure` source region grep" that does not exist anywhere
   in the repository. Plan 12 touched this same file (added
   `TestOTelErrorHandlerBoundsRepeatedExportErrors`) but did not fold in the suggested
   grep-based gate. Carried forward below at its original ID, WR-01.
7. **[LOW] `SetupErrorHandler` called on every `Init`** — confirmed harmless.
   `setupErrorHandlerOnce.Do(...)` (`telemetry.go:34-36, 81-85`) guarantees only the
   first call in the process actually installs a handler; `TestCollectorUnavailable`
   (which calls `Init`, and is itself invoked twice via the
   `TestCollectorUnavailableKeepsConsole` wrapper) never observes a different handler
   because of this. Separately, `TestOTelErrorHandlerBoundsRepeatedExportErrors`
   constructs its `boundedErrorHandler` directly via `newBoundedErrorHandler(...)`,
   bypassing `SetupErrorHandler`/`sync.Once` entirely, so it has no dependency on test
   execution order either.

## Warnings

### WR-01 (carried forward, still open): CR-04's dedicated regression test still cannot detect a TLS regression

**File:** `gateway/internal/telemetry/telemetry_test.go:448-462`
**Issue:** Unchanged since the 2026-08-24 review. `TestOTLPExportersFollowEndpointSecurity`
only asserts that `otlpGRPCOptions(true)` and `otlpGRPCOptions(false)` each return
non-empty option slices; it does not inspect which option (`WithTLSCredentials` vs
`WithInsecure`) was actually selected. The comment still claims verification happens
"via the `WithInsecure` source region grep rather than runtime option introspection,"
but no such grep exists anywhere in the repository (confirmed again this round: the only
`WithInsecure` occurrences are the three call sites in `telemetry.go` and this comment).
Plan 12 edited this same file (adding `TestOTelErrorHandlerBoundsRepeatedExportErrors`
immediately below) without folding in the cheap fix suggested in the prior review.
**Fix:** Make `otlpGRPCOptions` return an observable `secure bool` marker the test can
assert on directly, or add the missing grep-based CI gate the comment claims exists.

### WR-04 (carried forward, still open): OTLP endpoint scheme parsing remains case-sensitive and path-naive

**File:** `gateway/internal/telemetry/telemetry.go:89-95`
**Issue:** Unchanged since the prior review. `otlpEndpointSecurity` still does
`strings.HasPrefix(trimmed, "https://")`, case-sensitive against the case-insensitive
URI scheme grammar (RFC 3986); `HTTPS://collector:4317` silently resolves to the
insecure branch — the same failure class CR-04 fixed, reached via a different input. A
path-suffixed endpoint (`https://collector:4317/v1/traces`) still produces an invalid
gRPC target (`collector:4317/v1/traces`), which fails exporter construction and silently
degrades that signal to no-op per `Init`'s fail-open design. Neither case is covered by
`TestOTLPEndpointSecurity`.
**Fix:** Parse with `net/url.Parse`, use `u.Host`, and compare scheme via
`strings.EqualFold(u.Scheme, "https")`.

### WR-06 (carried forward, still open): `collector_prometheus_exporter_has_no_namespace` still only guards one token via a hand-rolled line scanner

**File:** `engine/src/tests/telemetry_metrics.rs:789-836`
**Issue:** Unchanged since the prior review. The CR-02 regression test still uses an
indentation-based line scanner and asserts only `!contains("namespace:")` and
`contains("endpoint:")`; it doesn't pin the endpoint value and doesn't guard against
`add_metric_suffixes: false` being added (which would strip the
`_milliseconds`/`_total`/`_bucket` suffixes this same file's
`dashboard_panels_resolve_to_defined_instruments` and `duration_panels_query_histogram_buckets`
tests depend on). The two new tests added this round
(`grafana_traces_to_logs_maps_no_span_tag`, `duration_panels_query_histogram_buckets`)
use the identical brittle line-scanning pattern for a different config block, so this
class of test debt has been replicated rather than addressed.
**Fix:** Parse YAML properly (`serde_yaml::Value`) for both the collector config and the
Grafana datasources config, or at minimum add
`assert!(!prometheus_block.contains("add_metric_suffixes: false"))`.

### WR-10 (carried forward, still open): `resource.Merge` error silently discarded in gateway telemetry init

**File:** `gateway/internal/telemetry/telemetry.go:159`
**Issue:** Unchanged since the prior review.
`res, _ := resource.Merge(resource.Default(), resource.NewWithAttributes(...))` discards
the error return. `resource.Merge` can return a non-fatal `ErrSchemaURLConflict`, and
every other exporter-construction failure path in this same function logs a `WARNING` —
this one doesn't, so a merge conflict is invisible to an operator.
**Fix:** Log the error at `WARNING` level, consistent with the other construction-error
paths in this file.

### WR-11 (new): `TestOTelErrorHandlerBoundsRepeatedExportErrors` cannot detect the information-disclosure regression it claims to guard

**File:** `gateway/internal/telemetry/telemetry_test.go:464-524` (assertion at 491-496); implementation at `gateway/internal/telemetry/telemetry.go:62-78`
**Issue:** `06.2-12-PLAN.md`'s threat table (T-06.2-12-03, Information Disclosure) claims
this test's "no line contains an OTLP endpoint or credential-shaped string" assertion
mitigates the exporter error text leaking the collector endpoint or credentials into
console output. But `boundedErrorHandler.Handle` performs no redaction at all — it
prints `fmt.Fprintf(h.sink, "WARNING: OpenTelemetry export error: %v\n", err)` verbatim
for whatever `err.Error()` the OTel SDK hands it. The test only ever calls
`handler.Handle(errors.New("exporter export timeout"))` / `errors.New("second export
error after window")` — synthetic strings that were never going to contain `http://`,
`https://`, or `Bearer `. The negative assertion (lines 491-496) is therefore vacuously
true: it would pass identically even if `Handle` printed the endpoint or a credential
verbatim, because the test never feeds it an error that contains one. Real OTel gRPC
exporter errors routinely do embed the dial target (e.g. `otlptracegrpc`/`otlpmetricgrpc`
connection failures commonly stringify as `rpc error: ... dial tcp <host:port>: connect:
connection refused`), and `cleanEndpoint` (the collector target derived from
`cfg.OTLPEndpoint`) is exactly what gets dialed — so the one line per 5-minute window
that this handler *does* print for a real, unavailable-collector failure is likely to
contain the collector address, unredacted, and no test in this file would catch that
regressing further (e.g. into printing request metadata). Note: this is not assessed as
a novel disclosure risk in practice, since the endpoint is already logged plainly
elsewhere in this same file at construction-failure time (`telemetry.go:205,233,251`) —
the defect is the vacuous assertion and the over-claiming threat-table entry, not a new
secret leak.
**Fix:** Either (a) add a test case that feeds `Handle` an error value shaped like a real
gRPC dial failure containing an endpoint substring, and assert the *handler* redacts it
(if redaction is actually intended), or (b) if bounding frequency — not redacting
content — is the actual, accepted design, narrow the threat-table claim in
`06.2-12-PLAN.md` and the test's stated intent so it doesn't over-promise a
content-redaction guarantee the code doesn't provide.

### WR-12 (new): Dashboard drift-check script exists but is not wired into any executed gate

**File:** `scripts/generate-dashboards.sh`; cross-referenced `06.2-VALIDATION.md:85`
**Issue:** The prior review's WR-08 ("Nothing in this file set enforces that the
generator... and the checked-in JSON... stay in sync... neither this test nor CI would
catch it") is only partially addressed. `generate-dashboards.sh` now exists and performs
a correct byte-for-byte `cmp` between a freshly generated dashboard and the committed
JSON, failing loudly on drift — the *mechanism* is real and correctly implemented. But
nothing in the repository actually invokes it automatically: there is no
`.github/workflows` directory, no Makefile/justfile, and no other script under `scripts/`
that calls `generate-dashboards.sh`. The only place it's referenced is
`06.2-VALIDATION.md:85`, where the corresponding row is marked `❌ Wave 0` /
`⬜ pending` — i.e. it is documented as a manual validation command an operator or agent
must remember to run, not a gate that runs itself. A future edit to `main.go` that isn't
followed by manually re-running this script and committing the regenerated JSON would
still silently diverge from what Grafana serves, exactly as WR-08 originally described,
because there is no automated trigger.
**Fix:** Add `sh scripts/generate-dashboards.sh` as a step in whatever CI workflow (or
pre-commit/test-target script) runs `engine-test-targets.sh`/`gateway-test-targets.sh`,
so drift fails the build rather than depending on someone remembering to run a documented
manual command.

### WR-13 (new): Suppression message hardcodes "5m" independent of the actual configured window; both regression tests lock in the literal text

**File:** `gateway/internal/telemetry/telemetry.go:76`; `engine/src/telemetry/mod.rs:104`; asserted at `gateway/internal/telemetry/telemetry_test.go:487,521`
**Issue:** Both `boundedErrorHandler.Handle` (Go) and `BoundedOtelDiagnostics::should_emit_at`
(Rust) take `window`/`window: Duration` as a constructor parameter, but the printed
suppression line hardcodes the literal string `"suppressed for 5m (D-38)"` rather than
formatting the actual `h.window`/`self.window` value. Both constructors
(`newBoundedErrorHandler`, `BoundedOtelDiagnostics::new`) are public and parameterized
specifically so callers/tests can vary the window — `TestOTelErrorHandlerBoundsRepeatedExportErrors`
itself passes `5*time.Minute` explicitly rather than relying on a default, which is only
coincidentally consistent with the hardcoded text. If a future change (production config,
or a different call site) constructs either type with a different window — e.g. 30
seconds for a more aggressive re-arm — the printed message will keep claiming "suppressed
for 5m" while actually re-arming on a different cadence, misleading whoever reads the
console output. Worse, the regression tests themselves assert the literal string
`"suppressed for 5m (D-38)"` (`telemetry_test.go:487,521`) instead of deriving the
expected text from the window value passed to the constructor, so a window/message
mismatch introduced elsewhere would not be caught by these tests either.
**Fix:** Format the message from the actual `window` field (e.g. Go:
`fmt.Fprintf(h.sink, "WARNING: further OpenTelemetry export errors suppressed for %s (D-38)\n", h.window)`;
Rust: `eprintln!("WARNING: further OpenTelemetry export diagnostics suppressed for {:?} (D-38)", self.window)`),
and update both tests to assert against the formatted window rather than a hardcoded
`"5m"` literal.

**File:** `deploy/grafana/dashboard_gen/main.go:16-23`
**Issue:** Unchanged since the prior review. When `-output` is omitted, the default
`filepath.Join("..", "dashboards", "lancet-rag-operations.json")` only resolves
correctly when the process's working directory is `deploy/grafana/dashboard_gen/`.
Impact is now lower than before because the new `scripts/generate-dashboards.sh` always

supplies it anyway.

### IN-03 (carried forward, still open): "Answer Degraded Rate" panel description still doesn't disambiguate from the wire-level `degraded_mode` flag

**File:** `deploy/grafana/dashboard_gen/main.go:58-68`, `engine/src/telemetry/metrics.rs:6-12`
**Issue:** Unchanged since the prior review. `metrics.rs`'s module doc still documents
that `lancet.rag.answer.degraded` fires only on `answer_basis != RETRIEVAL`, deliberately
narrower than the wire-level `degraded_mode` flag which also fires on several notice

**Fix:** Rename/re-describe the panel (e.g. "Terminal answer basis mismatches") or add a
companion panel for the broader `degraded_mode` signal.
