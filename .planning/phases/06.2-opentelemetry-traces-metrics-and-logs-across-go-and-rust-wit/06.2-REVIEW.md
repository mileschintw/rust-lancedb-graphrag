# Phase 06.2: Code Review Report (Re-Review After Gap Closure)

**Reviewed:** 2026-08-24T00:00:00Z
**Depth:** standard
**Files Reviewed:** 17
**Status:** issues_found

## Summary

This is a re-review after three gap-closure plans (06.2-07, 06.2-08, 06.2-09) addressed four
critical findings from the original review. All four are confirmed closed:

- **CR-01** (committed `dashboard_gen.exe`): confirmed removed from git tracking
  (`git ls-files` shows only `go.mod`/`go.sum`/`main.go`), and `.gitignore` covers
  `deploy/grafana/dashboard_gen/*.exe` and `deploy/grafana/dashboard_gen/dashboard_gen` going
  forward.
- **CR-02** (double-prefixed Prometheus metric names): `otel-collector-config.yaml`'s
  `prometheus:` exporter no longer sets `namespace: lancet`. The `_milliseconds` unit-suffix
  convention (not `_ms`) is now consistent across `engine/src/telemetry/metrics.rs`
  (`.with_unit("ms")`), `deploy/grafana/dashboard_gen/main.go`, the generated
  `lancet-rag-operations.json`, and the assertion in `telemetry_query.rs`'s
  `dashboard_panels_resolve_to_defined_instruments` test.
- **CR-03** (hardcoded `gen_ai.request.model`): both `engine/src/service.rs`
  (`embedding_request` span, line 431) and `engine/src/workflow/nodes/generate.rs`
  (`llm_attempt` spans, lines 122 and 178) now read `.model_id()` off the injected
  `Generator`/`EmbeddingProvider` trait objects, which resolve to real adapter-reported model
  IDs (`OpenRouterGenerator::model_id()` returns the configured model string).
  `engine/src/tests/telemetry_query.rs` exercises this end-to-end with
  `test-gen-model-override` / `test-embed-model-override` fixtures.
- **CR-04** (gateway OTLP exporters forcing `WithInsecure()`): `gateway/internal/telemetry/telemetry.go`
  now branches all three exporters (trace, metric, log) on `otlpEndpointSecurity()`'s parsed
  scheme via `otlpGRPCOptions(useTLS)`; none of the three was left on the insecure path.

None of the four original defects reproduce. However, this pass surfaces several **new**
findings: some are genuine residual defects the gap-closure work didn't reach, and — more
importantly — several of the regression tests added specifically to guard CR-02 and CR-04 are
weak enough that the same class of regression could reappear silently without failing CI. Those
are flagged below as the most actionable items from this pass.

## Warnings

### WR-01: CR-04's dedicated regression test cannot detect a TLS regression

**File:** `gateway/internal/telemetry/telemetry_test.go:446-460`
**Issue:** `TestOTLPExportersFollowEndpointSecurity` only asserts that
`otlpGRPCOptions(true)` and `otlpGRPCOptions(false)` each return non-empty option slices. It
does not inspect which option (`WithTLSCredentials` vs `WithInsecure`) was actually selected.
The test's own comment states the real verification is "via the `WithInsecure` source region
grep rather than runtime option introspection" — but no such grep-based check exists anywhere
in the repository (confirmed via search; the only three occurrences of `WithInsecure` are the
three call sites in `telemetry.go` itself and this comment). If a future edit swapped
`WithTLSCredentials(tlsCreds)` for `WithInsecure()` in the `useTLS == true` branch — reproducing
CR-04 exactly — this test would still pass, because both branches still return non-empty
slices.
**Fix:** Make the option constructors observable, e.g. have `otlpGRPCOptions` return a marker
alongside the options (`secure bool`) that the test asserts directly, or refactor
`otlpEndpointSecurity` + `otlpGRPCOptions` to build `grpc.DialOption`s directly and assert on
`credentials.TransportCredentials.Info().SecurityProtocol` rather than the opaque
`otlptracegrpc.Option` closures.

### WR-02: Dashboard "RAG Query Duration" panel plots throughput, not duration

**File:** `deploy/grafana/dashboard_gen/main.go:33-44`, `deploy/grafana/dashboards/lancet-rag-operations.json:16-56`
**Issue:** Panel 1 ("RAG Query Duration", described as "Duration of end-to-end RAG queries by
outcome") uses the expression
`sum by (outcome) (rate(lancet_rag_query_duration_milliseconds_count[5m]))`. `..._count` is the
histogram's observation counter, so `rate(..._count[5m])` is queries-per-second, not a duration
value — the panel never touches `_sum` or `_bucket`. Contrast with panel 9 ("Index Rebuild
Duration"), which correctly uses
`histogram_quantile(0.95, sum(rate(..._bucket[5m])) by (le, outcome))`. An operator reading
panel 1 would see a rate graph labeled as a duration graph. The dashboard cross-check test
(`telemetry_query.rs::dashboard_panels_resolve_to_defined_instruments`) only checks that the
expression references a known metric stem, so it cannot catch this class of PromQL
misuse.
**Fix:** Change panel 1 to a duration-shaped query, e.g.
`histogram_quantile(0.95, sum(rate(lancet_rag_query_duration_milliseconds_bucket[5m])) by (le, outcome))`
(mirroring panel 9), or rename/re-describe the panel if throughput was actually intended.

### WR-03: `Generator::model_id()` default is a silent-hazard magic string

**File:** `engine/src/generation/mod.rs:563-569`
**Issue:** The `Generator` trait's default `model_id()` implementation returns the literal
`"unspecified"`. This exists "so existing test doubles remain source-compatible," but it also
means any future production `Generator` adapter that forgets to override `model_id()` will
silently emit `gen_ai.request.model = "unspecified"` on every `llm_attempt` span — exactly the
class of defect CR-03 fixed, reintroduced by omission rather than by a hardcoded literal. There
is no compile-time or test-time signal that a new adapter is missing the override (contrast with
`EmbeddingProvider::model_id()` in `engine/src/ingest.rs:1415-1418`, whose default at least
resolves to a real named constant, `client::EMBEDDING_MODEL`, rather than a sentinel string).
**Fix:** Remove the default from `Generator::model_id()` and require every implementor
(including `#[cfg(test)]` fakes) to provide one explicitly, or add a debug-time assertion in the
call sites that `model_id() != "unspecified"` before using it in a span attribute.

### WR-04: OTLP endpoint scheme/target parsing is case-sensitive and path-naive

**File:** `gateway/internal/telemetry/telemetry.go:36-42`
**Issue:** `otlpEndpointSecurity` does `strings.HasPrefix(trimmed, "https://")`, which is
case-sensitive (URI schemes are case-insensitive per RFC 3986); an endpoint configured as
`HTTPS://collector:4317` silently falls through to the insecure branch — the exact failure mode
CR-04 targeted, just reached via a different input. Separately, if an operator configures an
endpoint with a path suffix (e.g. copy-pasted from an HTTP OTLP example,
`https://collector:4317/v1/traces`), the returned `target` is
`collector:4317/v1/traces`, which is invalid as a gRPC `host:port` target passed to
`otlptracegrpc.WithEndpoint()` — exporter construction fails, and `Init`'s fail-open behavior
(D-38) swallows this into a stderr warning with telemetry silently disabled for that signal.
Neither case is covered by `TestOTLPEndpointSecurity` (`telemetry_test.go:394-444`).
**Fix:** Parse with `net/url.Parse(endpoint)`, use `u.Host` as the target, and compare scheme
case-insensitively with `strings.EqualFold(u.Scheme, "https")`; add test cases for mixed-case
scheme and endpoints with a path component.

### WR-05: Collector verification script's stem check uses unanchored substring match

**File:** `scripts/verify-collector-prom-export.sh:270-274`
**Issue:** Step 4 checks presence of each dashboard-derived stem with
`printf '%s' "$SCRAPE_BODY" | grep -q "$stem"` — an unanchored substring match. If the
Collector's prometheus exporter regressed back to double-prefixing (e.g. `namespace: lancet`
were reintroduced, reproducing CR-02), the scraped body would contain
`lancet_lancet_rag_query_duration_milliseconds_count`, which still contains
`lancet_rag_query_duration_milliseconds` as a substring — step 4 would report `ALL_FOUND=1` and
proceed. Only the separate, narrower step 5 check
(`grep -E '^# (HELP|TYPE) lancet_lancet_|^lancet_lancet_'`) would actually catch the
regression. This means the "stem presence" assertion silently passes under the exact defect
class this script exists to guard against; correctness currently depends entirely on step 5.
**Fix:** Anchor the step 4 match to the metric-name start of a line, e.g.
`grep -qE "^${stem}(\{|_)"` (or similarly anchor on the `# TYPE ${stem} ` prefix), so a doubled
prefix cannot satisfy the "stem found" check.

### WR-06: `collector_prometheus_exporter_has_no_namespace` test only guards one token

**File:** `engine/src/tests/telemetry_metrics.rs:789-836`
**Issue:** The regression test for CR-02 parses the `prometheus:` exporter block with a
hand-rolled indentation-based line scanner and asserts only `!contains("namespace:")` and
`contains("endpoint:")`. It does not pin the endpoint value (`0.0.0.0:8889`, which
`deploy/prometheus/prometheus.yml:8` and `scripts/verify-collector-prom-export.sh:18`
independently hardcode as `collector:8889` / `127.0.0.1:8889`), and it does not guard against
`add_metric_suffixes: false` being added to the exporter block — an option that, if set, would
strip the `_milliseconds`/`_total`/`_bucket` suffixes every dashboard panel and this same test
suite's `dashboard_panels_resolve_to_defined_instruments` depend on, silently breaking all ten
dashboard stems. The line-based parser is also brittle to any valid YAML re-indentation of the
`exporters:` block that doesn't change semantics.
**Fix:** Either parse the YAML properly (a `serde_yaml::Value` walk keyed on
`exporters.prometheus`) and assert on the full expected key set (`endpoint`, absence of
`namespace`, absence of `add_metric_suffixes: false`), or at minimum add an explicit
`assert!(!prometheus_block.contains("add_metric_suffixes: false"))`.

### WR-07: `test_record_query_duration_ms` doesn't take the shared metrics-test mutex

**File:** `engine/src/tests/telemetry_query.rs:297-301`
**Issue:** Every other test in `telemetry_metrics.rs` that records into the process-global
OTel meter provider takes `METRIC_TEST_MUTEX` first (see `setup_test_meter()` callers) precisely
because the meter provider is process-global shared state and tests assert exact metric counts
(`assert_eq!(dps.len(), N)`). `test_record_query_duration_ms` is a plain `#[test]` that calls
`record_query_duration_ms` twice without acquiring that mutex or calling `setup_test_meter()`.
Run with `cargo test` (which parallelizes by default), this can interleave with, e.g.,
`metrics_query_duration_outcome_stays_two_valued` (`telemetry_metrics.rs:602-630`), which asserts
`find_hist_total_count(&finished, "lancet.rag.query.duration") == 1` — a flaky/racy count
assertion depending on scheduling.
**Fix:** Convert to `#[tokio::test]` and acquire `METRIC_TEST_MUTEX` (or move it into
`telemetry_metrics.rs` alongside the other metric-recording tests) so it participates in the
same serialization discipline.

### WR-08: No drift check between `dashboard_gen/main.go` and the committed dashboard JSON

**File:** `engine/src/tests/telemetry_query.rs:744-787`
**Issue:** `dashboard_panels_resolve_to_defined_instruments` reads only the committed
`lancet-rag-operations.json` and checks `panels.len() == 10` plus a per-panel substring match
against a hardcoded stem list — it never regenerates the dashboard from
`dashboard_gen/main.go` and diffs. Nothing in this file set enforces that the generator (which a
developer would edit to make a legitimate change) and the checked-in JSON (which is what
Grafana and this test actually consume) stay in sync; the two could silently diverge on a future
edit to `main.go` that isn't followed by re-running the generator, and neither this test nor CI
would catch it.
**Fix:** Add a test/script step that runs `go run ./deploy/grafana/dashboard_gen -output <tmp>`
and diffs the output against the committed JSON, failing if they differ.

### WR-09: `service.rs` computes and discards a duplicate `disable_graph_context` value

**File:** `engine/src/service.rs:840-842`
**Issue:** `let _disable_graph_context = req.disable_graph_context.unwrap_or(false);` computes
the flag and immediately discards it (underscore-prefixed to suppress the unused-variable
warning). The value that actually governs behavior is derived independently a few lines later
inside `workflow::WorkflowContext::new(...)`, which reads `request.disable_graph_context` off
the same `req` (`engine/src/workflow/mod.rs:120`). The two derivations happen to agree today,
but the dead local is confusing: it reads as though the flag were meant to be threaded through
explicitly (e.g. into telemetry or validation) and isn't, and it's the kind of unused
computation that tends to accumulate silently divergent duplicate logic over time.
**Fix:** Delete the dead local, or if it was intended for something (e.g. an admission-time span
attribute), wire it through explicitly instead of discarding it.

### WR-10: `resource.Merge` error silently discarded in gateway telemetry init

**File:** `gateway/internal/telemetry/telemetry.go:105`
**Issue:** `res, _ := resource.Merge(resource.Default(), resource.NewWithAttributes(...))`
discards the error return. `resource.Merge` can return a non-fatal `ErrSchemaURLConflict`
warning-class error that's normally worth logging (and, more importantly, a nil/degraded
`res` would silently propagate into every subsequent provider), but there's no path here for a
future maintainer to notice a merge conflict was ever reported.
**Fix:** Log the error at `WARNING` level (consistent with how other exporter-construction
errors in this same function are handled, e.g. lines 150-154).

## Info

### IN-01: "Answer Degraded Rate" panel description doesn't match its narrower recording predicate

**File:** `deploy/grafana/dashboard_gen/main.go:57-67`, `engine/src/telemetry/metrics.rs:6-12`
**Issue:** `metrics.rs`'s module doc explicitly documents that `lancet.rag.answer.degraded`
fires only when `answer_basis != RETRIEVAL`, "deliberately narrower" than the wire-level
`degraded_mode` flag (`derive_degraded_mode` in `telemetry_query.rs:1112-1143`), which also
fires on 11 notice codes even when `answer_basis == RETRIEVAL` (e.g. graph timeouts, retrieval
degradation, citation drops). The dashboard panel titled "Answer Degraded Rate" is described as
"Degraded mode answers by basis," which reads as if it tracks the same signal as the
`degraded_mode` wire flag. This is a deliberate, documented design decision, not a code defect —
noting it here only because an operator relying on this panel to gauge overall degraded-mode
rate would under-count.
**Fix:** Consider renaming the panel description to something like "Terminal answer basis
mismatches (non-retrieval-grounded answers)" to disambiguate from `degraded_mode`, or add a
companion panel/counter for the broader `degraded_mode` signal if operators need it.

### IN-02: `dashboard_gen`'s default output path is CWD-relative

**File:** `deploy/grafana/dashboard_gen/main.go:16-23`
**Issue:** When `-output` is not passed, the default is
`filepath.Join("..", "dashboards", "lancet-rag-operations.json")`, which only resolves correctly
when the binary is run with a working directory of `deploy/grafana/dashboard_gen/`. Running
`go run ./deploy/grafana/dashboard_gen` from the repo root (a natural invocation) writes to
`../dashboards` relative to the repo root, i.e. outside the repo entirely, rather than failing
loudly.
**Fix:** Derive the default path relative to the source file's own location (e.g. via
`runtime.Caller` or a build-time constant) or require `-output` to be explicit.

### IN-03: Duplicate no-op test wrapper inflates the gateway telemetry package test count

**File:** `gateway/internal/telemetry/telemetry_test.go:260-262`
**Issue:** `TestCollectorUnavailableKeepsConsole` is `func TestCollectorUnavailableKeepsConsole(t *testing.T) { TestCollectorUnavailable(t) }` — a bare re-invocation of the preceding test under a new
name, contributing a fully duplicate test run rather than new coverage. It inflates the
`gateway/internal/telemetry 11` count asserted by `scripts/gateway-test-targets.sh`'s
`EXPECTED_PACKAGES` gate without adding assertion coverage.
**Fix:** Remove the wrapper (adjusting the expected package count in
`gateway-test-targets.sh` accordingly), or give it a body that actually exercises something the
first test doesn't.
