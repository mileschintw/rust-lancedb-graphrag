# Plan Review: Phase 06.2 — OpenTelemetry Traces, Metrics, and Logs across Go and Rust

## Overall Assessment

Phase 06.2 delivers a robust, production-grade observability architecture for Lancet, satisfying requirement **OBS-01** across both the Go API gateway (control plane) and Rust RAG engine (data plane). The implementation plans (06.2-01 through 06.2-06) execute a well-structured bridge architecture without rewriting existing `tracing` and `zap` instrumentation. Key architectural challenges—such as W3C `traceparent` extraction prior to gRPC payload consumption in [`LancetServiceImpl::query_rag`](file:///D:/Repos/lancet/engine/src/service.rs#L738-L760), `tracing` parent-binding at span construction time in [`engine/src/ingest.rs`](file:///D:/Repos/lancet/engine/src/ingest.rs#L1676-L1680), and strictly bounded Prometheus metric dimensions—are accurately diagnosed and addressed with verified source-level seams. Dependency ordering is clean across 5 waves, and file ownership boundaries prevent cross-task collisions.

- **Complete Signature Threading**: Identifies all affected spawn sites including [`engine/src/main.rs:88-99`](file:///D:/Repos/lancet/engine/src/main.rs#L88-L99) and 15 test call sites in [`engine/src/tests.rs`](file:///D:/Repos/lancet/engine/src/tests.rs) while leaving [`rebuild_and_swap`](file:///D:/Repos/lancet/engine/src/ingest.rs#L1441) signature untouched.

## Consensus Summary

The two fresh source-grounded reviews agree that the revised five-wave architecture is coherent: Plan 01 establishes propagation and provider seams, Plans 02 and 03 can run in parallel, Plan 04 carries ingestion causality and rebuild links, Plan 05 owns the ten bounded D-35 instruments, and Plan 06 owns correlated logs plus the single D-41 degradation derivation. Both reviewers also confirmed the important non-functional boundaries: `correlation_id` remains separate from the OTel trace identity, node spans are runner-owned, leaf spans belong at real I/O boundaries, rebuilds use links rather than a single parent, and telemetry must remain non-load-bearing.

### Agreed Strengths

- W3C propagation is placed at the correct HTTP/gRPC and tonic metadata seams, before request consumption, without replacing the existing wire correlation UUID.
- The revised span ownership and nesting rules are explicit, including the construction-time parent requirement for `index_document` and the single `graph_augmentation` record.
- The Collector topology, loopback-only bindings, unprofiled PostgreSQL service, native Loki OTLP path, and generated Grafana dashboard are appropriately scoped for the local observability demo.
- Metric cardinality is structurally bounded, the corpus-generation gauge uses numeric `nodes_version`, and the query-duration histogram remains two-valued so Plan 05 does not depend on Plan 06.
- D-41 metadata is assembled once at the terminal owner, uses epoch milliseconds, explicitly handles `NOTICE_CODE_UNSPECIFIED`, and is mirrored to both the wire event and query span.

### Agreed Concerns

- **MEDIUM — Live integration assumptions remain blocking.** The Grafana Jaeger↔Loki↔Prometheus click-through and the Windows Docker Desktop bind-mount smoke cannot be proven by YAML or datasource-count tests. Keep the existing blocking `<human-check>` items in Plan 03 and do not treat a green automated suite as closure for these paths.
- **MEDIUM — Versioned API and export behavior still need execution-time proof.** The exact Rust OTel exporter features/SDK test exporters, semantic-convention constants, Collector 0.159.0 component identifiers, and OTel-to-Prometheus series-name transformation must be confirmed by the pinned dependencies and live scrape. The plans already assign these to explicit assumptions or summaries; they remain implementation gates rather than facts to guess.
- **LOW — Test lifecycle and failure-path evidence need care.** In-memory providers must be isolated/reset per test, scoped subscribers must remain non-global, and bounded shutdown/error paths should be exercised without hanging or dropping buffered telemetry. These are especially important for exporter fallback, SSE interruption, and ignored live-Collector tests.
- **LOW — Privacy and boundedness must remain enforced during implementation.** Neither review found a design-level privacy hole, but all new span/log/metric attributes still need to exclude query/document content, prompts, answers, and unbounded identifiers, including on ingestion and error paths.

### Divergent Views

- **Overall risk:** AgY assessed the revised plans as **LOW** and ready to execute. Cursor assessed them as **MEDIUM**, primarily because it reported instruction/path mismatches that would make literal execution unsafe.
- **Cursor identifier/path findings:** Rechecking the current revised plans does not reproduce several of those claims: Plan 03 names `docker-compose.yml` in its frontmatter and actions (`06.2-03-PLAN.md:9`, `:131`), the root guideline files are named `rust-guidelines.md` and `go-guidelines.md`, and the test gates are intentionally invoked as `sh scripts/...`. Treat those specific mismatches as unconfirmed reviewer observations, not as new plan defects, unless a fresh tree comparison finds different text.
- **Residual execution risk:** Cursor's valid caution about exact SDK features and live Prometheus names is already represented as flagged assumptions and live verification in the revised plans. AgY additionally emphasizes reset/isolation of in-memory metric and span state and explicit handling of stream/export failure paths; these should be retained as implementation checks rather than trigger another broad plan rewrite.

### Risk Assessment

**Overall risk: MEDIUM (integration/API verification), not architectural.** The revised plans closed the previously identified high-severity instruction gaps. Remaining risk is concentrated in pinned-library API details, live Collector/backend behavior, and host-specific Docker verification. The phase is ready for execution after those gates remain explicit and blocking where marked.
