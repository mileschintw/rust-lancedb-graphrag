# Cross-AI Plan Review — Phase 06.2

## Antigravity Review

### Summary

The Phase 06.2 implementation plans present a comprehensive, production-grade observability architecture satisfying OBS-01 across the Go API gateway and Rust RAG engine. Across five ordered waves, the plans bridge tracing, operational metrics, and correlated logging into an OpenTelemetry Collector topology fanning out to Jaeger, Prometheus and Loki, with an auto-provisioned Grafana pane. Critical cross-runtime contracts — W3C propagation without wire UUID mutation (D-27/D-28), construction-time span parenting in `WorkflowRunner::run_node` and `engine/src/ingest.rs`, strict cardinality enforcement on D-35 metrics, and unified D-41 `degraded_mode` derivation — are grounded in exact source seams. All high-severity instruction and symbol discrepancies from prior reviews have been resolved in the current plan specifications.

### Strengths

- **Authoritative W3C propagation seams:** Plan 01 extracts the OpenTelemetry context from `request.metadata()` before `request.into_inner()` in `engine/src/service.rs:738-743`, while preserving the independent `correlation_id` UUID.
- **Subscriber isolation:** Plan 01 decouples global subscriber registration from test execution through an install-free `build_providers_and_layers` builder and scoped subscribers, matching existing tests in `engine/src/tests.rs:7038-7130`.
- **Ambient observation fields:** Plan 02 declares `graph_augmentation` on both the graph node and leaf spans, preserving the single recording site at `engine/src/service.rs:479` and the existing end-to-end assertions.
- **Lexical span parent binding:** Plan 04 moves `index_document` span construction at `engine/src/ingest.rs:1676-1680` inside the instrumented `ingest_document` block, so the document stages nest correctly.
- **Many-to-one rebuild causality:** Plan 04 buffers `SpanContext` values in `RebuildTriggerLinks`, caps them at 1024, records dropped links, and attaches them as links to `index_rebuild`.
- **Separated metric and wire semantics:** Plan 05 keeps `lancet.rag.query.duration` two-valued and scopes `lancet.rag.answer.degraded` to `answer_basis != RETRIEVAL`, leaving notice-inclusive `degraded_mode` to Plan 06.
- **Precise logging seams:** Plan 06 keeps `compensateFailedIngest` detached from request cancellation while threading context through `writeWorkflowEvent` for request-owned checkpoint logs.
- **Exhaustive degradation and predicate handling:** Plan 06 explicitly maps `NOTICE_CODE_UNSPECIFIED` to the non-degrading arm and defines `reformulation_used` so the default pass-through path is false.

### Concerns

- **MEDIUM — Live Docker Desktop Grafana correlation remains unverifiable by automated tests.** Plan 03's Windows bind-mount check and Jaeger-to-Loki click-through are necessary because provisioning can return HTTP 200 while mounts or `filterByTraceID` behavior are wrong.
- **LOW — Collector internal telemetry polling may be flaky.** The ignored `telemetry_otlp_export_reaches_collector` test in Plan 01 depends on batch processors flushing under cold starts and resource-constrained environments.
- **LOW — Prometheus metric-name suffix transformation can drift.** Plan 03 and Plan 05 must use the names observed from the live Collector exposition endpoint rather than predicted dot-to-underscore and unit-suffix transformations.

### Suggestions

1. Treat Plan 03's Windows bind-mount and Grafana trace-to-log checks as blocking gates before closing the phase.
2. Run the dashboard panel cross-check against the live Collector exposition endpoint before closing Plan 05.
3. Instantiate fresh in-memory metric readers and span exporters per test, or reset them explicitly, to avoid parallel test contamination.

### Risk Assessment

**Overall risk: LOW.** The revised suite is structurally sound, preserves wire and schema contracts, keeps telemetry non-load-bearing under D-38, and aligns dependency and wave boundaries. Remaining risk is concentrated in live Docker/Grafana verification, Collector flush timing and runtime metric-name transformation.

## Cursor Review

### Summary

The six Phase 06.2 plans still match the intended OBS-01 / D-27–D-43 design: W3C propagation before tonic `into_inner()`, runner-owned node spans, leaf spans at real I/O, SSE covered by `otelhttp` rather than a second root, ingest parent binding at span construction, rebuild links rather than a fake parent, bounded D-35 instruments, Collector fan-out, and one `degraded_mode` derivation for D-41. Those seams line up with the current tree at `engine/src/service.rs:738-857`, `engine/src/workflow/runner.rs:318-357`, `gateway/main.go:533-631`, `engine/src/ingest.rs:1676-1724`, and `proto/lancet/v1/lancet.proto:231-253`. The review nevertheless reported instruction and contract drift that would make literal execution unsafe.

### Strengths

- **Correct W3C and metadata timing:** `query_rag` consumes the request at `engine/src/service.rs:742`; Plan 01's extraction-before-consumption and construction-time `set_parent` rule matches the `tracing` parent model.
- **Correct SSE ownership:** `queryRAG` reads and writes the stream inside one handler in `gateway/main.go:533-631`, so Plan 02's prohibition on a second server span is correct.
- **Correct node and leaf ownership:** `NodeKind` has five variants in `engine/src/workflow/node.rs:75-81`; `run_node` is the central dispatch point, while production I/O and the two `generator.generate` calls are real leaf boundaries.
- **Source-true ingestion diagnosis:** `index_document` is constructed at `engine/src/ingest.rs:1676-1680`, while graph extraction runs after the existing instrumented future closes; Plan 04's parent-binding diagnosis is correct.
- **Correct D-35 sites and numeric gauge:** Notice sites in `retrieve.rs`, `graph_context.rs` and `generate.rs`, plus `CorpusSnapshot.nodes_version: u64` in `workflow/ports.rs:15-24`, are the right recording boundaries.
- **Correct D-41 ownership:** `workflow_completed` currently leaves `metadata: None` in `engine/src/workflow/events.rs:365-373`; Plan 06 correctly assigns the wire metadata and gateway terminal-span handling.
- **Correct Compose port concern:** `docker-compose.yml:23-25` currently publishes Jaeger on host ports 4317/4318, so Plan 01 must move host OTLP ownership to the Collector.
- **Test isolation and live-export distinction are explicit:** The plans preserve scoped subscribers, install-free test builders and a separate ignored live-Collector check.

### Concerns

- **HIGH — Reported YAML/artifact path drift in Plan 01.** The review claimed that the plan's path metadata names the wrong tree even though the current repository uses `engine/`, `gateway/`, `docker-compose.yml` and `scripts/*test-targets.sh`.
- **HIGH — Reported Compose-file drift in Plan 03.** The review claimed the plan targets a different Compose filename and an unprofiled `db` service, while the current Plan 03 names the root `docker-compose.yml` and explicitly describes the existing unprofiled PostgreSQL service.
- **HIGH — Reported Go module/API drift in Plan 01.** The review claimed the plan uses non-existent contrib module paths, while the current dependency block at `06.2-01-PLAN.md:224` names `otelhttp`, `otelgrpc` and `otelzap` at their researched module coordinates.
- **HIGH — Reported D-35 and D-43 vocabulary drift.** The review claimed Plans 01/03/05 use inconsistent metric and service-name contracts. The current plans explicitly freeze the ten instrument names in Plan 03 (`06.2-03-PLAN.md:224`), consume that list in Plan 05 (`06.2-05-PLAN.md:112-127`), and use `lancet-engine` / `lancet-gateway` in Plan 01 (`06.2-01-PLAN.md:49`).
- **MEDIUM — Guideline and test-script path findings were reported.** The current repository contains `rust-guidelines.md`, `go-guidelines.md`, `scripts/engine-test-targets.sh` and `scripts/gateway-test-targets.sh`, and the plans intentionally invoke the POSIX scripts through `sh` on Windows.
- **MEDIUM — D-41 field and enum handling must remain generated-name accurate.** The current Plan 06 explicitly names `NOTICE_CODE_UNSPECIFIED` and requires `Unspecified` in the false arm at `06.2-06-PLAN.md:251`, but implementation must preserve that exhaustive match.
- **MEDIUM — Ingestion LLM/graph I/O leaf inventory may be incomplete.** D-30 and the research describe graph queries and LLM calls in ingestion; Plan 04 adds the outer `graph_extraction` span but does not explicitly add per-attempt LLM or graph-query leaf spans on that path. The plan should either make the outer-span scope an explicit phase exception or add the missing leaves.
- **MEDIUM — Live correlation and Windows mounts remain assumptions.** Plan 03's `allow_structured_metadata`, Grafana correlation configuration and Git Bash mount instructions require the blocking human checks because datasource/API success alone cannot prove click-through behavior.
- **MEDIUM — Rust OTLP transport and `tonic` feature alignment remain runtime gates.** Plan 01 correctly leaves the `grpc-tonic` versus `tonic` feature and possible dual-`tonic` graph unresolved until the pinned crate feature table and `cargo tree -i tonic` are checked.
- **LOW — End-to-end propagation proof is compositional.** The Plan 01 unit tests share a traceparent fixture but do not observe one HTTP → gRPC → `query_rag` process; the live Compose smoke is needed for that stronger claim.

### Suggestions

1. Recheck every disputed path and symbol with exact-byte tree comparisons before changing plan text; do not act on a finding where the reported “wrong” and “right” names are identical.
2. Keep the explicit ten-name metric contract and the separate `lancet.rag.answer.degraded` versus D-41 `degraded_mode` semantics.
3. Preserve Plan 06's explicit `Unspecified` false arm and generated protobuf field names.
4. Decide explicitly whether ingestion requires per-call graph/LLM leaf spans under D-30, then reflect that decision in Plan 04's acceptance criteria and tests.
5. Keep blocking human checks for Grafana trace/log click-through and Windows bind mounts; do not let datasource polls close SC5/SC6.

### Risk Assessment

**Overall risk: HIGH for literal execution of the review's reported path/module findings; MEDIUM for the architecture once those claims are reconciled.** The span, propagation, lifecycle and cardinality design is grounded in the repository. The remaining genuine risk is implementation-time verification of pinned SDK features, live Collector/Loki/Grafana behavior, and whether ingestion needs finer-grained external-call spans.

## Consensus and Reconciliation

### Agreed strengths

- W3C propagation is placed before request consumption and keeps the wire `correlation_id` separate from the OpenTelemetry trace identity.
- Workflow node spans are runner-owned; leaf spans belong at real external-I/O boundaries; the SSE path uses the existing synchronous `otelhttp` root rather than a duplicate manual root.
- Ingestion requires construction-time parent binding for `index_document`, and coalesced rebuilds use bounded span links rather than a single misleading parent.
- D-35 dimensions are bounded, the corpus-generation gauge uses numeric `nodes_version`, and query duration remains two-valued so Plan 05 does not depend on Plan 06.
- D-41 metadata is owned by the terminal workflow emitter, uses epoch timestamps, and explicitly handles the protobuf zero-value notice code.

### Reconciled disagreements

- The Cursor path/module findings are not reproduced by the current files. Direct checks found the sole root Compose file `docker-compose.yml`, both root guideline files, both test-count scripts, the Plan 03 ten-name list, the Plan 05 handoff to `06.2-03-SUMMARY.md`, and the researched Go module coordinates in `06.2-01-PLAN.md:224`. These should not be carried forward as unresolved plan defects.
- The reviewers' different risk labels therefore describe different scopes: Antigravity assessed the revised design after the corrections; Cursor reported a literal-execution hazard based on path comparisons that conflict with the current plan text.
- The ingestion leaf-span observation is the one substantive cross-plan issue not already clearly closed by the current plan dispositions. D-30's research explicitly mentions graph queries and LLM calls in ingestion, while Plan 04's concrete contract names the outer `graph_extraction` span. Treat this as a medium implementation/contract gate.

### Remaining gates

- Resolve and record the exact pinned Rust OTLP transport and in-memory exporter features before dependency changes; run `cargo tree -i tonic` and keep the result in the Plan 01 summary.
- Validate Collector component identifiers inside the pinned 0.159.0 image.
- Bring up the stack from a clean Windows Docker Desktop state and manually verify non-empty mounts, service health, Jaeger-to-Loki trace-to-log navigation, and Loki-to-Jaeger derived-field navigation.
- Observe Prometheus series names from the live Collector scrape before finalizing dashboard PromQL.
- Keep in-memory exporters/readers isolated per test and retain the ignored live export-arrival test.
- Decide and document whether D-30 requires per-attempt ingestion LLM/graph leaf spans, or explicitly scope the outer `graph_extraction` span as sufficient.

### Overall assessment

**MEDIUM integration risk; low architectural risk.** The current plan suite is coherent and the previously documented path, naming and enum corrections are present. It is ready for execution only with the live infrastructure checks, pinned-library verification and ingestion leaf-span decision above kept explicit and blocking where applicable.
