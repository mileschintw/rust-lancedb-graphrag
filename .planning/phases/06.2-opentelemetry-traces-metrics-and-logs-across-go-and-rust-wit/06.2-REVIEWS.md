# Cross-AI Implementation Plan Review: Phase 06.2 — OpenTelemetry Traces, Metrics, and Logs (OBS-01)

## Executive Assessment

The implementation plan suite for Phase 06.2 (`06.2-01-PLAN.md` through `06.2-06-PLAN.md`) presents an exceptionally well-structured, production-grade telemetry architecture for Lancet's split Go gateway / Rust engine stack. It operationalizes OpenTelemetry across all three signals (traces, metrics, logs) and fans them out through an OTel Collector to Jaeger, Prometheus, and Loki, visualized through file-provisioned Grafana dashboards.

The review verified every claim, path, line reference, and symbol against the actual codebase at `D:\Repos\lancet`. The plans exhibit high architectural maturity: they avoid common distributed tracing pitfalls (such as context loss across async boundaries, duplicate node spans, and high-cardinality metric labels), honor existing wire and storage contracts, and maintain strict scope discipline.

Below is the detailed review for each plan and cross-cutting architectural assessments.

### Plan 06.2-01: Tracer Foundation, Cross-Runtime W3C Propagation & Compose Stack

#### 1. Summary

Plan 06.2-01 establishes the minimal end-to-end "tracer slice." It wires W3C `traceparent` propagation from Go HTTP ingress (`otelhttp`) across gRPC client stats (`otelgrpc`) into tonic metadata extraction in Rust, initializes all three signal providers in both runtimes, records one domain metric (`lancet.rag.query.duration`), logs through an OTel bridge at one request-owned site, implements fail-closed configuration validation (D-84), and updates Docker Compose with an `observability` profile and Collector configuration.

#### 2. Strengths

- **Resolved Order-of-Initialization Bug:** Correctly identifies that [`engine/src/main.rs:23-25`](file:///D:/Repos/lancet/engine/src/main.rs#L23-L25) currently initializes the subscriber before [`load_settings()`](file:///D:/Repos/lancet/engine/src/main.rs#L26), and inverts the order so `settings.engine.telemetry` configures the single subscriber registry.
- **Tonic Extraction Ordering:** Correctly places metadata extraction in [`engine/src/service.rs:740-743`](file:///D:/Repos/lancet/engine/src/service.rs#L740-L743) strictly *before* `request.into_inner()` consumes the request wrapper.
- **Host Port Collision Prevention:** Eliminates the port collision on `127.0.0.1:4317/4318` by removing host OTLP port publications from Jaeger in [`docker-compose.yml:24-25`](file:///D:/Repos/lancet/docker-compose.yml#L24-L25), reserving host loopback OTLP ports exclusively for the Collector.
- **File Disjointness & Ownership Fence:** Pre-declares empty test modules `telemetry_ingest.rs` and `telemetry_metrics.rs` in [`engine/src/lib.rs`](file:///D:/Repos/lancet/engine/src/lib.rs#L19-L28) during Wave 1 so subsequent plans in Waves 3 and 4 remain completely file-disjoint.
- **Strict Continuity:** Preserves the existing `correlation_id` wire contract on [`WorkflowEvent.trace_id`](file:///D:/Repos/lancet/engine/src/workflow/mod.rs#L79) and response headers while treating the OTel `SpanContext` as authoritative for telemetry.

#### 3. Concerns

- **[MEDIUM] Rust Test Subscriber Re-Initialization in Unit Tests:** `tracing_subscriber::registry().init()` or `set_global_default` can only be invoked once per process. Unit tests in `engine/src/tests/telemetry_query.rs` that instantiate in-memory tracer providers must use `tracing::subscriber::with_default` or an idempotent `std::sync::Once` test helper rather than global initialization, otherwise parallel test runs will panic on subsequent calls.
- **[LOW] Path Variable Formatting in Validation Shell:** The verification command `docker run --rm -v "$(pwd)/deploy/collector:/etc/otelcol:ro" ...` relies on `$(pwd)`. In Windows PowerShell environments, `$(pwd)` resolves to a .NET `PathInfo` object which can break volume mount parsing if not converted to POSIX format or executed within Git Bash / WSL.

#### 4. Suggestions

- Explicitly document in `engine/src/telemetry/mod.rs` or `testkit` that unit tests testing telemetry layer subscriber output should use scoped subscriber guards (`tracing::subscriber::with_default`) rather than attempting global subscriber installation.

#### 5. Risk Assessment

- **Risk Level: LOW**. The plan attacks the highest-risk integration seams early on the cleanest context, backed by deterministic test fixtures with identical pinned trace IDs (`00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`).

### Plan 06.2-02: Query-Path Span Surface & SSE Root Span Lifecycle

#### 1. Summary

Plan 06.2-02 instruments the entire synchronous query path: five runner-owned node spans (`query_reformulation`, `hybrid_retrieval`, `graph_context_extraction`, `prompt_assembly`, `llm_generation`), leaf spans at real I/O boundaries (`embedding_request`, `dense_search`, `bm25_search`, `graph_traversal`, and `llm_attempt`), and attaches terminal outcome facts and status to the gateway's SSE server span.

#### 2. Strengths

- **Single Span Ownership for Nodes:** Node spans are created exclusively in [`engine/src/workflow/runner.rs:318-360`](file:///D:/Repos/lancet/engine/src/workflow/runner.rs#L318-L360) (`run_node`) via an exhaustive `match NodeKind` without wildcard arms. Individual node implementations in `engine/src/workflow/nodes/*.rs` are prohibited from creating node spans, preventing span duplication.
- **Leaf Spans at True External Call Sites:** Places leaf spans on the production adapter structs in [`engine/src/service.rs:417-600`](file:///D:/Repos/lancet/engine/src/service.rs#L417-L600) (`ProductionEmbeddingPort`, `ProductionGraphQueryPort`, `ProductionDenseRetrievalPort`, `ProductionBm25RetrievalPort`) and the two `generator.generate` calls in [`engine/src/workflow/nodes/generate.rs:114,140`](file:///D:/Repos/lancet/engine/src/workflow/nodes/generate.rs#L114), ensuring test doubles/fakes do not emit phantom I/O spans.
- **Retry Observability:** Generation retries appear as two sibling `llm_attempt` spans with `attempt = 1` and `attempt = 2`, making retry latency and outcomes transparent.
- **No Manual Root Span Duplication:** Leverages the synchronous nature of [`gateway/main.go:533-630`](file:///D:/Repos/lancet/gateway/main.go#L533-L630) (`queryRAG`), where the `otelhttp.NewHandler` server span naturally encloses the full SSE stream lifetime, recording terminal attributes directly onto the active request span.

#### 3. Concerns

- **[LOW] BoxFuture Instrumentation in Port Adapters:** Port adapters return `workflow::node::BoxFuture<'a, ...>`. Wrapping async operations must ensure the span is attached via `.instrument(span)` to the returned pinned future so the span context follows across `.await` points inside Tokio tasks.

#### 4. Suggestions

- Ensure that `lancet.notice_codes` recorded at the terminal SSE frame in `gateway/main.go` uses sorted, deduplicated string representations of the enum names (e.g. `RETRIEVAL_DEGRADED_DENSE`) rather than enum integer values or localized message text.

#### 5. Risk Assessment

- **Risk Level: LOW**. Implementation is strictly additive around existing state machine dispatches without changing control flow, timeouts, or cancellation logic.

### Plan 06.2-04: End-to-End Ingestion Traces & Linked Rebuild Spans

#### 1. Summary

Plan 06.2-04 extends distributed tracing across the asynchronous document ingestion pipeline: spans the document upload/admission RPC in Go/Rust, carries W3C trace context across the bounded channel via `IngestionJob.trace_parent`, encloses worker chunking, embedding, staging write, and graph extraction in a single `ingest_document` span, and creates an `index_rebuild` span linked via OTel Span Links to all triggering documents coalesced in the debounce window.

#### 2. Strengths

- **Resolves Worker Span Scope Gap:** Directly fixes the reality in [`engine/src/ingest.rs:1681-1715`](file:///D:/Repos/lancet/engine/src/ingest.rs#L1681-L1715) where `extract_and_persist_entities` (line 1689) currently runs *after* the `index_document` span (lines 1676-1685) has already terminated, enclosing both inside the new `ingest_document` parent span.
- **Accurate IngestionJob Audit:** Verified that exactly 4 struct-literal construction sites exist ([`ingest.rs:377`](file:///D:/Repos/lancet/engine/src/ingest.rs#L377), [`service.rs:683`](file:///D:/Repos/lancet/engine/src/service.rs#L683), [`tests.rs:4402`](file:///D:/Repos/lancet/engine/src/tests.rs#L4402), [`tests.rs:4419`](file:///D:/Repos/lancet/engine/src/tests.rs#L4419)), while all other 55 sites use [`IngestionJob::new`](file:///D:/Repos/lancet/engine/src/ingest.rs#L131), which defaults `trace_parent` to `None`.
- **Accurate Many-to-One Causality via Span Links:** Recognizes that debounced index rebuilds coalesce multiple documents; rather than misattributing the rebuild to a single arbitrary parent, it creates a root `index_rebuild` span carrying OTel Span Links to each triggering document trace context.
- **SDK Ordering Compliance:** Drains the trigger link buffer *before* constructing `index_rebuild`, respecting the Rust OTel SDK requirement that links must be provided during span creation.

#### 3. Concerns

- **[LOW] Trigger Buffer Concurrency:** Threading the `Arc<Mutex<Vec<SpanContext>>>` trigger buffer into [`spawn_worker_with_boundary`](file:///D:/Repos/lancet/engine/src/ingest.rs#L1627) and [`spawn_rebuild_debounce_task`](file:///D:/Repos/lancet/engine/src/ingest.rs#L1548) must use a standard non-blocking mutex lock (or bounded cap) to ensure worker indexing is never blocked by a slow debounce drain.

#### 4. Suggestions

- Explicitly enforce a maximum buffer capacity (e.g. 1,024 entries) with a dropped/overflow counter attribute (`lancet.index.rebuild.dropped_links`) to guard against unbounded memory growth during extreme ingestion spikes.

#### 5. Risk Assessment

- **Risk Level: LOW**. The design preserves existing queue capacity ([`QUEUE_CAPACITY = 100`](file:///D:/Repos/lancet/engine/src/ingest.rs#L13)), rollback logic on indexing failure, and the rebuild watch notification channel.

## Consensus Summary

The reviewers agree that the six-wave architecture is correctly ordered and that the core design choices are strong: standard W3C propagation, runner-owned node spans, production-adapter leaf spans, `otelhttp` coverage for the synchronous SSE stream, Collector fan-out, loopback-only exposure, bounded metric dimensions, and terminal-owned D-41 metadata. Both reviewers verified the plans against the live repository rather than reviewing plan text alone.

### Agreed Strengths

- Wave order and file ownership are coherent: foundation first, query/deployment work in parallel, then ingestion, metrics, and log/metadata completion.
- W3C metadata must be extracted before tonic `Request::into_inner()`, while the existing wire `correlation_id` remains separate from the authoritative OTel trace ID.
- Node spans belong in `WorkflowRunner::run_node`; leaf spans belong at real external-call boundaries, with async futures instrumented so context survives awaits.
- The current synchronous SSE handler can use the `otelhttp` server span as the root without adding a duplicate manual root.
- Compose must leave PostgreSQL unprofiled, move Jaeger OTLP host publication out of the way, and reserve loopback Collector ports.
- Privacy and cardinality constraints are appropriately explicit: no raw query/content/API keys in telemetry and no unbounded metric labels.
- D-40’s typed dashboard source plus committed generated JSON and D-41’s single terminal fact assembly are good contract boundaries.

### Agreed Concerns

- **Subscriber test isolation:** production/global subscriber initialization must not be reused by parallel unit tests that already rely on scoped subscribers; the plans need an explicit test-only scoped-subscription seam.
- **Async span context and parent attributes:** leaf instrumentation must preserve context across `await`/`BoxFuture` execution and must not cause existing attributes such as `graph_augmentation` to be recorded on a new leaf span that does not declare them.
- **Provisioning assumptions need blocking verification:** the exact Grafana/Loki trace-to-log click-through and Windows Docker Desktop Compose smoke remain integration assumptions and should stay blocking human checks.

### Divergent Views

- Antigravity assessed the suite as **LOW risk / APPROVED with minor operational suggestions**, while Cursor assessed it as **MEDIUM–HIGH risk** because several plan instructions would fail or silently lose telemetry if followed literally.
- Antigravity accepted Plan 06.2-04’s ingestion nesting as correctly diagnosed and implemented; Cursor found the stated insertion range would leave `index_document` outside `ingest_document` and also found `engine/src/main.rs` missing from the modified-file list.
- Antigravity treated Plan 06.2-06’s request/background logging classification as sound; Cursor found the compensation and checkpoint sites lack request context and that `NOTICE_CODE_UNSPECIFIED` must be handled explicitly.

### Recommended Planning Action

Feed this review back into planning before execution. Resolve Cursor’s HIGH findings first: add or correctly thread the request-scoped log site, define scoped telemetry test initialization, retarget `graph_augmentation` after leaf spans are introduced, enter `ingest_document` before `index_document`, include `engine/src/main.rs` in Plan 04’s file ownership, and make the D-35 degraded outcome plus D-41 notice classification a single explicit rule.
