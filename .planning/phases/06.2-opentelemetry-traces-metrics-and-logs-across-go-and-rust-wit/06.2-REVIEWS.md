Secondary issues: the plans pin a Collector image version that does not match the one in `docker-compose.yml`, and Plan 09's "exporters follow the helper" test is structurally at risk of being tautological.

## 3. Concerns

### HIGH — Plan 07's live probe is blind to the unit-suffix half of the naming contract

**Evidence.** Plan 07 Task 1 specifies the probe instrument as `lancet.ingest.documents` and asserts only `lancet_ingest_documents` present / `lancet_lancet_ingest_documents` absent. But `engine/src/telemetry/metrics.rs:78` and `:151` both call `.with_unit("ms")`:

```rust
.u64_histogram("lancet.rag.query.duration").with_unit("ms")      // metrics.rs:76-79
.u64_histogram("lancet.index.rebuild.duration").with_unit("ms")  // metrics.rs:149-152
```

and the committed dashboard queries the `_ms` form:

```
"expr": "sum by (outcome) (rate(lancet_rag_query_duration_ms_count[5m]))"          // lancet-rag-operations.json:20
"expr": "histogram_quantile(0.95, sum(rate(lancet_index_rebuild_duration_ms_bucket[5m])) by (le, outcome))"  // :348
```

The Collector's Prometheus translator normalizes known unit abbreviations (`ms` → `milliseconds`) when appending metric suffixes. If that normalization is active in the running image, the exported series is `lancet_rag_query_duration_milliseconds_count`, and **those two panels stay broken after the namespace is removed** — the exact failure mode this plan exists to close.

The orchestrator's empirical repro (`lancet.test.probe` → `lancet_lancet_test_probe_total`) proves namespace doubling and `_total` suffixing, but a synthetic probe with no unit cannot say anything about unit translation. Plan 07 then picks another unit-less counter for its permanent gate, so the question stays unanswered — and the plan's Task 3 additionally instructs the executor to rewrite `06.2-03-SUMMARY.md`'s transformation rule to say "millisecond duration units append `_ms`", which would re-document a possibly-wrong rule as verified.

I cannot run the live scrape from here, so I am not asserting the `_milliseconds` outcome as fact — but that is the point: **the plan's own design makes it impossible for the executor to settle it either.**

**Fix:** make the probe push a histogram named with a `ms` unit (or, better, have `scripts/verify-collector-prom-export.sh` scrape once and assert **all ten** dashboard stems from `deploy/grafana/dashboards/lancet-rag-operations.json` are present, driving the stem list from the JSON rather than a hardcoded literal). If the unit does normalize, the plan needs a fourth decision recorded: drop `.with_unit("ms")` from the two histograms, or regenerate the dashboard (`deploy/grafana/dashboard_gen/main.go`) plus the stem list at `tests/telemetry_metrics.rs:761-772`.

### MEDIUM — Collector image pin drift: plans reference 0.159.0; the stack runs 0.120.0

**Evidence.** `docker-compose.yml:65` is `otel/opentelemetry-collector-contrib:0.120.0`, and the config uses the older component aliases consistent with it (`otlp/jaeger` at `otel-collector-config.yaml:19`, `otlphttp/loki` at `:23`) — not the `otlp_grpc` / `otlp_http` identifiers RESEARCH and `06.2-03-PLAN.md:139` declared canonical for 0.159.0. So Plan 03's in-image validation gate (`06.2-03-PLAN.md:153`, `docker run ... :0.159.0 validate`) validated a config against an image the stack does not run.

Plan 07 inherits this: it removes the namespace but runs **no** in-image `validate` at all, and its behavior/acceptance never names the running image. Since unit-suffix and name-normalization behavior is version-sensitive, this drift compounds the HIGH above.

**Fix:** add `docker run --rm -v ... otel/opentelemetry-collector-contrib:0.120.0 validate --config=...` to Plan 07 Task 1's `<verify>`, sourcing the tag from `docker-compose.yml` rather than a literal, and record the actual running version in `06.2-07-SUMMARY.md` alongside the scraped line.

### MEDIUM — Plan 09's "exporters follow the helper" test is structurally at risk of being tautological

**Evidence.** Plan 09 Task 2 behavior asks to assert "the insecure option is not applied" for trace/metric/log exporters. OTel Go exporter options (`otlptracegrpc.Option`, etc.) are opaque closures over unexported config structs — they cannot be introspected from a test. The plan anticipates this and offers a fallback: "a package-level function that returns `insecureSelected bool` for a given endpoint." But that function *is* `otlpEndpointSecurity` under another name, so `TestOTLPExportersFollowEndpointSecurity` would re-assert Task 1's test and prove nothing about the three call sites at `telemetry.go:121-124,151-154,171-174`.

The only load-bearing gate in Plan 09 Task 2 is the grep-shaped acceptance criterion ("the insecure constructor must appear only inside the `!useTLS` branch"), which is a source check, not a behavioral one.

**Fix:** either (a) accept this honestly — make the grep the named gate, mark the second test as coverage-only, and say so in the summary; or (b) get a real behavioral assertion by standing up a TLS-terminated in-process gRPC listener and confirming an `https://` endpoint completes a handshake while an `http://` one does not. Option (a) is proportionate for a local-only project; option (b) is the only thing that actually proves the branch.

## 4. Suggestions

1. **Rewrite Plan 07's probe as a full-contract scrape.** Have `scripts/verify-collector-prom-export.sh` parse the ten `"expr"` values out of `deploy/grafana/dashboards/lancet-rag-operations.json`, extract the metric stems, and assert every one appears in the `:8889` scrape after driving one real query and one real ingestion. That makes the script the actual SC5/SC6 gate instead of a single-counter smoke, and it structurally cannot miss the unit-suffix problem.

2. **Pin the probe and any `validate` invocation to the tag in `docker-compose.yml`**, not to a literal, and record the resolved tag in `06.2-07-SUMMARY.md`. The 0.120.0-vs-0.159.0 drift is exactly the class of thing that makes "we verified it live" untrustworthy.

3. **Make Plan 07's SUMMARY correction conditional on the scrape, in the plan text.** Right now Task 3 pre-writes the expected rule ("dots→underscores, `_total`/`_bucket`, `_ms` from `with_unit`"). Replace that with "transcribe the observed line verbatim, then derive the rule from it" — the same anti-prediction discipline Plan 03 stated but did not achieve.

4. **Add an explicit re-run row for the four blocking manual checks** to `06.2-VALIDATION.md`, owned by the wave-6 close-out rather than by the already-executed plans whose `<human-check>` blocks they currently sit in.

5. **Downgrade Plan 09 Task 2's second test to coverage-only and promote its grep to the gate**, or replace it with a real TLS listener. Shipping a test that only re-asserts Task 1 under a name implying end-to-end coverage is the same "green-on-doubles" pattern the phase has already been burned by twice.

6. **Fix the two command-level bugs** (`grep -c` exit status in Plan 07 acceptance; `-count=0` in Plan 09 Task 2) before dispatch — both are the kind of thing that costs a build cycle and reads as a real failure.

### Concerns

#### HIGH — Plan 10's live poll can force a destructive false-positive recovery

The poll rejects any `"tags"` substring in the entire datasource response (`06.2-10-PLAN.md:194`). Grafana may serialize an omitted field as `"tags":[]` or `"tags":null`; this is an assumption about the live API, but either form would fail the poll even when `tracesToLogsV2.tags` is absent. The fallback `docker compose ... down -v` deletes Compose volumes, so a false positive can wipe local Prometheus/Loki/Grafana state. Check the structured `jsonData.tracesToLogsV2` object and reserve `down -v` for evidence that that object still contains the invalid mapping.

#### MEDIUM — Plan 12's `filter::Targets` rationale is technically false

The plan says `Targets` uses `::`-segment prefix matching. The vendored implementation uses `meta.target().starts_with(&target[..])` at `tracing-subscriber-0.3.23/src/filter/directive.rs:250-252`, so `opentelemetry` would match `opentelemetry_sdk`. Rejecting `Targets` is still correct because it cannot implement a running cap; retain that reason and remove the incorrect prefix explanation.

#### MEDIUM — Plan 12 contains stale construction-time SDK citations

`logger_provider.rs:58,67` are logger setup sites, but `:101` is shutdown; `meter_provider.rs:114` is also shutdown rather than construction. Level scoping remains justified by `batch_log_processor.rs:355-360` and the logger setup diagnostics at `logger_provider.rs:58-70`, but the stale line descriptions should be corrected.

#### MEDIUM — Pin acceptance contradicts the measurement rule

Plans 11 and 12 say to trust `cargo test -- --list` when it disagrees with the expected `+1`, but also require the final value to be exactly `+1` from the predecessor (`06.2-11-PLAN.md:214,235`, `06.2-12-PLAN.md:460,478`). Require measured values; keep `+1` only as a sanity check.

#### MEDIUM — Plan 12's unit tests do not exercise a dead Collector

The Go test invokes an injected handler and the Rust test exercises counter/filter behavior with a stand-in layer. They do not run the real background exporters against an unavailable Collector. This is acceptable only because the plan explicitly assigns runtime behavior to the Task 3 human check; the automated gates must not be presented as end-to-end outage proof.

#### MEDIUM — VALIDATION.md retains the obsolete manual-check owner

The Manual-Only table still names `06.2-07/T3` at `06.2-VALIDATION.md:123-128`. Plans 10–12 add new human checks but do not retarget that table, so a later verifier can miss the current owners.

#### LOW — Additional execution footguns

`grep -c "tags:"` can exit 1 on the successful zero-match case (`06.2-10-PLAN.md:163`); XML `&amp;&amp;` in verify blocks depends on execute-plan unescaping; the Plan 12 task says there are four Go startup warnings although `telemetry.go:151,179,197` has three; and Plan 11's `git checkout HEAD~1` fail-first route stages the old JSON and must be cleaned up exactly as specified.
