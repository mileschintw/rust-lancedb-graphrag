## 2. Strengths

- **Plan 12's layer-order analysis is verified, and the hazard is real.** `tracing-subscriber-0.3.23/src/filter/layer_filters/mod.rs:766-791` — `Filtered::enabled` returns `true` on the disabled branch specifically so per-layer filters don't short-circuit siblings. `src/layer/layered.rs:266-274` evaluates `self.layer` before `self.inner`, and `.with(L)` puts `L` in the `layer` slot. A shared counter with `limit = 1` would therefore have the bridge spend the slot and the console print only the suppression notice. Plan 12's decision to use a stateless drop filter on the bridge and keep counting state exclusively on the fmt layer is the correct fix, and its `T-06.2-12-08` registers it as its own high-severity threat with its own gates.

## 3. Concerns

### HIGH — Plan 10 fixes one direction of a two-direction check; the return direction has an independent, undiagnosed defect

`deploy/grafana/provisioning/datasources/datasources.yaml:33-37` configures the Loki→Jaeger return path as:

```yaml
derivedFields:
  - datasourceUid: jaeger-datasource
    matcherRegex: "trace_id=([0-9a-fA-F]+)"
```

Grafana's default `matcherType` for a derived field is `regex`, matched against the **log line body**. But the engine emits log records through `opentelemetry-appender-tracing` (`engine/src/telemetry/mod.rs:173-175`), so the body is just the message text and trace context rides as OTLP LogRecord trace fields, which Loki 3.x surfaces as **structured metadata** (`allow_structured_metadata: true` per `06.2-03-SUMMARY.md`). No log line contains the literal string `trace_id=`, so this regex will match nothing.

Plan 10's human check (Task 2) explicitly requires *both* directions: "follow a Loki log line's derived TraceID field back to Jaeger." Its only guard on this half is asserting that the `matcherRegex` string still exists in the file — presence, not function. So the plan can pass every automated gate, close the Jaeger→Loki direction correctly, and still fail its own closing evidence on a defect it does not name, with no diagnosis recorded for the next pass.

This is the same class as the WR-02 dashboard defect: the artifact is present and syntactically valid, the assertion checks presence, and the semantics are wrong.

**Fix:** either (a) change the Loki derived field to `matcherType: "label"` with `matcherRegex: "trace_id"` (Grafana ≥10.1 supports label-based derived fields, which is the correct mechanism for structured metadata), or (b) explicitly scope the Loki→Jaeger direction out of Plan 10's success criteria and record it as a separate gap so it is not silently attached to this plan's human check. Do not leave it as an unnamed dependency of the closing evidence.

I could not run the live stack to confirm the regex fails, so treat the mechanism as high-confidence-but-unverified; the *structural* problem — one direction guarded by presence only while the human check tests both — is verified from the plan text and the config file.

### MEDIUM — Plan 10's live poll is a three-level-nested Python construction where `jq` is available

Plan 10 Task 2 specifies a triple-nested `sh -c` → `python -c` quoting construction. `jq 1.8.2` is on PATH and expresses the same assertion in one clause:

```bash
jq -e '.jsonData.tracesToLogsV2 | (.filterByTraceID == true) and ((.tags // []) | map(select(.key == "trace_id")) | length == 0)'
```

The current form is likely to fail on a quoting error and read as a provisioning failure it is not — the exact false-negative→`down -v` path the prior review flagged, reached through a different door.

**Fix:** use `jq -e`. If `jq` must not be assumed, add it to the Task 1 precondition alongside `curl`.

### MEDIUM — Plan 12's cap of one line for the process lifetime is stronger silence than the failing UAT asked for

The UAT failure (`06.2-UAT.md` Test 4) was an *unbounded* stream at ~3s and ~10s intervals. Plan 12's remedy is `limit = 1` for the whole process lifetime in both languages, traced to D-38's "one startup warning."

But D-38's "one startup warning" governs *initialization*; this is the *runtime* export channel, and the two are different. After the first export failure, an operator running a long session gets zero further signal — including for a distinct failure hours later after the Collector recovered and broke again.

**Fix:** make the bound time-windowed rather than absolute — e.g. at most one diagnostic per N minutes, with the suppression notice re-armed on each window. If the lifetime cap is kept deliberately, say so in the SUMMARY as an accepted operational limitation.

### MEDIUM — Plan 11's fail-first demonstration is over-specified and touches the git index unnecessarily

Plan 11's acceptance criteria run six steps with two mutually exclusive git routes (`git stash push` vs `git checkout HEAD~1 -- path`), a topology precondition, and mandatory index-cleanup verification. A simpler route that never touches git:

```bash
cp deploy/grafana/dashboards/lancet-rag-operations.json /tmp/dash.bak
sed -i 's/histogram_quantile(0.95, sum(rate(lancet_rag_query_duration_milliseconds_bucket\[5m\])) by (le, outcome))/sum by (outcome) (rate(lancet_rag_query_duration_milliseconds_count[5m]))/' deploy/grafana/dashboards/lancet-rag-operations.json
cargo test ... -- duration_panels_query_histogram_buckets   # observe FAIL
cp /tmp/dash.bak deploy/grafana/dashboards/lancet-rag-operations.json
```

### LOW — Plan 11's panel will render a unitless number

Plan 11 forbids adding a Y-axis unit "to stay symmetric with panel 9." Since Plan 11 is already regenerating the dashboard to fix a *legibility* defect, setting `Unit("ms")` on both duration panels finishes the job.

### LOW — Plan 12's Go `SetupErrorHandler` will install during tests

`gateway/internal/telemetry/telemetry_test.go:227` (`TestCollectorUnavailable`) calls `Init`, which under Plan 12 calls `SetupErrorHandler()` first. Per `otel@v1.45.0/handler.go:24-30`, only the *first* `SetErrorHandler` call re-delegates previously-returned handlers. Harmless here, but worth a sentence in the SUMMARY.

### LOW — no plan closes WR-01, and Plan 12 is the cheap opportunity

`06.2-REVIEW.md` WR-01 records that `TestOTLPExportersFollowEndpointSecurity` only asserts non-empty option slices. Plan 12 already modifies `telemetry_test.go` and establishes a named-grep-gate pattern. Adding a real grep gate for CR-04 alongside it is one acceptance criterion.

### LOW — SC1 is being closed implicitly by Plan 10's human check with nobody saying so

`06.2-VERIFICATION.md` leaves SC1 as `PRESENT_BEHAVIOR_UNVERIFIED`. Plan 10's Task 2 human check requires observing "the gateway root span with the engine node spans nested beneath it" in Jaeger — which *is* the SC1 observation. No plan records the double duty.

**Fix:** add one line to Plan 10's `<human-check>` `expect` asking the operator to confirm the single continuous trace ID across gateway and engine spans, and cross-reference it from the SC1 row.
