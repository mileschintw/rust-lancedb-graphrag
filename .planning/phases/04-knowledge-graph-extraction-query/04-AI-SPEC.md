## 1. System Classification

**System Type:** Hybrid (Extraction + RAG)

**Description:**
This is the knowledge-graph extraction and query layer of Lancet, a local-first, systems-engineering-focused RAG/GraphRAG platform (Rust data-plane + Go control-plane). During ingestion it extracts open-vocabulary entities and relationships from each document chunk via a provider-neutral LLM call, resolves duplicate entity mentions (case-normalized exact match, scoped globally across the whole corpus per D-05), and persists the resulting node/edge graph in dedicated LanceDB tables. At query time it seeds a Cypher traversal (via `lance-graph`) from vector-matched entities and compiles the resulting neighborhood into a "Related Entities & Relationships" section that is interleaved with chunk evidence in the RAG answer prompt. The direct users are developers/practitioners who deploy or extend the Lancet engine to build their own document-Q&A or knowledge-exploration applications; the immediate downstream consumer of this phase's output is Phase 3's answer-generation LLM call, and one level further downstream, whoever reads the RAG answer that the graph context helped shape. "Good" looks like: entities that are the same real-world thing get merged and entities that are different real-world things stay separate; extracted relationships are traceable to the chunk text that supports them; and when extraction or traversal fails, that failure is visible enough for an operator to notice systemic degradation rather than letting answer quality erode silently over time.

**Critical Failure Modes:**
<!-- The 3-5 behaviors that absolutely cannot go wrong in this system -->
1. **Cross-entity conflation via over-aggressive global exact-match merging** — two distinct real-world entities sharing a normalized name (e.g. two people named "John Smith" in unrelated source documents) get merged into one node, and every edge attributed to either now corrupts answers about both. D-05 itself flags this as "costly to reverse" — unmerging later requires re-splitting nodes and re-attributing `source_chunk_ids`.
2. **Silent, accumulating extraction/traversal failures** — D-06 (per-chunk extraction failure is non-fatal) and D-32 (query-time graph failure silently falls back to chunk-only evidence) are both fail-open by design, so a chunk's entities or a query's graph augmentation can be dropped with zero operator-visible signal, letting answer quality degrade invisibly across many documents/queries before anyone notices a pattern.
3. **Fabricated (ungrounded) entities or relationships** — the extraction LLM call invents a relationship not actually stated in the chunk text (e.g. inferring "employed_by" from mere co-occurrence), and that fabricated edge is later surfaced into a RAG answer as if it were grounded fact, since graph facts are not citation-validated the way chunk `EvidenceBlock`s are (D-27).
4. **Relation-vocabulary fragmentation defeating traversal** — open freeform `relation_type` strings for the same real-world relationship diverge across chunks/documents (e.g. "founded_by" vs. "founder_of" vs. "was founded by"), so Cypher pattern queries and `relation_type` filters miss facts that are present in the graph but lexically scattered, silently shrinking what the graph can actually answer.
5. **Unbounded or mis-seeded traversal diluting answer quality** — an incorrect seed-entity match or an under-filtered neighborhood crowds the shared evidence token budget (D-29/D-30) with low-relevance graph facts, displacing higher-value chunk evidence instead of adding value.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Developer tooling / AI infrastructure — specifically GraphRAG-style knowledge-graph construction and query for retrieval-augmented generation. Lancet is a general-purpose, local-first RAG engine (not a vertical SaaS product), so this phase has no single regulated industry — the relevant "domain" is the practitioner discipline of building and operating production knowledge graphs feeding an LLM, and, transitively, whatever domain the documents fed into it happen to come from (which this phase does not control or know in advance).

**User Population:** Two layers. (1) Direct users: developers/practitioners who deploy, extend, or evaluate the Lancet engine (including anyone reviewing it as a systems-engineering portfolio artifact) — they interact with `QueryGraph`/`QueryRAG` gRPC calls, inspect logs/traces, and judge whether the graph layer behaves correctly. (2) Indirect/downstream users: whoever ultimately reads a `/rag/query` answer that graph context helped shape — an end user of whatever application is built on top of Lancet, who has no visibility into the graph layer at all and simply experiences a better- or worse-grounded answer.

**Stakes Level:** Medium — this is not a medical/legal/financial-critical system, and no single query failure is catastrophic. But it is not "no stakes" either: entity over-merging is explicitly flagged (D-05) as costly-to-reverse once corpus-wide, and because the platform is document-agnostic, it can be pointed at genuinely sensitive or high-consequence corpora (contracts, internal knowledge bases, research corpora) by a downstream deployer even though this phase doesn't know that in advance.

**Output Consequence:** Extracted entities/relations are persisted durably into LanceDB and become load-bearing for every future query that traverses them — a bad merge or a fabricated relationship, once written, silently biases every subsequent answer that seeds or traverses through that node until someone manually detects and corrects it (no auto-migration/auto-repair path per D-14/D-16's fail-fast posture). At query time, graph facts are blended directly into the prompt context for the final answer-generation call (D-26/D-27/D-29) — a practitioner or end user reading that answer has no built-in way to tell which claims came from graph traversal vs. chunk evidence, since graph facts are not citation-marked (D-27).

### What Domain Experts Evaluate Against

```
Dimension: Entity merge correctness (canonical identity fidelity)
Good: Two mentions are merged into one entity node only when a practitioner reviewing the merged node's contributing source_chunk_ids would agree they refer to the same real-world thing.
Bad: Entities that are different real-world things (e.g. two different people/organizations sharing a normalized name) get merged purely on case-normalized string equality, so relationships attributed to either now corrupt answers about both.
Stakes: Critical
Source: Production knowledge-graph-construction practitioner literature — over-merging is described as "a particularly insidious failure mode" that "corrupts your graph" and "loses the trust... that made it worth building" (Modern Data 101, "Entity Resolution at Scale"; Decoding AI, "How to Keep a Knowledge Graph Clean for AI Agents").

Dimension: Failure transparency (extraction & traversal path)
Good: Whenever a chunk's extraction fails or a query-time graph traversal errors, the failure is logged with enough context (chunk_id/document_id, error kind, attempt number per 4b.1) that an operator investigating a suspiciously chunk-only answer can determine whether graph augmentation was attempted and failed, versus never applicable.
Bad: Extraction/traversal failures are swallowed with no aggregate operator-visible signal — repeated failures accumulate unnoticed until someone happens to notice systemic degradation in answer quality.
Stakes: High
Source: RAG production-failure literature — "the defining trait of a failed production RAG system is that nothing crashes... the system is degrading on every axis that matters" underneath healthy-looking dashboards (Atlan, "RAG Evaluation: Metrics, Tools, and the Context Gap"; Digital Applied, "RAG Anti-Patterns").

Dimension: Relation-type coherence (open-vocabulary quality)
Good: Semantically equivalent relationships across chunks/documents converge on the same or closely related relation_type strings (e.g. consistently "founded_by"), so a Cypher query filtering on that relation_type actually finds the fact.
Bad: The same real-world relationship appears under many distinct freeform relation_type strings scattered across the corpus, so relation_type-filtered traversal misses facts that are semantically present but lexically fragmented.
Stakes: Medium
Source: Open-vocabulary information-extraction literature — LLM extraction is known to produce "schema drift, non-deterministic formatting, and inconsistencies across runs" absent constraining few-shot guidance (general IE/KG-construction practitioner consensus, corroborated by this project's own 4b.3 few-shot mitigation).

Dimension: Provenance-backed graph facts (extraction faithfulness)
Good: Every entity/relation surfaced in the "Related Entities & Relationships" prompt section traces back to explicit or clearly-implied text in a source chunk — spot-checking source_chunk_ids for a surfaced fact finds a chunk that plausibly supports it.
Bad: The extraction step invents a relationship not stated in the chunk text (e.g. inferring "employed_by" from mere co-occurrence), and that fabricated edge is surfaced into the RAG answer as if it were grounded fact, with no citation marker to flag it as graph-derived (D-27).
Stakes: High
Source: LLM knowledge-graph-extraction hallucination literature — "LLMs may hallucinate plausible but unsupported facts" during KG construction (Towards AI, "Why LLMs Fail at Knowledge Graph Extraction").

Dimension: Graph-augmentation signal-to-noise at query time
Good: Graph facts injected into the prompt are the ones most relevant to the user's query (correctly seeded, correctly ranked/interleaved with chunk evidence per D-29/D-30) — a practitioner reading the compiled prompt would say the graph section adds information the chunk evidence alone didn't have.
Bad: Traversal returns a broad, low-relevance neighborhood (or seeds on the wrong entity entirely) that crowds out higher-value chunk evidence within the shared token budget, diluting rather than improving answer quality.
Stakes: Medium
Source: "Less is More: Denoising Knowledge Graphs For Retrieval Augmented Generation" (arXiv:2510.14271) — noisy graph context measurably degrades RAG answer quality rather than helping it.
```

### Known Failure Modes in This Domain

1. **Cross-document entity conflation via global exact-match resolution** — common names collapse distinct real-world entities into one node under D-05's corpus-wide, case-normalized exact match; every edge later attributed to that node corrupts answers touching either original entity, and reversal requires manual re-splitting.
2. **Relation-vocabulary fragmentation** — because `relation_type` is a freeform LLM-assigned string with no fixed taxonomy (D-04), semantically identical relationships splinter into many surface forms across the corpus, so relation-filtered Cypher queries silently miss facts that are actually present in the graph.
3. **Silent query-time degradation with no completeness signal** — D-32's fail-open behavior for entity seeding/traversal errors means a query's "value add" from graph augmentation can quietly and permanently vanish for a given query pattern (e.g. a systematically failing seed lookup) with the response looking indistinguishable from a query that simply had no relevant graph context.
4. **Partial graph coverage masquerading as completeness** — D-06's per-chunk non-fatal extraction failure means an entity's edge list in the graph can be incomplete (some supporting chunks never contributed extractions) with no accessible signal distinguishing "this entity truly has no more relationships" from "extraction failed for some of its source chunks" — a practitioner querying the graph has no built-in way to tell the difference.

### Regulatory / Compliance Context

None identified as directly binding on this phase's implementation. Lancet is a local-first, self-hosted developer-tooling/portfolio system with no built-in vertical (healthcare, legal, finance) scope, and this phase does not itself collect or process any regulated data category. However, because the platform is document-agnostic and persists LLM-derived entities/relationships durably and globally (D-05, D-10–D-16), a deployer who points it at regulated content (e.g. contracts, health records, PII-bearing internal documents) would inherit obligations (GDPR/HIPAA-class data-handling, right-to-erasure against a graph with no per-record deletion/re-scoping story in v1) that this phase's schema and merge design do not currently account for — flagged here for any future deployment-hardening work, not treated as in-scope for this phase.

## 2. Framework Decision

**Selected Framework:** Native Rust stack — `lance-graph` (Cypher-over-Lance traversal) atop the existing `lancedb ~0.31` store; entity/relation extraction via the existing provider-neutral `Generator` trait (OpenRouter, per D-08). No framework from the AI-framework decision matrix applies — all candidates there (LangChain, LlamaIndex, LangGraph, CrewAI, OpenAI Agents SDK, Claude Agent SDK, AutoGen/AG2, Google ADK, Haystack) are Python/TypeScript-only, and this is a Rust engine by explicit architectural mandate (REQUIREMENTS.md Out-of-Scope rejects "a generic workflow-engine clone"; Rust-owns-semantics/Go-thin split from Phase 2 D-48).

**Version:** `lance-graph` 0.5.4, added with `default-features = false` (default features pull in `unity-catalog`/`delta` — cloud object-store, S3/Azure/GCS, and geospatial deps inconsistent with this project's local-first, no-new-infrastructure posture).

**Status:** CONFIRMED — empirically verified by the Phase 04 spike documented in 04-RESEARCH.md's `## Summary` and `## Code Examples`. The IPC bridge compiled and correctly round-tripped real data across the arrow ~58.3 / arrow ^56.2 version boundary, and `CypherQuery::execute()` was confirmed to take a plain `HashMap<String, RecordBatch>` rather than a path/URI or a typed `lance::Dataset` handle. Both of this section's original open spike questions are therefore resolved: Question 1 is answered directly by that `HashMap` signature, and Question 2 is moot — no code path in `lance-graph` 0.5.4 ever touches a `lance::Dataset` handle on this integration route, so the seven-major-version divergence between `lance-graph`'s bundled `lance-1.0.4` and `lancedb`'s `lance-8.0.0` never actually collides. This is the already-locked D-17/D-19 mechanism, not a fresh pick; the selector's job here was verification, and this phase's checked-in `engine/src/graph/{mod.rs,bridge.rs,tests.rs}` reproduces the proof as five passing, reproducible tests rather than a deleted scratch crate.

**Rationale:**
Extraction and traversal mechanisms are already locked by prior architectural decisions (D-08: extraction via `Generator` trait; D-17/D-19: traversal via genuine `lance-graph` Cypher queries rather than hand-rolled BFS). This phase's job is direct native integration, not framework selection. D-08 keeps model access provider-neutral (no framework-specific client); D-17/D-19 keep traversal expressive (Cypher) without introducing a second language/runtime or a cross-process boundary.

**Critical Finding (empirically verified, not inferred):**
`lance-graph` 0.5.4 requires `lance ^1.0.0` / `arrow ^56.2` / `datafusion ^50.3`. `lancedb ~0.31` requires `lance =8.0.0` / `arrow ^58.0.0` / `datafusion ^53.0.0`. Verified via `cargo add lance-graph` + `cargo tree --duplicates` in `engine/` (then fully reverted — `git status --porcelain` clean, `Cargo.lock` grep confirmed no residue): Cargo resolves **both major-version trees side by side** rather than erroring at resolution — meaning `lance-graph`'s types are structurally distinct from `lancedb`'s, not shared.

**Spike required before Phase 04 planning locks in D-17's implementation** (do not run this spike inside the AI-SPEC workflow — it is a planning-phase prerequisite):
1. Does `lance-graph`'s Cypher traversal API accept a path/URI (opens its own independent reader) or a typed `lance::Dataset` handle from the caller? If typed, this is a hard compile-time wall regardless of feature flags.
2. If path-based: can `lance-graph`'s bundled `lance-1.0.4` reader open a dataset manifest written by `lancedb 0.31`'s `lance-8.0.0` (seven major versions apart)?

If either answer is unfavorable, escalate to the fallback below before implementation begins.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangChain / LlamaIndex / LangGraph / CrewAI / OpenAI Agents SDK / Claude Agent SDK / AutoGen-AG2 / Google ADK / Haystack | All Python/TypeScript-only — would require a second runtime and a cross-process boundary, violating the Rust-owns-semantics/Go-thin split and REQUIREMENTS.md's explicit rejection of a generic workflow-engine clone |
| Hand-rolled DataFusion SQL traversal directly over the `entities`/`edges` LanceDB tables (live fallback, not ruled out) | Stays fully in-process Rust with zero dependency-graph conflict, but loses `lance-graph`'s Cypher ergonomics in favor of hand-written pattern-matching logic — this is what D-19 originally rejected in favor of `lance-graph`; becomes the fallback if the spike above confirms lance-graph/lancedb are incompatible |

**Vendor Lock-In Accepted:** No — model access stays provider-neutral via OpenRouter/`Generator` trait; `lance-graph` is a local, open-source, in-process dependency, not a hosted vendor.

**Correction to upstream artifact:** `04-CONTEXT.md`'s `canonical_refs` lists `lance-graph`'s repo as `github.com/lance-format/lance-graph`. The actual repo (per crates.io) is `github.com/lancedb/lance-graph`, published by the `lance-community` org. Not corrected in `04-CONTEXT.md` itself (out of this workflow's write scope — that file is a prior phase's gated artifact) — flagged here for the planner to carry forward. 04-RESEARCH.md's Package Legitimacy Audit independently re-confirmed this correction via `crates.io`'s registry API `repository` field, a second, independent citation strengthening the correction above.

## 3. Framework Quick Reference

> Fetched from official docs by `gsd-ai-researcher` (docs.rs/lance-graph 0.5.4, crates.io metadata, GitHub source view — see Sources below). Distilled for this specific use case.
>
> **Refinement to Section 2's open spike question:** the fetched API surface answers "path/URI vs. typed `lance::Dataset`?" — it's **neither**. `CypherQuery::execute()` takes `HashMap<String, RecordBatch>` (plain in-memory Arrow data), and `LanceNativePlanner` is a documented **placeholder** in 0.5.4 (no native Lance-dataset reader ships in this version; `table_readers` only has `ParquetTableReader`/`DeltaTableReader`). So the `lance ^1.0.0` vs. `lance =8.0.0` divergence never actually collides — lance-graph never touches a `lance::Dataset` handle on this path. **The real wall moved one layer up: `arrow::RecordBatch` from lance-graph's pinned `arrow ^56.2` is a different Rust type than this project's `arrow-array ~58.3`** (same memory layout, not the same type — a compile-time mismatch, not a runtime one). **The Phase 04 spike ran and this pattern is now empirically confirmed** — the bridge below compiles and round-trips correctly, and a checked-in reference implementation lives at `engine/src/graph/{mod.rs,bridge.rs,tests.rs}` (this phase's Task 1/2 output), not only in this document's illustrative code blocks below.

### Installation
```toml
# engine/Cargo.toml — add to [dependencies]
lance-graph = { version = "0.5.4", default-features = false }
# default features (unity-catalog, delta) pull cloud object-store (S3/Azure/GCS)
# and geospatial (wkb/wkt, tantivy) deps — inconsistent with local-first posture (Section 2).

# Second dependency needed ONLY to construct the arrow ^56.2 RecordBatch lance-graph's
# execute() requires — kept out of the primary arrow-array ~58.3 tree used everywhere
# else in the engine. Pin the *umbrella* `arrow` crate (not `arrow-array` directly) within
# lance-graph's own `^56.2` range so Cargo's resolver unifies it with lance-graph's own
# transitively-resolved arrow version instead of creating a THIRD incompatible arrow copy.
arrow-ipc = { version = "~58.3" }              # engine-side encoder (writer), matches arrow-array ~58.3
arrow-lg = { package = "arrow", version = "^56.2" }       # renamed, unifies with lance-graph's own tree
arrow-ipc-lg = { package = "arrow-ipc", version = "^56.2" } # renamed decoder (reader), matching arrow-lg
```

### Entry Point Pattern
```rust
// engine/src/graph/query.rs — illustrative shape; the checked-in, compiled, and tested
// implementation lives at engine/src/graph/{mod.rs,bridge.rs} (this phase's Task 1/2).
// Two flags the Phase 04 spike resolved:
//   (1) The IPC bridge below is confirmed working — a real, checked-in test
//       (bridge_round_trip_preserves_schema_and_values) proves it compiles and round-trips
//       real data. `arrow::ffi`'s C Data Interface remains a valid zero-copy optimization
//       if profiling later shows the copy matters, but is not needed to unblock planning.
//   (2) `RelationshipMapping.type_field` is CONFIRMED working as a dynamic per-row
//       type-column mechanism — resolved, not just clarified, per Pitfall 4 below. The
//       call below matches the empirically proven pattern.
use std::collections::HashMap;

/// Bridges an engine-native (arrow ~58.3) RecordBatch across the version boundary into
/// the arrow ^56.2 RecordBatch type lance-graph's `execute()` requires. IPC round-trip,
/// not a native cast — `arrow::RecordBatch` from two different arrow-rs majors are
/// distinct Rust types even though the wire format is stable across majors.
fn bridge_batch(batch: &arrow_array::RecordBatch) -> Result<RecordBatchLg, String> {
    let mut buf = Vec::new();
    {
        let mut writer = arrow_ipc::writer::StreamWriter::try_new(&mut buf, &batch.schema())
            .map_err(|e| format!("ipc encode: {e}"))?;
        writer.write(batch).map_err(|e| format!("ipc encode: {e}"))?;
        writer.finish().map_err(|e| format!("ipc encode: {e}"))?;
    }
    arrow_ipc_lg::reader::StreamReader::try_new(buf.as_slice(), None)
        .map_err(|e| format!("ipc decode: {e}"))?
        .next()
        .transpose()
        .map_err(|e| format!("ipc decode: {e}"))?
        .ok_or_else(|| "empty batch produced by bridge".to_string())
}

/// Inverse of `bridge_batch`: decodes lance-graph's arrow ^56.2 result RecordBatch
/// with the renamed `arrow-ipc-lg` writer, re-encodes with the engine's own
/// `arrow-ipc` (~58.3) reader. Needed because downstream engine code (prompt
/// assembly, D-27's rendering) is written against arrow-array ~58.3 types.
/// CONFIRMED working — the Phase 04 spike's checked-in
/// `bridge_round_trip_preserves_schema_and_values` test proves this round-trips
/// real data correctly; this was previously the unverified half of the bridge.
fn bridge_batch_back(batch: &RecordBatchLg) -> Result<arrow_array::RecordBatch, String> {
    let mut buf = Vec::new();
    {
        let mut writer = arrow_ipc_lg::writer::StreamWriter::try_new(&mut buf, &batch.schema())
            .map_err(|e| format!("ipc encode: {e}"))?;
        writer.write(batch).map_err(|e| format!("ipc encode: {e}"))?;
        writer.finish().map_err(|e| format!("ipc encode: {e}"))?;
    }
    arrow_ipc::reader::StreamReader::try_new(buf.as_slice(), None)
        .map_err(|e| format!("ipc decode: {e}"))?
        .next()
        .transpose()
        .map_err(|e| format!("ipc decode: {e}"))?
        .ok_or_else(|| "empty batch produced by bridge".to_string())
}

/// Bounded neighborhood traversal seeded from `seed_entity_id` (D-18, D-20, D-23).
/// IMPORTANT: `execute()`'s `HashMap<String, RecordBatch>` signature means the ENTIRE
/// map is materialized in memory per call — there is no predicate pushdown into the
/// lancedb scan through this API. The neighborhood MUST be pre-narrowed in Rust via
/// lancedb queries (bounded by hop_cap) before crossing into lance-graph; Cypher only
/// pattern-matches over the already-narrowed subgraph, not the full entities/edges tables.
pub async fn traverse(
    db: &crate::db::DatabaseManager,
    seed_entity_id: &str,
    hop_cap: u32,
) -> Result<arrow_array::RecordBatch, String> {
    // 1. Rust-side bounded BFS neighborhood expansion against lancedb's entities/edges
    //    tables (hop_cap enforces D-23; direction handling per D-24). This step is the
    //    part D-19 wanted Cypher to fully replace — the HashMap<String,RecordBatch> API
    //    forces a pre-filter step back into hand-written Rust, just at the
    //    neighborhood-selection layer instead of the whole-graph layer. Flag this
    //    honestly in planning rather than presenting Cypher as replacing all traversal logic.
    //
    //    PROJECT COLUMNS BEFORE BRIDGING: select only entity_id/name/entity_type from
    //    entities and source_node_id/target_node_id/relation_type/weight from edges.
    //    Cypher never reads name_vector/summary_vector (2048-dim FixedSizeList<Float32>,
    //    ~8KB/row) — seeding already happened against name_vector in lancedb per D-18.
    //    IPC-serializing and re-decoding those columns through the bridge for no reason
    //    is pure waste on every query; `fetch_neighborhood` must project them out.
    let (entities_batch, edges_batch) = fetch_neighborhood(db, seed_entity_id, hop_cap).await?;

    // 2. Cross the arrow-version boundary.
    let entities_lg = bridge_batch(&entities_batch)?;
    let edges_lg = bridge_batch(&edges_batch)?;

    // 3. Map our lancedb schema (entities.entity_id/name/entity_type, edges.source_node_id/
    //    target_node_id/relation_type/weight per D-11/D-13) onto Cypher labels.
    let config = GraphConfigBuilder::new()
        .with_node_label("Entity", "entity_id")
        .with_relationship_mapping(RelationshipMapping {
            relationship_type: "RELATED".into(), // generic wrapper type; see Pitfall 4
            source_id_field: "source_node_id".into(),
            target_id_field: "target_node_id".into(),
            type_field: Some("relation_type".into()), // CONFIRMED working — resolved, not just clarified (Pitfall 4)
            property_fields: vec!["weight".into()],
            filter_conditions: None,
        })
        .build()
        .map_err(|e: GraphError| format!("graph config: {e}"))?;

    let mut datasets = HashMap::new();
    datasets.insert("Entity".to_string(), entities_lg);
    datasets.insert("RELATED".to_string(), edges_lg);

    // hop_cap is validated as a bounded integer (D-23) and interpolated directly —
    // NOT a Cypher `$parameter`. Variable-length path bounds (`*1..N`) cannot be
    // parameterized in Cypher (same restriction as Neo4j); this is a fixed language
    // limitation, not a gap this integration can close. Never string-interpolate
    // this from raw caller input — hop_cap must already be a range-checked u32
    // (clamped to the configured maximum, D-23) before it reaches this format!.
    let cypher = format!(
        "MATCH (seed:Entity {{entity_id: $seed_id}})-[r:RELATED*1..{hop_cap}]-(neighbor:Entity) \
         RETURN seed, r, neighbor"
    );
    let query = CypherQuery::new(&cypher)
        .map_err(|e| format!("cypher parse: {e}"))?
        .with_config(config)
        .with_parameter("seed_id", seed_entity_id);

    let result_lg = query
        .execute(datasets, None::<ExecutionStrategy>)
        .await
        .map_err(|e| format!("cypher execute: {e}"))?;

    // Bridge the result back to arrow ~58.3 for downstream engine code (inverse of step 2).
    bridge_batch_back(&result_lg)
}
```

### Key Abstractions
| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `CypherQuery` | Parsed+executable Cypher query; `execute(datasets, strategy)` takes `HashMap<String, RecordBatch>` and returns one `RecordBatch` | Every graph read — both the standalone `QueryGraph` RPC (D-20) and the auto-triggered 1-hop RAG augmentation (D-26, D-31) |
| `GraphConfigBuilder` / `GraphConfig` | Maps table column names onto Cypher node labels and relationship types | Built from the `entities`/`edges` schema before each `execute()` call (or cached if schema is static) |
| `NodeMapping` / `RelationshipMapping` | Per-label / per-relationship-type column bindings (`id_field`, `source_id_field`/`target_id_field`, optional `type_field`) | Configuring how `entities.entity_id`/`edges.source_node_id`+`target_node_id`+`relation_type` map to `:Entity`/`:RELATED` patterns |
| `ExecutionStrategy` (`Option<ExecutionStrategy>`) | Controls physical execution approach | Second arg to `execute()`; start with `None` (default) unless profiling shows a reason to override |
| `table_readers::{ParquetTableReader, DeltaTableReader}`, `lance_native_planner::LanceNativePlanner` | Bundled alternate data-source adapters; `LanceNativePlanner` is a documented **placeholder** in 0.5.4 | **Not used** by this integration — no native Lance/lancedb reader exists yet; the `HashMap<String, RecordBatch>` path is the only viable route in this version |

### Common Pitfalls
1. **The wall isn't `lance::Dataset` typing — it's `arrow::RecordBatch` version skew.** `execute()` requires a `RecordBatch` built against lance-graph's pinned `arrow ^56.2`; a `RecordBatch` built with this project's `arrow-array ~58.3` is a **different Rust type** (compile error, not a runtime surprise). Requires the explicit IPC bridge shown above — **CONFIRMED**: the Phase 04 spike built this exact bridge (`engine/src/graph/bridge.rs`, `bridge_batch`/`bridge_batch_back`) and proved it round-trips a `RecordBatch` losslessly in both directions via a passing `cargo test` (see 04-RESEARCH.md, 04-01-SUMMARY.md).
2. **No predicate pushdown through this API.** `execute()` materializes the *entire* `HashMap<String, RecordBatch>` argument in memory — there is no way to push a `WHERE`/seed filter down into the lancedb scan through lance-graph. Every query must pre-narrow the neighborhood in Rust first (hop-capped BFS against lancedb), which partially re-litigates what D-19 wanted Cypher to replace — say this explicitly to the planner rather than presenting Cypher as doing all the traversal work. Column projection matters here too: `entities.name_vector`/`summary_vector` are 2048-dim `FixedSizeList<Float32>` (~8KB/row) that Cypher never reads (seeding already happened against `name_vector` in lancedb per D-18) — project them out before the IPC bridge, or every traversal pays to serialize/deserialize vector columns for nothing.
3. **`execute_with_context(SessionContext)` looks like a shortcut around materialization — it is not.** DataFusion's `SessionContext`/`TableProvider` are trait objects built against lance-graph's pinned `datafusion ^50.3`; lancedb's are `datafusion ^53.0`. Trait objects cannot cross a dependency-version boundary the way plain data (Arrow IPC bytes) can. Only the `HashMap<String, RecordBatch>` path is viable for this project's two-tree situation — do not let implementation "discover" `execute_with_context` as a tempting dead end.
4. **`RelationshipMapping.type_field` semantics — RESOLVED, confirmed dynamic per-row.** The doc comment reads "optional field containing the relationship type" (suggesting a dynamic per-row type column — exactly what D-04's freeform `relation_type` needs). **CONFIRMED** by the Phase 04 spike: `traverse_fixed_hop`/`traverse_multi_hop` set `property_fields: vec!["relation_type".into()]` plus `.with_default_relationship_type_field("relation_type")` on the `GraphConfigBuilder`, and the spike's `WHERE`-filtered `relation_type_filter` test (`engine/src/graph/tests.rs`) passed against fixture edges carrying distinct open-vocabulary `relation_type` values in a single relationship mapping — no per-value mapping registration is needed. `RelationshipMapping` does not require one mapping per distinct type string.
5. **Forgetting `default-features = false` silently reintroduces cloud/geospatial deps** (`unity-catalog`, `delta` pull S3/Azure/GCS object-store clients and `wkb`/`wkt`/`tantivy`) on any `cargo update` that touches this line — inconsistent with the project's local-first, no-new-infrastructure posture (Section 2).

## 4. Implementation Guidance

**Model Configuration:**
Reuses the existing `Generator` trait's OpenRouter adapter (`engine/src/generation/openrouter.rs`) — no new model client per D-08. Default model `DEFAULT_OPENROUTER_MODEL = "openai/gpt-4o-mini"`, `temperature = 0.0` (deterministic — matters more here than for RAG answers, since D-05's `ExactMatchResolver` merges entities by exact case-normalized name; nondeterministic entity naming would fragment what should resolve to one node), `top_p = 1.0`. The existing `max_completion_tokens` default (2048) is sized for full RAG answers — extraction output for a single chunk (D-02) is much smaller; configure a distinct, tighter cap (recommend 512–768 tokens) via a **separate `OpenRouterGenerationConfig` instance** so the RAG-answer and extraction paths can be tuned independently (the config struct already supports a per-instance `model`/token-budget, so this needs no new plumbing — see 4b.5 for why a cheaper model may also make sense here).

**Core Pattern:**
D-08 says extraction "reuses the existing provider-neutral `Generator` trait" — but `Generator::generate()` is hard-bound to `GenerationRequest`/`ModelOutput`, which are shaped for RAG answers (`answer`, `cited_evidence_ids`, `answer_basis`) and don't fit extraction's output shape (entity/relation lists). The pattern that honors D-08's intent without breaking Phase 3's already-shipped contract is a **sibling trait that mirrors `Generator`'s structure** (same `BoxFuture`-returning async signature, same OpenRouter HTTP client/timeout/response-parsing helpers factored out and shared) but bound to an extraction-specific request/output pair:

```rust
// engine/src/graph/extraction.rs
use crate::generation::{BoxFuture, GenerationError};

#[derive(Debug, Clone, serde::Serialize, serde::Deserialize)]
pub struct ExtractionRequest {
    pub chunk_id: String,
    pub chunk_text: String, // untrusted — see Section 4b.3 boundary note
}

pub trait ExtractionGenerator: Send + Sync {
    fn extract<'a>(
        &'a self,
        request: ExtractionRequest,
    ) -> BoxFuture<'a, Result<ExtractionOutput, GenerationError>>;
}
// OpenRouterGenerationConfig / build_http_client / timeout wrapper from
// generation/openrouter.rs are reused as shared helpers by both this adapter
// and the existing RAG-answer `Generator` impl — one HTTP seam, two schemas.
```

Per-document, chunks are extracted concurrently in batches of up to 5 (D-09, reusing the Phase 2 D-20 `futures::stream::iter(...).buffer_unordered(5)` pattern — `futures ~0.3` is already a dependency), each call fully awaited before the batch advances (structured output requires the complete JSON body, no partial/streaming consumption).

**Tool Use:**
No agentic tool-calling loop in this phase (system type is Hybrid Extraction+RAG, not autonomous/multi-agent) — "tool use" here is the OpenRouter `response_format: {type: "json_schema", strict: true}` structured-output constraint (already the pattern in `openrouter.rs`, reused for extraction per 4b.1) plus the `lance-graph` Cypher engine acting as an in-process "tool" invoked during the RAG query path. Per D-32, if that in-process tool call fails or errors, the query silently continues with chunk-only evidence — the failure-handling posture takes the place of a guardrail/circuit-breaker for tool-use failure.

**State Management:**
LanceDB remains the single durable state store — no separate session/cache layer. Extraction results (entities, edges) persist synchronously per-chunk during ingestion (D-01), before the document reaches `completed`. Each `/rag/query` call is stateless beyond the existing `session_id`/`correlation_id` passthrough already on `GenerationRequest` — graph traversal state (the narrowed neighborhood RecordBatch) is constructed fresh per call and discarded after the response, no caching in v1 (see 4b.5 for why this is an acceptable default).

**Context Window Strategy:**
Graph facts and chunk evidence **share** the existing evidence token budget (D-29/D-39, `GroundingLimits::evidence_token_budget()`) rather than reserving a separate allocation — the graph-context "Related Entities & Relationships" section (D-27) must be token-estimated with the same `tiktoken-rs` estimator already used for chunk `EvidenceBlock`s, then interleaved by normalized relevance score (D-29/D-30) before truncation, not appended after chunk evidence is already packed.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.
>
> **Note on this heading's title:** this is a Rust project — there is no Pydantic in Rust. The substitution used throughout 4b.1 is a `serde`-derived struct with a hand-written JSON Schema (mirroring the pattern already shipped in `engine/src/generation/openrouter.rs`), used to constrain OpenRouter's `response_format: json_schema` output and validated via `serde_json` deserialization with `#[serde(deny_unknown_fields)]`. Flagging this explicitly so downstream readers don't go looking for a `pydantic` dependency that doesn't and shouldn't exist here.

### Structured Outputs (Rust: `serde` + hand-written JSON Schema — Pydantic does not apply)

The existing seam (`openrouter.rs` lines ~374–436) builds the JSON Schema for `ModelOutput` by hand via `serde_json::json!({...})` and sends it as OpenRouter's `response_format.json_schema.schema` with `"strict": true` and `"additionalProperties": false`. The extraction output schema should mirror this exact pattern rather than introducing a new dependency (e.g. `schemars`) — the codebase-consistent option is the recommended default; `schemars`-derived JSON Schema generation is a viable alternative if the hand-written schema becomes unwieldy, but it isn't in the current dependency baseline and adds surface area for no clear gain at this schema's size.

```rust
// engine/src/graph/extraction.rs
use serde::{Deserialize, Serialize};

/// Per-chunk structured extraction output (D-02, D-03, D-04). Entity/relation
/// types are open-domain freeform strings — no fixed enum (D-03).
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct ExtractionOutput {
    pub entities: Vec<ExtractedEntity>,
    pub relations: Vec<ExtractedRelation>,
}

#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct ExtractedEntity {
    pub name: String,
    pub entity_type: String, // freeform, LLM-assigned (D-03)
}

#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct ExtractedRelation {
    pub source: String,        // must match an entities[].name in this same output
    pub target: String,
    pub relation_type: String, // freeform, LLM-assigned (D-04)
    pub confidence: f32,       // 0.0-1.0, maps directly to edges.weight (D-04)
}

// Hand-written JSON Schema mirroring openrouter.rs's existing ModelOutput pattern:
fn extraction_schema_json() -> serde_json::Value {
    serde_json::json!({
        "type": "object",
        "properties": {
            "entities": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "name": { "type": "string", "maxLength": 512 },
                        "entity_type": { "type": "string", "maxLength": 128 }
                    },
                    "required": ["name", "entity_type"],
                    "additionalProperties": false
                }
            },
            "relations": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "source": { "type": "string", "maxLength": 512 },
                        "target": { "type": "string", "maxLength": 512 },
                        "relation_type": { "type": "string", "maxLength": 128 },
                        "confidence": { "type": "number", "minimum": 0.0, "maximum": 1.0 }
                    },
                    "required": ["source", "target", "relation_type", "confidence"],
                    "additionalProperties": false
                }
            }
        },
        "required": ["entities", "relations"],
        "additionalProperties": false
    })
}
```

**Framework integration:** sent as `response_format: { type: "json_schema", json_schema: { name: "extraction_output", strict: true, schema: extraction_schema_json() } }` on the OpenRouter chat payload — identical wiring to the existing `ModelOutput` call, different schema/struct. `serde_json::from_str::<ExtractionOutput>(...)` with `deny_unknown_fields` is the validation step; OpenRouter's `strict: true` mode should make schema violations rare, but the deserialize step is still the authoritative validator (never trust `strict` alone).

**Retry logic:** per D-06 (extraction failure for a single chunk is non-fatal), retry the extraction call up to **2 times** (3 attempts total) on deserialize failure or `GenerationErrorKind::SchemaValidation`/`ProviderError`, with the raw (truncated, e.g. first 500 chars) model output, `chunk_id`, `document_id`, error kind, and attempt number logged at `warn` level per attempt. After retries are exhausted, log at `warn` (not `error` — this is expected-non-fatal per D-06) and let the chunk proceed with zero entities/relations; the document still reaches `completed`. Surface to on-call/monitoring only as an **aggregate rate** (e.g. "extraction failure rate > X% over Y documents") — never alert on a single chunk's exhausted retries, that's normal operating noise by design.

### Async-First Design

Everything in this phase runs on the existing `tokio ~1.53` multi-thread runtime already driving the `tonic` gRPC server — extraction and traversal are both `async fn`s returning `BoxFuture`, matching the existing `Generator` trait's shape. D-09's per-document concurrency (up to 5 concurrent extraction calls) uses `futures::stream::iter(chunks).map(|c| extract(c)).buffer_unordered(5)` (`futures ~0.3` already a dependency) rather than sequential `.await`s in a loop.

**The one common mistake, in Rust terms:** never call a blocking/synchronous wait (e.g. `futures::executor::block_on`, or spinning up a second `tokio::runtime::Runtime` and calling `.block_on()` on it) from inside code that is already running under the `#[tokio::main]` runtime — this deadlocks or starves the executor exactly the way `asyncio.run()` inside a running event loop does in Python. Propagate `async`/`.await` through the full call chain from the gRPC handler down through `traverse()`/`extract()`. Separately: `lance-graph`'s `CypherQuery::execute()` is `async`, but DataFusion's query planning/execution underneath can be CPU-bound — if profiling shows it stalling other tasks on the shared runtime, wrap it in `tokio::task::spawn_blocking`, but don't assume that's needed without measuring first.

**Stream vs. await:** both extraction and traversal are fully-`await`ed, never streamed — extraction needs the complete JSON body to deserialize/validate against the schema (partial JSON can't be validated), and traversal needs the complete `RecordBatch` to bridge back across the arrow-version boundary and merge into the evidence set. There is no token-by-token streaming UX surface in this backend service (no chat UI in this phase) — streaming would only be relevant if a future phase adds a live-typing client experience for `/rag/query`.

### Prompt Engineering Discipline

System vs. user separation mirrors the existing `GenerationRequest::new()` pattern (`system_policy` field carries a fixed instruction string, separate from user/corpus-derived content). Extraction should define its own fixed system policy (e.g. *"You are a precise entity/relationship extraction engine operating on a single text chunk. Extract only entities and relations explicitly supported by the text..."*) — kept structurally separate from the chunk text field, which is **untrusted corpus content** and must go through the same escaping/boundary discipline already applied to `EvidenceBlock` rendering in `prompt.rs` (`encode_field_value`'s `&`/`<`/`>`/`"`/`'` escaping, `<EVIDENCE>`-style delimiting tags) rather than being interpolated raw into the prompt.

Few-shot: given D-03/D-04's open-vocabulary entity/relation types, 2–3 **inline** few-shot examples embedded in the fixed system prompt (not dynamically retrieved — unnecessary complexity at this scale) illustrating the intended granularity (e.g. showing `"founded_by"` as the expected relation-type style, not `"was founded by"` or `"founder_of"`) reduces raw vocabulary fragmentation before D-05's exact-match resolver runs. This doesn't replace resolution — it just lowers the pre-resolution fragmentation rate.

`max_tokens`: set explicitly and separately from the RAG-answer path's 2048-token default (see Section 4 Model Configuration) — recommend 512–768 for the extraction call, since per-chunk entity/relation lists are far smaller than a full answer. Never leave `max_completion_tokens` unbounded in production; the existing `OpenRouterGenerationConfig::validate()` already enforces a ceiling (`MAX_SERVICE_OUTPUT_TOKENS`), reuse that same enforcement path for the extraction config instance rather than a bespoke check.

### Context Window Management

**Extraction side:** inherently bounded — D-02's one-call-per-chunk granularity means context pressure is fixed by the existing Phase 2 chunk-size config; no summarization or truncation logic is needed at extraction time (D-07's minimum-content-length skip further reduces wasted calls on trivially small chunks).

**RAG/traversal side:** the binding constraint is Pitfall 2 above — `CypherQuery::execute()`'s `HashMap<String, RecordBatch>` signature materializes the full argument in memory with no pushdown, so truncation/ranking must happen **before** crossing into lance-graph, not after:
1. Hop-cap (D-23, e.g. default 3) and the always-on RAG path's 1-hop default (D-31) bound how large the pre-narrowed neighborhood RecordBatch gets in the first place.
2. Within the returned neighbor set, rank by D-30's `graph_weight`-scaled, normalized score and truncate to fit the **shared** evidence token budget (D-29) using the same `tiktoken-rs` estimator as chunk evidence — render `"A —relation_type→ B"` triples (D-28's `SourceChunks`-fallback rendering, since `summary`/`summary_vector` are null in v1) in relevance order until the shared budget is exhausted, exactly mirroring how chunk `EvidenceBlock`s are packed in `prompt.rs` today.

### Cost and Latency Budget

**Extraction (ingestion-time, per D-02):** one LLM call per chunk at `gpt-4o-mini` OpenRouter rates with a tightened ~512–768 output-token cap (4b.3) keeps per-chunk cost low (sub-cent range at current OpenRouter pricing — verify current rates before finalizing a budget line, they change). D-09's 5-way concurrency improves ingestion wall-clock throughput, **not** dollar cost — total extraction spend scales linearly with chunk count regardless of concurrency. No caching applies here: each chunk's text is unique at ingestion time (D-01 runs once per chunk), so exact-match caching would rarely hit and semantic caching isn't worth the complexity for a one-shot ingestion-time call.

**Query-time (RAG augmentation, D-26 always-on):** this path runs on *every* `/rag/query` call, so it's the latency-sensitive side, not the cost-sensitive side — the entity-seed lookup (D-18, a vector search against `entities.name_vector`) and the `lance-graph` Cypher execution are both **LLM-free** (pure data operations). This phase adds **zero incremental LLM cost** to the query path: graph facts are appended to the same single final-answer generation call Phase 3 already makes, not a second LLM round-trip. Budget attention should go to wall-clock latency (bridge IPC round-trip + Cypher execution + narrowed lancedb reads on every query), with D-32's silent-fallback-to-chunk-only serving as the latency circuit-breaker — if graph augmentation is slow or erroring, the query fails open rather than blocking the response.

**Cheaper models for sub-tasks:** extraction already defaults to the cheaper shared model (`gpt-4o-mini`) rather than a larger model reserved for final answers. If Section 5's evaluation shows extraction quality holds up, consider routing extraction to an even smaller/cheaper OpenRouter model independently of the RAG-answer model — the existing `OpenRouterGenerationConfig` already supports a distinct `model` field per instance (see Section 4 Model Configuration), so this requires no new plumbing, only a second config instance and, per 4b.1, keeping the model's advertised `response_format`/`json_schema` support in mind (the existing capability check in `openrouter.rs` already gates on this).

### Eval Tooling

**Primary Tool:** Arize Phoenix via OpenTelemetry for trace inspection — same default as Phase 03 (no Langfuse, LangSmith, Braintrust, Promptfoo, or RAGAS integration detected in this repository's dependency tree; confirmed via `engine/Cargo.toml`, `gateway/go.sum`, and a source-tree scan for this phase) — paired with code-based Rust `cargo test` fixtures for the deterministic dimensions (schema compliance, failure-tagging, traversal bounds) and a calibrated LLM judge for the semantic dimensions (entity-merge correctness, extraction faithfulness, signal-to-noise).

The judge is **not** a reuse of the `Generator` trait: Section 4 established that trait is hard-bound to `GenerationRequest`/`ModelOutput` for RAG answers, and `ExtractionGenerator` was introduced as a sibling specifically because extraction's shape didn't fit it — a judge has a third output shape again. ### Reference Dataset

**Size:** Phase 04 gate: minimum 16 examples — 8 rubric categories below, ~2 paired examples each, since several dimensions require a positive/negative contrast pair and a flat 10 undercounts what's needed to gate them. Expand to 20+ for the Phase 6 production harness (`OBS-02`), adding categories only as real failures are observed, per ai-evals.md's "don't build for hypothetical coverage."

**Composition (Phase 04 gate; paired where the dimension needs a positive/negative contrast):**
1. **Entity-merge pairs** — one genuine same-entity-different-mention pair (should merge) + one different-entity-same-normalized-name pair (should NOT merge — the "two John Smiths" adversarial case). Gates the entity-merge correctness dimension.
2. **Extraction faithfulness pairs** — one chunk with an explicitly stated relationship (should extract) + one chunk with mere entity co-occurrence and no stated relationship (should NOT fabricate a relation). Gates extraction faithfulness.
3. **Injection-resistance pair** — one chunk with an embedded instruction-like string + the same chunk with that string removed (control); extraction output must not differ in a way attributable to the injected instruction. Gates the injection-resistance half of extraction faithfulness.
4. **Extraction schema/retry fixtures** — malformed/truncated provider JSON, a relation with a dangling source/target reference, and a below-minimum-content-length chunk (D-07 skip boundary). Gates schema compliance.
5. **Relation-type paraphrase set** — 2-3 chunks describing the same real-world relationship in different surface phrasing (e.g. "founded by" / "was founded by" / "founder of"). Gates relation-type coherence.
6. **Failure-tagging pair** — a simulated extraction/traversal failure (injected `FakeGenerator`/`lance-graph` error) + a genuine no-match case (valid seed lookup, zero neighbors); these must produce distinguishable trace tags. Gates failure transparency.
7. **Traversal-bounds fixtures** — hop depth exactly at the configured cap, one over the cap, and a seed-as-edge-target case (tests D-24 bidirectionality). Gates traversal bounds/direction/determinism.
8. **Signal-to-noise pair** — one query with a correctly-seeded high-relevance neighborhood + one with a deliberately wrong seed or noisy neighborhood, to verify budget interleaving favors the former. Gates graph-augmentation signal-to-noise.

**Labeling:**
Reuses Section 1b's Domain Expert Roles table: the senior RAG/knowledge-graph practitioner (project owner) calibrates the entity-merge and faithfulness rubrics and gives final sign-off on labels; the GraphRAG/KG-construction reviewer labels each fixture chunk's expected entities/relations and each merge pair as same-entity or different-entity; the downstream RAG-answer consumer proxy flags production `/rag/query` answers with suspicious or absent graph context, feeding the offline flywheel (Section 6). LLM judge scores are used only after calibration against the human-labeled fixture set, requiring ≥0.7 correlation before trusting judge output as a gate (ai-evals.md, Phase 03 precedent). Fixtures are built concurrently with the extraction/resolver/traversal implementation, not after.

## 6. Guardrails

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| Extraction structured-output validation | OpenRouter extraction response fails `ExtractionOutput` deserialization or contains a dangling source/target reference after all 3 attempts (D-06, 4b.1) | Flag — log at `warn` (not `error`, per 4b.1's expected-non-fatal framing) with `chunk_id`/`document_id`/error kind/attempt number; the chunk proceeds with zero entities and the document still reaches `completed`. Escalate only via the aggregate rate in Section 7 — never a per-chunk alert. |
| Hop-cap / traversal-bound clamp | A caller-specified (`QueryGraph`, D-20) or default (RAG-path, D-31) hop depth is absent, exceeds, or would exceed the configured maximum (D-23) before reaching the `format!`-interpolated Cypher string (Section 3's non-parameterizable `*1..N` limitation) | Block/Clamp — reject an out-of-range explicit `QueryGraph` hop depth with a structured validation error before any Cypher execution; clamp the RAG-path default to the configured maximum. Never let an unbounded or caller-influenced value reach the interpolated Cypher string — this is a resource-exhaustion and injection-shaped risk, not just a UX bound. |
| Graph-augmentation failure-transparency tagging | Entity seed-matching (D-18) or `lance-graph` traversal (D-32) errors at query time | Flag — the query still continues with chunk-only evidence per D-32's locked fail-open design (this guardrail does not change that behavior or the `/rag/query` response contract), but every attempt emits a trace/log-level `graph_augmentation` outcome tag — `attempted_and_failed`, distinct from `no_match_found` (seed lookup succeeded, zero neighbors) and `succeeded` — so silent degradation (Section 1's critical failure mode #2) becomes operator-visible in logs/traces even though no single request is blocked. Surfacing this tag into the `/rag/query` response itself is a future DEBT-RAG-01-adjacent target, out of scope here. |
| Entity-merge fan-in anomaly threshold | A single entity row's `source_chunk_ids` list (D-12) crosses a configured cumulative-length threshold — a cheap, stateless proxy for the "two John Smiths" over-merge pattern (exact threshold is implementer discretion; recommend starting low and tuning from the offline flywheel below). This counts *chunks*, not distinct *documents* — a stronger distinct-document signal would require joining `source_chunk_ids` back against `nodes.document_id`, which this guardrail intentionally skips to stay O(1) per merge event. | Flag — queue the entity node for KG-construction-reviewer sampling (offline table below); never auto-split or auto-block ingestion, since D-14/D-16's fail-fast/no-auto-migrate posture means any repair here is a manual/future-phase concern, not a runtime action this guardrail should attempt. |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| Entity-merge precision (sampled merge review) | Every entity flagged by the fan-in guardrail above, plus a weekly stratified random sample of all merge events | KG-construction reviewer judges same-entity vs. different-entity per merge (Section 5's entity-merge correctness rubric); confirmed over-merges are logged as known-bad nodes for future manual re-split tooling (no auto-repair per D-14/D-16) and feed a few-shot/resolver-tuning discussion for a later phase. |
| Extraction faithfulness / hallucination rate | Stratified random sample of extracted relations per ingestion batch, plus the bottom decile (10th percentile) of observed `confidence` (`edges.weight`) within the sampled batch — not an absolute floor, since D-04's LLM-self-reported confidence is routinely degenerate (e.g. clustering tightly in 0.85-0.95) and an absolute threshold may never fire | LLM judge scores groundedness against the source chunk (calibrated per Section 5); human review of disagreements and all bottom-decile relations; confirmed fabrications feed back into system-prompt/few-shot tuning (4b.3). Separately, a code-based check should flag if the observed confidence distribution is degenerate (low variance/no spread) — if so, `edges.weight` also carries no usable ranking signal for D-30's score interleaving, which is worth surfacing as its own finding, not just a sampling nuisance. |
| Relation-type vocabulary fragmentation rate | Weekly batch analysis: distinct `relation_type` string count vs. clustered/canonical count, tracked as the corpus grows | If the fragmentation ratio rises, tighten/expand the 4b.3 few-shot examples; if it stays high despite tuning, escalate "does this need a constrained taxonomy" as a future-phase decision. |
| Graph-augmentation outcome mix (`succeeded` / `no_match_found` / `attempted_and_failed`) | Aggregate over a rolling window of all `/rag/query` calls — the guardrail's tag is already computed per-request, so this is a 100%-sampled aggregation, not a subsample | A rising `attempted_and_failed` rate → investigate the Section 3 arrow-version IPC bridge and `lance-graph` execution path (flagged as new/unverified code pending the Phase 04 spike). An unexpectedly high `no_match_found` rate → investigate D-18's seed-vector-search quality, not traversal itself. |
| Extraction cost/latency drift | Batch weekly during development, weighting long-chunk and provider-error traces (mirrors Phase 03 precedent) | Review the 512-768 output-token cap and model choice (4b.5's cheaper-model consideration) before adding retries/fallback complexity. |

**Key Metrics to Track:**
1. Extraction failure rate (post-retry-exhaustion, aggregate only per D-06/4b.1 — never a single-chunk alert).
2. Entity-merge fan-in distribution (flags outliers per Section 6's fan-in guardrail).
3. Graph-augmentation outcome breakdown: `succeeded` / `no_match_found` / `attempted_and_failed` (Section 1b's "failure transparency" ingredient, made concrete and trace-visible).
4. Relation-type vocabulary cardinality growth rate (fragmentation proxy).
5. Traversal latency (IPC bridge round-trip + Cypher execution) p50/p95 — the latency-sensitive side per Section 4b's Cost/Latency Budget, since query-time augmentation runs on every `/rag/query` call with zero incremental LLM cost but real wall-clock cost.

**Alert Thresholds:**
Initial development thresholds, to be calibrated in Phase 6 once a production baseline exists: extraction failure rate (post-retry) above 10% over a rolling window of documents opens an investigation (chunk-level failure is lower-stakes/non-fatal than a full provider error, so this starts looser than Phase 03's 5% provider-error threshold); any single entity's merge fan-in crossing the Section 6 threshold routes to the human-review queue, not a page; `attempted_and_failed` rate for graph augmentation above 5% of `/rag/query` calls over a rolling window is page-worthy (this exercises new, unverified bridge/traversal code per Section 3's flagged spike risk, closer in spirit to Phase 03's provider-error threshold than to a soft quality signal); relation-type distinct-string growth sustainably outpacing corpus growth is a review-only signal, not a page; traversal p95 latency exceeding the configured query budget (exact figure is implementer discretion pending Phase 04's own latency baseline) opens an investigation into the bridge/Cypher execution path.

**Smart Sampling Strategy:**
Capture 100% of: extraction retry-exhaustion events (aggregated, never per-chunk-alerted), traversal `attempted_and_failed` events, and Section 6's merge-fan-in flags. Layer a stratified sample of successful extractions, merges, and traversals across document types/sizes and query patterns for the offline flywheel (entity-merge precision, faithfulness, signal-to-noise rows in Section 6). Redact raw chunk text and API keys from retained traces beyond what a domain reviewer needs; Section 1b's domain-expert roles (KG-construction reviewer, downstream RAG-answer consumer proxy) inspect sanitized samples and judge-model disagreements.
