# Phase 06.3.5 Plan 09: Held-out gates, arm-mode preflight canaries and per-arm provider map Summary

**`unpark_gates --stage heldout` reads completeness and error-mode/flatness per arm and pooled so no failing arm hides in the pool, preflight proves every arm's provenance from rehearsal-pool canaries (refusing any dev or held-out ID before a request, and skipping the legacy canaries), and a generalised provider map discloses a mid-drive provider switch per arm.**

## Performance

- **Duration:** about 80 min
- **Completed:** 2026-10-07
- **Tasks:** 3 (each a RED test commit and a GREEN feat commit)
- **Files:** 6 (3 created, 3 modified), all under `eval/`

## Accomplishments

- **Held-out gates (D-109).** `HELDOUT_STAGE` branch in `unpark_gates.main`: `evaluate_sc1_arm` (missing keys from the one `completeness_comparison` call grouped by arm; `n_expected` = corpus questions; zero-record arm and empty corpus MISS), `evaluate_sc2_arm` (canonical-label filter, first-attempt tally, PID check, flatness over the arm's records renumbered 1..n via `records_from_run_journal`), the existing `evaluate_sc2` for the pooled line under `HELDOUT_ARM_ROLES`, and the D-69 companion per arm and pooled as a disclosure. Output is `gates-heldout.md` (one table, columns per arm plus pooled, cells `PASS (n)` / `MISS (n): reason`) and `gates-heldout.json` (`{gate: {arm: reading, ..., pooled: reading}}`, `not_computed` for SC-3, SC-4, SC-5). `--populations` and `--gold-chunks` are required for every other stage and optional for `heldout`.
- **Preflight (D-108, D-124).** `check_arm_mode_canaries` runs each `canary.arms.jsonl` row under each configured arm through `run_query(**request_fields(arm))` and fails, naming the question and the arm, on any `provenance_failures` clause (echo, ranking, GRAPH_ABLATION, snapshot config, `bm25_count` / `vector_count`), a missing completed snapshot, an unmet `min_retrieved_chunks`, or a node at or over its live budget. A manifest holding a dev, held-out G or held-out null ID is refused before any request. `run_preflight_checks` reports `canary_manifest` and `canary_floors` as named D-124 skips for `legacy_canaries = false` corpora and adds `arm_mode_canaries` for corpora with an `arm_canaries` manifest and more than two arms; legacy corpora are unchanged. Arm-canary snapshots also feed `corpus_generation_from_canaries`.
- **Provider map (D-107, D-96).** `eval/scripts/provider_format_map.py` (RUN_DIR, ENGINE_STDERR_LOG, `--out-dir`) writes `provider_format_map.jsonl` (one row per journal record, `provider: null` when unmatched) and `provider_format_map-summary.json` (`by_arm_provider`, `provider_sequence_rle`, `per_provider`, `by_arm` NO_EVIDENCE and errored counts, `unmatched_count` split into NO_EVIDENCE, errored and unexplained, `join_coverage`, `served_lines_total`, `served_lines_not_in_journal`). Run over the recorded drive-2 journal it reproduces the 06.3.4.1 format counts exactly.

## Decisions Made

See `key-decisions`. The two worth restating: a failed precondition leaves SC-2 and D-69 as bare MISS (nothing is computed from an incomplete or mis-staged journal) while SC-1 still names each arm's own missing count, and `arm_mode_canaries` is stricter than the scorer (every provenance clause fails the check, not only the zero-tolerance ones), because a preflight canary exists to prove the arm is wired.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Fixture size: 12 questions per arm, not 5**
- **Found during:** Task 1 test design
- **Issue:** the plan's behaviour says a 5-question x 4-arm journal reads SC-2 PASS per arm. A probe of `flatness_verdict` showed 5 records read `unavailable` (not flat) and 8 read `flat`, so a per-arm PASS cannot exist at n=5, and loosening flatness would defeat the gate.
- **Fix:** held-out gate fixtures hold 12 questions per arm; flatness is untouched.
- **Files modified:** `eval/tests/test_heldout_gates.py`
- **Commit:** `1074890e`

**2. [Interpretation] The "no legacy canary ID in any request" proof is by question text and an exact count**
- **Found during:** Task 2 test design
- **Issue:** `mhr-0d5e238015ef` is in both `canary.jsonl` and `canary.arms.jsonl`, so "none of the legacy IDs appears in any request" is literally false for the shared row.
- **Fix:** the held-out preflight test asserts that no request's query equals a legacy-only canary question text, and that exactly 12 requests (3 rows x 4 arms) carry an arm-manifest question. The legacy manifest itself holds dev IDs (for example `mhr-01a03d465730`), which is why skipping it is required.
- **Files modified:** `eval/tests/test_preflight_canary.py`
- **Commit:** `e75cc578`

**3. [Rule 3 - Blocking] Verify commands run in the sanctioned form**
- **Issue:** the plan's `uv run --project eval ...` is rejected by the worktree command guard, and compound git commands are refused.
- **Fix:** every run used `UV_PROJECT=./eval uv run ...`, and each git verify ran as its own plain command with the same pass condition.

### Interpretation notes (no behaviour change to the plan)

- `_journal_preconditions` is now a thin wrapper over a new `_journal_state` that also returns the missing-key set, so `completeness_comparison` is still called exactly once per run (an existing test pins this). The wrapper returns the same tuple as before.
- `citation_rejection_rate` delegates to a records-based `_citation_rejection_from_records`; its behaviour is unchanged and the per-arm D-69 reading reuses the core.
- The RED commit of Task 3 carries a neutral placeholder `provider_format_map.py` (as plan 07 did) so the RED fails on assertions, not on a missing file. The plan is `type: execute`, so no `check tdd-red-evidence` record was persisted.
- The 06.3.4.1 script's `_unescape` (a utf-8 to `unicode_escape` round trip that mangles non-ASCII) was replaced by an explicit unescape of the `Debug` sigils; the join key is unaffected.
- `arm_mode_canaries`, like `canary_floors`, runs only when the gateway and engine health checks pass.
