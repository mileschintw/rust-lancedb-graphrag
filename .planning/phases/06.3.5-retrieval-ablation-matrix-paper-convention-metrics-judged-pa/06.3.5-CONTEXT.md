## Phase Boundary

**What this phase delivers:** run the **unchanged drive-2 system** as four retrieval arms on
a committed held-out split, `dense-only`, `bm25-only`, `hybrid` (reference) and `hybrid+graph`.
Score each arm with Lancet's metrics and with MultiHop-RAG's own retrieval convention
(Hits@k, MRR@10, MAP@10). Run the LLM-judged dimensions on every arm, calibrate them against a
blinded human slice, and publish one four-arm run of record with paired deltas against `hybrid`.

**The system under test does not change.** No reranker, graph change, prompt change, weight or
threshold change. The two engine additions in this phase are both behaviour-neutral under the
default request: `retrieval_mode`, whose default `hybrid` keeps today's output, and an opt-in
diagnostic ranking field. Golden tests prove both are byte-identical to drive 2 when the default
request is used (D-99, D-100). Quality levers belong to Phase 06.3.6.

**Evidence gathered during this discussion (2026-10-06):**
- Records carry only the final `final_limit = 8` chunks (`config/config.toml` `[engine.retrieval]`).
  Nothing in the snapshot, the proto or `eval/report.schema.json` carries a ranking from before
  truncation, so **Hits@10, MRR@10 and MAP@10 cannot be computed from any existing journal.** This
  is why D-100 exists.
- Held-out pool, read from `.planning/phases/06.3.4.1-.../diagnostic/post-reconcile/populations.json`
  (G = 398 over the 500 sample): of the 400 non-dev sample questions, **308 are in G** (125
  comparison, 105 inference, 78 temporal), and **43 are `null_query`**. D-63 counts the 49
  `split_across_chunks` evidence items as "no", so the G restriction does exclude questions.
- Drive-2 cost about $0.00036 per record and ran at about 6.6 records per minute at `--workers 1`.
- The arm registry today is `GRAPH_ARMS` (`eval/src/lancet_eval/run.py:60`, two entries).
  `unpark_gates` reads the reference arm as the literal `"graph-off"`
  (`eval/src/lancet_eval/unpark_gates.py:596`).

**Out of scope (ROADMAP, unchanged):** chunking comparison (DATA-02), new corpora, reranking, graph
repair, prompt changes and provider pinning. Further arm combinations (D-116) are also out.

### Retrieval mode and the ranking field (SC-1, SC-2, SC-3 input)

- **D-99:** **`retrieval_mode` is a request field** (`dense_only` / `bm25_only` / `hybrid`, default
  `hybrid`). It is orthogonal to `disable_graph_context`.
  - **Mechanics: the excluded path is skipped, not zero-weighted.** `dense-only` never calls the
    BM25 port and `bm25-only` never calls the dense port. RRF then runs over the single list, so
    per-arm latency and cost show the real cost of each path.
  - Under the default, `engine/src/retrieval/testdata/graph_off_fusion.golden` stays byte-identical.
  - The mode is visible per record on the wire, as a notice code or a snapshot field, so the
    harness can verify arm provenance the way it verifies `GRAPH_ABLATION`. Follow the D-52 pattern:
    regenerate both proto trees and the gateway's vendored `gateway/proto/lancet/v1/lancet.pb.go`,
    and add a gateway test that pins the field end to end.
  - **Reversibility:** costly. It adds a field to the public query contract that every API client
    sees, and removing it later breaks any client that set it.
- **D-100:** **An opt-in pre-truncation ranking field.** When the request sets a diagnostic flag
  next to `retrieval_mode`, the snapshot carries the full fused ranking before truncation, up to
  `candidate_limit` (32).
  - It carries IDs and ranks only: `chunk_id`, `document_id`, fused rank, and the per-list ranks
    that `Candidate` already holds (`vector_rank`, `bm25_rank`, graph contribution). There is no
    text.
  - Without the flag the field is absent and responses do not grow.
  - A golden test proves that with the flag on, the final 8, the prompt and the answer path are
    byte-identical to the flag being off.
  - The harness sets the flag on every arm of the held-out drive.
  - 06.3.6's reranker reads the same field ("gold was at rank 14 before rerank").
  - **Reversibility:** costly, for the same contract reason as D-99.
- **D-101:** **The arm registry generalises to a label → request-flags table.**

  | Arm | `retrieval_mode` | Graph |
  |---|---|---|
  | `dense-only` | `dense_only` | off |
  | `bm25-only` | `bm25_only` | off |
  | `hybrid` | `hybrid` | off |
  | `hybrid+graph` | `hybrid` | on |

  - `[arms]` in the corpus TOML, `--arm` on the CLI and the provenance checks all agree, and every
    record carries its arm.
  - The legacy labels `graph-off` and `graph-on` resolve as read-only aliases of `hybrid` and
    `hybrid+graph` when historical journals are read.
  - `unpark_gates` takes the reference arm as a parameter. The recorded drive 1, 1b and 2 verdicts
    must re-read unchanged, proven by a test.

### Paper-convention metrics (SC-3)

- **D-102:** **Hits@4, Hits@10 and MRR@10 follow the official MultiHop-RAG evaluation script**, and
  so does **MAP@10** if that script computes it.
  - Research pins the script's repository and commit, and the canonical refs record it.
  - Matching is at document level, and chunks are deduplicated to documents exactly as the script
    does. This is not reconstructed from memory.
  - The ranking input is D-100's field.
  - These are additive, labelled dimensions **side by side** with Lancet's chunk-level metrics
    (coverage@4, precision@4). The methodological caveat is rewritten to name exactly which figures
    are comparable to the paper's table, and why the corpus still differs (346-doc subset, Lancet's
    chunker and embedder).
- **D-103:** **The paper's published retrieval figures appear as a cited reference row** under the
  four arms. The citation names the paper version and table, and the non-comparability caveat sits
  beside the row.
- **D-104:** **Hits@4 is retro-computed on the drive-2 journal**, as a read-only offline analysis
  under the D-74 guardrail.
  - It never calls `score` or `report` and adds no bypass of the fail-closed path.
  - It is labelled "dev-only, paper-convention @4". The @10 metrics are not computable there.
  - It gives 06.3.6 a dev baseline for `hybrid` and `hybrid+graph` at no cost.

### Dev / held-out split (SC-4)

- **D-105:** **The held-out set is the whole non-dev pool:** all **308** non-dev G questions plus all
  **43** non-dev null questions, 351 questions in total.
  - Null questions feed only the D-72 abstention metric per arm. They never enter retrieval or
    answer denominators.
  - Before any paid request, a committed split file records:
    - the dev IDs, from `eval/corpora/multihop_rag/diag_selection.json`;
    - the held-out IDs;
    - the derivation rule ("every non-dev sample question in G, plus every non-dev null");
    - the sha256 of the `populations.json` it was derived from;
    - the seed for the drive's question and arm order.
  - Since the whole pool is taken, there is no sampling seed. If the pool ever has to be
    subsampled, the fallback is proportional stratification by `question_type`, with the seed
    recorded.
  - 06.3.6 inherits the split, develops on dev only and reads held-out once.
  - **Reversibility:** one-way. Once held-out has been read it cannot be made fresh again, and
    taking the whole pool leaves no untouched question in the 500 sample for a third read.
    Accepted by the owner for the narrower CIs (about ±5.5 points).
- **D-106:** **The dev set gets no new arms.** It already has `hybrid` and `hybrid+graph` from
  drive 2 (graph-off and graph-on), plus D-104's retro Hits@4. Within this phase no weight,
  threshold or prompt changes after a held-out reading (D-49).

### Drive shape (SC-5)

- **D-107:** **There is one held-out drive with the four arms interleaved per question.**
  - All four arms of a question run back to back. Arm order is a seeded, balanced rotation, so each
    arm runs first about 25% of the time.
  - The drive uses `--workers 1` (latency stays comparable to drive 2), `--retries 0` (D-67) and
    `--gate-stage`. It is preceded by its own D-86 `checkpoint:decision` for `--stage-cap`.
  - Size is 351 × 4 = **1,404 records**, at roughly $0.45–0.55 and about 3.5 h, run detached.
  - D-96 routing is unchanged. A provider switch is disclosed per arm, as in drive 2.
- **D-108:** **A rehearsal comes before the paid drive.** It covers:
  - preflight and canaries under all four modes;
  - D-99 and D-100's golden tests;
  - a tiny live probe of about 3 questions × 4 arms under a cent-level cap. It is paid, so it gets
    its own D-86 checkpoint. It proves arm provenance and the ranking field on the wire, through
    harness → gateway → engine.

  Only then comes the drive's cap checkpoint.
- **D-109:** **Gates are read per arm, plus a pooled line.** Completeness and error mode/flatness
  use 06.3.4.1's SC-1 and SC-2 definitions, with D-89 materiality. A failing arm cannot hide in
  the pool, and the pooled line keeps continuity with drive 2's readings.
- **D-110:** **A gate miss allows one bounded re-drive, then halt-disclose** (the D-83/D-84 rule).
  - The one fix allowed is an infrastructure or plumbing bug (harness, wire, provenance), justified
    by the per-record table, and the re-drive gets a new cap. A quality change to the system under
    test is never allowed.
  - An arm that is genuinely worse (for example BM25 retrieving less gold) is a result, not a gate
    miss.

### Pre-registration and reporting (SC-7)

- **D-111:** **Two pre-registered primaries**, committed in `thresholds.py` before the drive (D-73
  pattern):
  - paper-convention **Hits@4** for retrieval;
  - **`answer_usable`** for answers (the SC-3 metric of 06.3.4.1).

  **Holm step-down** runs across the three arm-vs-`hybrid` paired deltas within each primary.
  Everything else is a secondary: reported, never decisive. Paired deltas use bootstrap 95% CIs
  (B = 10 000, recorded seed), with Wilson intervals for rates. Per-arm latency and prompt-token
  cost are reported (D-42). D-40 per-type strata apply. The results are published whichever
  direction they take (D-49). These are the same primaries 06.3.6 uses by default, so the two
  phases read on one scale.
- **D-115:** **The run of record:**
  - a new dated run directory, scored and reported through the unmodified fail-closed path;
  - a four-arm comparison table: per-arm retrieval (both conventions), answer, abstention and
    judged metrics with CIs, plus paired deltas against `hybrid`;
  - chart data as JSON plus an interim eval-results chart under the run directory.

  Phase 6.4 regenerates the final `docs/` chart from the JSON after 06.3.6.

### Judged pass and human calibration (SC-6)

- **D-112:** **Every judgeable held-out record of all four arms is judged** on faithfulness and
  groundedness. "Judgeable" uses the shared `_is_judgeable` predicate (`score.py`), with no
  `--sample` cap. The judge runs as its own capped stage (D-47/D-86) with cached verdicts, and
  produces paired judged deltas against `hybrid` (D-97).
- **D-113:** **The calibration slice has 20 items** (the SC-6 floor, sized to the owner's real
  effort per D-48), all drawn from the held-out run of record.
  - **Draw:** 5 per arm, seeded, spread across question types.
  - **Blinding:** the worksheet hides the arm label and the judge verdict.
  - **Sequence:** the slice IDs and worksheet are committed before scoring, and the owner's scores
    are committed **before any judged aggregate or per-arm judged delta is shown**. The plan must
    make that ordering hold.
  - **Output:** QWK and Spearman rho with bootstrap CIs per dimension, from `agreement.py`.
- **D-114:** **A pre-committed trust floor on judge–human agreement.**
  - The floor applies **per dimension** to the QWK **point estimate**, with the CI disclosed. Research
    proposes the value, and it is committed in `thresholds.py` before the owner scores.
  - A dimension below the floor is still published, labelled **"uncalibrated"**, and is barred from
    any 06.3.6 default decision.
  - There is no judge re-prompting or rubric change to chase agreement (D-49).

## Specific Ideas

- Drive-2 reference readings: hybrid (graph-off) `answer_usable` 0.58. Paired graph-on minus graph-off is within CI of zero on every answer metric. `ranking_quality` is significantly negative (-0.08). Graph-on latency is +1.2–1.6 s.

- The owner wants this as the standard-RAG baseline the project never had, placed against the paper's retrieval table, honestly, in whichever direction it comes out.
