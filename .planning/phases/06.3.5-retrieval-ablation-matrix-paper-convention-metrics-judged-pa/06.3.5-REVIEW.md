## Critical Issues

### CR-01: A lowercase `answer:` line defeats the abstention disagreement guard, so a contradicting `model_only` output is normalised

**File:** `engine/src/generation/final_answer.rs:175-196` and `:255-265`
**Issue:** `abstains` has the documented purpose that "a `final_answer` field that disagrees with the model's own prose is never read as an abstention". It enforces this through `locate_trailing_model_answer`, which uses `rfind("Answer:")`, so it is case-sensitive. `published_answer_text` matches the engine-rendered line case-insensitively. Take a `model_only` output citing `[1]`, with `answer` = `"Checked [1].\nanswer: Yes"` and `final_answer` = `"Insufficient information"`.
- `locate_trailing_model_answer` finds no segment.
- `strip_trailing_model_answer` leaves the model's line in place.
- The rendered text is `"...answer: Yes\nAnswer: Insufficient information"`.
- `published_answer_text` matches, and `is_none_or` returns true.
- The output is normalised to `retrieval` and published as an abstention while the model's own last line said yes.

The pinned test uses the capitalised `Answer: Yes` only. The same applies to `**answer:**`.
**Fix:** Locate the label case-insensitively, consistent with `strip_leading_answer_label` and the harness `_ANSWER_LINE` regex (`(?i)`), for example by scanning `last_line` with an ASCII-case-insensitive `rfind`. Add a test for `answer: Yes` and `**answer:** Yes` against `final_answer = "Insufficient information"`.

**Why this is a BLOCKER:** the path is reachable on the live stack and violates both the documented contract of `abstains` and the requirement that a substantive `model_only` answer stay rejected. The harness detector cannot see it: `eval/scripts/basis_normalisation_counts.py` computes `normalised_not_abstaining` with `metrics.is_abstention`, which reads the engine-appended last line. That line is the abstention, so the counter reports 0 whether or not this has happened. The only sign in the journal is the model's own `answer: Yes` line in the prose.

## Warnings

### WR-01: Split integrity hashes and the journal's `order_seed` / `split_sha256` are written but never verified

**File:** `eval/src/lancet_eval/run.py:386-449`, `eval/scripts/select_heldout_split.py:141-143`, `eval/src/lancet_eval/split.py:31-37`
**Issue:** `heldout_split.json` stores `populations_sha256`, `diag_selection_sha256` and `questions_sample_sha256`. The drive writes `order_seed` and `split_sha256` into the journal header. A grep of `eval/src` and `eval/scripts` finds no reader of any of them. On `--resume`, `_require_matching_journal_marker` checks only `(gate_stage, max_retries)`, and `write_header` is a no-op on an existing header. A resumed `[split]` drive therefore recomputes `plan_work_units` from whatever split file is on disk today and appends to a journal that may have been started under a different split or seed. Nothing at `score` time compares the header's `split_sha256` with the split it loads. D-73 covers only `eval/src/lancet_eval/`, not `eval/corpora/`. A changed `questions.sample.jsonl`, `populations.json` or split file, or a changed seed, passes every gate. The recorded hashes then give false assurance.
**Fix:** In `drive`, when the existing header carries `split_sha256` or `order_seed`, require equality with `split_sha256(split)` and `split.order_seed`, and raise `ValueError` otherwise. For a `[split]` corpus, refuse a header that lacks them. In `score_run`, compare the header's `split_sha256` with `split_sha256(load_split(...))`. In `load_split` or `_enforce_split_role`, recompute `lf_sha256` of the three input files and compare with the stored fields.

### WR-02: D-73 gate proves the pre-registration commit predates the data but not that its values are unchanged since

**File:** `eval/src/lancet_eval/gitcheck.py:194-239`, `eval/src/lancet_eval/score.py:257-280`, `eval/src/lancet_eval/thresholds.py:277`
**Issue:** `preregistration_problems` checks that the commit introducing the token is an ancestor of HEAD, is older than `created_at`, and (drive/judge only) that the source tree is clean. It never compares the `PREREGISTRATION_06_3_5` block at HEAD with its value at the introducing commit. Any later commit can edit `family_alpha`, `complete_case_floor`, `comparison_arms` or `matching_rule`. `score` and `compare` read those values live from `thresholds.py`, so they would be applied, and the gate would still pass. The trust floor does have this check (`calibration.py:1135` parses the blob at `emitted_at_sha` and compares it with the constant). The asymmetry shows it was intended and missed for the primary pre-registration.
**Stronger form:** `score._require_preregistered_before` calls `preregistration_problems` without `require_clean_tree` (`run` and `judge_stage` both pass it), and `comparison.py` imports no `gitcheck` at all. `compare` is where `family_alpha`, `complete_case_floor` and `comparison_arms` decide "significant" and "evaluable". An uncommitted local edit to `thresholds.py` is therefore applied by `compare` with no gate, and by `score` too. A later commit is not even needed.
**Fix:** In `score_run` for a `[split]` corpus, read `show_blob(sha, THRESHOLDS_PATH)` at the introducing commit and require the `PREREGISTRATION_06_3_5` assignment to be AST-equal to the one at HEAD (reuse the `_parse_floor` approach), or hash the block into the journal header at drive time and compare at score time.

### WR-03: The abstention check bounds only the last line, not the prose, so the "substantive model_only is still rejected" guarantee depends on the model

**File:** `engine/src/generation/final_answer.rs:255-265`, `engine/src/generation/mod.rs:223-235`, `engine/src/generation/tests.rs:3210-3260`
**Issue:** `abstains(prose, Some("Insufficient information"))` is true for any prose, and a test pins this with prose that is only a stub. Take a `model_only` output with substantive prose, for example `"Paris is the capital of France [1]."`, one cited ID, no model-written `Answer:` segment, and `final_answer = "Insufficient information"`.
- `grounded_abstention_view` returns a `retrieval` view.
- Both seams accept it, and it is published with a BASIS_RECONCILED notice.
- The harness then counts it as an abstention and drops it from the judged population.

The rejection test covers only `final_answer: "Yes"`. The decision text says a grounded abstention names the evidence blocks it checked, but nothing enforces that the prose is an abstention.
**Fix:** Either accept the residual risk and say so in the decision record and docs, or constrain the view. For example, require that the prose contains no sentence outside the `[n]` checked-blocks form, or cap its length. At minimum add a test that pins the chosen behaviour for substantive prose plus an abstaining `final_answer`.

### WR-04: Alias-equivalent or repeated arm labels in a corpus TOML pass `CorpusConfig` and fail only at score time, after paid spend

**File:** `eval/src/lancet_eval/corpus.py:143-146`, `eval/src/lancet_eval/run.py:402-408`, `eval/src/lancet_eval/score.py:156-166`
**Issue:** The load-time check validates each label with `canonical_arm(label)` but never checks that labels are distinct after canonicalisation. `arms = ["hybrid", "graph-off", ...]` loads. `plan_work_units` and the non-split cross product then schedule both. `journal_key` differs per label, so both are driven and paid for. Scoring then raises `ScoreError` ("are the same arm"), and `plan_work_units` also has a `ZeroDivisionError` for an empty arm list (`i % len(arm_list)`).
**Fix:** In `CorpusConfig.__init__`, after the loop, reject an empty list and any two labels with equal `canonical_arm`, naming both, mirroring `_group_records_by_arm` and `p4._canonical_arms`.

### WR-05: `form_arm_pairs` applies the graph-off provenance edge to the reference unconditionally, contradicting its docstring

**File:** `eval/src/lancet_eval/pairing.py:216-221` (docstring at `:125-135`)
**Issue:** The docstring says the GRAPH_ABLATION provenance edge "applies to every side whose arm disables graph context". The code applies `has_arm_provenance(rec_off)` to the reference regardless of the reference arm, and applies the treatment-side check only when the treatment disables the graph. Today every caller passes `reference = hybrid` or `graph-off`, so it is latent. `unpark_gates.ArmRoles` and `_form_drive2_pairs` accept arbitrary roles. Passing `hybrid+graph` as the reference would drop every pair as a provenance drop (reading as zero coverage) rather than raising.
**Fix:** Mirror the treatment logic: compute `reference_needs = resolve_arm(reference).disable_graph_context` and apply `has_arm_provenance(rec_off)` only when it is true. Pass both flags into `_join_pairs`.

## Info

### IN-01: A resumed judge stage overwrites its counts, spend and call totals

**File:** `eval/src/lancet_eval/judge_stage.py:390-397` and `:477`
**Issue:** `spend`, `calls`, `keys_attempted` and the per-arm counters start at zero on every invocation, and `_write_stage` replaces `judge-stage.json`. After a stop and a resumed stage, the committed record shows only the last portion's spend and call count. The run of record's total judge spend and the per-arm `judged_now` split cannot be reconstructed from it.
**Fix:** Read an existing stage file and carry forward cumulative `calls`, `spend_usd` and `wall_clock_s`, or append each invocation as an entry in a history list.

### IN-02: A normalised abstention is flagged `degraded_mode`

**File:** `engine/src/workflow/mod.rs:320`, `engine/src/workflow/nodes/generate.rs:555-562`
**Issue:** `derive_degraded_mode` treats any `BasisReconciled` notice as degraded. The 06.3.5-18 normalisation adds that code to a record whose final basis is `Retrieval`. The record therefore reports `degraded_mode = true` although the normalisation strengthened the claim. Harness usability does not depend on it, but any consumer of `degraded_mode` will count normalised abstentions as degraded.
**Fix:** Decide whether that is intended and document it. If not, exclude the fixed normalised-notice text from the degraded set, or give the normalisation its own notice code.

### IN-03: Preflight silently runs the legacy canaries when the corpus config fails to load

**File:** `eval/src/lancet_eval/preflight.py:1326-1332`
**Issue:** `except Exception: corpus_config = None` makes `skip_legacy_canaries` false. A held-out corpus whose TOML is malformed would then send the 8 legacy canary rows (dev IDs) to the live stack, even though the corpus declares `legacy_canaries = false`.
**Fix:** Treat a load failure as a failed preflight check, not a fall-back to the legacy behaviour.

### IN-04: Provenance clause (a) is selected by substring-matching a message

**File:** `eval/src/lancet_eval/provenance.py:200-204`
**Issue:** `mode_provenance_failures` returns prose, and `provenance_failures` keeps the ones containing `"retrieval_mode"`. Rewording either message silently moves failures between clauses (a) and (e). Clause (a) is zero-tolerance and (e) is count-and-exclude, so this changes whether the report is refused.
**Fix:** Have `mode_provenance_failures` return `(code, message)` pairs, or expose the echo check as its own function that `provenance.py` calls directly.

### IN-05: `gen_paper_golden.py` executes an externally fetched file without verifying its hash

**File:** `eval/scripts/gen_paper_golden.py:56-62` and `:243-247`
**Issue:** `load_official` runs `spec.loader.exec_module` on the path given by `--official`. The file's sha256 is recorded in the output header only after it has been executed. Pinning is by commit in the docstring, but nothing in the code checks the bytes.
**Fix:** Add an expected-sha256 constant and compare it before `exec_module`.

### IN-06: Hand-rolled SHA-256 in `inspect_lancedb`

**File:** `engine/src/bin/inspect_lancedb.rs:1306-1371`
**Issue:** A custom SHA-256 is carried "so the inspector adds no dependency", but `sha2` is already in `Cargo.lock` as a transitive dependency. The unit tests pin it to published vectors and it is correct for the cases covered. A maintained crate removes the maintenance and correctness surface at no real dependency cost.
**Fix:** Add `sha2` as a direct dependency of the engine crate and delete `sha256_hex`.
