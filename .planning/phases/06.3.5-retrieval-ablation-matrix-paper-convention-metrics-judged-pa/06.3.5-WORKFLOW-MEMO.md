# Memo: running GSD execute-phase with dynamic Workflow fan-out (phase 06.3.5)

This memo covers 2026-10-07: what we tried, what happened, how each problem was handled, and what I'd keep or change. Plan-by-plan results are in `06.3.5-HANDOVER.md`.

## The setup in one paragraph

GSD's `execute-phase` normally spawns one executor agent per plan and parallelises a wave inside one orchestrator turn. You asked for parallel waves to fan out through a dynamic Workflow instead. Here is how that worked:

- **Parallel waves** (waves 1 and 3-6, two plans each) ran as one Workflow run each. The script was generated on disk, and each run executed two `gsd-executor` agents on Sonnet in parallel:
  - The plan that touches Rust (or the lower-numbered plan, in all-Python waves) ran on the main checkout, so it could reuse the warm cargo target.
  - Its sibling ran in an isolated git worktree, which the GSD merge gauntlet folded back afterwards.
- **Single-plan waves, checkpoint continuations and the live, paid plans** (14-17) ran as ordinary sequential Agent calls on main.
- **Bookkeeping stayed with the orchestrator:** STATE.md, ROADMAP.md, the post-merge test gate, the wave:post checks and the tracking commits.

## What worked well

- **Throughput.** Each two-plan Workflow wave took 15-30 minutes of wall time: 1017 s, 934 s, 1229 s and 1758 s for waves 3-6. Running those plans one after another on main would have taken roughly twice that.
- **No merge conflicts in five parallel waves.** The planner had already given each wave's plans disjoint `files_modified`. I also told each executor which files belonged to its sibling, and none ever touched the other's files.
- **The GSD merge gauntlet accepted Workflow worktrees unchanged.** For every wave the sequence was the same:
  1. write a manifest;
  2. run `worktree.record-agent`;
  3. run `worktree.cleanup-wave`.
  It merged, removed the worktree and deleted the branch every time. The `worktree-wf_<run>-<n>` branch names were accepted with no special handling.
- **Orchestrator context stayed small.** Each executor prompt is about 37K tokens, because GSD inlines its workflow, templates and references. Passing that through Agent calls would have filled the orchestrator's context within a few waves, so I avoided it two ways:
  - The prompts were rendered to disk by a small generator, `build_wave.cjs`, and Workflow ran them through `scriptPath`.
  - Sequential agents got a "compact" prompt instead: a file path and a list of reference files to Read themselves.
- **Mid-run helpers cut per-wave overhead to about four tool calls.** Each was a small script written once and reused:
  - `merge.sh`: the gauntlet, plus a line-ending fix.
  - `gate.sh`: build, all test suites one after another, and the three wave:post checks.
  - `stateupd.cjs`: STATE pointer and status entry.
- **Quality held up.** The Sonnet executors followed TDD (RED then GREEN commits) and recorded deviations under the plan's rules. They also flagged real defects in the plans:
  - an arithmetically impossible tripwire example;
  - a stale diff anchor;
  - a too-small fixture size.
  The eval suite grew from 1117 to 1748 tests, and the engine suite from 721 to 741.

## Autonomous mode

After wave 3 you switched the run to autonomous mode:
- pre-authorised answers for each paid checkpoint;
- a strict list of stop conditions;
- a handover file instead of interactive questions.

Two cap checkpoints were answered from the pre-authorisation: 14 Task 2, and 15 Task 1, which was applied before dispatch because it is the plan's first task. Each answer was recorded in STATE in its own commit before its continuation started. The first unforeseen live event (item 7) triggered a clean stop with everything committed.

## Numbers

- **Plans:** 14 of 17 done in about 5.5 hours of wall time (first commit 07:17Z, stop 12:37Z). That includes the crash recovery and about 40 minutes of live rehearsal and preflight.
- **Executor runs:** 13 code plans, 1 rehearsal, plus continuations. 10 ran inside 5 Workflow runs.
- **Spend:** $0.0080 total on paid steps, against caps of $0.05, $0.02 and $2.00. No cap was hit.
- **Merges:** 5 worktree merges, 0 conflicts, 5 line-ending-only blocks, all auto-resolved.
- **Tests at the stop:** engine 741, gateway 120, eval 1748. Every post-merge gate was green.

## Would I do it this way again?

Yes, for phases with clean file splits and offline work. Keep these:
- the on-disk prompt generator;
- explicit sibling-file ownership notes in each prompt;
- the orchestrator-owned STATE and ROADMAP writes;
- the helper scripts.

Change these:
- plan long live runs as split tasks from the start;
- pre-authorise one canary retry for any fail-closed check on a stochastic model;
- put the resource limits in the generator from day one.

Don't use Workflow for anything that needs the gitignored live store, `.env` or a running stack. Those stay sequential on main.
