### Retrieval mode and the ranking field (SC-1, SC-2, SC-3 input)

- **D-99:** **`retrieval_mode` is a request field** (`dense_only` / `bm25_only` / `hybrid`, default
  `hybrid`). It is orthogonal to `disable_graph_context`.
  - **Mechanics: the excluded path is skipped, not zero-weighted.** `dense-only` never calls the
    BM25 port and `bm25-only` never calls the dense port. RRF then runs over the single list, so
    per-arm latency and cost show the real cost of each path.
  - Under the default, `engine/src/retrieval/testdata/graph_off_fusion.golden` stays byte-identical.
  - The mode is visible per record on the wire, as a notice code or a snapshot field, so the
    harness can verify arm provenance the way it verifies `GRAPH_ABLATION`. Follow the D-52 pattern:
    regenerate both proto trees and the gateway's vendored `gateway/proto/lancet/v1/lancet.pb.go`,
    and add a gateway test that pins the field end to end.
  - **Reversibility:** costly. It adds a field to the public query contract that every API client
    sees, and removing it later breaks any client that set it.
- **D-100:** **An opt-in pre-truncation ranking field.** When the request sets a diagnostic flag
  next to `retrieval_mode`, the snapshot carries the full fused ranking before truncation, up to
  `candidate_limit` (32).
  - It carries IDs and ranks only: `chunk_id`, `document_id`, fused rank, and the per-list ranks
    that `Candidate` already holds (`vector_rank`, `bm25_rank`, graph contribution). There is no
    text.
  - Without the flag the field is absent and responses do not grow.
  - A golden test proves that with the flag on, the final 8, the prompt and the answer path are
    byte-identical to the flag being off.
  - The harness sets the flag on every arm of the held-out drive.
  - 06.3.6's reranker reads the same field ("gold was at rank 14 before rerank").
  - **Reversibility:** costly, for the same contract reason as D-99.
- **D-101:** **The arm registry generalises to a label → request-flags table.**

  | Arm | `retrieval_mode` | Graph |
  |---|---|---|
  | `dense-only` | `dense_only` | off |
  | `bm25-only` | `bm25_only` | off |
  | `hybrid` | `hybrid` | off |
  | `hybrid+graph` | `hybrid` | on |

  - `[arms]` in the corpus TOML, `--arm` on the CLI and the provenance checks all agree, and every
    record carries its arm.
  - The legacy labels `graph-off` and `graph-on` resolve as read-only aliases of `hybrid` and
    `hybrid+graph` when historical journals are read.
  - `unpark_gates` takes the reference arm as a parameter. The recorded drive 1, 1b and 2 verdicts
    must re-read unchanged, proven by a test.

### Paper-convention metrics (SC-3)

- **D-102:** **Hits@4, Hits@10 and MRR@10 follow the official MultiHop-RAG evaluation script**, and
  so does **MAP@10** if that script computes it.
  - Research pins the script's repository and commit, and the canonical refs record it.
  - Matching is at document level, and chunks are deduplicated to documents exactly as the script
    does. This is not reconstructed from memory.
  - **Precedence:** if the official script's matching unit is not document level (for example,
    it matches evidence text inside retrieved chunks), the script governs. The ROADMAP's
    "document-level" wording is then recorded as a deviation in the caveat.
  - The ranking input is D-100's field. **IDs-only is enough under either matching unit.** For
    chunk-level matching, the harness uses the D-61 evidence-to-chunk mapping
    (`.planning/phases/06.3.4.1-.../diagnostic/post-reconcile/gold_chunks.jsonl`, `in_chunk` items)
    to match by chunk ID, so no text is needed on the wire. G already excludes
    `split_across_chunks` items.
  - These are additive, labelled dimensions **side by side** with Lancet's chunk-level metrics
    (coverage@4, precision@4). The methodological caveat is rewritten to name exactly which figures
    are comparable to the paper's table, and why the corpus still differs (346-doc subset, Lancet's
    chunker and embedder).
- **D-103:** **The paper's published retrieval figures appear as a cited reference row** under the
  four arms. The citation names the paper version and table, and the non-comparability caveat sits
  beside the row.
- **D-104:** **Hits@4 is retro-computed on the drive-2 journal**, as a read-only offline analysis
  under the D-74 guardrail.
  - It never calls `score` or `report` and adds no bypass of the fail-closed path.
  - It is labelled "dev-only, paper-convention @4". The @10 metrics are not computable there.
  - It gives 06.3.6 a dev baseline for `hybrid` and `hybrid+graph` at no cost.

### Dev / held-out split (SC-4)

- **D-105:** **The held-out set is the whole non-dev pool:** all **308** non-dev G questions plus all
  **43** non-dev null questions, 351 questions in total.
  - Null questions feed only the D-72 abstention metric per arm. They never enter retrieval or
    answer denominators.
  - Before any paid request, a committed split file records:
    - the dev IDs, from `eval/corpora/multihop_rag/diag_selection.json`;
    - the held-out IDs;
    - the derivation rule ("every non-dev sample question in G, plus every non-dev null");
    - the sha256 of the `populations.json` it was derived from;
    - the seed for the drive's question and arm order.
  - **Mapping to SC-4's wording:** the SC-4 held-out set, which is the retrieval and answer
    population restricted to gold-in-index, is the **308 G questions**. It is a deterministic
    whole-pool draw. Its recorded seed is the order seed, and its size and IDs are in the split
    file. The **43 nulls are an additive abstention-only stratum** outside SC-4's restricted set.
  - Since the whole pool is taken, there is no sampling seed. If the pool ever has to be
    subsampled, the fallback is proportional stratification by `question_type`, with the seed
    recorded.
  - 06.3.6 inherits the split, develops on dev only and reads held-out once.
  - **Reversibility:** one-way. Once held-out has been read it cannot be made fresh again, and
    taking the whole pool leaves no untouched question in the 500 sample for a third read.
    Accepted by the owner for the narrower CIs (about ±5.5 points).
- **D-106:** **The dev set gets no new arms.** It already has `hybrid` and `hybrid+graph` from
  drive 2 (graph-off and graph-on), plus D-104's retro Hits@4. Within this phase no weight,
  threshold or prompt changes after a held-out reading (D-49).

### Drive shape (SC-5)

- **D-107:** **There is one held-out drive with the four arms interleaved per question.**
  - All four arms of a question run back to back. Arm order is a seeded, balanced rotation, so each
    arm runs first about 25% of the time.
  - The drive uses `--workers 1` (latency stays comparable to drive 2), `--retries 0` (D-67) and
    `--gate-stage`. It is preceded by its own D-86 `checkpoint:decision` for `--stage-cap`.
  - Size is 351 × 4 = **1,404 records**, at roughly $0.45–0.55 and about 3.5 h, run detached.
  - D-96 routing is unchanged. A provider switch is disclosed per arm, as in drive 2.
- **D-108:** **A rehearsal comes before the paid drive.** It covers:
  - preflight and canaries under all four modes;
  - D-99 and D-100's golden tests;
  - a tiny live probe of about 3 questions × 4 arms under a cent-level cap. It is paid, so it gets
    its own D-86 checkpoint. It proves arm provenance and the ranking field on the wire, through
    harness → gateway → engine.

  Only then comes the drive's cap checkpoint.
- **D-109:** **Gates are read per arm, plus a pooled line.** Completeness and error mode/flatness
  use 06.3.4.1's SC-1 and SC-2 definitions, with D-89 materiality. A failing arm cannot hide in
  the pool, and the pooled line keeps continuity with drive 2's readings.
- **D-110:** **A gate miss allows one bounded re-drive, then halt-disclose** (the D-83/D-84 rule).
  - The one fix allowed is an infrastructure or plumbing bug (harness, wire, provenance), justified
    by the per-record table, and the re-drive gets a new cap. A quality change to the system under
    test is never allowed.
  - An arm that is genuinely worse (for example BM25 retrieving less gold) is a result, not a gate
    miss.

### Judged pass and human calibration (SC-6)

- **D-112:** **Every judgeable held-out record of all four arms is judged** on faithfulness and
  groundedness. "Judgeable" uses the shared `_is_judgeable` predicate (`score.py`), with no
  `--sample` cap. The judge runs as its own capped stage (D-47/D-86) with cached verdicts, and
  produces paired judged deltas against `hybrid` (D-97).
- **D-113:** **The calibration slice has 20 items** (the SC-6 floor, sized to the owner's real
  effort per D-48), all drawn from the held-out run of record.
  - **Draw:** 5 per arm, seeded, spread across question types.
  - **Blinding:** the worksheet hides the arm label and the judge verdict.
  - **Sequence:** the slice IDs and worksheet are committed before scoring, and the owner's scores
    are committed **before any judged aggregate or per-arm judged delta is shown**. The plan must
    make that ordering hold.
  - **Output:** QWK and Spearman rho with bootstrap CIs per dimension, from `agreement.py`.
- **D-114:** **A pre-committed trust floor on judge–human agreement.**
  - The floor applies **per dimension** to the QWK **point estimate**, with the CI disclosed. Research
    proposes the value, and it is committed in `thresholds.py` before the owner scores.
  - A dimension below the floor is still published, labelled **"uncalibrated"**, and is barred from
    any 06.3.6 default decision.
  - There is no judge re-prompting or rubric change to chase agreement (D-49).

*D-118..D-120 were added on 2026-10-06, after the AI-SPEC was drafted (owner decisions; see `06.3.5-AI-SPEC.md` §5 "Owner decisions and forced settlements").*

- **D-118:** **How abstention is handled in the judged pass** (owner-approved).
  - **Definition:** an answer abstains when its final line is `Answer: Insufficient information`, compared
    after normalisation (case and trailing punctuation).
  - **Judged dimensions:** groundedness and faithfulness are computed only on non-abstaining answers.
  - **Reporting:** the per-arm abstention rate, with its n, is reported next to every judged aggregate and every
    paired judged delta. A judged number is never shown without it.
  - **Paired judged deltas (D-97):** pair only questions where both arms gave a non-abstaining answer. Report the
    pairing n and the count excluded for abstention.
  - **Calibration slice (D-113):** drawn only from non-abstaining, judgeable records.
  - **Null questions:** the 43 nulls are never sent to the judge. They are scored only on abstention correctness
    (06.3-AI-SPEC #5, D-105).
  - **Abstaining G records:** they may be judged and cached for audit, but they are excluded from every judged
    aggregate, delta and calibration draw.
- **D-119:** **The D-114 floor value** (owner-approved).
  - **Value:** 0.70 per dimension, on the QWK point estimate. This continues `gate.py` `AGREEMENT_TARGET`.
  - **When:** committed as a new `thresholds.py` constant, with a provenance comment in the 06.3.4.1 style,
    before the owner scores the slice.
  - **Noise, stated outright:** at n = 20 the bootstrap CI is roughly ±0.3 at its widest, so a true value near
    0.70 makes the call close to a coin flip. The CI is always disclosed.
  - **One gate only:** "uncalibrated" is decided only by this floor. The legacy `calibration_state` (kappa and
    Spearman ≥ `AGREEMENT_TARGET`, `CALIBRATION_SIZE` 12) is informational and gates nothing in 06.3.5.
- **D-120:** **Judge mechanics forced by locked decisions** (settled 2026-10-06, no owner choice involved).
  - **Registry:** the judge loop runs over the D-101 arm registry (all four arms), replacing `score.py:287`'s
    hard-coded graph-on/graph-off and the primary-arm-only `p_records` loop. A record whose arm is not in the
    registry fails closed; it is never silently dropped.
  - **D-113 ordering:**
    1. A cache-only judge stage fills `judge_cache.json` and emits the worksheet. No judged aggregate is written
       or shown.
    2. The owner's calibration file is committed and ingested.
    3. Only then are judged aggregates computed.

    The mechanism is left to the planner; the ordering is not.
  - **Worksheet:**
    - A seeded, arm-stratified draw replaces the first-20-in-journal-order draw (`score.py:959-980`).
    - Rows carry opaque slice IDs, with no `cache_key` and no arm label.
    - A separate mapping file (slice_id → cache_key, arm) has its hash committed before scoring.
    - Identical cache keys are deduplicated across arms before the draw.
  - **Bootstrap:** the D-111 deltas use `stats.py` `BOOTSTRAP_B = 10_000`, and the agreement CIs pass `b=10000`
    explicitly to `bootstrap_agreement_ci`.
  - **Judge prompt:** `JUDGE_PROMPT_VERSION` stays `"v1"`. The `Answer:` line is judged as one more claim under the
    existing rubric (D-49).

## Summary

The phase is mostly **harness work on a closed measurement system**, with one small and costly wire change. The wire change adds `retrieval_mode` (request) and an opt-in pre-truncation ranking (snapshot) to protobuf, the Rust `RetrieveHybridNode`, the Go gateway's hand-written request and DTO mapping, and the Python client. Everything else (arm registry, split, rotation, paper metrics, abstention predicate, P4 population, exact sign-flip and Holm, per-arm gates, judge stage, blinded calibration, comparison artifact, chart) is new Python on top of existing modules. No new dependency is needed: `eval/uv.lock` contains no scipy, numpy or matplotlib [VERIFIED: ran `grep -c "scipy\|numpy\|matplotlib" eval/uv.lock` = 0], and everything required (exact binomial via `math.comb`, Holm, SVG via `jinja2` or string templates) is stdlib.

The most important research findings are the places where the repository contradicts the inputs (see "Disagreements" below): the gateway test-count gate fails today (118 vs 114); the prost struct-literal count is 6 `RetrievalSnapshot` literals and **zero** `QueryRagRequest` literals (not 9 and 20); `DimensionResult.detail` is `dict[str, float]` so labels cannot live in `report.json` and the AI-SPEC's "add dimensions to `report.schema.json`" is unnecessary; the pre-existing preflight canaries send **four of the seven distinct canary questions that are held-out** to the live system; and `index_generation` is `lance-<nodes_version>`, which makes a version-pinned chunk-text dump possible. Each is resolved with a recommendation below.

**Primary recommendation:** Build a tracer slice first (one `dense_only` request with the ranking flag, end to end through proto, engine, gateway, harness client and `paper_metrics`, proven offline with the existing fakes), record the byte-identity goldens at the pre-change HEAD before touching the engine, make the wire contract land before the harness sends any new field (the gateway uses `DisallowUnknownFields`), commit every pre-registered constant and the abstention predicate in one `thresholds.py` commit before the first paid request, and keep all judged aggregates behind a code-enforced ordering gate (`judge` writes the cache only; `score --judged` is the single path that computes judged numbers).

### Pattern 1: Resolve the mode once at admission and echo it only when it was sent
**What:** `WorkflowContext` stores the request's `RetrievalMode` as received (`Unspecified` when absent). Helpers treat `Unspecified` as `Hybrid`; the snapshot echoes the stored value verbatim, so an absent mode echoes `0` and the gateway DTO omits it (`omitempty`). This gives "default is indistinguishable from absent" for free, with no separate `explicit` flag.
**When to use:** every new request option whose default must equal today's behaviour.
**Example (PROPOSED; existing symbols cited):**
```rust
// engine/src/workflow/mod.rs  (next to the existing `pub disable_graph_context: bool,` at :86 and its init at :142)
pub retrieval_mode: RetrievalMode,               // PROPOSED: request value; Unspecified == Hybrid
pub include_pre_truncation_ranking: bool,        // PROPOSED
// in WorkflowContext::new: retrieval_mode: RetrievalMode::try_from(request.retrieval_mode).unwrap_or_default(),
// (service.rs admission has already rejected unknown values, so unwrap_or_default is unreachable in production)
```

### Pattern 2: Gate the call inside `execute_inner`, never by removing the port
**What:** `fetch_graph_candidates` reads graph rows through `dense_port.fetch_chunks_by_id` and returns empty when there is no dense port [VERIFIED: engine/src/workflow/nodes/retrieve.rs:513-516 "let Some(dense_port) = &self.dense_port else {" / "return Ok(Vec::new());"]. **What "RRF over the single list" means.**

- `bm25_only`: dense never runs. "Vec::new()"].

## Common Pitfalls

### Pitfall 1: Hashing working-tree bytes
**What goes wrong:** the split file's `populations_sha256` (or the worksheet key hash) is computed on a CRLF working copy and cannot be re-verified from a clean checkout or `git show`.
**Why it happens:** `core.autocrlf=true`; `populations.json` is CRLF in the tree and LF in the index (hashes differ, see Anti-Patterns).
**How to avoid:** hash LF-normalised bytes or canonical parsed JSON; generator and test share one function.
**Warning signs:** a hash that differs between `sha256sum file` and `git show HEAD:file | sha256sum`.

### Pitfall 2: The embedding skip trips a source-text test
**What goes wrong:** `engine/src/tests/graph_cutover.rs` reads `graph_context.rs` with `include_str!` and asserts the byte order of three strings: `"if ctx.disable_graph_context {"`, `"let question = ctx.original_query.clone();"`, `"graph_port.query_graph("` [VERIFIED: engine/src/tests/graph_cutover.rs:592-612], and that `graph_port.query_graph(` appears exactly once.
**How to avoid:** express the embedding guard with a named boolean (`needs_query_embedding`), never with the literal `if ctx.disable_graph_context {` before the existing line at :96; do not add a second `query_graph(` call.
**Warning signs:** `the_node_copies_the_question_for_the_port_only_after_the_ablation_return` fails after an unrelated-looking edit.

### Pitfall 3: Harness sends new keys before the gateway knows them
**What goes wrong:** HTTP 400 `invalid request body` on every request (`dec.DisallowUnknownFields()` at gateway/main.go:656), so the drive records every unit as an error.
**How to avoid:** plan order 02 -> 03 -> harness live use; the rehearsal journal-level assertion catches it.

### Pitfall 4: `omitempty` hides "flag on, nothing retrieved"
See U2: an empty ranking is omitted. The invariant checker keys on `retrieved_chunks` being non-empty.

### Pitfall 5: `report.json` cannot carry a label
`DimensionResult.detail` is `dict[str, float]` (dimensions.py:39). Use float codes for in-report state and the `comparison.json` sidecar for text (U13).

### Pitfall 6: `KeyError` from the hard-coded primary arm
`score_run` builds `arm_metrics` per arm and then does `p_data = arm_metrics[primary_arm]` with `primary_arm` defaulting to `"graph-on"` (score.py:417-425). Rebuilding `records_by_arm` with canonical keys without changing this raises `KeyError`. Make the primary arm `hybrid+graph` via `canonical_arm`.

### Pitfall 7: Per-arm flatness needs renumbered ordinals
Proven `DecayAnalysisError: Gap in ordinals detected: expected 2, found 3` (U11).

### Pitfall 8: The legacy judge path or `report` silently writes judged aggregates
`score --judge` judges, emits the worksheet and rewrites `report.json` in one call; `report` and `staged-gate` call `score_run(no_judge=True)` themselves when `report.json` is absent. Gate the legacy path on the corpus `[judge] protocol` key, and make `score --judged` the only judged-aggregate writer.

### Pitfall 9: Canary rows are held-out questions
Four of seven distinct canary IDs are held-out and two are dev (Disagreement 5). The legacy 8-row manifest therefore cannot be reused for the four-arm preflight: held-out IDs are a D-105 read and dev IDs under `dense-only`/`bm25-only` violate D-106. The arm-mode canaries come from the 49-question rehearsal pool only. Decide before the first preflight of the held-out corpus.

### Pitfall 10: `pytest -q` from the root fails for an unrelated reason
`scripts/test_phase02_live_evidence.py` requires `-O`. Use `uv run --project eval pytest eval/tests -q` for the harness gate.

### Pitfall 11: The judge cache is rewritten on every `set`
`JudgeCache.set` calls `save()` (full JSON rewrite, `indent=2`) each time [VERIFIED: eval/src/lancet_eval/judge.py `def set(self, key: str, entry: JudgeCacheEntry) -> None:` followed by `self.entries[key] = entry` and `self.save()`]. At about 808 entries of a few KB each this is acceptable (about a gigabyte of cumulative disk writes [ASSUMED: estimated]), and it is crash-safe; do not "optimise" it away in the judge stage.

### Pitfall 12: bm25-only can produce blank NO_EVIDENCE answers
A BM25-only query with no lexical overlap can retrieve nothing, take the NO_EVIDENCE path and skip generation (blank answer, no citations). `has_scorable_payload` excludes blank answers from legacy per-arm denominators, which would flatter a declining arm; D-121's P4 keeps the record and scores `answer_usable` = 0, and D-122's script-faithful line scores an empty ranking as a miss. Print the per-arm NO_EVIDENCE count (AI-SPEC §6).

### Exact paired sign-flip (exact McNemar) and Holm, stdlib only (PROPOSED; behaviour verified)
```python
# Source: executed in research/u10_stats_probe.py; D-123
from fractions import Fraction
from math import comb

def exact_signflip_p(n_pos: int, n_neg: int) -> Fraction:
    nd = n_pos + n_neg
    if nd == 0:
        return Fraction(1)
    s_obs = abs(n_pos - n_neg)
    tail = sum(comb(nd, k) for k in range(nd + 1) if abs(2 * k - nd) >= s_obs)
    return Fraction(tail, 2**nd)          # (5, 0) -> 1/16

def holm_stepdown(ps, alpha=0.05):
    m, order = len(ps), sorted(range(len(ps)), key=lambda i: ps[i])
    reject, adj, running, stopped = [False] * m, [0.0] * m, 0.0, False
    for rank, i in enumerate(order):
        running = max(running, min(1.0, (m - rank) * ps[i])); adj[i] = running
        if not stopped and ps[i] <= alpha / (m - rank): reject[i] = True
        else: stopped = True
    return reject, adj
```

# Source: AI-SPEC §3 Entry Point, re-executed this session (0 mismatches / 1707 queries)
def paper_question_scores(ranked, gold, matches):
    """ranked: list of items (chunk ids or texts); gold: list of gold units; matches(item, unit) -> bool."""
    found, ap_sum, first = set(), 0.0, None
    for rank, item in enumerate(ranked[:10], start=1):
        hit = [i for i, g in enumerate(gold) if matches(item, g)]
        if hit:
            new = [i for i in hit if i not in found]
            first = first or rank
            found.update(new)
            ap_sum += len(new) / rank           # NON-STANDARD numerator: facts first found here
    return {"hit4": first is not None and first <= 4, "hit10": first is not None,
            "rr": 1 / first if first else 0.0, "ap": ap_sum / min(len(gold), 10)}
# ID matcher:   lambda cid, gold_set: cid in gold_set       (split_across_chunks -> frozenset(): never matches, still counted)
# text matcher: lambda text, fact: strip(fact) in strip(text), strip = remove " " and "\n"

### Known Threat Patterns for this stack
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Unknown or out-of-range enum value silently treated as hybrid | Tampering / Repudiation (an arm delta becomes an artefact) | Reject at gateway (400) and engine (`InvalidArgument`); pin tests that the engine is not called. |
| Predicate injection through a chunk ID in the store dump | Tampering | Validate ID shape + escape + batch; read-only store. |
| Calibration leakage (arm or verdict visible to the scorer) | Information disclosure -> biased agreement | Opaque slice IDs, no `cache_key`/arm/question_id in rows, commit-reveal key hash, verdict-free stage output, code-enforced ordering. |
| Forking paths (constants chosen after seeing data) | Repudiation | One pre-drive `thresholds.py` commit older than the journal `created_at`; the floor read from the emit commit via `git show`. |
| Prompt injection through retrieved evidence reaching the judge | Tampering | Inherited: evidence is untrusted data in the user turn; rubric in the system turn; no change here. |
| Response growth / DoS via the ranking flag | Denial of service | Opt-in flag; capped at `candidate_limit`; gateway body-size limit unchanged. |
