### WR-01: Split integrity hashes and the journal's `order_seed` / `split_sha256` are written but never verified

**Files modified:** `eval/src/lancet_eval/split.py`, `eval/src/lancet_eval/run.py`, `eval/src/lancet_eval/score.py`, `eval/scripts/select_heldout_split.py`, `eval/tests/test_split_integrity.py` (new), `eval/tests/test_run_arms.py`, `eval/tests/test_four_arm_report.py`
**Commits:** c453d88f (checks and tests), 40436445 (proof against every tracked journal)
**Applied fix:**
- `split.split_input_problems(split, repo)` recomputes `lf_sha256` of `populations.json`, the dev-ID file (`split.dev_source`) and `questions.sample.jsonl` and names any that is missing or differs from the split's stored field. `drive` runs it before `_enforce_split_role` and raises `ValueError` ("no longer matches ... refusing to drive") before any journal I/O. `POPULATIONS_REL` moved to `split.py` and `select_heldout_split.py` imports it, so the path has one definition.
- `run._require_matching_split_marker`: a `[split]` drive that finds an existing non-empty journal requires its header to carry both `order_seed` and `split_sha256` and to equal this drive's; it refuses a header that lacks them. A non-split drive refuses a journal whose header carries either marker. A new or empty file is accepted.
- `score_run`: for a `[split]` corpus, a header `order_seed` or `split_sha256` that differs from the split on disk raises `ScoreError`.

**Scope limits, deliberate:**
- `score` compares a marker only when the header carries one. It does not refuse an absent marker, and it does not recompute the three input-file hashes. The score fixtures (`test_four_arm_report.py`, `test_score_judged_ordered.py`, `test_paper_text_crosscheck.py`) write hand-built headers without the markers and splits with placeholder hashes, so either refusal would have meant rewriting those fixtures. The drive is the point that spends money, and it carries the full check (markers and input hashes).
- `judge_stage` was not given the check.

**Accepts the committed artifacts:** the three committed `[split]` journals (`2026-10-07-heldout-...`, `-rehearsal-...`, `-rehearsal2-...`) all carry `order_seed` 42 and `split_sha256` `d0d56609...1c2`. Before coding, confirmed each equals the split on disk, and that all three input-file hashes match the committed `heldout_split.json`. A non-`[split]` drive that resumes into a pre-marker journal does read its header and refuses only a header that carries `order_seed` or `split_sha256`; none of the legacy, diag or headerless measure journals does. `test_split_marker_check_accepts_every_tracked_journal_under_eval_runs` runs the drive check over every git-tracked `eval/runs/*/journal.jsonl` (the three `[split]` journals against the committed split, every other one against `None`). Tests `test_every_committed_split_journal_names_the_committed_split`, `test_the_committed_split_matches_the_files_it_was_derived_from` and `test_split_marker_check_accepts_every_committed_split_journal` run the checks against the real files.

### WR-02: D-73 gate proves the pre-registration commit predates the data but not that its values are unchanged since

**Files modified:** `eval/src/lancet_eval/gitcheck.py`, `eval/src/lancet_eval/run.py`, `eval/src/lancet_eval/score.py`, `eval/tests/conftest.py`, `eval/tests/test_preregistration.py`
**Commit:** 7a0abe78
**Applied fix:**
- `gitcheck.preregistered_value_problem(token, sha)` parses (never executes) the `THRESHOLDS_PATH` blob at the introducing commit and the file on disk, and requires the module-level assignment of the token to be AST-equal. Comments and formatting are not differences; a changed literal is. A token with no readable assignment on either side is a problem (fail closed).
- `preregistration_problems(..., unchanged_since_introduction=True)` applies it per token. `drive` (for `PREREGISTRATION_06_3_5`) and `score` (for both tokens) now pass it.
- The comparison is against the file on disk, which is what the harness imports and applies. That catches a later commit and an uncommitted edit alike.
- Stronger form, partly applied: `score._require_preregistered_before` now also passes `require_clean_tree=True`, as `drive` and the judge stage already do. The affected suites stayed green with no fixture changes beyond one added patch line in the shared `preregistered_clean_tree` fixture (it stubs the new function, like the five gitcheck functions it already stubs).

**Not applied (partial):** `compare` still has no git gate. `comparison.py` imports no `gitcheck`; adding one needs its own fixtures and git plumbing across `test_comparison.py`, which the hand-off ruled out ("only if green without fixture gymnastics"). A local uncommitted edit of `family_alpha`, `complete_case_floor` or `comparison_arms` is therefore still applied by `compare` without a gate. `score` is now covered. Worth carrying to 06.3.6.

**Accepts the committed artifacts:** `test_the_live_repository_values_match_their_introducing_commit` runs the check against the real history; `thresholds.py` has not changed since the introducing commit `ac2bf45d`.
**Status:** partial: AST-equality (drive and score) and the score clean-tree gate applied, `compare` gate not applied. Requires human verification (gate logic).
