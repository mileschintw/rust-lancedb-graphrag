# Phase 04.1 Plan 05: Score-Interleaved Graph-Weighted Prompt Integration Summary

**Upgraded Plan 02's append-order graph-context packing to score-interleaved, validated `graph_weight`-scaled competition for the shared prompt token budget, fixed a real bug that silently dropped graph facts from the actual outbound OpenRouter request, and proved `graph_augmentation` outcome tagging observable end-to-end via a real async-safe tracing capture layer.**

## Performance

- **Duration:** ~65 min
- **Completed:** 2026-08-08T00:19Z
- **Tasks:** 2
- **Files modified:** 7

## Accomplishments

- Rewrote `pack_evidence_and_graph_prompt` (`engine/src/prompt.rs`) so remaining chunk evidence (beyond the single reserved top block) and graph facts each min-max normalize within their own source, graph facts are scaled by a new `graph_weight` parameter, and both compete for the same remaining token budget via one descending-score-sorted pass — with an explicit graph-wins-ties rule that reverses the append-only design's historical bias against graph facts.
- Added `graph_weight == 0.0` as an unconditional hard-exclude, applied before any normalization or packing runs, proven correct under both a tight budget (Test 3) and a deliberately abundant one (Test 3b) — closing REVIEWS.md's MEDIUM finding that a prior draft only deprioritized zero-weighted graph facts rather than truly excluding them.
- Added empty-slice guards: an empty `evidence` slice always returns `Err(EmptyEvidence)` regardless of `graph_facts` content (D-27); an empty `graph_facts` slice returns `Ok(..)` with zero `<GRAPH_FACT>` blocks — neither path panics on `.min_by`/`.max_by` over an empty iterator (REVIEWS.md/Antigravity MEDIUM, must-resolve #3).
- Added validated `graph_weight: f64` to `RetrievalSettings`/`RetrievalConfigSettings` (same finite/nonnegative/`<=16.0` discipline as `vector_weight`/`bm25_weight`, but `0.0` alone is a valid opt-out unlike those two) and to `config/config.example.toml`.
- Threaded `graph_weight` through `GenerationRequest` so `main.rs`'s pre-check and the OpenRouter adapter's actual outbound call read the same field — and in doing so, found and fixed a real bug: `openrouter.rs`'s `execute_one_call` was calling `pack_evidence_prompt` (the graph-blind wrapper), meaning Plan 02's `GenerationRequest.graph_facts` never reached the real outbound chat request body at all. Now proven end-to-end via a raw-HTTP-capture test against a real local mock OpenRouter server, run twice (`graph_weight = 1.0` and `graph_weight = 0.0`) against the same fixture.
- Proved all three `graph_augmentation` outcomes ("succeeded", "no_match_found", "attempted_and_failed") observable through the full `query_rag` handler via a real `tracing_subscriber::layer::Layer` capture (not only Plan 02's isolated-function tests), using `#[tokio::test(flavor = "current_thread")]` so the thread-local default subscriber survives every `.await` point — including a genuine forced fault (deleted `entities.lance` on-disk directory) for the `attempted_and_failed` case.

## Decisions Made

- `graph_weight == 0.0` hard-excludes by rebinding the `graph_facts` slice to `&[]` before any normalization runs, not by feeding a weighted score of zero into the existing sort/pack path — the latter would still admit graph facts whenever the token budget is large enough, which is exactly the contradiction REVIEWS.md flagged.
- On an exact score tie between a remaining evidence block and a graph fact (the common case, since a singleton candidate set always min-max-normalizes to `1.0`), the graph fact wins the tie — a deliberate, documented choice that reverses the append-only design's bias toward chunk evidence rather than reproducing it under a new sort key.
- The reserve-one-citable-chunk rule keeps reserving `evidence[0]` (the first element of the caller-supplied slice), not `max_by(score)` — unchanged from Plan 02, since the plan explicitly required this and changing it would undercut Test 4's stable-marker premise.
- `graph_augmentation` observability tests (Task 2) intentionally carry no chunk evidence at all: the tracing span is recorded before dense/bm25 retrieval runs, so every fixture resolves to the pre-existing `NO_EVIDENCE` early-return — sufficient to prove both the tag's presence and that none of the three outcomes changes the response contract (D-32), without needing a heavier hybrid-retrieval fixture.
