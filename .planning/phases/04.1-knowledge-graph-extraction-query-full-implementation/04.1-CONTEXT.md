## Implementation Decisions

**Phase 4 was a spike/PoC that proved the `lance-graph` integration pattern but implemented no extraction, no persistence, and no prompt integration** (verified: `engine/src/graph/{mod.rs,bridge.rs,tests.rs}` contains only traversal/bridge functions against synthetic fixtures, feature-gated behind `graph-spike` and off the default build; `grep -n "graph" engine/src/prompt.rs` — zero matches). All decisions below were captured during Phase 4's discussion (`04-CONTEXT.md`) as the target for this phase and remain sound. They are carried forward in full, now in-scope (no longer `[deferred]`), with corrections/refinements from what the spike actually discovered marked `[R]`.

### Entity & Relationship Extraction
- **D-01:** Entity/relationship extraction runs synchronously during ingestion, blocking document completion — same execution model as the existing embedding-generation step.
- **D-02:** Extraction runs at per-chunk granularity: one LLM structured-extraction call per chunk (matches the GraphRAG "text unit" pattern and preserves `char_start`/`char_end`-level provenance).
- **D-03:** Entity types are open-domain freeform strings assigned by the LLM — no fixed taxonomy/enum.
- **D-04:** `relation_type` is a freeform LLM-assigned string (e.g. `"founded_by"`); `edges.weight` stores an LLM-reported confidence score (0.0–1.0), not a fixed placeholder.
- **D-05:** The existing `ExactMatchResolver` (`EntityResolver` trait, scaffolded in Phase 2, `engine/src/db/mod.rs:277-289`) is wired into extraction to merge duplicate entity mentions by case-normalized exact name match, scoped **globally across the whole corpus** (not per-document). — **Reversibility:** costly — once entities are merged globally, narrowing resolution to per-document later requires re-splitting merged nodes and re-attributing `source_chunk_ids`.
- **D-06:** Extraction failure for a single chunk is non-fatal: the chunk keeps zero entities and the document still reaches `completed` status. Extraction is additive graph enrichment, not a precondition for a document being queryable via existing hybrid retrieval.
- **D-07:** Chunks below a minimum content-length threshold skip the extraction call entirely (exact threshold is implementer discretion).
- **D-08:** Extraction reuses the existing provider-neutral `Generator` trait pattern (OpenRouter, from Phase 3) via a sibling trait (see AI-SPEC.md Section 4's `ExtractionGenerator`) rather than a separate extraction-specific client from scratch.
- **D-09:** Extraction calls for chunks within one document run concurrently in batches, reusing the Phase 2 D-20 pattern (`futures::stream::iter(...).buffer_unordered(5)`, up to 5 concurrent OpenRouter requests) rather than sequentially.

### Graph Node/Edge Schema Resolution
- **D-10:** Extracted entities are stored in a **new dedicated `entities` table**, separate from the existing chunk-level `nodes` table. — **Reversibility:** one-way — merging the tables back later requires redesigning every entities-table consumer (extraction writer, resolver, traversal seed lookup) around a shared polymorphic schema.
- **D-11:** The `entities` table carries `name`, `entity_type`, `name_vector`, `summary` (nullable), `summary_vector` (nullable), `unsummarized_refs` (nullable list), and `community_ids` (nullable list) — these summary/community columns move from `nodes` to `entities`, where they conceptually belong.
- **D-12:** Entities link back to their source chunk(s) via a `source_chunk_ids` list column on the `entities` table (not via implicit `MENTIONED_IN` edges). This column is also this phase's answer to Phase 4's judgment-tier prohibition #1 (entity over-conflation without operator-visible signal) — when `ExactMatchResolver` merges two mentions, `source_chunk_ids` accumulates both, giving traceable provenance without building 999.6's non-destructive `SAME_AS` linking early.
- **D-13:** `edges.source_node_id`/`target_node_id` reference entity IDs only (entity-to-entity relationships). Edges never connect a chunk to an entity.
- **D-14:** The new `entities` table follows the same Phase 2 D-22 fail-fast/no-auto-migrate schema-drift rule — any drift aborts engine startup with a clear error.
- **D-15:** The dormant `community_ids`/`summary`/`summary_vector`/`unsummarized_refs` columns already shipped on the chunk `nodes` table in Phase 2 are **removed** now that `entities` owns that data. — **Reversibility:** one-way — this is itself a drift-inducing schema change against an already-shipped table.
- **D-16:** The `nodes`-table column removal is handled by bumping the schema version and documenting that upgrading past this phase requires deleting the local LanceDB directory and re-ingesting (no in-engine auto-migration) — consistent with D-22's "manual user intervention" clause, not a contradiction of it.
- **[Note]** REQUIREMENTS.md's DATA-06 ("optional `community_ids` array **on nodes**") and DATA-07 ("`summary`/`summary_vector`/`unsummarized_refs` **on the `nodes` table**") use pre-D-11/D-15 wording — those columns land on `entities`, not `nodes`, per D-11/D-15. Treat DATA-06/DATA-07's "on nodes" phrasing as superseded; their underlying port intent (leave schema/trait shapes clean for 999.1/999.4) is still satisfied, just on the corrected table.

### Graph Traversal & Query
- **D-17:** Graph traversal uses the real **`lance-graph` crate** (`lance-graph = "0.5.4"`, `default-features = false`), not a hand-rolled BFS implementation. **Status: CONFIRMED, not just decided** — Phase 4's spike empirically proved the integration pattern (5 passing tests, `04-RESEARCH.md`, `04-AI-SPEC.md` §2 `Status: CONFIRMED`).
- **D-18:** A RAG query seeds graph traversal via **vector search against the `entities.name_vector` column** — not exact substring match, not a second LLM extraction call on the query text.
- **D-19 [R — refined by the spike, not overturned]:** Traversal is expressed as genuine Cypher pattern queries executed via `lance-graph` — **but the spike proved this cannot mean "Cypher replaces all traversal logic."** `lance-graph`'s `CypherQuery::execute()` takes a `HashMap<String, RecordBatch>` with **no predicate pushdown into the lancedb scan** (`04-AI-SPEC.md` Pitfall 2, `04-RESEARCH.md` Pitfall 2 — both confirmed, not theoretical). The actual mechanism is **hybrid**: a hop-capped BFS neighborhood expansion runs first in Rust directly against the `entities`/`edges` lancedb tables (bounded by D-23's hop cap, direction handling per D-24), and only that already-narrowed subgraph is bridged across the arrow-version boundary and pattern-matched by Cypher. This is the proven `engine/src/graph/mod.rs` shape from the spike (`fetch_neighborhood` → `bridge_batch` → `CypherQuery::execute()` → `bridge_batch_back`) — reuse it directly rather than re-deriving it. Say this explicitly in planning; do not present Cypher as doing all traversal work.
- **D-20:** The standalone `QueryGraph` RPC accepts a **structured request** (seed entity name/id, hop depth, optional `relation_type` filter) rather than a raw Cypher query string, even though `lance-graph` could safely parse one — keeps the public contract typed and bounded, matching the `QueryRAG` convention from Phase 3. **Constraint discovered by the spike (Pitfall 6, `04-RESEARCH.md`):** variable-length Cypher patterns (`*1..N`, needed for `QueryGraph`'s caller-specified hop depth) cannot project the relationship variable (`r`) in `RETURN` — only fixed single-hop patterns can. For `QueryGraph`'s variable-hop responses, either (a) return node-only results, or (b) correlate the Cypher result's matched node-ID pairs back against the already-in-scope `edges_batch` (already read from lancedb before bridging, per D-19's pre-narrow step) to recover `relation_type`/`weight` without a second query. Which of (a)/(b) to implement is **Claude's discretion** — (b) is recommended since it preserves the relation-type/weight data D-28's rendering wants without extra round-trips, but either is a legitimate implementation choice.
- **D-21:** `entities.name_vector` is populated by reusing the existing OpenRouter embedding client/model (same one used for chunk embeddings, same `EMBEDDING_DIMENSIONS` constant already in `engine/src/db/mod.rs`), generated when an entity node is created or its canonical name changes via resolution.
- **D-22:** `QueryGraph` accepts only an explicit seed entity name/id — no natural-language query text embedded server-side (that seeding logic lives in the main `/rag/query` path per D-18, keeping the two RPCs' responsibilities distinct).
- **D-23:** Both `QueryGraph` and the auto-triggered RAG augmentation enforce a **configurable maximum hop cap** (default 3, matching the spike's `MAX_HOP_CAP` already implemented in `engine/src/graph/mod.rs`'s `clamp_hop_cap`) bounding caller-controllable traversal cost, consistent with existing bounded-input patterns (Phase 3 D-55/D-56). The spike's `clamp_hop_cap` (rejects 0 and values over the max, `u32`-typed so no negative/non-numeric value can reach the Cypher `format!` call) is reusable as-is — this closed threat T-04-01-01 in Phase 4's security register and should be carried forward unchanged, not rebuilt.
- **D-24:** The always-on RAG-path traversal follows edges in **both directions** from a seed entity (entity as source OR target), not outgoing-only — otherwise relationships where the seed is the edge's target would be silently missed. (Expressible as an undirected Cypher pattern `-[r]-`, per `04-RESEARCH.md` A3 — already how the spike's example queries are written.)
- **D-25:** `QueryGraph` remains **gRPC-only/internal** for this phase — the Go gateway does not add an HTTP wrapper (e.g. `POST /graph/query`) for it.

### RAG Prompt Integration (ContextAssemblyStrategy)
- **D-26:** Every `/rag/query` call automatically attempts entity seed-matching; graph context is added to the prompt only when matches are found. No new opt-in request flag is added to the Phase 3 `QueryRAG` contract.
- **D-27:** Graph context appears in the compiled prompt as a **separate "Related Entities & Relationships" section**, distinct from the numbered chunk-evidence citations (`[1]`, `[2]`). Graph facts are **not** citable `EvidenceBlock`-like entries in v1 — this keeps Phase 3's citation-marker/validation contract untouched. This is also this phase's answer to Phase 4's judgment-tier prohibition #3 (graph-fact/citation-grounded-evidence indistinguishability) — the separate, non-citable section structurally prevents conflation.
- **D-28:** Per the `ContextAssemblyStrategy`'s `PrecomputedSemantics`/`SourceChunks` distinction (999.5 D-02/D-03): since entity/edge `summary` columns are null in v1, "falling back to source chunks" concretely means rendering the **raw entity name + relation triple text** (e.g. `"A —founded_by→ B"`), not re-fetching the original source chunk text via `source_chunk_ids`.
- **D-29:** Graph context and chunk evidence **share a single evidence token budget** (Phase 3 D-39) rather than separate reserved allocations, and are **interleaved by relevance score** across both sources rather than packed chunk-evidence-first.
- **D-30:** Interleaving uses a configurable `graph_weight` multiplier (default **1.0**, equal footing with chunk evidence) applied to normalized graph-match scores before merging with normalized RRF-fused chunk scores — mirrors the Phase 3 pattern of defaulting RRF's vector/BM25 weights to 1.0 each with config overrides.
- **D-31:** The always-on RAG-path graph augmentation defaults to **1-hop** traversal (distinct from the caller-specified hop depth on the standalone `QueryGraph` RPC), bounding latency/prompt-size impact on every query. This is the case Pitfall 6 does NOT affect — fixed single-hop patterns can project relationship properties directly (`04-RESEARCH.md`'s "Fixed single-hop projecting relationship properties" example, already proven), so D-31's path needs no correlate-back workaround.
- **D-32:** If entity seed-matching or the `lance-graph` traversal fails/errors at query time, the query **silently continues with chunk-only evidence** rather than failing the whole request — graph augmentation is additive/optional and must not make the already-shipped Phase 3 hybrid-retrieval path fragile to a new dependency.

### Extracted Content Handling (new for this phase — Phase 4's prohibition #2)
- **D-33 (this discussion):** Extracted entity/relation text is persisted **as-is, with no redaction/PII-scrubbing system** — this is a deliberate, documented risk acceptance, not an oversight. Rationale: Lancet is a local-first, single-user demo project (PROJECT.md — no multi-tenancy, no production users), and PROJECT.md's "scope discipline" constraint explicitly favors avoiding this kind of speculative hardening. **Carry-forward action:** extend Phase 4's `AR-04-01` accepted-risk entry (`04-SECURITY.md`) into this phase's threat register, now scoped against the real `entities`/`edges` tables instead of synthetic fixtures — this closes Phase 4's `T-04-01-02` "revisit when Phase 04.1 wires this against real tables" note. Error/log messages must still keep row values out (matching the already-shipped `GraphSpikeError::Display` pattern, which only carries codec error text) — that constraint is unaffected by this decision.

### Carried-Forward Code Debt (must address, not optional polish)
- **WR-01 (from `04-REVIEW.md`, must-fix — not "nice to have"):** `bridge_batch`/`bridge_batch_back` (`engine/src/graph/bridge.rs:28-35,60-67`) silently discard IPC-decoded batches beyond the first. This was low-risk against the spike's single-batch synthetic fixtures; it is **not** low-risk once this phase wires the bridge against real `entities`/`edges` lancedb reads, which may legitimately split across multiple IPC stream messages depending on the writer's internal batching (e.g. dictionary-encoded columns). Fix per the review's suggestion: either assert single-batch-ness explicitly (return an error if a second batch exists) or concatenate all yielded batches. Silent data loss on a real graph read is a correctness bug, not a style nit.
- **IN-01–IN-04 (`04-REVIEW.md`, non-blocking maintainability):** duplicated `GraphConfigBuilder`/dataset-map boilerplate across traversal functions, near-duplicate bridge functions, unnecessarily-public `bridge` module, `GraphSpikeError::Display` dropping the `kind` field. Worth cleaning up while this phase is already touching this code, but not blocking.

### Locked Implications (forced by this phase's scope, not decisions to revisit)
- The `graph-spike`-gated code (`engine/src/graph/{mod.rs,bridge.rs,tests.rs}`) **must be promoted into the default build** — DATA-05 requires graph traversal in the live `/rag/query` path, which cannot stay behind an opt-in feature flag. Budget for the consequence: Phase 4's research (`04-RESEARCH.md` Pitfall 5, `04-SECURITY.md` T-04-01-03) found `default-features = false` does **not** eliminate `lance-graph`'s transitive cloud-SDK/geospatial/full-text-search footprint (~350+ additional crates, ~3 min cold build on the research session's hardware) — that weight lands in the default build once promoted, not just CI-time-gated as it was in Phase 4.
