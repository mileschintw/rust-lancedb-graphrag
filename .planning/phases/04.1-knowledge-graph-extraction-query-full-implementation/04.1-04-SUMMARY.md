## Accomplishments

- Replaced the `{"status":"scaffolding"}` stub `query_graph()` handler with a real implementation: validates input, resolves the seed entity (UUID or case-folded name lookup), clamps `hop_depth`, calls `fetch_neighborhood` then `narrow_via_cypher`, applies an optional `relation_type_filter`, and builds a structured `QueryGraphResponse`.
- Fixed two real behavior bugs left over from the prior session's in-progress work: `hop_depth = 0` was silently defaulted to `1` instead of rejected, and `QueryGraphResponse.nodes` was built from the full unfiltered entity set even when `relation_type_filter` narrowed `.edges` — both now match the plan's locked contract.
- Discovered and fixed a genuine pre-existing bug in `fetch_neighborhood` (Plan 02 code, in this task's file scope): bidirectional per-hop BFS re-fetches an edge already accumulated at a prior hop once its *other* endpoint enters a later frontier (e.g. `seed --knows--> Bob` gets re-matched at hop 2 once `Bob` is itself queried), double-counting the edge in the response. Added `dedup_edges_by_identity` to `fetch_neighborhood`'s final edge-batch construction.
- Implemented case-folded, full-table-scan `seed_entity_name` lookup matching this codebase's existing D-05 write-time merge convention (`.trim().to_lowercase()`, mirrored from `extract_and_persist_entities`), replacing the prior session's raw unescaped-equality single-row lookup. Zero matches now returns `Status::not_found` (previously returned `Ok` with an empty response).
- Added `[engine.graph]` to `config/config.example.toml` and wired `engine.graph.seed_match_min_score`/`engine.graph.max_hop_cap` into `REQUIRED_EFFECTIVE_RAG_KEYS`/`REQUIRED_EFFECTIVE_RAG_ANNOTATIONS` and the `config_example_matches_effective_rag_contract` section matcher.
- Wrote all 10 plan-required named tests (2 pre-existing `clamp_hop_cap_with_ceiling` unit tests were already correct from the prior session; added/renamed/split the remaining 9 `query_graph_*` handler tests), including two new real-graph fixtures (`seed_two_hop_graph`, `seed_single_edge_graph`) built via `extract_and_persist_entities` to prove multi-hop relation recovery and relation-type filtering against actual persisted data, not synthetic RecordBatches.

## Decisions Made

- Case-folding for `seed_entity_name` lookup uses `.trim().to_lowercase()` (this codebase's actual D-05 write-time merge convention, per `extract_and_persist_entities` lines ~2437/2488) rather than the `unicode_casefold` crate the plan's prose mentioned — using the same fold function at read time as write time is what actually guarantees a lookup finds what the merge step folded together; introducing a second, subtly different Unicode-casefold definition at read time would risk read/write fold divergence on non-ASCII names.
- A `seed_entity_name` with zero case-folded matches now returns `Status::not_found` rather than `Ok` with an empty response. This was necessary to make Test 8 (`query_graph_rejects_oversized_seed_entity_name`) actually prove that the length check runs *before* the lookup rather than merely coinciding with a lookup failure — the plan's Test 8 spec explicitly requires this distinguishing behavior.
- Fixed `fetch_neighborhood`'s edge-duplication bug (bidirectional per-hop BFS) rather than working around it in the response builder, since `engine/src/graph/mod.rs` is in this task's file scope and the duplication would otherwise produce an incorrect (padded) edge count in every multi-hop bidirectional response, not just this task's own new code paths.

**4. [Rule 1 - Bug] Fixed `fetch_neighborhood` double-counting an edge across hops (bidirectional BFS)**
- **Found during:** Task 2's own new test, `query_graph_recovers_multi_hop_edge_relation_properties`, which failed with 3 edges returned instead of 2 (the seed's first-hop edge appeared twice).
- **Issue:** At each BFS hop, the edge query predicate is `source_node_id IN (frontier) OR target_node_id IN (frontier)`. When a node enters the frontier at hop N, this re-matches every edge touching that node — including an edge already accumulated at hop N-1, if the node was that edge's *other* endpoint.
- **Fix:** Added `dedup_edges_by_identity`, applied to the final concatenated edge batch, keying on `(source_node_id, target_node_id, relation_type, weight)` — distinct edges persisted from separate extractions would differ in at least `weight` even with a coincidentally-identical source/target/relation_type triple, so this identity does not risk collapsing genuinely distinct edges.
- **Files modified:** `engine/src/graph/mod.rs`
- **Verification:** `query_graph_recovers_multi_hop_edge_relation_properties` passes with exactly 2 edges.
- **Committed in:** `b34016f`
