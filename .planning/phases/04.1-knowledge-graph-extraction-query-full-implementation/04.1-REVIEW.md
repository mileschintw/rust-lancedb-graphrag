## Narrative Findings (AI reviewer)

### Critical Issues

#### CR-01: `fetch_neighborhood` counts duplicate edges before dedup, over-rejecting valid neighborhoods against `MAX_TOTAL_EDGES`

**File:** `engine/src/graph/mod.rs:356-367` (count) and `:463-474` (dedup)

**Issue:** `fetch_neighborhood`'s per-hop loop accumulates `hop_rows` and compares `total_edge_count + hop_rows` against `MAX_TOTAL_EDGES` (500) *before* any deduplication:

```rust
let hop_rows: usize = edge_batches.iter().map(|b| b.num_rows()).sum();
if total_edge_count + hop_rows > MAX_TOTAL_EDGES {
    return Err(GraphSpikeError::new(..., "accumulated edge count {} exceeds MAX_TOTAL_EDGES {}", ...));
}
total_edge_count += hop_rows;
```

The function's own doc comment on `dedup_edges_by_identity` (lines 468-472) documents that, under `bidirectional=true` (the only mode ever passed from `main.rs`, at both call sites), the same edge is legitimately re-fetched across hops once its other endpoint enters a later frontier — and dedup is applied only once, after the loop, on the final concatenated batch. This means a neighborhood whose *distinct* edge count is comfortably under 500 can still trip the per-hop pre-dedup counter and fail the whole request with `GraphSpikeErrorKind::Bridge`, purely because the same edges were counted more than once across hops. This is a false-positive rejection of a request that is actually within the documented safety bound — a correctness bug in the bounding logic this function exists to implement, not a cosmetic issue.

Both `query_graph` (main.rs:1841) and `attempt_graph_augmentation` (main.rs:1146, via `query_rag`) call `fetch_neighborhood(..., bidirectional=true)`, so both the explicit graph RPC and the automatic RAG graph-augmentation path are exposed to this over-rejection.

**Fix:** Track `total_edge_count` against distinct `edge_id`s (e.g. accumulate into a running `HashSet<String>` of seen edge IDs, or dedup per-hop before adding to the running total) instead of raw per-hop row counts:

```rust
let mut seen_edge_ids: HashSet<String> = HashSet::new();
for batch in &edge_batches {
    if let Some(id_col) = batch.column_by_name("edge_id").and_then(|c| c.as_any().downcast_ref::<StringArray>()) {
        for i in 0..batch.num_rows() {
            if !id_col.is_null(i) {
                seen_edge_ids.insert(id_col.value(i).to_string());
            }
        }
    }
}
if seen_edge_ids.len() > MAX_TOTAL_EDGES {
    return Err(...);
}
total_edge_count = seen_edge_ids.len();
```

### Warnings

#### WR-01: `attempt_graph_augmentation` ignores the configured `graph.max_hop_cap`, always fetching a 1-hop neighborhood

**File:** `engine/src/main.rs:1146,1156` (hardcoded `1`), contrasted with `:1835` (`query_graph` correctly using `self.effective_settings.graph.max_hop_cap`)

**Issue:** `attempt_graph_augmentation` receives `settings: &GraphSettings` (which carries both `seed_match_min_score` and `max_hop_cap`) but only ever reads `settings.seed_match_min_score`:

```rust
let (entities_batch, edges_batch) =
    match graph::fetch_neighborhood(database, &matched_entity_id, 1, true).await { ... };
let (entities_batch, edges_batch) =
    graph::narrow_via_cypher(&entities_batch, &edges_batch, &matched_entity_id, 1).await;
```

Both hop-depth arguments are hardcoded to `1` and never derived from `settings.max_hop_cap`. An operator who configures `engine.graph.max_hop_cap = 3` (as `config.example.toml` demonstrates) gets that ceiling honored for the explicit `QueryGraph` RPC but silently gets a fixed 1-hop neighborhood for automatic graph augmentation inside `QueryRag` — the path most callers exercise by default. There is no comment anywhere in `attempt_graph_augmentation` documenting this as an intentional MVP scope limit, so it reads as configuration being silently ignored on one of its two call sites.

**Fix:** Either thread `settings.max_hop_cap` (via `graph::clamp_hop_cap_with_ceiling`) into both `fetch_neighborhood` and `narrow_via_cypher` calls, or, if a fixed 1-hop augmentation is intentional, document it explicitly in `attempt_graph_augmentation`'s doc comment and stop passing the unused field through `GraphSettings` to this call site.

#### WR-02: Entity update is a non-atomic delete-then-add with a real, awaited, per-entity visibility gap

**File:** `engine/src/main.rs:2696-2776`

**Issue:** In `extract_and_persist_entities`'s mutation phase, updated (pre-existing) entities are deleted one at a time in a sequentially-awaited loop, and only re-inserted (together with newly-created entities) in a single batch `add` afterward:

```rust
for entity in &updated_entities {
    let ent_pred = format!("entity_id = '{}'", escape_sql_literal(&entity.entity_id));
    entities_table.delete(&ent_pred).await...;
}
// ... entities re-added afterward, batched, in a single `add`
```

Between the first `delete` and the final `add`, every already-deleted updated entity is absent from `entities_table`. Because deletes are awaited one-by-one, this window scales with the number of updated entities in the document, not with a single round trip. Ingestion is serialized through the single worker task (confirmed: `spawn_worker` spawns exactly one `tokio::spawn` loop), but readers are not serialized against the worker — `query_rag` (via `attempt_graph_augmentation`) and `query_graph` run concurrently on the gRPC server and can observe a matched seed entity's neighborhood as transiently missing rows mid-ingestion of an unrelated (or the same) document's re-extraction.

**Fix:** Batch the deletes into a single `entity_id IN (...)` predicate (mirroring the pattern already used for `entity_edges_table.delete(&edge_pred)`) to shrink the window to one round trip, or restructure as insert-new-then-delete-old-by-superseded-id to avoid a window where the row is absent entirely.

#### WR-03: `query_graph`'s post-narrowing Arrow filters silently fall back to unfiltered data on failure, with no error or log

**File:** `engine/src/main.rs:1864-1865` and `:1911-1912`

**Issue:** Both `relation_type_filter` application and the corresponding node-endpoint narrowing swallow `filter_record_batch` errors and substitute the *pre-filter* batch:

```rust
arrow_select::filter::filter_record_batch(&edges_batch, &mask)
    .unwrap_or(edges_batch)
...
arrow_select::filter::filter_record_batch(&entities_batch, &node_mask)
    .unwrap_or_else(|_| entities_batch.clone())
```

If either filter call fails (e.g. a future schema change introduces a mask/batch length mismatch), the RPC returns the *unfiltered* edges/nodes to a caller who explicitly requested `relation_type_filter` — silently violating the documented nodes/edges-consistency invariant this function's own comments describe, and without any `tracing::warn!` to make the failure observable (unlike the `narrow_via_cypher` fail-open path a few lines above, which does log via `tracing::warn!`).

**Fix:** At minimum, log via `tracing::warn!` on the `Err` branch so silent fallback is observable in production; consider returning `Status::internal` instead of fabricating a response that doesn't match what the caller asked for.

#### WR-04: `narrow_via_cypher_fails_open_on_genuine_cypher_error` test does not exercise a genuine Cypher execution failure

**File:** `engine/src/graph/tests.rs:493-499`

**Issue:** The test passes `hop_cap = 0`:

```rust
async fn narrow_via_cypher_fails_open_on_genuine_cypher_error() {
    let (entities, edges) = three_entity_two_edge_fixture();
    let (out_entities, out_edges) = super::narrow_via_cypher(&entities, &edges, "abc-123", 0).await;
    ...
}
```

`hop_cap = 0` is rejected by `clamp_hop_cap` inside `traverse_multi_hop` *before* any Cypher query is built or executed, producing `GraphSpikeErrorKind::InvalidHopCap` — not `CypherParse` or `CypherExecute`. The test's assertions (full unconstrained fallback) do pass, but only because `narrow_via_cypher`'s fail-open `match` arm treats every `GraphSpikeError` kind identically, so the test is exercising the input-validation fail-open path while its name and framing claim to cover "genuine Cypher error" fail-open behavior. A regression that broke fail-open specifically for `CypherExecute`/`CypherParse` failures (e.g. a real lance-graph runtime error) would not be caught by any test in this file.

**Fix:** Add or repoint the test to force an actual `CypherExecute`/`CypherParse` failure (e.g. malformed/mismatched schema fixture that reaches query execution before failing) and assert on `err.kind` inside a direct `cypher_confirmed_neighbor_ids`/`traverse_multi_hop` call, or rename/re-scope the existing test to reflect that it only covers the `InvalidHopCap` fail-open case.

### Info

#### IN-01: `IngestionJob::new` silently substitutes default chunk settings on invalid metadata

**File:** `engine/src/main.rs:613-628`

**Issue:** `IngestionJob::new` swallows `parse_chunk_settings` errors: `parse_chunk_settings(&metadata).unwrap_or_default()`. Any invalid `chunk_strategy`/`chunk_size`/`chunk_overlap` metadata silently becomes `structure-aware`/500/50 with no signal to the caller. Currently this constructor is only called from `engine/src/tests.rs` (grep-confirmed) — the production gRPC ingestion path constructs `IngestionJob` via a struct literal with `.expect(...)` on already-validated settings, and `read_staged_jobs` also builds it via struct literal. So this is not reachable from a production code path today, but it is a public-shaped constructor on a production type with silent-failure semantics that would surprise a future caller.

**Fix:** Either remove `IngestionJob::new` if it is test-only scaffolding (move the equivalent helper into `tests.rs`), or have it return `Result<Self, Status>` like `parse_chunk_settings` does, rather than defaulting silently.

#### IN-02: Duplicate SQL single-quote escaping helpers

**File:** `engine/src/main.rs:1997-1999` (`sql_string`) and `engine/src/graph/mod.rs:289-291` (`escape_sql_literal`)

**Issue:** Both functions are byte-for-byte identical (`value.replace('\'', "''")`), maintained independently in two modules.

**Fix:** Consolidate into one shared helper (e.g. re-export `graph::escape_sql_literal` for use in `main.rs`, which already imports it for one call site at line 26/2684).

#### IN-03: `communities` table is created and schema-validated but has no accessor and no callers

**File:** `engine/src/db/mod.rs:258-267,296-306`

**Issue:** `communities_schema()` is registered in `table_schemas()` (so `initialize_tables`/`open_and_validate` create/validate it) but `DatabaseManager` has no `communities_table()` accessor, and nothing in the reviewed files reads or writes it. This is presumably scaffolding for a future community-detection/summarization phase; flagging so it's visible as intentionally-unused rather than accidentally-orphaned.

**Fix:** No action required if intentional forward scaffolding; otherwise remove until the consuming phase lands.

#### IN-04: Duplicated `RetrievalSnapshot` construction in `query_rag`'s no-evidence and success paths

**File:** `engine/src/main.rs:1509-1531` and `:1669-1694`

**Issue:** The no-evidence early-return branch and the success branch each independently construct a `lancet::v1::RetrievalSnapshot` with the same seven fields (`index_generation`, `embedding_model`, `vector_weight`, `bm25_weight`, `rrf_k` via `snapshot_rrf_k`, `candidate_limit`/`final_limit` via `snapshot_limit`, `active_filter`), differing only in `result_hash` (constant-over-empty-input in the early branch vs. hashing `final_candidates` chunk IDs in the success branch — these two computations are equivalent when candidates are empty, so this is not a correctness bug, just duplicated construction logic).

**Fix:** Factor the seven shared fields into a small helper (`fn base_snapshot(&self, query_request: &QueryRequest) -> Result<RetrievalSnapshotBuilder, Status>`) that both branches call, passing only the `result_hash` in.

#### IN-05: `seed_rag_fixture.rs`'s `lancedb_path()` uses a `while let` loop that can never iterate more than once

**File:** `engine/src/bin/seed_rag_fixture.rs:49-61`

**Issue:** The loop body unconditionally `return`s on every branch (either the matched `--lancedb-path` case or the `else` "unknown argument" case), so it is not actually a loop — it only ever inspects the first CLI argument. Functionally harmless for this single-flag dev fixture tool, but the `while let` framing implies argument-order flexibility that doesn't exist.

**Fix:** Rewrite as `if let Some(arg) = args.next() { ... } else { Err(usage) }` to match actual behavior, or genuinely support scanning past unrelated arguments if that's the intent.
