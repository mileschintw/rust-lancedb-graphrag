# Phase 04.1: Code Review Report

**Reviewed:** 2026-08-07T00:00:00Z
**Depth:** standard
**Files Reviewed:** 24
**Status:** issues_found

## Summary

This phase adds the `QueryGraph` RPC (Cypher-constrained induced-neighborhood query), the bounded BFS neighborhood fetch (`fetch_neighborhood`), the lance-graph Arrow IPC bridge, and the entity/relationship extraction pipeline. The core traversal logic (hop clamping, SQL-literal escaping, byte-ceiling input validation) is careful and well-documented. However, the edge-deduplication step in `fetch_neighborhood` uses an identity key that omits the one column (`edge_id`) that would make it correct, which can silently drop real edges persisted from separate documents. Several smaller correctness/robustness gaps and one API-consistency gap around seed-entity resolution round out the findings below.

## Critical Issues

### CR-01: Edge deduplication can silently drop distinct edges from different documents

**File:** `engine/src/graph/mod.rs:345-358, 477-521`
**Issue:**

`fetch_neighborhood` projects only `source_node_id, target_node_id, relation_type, weight` from `entity_edges_table()` (the `select` call at lines 353-358 deliberately excludes `edge_id`, even though `entity_edges_schema()` in `engine/src/db/mod.rs` defines `edge_id` as the table's non-nullable primary identifier).

`dedup_edges_by_identity` (lines 485-521) then treats the 4-tuple `(source_node_id, target_node_id, relation_type, weight)` as the edge's identity, and its doc comment (lines 477-484) justifies this by asserting:

> "distinct edges persisted from separate extractions would differ in at least `weight` (each relation's `weight` is its own extraction's confidence) even when `source_node_id`/`target_node_id`/`relation_type` coincide."

This assumption does not hold. In `extract_and_persist_entities` (`engine/src/main.rs`, ~line 2659-2666), each edge's `weight` is set directly from `rel.confidence`, the LLM's raw extraction confidence for that relation. Two different documents that each extract the same fact (e.g., "Alice knows Bob") through the same model/temperature (the generation config defaults `temperature: 0.0`, see `config/config.example.toml`) will very plausibly produce identical confidence values, giving two genuinely distinct edges (different `edge_id`, different `document_id`) an identical 4-tuple identity. `dedup_edges_by_identity` will then discard one of them as if it were a re-fetched duplicate from the bidirectional BFS re-traversal it is meant to guard against.

The dedup is legitimate in intent (collapsing an edge re-observed via the bidirectional frontier query across hops), but the identity it uses is not sufficient to distinguish "same edge, seen twice" from "two different edges that happen to look alike." The correct de-duplication key is `edge_id`, which is unique by construction (`Uuid::new_v4()` at edge-creation time) but is never selected into the batch this function operates on.

**Fix:**
Select `edge_id` alongside the other columns in `fetch_neighborhood`'s two `.select(...)` calls, add it to the local `edges_schema` built at lines 447-452, and change `dedup_edges_by_identity` to key on `edge_id` alone (or `edge_id` plus the existing tuple, for defense in depth) instead of `(source_node_id, target_node_id, relation_type, weight)`:

```rust
// in fetch_neighborhood's edges select:
.select(lancedb::query::Select::columns(&[
    "edge_id", "source_node_id", "target_node_id", "relation_type", "weight",
]))

// edges_schema gains a leading edge_id field, and dedup_edges_by_identity
// keys its `seen` set on edge_col.value(i).to_string() instead of the 4-tuple.
```

## Warnings

### WR-01: `visited` entity set has no upper bound on the final hop, feeding an unbounded SQL predicate

**File:** `engine/src/graph/mod.rs:322-413`
**Issue:** `MAX_FRONTIER_SIZE` is checked only at the *top* of each loop iteration (line 323), before that hop's query runs — i.e., it validates the *previous* hop's `next_frontier` before using it to query the *current* hop. The `next_frontier` computed on the loop's *final* iteration (`_hop == hop_cap`) is folded into `visited` (line 407) and never checked against `MAX_FRONTIER_SIZE`, because there is no subsequent iteration to perform that check. A single hub entity with many edges can therefore make the final hop's `next_frontier` — and thus the cumulative `visited` set — arbitrarily large. `visited` is exactly what builds the `entity_id IN (...)` predicate at lines 415-420, so the final entities query can carry an unbounded number of quoted UUIDs in a single SQL string, unlike `MAX_TOTAL_EDGES`, which is enforced unconditionally on every hop (lines 366-377) and is therefore genuinely bounded.
**Fix:** Apply the `MAX_FRONTIER_SIZE` check to `next_frontier` immediately after it is computed (end of each loop body), not just at the top of the next iteration, so it also covers the last hop before `visited` is extended.

### WR-02: Hand-rolled Arrow schema for BFS results is not derived from the actual query result

**File:** `engine/src/graph/mod.rs:441-459`
**Issue:** `entities_schema`/`edges_schema` inside `fetch_neighborhood` are built by hand to match the expected shape of the `.select(...)` projection, then passed to `concat_batches` against the batches actually returned by LanceDB. This works today because the projected column order and nullability happen to match the source table schemas, but nothing enforces that invariant — if a future schema change to `entities_schema()`/`entity_edges_schema()` in `db/mod.rs` (e.g., changing `entity_type` to nullable) is not mirrored here, `concat_batches` will fail with a schema-mismatch error, and only on the multi-batch path (i.e., when a hop's query result spans more than one `RecordBatch`), which the current fixture-sized unit tests won't exercise.
**Fix:** Derive the local schema from the actual table schema (`entities_table.schema().await?.project(&["entity_id","name","entity_type"])` or equivalent) rather than reconstructing it by hand, so schema drift is caught at the source rather than silently diverging.

### WR-03: `seed_entity_id` UUID validation in `QueryGraph` does not enforce v4/RFC4122, unlike other UUID inputs

**File:** `engine/src/main.rs:1751-1757`
**Issue:** `validate_document_id` (line 1035) and the `QueryRAG` `session_id` validation (lines 1357-1364) both check `get_version_num() != 4 || get_variant() != uuid::Variant::RFC4122` after `Uuid::parse_str`. The `QueryGraph` handler's `seed_entity_id` path only calls `Uuid::parse_str(&seed_entity_id)` and accepts any valid UUID variant/version. Since all entity IDs are generated via `Uuid::new_v4()` at write time, a non-v4 UUID will simply never match a row — this is not exploitable — but it is an inconsistent validation contract across otherwise-parallel code paths in the same file, and a caller supplying a v1/v5/nil UUID gets accepted input where the equivalent `document_id`/`session_id` fields would reject it.
**Fix:** Reuse the same version/variant check used by `validate_document_id` for `seed_entity_id`.

### WR-04: Asymmetric not-found behavior between name-based and ID-based seed resolution

**File:** `engine/src/main.rs:1758-1828`, confirmed by `engine/src/tests.rs:5280-5316`
**Issue:** When `seed_entity_name` does not match any entity, the handler returns `Status::not_found` (lines 1806-1809). When `seed_entity_id` is a syntactically valid UUID that does not correspond to any stored entity, `fetch_neighborhood` tolerates the nonexistent seed and the handler returns `Ok` with an empty `QueryGraphResponse { nodes: [], edges: [] }`. This is explicitly acknowledged by the doc comment on `query_graph_rejects_out_of_range_hop_depth` in `engine/src/tests.rs` ("fetch_neighborhood tolerates a nonexistent seed"), but no test asserts the ID-based "not found" case actually returns `not_found`, and no test documents this asymmetry as an accepted contract — it reads as an oversight rather than an intentional design choice.
**Fix:** Either make both resolution paths return `Status::not_found` for an unresolvable seed, or document (and test) the asymmetry as intentional if the empty-response behavior is deliberate for the ID path.

### WR-05: Cypher fail-open outcome is not observable to `QueryGraph` callers

**File:** `engine/src/graph/mod.rs:616-641` (`narrow_via_cypher`), `engine/src/main.rs:1845-1847`
**Issue:** `narrow_via_cypher` silently falls back to the unconstrained BFS-fetched neighborhood whenever Cypher confirmation fails or returns zero matches (logging only via `tracing::warn!`). `QueryGraphResponse` (see `proto/lancet/v1/lancet.proto:133-136`) carries no notice/warning field (unlike `QueryRAGResponse`, which has `notices`), so a caller of `QueryGraph` has no way to distinguish "this neighborhood was Cypher-verified" from "Cypher failed internally and you received the raw BFS candidate set instead." This is purely an observability gap in the current contract, not a functional bug.
**Fix:** No proto change is proposed here (out of this review's scope), but this gap should be tracked — e.g., surface the fallback via server-side logging/metrics that ops can alert on, since the API itself cannot express it today.

## Info

### IN-01: Name-based seed lookup performs a full unbounded scan of the `entities` table

**File:** `engine/src/main.rs:1767-1804`
**Issue:** Every `QueryGraph` call using `seed_entity_name` reads the entire `entities` table (`entity_id`, `name`) into memory and does an in-process case-folded linear scan, since there is no secondary index on `entities.name`. This is explicitly documented as an accepted trade-off in the surrounding comment and is a performance concern (out of this review's v1 scope), not a correctness one — noted here for visibility only.
**Fix:** None required for this review; consider a name index if corpus size grows significantly.
