## Summary

This is a refresh review following gap-closure plan `04.1-09`, which claims to fix `04.1-REVIEW.md`'s CR-01 (`fetch_neighborhood`'s `MAX_TOTAL_EDGES` bound double-counting bidirectionally re-matched edges) and WR-04 (a misleadingly-named test). The actual code change was verified directly against `git show 9dc9ad2` rather than trusted from `04.1-09-SUMMARY.md`: the diff touches exactly `engine/src/graph/mod.rs` (22 lines), `engine/src/graph/tests.rs` (9 lines, a rename + doc comment), and `engine/src/tests.rs` (90 lines, one new test) — nothing else in this phase's file set changed since the prior review.

**CR-01 (fixed, verified):** `fetch_neighborhood` now accumulates a running `HashSet<String>` of `edge_id` values across hops (`seen_edge_ids`) and checks `seen_edge_ids.len() > MAX_TOTAL_EDGES`, replacing the old raw per-hop-row-sum accumulator. I independently traced the arithmetic of the new regression test (`fetch_neighborhood_accepts_in_bounds_neighborhood_despite_raw_recount_exceeding_max_total_edges`, `engine/src/tests.rs:6604`): hop 1 contributes 1 row/1 distinct id; hop 2 re-matches hop 1's edge (bidirectional predicate) plus 1 new edge, raw cumulative 3 / distinct cumulative 2; hop 3 re-matches hop 2's edge plus 497 new edges converging on one shared leaf entity, raw cumulative 501 (which would wrongly exceed `MAX_TOTAL_EDGES=500` under the pre-fix counting) / distinct cumulative 499 (which correctly stays under it). This is a real, non-tautological proof: it uses a real `DatabaseManager`, real LanceDB-backed Arrow batches, `hop_cap=3` (satisfying the `>=2` bidirectional re-match requirement), and asserts both `Ok` and an exact 499-row/499-distinct-id result. The two pre-existing bound-rejection tests (`fetch_neighborhood_rejects_oversized_edge_batch`, `fetch_neighborhood_rejects_oversized_final_hop_frontier`) are unaffected by the change, confirmed by re-deriving their arithmetic against the new counting logic. The new counting loop also fails closed (`Err(GraphSpikeErrorKind::Bridge)`) if a hop's `edge_id` column is missing or the wrong Arrow type, mirroring `dedup_edges_by_identity`'s existing pattern — this is correct and intentional.

**WR-04 (fixed, verified):** the test formerly named `narrow_via_cypher_fails_open_on_genuine_cypher_error` is renamed to `narrow_via_cypher_fails_open_on_invalid_hop_cap` (`engine/src/graph/tests.rs:501`) with a new doc comment that accurately states it exercises the `InvalidHopCap` fail-open path only, and explicitly documents that genuine `CypherParse`/`CypherExecute` fail-open remains an untested residual gap. Body and assertions are unchanged and still pass the described scenario.

**One new finding surfaced by this pass (WR-01 below):** the fix introduces an inconsistency immediately adjacent to itself. The new counting loop fails *closed* on a missing/malformed `edge_id` column; the pre-existing frontier-computation loop three lines later fails *open* on the exact same failure class for `source_node_id`/`target_node_id`, silently truncating the traversal instead of erroring. This was not flagged by the prior review (that review's CR-01 concerned only the counting arithmetic, not this column-read robustness gap) and is reported fresh here.

**Carried forward, independently re-verified against current code (not re-discovered, but confirmed still accurate):** `04.1-09-PLAN.md`'s "Review Findings Disposition" section explicitly defers WR-01, WR-02, WR-03, and IN-01 through IN-05 from the prior `04.1-REVIEW.md`. They are listed below (renumbered for this review) with the prior review's ID noted for traceability, not presented as new discoveries.

## Narrative Findings (AI reviewer)

### Warnings

#### WR-01: `fetch_neighborhood`'s frontier-computation loop fails open on the same missing/malformed-column failure the new counting loop (this plan's own fix) fails closed on

**File:** `engine/src/graph/mod.rs:377-402` (frontier loop), contrasted with `:356-364` (the new counting loop three lines earlier)

**Issue:** The counting loop `04.1-09` just introduced correctly fails closed if a hop's `edge_id` column is missing or the wrong Arrow type:

```rust
let edge_id_col = batch
    .column_by_name("edge_id")
    .and_then(|c| c.as_any().downcast_ref::<arrow_array::StringArray>())
    .ok_or_else(|| GraphSpikeError::new(GraphSpikeErrorKind::Bridge, "missing edge_id column"))?;
```

Immediately after, the pre-existing frontier-computation loop reads `source_node_id`/`target_node_id` from the same per-hop batches, but silently skips a batch if either column is absent or fails to downcast, instead of erroring:

```rust
let src_col = batch.column_by_name("source_node_id").and_then(|c| c.as_any().downcast_ref::<arrow_array::StringArray>());
let tgt_col = batch.column_by_name("target_node_id").and_then(|c| c.as_any().downcast_ref::<arrow_array::StringArray>());
if let (Some(src_col), Some(tgt_col)) = (src_col, tgt_col) {
    // only path that populates next_frontier
}
```

If every batch in a hop hits this (e.g. a future `select()` projection change, or schema drift on `entity_edges_table()` that the `edge_id` fail-closed path would have caught first at some other hop), `next_frontier` stays empty for that hop. `frontier.is_empty()` is then true, the traversal loop `break`s, and `fetch_neighborhood` returns `Ok` with a **silently truncated** neighborhood — directly contradicting the function's own doc comment ("Enforces `MAX_FRONTIER_SIZE` and `MAX_TOTAL_EDGES` bounds ..., returning a `GraphSpikeError` if exceeded rather than silently truncating"). `query_graph` would serve this truncated result to the caller as an ordinary successful response, with no `tracing::warn!` anywhere on this path. This is reachable only via schema drift or a projection change (not an ordinary caller-controlled input), so it is not a shipping blocker, but it is a genuine robustness/contract gap directly next to code this plan just touched, and the inconsistency between the two loops' failure modes (fail-closed vs. fail-open for structurally the same kind of read failure) is easy to miss in review.

**Fix:** Mirror the counting loop's fail-closed pattern at the frontier site:

```rust
let src_col = batch
    .column_by_name("source_node_id")
    .and_then(|c| c.as_any().downcast_ref::<arrow_array::StringArray>())
    .ok_or_else(|| GraphSpikeError::new(GraphSpikeErrorKind::Bridge, "missing source_node_id column"))?;
let tgt_col = batch
    .column_by_name("target_node_id")
    .and_then(|c| c.as_any().downcast_ref::<arrow_array::StringArray>())
    .ok_or_else(|| GraphSpikeError::new(GraphSpikeErrorKind::Bridge, "missing target_node_id column"))?;
```

or, at minimum, `tracing::warn!` before allowing the loop to `break` on an empty-because-unreadable frontier, so silent truncation is at least observable in production.

#### WR-02: `attempt_graph_augmentation` ignores the configured `graph.max_hop_cap`, always fetching a 1-hop neighborhood

_(Carried forward from prior review's WR-01; independently re-confirmed present and unchanged.)_

**File:** `engine/src/main.rs:1146,1156` (hardcoded `1`), contrasted with `:1835` (`query_graph` correctly using `self.effective_settings.graph.max_hop_cap`)

**Issue:** `attempt_graph_augmentation` receives `settings: &GraphSettings` (carrying both `seed_match_min_score` and `max_hop_cap`) but only ever reads `settings.seed_match_min_score`. Both hop-depth arguments to `fetch_neighborhood`/`narrow_via_cypher` are hardcoded to `1`. An operator who configures `engine.graph.max_hop_cap = 3` gets that ceiling honored for the explicit `QueryGraph` RPC but silently gets a fixed 1-hop neighborhood for automatic graph augmentation inside `QueryRag`. `04.1-09-PLAN.md` explicitly defers this ("Config-plumbing, not counting-correctness — out of this plan's scope") and confirms that at `hop_cap=1` the CR-01 double-counting defect could never have manifested on this path regardless.

**Fix:** Either thread `settings.max_hop_cap` (via `graph::clamp_hop_cap_with_ceiling`) into both calls, or document the fixed 1-hop augmentation as an intentional MVP scope limit in `attempt_graph_augmentation`'s doc comment.

#### WR-03: Entity update is a non-atomic delete-then-add with a real, awaited, per-entity visibility gap

_(Carried forward from prior review's WR-02; independently re-confirmed present and unchanged.)_

**File:** `engine/src/main.rs:2702-2712`

**Issue:** In `extract_and_persist_entities`'s mutation phase, updated (pre-existing) entities are deleted one at a time in a sequentially-awaited loop, and only re-inserted (batched with newly-created entities) afterward:

```rust
for entity in &updated_entities {
    let ent_pred = format!("entity_id = '{}'", escape_sql_literal(&entity.entity_id));
    entities_table.delete(&ent_pred).await...;
}
```

Between the first `delete` and the final `add`, every already-deleted updated entity is absent from `entities_table`. Ingestion is serialized through a single worker task, but readers (`query_rag` via `attempt_graph_augmentation`, and `query_graph`) are not serialized against the worker and can observe a matched seed entity's neighborhood as transiently missing rows mid-re-ingestion.

**Fix:** Batch the deletes into a single `entity_id IN (...)` predicate (mirroring the pattern already used for `entity_edges_table.delete(&edge_pred)`), or restructure as insert-new-then-delete-old to avoid a window where the row is absent entirely.

#### WR-04: `query_graph`'s post-narrowing Arrow filters silently fall back to unfiltered data on failure, with no error or log

_(Carried forward from prior review's WR-03; independently re-confirmed present and unchanged.)_

**File:** `engine/src/main.rs:1864-1865` and `:1911-1912`

**Issue:** Both `relation_type_filter` application and the corresponding node-endpoint narrowing swallow `filter_record_batch` errors and substitute the pre-filter batch (`.unwrap_or(edges_batch)` / `.unwrap_or_else(|_| entities_batch.clone())`). If either filter call fails, the RPC returns the *unfiltered* edges/nodes to a caller who explicitly requested `relation_type_filter`, silently violating the documented nodes/edges-consistency invariant, without any `tracing::warn!` (unlike `narrow_via_cypher`'s adjacent fail-open path, which does log).

**Fix:** At minimum, log via `tracing::warn!` on the `Err` branch; consider `Status::internal` instead of fabricating a response that doesn't match the request.
