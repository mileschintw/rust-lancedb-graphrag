## User Constraints (from CONTEXT.md)

### Locked Decisions

**Entity & Relationship Extraction**
- D-01: Extraction runs synchronously during ingestion, blocking document completion — same execution model as embedding generation.
- D-02: Per-chunk granularity — one LLM structured-extraction call per chunk.
- D-03: Entity types are open-domain freeform strings, no fixed taxonomy.
- D-04: `relation_type` is freeform LLM-assigned; `edges.weight` is an LLM-reported confidence 0.0-1.0.
- D-05: `ExactMatchResolver` merges duplicate entity mentions by case-normalized exact name, scoped globally across the corpus. Reversibility: costly (narrowing later requires re-splitting merged nodes).
- D-06: Extraction failure for a single chunk is non-fatal — the chunk keeps zero entities, document still reaches `completed`.
- D-07: Chunks below a minimum content-length threshold skip extraction entirely (threshold is implementer discretion).
- D-08: Extraction reuses the provider-neutral `Generator` trait pattern via a sibling trait (`ExtractionGenerator`), not a separate client.
- D-09: Extraction calls within one document run concurrently in batches — `futures::stream::iter(...).buffer_unordered(5)`, reusing Phase 2 D-20.

**Graph Node/Edge Schema Resolution**
- D-10: Extracted entities go in a new dedicated `entities` table, separate from `nodes`. Reversibility: one-way.
- D-11: `entities` carries `name`, `entity_type`, `name_vector`, nullable `summary`/`summary_vector`/`unsummarized_refs`/`community_ids` — moved from `nodes`.
- D-12: `entities.source_chunk_ids` (list) tracks provenance; merges accumulate both mentions' chunk ids.
- D-13: `edges.source_node_id`/`target_node_id` reference entity IDs only — entity-to-entity relationships, edges never connect a chunk to an entity.
- D-14: The new `entities` table follows Phase 2 D-22's fail-fast/no-auto-migrate schema-drift rule.
- D-15: The dormant `community_ids`/`summary`/`summary_vector`/`unsummarized_refs` columns on `nodes` are removed now that `entities` owns that data. Reversibility: one-way.
- D-16: `nodes`-column removal handled via a documented manual store-reset (delete local LanceDB dir, re-ingest) — no in-engine auto-migration, consistent with D-22.
- `[Note]` REQUIREMENTS.md's DATA-06/DATA-07 "on nodes" wording is superseded by D-11/D-15 — those columns land on `entities`.

**Graph Traversal & Query**
- D-17: Traversal uses the real `lance-graph` crate (`lance-graph = "0.5.4"`, `default-features = false`) — **CONFIRMED**, not just decided, by Phase 4's spike (5 passing tests).
- D-18: RAG queries seed graph traversal via vector search against `entities.name_vector` — not exact match, not a second LLM call.
- D-19 [R]: Traversal is hybrid — hop-capped BFS pre-narrow in Rust against `entities`/`edges` lancedb tables, THEN Cypher pattern-matches only the already-narrowed subgraph (`lance-graph`'s `execute()` has no predicate pushdown). Reuse `engine/src/graph/mod.rs`'s proven `fetch_neighborhood` → `bridge_batch` → `CypherQuery::execute()` → `bridge_batch_back` shape directly.
- D-20: The standalone `QueryGraph` RPC accepts a structured request (seed entity name/id, hop depth, optional `relation_type` filter), never a raw Cypher string. Variable-length Cypher patterns (`*1..N`) cannot project the relationship variable `r` in `RETURN` (Pitfall 6) — Claude's discretion was originally framed as (a) node-only vs (b) correlate-back-to-`edges_batch`; **this phase's actual PLAN.md resolves it with a third option — see Architecture Patterns below.**
- D-21: `entities.name_vector` reuses the existing OpenRouter embedding client/model and `EMBEDDING_DIMENSIONS`.
- D-22: `QueryGraph` accepts only an explicit seed entity name/id — no server-side NL-query embedding (that stays on the `/rag/query` path per D-18).
- D-23: Both `QueryGraph` and auto-triggered RAG augmentation enforce a configurable max hop cap (default 3, matching the spike's `MAX_HOP_CAP`/`clamp_hop_cap`).
- D-24: Always-on RAG-path traversal follows edges in both directions from the seed (undirected Cypher `-[r]-`).
- D-25: `QueryGraph` remains gRPC-only/internal — no Go gateway HTTP wrapper.

**RAG Prompt Integration (ContextAssemblyStrategy)**
- D-26: Every `/rag/query` call automatically attempts entity seed-matching; graph context added only when matches are found. No new opt-in flag.
- D-27: Graph context appears as a separate "Related Entities & Relationships" section, distinct from numbered `[N]` chunk citations. Not citable `EvidenceBlock`-like entries in v1.

## Summary

This is a **redo of research for a phase whose empirical unknowns are already settled**. Phase 4's spike (`04-RESEARCH.md`) proved, via real `cargo test` runs against the published `lance-graph 0.5.4` crate, that the arrow ~58.3 ↔ arrow ^56.2 IPC bridge round-trips real data losslessly, that Cypher pattern-matching against a pre-narrowed, already-bridged neighborhood works (including open-vocabulary `relation_type` `WHERE` filtering), and that fixed single-hop Cypher queries can project relationship properties directly while variable-length (`*1..N`) queries cannot. None of that needs re-investigation.

What this phase actually needs — and what this research focuses on — is the **application layer around that proven mechanism**: (1) how the per-chunk LLM extraction call is made concurrently and safely re-runnable on re-ingestion, (2) how the `entities`/`entity_edges` LanceDB tables are shaped and how they coexist with the pre-existing chunk-structural `edges` table, (3) how the hop-bounded BFS neighborhood expansion (`fetch_neighborhood`) composes with both the always-on RAG-path augmentation and the standalone `QueryGraph` RPC, (4) how graph-match scores are normalized and interleaved with Phase 3's RRF-fused chunk scores under a configurable `graph_weight`, and (5) the concrete shape of the `ContextAssemblyStrategy` trait/enum and its `SourceChunks` fallback rendering.

Critically, this phase already has **five `PLAN.md` files in its own directory, refined through at least two rounds of checker iteration and one round of cross-AI review** (`04.1-REVIEWS.md`, dated after all five plans). Those plans encode real, load-bearing design corrections beyond what `04.1-CONTEXT.md` originally specified — most importantly, a **new dedicated `entity_edges` table** (not the pre-existing `edges` table, which already holds Phase-2-written chunk-structural `next_chunk`/`same_section` rows) and a **third resolution for `QueryGraph`'s variable-hop relation-property problem** (serve the response directly from `fetch_neighborhood`'s own accumulated output, never from a Cypher correlate-back, which cross-AI review proved is mathematically impossible to reconstruct for path length > 1). This research treats those already-checker-vetted corrections as the current best design and documents them as such, while also surfacing the cross-AI review's still-open concerns (a possible empty-slice panic in min-max normalization, a serde-derive privacy-bypass risk on `GraphFact`, a system-prompt wording gap, and a re-ingestion data-loss edge case) that the next planning pass should explicitly close.

**Primary recommendation:** Plan around the already-designed five-wave shape (schema restructure → tracer slice → concurrency/idempotency hardening → `QueryGraph` RPC → score-interleaving), reusing `engine/src/graph/{mod.rs,bridge.rs}` and `engine/src/generation/openrouter.rs`'s HTTP/schema conventions verbatim, and explicitly re-verify or fix the four cross-AI-review findings called out in Common Pitfalls before treating the phase as execution-ready.

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Min-max normalization for graph/chunk score merging | Z-score / L2 normalization, or drop scores entirely and use Reciprocal Rank Fusion (RRF) by rank | [CITED: web, MEDIUM confidence] Min-max is simplest and matches this codebase's existing RRF-weight-multiplier convention (`vector_weight`/`bm25_weight`), but a single outlier score compresses the rest of the distribution into a narrow band, and it is undefined (NaN risk) on a single-element or all-equal-score set — the exact edge case cross-AI review flagged (see Common Pitfalls). ### Pattern 1: Concurrent bounded extraction — reuse `get_embeddings`'s shape, but `collect()` not `try_collect()`

**What:** `engine/src/client/mod.rs`'s `get_embeddings` is the exact, already-shipped precedent for D-09's `buffer_unordered(5)`:
```rust
// engine/src/client/mod.rs:206-226 (VERIFIED, read this session)
pub async fn get_embeddings(&self, texts: &[String]) -> Result<Vec<Vec<f32>>, String> {
    let client = self.clone();
    let mut indexed =
        stream::iter(texts.iter().cloned().enumerate().map(move |(index, text)| {
            let client = client.clone();
            async move {
                client.embed_with_retry(&text).await.map(|embedding| (index, embedding))
            }
        }))
        .buffer_unordered(self.config.max_concurrency)
        .try_collect::<Vec<_>>()   // <-- fail-fast: ONE bad embedding aborts the whole batch
        .await?;
    indexed.sort_unstable_by_key(|(index, _)| *index);
    Ok(indexed.into_iter().map(|(_, embedding)| embedding).collect())
}
```
Extraction's concurrency runner must copy the `stream::iter(...).buffer_unordered(N)` + `sort_unstable_by_key` shape, but **must NOT copy `try_collect`** — D-06 requires every chunk's extraction result to survive individually (one chunk's failure must not abort its siblings' successful extractions or the document's completion). Use `.collect::<Vec<(usize, Result<ExtractionOutput, GenerationError>)>>().await` instead, then sort back into chunk order and merge/persist sequentially. This distinction is exactly what `04.1-03-PLAN.md` Task 1 specifies and is the single most important divergence from the otherwise-identical embedding precedent.

**When to use:** The per-document extraction runner inside `extract_and_persist_entities` (D-01/D-02/D-09).

### Pattern 2: `entity_edges` as a dedicated table, not a reuse of the existing `edges` table

**What:** `engine/src/db/mod.rs`'s current `edges_schema()` — `edge_id`, `source_node_id`, `target_node_id`, `relation_type`, `weight`, `document_id`, `summary`, `summary_vector` — [VERIFIED: read `engine/src/db/mod.rs` this session] **already exists in production** and is **already being written to** by `replace_document_with_faults` in `engine/src/main.rs` (chunk-structural `next_chunk`/`same_section` rows, since Phase 2). `04.1-CONTEXT.md`'s D-13 ("`edges.source_node_id`/`target_node_id` reference entity IDs only") was written without this fact in view. Mixing entity-relationship edges into the same physical table would make D-13's "entity IDs only" claim true only by ID-space convention (entity UUIDs never colliding with `<document_id>:<index>` chunk-ID strings) — cross-AI review (`04.1-REVIEWS.md`) flagged this as an unenforced-by-structure HIGH finding, and `04.1-01-PLAN.md` Task 2/3 resolved it by adding a **new, dedicated `entity_edges` table**, field-for-field identical to `edges_schema()`'s shape but a physically distinct table:
```rust
// entity_edges_schema() — byte-for-byte identical Field list to edges_schema(),
// registered under a new table name, per 04.1-01-PLAN.md Task 3
Field::new("edge_id", Utf8, false),
Field::new("source_node_id", Utf8, false),   // entity IDs only, D-13, now enforced by
Field::new("target_node_id", Utf8, false),   // TABLE MEMBERSHIP, not ID-space convention
Field::new("relation_type", Utf8, false),
Field::new("weight", Float32, false),
Field::new("document_id", Utf8, false),
Field::new("summary", Utf8, true),
Field::new("summary_vector", vector(), true),
```
`fetch_neighborhood` (and every downstream traversal call) must query `entity_edges_table()` exclusively and never `edges_table()` — chunk-structural edges become structurally unreachable from graph traversal, not merely disjoint by convention. `edges_schema()`/`edges_table()`/`replace_document_with_faults`'s existing writes are **completely unchanged** by this correction.

**When to use:** Every place this phase's design docs (`04.1-CONTEXT.md`) say "edges" in the entity-relationship sense — read it as "`entity_edges`", not the pre-existing `edges` table.

### Pattern 3: `entities`/`nodes` schema evolution — additive new table + subtractive column removal on an already-shipped table

**What:** [VERIFIED: read `engine/src/db/mod.rs` this session] The current `nodes_schema()` has 23 fields, the last four being the dormant Phase-2 placeholders (`community_ids`, `summary`, `summary_vector`, `unsummarized_refs`) that D-15 removes (down to 19 fields — these columns move to the new `entities` table per D-11). The new `entities_schema()` (per `04.1-01-PLAN.md` Task 3):
```rust

Field::new("name", Utf8, false),
Field::new("entity_type", Utf8, false),        // freeform, D-03
Field::new("name_vector", vector(), false),    // reuses the existing vector() helper / EMBEDDING_DIMENSIONS
Field::new("summary", Utf8, true),
Field::new("summary_vector", vector(), true),
Field::new("unsummarized_refs", list(Utf8), true),
Field::new("community_ids", list(Int32), true),
Field::new("source_chunk_ids", list(Utf8), false),  // D-12, always >= 1 entry
```
This restructure is a **one-way, drift-inducing change against a live LanceDB store**. `validate_schema()` (`engine/src/db/mod.rs`, [VERIFIED: read this session]) does exact `Field`-list equality — there is no schema-version field or migration registry anywhere in this codebase. "Upgrading past this phase" concretely means deleting the local LanceDB directory and re-ingesting, consistent with D-14/D-16/D-22's existing "manual user intervention" convention — this is a local-first, single-developer project so that cost is acceptable, but it must be called out explicitly to whoever executes the plan (already correctly framed as a `checkpoint:decision` gate in `04.1-01-PLAN.md` Task 2).

**When to use:** Any planning around `table_schemas()` — it grows from a 5-tuple (`documents`, `staged_documents_v2`, `nodes`, `edges`, `communities`) to a 7-tuple, adding `entities` and `entity_edges`.

### Pattern 4: `QueryGraph`'s variable-hop problem — served directly from `fetch_neighborhood`, never a Cypher correlate-back

**What:** `04.1-CONTEXT.md`'s D-20 framed the choice as (a) node-only results vs. (b) correlate the Cypher result's node-ID pairs back against the already-in-scope `edges_batch`. **`04.1-04-PLAN.md` (already checker-iterated) resolved this with a third option that neither (a) nor (b) anticipated**, discovered during cross-AI review: `fetch_neighborhood` itself is *already* a genuine, real, hop-capped bidirectional BFS against the real `entity_edges` table — its own accumulated output (`entities_batch`, `edges_batch`) is the authoritative source for `QueryGraphResponse.nodes`/`.edges` at **every** `hop_depth`, including 1, with **no second Cypher call needed to fill in a field at all**. Cross-AI review proved option (b) is mathematically impossible for path length > 1 (a variable-hop Cypher result's final `(seed, neighbor)` pair does not identify which edge(s) along the path connect them — there is nothing to correlate back to), and a separate review pass proved a naive hop-1 exception (serving the response from `traverse_fixed_hop`'s Cypher-projected result) also fails the response contract: that projection lacks `entity_type` and a complete seed row, and an **undirected** Cypher match cannot preserve which node was the edge's original source vs. target.

Instead, `lance-graph`'s Cypher engine is kept as a genuine **production call site** (honoring D-17/D-19/DATA-05's "Cypher pattern-matching" requirement literally) but strictly as a **non-load-bearing validation/demo layer**, `validate_via_cypher`, called only for `hop_depth == 1` (the only case with a directly comparable fixed-single-hop Cypher pattern), whose `Agreed`/`Disagreed`/`Errored` outcome is read only inside a `tracing::debug!`/`tracing::warn!` log line and never touches `nodes`/`edges`. This same `validate_via_cypher` helper is shared verbatim by the always-on RAG-path augmentation (`attempt_graph_augmentation`) — one shared helper, two call sites, both non-load-bearing.

When a `relation_type_filter` is set, `QueryGraphResponse.nodes` is redefined as exactly the entities appearing as `source_node_id`/`target_node_id` in a *matching* edge (a strict subset of `entities_batch`), keeping nodes/edges mutually consistent under filtering — a filter matching zero edges is a valid `Ok` response with both empty, never `Status::not_found`.

**When to use:** Implementing `query_graph()`'s handler body and any future extension of `QueryGraph`'s response contract.

### Pattern 5: Score-interleaving under `graph_weight` — min-max normalize both sides, thread the weight through `GenerationRequest`

**What:** `04.1-05-PLAN.md` Task 1 (already designed, not yet executed) upgrades an intentionally-simpler Plan-02 append-order integration into real score interleaving: reserve the single highest-scoring chunk `EvidenceBlock` first (an existing Plan-02 rule, needed because `ModelOutput::validate_grounding_with_limits` requires at least one citable evidence ID whenever chunk evidence exists — [VERIFIED: `engine/src/generation/mod.rs` lines 191-199, read this session]), then min-max normalize the *remaining* chunk scores to `[0,1]`, separately min-max normalize graph-fact scores to `[0,1]`, multiply the graph side by `graph_weight`, merge both into one descending-sorted sequence, and pack sequentially into the existing shared token-budget loop. Chunk `EvidenceBlock.id` markers (`[1]`, `[2]`, ...) are **stable** — assigned once at `from_candidate` construction time reflecting original candidate rank, never renumbered by packing position; graph facts never receive a marker at any position (D-27 holds under interleaving).

Critically, `graph_weight` must be threaded through `GenerationRequest` (a new field) rather than let `main.rs`'s pre-check and `openrouter.rs`'s actual outbound-request-building call independently derive it from two different places — `04.1-05-PLAN.md` explicitly names this as a cross-AI-review HIGH finding on an earlier draft ("`graph_weight` has no complete path to the actual provider request") and fixes it by having both call sites read the same `GenerationRequest.graph_weight`/`self.effective_settings.retrieval.graph_weight` expression.

**When to use:** `prompt.rs`'s `pack_evidence_and_graph_prompt` (upgrading Plan 02's append-order version in place, same function name, new required parameter).

### Anti-Patterns to Avoid
- **Reusing `try_collect()` for concurrent extraction results** (Pattern 1) — this is the exact wrong half of the `get_embeddings` precedent to copy; it violates D-06's per-chunk non-fatal contract.
- **Writing entity-relationship edges into the pre-existing `edges` table** — breaks D-13's structural intent; use the dedicated `entity_edges` table (Pattern 2).
- **Attempting to correlate a variable-hop Cypher result's node pairs back to the edge batch for `QueryGraph`'s response** — proven mathematically impossible for path length > 1 by cross-AI review (Pattern 4); serve directly from `fetch_neighborhood`'s own output instead.
- **Building `QueryGraph`'s hop-1 response from `traverse_fixed_hop`'s Cypher-projected result** — its projection lacks `entity_type` and cannot preserve directed edge orientation (undirected Cypher match); use it only as a non-load-bearing validation call via `validate_via_cypher` (Pattern 4).
- **Deriving `graph_weight` independently in two call sites** (`main.rs` pre-check vs. `openrouter.rs`'s actual send) — thread it through `GenerationRequest` so both read one source (Pattern 5).
- **Projecting the relationship-pattern variable (`r`) inside a variable-length quantifier's `RETURN` clause** — `RETURN seed, r, neighbor` under `*1..N` fails at query-planning time (04-RESEARCH.md Pitfall 6, empirically confirmed, unchanged by this phase).
- **Assuming `default-features = false` yields a lean, cloud-free `lance-graph` dependency tree** — it does not (04-RESEARCH.md Pitfall 5); budget CI/build time for ~350+ transitive crates in the *default* build once promoted.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Cypher pattern matching / multi-hop traversal | Custom BFS + manual pattern-matching in Rust for the Cypher-matching portion | `lance-graph`'s `CypherQuery` (already proven, `engine/src/graph/mod.rs`) | Locked by D-19; this phase's job is to feed it a pre-narrowed neighborhood, not to replace it |
| Cross-arrow-version data transfer | Custom binary serialization / unsafe transmute | Arrow IPC stream format (`bridge_batch`/`bridge_batch_back`) | Already empirically proven to round-trip losslessly (04-RESEARCH.md, `cargo test`) |
| Open-vocabulary `relation_type` filtering | Enumerating every observed value into a distinct `RelationshipMapping`/Cypher label | Single generic wrapper label + `type_field` + Cypher `WHERE` | Confirmed working via the spike's `relation_type_filter_on_open_vocabulary_field` test |
| Concurrent bounded HTTP calls | A bespoke semaphore/worker-pool for extraction | `futures::stream::iter(...).buffer_unordered(5)` (Pattern 1) | Already the shipped, tested pattern for embeddings; extraction only needs the `collect()`-not-`try_collect()` variant |

**Key insight:** Every "don't hand-roll" item here already has a proven, shipped precedent somewhere in this codebase (embeddings concurrency, SQL escaping, case-folding, Cypher bridging) — this phase's actual engineering work is almost entirely about *reusing those precedents in a new context* (extraction instead of embedding, entity names instead of BM25 tokens, entity relationships instead of chunk structure), not inventing new mechanisms.

## Common Pitfalls

### Pitfall 1: `lance-graph`'s `execute()` has no predicate pushdown — this is settled, not a new finding
**What goes wrong:** `CypherQuery::execute()`'s `HashMap<String, RecordBatch>` argument is fully materialized in memory; there is no way to push a seed/hop filter into a `lancedb` scan through this API.
**How to avoid:** Always pre-narrow via `fetch_neighborhood`'s Rust-native hop-capped BFS against `entity_edges_table()` before bridging (Pattern 4's whole design exists because of this constraint). [VERIFIED: `04-RESEARCH.md` Pitfall 2, empirically confirmed via `cargo test` in Phase 4's spike — carried forward unchanged, not re-tested this session since the mechanism itself is unchanged.]

### Pitfall 2: The pre-existing `edges` table is NOT where entity relationships go — this phase's own CONTEXT.md got this wrong before cross-AI review caught it
**What goes wrong:** `04.1-CONTEXT.md`'s D-13 reads naturally as "the `edges` table holds entity relationships," but that table is already live and already holds Phase-2 chunk-structural rows.
**How to avoid:** Use the dedicated `entity_edges` table (Pattern 2). Every reference to "edges" in D-10 through D-32 that concerns entity-to-entity relationships should be mentally substituted with "`entity_edges`" when planning.
**Warning signs:** Any task description that says "write to the `edges` table" for entity/relation persistence — this is the corrected-by-review pattern, not the original CONTEXT.md wording.

### Pitfall 3: Min-max score normalization can divide by zero / panic on a degenerate or empty candidate set — flagged by cross-AI review, not yet proven fixed in source
**What goes wrong:** `04.1-05-PLAN.md`'s action text specifies a `max == min` guard for the all-equal-scores degenerate case (`if max == min { 1.0 } else { (score - min) / (max - min) }`), on both the chunk side and the graph-fact side. Cross-AI review (Antigravity pass, `04.1-REVIEWS.md`) separately flagged that the *plan text* does not explicitly describe an **empty-slice** guard before calling `.min_by`/`.max_by` — an empty `evidence` or `graph_facts` slice would panic on `.unwrap()` inside those calls, a straightforward crash bug independent of the min-max-vs-alternatives design choice.
**Why it happens:** `graph_facts` is legitimately empty on `no_match_found` (D-32's silent-fallback path) — a real, expected runtime state, not an edge case that "shouldn't happen."
**How to avoid:** The interleaving function must short-circuit (skip normalization entirely, or default to an empty normalized set) when either input slice is empty, before any `min_by`/`max_by` call — this must be an explicit, tested guard, not implied by the `max == min` degenerate-value check (which assumes at least one element exists).
**Warning signs:** A `/rag/query` call whose graph augmentation returns `no_match_found` (very common — most queries won't seed-match an entity) triggering a panic instead of a normal chunk-only response.
**Status as of this research:** [CITED: `04.1-REVIEWS.md`, Antigravity review, MEDIUM severity] — this concern's timestamp (last-modified) is *after* the current `04.1-05-PLAN.md`'s own last edit, meaning the plan text as currently written may not yet reflect a fix. The planner should treat this as an open, unresolved finding requiring an explicit empty-slice test case, not assume it is already closed.

### Pitfall 4: `GraphFact`'s escaping-constructor invariant may be bypassable by `#[derive(Serialize, Deserialize)]`
**What goes wrong:** `04.1-02-PLAN.md` designs `GraphFact` with private string fields and `GraphFact::new(...)` as the sole (escaping) constructor, intended to make it impossible to construct an unescaped instance. If `GraphFact` (or the `GraphFactBlock` wrapper threaded through `GenerationRequest`, which needs `Serialize`/`Deserialize` for the existing `GenerationRequest` derive) also derives `Serialize`/`Deserialize`, Rust's field-privacy model is **module-scoped, not type-scoped** — a `#[derive(Deserialize)]` expansion is generated in the same module as the struct definition, so it has the same field access the struct's own `impl` block has, and CAN construct the struct directly from arbitrary deserialized field values, bypassing `GraphFact::new`'s escaping entirely.
**Why it happens:** This is a general, well-documented Rust language behavior (privacy is `mod`-scoped), not specific to `serde` — but it is a genuinely easy trap to fall into when a "private fields + smart constructor" pattern is combined with `#[derive(Deserialize)]` for unrelated reasons (here, threading `graph_facts`/`GraphFactBlock` through `GenerationRequest`, which already derives `Serialize`/`Deserialize` for its other fields).
**How to avoid:** Either (a) implement `Deserialize` manually for `GraphFact`/`GraphFactBlock` routing through the same escaping path `new()` uses, or (b) don't derive `Deserialize` on the type at all if nothing actually deserializes a `GraphFact` from external input in this phase (only chunk-derived data flows into it, never a wire-deserialized request) — confirm which is actually needed before adding the derive.
**Warning signs:** A `GraphFact`/`GraphFactBlock` type with `#[derive(Serialize, Deserialize)]` sitting in the same file as a doc comment claiming "cannot be constructed unescaped."
**Status as of this research:** [CITED: `04.1-REVIEWS.md`, Codex review, MEDIUM severity] — genuinely unverified in code (the type doesn't exist yet, `context_strategy.rs` is a planned-not-yet-executed file); flagged here as a concrete implementation constraint the executing task must satisfy, not merely a design nicety.

### Pitfall 5: Re-ingestion's delete-before-extract ordering can silently reduce graph completeness if extraction partially fails
**What goes wrong:** `extract_and_persist_entities`'s self-contained delete-by-`document_id` step (against `entity_edges_table()`) runs before the new extraction pass. If some chunks' extraction calls fail after retries are exhausted (D-06's non-fatal-per-chunk contract), those chunks contribute zero entities — correct and by design for a *first* ingestion, but on a *re-ingestion* this means the document's entity_edges rows can end up strictly smaller than before the re-ingestion, with no operator signal distinguishing "the new content genuinely has fewer relationships" from "extraction degraded on retry."
**Why it happens:** D-06 was designed for the first-ingestion case (a chunk with no prior graph data losing nothing by contributing zero entities); it wasn't explicitly re-examined for the re-ingestion case, where "delete existing rows, then maybe fail to fully repopulate them" is a different risk shape than "never had rows to begin with."
**How to avoid:** At minimum, this asymmetry should be a documented, explicit v1 limitation (matching the existing pattern `04.1-03-PLAN.md` Test 5 already uses for stale-entity survival) — the planner should decide whether this needs an aggregate-rate guardrail extension (AI-SPEC §6 already has one for extraction failure rate) that specifically flags a *re-ingestion* whose new entity/edge count regresses versus its prior count, since that is a stronger, more actionable signal than the existing per-chunk-failure aggregate alone.
**Warning signs:** A document's `entity_edges` row count for a given `document_id` dropping between two successive ingestions of similar-length content.
**Status as of this research:** [CITED: `04.1-REVIEWS.md`, Codex review, HIGH severity] — this appears to be the least-resolved of the cross-AI findings; none of the five `PLAN.md` files' `must_haves.truths` explicitly test for a *count regression* across re-ingestion (Plan 03 Test 3 tests exact-count stability for an *identical* re-ingestion, not a partial-failure scenario). Recommend the planner add this as an explicit test case or an accepted-risk log entry with rationale, rather than leaving it silently unaddressed.

### Pitfall 6: The system prompt's "ONLY the provided evidence blocks" wording doesn't mention the new graph section
**What goes wrong:** [VERIFIED: `engine/src/prompt.rs` lines 208-212, read this session] The existing `system_policy` string says: *"Answer the user's question accurately using ONLY the provided evidence blocks... Cite evidence using numbered markers like [1], [2] matching evidence block IDs."* This predates the graph-facts section (D-27) entirely. A literal reading tells the model to ignore anything that isn't an "evidence block," which could suppress legitimate use of the non-citable "Related Entities & Relationships" section, or — worse — the model could still use graph facts to shape its answer without the system prompt's citation-discipline framing ever having been extended to cover that new input class.
**How to avoid:** Update `system_policy` to explicitly acknowledge the graph-facts section as a distinct, non-citable-but-usable context class, consistent with D-27's "non-citable but present" design — this is a one-string change but affects grounding-quality wording that hasn't been re-validated against the new prompt shape.
**Status as of this research:** [CITED: `04.1-REVIEWS.md`, Codex review, MEDIUM severity] — confirmed via direct source read that the wording gap is real as of this session; not yet addressed by any of the five plans' task text (none of `04.1-02`/`04.1-05-PLAN.md`'s actions mention editing `system_policy`'s string content, only `prompt.rs`'s packing logic).

### Pitfall 7 (carried forward, settled): Variable-length Cypher patterns cannot project the relationship variable
**What goes wrong / How to avoid:** See Pattern 4 above — this is why `QueryGraph`'s variable-hop response is served directly from `fetch_neighborhood`, not from a Cypher projection. [VERIFIED: `04-RESEARCH.md` Pitfall 6, `cargo test`, Phase 4 spike — unchanged, not re-tested this session.]

### Pitfall 8 (carried forward, settled): `default-features = false` does not eliminate `lance-graph`'s cloud/geospatial dependency weight
**What goes wrong / How to avoid:** Budget for ~350+ transitive crates and several minutes of cold build time once promoted to the *default* (not feature-gated) build — this is a Locked Implication of this phase, not optional.
