<objective>
Fix the one remaining `gaps:` entry from 04.1-VERIFICATION.md (verified 2026-08-08, score 3/4, status `gaps_found`): `fetch_neighborhood`'s `MAX_TOTAL_EDGES` bound (`engine/src/graph/mod.rs`) is checked against **raw per-hop edge row counts**, summed *before* `dedup_edges_by_identity` ever runs. Because `fetch_neighborhood`'s bidirectional predicate (`source_node_id IN (frontier) OR target_node_id IN (frontier)`) legitimately re-matches an edge discovered at hop N again once its other endpoint enters hop N+1's frontier — the exact reason `dedup_edges_by_identity` exists — every edge is counted at least twice by the time a second hop touches it, and deeper hops compound the effect. A neighborhood whose TRUE distinct edge count is comfortably under 500 can be wrongly rejected with `Err(GraphSpikeErrorKind::Bridge)` once `hop_cap >= 2`, purely from this double-counting. This is a false-positive rejection of a request that is genuinely within the D-23 resource bound this function exists to enforce — a correctness bug in the bound-check itself, not the traversal logic it protects.

This is reachable by an ordinary `QueryGraph` client request with no special configuration: `query_graph` calls `fetch_neighborhood` with `self.effective_settings.graph.max_hop_cap` (`main.rs:1835`), which defaults to 3 (`config.example.toml`). `attempt_graph_augmentation` (the automatic RAG-path graph augmentation on every `/rag/query`) is NOT currently exposed to this defect — it hardcodes `hop_cap=1` for both its `fetch_neighborhood` and `narrow_via_cypher` calls (`main.rs:1146,1156`; this is WR-01, still open, see disposition below), and at `hop_cap=1` the hop loop runs exactly once, so no edge can ever be re-matched at a "later hop." **Coupling this plan closes, not merely notes:** because this plan's fix is unconditional — it patches `fetch_neighborhood` itself, the one function both call sites share, not a per-call-site workaround — a future fix to WR-01 that wires `settings.graph.max_hop_cap` into `attempt_graph_augmentation`'s call sites will be automatically safe against this double-counting defect from the moment it lands, with no further coordination required between the two fixes.

**Fix approach:** track the bound against distinct `edge_id` values via a running `HashSet<String>` accumulated across hops, checked with `seen_edge_ids.len() > MAX_TOTAL_EDGES`, replacing the current raw-row-sum accumulator — per the review's own proposed fix (04.1-REVIEW.md CR-01) and per D-23 (the configurable-hop-cap resource-bounding decision this check enforces).

**Acceptance-criteria trap, resolved explicitly (per `04.1-VERIFICATION.md`'s own framing — do not re-litigate):** Task 1's regression fixture uses **approach (a)** — a fixture shaped so the arithmetic genuinely works at the real, unmodified `MAX_TOTAL_EDGES = 500` production constant (a shared entity revisited across enough hops), **not approach (b)** (making the bound injectable/configurable for a smaller test constant). `MAX_TOTAL_EDGES` itself is never edited by this plan.
