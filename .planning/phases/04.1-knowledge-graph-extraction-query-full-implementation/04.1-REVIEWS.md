# Cross-AI Plan Review — Phase 04.1

Reviewed by Codex and Antigravity CLI as independent, source-grounded reviewers. Claude was excluded by design since this review was run from within Claude Code (self-review avoidance). Gemini, CodeRabbit, OpenCode, Qwen, and Cursor were not installed on this system (see `reviewers_unavailable` above).

This is a re-review of the plan set after checker-iteration-2 revisions (Plans 02 and 04 were revised to drop unreachable Test 3f, fix `bfs_neighbor_ids` ambiguity, and add test-name grep gates — see `e34432a`).

## Codex Review

### Summary

The plans are substantially improved and cover the main implementation surface, but the phase remains high risk. Earlier review findings were addressed well — especially dedicated `entity_edges`, real provider-payload capture, bounded extraction, bridge multi-batch handling, QueryGraph filtering, and tracing capture. However, several source-level contract conflicts remain: production Cypher is diagnostic-only rather than authoritative traversal, re-ingestion can delete valid graph data before a swallowed failure, stale chunk IDs can point to replacement content, and the `graph_weight = 0` behavior contradicts its test. These should be resolved before execution.

### Strengths

- Plan 01 correctly preserves chunk-structural edges separately. Current ingestion writes `next_chunk`/`same_section` relationships to `edges` in `engine/src/main.rs:1726-1754`; introducing `entity_edges` prevents graph traversal from accidentally consuming them.
- The schema work respects the existing fail-fast drift contract. `engine/src/db/mod.rs:145-158` compares actual and expected fields exactly, so adding validated `entities`/`entity_edges` tables and removing dormant `nodes` fields is coherent.
- Plan 02 traces graph context to the actual provider request. The current provider path constructs the outbound prompt in `engine/src/generation/openrouter.rs:351-365`; requiring a raw mock-server capture is the right verification boundary.
- The reserved citation block is well motivated. `ModelOutput::validate_grounding_with_limits` rejects empty citation sets in `engine/src/generation/mod.rs:191-199`, so Plan 02's reserve-one-citable-chunk rule prevents graph context from making otherwise valid answers ungroundable.
- Plan 03 directly fixes the real bridge bug. Both current bridge functions only read one IPC batch in `engine/src/graph/bridge.rs:14-43` and `:46-75`; a two-batch fixture is an appropriate regression test.
- Plan 04's induced-neighborhood response avoids the known variable-length Cypher limitation and preserves directed edge fields from the LanceDB batch rather than reconstructing them from an undirected match.

### Concerns

- **HIGH — Cypher is present in production but not load-bearing.** D-19 requires a hybrid pre-narrow/bridge/Cypher traversal (`04.1-CONTEXT.md:48`), but Plan 02 explicitly makes `validate_via_cypher` non-load-bearing and says its result never changes returned facts (`04.1-02-PLAN.md:27`, `:179`). Plan 04 repeats this for QueryGraph (`04.1-04-PLAN.md:24`, `:139`). A Cypher failure is therefore logged while BFS-derived facts still produce `Succeeded`. This may not satisfy DATA-05's "query graph context with lance-graph/Cypher-style pattern matching" requirement.
- **HIGH — Re-ingestion can destroy previously valid graph edges.** Plan 02 deletes all prior `entity_edges` for the document before extraction (`04.1-02-PLAN.md:185`), while extraction errors are swallowed and the document is still marked completed (`:191`). A provider or persistence failure during re-ingestion can therefore leave the document with fewer or no graph edges. Plan 03 only tests successful idempotent re-ingestion (`04.1-03-PLAN.md:76`).
- **MEDIUM — Stale provenance becomes ambiguous, not merely stale.** Chunk IDs are deterministic as `{document_id}:{index}` in `engine/src/main.rs:1624`. Plan 03 intentionally leaves old `source_chunk_ids` unchanged after replacement (`04.1-03-PLAN.md:76`), so those IDs can now refer to entirely different replacement content. The entity may therefore appear supported by a chunk that no longer contains it.
- **MEDIUM — Extraction retry and output validation are underplanned.** The AI-SPEC requires retries for provider/schema failures (`04.1-AI-SPEC.md:457-459`) and confidence validation in `[0,1]` (`:501`). The plans describe one extraction call per chunk and persist relation confidence directly (`04.1-02-PLAN.md:189`), without explicit retry, confidence validation, or a dangling-reference validation gate.
- **MEDIUM — `graph_weight = 0` contradicts the implementation description.** Plan 05 says zero excludes graph facts (`04.1-05-PLAN.md:78`), but its action only gives them score zero and sorts them last (`:89`). The current packer includes every block that fits and stops only when the token budget is exceeded (`engine/src/prompt.rs:226-256`). With sufficient budget, zero-weight graph facts will still be sent.
- **MEDIUM — Private `GraphFact` fields are not sufficient if serde is derived.** `GenerationRequest` currently derives `Serialize, Deserialize` in `engine/src/generation/mod.rs:375-394`. Adding graph facts may require serde support that can deserialize private fields directly, bypassing the promised sole escaping constructor in `04.1-02-PLAN.md`'s acceptance criteria.
- **MEDIUM — The prompt's system policy conflicts with graph context.** The existing prompt says the answer must use "ONLY the provided evidence blocks" (`engine/src/prompt.rs:208-214`). Plan 02 adds a separate non-citable graph section (`04.1-02-PLAN.md:181`) but does not explicitly revise that policy. The graph text may be ignored or treated inconsistently by the model.
- **MEDIUM — QueryGraph adds unbounded caller-controlled strings.** Existing QueryRAG input enforces a byte limit in `engine/src/retrieval/mod.rs:359-365`, but Plan 04's `seed_entity_name` and `relation_type_filter` have no equivalent length limits while name lookup scans the entire entity table (`04.1-04-PLAN.md:146`). Hop and edge caps do not bound request size or lookup cost.
- **LOW — Traceability artifacts remain inconsistent.** `REQUIREMENTS.md:23-26` still describes summary/community fields on `nodes`, while the plans move them to `entities`. The context explains the supersession, but leaving the requirements file unchanged will cause future audits to report a false schema discrepancy.

### Suggestions

- Make Cypher response-affecting: use its matched entity IDs to constrain the returned neighborhood while sourcing directed edge properties from the raw edge batch, or explicitly revise D-19/DATA-05 to declare Cypher validation-only.
- Stage new extraction results and atomically replace old document-owned `entity_edges`; on re-ingestion failure, preserve the previous graph.
- Add ingestion-generation/versioned chunk IDs, or mark stale entity provenance as potentially misleading rather than "inert."
- Implement the AI-SPEC's bounded retry loop and validate confidence, entity references, and output shape before persistence.
- Decide explicitly whether `graph_weight == 0` means "skip graph facts" or merely "lowest priority," then align the packer, tests, and documentation.
- Add a prompt-policy test and either custom serde handling or make internal graph prompt types non-deserializable.

### Risk Assessment

**HIGH.** The phase has strong decomposition and good regression-test intent, but the Cypher contract and re-ingestion consistency issues affect core correctness rather than polish. The phase should not be considered execution-ready until those two concerns — and the `graph_weight` contradiction — are resolved.

## Antigravity Review

### Summary

The 5-wave implementation plan for Phase 04.1 (`04.1-01-PLAN.md` through `04.1-05-PLAN.md`) presents a mature, well-structured, and rigorously audited design for introducing knowledge graph extraction, LanceDB graph persistence, Cypher/BFS neighborhood traversal, and RAG prompt integration into Lancet's Rust engine. The plan demonstrates exceptional engineering discipline by addressing subtle architectural pitfalls early — such as separating chunk-structural edges from entity-to-entity relationships into dedicated tables, preserving directed edge orientation directly from LanceDB reads, establishing strict reserve-one-citable-chunk token packing rules, fixing IPC stream multi-batch truncation, and avoiding invalid multi-hop Cypher property projections. The plans are tightly linked to actual codebase realities and include robust acceptance criteria and threat mitigations.

### Strengths

- **Structural Table Separation (`04.1-01-PLAN.md`, `04.1-02-PLAN.md`)**: In `engine/src/db/mod.rs:206-217`, the pre-existing `edges` table stores chunk-structural relationships (`next_chunk`, `same_section`). The plan avoids overloading this table and instead introduces a dedicated `entity_edges` table (`entities_schema()` and `entity_edges_schema()`). This guarantees by table membership — rather than loose ID conventions — that traversal queries can never accidentally mix chunk sequence edges with knowledge graph entity triples.
- **Directional Orientation & Fact Integrity (`04.1-02-PLAN.md`)**: The plan recognizes that Cypher undirected matches (`-[r]-`) losslessly collapse edge directionality. By building returned `GraphFact` triples directly from `fetch_neighborhood`'s raw `entity_edges` batch (`source_node_id` and `target_node_id`), facts preserve their true stored orientation (`A —relation→ B`) instead of outputting inverted claims.
- **IPC Multi-Batch Concatenation (`04.1-03-PLAN.md`)**: `engine/src/graph/bridge.rs:30-32,62-64` currently calls `.next().transpose()`, which silently drops all IPC stream batches beyond the first. Plan 03 refactors this into `decode_all_batches` using Arrow batch concatenation (`concat_batches`), resolving technical debt WR-01 before production LanceDB queries return multi-batch streams.
- **Robust Prompt Escaping Enforced by Constructor (`04.1-02-PLAN.md`)**: In `engine/src/prompt.rs:107-114`, escaping is currently internal to `encode_field_value`. Plan 02 makes string fields on `GraphFact` private and forces all construction through `GraphFact::new(...)`, which applies `escape_evidence_delimiters` at creation time. This prevents unescaped LLM-extracted text from breaking out of `<GRAPH_FACT>` prompt delimiters.
- **Citable Evidence Grounding Guardrail (`04.1-02-PLAN.md`, `04.1-05-PLAN.md`)**: The prompt packing logic in `pack_evidence_and_graph_prompt` enforces a "reserve-one-citable-chunk" rule: the single highest-scoring `EvidenceBlock` is always included first regardless of graph fact scores. This prevents high-scoring graph facts from crowding out all citable chunk evidence, which would otherwise cause `ModelOutput::validate_grounding_with_limits` to fail.
- **Async-Safe Tracing Infrastructure (`04.1-05-PLAN.md`)**: Plan 05 explicitly specifies `#[tokio::test(flavor = "current_thread")]` for `tracing_subscriber::set_default` capture tests, preventing thread-local subscriber state from leaking or dropping spans when Tokio tasks yield across multi-threaded runtime threads.
- **Config Contract Synchronization (`04.1-04-PLAN.md`)**: The plan updates both `REQUIRED_EFFECTIVE_RAG_KEYS` and the section matcher `matches!(section, ...)` in `engine/src/tests.rs:167-172` when introducing `engine.graph.max_hop_cap` and `engine.graph.seed_match_min_score`, preventing false-positive contract validation failures.

### Concerns

- **MEDIUM — Degenerate Min-Max Normalization on Empty Slices.** Location: `04.1-05-PLAN.md` (Task 1 action), `engine/src/prompt.rs`. Plan 05 specifies min-max normalizing `EvidenceBlock.score` and `GraphFactBlock.score` prior to weighting and interleaving. It explicitly guards against equal scores (`if max == min { 1.0 }`). However, if `evidence` is empty (e.g., retrieval returns zero candidates) or `graph_facts` is empty (e.g., seed match yields no graph neighborhood), calculating `min`/`max` on an empty slice without an `is_empty()` guard will cause an iterator panic (e.g., `.unwrap()` on `min_by`/`max_by` returning `None`). Impact: server panic inside `pack_evidence_and_graph_prompt` when handling queries that match zero chunk candidates or zero graph entities.
- **LOW — Unconditional Build Footprint Impact.** Location: `04.1-01-PLAN.md` (Task 1 action), `engine/Cargo.toml:28-35`, `engine/src/lib.rs:6-7`. Removing `optional = true` from `lance-graph` and deleting the `graph-spike` feature flag promotes `lance-graph` (and its ~350+ transitive dependencies) into the unconditional default build. Developer cold build times increase by 3–4 minutes — an acknowledged trade-off, but developers should be aware during local iteration.

### Suggestions

- Add explicit empty-slice pre-checks in `pack_evidence_and_graph_prompt` (in `engine/src/prompt.rs`), guarding both `evidence` and `graph_facts` before computing min/max, so empty inputs yield empty score vectors cleanly without panicking.
- Pre-allocate the string buffer in `escape_sql_literal` (`engine/src/graph/mod.rs`) — use a fast single-pass string builder instead of `value.replace('\'', "''")` to reduce temporary allocations during deep graph frontier expansion.

### Risk Assessment

**LOW.** Justification:
1. **Incremental Waves** — the phase is divided into 5 logically isolated waves: schema foundation (Wave 1), end-to-end tracer (Wave 2), hardening/concurrency (Wave 3), standalone RPC redesign (Wave 4), and score-interleaved prompt integration (Wave 5).
2. **Defensive Error Handling** — non-fatal fallback mechanisms are baked in: LLM extraction failure per chunk skips extraction without failing document ingestion (D-06); graph traversal failure silently degrades to chunk-only evidence (D-32); invalid input params yield clean gRPC `Status::invalid_argument` errors.
3. **Comprehensive Verification** — the plans contain exhaustive acceptance criteria, exact `grep` verification checks, TDD test definitions, and real HTTP wire-payload assertions that prevent silent degradation or broken contracts.

## Consensus Summary

The two reviewers agree closely on what is *well-designed* but diverge sharply on *overall risk* — Codex rates the phase **HIGH** risk, Antigravity rates it **LOW** risk. The divergence is not really a disagreement about the same evidence: each reviewer surfaced a materially different set of concerns, with almost no overlap between the two concern lists. Treat this as two independent, non-redundant passes rather than a confirmed/refuted split.

### Agreed Strengths

Both reviewers independently praised the same architectural decisions, each with matching file:line citations:

- **Dedicated `entity_edges` table separate from structural `edges`** (`engine/src/db/mod.rs`, `engine/src/main.rs`) — prevents chunk-sequence edges from mixing with knowledge-graph triples.
- **Directed edge orientation preserved from raw `entity_edges` batch** rather than reconstructed from an undirected Cypher match — avoids inverted-fact bugs.
- **IPC multi-batch fix in `engine/src/graph/bridge.rs`** (WR-01) — both flag the current `.next().transpose()` as silently dropping batches beyond the first, and both confirm Plan 03's fix is the correct remedy.
- **Reserve-one-citable-chunk packing rule** — both trace this to `ModelOutput::validate_grounding_with_limits`'s citation requirement and agree it correctly prevents graph facts from crowding out citable evidence.
- **Prompt-escaping enforced through a single `GraphFact::new()` constructor** — both cite this as closing an injection/delimiter-breakout risk (though Codex separately flags a serde bypass risk on the same mechanism — see below).

### Agreed Concerns

None of the concerns were raised by both reviewers at matching severity — each reviewer's finding set is distinct. This itself is a finding worth flagging: neither reviewer's concern list was a subset of the other's, so treat both as additive rather than confirmatory.

### Divergent Views

- **Overall risk verdict**: Codex says HIGH (blocking issues in Cypher contract compliance and re-ingestion data loss); Antigravity says LOW (only one MEDIUM panic risk and one LOW build-footprint note). Since the two reviewers examined largely non-overlapping concern surfaces, this is best read as "Antigravity's LOW verdict did not have visibility into the issues Codex found" rather than a genuine LOW-vs-HIGH disagreement on the same facts.
- **Codex-only findings** (not mentioned by Antigravity, all correctness/contract-level):
  - Cypher validation is diagnostic-only, not response-affecting, which may not satisfy DATA-05/D-19's stated requirement for Cypher-based traversal (HIGH).
  - Re-ingestion deletes prior `entity_edges` before extraction, with extraction failures swallowed and the document still marked completed — risking silent graph data loss (HIGH).
  - `graph_weight = 0` is documented as excluding graph facts but the packer implementation only deprioritizes them, so they can still appear in the prompt (MEDIUM).
  - Stale `source_chunk_ids` after re-ingestion can point to replacement content with different meaning, not just "old" content (MEDIUM).
  - Extraction retry/confidence-validation from the AI-SPEC is not reflected in the plans (MEDIUM).
  - `GenerationRequest`'s derived `Serialize`/`Deserialize` may let private `GraphFact` fields bypass the escaping constructor (MEDIUM).
  - System prompt policy ("ONLY the provided evidence blocks") is not reconciled with the new non-citable graph section (MEDIUM).
  - `QueryGraph`'s `seed_entity_name`/`relation_type_filter` lack length limits present on the existing QueryRAG path (MEDIUM).
- **Antigravity-only finding** (not mentioned by Codex, a correctness bug of its own):
  - Min-max score normalization in Plan 05 will panic on empty `evidence` or `graph_facts` slices — no `is_empty()` guard before `.unwrap()` on `min_by`/`max_by` (MEDIUM).

**Recommendation:** Given the near-zero overlap between reviewers, resolve findings from *both* lists before treating the phase as execution-ready — particularly Codex's two HIGH items (Cypher non-load-bearing vs. D-19/DATA-05 contract, and re-ingestion's delete-before-swallowed-failure data-loss path) and Antigravity's empty-slice panic, which is a straightforward crash bug independent of the risk-level disagreement.
