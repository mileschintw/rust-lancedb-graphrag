# Cross-AI Plan Review — Phase 04.1

Reviewed by Codex and Antigravity CLI as independent, source-grounded reviewers. Claude was excluded by design since this review was run from within Claude Code (self-review avoidance). Gemini, CodeRabbit, OpenCode, Qwen, and Cursor were not installed on this system (see `reviewers_unavailable` above).

## Codex Review

### Summary

The plans are unusually thorough and address real issues in the repository: schema separation, provider-payload capture, multi-batch IPC, bounded extraction, and typed graph queries. However, they are not execution-ready yet. Three high-risk gaps remain: production extraction-provider wiring is not explicitly completed, `graph_weight` cannot reach the actual OpenRouter prompt path as specified, and the QueryGraph hop-1/filter response semantics contradict the required contract. Overall risk is **HIGH**.

### Strengths

- **Plan 01** correctly separates entity relationships from existing chunk-structural edges. The current structural `edges` writes are in [engine/src/main.rs:1738](engine/src/main.rs:1738), so the dedicated `entity_edges` correction is materially safer than relying on ID conventions.
- The schema plan aligns with the existing fail-fast comparison in [engine/src/db/mod.rs:145](engine/src/db/mod.rs:145) and appropriately uses a blocking checkpoint for the one-way local-store reset.
- **Plan 02** tests the actual provider boundary rather than only an intermediate prompt string. This matches the existing TCP capture harness in [engine/src/generation/tests.rs:499](engine/src/generation/tests.rs:499) and the real outbound packing call in [engine/src/generation/openrouter.rs:358](engine/src/generation/openrouter.rs:358).
- **Plan 03** correctly identifies the real bridge defect: both current bridge functions read only the first IPC batch at [engine/src/graph/bridge.rs:28](engine/src/graph/bridge.rs:28) and [engine/src/graph/bridge.rs:60](engine/src/graph/bridge.rs:60). The keyed fake and non-fail-fast collection design are appropriate.
- **Plan 04** avoids the impossible variable-hop Cypher property correlation approach by serving responses from the induced neighborhood. Keeping QueryGraph gRPC-only also matches the current gateway boundary.
- **Plan 05** preserves the important "at least one citable chunk" invariant and recognizes that graph facts must compete for a shared budget rather than silently bypassing prompt limits.

### Concerns

- **HIGH — Plan 02 does not explicitly wire the real extraction provider into production.** The current worker is created at [engine/src/main.rs:2024](engine/src/main.rs:2024), before the OpenRouter generation provider is constructed at [engine/src/main.rs:2051](engine/src/main.rs:2051). The worker currently accepts only an embedder at [engine/src/main.rs:1864](engine/src/main.rs:1864), and `LancetServiceImpl` has no extraction provider at [engine/src/main.rs:804](engine/src/main.rs:804). Plan 02 adds the trait and test fake, but does not specify constructing `OpenRouterExtractionGenerator` from the live settings and passing it into the worker. Without that step, the end-to-end tests could pass while real ingestion performs no extraction.
- **HIGH — Plan 05's `graph_weight` has no complete path to the actual provider request.** The current `GenerationRequest` has no weight or prompt-settings field at [engine/src/generation/mod.rs:375](engine/src/generation/mod.rs:375), and OpenRouter invokes the packer directly at [engine/src/generation/openrouter.rs:358](engine/src/generation/openrouter.rs:358). Plan 05 requires the same packer signature and does not list `generation/mod.rs` or `generation/openrouter.rs` in `files_modified`. Main-side packing could use one weight while the actual outbound request uses another. Pass a prompt-assembly settings object or `graph_weight` through `GenerationRequest`, and add a raw HTTP test proving the configured value affects the provider body.
- **HIGH — Plan 04's hop-1 exception cannot satisfy its own response contract.** The existing Cypher projection at [engine/src/graph/mod.rs:121](engine/src/graph/mod.rs:121) returns only seed ID, relation type, neighbor ID, and neighbor name. It does not provide `entity_type`, the original edge orientation, or a complete seed node row. Because the pattern is undirected, a seed that is stored as the target can be returned as the apparent source. The plan's "build the response from `traverse_fixed_hop`" exception conflicts with its requirements that the response include the seed and preserve `source_entity_id`/`target_entity_id`. Build the API response from `fetch_neighborhood` consistently; use Cypher only as an additional validation/demo call.
- **HIGH — Plan 04's relation-filter semantics are contradictory.** Its test requires only the matching edge and its connected nodes, while the implementation says `nodes` should contain every row from the unfiltered `entities_batch`. For a two-hop path where the first edge does not match but the second does, post-filtering edges leaves unrelated nodes or a disconnected retained edge. Define whether filtering restricts traversal or only filters the returned induced subgraph, then make node selection and tests match that definition.
- **HIGH — Plan 02's prompt escaping is convention-based, not enforced.** The plan makes `GraphFact` fields public but says they are escaped before construction. Its own test uses a raw struct literal in [04.1-02-PLAN.md:133](04.1-02-PLAN.md:133). A caller can bypass the convention, and `assemble()` is explicitly not supposed to escape again. Make fields private and expose an escaping constructor/newtype; retain render-time escaping as defense in depth.
- **MEDIUM — Invalid QueryGraph seed IDs may map to `internal` instead of `invalid_argument`.** Plan 02 specifies malformed UUIDs as a `Bridge` error at [04.1-02-PLAN.md:144](04.1-02-PLAN.md:144), while Plan 04 maps only `InvalidHopCap` to `invalid_argument` and everything else to `internal` at [04.1-04-PLAN.md:121](04.1-04-PLAN.md:121). Add a distinct invalid-seed error kind or validate in the handler.
- **MEDIUM — The planned name lookup cannot directly reuse the proposed helper.** Plan 02 describes `escape_sql_literal` as a local helper in `graph/mod.rs`, while Plan 04 calls it from `main.rs`. The existing equivalent in [engine/src/retrieval/dense.rs:158](engine/src/retrieval/dense.rs:158) is private. Also, the schema has only `name`; a case-folded exact lookup requires an in-memory scan or a persisted normalized-name column. Specify that mechanism and duplicate-name behavior.
- **MEDIUM — Traversal bounds cap frontier size but not edge count.** A high-degree seed can return an arbitrarily large edge batch before the next frontier check. Add per-hop and total node/edge limits, with explicit failure rather than relying only on the `MAX_FRONTIER_SIZE` rule.
- **MEDIUM — Plan 03 does not prove the concurrency bound.** Its acceptance criteria only grep for `buffer_unordered(5)` at [04.1-03-PLAN.md:93](04.1-03-PLAN.md:93). Add a fake generator that tracks current and maximum in-flight calls and assert the observed maximum is five or less.
- **MEDIUM — Plan 05's sequential citation-marker claim conflicts with current implementation.** IDs are assigned from the original candidate index at [engine/src/prompt.rs:35](engine/src/prompt.rs:35), and the current packer preserves input IDs while iterating at [engine/src/prompt.rs:226](engine/src/prompt.rs:226). Reserving the highest-scoring candidate first will not automatically produce `[1]`, `[2]`, etc. Either remap IDs and all grounding references during packing or preserve stable IDs and weaken the sequential-marker requirement.
- **MEDIUM — The tracing observability test assumes a span that does not currently exist.** `query_rag` starts at [engine/src/main.rs:1093](engine/src/main.rs:1093), but the current explicit spans are for indexing/embedding work, not the query request. Plan 02 says to record a field on "the request's tracing span," but does not specify creating a span with an `Empty` field. Add an explicit query span and use an async-safe capture test.
- **MEDIUM — Plan 04's config completeness work is incomplete as written.** The current config test only observes `engine.retrieval`, `engine.retrieval.bm25`, and `openrouter` at [engine/src/tests.rs:168](engine/src/tests.rs:168). Adding `engine.graph` keys to the required-key arrays without updating this section matcher will not validate the new section. The manual `EngineSettings` fixtures at [engine/src/tests.rs:652](engine/src/tests.rs:652) and `:2462` also need explicit updates.
- **MEDIUM — Plan 02's file manifest omits a file it explicitly modifies.** Its Test 3 is specified in `engine/src/graph/tests.rs` at [04.1-02-PLAN.md:129](04.1-02-PLAN.md:129), but that file is absent from the plan's `files_modified` list. This conflicts with the plan's own "diff touches only listed files" verification.
- **LOW — Plan 01's grep acceptance criterion is impossible literally.** The current `communities_schema()` also contains `summary_vector` at [engine/src/db/mod.rs:225](engine/src/db/mod.rs:225), but the acceptance text says matches should occur only in entities, edges, and entity_edges. Narrow the grep to node-batch construction sites.
- **LOW — Requirements documentation needs reconciliation.** `REQUIREMENTS.md` still describes `community_ids` and summary fields as belonging to `nodes`, while the phase plans intentionally move them to `entities`. Update the requirement wording or traceability artifact so later audits do not report a false schema mismatch.

### Suggestions

- Add an explicit Plan 02 task for constructing and wiring `OpenRouterExtractionGenerator` in `main()`, including its endpoint, model, timeout, API key, and startup behavior.
- Make `GraphFact` construction enforce escaping through private fields or an escaping constructor, then test the constructor-to-provider path.
- Rewrite Plan 04 so `fetch_neighborhood` is the sole source of API nodes and edges, define relation-filter semantics precisely, and add tests for preserved edge orientation and malformed seed status.
- Thread a shared prompt-assembly configuration through `GenerationRequest` so `main.rs` and `openrouter.rs` cannot diverge on `graph_weight`, normalization, or budget behavior.
- Add runtime tests for maximum extraction concurrency, high-degree graph limits, non-finite/out-of-range relation confidence, and actual outbound prompt behavior with `graph_weight = 0`.

### Risk Assessment

**Overall: HIGH.**

The architecture and decomposition are strong, but the remaining issues affect the actual runnable path and public RPC behavior. Until provider construction, prompt-weight propagation, and QueryGraph response semantics are made explicit and tested against the real request boundary, the phase could produce green isolated tests while failing to deliver production ingestion or returning incorrect graph edges.

## Antigravity Review

### Summary

The 5-plan execution sequence for Phase 04.1 (**Knowledge Graph Extraction & Query (Full Implementation)**) provides a disciplined, wave-structured roadmap that transitions the Phase 04 PoC spike into a production-grade component of the Lancet data plane. The plan set directly incorporates feedback from previous reviews (`04.1-REVIEWS.md`), addressing critical edge cases such as IPC multi-batch stream truncation (WR-01), Cypher variable-length relationship projection limitations (Pitfall 6), prompt escaping boundary security, and grounding validation invariants (`cited_evidence_ids`). By separating chunk-structural edges (`edges`) from entity-to-entity graph relationships (`entity_edges`), introducing seed-inclusive neighborhood expansion, and enforcing reserve-one-citable-chunk evidence packing, the plans guarantee system correctness, fail-open resiliency, and observability without corrupting existing Phase 02/03 contracts.

### Strengths

- **Structural Table Separation for Graph Integrity**: Plan 01 (`04.1-01-PLAN.md`) introduces a dedicated `entity_edges` LanceDB table alongside the new `entities` table (`engine/src/db/mod.rs:257-265`). This structurally isolates entity relationships from chunk-structural edges (`next_chunk`/`same_section`) written by `replace_document_with_faults` (`engine/src/main.rs:1552`), avoiding reliance on runtime ID-space disjointness conventions.
- **Resolution of Cypher Variable-Hop Correlation Limitations**: Plan 04 (`04.1-04-PLAN.md`) re-architects `QueryGraph` as an induced-neighborhood query served directly from `fetch_neighborhood`'s accumulated batches. This avoids the mathematical impossibility of correlating multi-hop Cypher path matches back to intermediate edge properties (Pitfall 6), while keeping fixed single-hop Cypher queries (`traverse_fixed_hop` in `engine/src/graph/mod.rs:94-135`) for 1-hop requests.
- **Strict Adherence to Grounding Validation Invariants**: Plan 02 (`04.1-02-PLAN.md`) and Plan 05 (`04.1-05-PLAN.md`) mandate a "reserve-one-citable-chunk" packing rule in `pack_evidence_and_graph_prompt` (`engine/src/prompt.rs`). This guarantees that whenever chunk evidence exists, at least one `EvidenceBlock` survives token budget bounding, ensuring `ModelOutput::validate_grounding_with_limits` (`engine/src/generation/mod.rs:191-199`) never fails with an empty `cited_evidence_ids` list.
- **Multi-Batch IPC Stream Correctness (WR-01 Fix)**: Plan 03 (`04.1-03-PLAN.md`) refactors `bridge_batch` and `bridge_batch_back` in `engine/src/graph/bridge.rs:30-35,62-67` with a shared `decode_all_batches` helper, eliminating silent data truncation when Arrow IPC streams emit multiple record batches.
- **Comprehensive Defense-in-Depth Security**: Across all plans, untrusted entity content is HTML-entity escaped at construction (`escape_evidence_delimiters` in `engine/src/prompt.rs:182-184`), seed entity inputs are UUID-validated (`Uuid::parse_str`), SQL predicates are string-escaped, and hop depths are strictly clamped (`clamp_hop_cap_with_ceiling` in `engine/src/graph/mod.rs:73-81`).

### Concerns

- **[LOW] Ingestion Worker Concurrency Assumption vs. Table Version Rollback**
  - **Location**: `engine/src/main.rs:1500-1509` & `engine/src/main.rs:1884-1940` (`spawn_worker_with_boundary`)
  - **Context**: Plan 02 specifies that `extract_and_persist_entities` will capture `version()` of `entities_table()` and `entity_edges_table()` prior to mutations, and call `restore_version` on internal errors. The plan notes this is safe because ingestion is serialized through a single worker task.
  - **Risk**: While `spawn_worker_with_boundary` currently processes jobs sequentially via a single `mpsc::Receiver` loop (`engine/src/main.rs:1893-1918`), if a future phase spawns multiple concurrent ingestion workers without updating table-level version rollback handling, `table.restore()` calls could revert concurrent writes from other workers.
  - **Mitigation**: Add a code comment inside `extract_and_persist_entities` documenting that LanceDB table-version checkout/restore assumes single-worker serialization during document ingestion.
- **[LOW] Degenerate Min-Max Normalization Guard in Score Interleaving**
  - **Location**: `engine/src/prompt.rs` (Plan 05 Task 1)
  - **Context**: Plan 05 specifies min-max normalization (`[0.0, 1.0]`) for `EvidenceBlock` scores and `GraphFact` scores before merging.
  - **Risk**: If all returned `EvidenceBlock`s or all `GraphFact`s have identical raw scores (e.g., single item or uniform scores where `max == min`), naive min-max division `(score - min) / (max - min)` will produce `NaN`.
  - **Mitigation**: Ensure the implementation explicitly checks `if max == min { 1.0 } else { (score - min) / (max - min) }`, as specified in Plan 05's task instructions.

### Suggestions

1. **Verify `tests.rs` Access to `bridge` Module Visibility**: In Plan 01 Task 1, `pub mod bridge;` in `engine/src/graph/mod.rs:18` is changed to `pub(crate) mod bridge;`. Confirm that `engine/src/graph/tests.rs` (which is a submodule of `graph`) retains full access to `bridge` functions without requiring `pub` visibility.
2. **Explicit Verification of `MIN_CHUNK_CONTENT_LENGTH`**: Ensure the skip check in `extract_and_persist_entities` (`engine/src/main.rs`, Plan 03) evaluates `chunk.content.trim().len() < MIN_CHUNK_CONTENT_LENGTH` using UTF-8 character length or byte length consistently with existing chunking metrics.

### Risk Assessment

- **Overall Risk Level**: **LOW**
- **Justification**: The implementation plan set is exceptionally thorough, highly aligned with the architectural specifications in `04.1-AI-SPEC.md` and `04.1-CONTEXT.md`, and incorporates concrete mitigations for all known security, schema-drift, and data-loss edge cases. All code changes maintain backwards compatibility with existing Phase 02/03 contracts while establishing complete test coverage across every wave.

## Consensus Summary

### Agreed Strengths

- Both reviewers endorse the **Plan 01 schema restructure**: splitting entity relationships into a dedicated `entity_edges` table, separate from the pre-existing chunk-structural `edges` table, removes reliance on ID-space conventions and is grounded in the same `engine/src/db/mod.rs` schema-validation code.
- Both reviewers confirm **Plan 03's multi-batch IPC bridge fix** correctly targets a real defect — the current bridge functions only read the first Arrow IPC batch (`engine/src/graph/bridge.rs`), and the proposed shared-decode-helper approach is sound.
- Both reviewers confirm **Plan 04's redesign of `QueryGraph`** as an induced-neighborhood query (served from `fetch_neighborhood`) correctly sidesteps the underlying impossibility of recovering multi-hop edge properties from Cypher's variable-length path projection.
- Both reviewers cite **Plan 02/05's evidence-packing and escaping mechanisms** favorably in principle (reserve-one-citable-chunk invariant, defense-in-depth escaping of entity-derived content).

### Agreed Concerns

None of the specific findings fully overlap — Codex's HIGH-severity findings are about contract-level gaps (production wiring, `graph_weight` propagation, QueryGraph hop-1/filter semantics, escaping enforcement) that Antigravity's review did not flag at all. This is itself a signal: Antigravity's LOW-risk assessment did not verify the same call chains Codex traced (e.g., whether `OpenRouterExtractionGenerator` is actually constructed and passed to the ingestion worker in `main.rs`, or whether `graph_weight` reaches `GenerationRequest`/`openrouter.rs`). Codex's findings are more heavily source-grounded with specific line citations proving absence of wiring, and should be treated as the higher-confidence assessment where the two reviews diverge.

### Divergent Views

- **Overall risk rating diverges sharply: HIGH (Codex) vs. LOW (Antigravity).** Codex traced concrete call sites showing the extraction provider is never constructed/wired into the ingestion worker, `graph_weight` has no field on `GenerationRequest` to reach the OpenRouter provider, and `QueryGraph`'s hop-1 exception path cannot produce the fields its own contract requires. Antigravity's review credits the same plans' *stated* mitigations (escaping, version-rollback, min-max normalization) without tracing whether the production wiring for extraction/`graph_weight` actually exists in `main.rs`/`generation/mod.rs`. Given Codex's citations are specific and falsifiable (file:line pairs showing missing fields/wiring), **the HIGH-risk findings should be treated as blocking** until independently verified against the plan text and, ideally, resolved in a replan before execution.
- Codex flags Plan 04's relation-filter semantics as contradictory (filtered edges vs. unfiltered node set) and its hop-1 exception as violating its own response contract — findings Antigravity did not surface. These are concrete, falsifiable claims worth verifying directly against `04.1-04-PLAN.md` before treating the plan as execution-ready.
- Codex additionally flags several MEDIUM/LOW documentation and test-coverage gaps (error-code mapping consistency, config-test completeness, file-manifest omissions, `REQUIREMENTS.md` reconciliation) that Antigravity's review did not address at that level of granularity.
