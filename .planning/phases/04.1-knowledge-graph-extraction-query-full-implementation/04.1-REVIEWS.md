# Cross-AI Plan Review — Phase 04.1

Only Codex was available as an independent, source-grounded reviewer this run (see `reviewers_unavailable` above for why Gemini and Antigravity were skipped). Claude was excluded by design since this review was run from within Claude Code (self-review avoidance).

## Codex Review

## Summary

The four plans have a strong architectural direction and sensible wave ordering, but they are not implementation-ready. Several source-level blockers would prevent the phase from delivering its stated end-to-end behavior: graph context is currently repacked away before the LLM call, `fetch_neighborhood` would omit the seed row required by the existing Cypher traversal, the shared `edges` table still contains chunk-structural edges despite the entity-only contract, and the proposed variable-hop relation recovery cannot recover path edges from the current Cypher result. Overall risk is **HIGH** until these contracts and test seams are corrected.

## Strengths

### Plan 01

- The schema checkpoint is appropriate for a one-way LanceDB change. The current database validates exact schemas and fails on drift at [engine/src/db/mod.rs:145](engine/src/db/mod.rs:145), so explicitly confirming the restructure before implementation is good process.
- The tracer test is the right shape: it attempts to prove real ingestion, persistence, traversal, prompt assembly, and fail-open behavior rather than validating only isolated synthetic fixtures.
- The plan correctly treats extraction as additive and non-fatal, and the current worker processes jobs through a single loop at [engine/src/main.rs:1934](engine/src/main.rs:1934), which supports the proposed serialized corpus mutation invariant.
- Escaping graph-derived values using the existing prompt boundary is sound. `EvidenceBlock` already escapes untrusted fields through `encode_field_value` at [engine/src/prompt.rs:91](engine/src/prompt.rs:91).

### Plan 02

- The explicit distinction between `collect` and `try_collect` is correct. Existing embedding code uses bounded concurrency with `buffer_unordered` at [engine/src/client/mod.rs:218](engine/src/client/mod.rs:218), but extraction must preserve individual failures rather than aborting the whole batch.
- Treating WR-01 as a correctness issue is justified. Both bridge functions currently read only the first decoded batch at [engine/src/graph/bridge.rs:28](engine/src/graph/bridge.rs:28) and [engine/src/graph/bridge.rs:60](engine/src/graph/bridge.rs:60).
- The plan covers useful production properties—short-content skipping, bounded concurrency, cross-document exact-match merging, and re-ingestion testing.

### Plan 03

- Replacing the raw `query`/`result_json` stub with typed protobuf messages is aligned with the project's service-boundary goals. The current stub is visible in `proto/lancet/v1/lancet.proto:113` and `:118`.
- Keeping QueryGraph gRPC-only is consistent with the current gateway interface, which exposes query RAG but no graph HTTP route at [gateway/main.go:207](gateway/main.go:207).
- Retaining the existing `clamp_hop_cap` behavior and adding a configurable ceiling is a good defense-in-depth design.
- The plan correctly identifies the variable-length Cypher relationship-property limitation and attempts to preserve relation metadata rather than silently returning incomplete edges.

### Plan 04

- A shared evidence budget and score-based interleaving are better aligned with the locked D-29/D-30 decisions than Plan 01's append-only graph section.
- Testing `graph_weight = 0` is valuable because it proves the setting changes behavior rather than merely appearing in configuration.
- Preserving graph facts as non-citable content respects the existing citation identity contract. Current validation requires cited evidence IDs at [engine/src/generation/mod.rs:177](engine/src/generation/mod.rs:177).
- The three-way outcome tagging is a useful observability contract, provided it is moved into a testable abstraction.

## Concerns

### Plan 01

- **HIGH — The planned traversal drops the seed row that the existing Cypher traversal requires.** The plan says `fetch_neighborhood` should return visited entities "minus the seed," but `traverse_fixed_hop` builds a Cypher query matching a seed entity from the supplied entities batch at [engine/src/graph/mod.rs:94](engine/src/graph/mod.rs:94) and [engine/src/graph/mod.rs:120](engine/src/graph/mod.rs:120). If the seed is absent, the query cannot match it and the planned end-to-end graph augmentation returns no facts. Either include the seed in the bridged entity batch or redesign traversal to receive the seed separately.

- **HIGH — Graph prompt text will not reach the actual LLM call.** The current query path packs evidence and then constructs `GenerationRequest` from only `packed_evidence.evidence` at [engine/src/main.rs:1272](engine/src/main.rs:1272) and [engine/src/main.rs:1280](engine/src/main.rs:1280). OpenRouter subsequently repacks the request from `request.evidence` at [engine/src/generation/openrouter.rs:358](engine/src/generation/openrouter.rs:358) and sends that newly packed prompt at [engine/src/generation/openrouter.rs:372](engine/src/generation/openrouter.rs:372). Appending graph facts to the prompt in `main.rs` therefore does not affect the real generation request. The generation contract/provider must be changed, or graph facts must be passed as first-class input to the provider's packing path.

- **HIGH — The entity-only edge contract conflicts with existing storage behavior.** The current ingestion replacement writes `next_chunk` and `same_section` rows into the shared `edges` table at [engine/src/main.rs:1738](engine/src/main.rs:1738) and [engine/src/main.rs:1740](engine/src/main.rs:1740). Plan 01 leaves those rows in the same table and relies on UUID/chunk-ID disjointness to make them inert. That may prevent accidental traversal, but it does not satisfy D-13's claim that edge endpoints reference entity IDs only. Use separate structural/entity edge tables, or add and consistently enforce an edge-kind discriminator.

- **HIGH — The schema change omits several current fixtures and tests.** The database test expects exactly five table names at [engine/src/db/tests.rs:42](engine/src/db/tests.rs:42), while the plan adds a sixth table. Multiple fixtures still construct the old node schema, including [engine/src/bin/seed_rag_fixture.rs:151](engine/src/bin/seed_rag_fixture.rs:151), [engine/src/inspect_lancedb_tests.rs:148](engine/src/inspect_lancedb_tests.rs:148), and [engine/src/retrieval/tests.rs:171](engine/src/retrieval/tests.rs:171). These files are not included in Plan 01's modification list, so the claimed full-suite green result is unlikely without an explicit schema-fixture migration task.

- **MEDIUM — The proposed forced traversal-error test has no injection seam.** `DatabaseManager` is a concrete type at [engine/src/db/mod.rs:9](engine/src/db/mod.rs:9), and `LancetServiceImpl` currently stores concrete database state at [engine/src/main.rs:804](engine/src/main.rs:804). A "fault-injecting DatabaseManager wrapper" cannot be introduced without changing the abstraction. Add a graph repository/provider trait or test the augmentation helper with injected closures/results.

- **MEDIUM — Seed matching has no defined threshold or score contract.** Existing dense retrieval performs nearest-neighbor search and limits results at [engine/src/retrieval/dense.rs:59](engine/src/retrieval/dense.rs:59) and [engine/src/retrieval/dense.rs:85](engine/src/retrieval/dense.rs:85), but Plan 01 introduces a "match above a similarity threshold" without defining the threshold, distance semantics, or configuration. Without this, any non-empty entity table may produce an arbitrary graph augmentation.

- **LOW — "Bump the schema version" does not match the current implementation.** The source currently performs exact schema validation but has no explicit schema-version field or migration registry. The plan should either add such a mechanism or state that this is a documented manual store-reset boundary, not a version bump.

### Plan 02

- **HIGH — The idempotency test does not exercise the actual replacement boundary and would leave duplicate edges.** Plan 02 proposes calling `extract_and_persist_entities` twice directly. The existing document replacement deletes document edges at [engine/src/main.rs:1589](engine/src/main.rs:1589), but the extraction helper itself is described as inserting new entity-relation edges. Calling it twice without the replacement delete step will create duplicate edge rows even if entity rows deduplicate. Test the complete replacement/worker path and assert both entity and edge counts.

- **MEDIUM — The queued fake generator cannot reliably fail a specific chunk under concurrency.** The existing fake removes queued responses in order at [engine/src/generation/mod.rs:498](engine/src/generation/mod.rs:498). With `buffer_unordered(5)`, response consumption follows completion order, not chunk index. A test claiming "chunk 3 fails" is nondeterministic unless the fake is keyed by `chunk_id` or supports a request-aware callback/delay.

- **MEDIUM — The bridge test cannot produce two batches through the current public API.** Each bridge function writes exactly one batch before finishing at [engine/src/graph/bridge.rs:19](engine/src/graph/bridge.rs:19) and [engine/src/graph/bridge.rs:51](engine/src/graph/bridge.rs:51). The proposed test says to perform two writes, but the current API provides no way to do that. Introduce a private encode/decode helper usable by the test, or construct a two-batch IPC stream explicitly. Also resolve the plan's inconsistency between "all rows from both batches" and the alternative "explicitly reject a second batch."

- **MEDIUM — Re-ingestion semantics for stale entities are only partially specified.** The plan accepts entities becoming inert after their source document is replaced, but it should explicitly define whether `source_chunk_ids` are pruned, whether an entity with no remaining sources is retained, and whether future seed matching should exclude source-less entities. Otherwise the "benign limitation" can become confusing operator behavior.

### Plan 03

- **HIGH — Pitfall-6 correlation cannot recover multi-hop path relations as specified.** The current variable-hop traversal returns only the seed/final-neighbor endpoint pair and neighbor name at [engine/src/graph/mod.rs:171](engine/src/graph/mod.rs:171). For `seed → neighbor1 → neighbor2`, the returned pair is not the pair of either edge in the path. Correlating that pair against `edges_batch` cannot recover the `seed→neighbor1` and `neighbor1→neighbor2` relation properties. Define QueryGraph as returning the induced neighborhood's actual edges, or return path/adjacency information sufficient to enumerate the traversed edges.

- **HIGH — Relation filtering ignores requested hop depth.** `traverse_filtered_by_relation_type` is a fixed single-hop query at [engine/src/graph/mod.rs:198](engine/src/graph/mod.rs:198) and [engine/src/graph/mod.rs:218](engine/src/graph/mod.rs:218). Plan 03 says to use it when a filter is present even when `hop_depth > 1`, which would silently return only one hop. Add a filtered multi-hop traversal or prefilter the fetched edge batch before the multi-hop operation.

- **HIGH — Caller-controlled entity IDs are interpolated into planned LanceDB predicates without a stated escaping/validation rule.** Hop-cap validation protects the Cypher hop value, but not the seed/frontier IDs used in `source_node_id IN (...) OR target_node_id IN (...)`. Existing retrieval code explicitly escapes SQL literals at [engine/src/retrieval/dense.rs:143](engine/src/retrieval/dense.rs:143) and [engine/src/retrieval/dense.rs:158](engine/src/retrieval/dense.rs:158). Require strict UUID validation for IDs, safe literal escaping for names/filters, and bounded frontier sizes.

- **MEDIUM — QueryGraph response semantics are underspecified.** It is unclear whether `nodes` includes the seed, all visited nodes, only direct neighbors, or only Cypher-returned nodes. This ambiguity directly affects the relation-property recovery algorithm and client expectations. Lock the response semantics before implementing tests.

- **MEDIUM — Configuration and test fallout is not included in the plan.** Adding graph settings requires updating `EngineSettings`, defaults, configuration examples, and exact configuration assertions. Existing config tests enumerate required keys at [engine/src/tests.rs:192](engine/src/tests.rs:192), while the example currently ends with retrieval weights at [config/config.example.toml:26](config/config.example.toml:26). These files are not listed in Plan 03's frontmatter.

### Plan 04

- **HIGH — The graph-only packing test conflicts with the existing citation contract.** `pack_evidence_prompt` rejects empty evidence at [engine/src/prompt.rs:203](engine/src/prompt.rs:203), and generation validation requires at least one cited evidence ID at [engine/src/generation/mod.rs:177](engine/src/generation/mod.rs:177). A test that allows a high-scoring graph fact to exclude the only chunk evidence cannot produce a valid answer under the current contract. Either reserve at least one citable chunk, or explicitly redesign the answer-validation contract for graph-only responses.

- **HIGH — Outcome tagging will not occur for every query.** The current query path returns early when `final_candidates` is empty at [engine/src/main.rs:1229](engine/src/main.rs:1229), before the planned graph augmentation block. This violates the "every `/rag/query` call" requirement unless graph seed matching is moved earlier or the requirement is narrowed to queries that already have chunk evidence.

- **HIGH — Graph scores are not actually produced by Plans 01–03.** The existing fixed-hop query projects `relation_type` but not `weight` at [engine/src/graph/mod.rs:110](engine/src/graph/mod.rs:110) and [engine/src/graph/mod.rs:120](engine/src/graph/mod.rs:120). Plan 04 introduces `GraphFact.score` and normalized interleaving without defining whether the score is entity similarity, edge weight, path score, or a combination. The ranking tests cannot be meaningful until this is specified and propagated.

- **MEDIUM — `graph_weight` needs the same validation discipline as existing retrieval weights.** Retrieval settings validate finite, nonnegative, bounded weights at [engine/src/retrieval/mod.rs:288](engine/src/retrieval/mod.rs:288). Plan 04 only specifies a default and a zero-weight test; it should reject NaN, infinity, negative values, and excessively large values.

- **MEDIUM — Precomputed summaries may bypass the prompt escaping boundary.** The plan requires escaping entity names and relation types, but `PrecomputedSemantics` can render `edge_summary`. Existing escaping is explicit for evidence fields through [engine/src/prompt.rs:91](engine/src/prompt.rs:91) and [engine/src/prompt.rs:107](engine/src/prompt.rs:107). Summary text must use the same escaping before it enters `<GRAPH_FACT>`.

- **MEDIUM — The outcome-tag tests lack a reliable observation mechanism.** The current service has no injected tracing collector or graph provider. Add a helper that returns a typed `GraphAugmentationOutcome` and separately records it, allowing deterministic unit tests for `succeeded`, `no_match_found`, and `attempted_and_failed`.

## Suggestions

- Resolve the storage model before implementation: separate structural chunk edges from entity-relation edges, or add an explicit edge-kind column and make every traversal/filter/delete path enforce it.
- Redesign graph prompt plumbing end-to-end. Graph facts must be first-class input to `GenerationRequest` or to the OpenRouter packing function; add a test that captures the final provider user message, not merely an intermediate prompt string.
- Make `fetch_neighborhood` include the seed row, or change the traversal API so the seed is not required in the bridged batch. Then define whether returned nodes are seed-inclusive.
- Define QueryGraph as an induced neighborhood response if relation properties are required. Return the actual fetched edge rows after applying hop and relation filters, rather than trying to infer path edges from final-node pairs.
- Add strict input handling for graph predicates: UUID validation for IDs, escaped literals for names and relation filters, maximum frontier/edge counts, and a configurable seed similarity threshold.
- Replace the queued extraction fake with a request-aware fake keyed by `chunk_id`; expose in-flight/max-concurrency counters so D-09 is directly tested.
- Test idempotency through the complete replacement workflow and assert entity rows, edge rows, and `source_chunk_ids`.
- Expand the schema-change inventory to include `engine/src/db/tests.rs`, retrieval fixtures, seed/inspection binaries, startup config tests, `config/config.example.toml`, and every direct `EngineSettings`/`RetrievalConfigSettings` literal.
- Split multi-filter Cargo verification into separate commands or use one shared test-name pattern; the plans currently show multiple positional test filters in a single `cargo test` command.
- Define and validate the graph ranking formula before Plan 04: seed similarity, edge weight, path distance, normalization, tie-breaking, and behavior when all scores are equal.

## Risk Assessment

**Overall: HIGH.**

The plans are conceptually coherent, but the highest-value path—ingest, retrieve, traverse, and generate with graph context—currently has incompatible interfaces. Plan 01 has multiple blockers, so Plans 02–04 would otherwise harden or extend a path that does not yet reach the LLM. Plan 02 is medium-to-high risk due to nondeterministic concurrency tests and incomplete edge idempotency. Plan 03 is high risk because its multi-hop response algorithm does not match the current traversal output and its planned predicates need stronger input validation. Plan 04 is high risk because graph-only budget behavior conflicts with mandatory citation validation and because ranking scores are not yet defined.
