## 06.3.4-01

### Summary

This plan correctly identifies a real latch that would otherwise make D-44’s staged-then-full design unpublishable: `Journal.write_header` writes only on a new/empty file (`eval/src/lancet_eval/journal.py:113-124`), `score_run` copies `header.partial` into metadata and skips `report.json` (`eval/src/lancet_eval/score.py:151-153, 1065-1069`), and both `render_markdown` / `render_json` raise on that flag (`eval/src/lancet_eval/report.py:149-153, 190-194`). The `score` command then calls `render_markdown` unconditionally (`eval/src/lancet_eval/cli.py:348-355`). Routing `staged-gate` through `score_run`’s return value, committing floors before any staged number exists, and reconciling the header in one direction only are the right machinery. The live-drive half is not safe as written: default `--resume` will select the superseded 2026-09-03 directory, and that check is scheduled after the first paid write.

### Strengths

- The latch diagnosis matches the code path. `write_header` is a one-shot (`journal.py:115-124`); a `--limit` drive stamps `partial=True` on the header (`eval/src/lancet_eval/run.py:173, 192`) and on every record (`run.py:139`). `score` cannot render that journal; `score_run` still returns a full `CorpusReport`. Building `staged-gate` on the returned object is the only way to gate a staged prefix.
- Completeness-via-cross-product is the right predicate. `drive` already builds `questions × config.arms` (`run.py:177-180`) and `load_done` already keys `(corpus, question_id, graph_arm)` (`journal.py:70-72, 75-103`). Reusing `load_done` for the comparison keeps resume and publication in agreement, including on unparseable lines (`journal.py:101-102`).
- Atomic header rewrite via `eval/runs/**/journal.jsonl.tmp` (`.gitignore:130`) is the tree’s existing idiom. Leaving per-record `partial` flags alone is correct: those flags are the only stage-attribution after merge (`run.py:139, 230`).
- Decision inputs are locked as comparisons, not predictions, with boundary semantics spelled as operators (`>= 0.80` coverage, `>= 0.20` yield, `> 0.80` complement). Caps are to be read from `06.3.3-BUDGETS.md` rather than restated — that file now exists and names staged `$2.00`, full `$5.00`, judging `$5.00`.
- Absent dimension/detail keys halt rather than default. After 06.3.2, the names are no longer hypothetical: pairing coverage is `graph_ablation_delta.detail.pairing_coverage` (`eval/src/lancet_eval/dimensions.py:104-106`); graph presence is dimension `graph_presence_rate` with complement `detail.no_match_rate` (`dimensions.py:519-527`).

### Concerns

- **HIGH — Default resume selects the superseded run.** `resolve_run_dir` with `resume=True` (the `run` default, `cli.py:256-262`) returns the lexicographically newest `????-??-??-{corpus}` directory (`cli.py:222-227`). `eval/runs/2026-09-03-multihop_rag/` exists and matches that glob. A first `lancet-eval run --resume` therefore appends to the D-45 evidence directory; `write_header` is a no-op on a non-empty file (`journal.py:115`), so the old header is kept and new records are appended. Task 1 tells the executor to “confirm the run directory the resume resolver will pick” and then drive into it, and Task 3 — the preconditions ledger that would record this — runs *after* that live write. `git diff --quiet` on that directory is a detection after damage, not a prevention.
- **HIGH — No fail-closed spend cap on `run`.** `06.3.3-BUDGETS.md` (Go/no-go, per-stage caps) requires each 06.3.4 paid driver to take `--stage-cap` “with no silent default.” That flag exists only on `lancet-eval measure` (`cli.py:746-752, 778`) and is enforced mid-loop in `measure.py:507-514`. `run_benchmark` has no such option (`cli.py:230-271`). This plan’s artifact table forbids new flags on `run`. Watching spend in a summary is not the fail-closed stop `measure` already implements.
- **MEDIUM — Tracer field names do not match `WorkflowWireMeta`.** Task 1’s acceptance criteria ask for “graph presence and graph influence fields present as keys.” `WorkflowWireMeta` carries `graph_node_count`, `graph_edge_count`, and `graph_prompt_fact_count` (`journal.py:28-42`). Presence/influence are *scored* from those counts in `dimensions.py:478-482, 575-576`, not stored under those names. A literal key check on the micro-slice journal will fail on a healthy wire.
- **MEDIUM — Stale `read_first` line numbers, and the latch is cited on the wrong command.** The plan cites `journal.py:86-97`, `score.py:801,811`, `report.py:130-133`, `cli.py:405-413`. Those locations have moved (header write is `113-124`; `report.json` write is `1065-1069`; render guards are `149-153` / `190-194`). `cli.py:404-408` is the `report` command’s partial check, not `score`. The mechanisms survive; an executor who reads only the cited windows will look at paired-ablation code (`score.py:787-817`) and the wrong CLI command.
- **LOW — `load_done` is broader than “truncated trailing line”.** It skips *every* unparseable line (`journal.py:101-102`). Completeness must call `load_done`, not reimplement a trailing-only parser, or the two will disagree about what has been driven.

### Suggestions

## 06.3.4-02

### Summary

Building quadratic weighted kappa and Spearman rho on the standard library, before any human score exists, is the right place in the wave graph and matches D-48 and `pyproject.toml:10-19` (no scipy/sklearn). Wiring both statistics beside the existing exact-match / MAD figures (`score.py:448-519`, `dimensions.py:186-189`) is correct. The plan collides with a schema invariant it does not mention: a dimension with `status="ok"` cannot carry a `reason`, which is exactly where the uncalibrated label is specified to land.

### Strengths

- Statistics are specified against published worked examples, not against this implementation’s own arithmetic, with scale bounds passed in rather than inferred. That prevents a 12-row worksheet that never used 1 or 5 from shrinking the kappa scale.
- Degenerate cases (zero variance, identical ratings, empty or unequal sequences, mid-rank ties) are named outcomes. A 12-row worksheet can easily hit all of them.
- Calibration guards that 06.3.4-05 depends on already exist and must stay: `--no-judge` plus a cached population raises (`score.py:332-346`); `--sample` narrower than the cached verdict count raises (`score.py:347-356`). Leaving them untouched is the right constraint.
- Rubric scale is 1–5 (`judge.py:27, 73-74`); the plan’s “scale the judge rubric actually uses” matches that, not a 0–N inference.
- `detail` is already `dict[str, float]` (`dimensions.py:24`). Kappa (possibly negative) and rho fit as optional floats beside `calibration_exact_match` / `calibration_mad`.

### Concerns

- **HIGH — Uncalibrated label cannot live in `reason` on an `ok` dimension.** `DimensionResult._validate_consistency` requires `status=="ok"` to have a score and `reason is None`, and forbids a score on `skipped`/`error` (`dimensions.py:28-41`). `make_groundedness_result` / `make_faithfulness_result` return `status="ok"` with a mean score when verdicts exist (`dimensions.py:190-196`). Putting “uncalibrated: kappa=…” in `reason` while keeping the judged number will fail model validation. There is no other string field: `extra="forbid"` (`dimensions.py:19`), and `detail` is float-only.
- **MEDIUM — Degenerate kappa/rho “named outcomes” vs float `detail`.** If those outcomes are strings, they cannot enter `detail`. If they are omitted, the report cannot show why agreement is missing. The plan does not say which encoding to use.
- **MEDIUM — `RunMetadata` is closed.** Adding a completed-score count requires a new field on `RunMetadata` (`report.py:24-45`, `extra="forbid"`). The plan lists `report.py`, so this is doable, but the template and `report.schema.json` must move with it or schema tests will fail.
- **LOW — Stale line citations.** Calibration block is `score.py:448-519`, not `395-475`; metadata assembly is `1027-1057`, not `780-815`; judged builders are `dimensions.py:150-241`, not `110-215`.

### Suggestions

- Add an explicit string field on `DimensionResult` (for example `caveat` or `label`) for the uncalibrated / no-calibration text, or encode a float flag in `detail` *and* put the human-readable sentence in `RunMetadata.notes` (`report.py:45`). Do not put it in `reason` on an `ok` row. Keep “no calibration” and “below target” as distinct strings, as specified.
- Define degenerate agreement as a concrete encoding: skip the detail keys and set the label, or use a documented sentinel float, not an unconstrained “named outcome.”
- Keep reading the 0.70 target from `gate.py`; do not restated it in `score.py`.

### Risk Assessment

**MEDIUM** — The statistics and the “build them before ratings exist” ordering are sound. The uncalibrated-label placement is incompatible with the current `DimensionResult` invariant and will fail at wiring time unless the model is extended.

## Consensus Summary

Both source-grounded reviewers covered all six plans and agreed that the phase DAG, staged decision checkpoints, one-way journal reconciliation, fresh human calibration, and honest handling of negative graph results are fundamentally well designed. They also found three issues that should be corrected before execution because they can corrupt evidence, exceed authorized spend, or make scoring fail at runtime.

### Agreed Strengths

- The wave ordering is coherent: tracer/gate machinery precedes staged spend authorization, full drive, human calibration, and final documentation.
- `checkpoint:decision` is the correct blocking mechanism for both paid-spend authorization and fresh human scoring under this repository's end-of-phase verification mode.
- The staged-header latch is correctly diagnosed, and one-directional atomic reconciliation preserves per-record stage provenance.
- Calibration statistics are deliberately implemented before ratings exist, while negative graph deltas remain publishable outcomes after bounded artifact checks.

### Agreed Concerns

1. **HIGH — The first default `--resume` can append to the retained 2026-09-03 evidence run.** `resolve_run_dir` selects the newest matching dated directory, which is currently the superseded run. Plan 01 checks identity after the first paid write, while Plans 03–04 inherit that directory. Require an explicit new output directory or `--no-resume` before any query, then assert the resolved path is not the superseded directory.
2. **HIGH — Paid stages lack fail-closed spend enforcement.** `06.3.3-BUDGETS.md` requires each paid driver to enforce a stage cap with no silent default, but `run` and judged `score` only rely on before/after observation. Port the existing `measure` stop rule or define another mechanical in-process cap before the staged, full, and judged drives.
3. **HIGH — Plan 02's uncalibrated label conflicts with the current result schema.** `DimensionResult` forbids `reason` when `status == "ok"`; setting it on a scored groundedness or faithfulness result will fail validation. Add a legal caveat/label field or place machine-readable values in `detail` with human-readable metadata/template support. Plan 05 depends on this correction.
4. **MEDIUM — Several verification commands are POSIX-only in a Windows-native repository.** Replace `test`, `grep`, `ls -d`, and `tail` constructs with cross-platform Python or PowerShell-safe checks.
5. **MEDIUM — Plans contain stale execute-time assumptions and source locations.** Phases 06.3.1–06.3.3 have landed, so revise-before-execute tables, dimension names, budget facts, decay disposition, and moved line references should be refreshed against the current tree.

### Divergent Views

- The reviewers did not materially disagree. Cursor rated the resume and spend-cap gaps as cross-plan HIGH risks; Antigravity emphasized the same mechanisms while assigning some individual plans MEDIUM risk.
- Antigravity gave greater weight to Windows command incompatibility. Cursor additionally identified that `metadata.json` is produced by the report command rather than scoring alone and that Plan 05's file list omits report schema/template changes.
