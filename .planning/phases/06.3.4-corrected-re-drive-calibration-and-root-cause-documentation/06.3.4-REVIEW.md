# Phase 06.3.4: Code Review Report

**Reviewed:** 2026-09-10T00:00:00Z
**Depth:** standard
**Files Reviewed:** 21
**Status:** issues_found

## Summary

Reviewed the evaluation-harness source (agreement/statistics, staged-gate, journal, run/drive loop,
scorer, report renderer, CLI, config overlays, and their tests) that make up Phase 06.3.4. The
agreement math (`agreement.py`), calibration state machine (`score.py`/`gate.py`), and staged-gate
threshold logic (`gate.py`) are careful, well-tested, and internally consistent — golden vectors,
boundary tests (exactly-at-floor, strictly-above-trigger), and disjoint state-code bands are all
verified by the accompanying test suite and hold up under inspection.

On the specific question of fail-open vs. fail-closed on missing gate data: `evaluate_staged_gate`
does fail closed when `graph_presence_rate` is not computed. This isn't an explicit
`status == "ok"` assertion, though — it's load-bearing on a narrower mechanism: `no_match_rate` is
only ever populated in `dimensions.py`'s `ok`-status return path of `make_graph_presence_rate`, so
any `skipped`/`error` dimension is missing the `"no_match_rate"` detail key, and the required-key
check at `gate.py:251-252` raises `ValueError` before any threshold comparison happens. That raise
propagates uncaught out of the `staged-gate` CLI command to a non-zero exit, which is the correct
fail-closed behavior — but it depends on that key never being set outside the `ok` path, which is
an implicit coupling between two modules rather than an explicit contract.

The more serious finding is the same class of bug the phase's own root-cause note
(`docs/evaluation-fidelity-and-graph-yield.md`) attributes to the *original* incident, reintroduced
one layer up: the `partial` flag that gates report publication is derived once, at journal-creation
time, from whether `--limit` was passed — not from whether the drive actually finished all expected
work units. A full (`--limit` omitted) drive that stops early for *any* reason (the fail-closed
stage-spend-cap logic added in this same phase, an operator `Ctrl+C`, a crash — exactly the "halted
at 658/1000+ records" scenario this phase documents) keeps `partial: false` all the way through to
`report.json`, so `lancet-eval score`/`report` will render and publish a final-looking report over
an incomplete journal. This is CR-01 below, and it directly contradicts a claim made in the
in-scope documentation file, covered as WR-05. The remaining findings are smaller robustness/
maintainability gaps in the same area (config duplication, fragile file-glob/regex resolution in
`gate.py`, a fail-open default for unrecognized ablation arms, and one dead-code invariant).

## Critical Issues

### CR-01: `partial` flag conflates "smoke-limited run" with "run actually complete"; a halted full drive is silently reported and published as a finished result

**File:** `eval/src/lancet_eval/run.py:247`, `eval/src/lancet_eval/score.py:1306`, `eval/src/lancet_eval/report.py:150-155,191-195`, `eval/src/lancet_eval/journal.py:162-217`

**Issue:**

`drive()` computes the journal header's `partial` bit exactly once, before any work unit runs:

```python
partial = limit is not None   # run.py:247
...
journal.write_header(corpus=corpus, partial=partial)   # run.py:267
```

This is the *only* place `partial` is ever set to `True` for a fresh journal. It reflects whether
the operator passed `--limit` (a smoke-test knob), not whether the drive will actually execute the
full cross-product of `questions × arms`. The header is written once (`Journal.write_header` is a
no-op if the file already exists/non-empty) and is never revisited by `drive()` itself:

- If the drive is stopped early by the (correct, fail-closed) stage-spend-cap logic added in this
  same phase (`stopped_by_cap=True`, run.py:341-345), the header still says `partial: false`,
  because that flag was fixed before the loop started and nothing rewrites it on early exit.
- If the process is killed, crashes, or is halted by operator directive mid-drive — precisely the
  "halted at 658/1000+ records" event this phase's own documentation describes — the on-disk
  journal is left with `partial: false` and an incomplete set of records.

`score_run` then copies this bit verbatim into the published report:

```python
metadata = RunMetadata(
    ...
    partial=header_partial,   # score.py:1306, header_partial read straight from the journal header
    ...
)
...
if not header_partial:
    report_json_path = dir_path / "report.json"
    with open(report_json_path, "w", encoding="utf-8") as f:
        f.write(render_json(report))   # score.py:1317-1320 — WRITES report.json for the halted run
```

And `report.py`'s only completeness gate checks the same mislabeled bit:

```python
if report.metadata.partial:
    raise ReportError("Cannot render report for partial run (partial: true set by --limit smoke knob)")
```

There is a `completeness_comparison()` / `reconcile_header()` pair in `journal.py` that *can*
correctly verify the full cross-product of expected `(question_id, arm)` keys — but it is:
1. Opt-in only, invoked by a separate `lancet-eval reconcile` CLI command that nothing else calls
   automatically, and
2. One-directional: it can only flip `partial: true → false` once verified complete; there is no
   equivalent path that flips `partial: false → true` when a run that started as "not `--limit`ed"
   turns out to have stopped short.

Net effect: the one automatic safeguard (`score_run`/`render_markdown`/`render_json` refusing to
publish "partial" data) never fires for the most likely real-world incomplete-run scenario — a full
drive halted by the cap it is supposed to respect, or by operator/infra interruption — because
those runs were never marked partial in the first place. This is the same failure shape ("aborted
executions ... recorded as successful") that `docs/evaluation-fidelity-and-graph-yield.md` names as
the root cause of the original incident, reintroduced one layer up (drive-level completeness rather
than per-record stream-truncation) — see WR-05.

**Fix:** Derive `partial` from actual completeness, not from whether `--limit` was passed. For
example, have `drive()` compute the expected key set once, and set/rewrite the header's `partial`
based on whether all expected keys are present in the journal after the run loop exits (covering
both the cap-stop and any-exception-stop cases via a `finally`), e.g.:

```python
finally:
    if should_close_client:
        eval_client.close()

expected_keys = {journal_key(corpus, q.id, arm) for q, arm in work_units}
actual_done = load_done(target_path)
still_partial = limit is not None or not expected_keys.issubset(actual_done)
# rewrite header (or call reconcile_header-style atomic update) to set partial=still_partial
```

and have `score_run` treat a journal with no explicit, *verified* completeness signal as partial by
default (fail closed) rather than trusting a boolean that was frozen before the drive ran.

## Warnings

### WR-01: `GRAPH_ARMS.get(arm, False)` silently treats any unrecognized arm string as "graph-on" (ablation disabled) instead of failing closed

**File:** `eval/src/lancet_eval/run.py:78`
**Issue:** `disable_graph_context = GRAPH_ARMS.get(arm, False)` defaults to `False` (i.e., graph
context stays enabled) for any `arm` value that is not exactly `"graph-on"` or `"graph-off"`. Given
that the whole harness is built around a strict two-armed ablation comparison (D-47, per the code
comment two lines above), a typo'd or drifted arm label (e.g. `"graph_off"`, extra whitespace, a
future third arm added to corpus config without updating this file) would silently execute as
graph-on rather than raising, corrupting the ablation pairing without any error.
**Fix:**
```python
if arm not in GRAPH_ARMS:
    raise ValueError(f"Unknown graph arm {arm!r}; expected one of {list(GRAPH_ARMS)}")
disable_graph_context = GRAPH_ARMS[arm]
```

### WR-02: `config/config.eval.toml` duplicates the entire `[engine.workflow]` block from `config/config.toml` with identical values, creating a silent drift risk

**File:** `config/config.eval.toml:7-14` vs `config/config.toml:36-69`
**Issue:** The eval overlay re-declares all seven workflow timeout keys
(`reformulate_timeout_ms` … `generation_node_timeout_ms`) with values that are byte-identical to
`config.toml`'s currently-derived budgets. The overlay's own header comment says its purpose is
isolated LanceDB directory for evaluation benchmarks, not timeout overrides. Because these values
are hand-copied rather than provably inherited, the next timeout re-derivation (e.g. a future
`06.3.x` latency pass) can update `config.toml` and silently leave `config.eval.toml` stale, with no
test catching the divergence — eval runs would then execute against a different, unreviewed timeout
budget than production without anyone noticing.
**Fix:** Add a test asserting the two files' workflow timeout values stay in lock-step (parse both
TOML files and assert the `[engine.workflow]` sub-tables are equal), so any future drift fails
loudly in CI. (Whether it is also safe to delete the duplicated block from `config.eval.toml`
depends on how the `LANCET_ENV=eval` overlay is merged over the base config at load time — that
merge behavior lives outside this review's file set and should be confirmed before removing the
block; the lock-step test is the safe fix regardless of that answer.)

### WR-03: `_find_budgets_file` / `_find_store_baseline_file` pick an arbitrary match when more than one `*06.3.3*` phase directory exists

**File:** `eval/src/lancet_eval/gate.py:51-66, 137-152`
**Issue:** Both helpers do `matches = list(planning_phases.glob("*06.3.3*/06.3.3-BUDGETS.md")); return matches[0]`
(same pattern for the store-baseline file) with no sort or tie-break rule. `Path.glob` order is
filesystem-dependent and not guaranteed to be sorted. If this repository ever ends up with more
than one directory matching `*06.3.3*` (e.g. an archived/superseded phase alongside the active one
— the repo's own history shows split/renumbered phases such as `06.3.x`/`06.3.x.y` are routine),
`get_stage_cap()` and `read_store_suspension()` could silently read stale or wrong budget/baseline
data depending on directory listing order, with no error or warning.
**Fix:** Sort matches deterministically (e.g. `sorted(matches)[-1]` or explicitly prefer a
non-archived path) and raise if more than one candidate remains ambiguous, mirroring the existing
fail-closed style used elsewhere in this module.

### WR-04: `read_store_suspension` derives a gating boolean from an unstructured regex search over free-form markdown prose

**File:** `eval/src/lancet_eval/gate.py:155-174`
**Issue:** `re.search(r"unpopulated:\s*(true|false)", text, re.IGNORECASE)` (and the
`graph_disposition:\s*(\w+)` fallback) scans the entire baseline document text for the first
matching substring. This directly controls whether the graph-yield investigation floor is
suspended for the whole evaluation run (`evaluate_staged_gate`'s `is_suspended` branch). A baseline
document that mentions "unpopulated: false" anywhere in explanatory prose, a historical note, or a
quoted example before the actual authoritative field would be picked up as the value, with no
structural (e.g. YAML frontmatter) validation to disambiguate.
**Fix:** Require the suspension flag to live in a fenced/structured block (YAML frontmatter or a
single well-delimited line anchored to line-start with `^`), and raise if zero or more-than-one
candidate matches are found, rather than taking the first regex hit anywhere in the file.

### WR-05: In-scope documentation overclaims that hidden-failure masquerading is solved, but CR-01 shows the same failure shape reintroduced at the drive/journal level

**File:** `docs/evaluation-fidelity-and-graph-yield.md:12`
**Issue:** The note's closing claim is:

> "The corrected evaluation pipeline enforces staged preflight validation, fresh agreement metrics,
> and empirically anchored timeout budgets that prevent hidden failures from masquerading as
> successes."

This is the exact failure shape CR-01 demonstrates is *not* prevented: a drive halted before
completion (by the stage-spend cap this same phase introduced, or by operator/infra interruption)
is not marked partial and is publishable as a final report, indistinguishable from a genuinely
complete run — i.e., a hidden (run-level) failure masquerading as a success, one layer up from the
per-record stream-truncation bug this document was written to describe. Because this document is
"cited by Phase 6.4's evaluation methodology and results pages" (per its own note at the top), the
overclaim propagates downstream into methodology/results pages that build on it.
**Fix:** Scope the claim to what's actually verified today (per-record stream truncation / typed
failure notices / paired ablation comparisons), and either note run-level completeness as a known
open gap or remove/soften the "prevent hidden failures from masquerading as successes" framing until
CR-01 is fixed.

## Info

### IN-01: Repeated local `import time` instead of a module-level import

**File:** `eval/src/lancet_eval/run.py:187, 212`
**Issue:** `time` is imported inline inside two separate branches of `drive_one` (both retry-sleep
paths) rather than once at module scope alongside the existing `import logging` /
`from pathlib import Path` block. Purely a style/consistency nit — no functional effect since
Python caches module imports — but it's inconsistent with the rest of the file's import style and
easy to forget to consolidate if a third retry path is added later.
**Fix:** Move `import time` to the top-level import block.

### IN-02: `GRAPH_YIELD_INVESTIGATION_FLOOR` (0.20) is duplicated as a magic-number literal in `dimensions.py` instead of imported from `gate.py`

**File:** `eval/src/lancet_eval/dimensions.py:553` vs `eval/src/lancet_eval/gate.py:21`
**Issue:** `make_graph_presence_rate` hardcodes `floor_val = 0.20  # MultiHop-RAG floor is 0.20` for
its `investigation_floor` detail field, duplicating the committed constant
`GRAPH_YIELD_INVESTIGATION_FLOOR = 0.20` defined in `gate.py`. Both currently agree, but because the
value lives in two places there is nothing preventing them from silently diverging if the committed
floor is ever revised in `gate.py` (the module docstring even calls these out as "Committed Decision
Inputs" that are supposed to be a single lock).
**Fix:** Import `GRAPH_YIELD_INVESTIGATION_FLOOR` from `lancet_eval.gate` in `dimensions.py` (or
relocate the constant to a shared location both modules import from) instead of re-declaring the
literal.

### IN-03: `derive_judged_slice_size`'s documented invariant guard is unreachable in the one case it exists for, and the function has no caller

**File:** `eval/src/lancet_eval/gate.py:386-420`
**Issue:** The docstring states the function "Refuses a result below cached_verdict_count," and the
guard is:
```python
if judgeable_count <= 0:
    return 0, "judgeable_count_is_zero"          # gate.py:397-398 — returns BEFORE the guard below

if n_cap < cached_verdict_count or judgeable_count < cached_verdict_count:
    raise ValueError(...)                         # gate.py:405-408
```
When `judgeable_count == 0` and `cached_verdict_count > 0` (a previously judged, cached population
that a later, narrower re-run would silently shrink — the exact scenario `score.py:345-369` raises
`ScoreError` to guard against for the sibling `--sample`/`--calibration-file` path), the early
`return 0, "judgeable_count_is_zero"` fires first and the documented refusal never triggers; the
function silently returns a slice size of `0` instead. Grepping the codebase shows this function is
defined and imported into `test_gate.py`'s import list, but is never called from any test in that
file, nor from `score.py`, `run.py`, or `cli.py` — it currently appears to be dead code, which is why
this broken guard-ordering has gone unnoticed rather than surfacing as a test failure.
**Fix:** Reorder the checks so the invariant guard runs before the zero-shortcut (e.g. check
`cached_verdict_count` conditions first regardless of `judgeable_count`), add a test exercising
`judgeable_count=0, cached_verdict_count>0`, and either wire this function into its intended caller
or remove it if it is genuinely unused.
