## Critical Issues

### CR-01: The T-06.3.4-25 judged-spend meter fails open when the provider response omits `usage` — the pre-dispatch cap check never fires and every remaining question in the slice is dispatched as an unmetered paid call

**File:** `eval/src/lancet_eval/score.py:500-503` (consumer), `eval/src/lancet_eval/judge.py:343-361` (producer)

**Issue:** `judge_once` returns `usage=None` whenever the provider response has no parseable
`usage` block (`judge.py:343-352`, `usage_seen` stays `False`) — this is a deliberately-handled,
tested return shape (`test_judge_once_returns_none_usage_when_omitted` pins it). `score_run`'s
judge loop consumes that result with:

```python
if usage is not None:
    accumulated_judge_spend += compute_judge_spend(
        usage.prompt_tokens, usage.completion_tokens
    )
```

There is no `else` branch. If `usage` is `None` — provider quirk, proxy stripping the field, a
model/endpoint that doesn't report token usage, or a transport failure after partial success —
`accumulated_judge_spend` never increases for that call. The pre-dispatch cap check at
`score.py:485-487` (`if ... accumulated_judge_spend >= stage_spend_cap: cap_stopped = True; break`)
compares against this frozen accumulator, so once the provider stops reporting usage, the cap check
can never trip again for the remainder of the judged slice — every subsequent question dispatches
as a real, paid judge call with **zero** enforcement, for as long as `judged_qids` has entries left
(bounded only by the up-front `derived_slice_size`/`--sample`, i.e. the *pre-estimate*, which
`06.3.4-05-PLAN.md`'s own threat-model entry for T-06.3.4-25 explicitly calls "a pre-estimate
rather than an enforcement" — the estimate `estimate_judge_cost_per_question()` also uses a fixed
`ESTIMATED_JUDGE_PROMPT_TOKENS = 1200`, well below the `EVIDENCE_CHAR_BUDGET = 12000`-char ceiling
`truncate_evidence` actually allows into the prompt, so the pre-estimate itself is not a tight
bound).

That same 06.3.4-05 plan text (which authored T-06.3.4-25's original mitigation claim) states the
requirement as: *"usage-absent reported distinctly from zero and falling back to `p` with the
fallback count recorded"* — i.e., the plan anticipated exactly this case and specified a fallback
to the pre-estimate `cost_per_question` (`p`) so the meter still advances conservatively. That
fallback does not exist anywhere in `score.py`; `estimate_judge_cost_per_question` /
`ESTIMATED_JUDGE_PROMPT_TOKENS` are referenced exactly once, before the loop, to compute
`cost_per_question` for slice sizing — never inside the loop as a per-call fallback.

No test in this file set exercises this path: every mocked judge response across
`test_score_judged.py`'s cap-related tests (`test_judge_loop_breaks_at_spend_cap`,
`test_judge_loop_cached_verdicts_consume_no_cap_headroom`, `test_score_run_judged_subset_bounded_by_cap`,
`test_score_run_cap_stopped_publishes_provenance`) supplies a `usage` block; `judge.py`'s own
`test_judge_once_returns_none_usage_when_omitted` only asserts `judge_once`'s isolated return
value, never score.py's loop behavior when it receives that `None`. The suite's 100% pass rate is
therefore not evidence this path is safe — it's evidence this path was never driven.

**Fix:** Give the meter a documented, conservative fallback instead of silently no-op'ing, per the
plan's own stated requirement, e.g.:

```python
if usage is not None:
    accumulated_judge_spend += compute_judge_spend(
        usage.prompt_tokens, usage.completion_tokens
    )
else:
    # Fail closed: charge the worst-case pre-estimate when the provider omits usage,
    # and record that this call's spend is an estimate rather than observed.
    accumulated_judge_spend += cost_per_question
    usage_absent_fallback_count += 1
```

and surface `usage_absent_fallback_count` in `RunMetadata.notes` / the dimension `detail` so a
report that relied on the fallback is distinguishable from one with fully-observed spend. Add a
regression test that mocks a judge response with no `usage` key and asserts the loop still stops
once the fallback-accumulated spend reaches the cap.

## Warnings

### WR-06: `judged_slice_state` reports `cap_bound`/`completed` based on the *derived* bound, not the bound actually applied when an explicit `--sample` narrows the slice further

**File:** `eval/src/lancet_eval/score.py:432-443,523-534`
**Issue:** `judged_slice_binding` (`"cap"`, `"data"`, or `"coincident"`) comes from
`derive_judged_slice_size`'s return value and describes what bounded the *derived* slice size
before any `--sample` override is applied. When `sample is not None`, `slice_count = sample`
overrides `derived_slice_size` outright (`score.py:439`), but `judged_slice_binding` is never
recomputed or overridden to reflect that the explicit `--sample` value — not the cap and not the
judgeable-question count — is what actually bounded `judged_slice_committed`. Concretely: with 100
judgeable questions, a cap that derives a bound of 50, and `--sample 10`, the published
`judged_slice_state` becomes `"cap_bound"` (since `judged_slice_binding == "cap"`) even though the
operator's own `--sample 10` — not the cap — determined the committed slice size. Symmetrically,
if the cap derives a bound larger than the judgeable population (`binding == "data"`) and
`--sample` narrows below both, the state publishes as `"completed"`, which reads as "every
judgeable question was judged" when in fact a deliberately smaller, operator-chosen subset was.
T-06.3.4-43's own stated purpose (06.3.4-09-PLAN.md) is that the published report states "which
constraint bound the slice" — this is the one case where it doesn't. No test in `test_score_judged.py`
exercises `--sample` set below both the cap-derived and data-derived bounds simultaneously with an
assertion on `judged_slice_state`.
**Fix:** When `sample is not None and sample < derived_slice_size`, set the binding/state to a
distinct value (e.g., a new `JUDGED_SLICE_STATE_SAMPLE_BOUND`) rather than reusing whatever
`derive_judged_slice_size` returned for the un-overridden derived bound.

### WR-07: `cached_verdict_count` counts cache entries regardless of `judge_prompt_version`/`judge_model`, so a prompt-version bump inflates the cap-derived bound with entries that can never be reused

**File:** `eval/src/lancet_eval/score.py:353-355`
**Issue:** `cached_verdict_count = sum(1 for e in cache.entries.values() if e.verdict is not None)`
counts every verdicted entry in `judge_cache.json` for the run directory, with no filter on
`prompt_version` or `judge_model` even though `cache_key()` (`judge.py:142-155`) folds both into
the key, meaning stale-version entries are permanently cache-misses going forward. This value
feeds `derive_judged_slice_size(..., cached_verdict_count=cached_verdict_count)`
(`score.py:423-428`), where `n_cap = cached_verdict_count + int(stage_spend_cap // cost_per_question)`
(`gate.py:422`) — a prompt-version bump silently inflates `n_cap` by however many stale entries
exist, sizing the judged slice as if that many *free* (already-paid) verdicts existed when none of
them will ever be looked up successfully; every one of those "budgeted" slots is actually a fresh
paid call. Separately, the invariant guard at `gate.py:424` (`if n_cap < cached_verdict_count or
judgeable_count < cached_verdict_count: raise ValueError`) can raise a confusing `ScoreError` on a
run whose *current* judgeable population is smaller than a large stale cache from a prior prompt
version, with a message that names "cached verdict count" without clarifying that those cached
verdicts are for a different, no-longer-matching prompt version.
**Fix:** Scope `cached_verdict_count` to entries whose `prompt_version == config.judge_prompt_version
and judge_model == config.judge_model`, matching the scope `cache_key()` itself already enforces
for lookups.

### IN-04: `derive_judged_slice_size`'s cap-derived bound uses float floor-division, susceptible to floating-point representation error, now on a live path for the first time

**File:** `eval/src/lancet_eval/gate.py:422`
**Issue:** `n_cap = cached_verdict_count + int(stage_spend_cap // cost_per_question)` floor-divides
two independently-derived floats (e.g. Python: `9.0 // 0.1 == 89.0`, not the mathematically exact
`90.0`). Before this gap-closure round the function was dead code (IN-03/T-06.3.4-24); plan 09
wires it into `score_run`'s judged-subset sizing, so this is the first time the computation runs
against a live, CLI-supplied `--stage-cap` divided by a `cost_per_question` it was not derived
from. All existing tests construct `cap` as `cost_per_q * N.5` and divide by that same
`cost_per_q`, which cancels out and never exercises the representation-error case. This is not a
spend-cap bypass — real enforcement is the per-dispatch accumulated-spend check (subject to CR-01
above) — the exposure here is limited to `judged_slice_committed`/`--sample`-bound accuracy being
off by one question at unlucky cap/cost ratios.
**Fix:** Use integer-cent or `Decimal` arithmetic for the ratio, or floor with a documented
epsilon; add a test dividing an independently-constructed cap literal (not derived from
`cost_per_question` by multiplication) to catch representation-error drift.

### IN-05: `make_groundedness_result` and `make_faithfulness_result` duplicate the entire judged-slice-provenance and calibration `detail`-construction block

**File:** `eval/src/lancet_eval/dimensions.py:164-264` and `267-367`
**Issue:** The two functions are near-identical (differing only in dimension name and reason
strings). T-06.3.4-43's fix added the same three-line `judged_slice_committed`/
`verdicts_obtained`/`judged_slice_state` block to both `err_detail` and `detail` construction in
both functions (eight near-identical insertions total), compounding pre-existing duplication of
the calibration fields. Any future field addition to the judged-dimension contract must be applied
in four places, with no test enforcing the two stay in lockstep beyond their individual coverage.
Separately, `score.py:485` still tests `stage_spend_cap is not None` even though it is unreachably
`None` at that point (guaranteed non-`None` by the `raise ScoreError` at `score.py:400-404`) — a
harmless but confusing dead condition. And `report.py`'s `format_details` renders the numeric
`judged_slice_state` code as a bare integer (e.g. `judged_slice_state=3`) in the human-readable
detail line even though `RunMetadata.judged_slice_state` carries the string label (`"cap_stopped"`)
for the same run — a minor readability inconsistency between the two places this concept surfaces.
**Fix:** Extract a shared helper for the judged-provenance/calibration `detail` block; consider
mapping the `detail["judged_slice_state"]` float back through `JUDGED_SLICE_STATES` when rendering
markdown so the human-readable row matches the metadata section's string.
