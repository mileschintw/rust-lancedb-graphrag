## Critical Issues

### CR-01: The "all judge calls failed" branch is unreachable whenever the primary arm contains any no-citation record — not just under cap/sample binding

**File:** `eval/src/lancet_eval/score.py:441-448, 1101-1102, 1144-1145`; `eval/src/lancet_eval/dimensions.py:200-207, 308-315`

**Issue:** As part of the WR-07 fix, `distinct_qids` (and therefore `judged_sample_count`, which only
increments for records actually selected into `judged_qids`) is scoped to the sampled/dispatched
subset of the *judgeable* population. `skipped_no_evidence` (lines 444-448), however, is computed
independently over the **entire primary-arm population**:

```python
skipped_no_evidence = sum(
    1
    for r in p_records
    if gold_map.get(r.question_id) and not r.structured_citations
)
```

Both are summed into `total_sampled`, which `dimensions.py` uses to discriminate "all judge calls
failed" from "no evidence to judge" from a generic "no judged items available":

```python
total_sampled=skipped_no_evidence + judged_sample_count,   # score.py:1102 / 1145
...
if judge_errors > 0 and judge_errors == total_sampled:                     # dimensions.py:200/308
    ... "All {judge_errors} judge calls failed with errors" (status="error")
if skipped_no_evidence == total_sampled and total_sampled > 0:             # dimensions.py:208/316
    ... "No evidence returned in responses; ... undefined" (status="skipped")
return ... "No judged items available" (status="skipped")
```

`judge_errors` can never exceed `judged_sample_count` (both only increment inside the dispatch loop,
over the same records). So `judge_errors == skipped_no_evidence + judged_sample_count` can only be
true when `skipped_no_evidence == 0`. **This makes the "all judge calls failed" error branch
unreachable in any run where the primary arm contains even one no-citation record anywhere** — this
is not limited to cap-bound or `--sample`-bound partial judging as first drafted; it holds for the
ordinary, unbounded `sample=None` full-population run too, as long as any record in the population
lacks citations (a realistic, common condition — abstentions/no-evidence answers are expected in
real journals).

Concrete repro: 5 judgeable records, 3 separate no-citation records in the same primary arm, no cap
binding (`sample=None`, generous cap). All 5 judgeable records are dispatched and all 5 judge calls
error out (`judge_errors=5`, `verdicts=[]`). `judged_sample_count=5`, `skipped_no_evidence=3`
(population-wide, from the unrelated no-citation records), so `total_sampled=8`. `judge_errors(5) ==
total_sampled(8)` is `False` → the dimension does **not** report `status="error"` /
`"All 5 judge calls failed with errors"` — it falls through to `status="skipped"` /
`"No judged items available"`.

Practical impact: a total judge-API failure (outage, malformed provider responses exhausting the
retry) self-reports as a benign-sounding `status="skipped"` / `"No judged items available"` instead
of `status="error"` / `"All N judge calls failed with errors"`, in any journal that also has
no-citation records — silently downgrading a total-failure signal that automated dashboards or
reviewers may filter on `status=="error"` to detect. The raw `judge_errors` count is still present in
`detail`, but the field designed to make this failure mode legible (`status`/`reason`) is wrong.
No test currently exercises this branch for the judged dimensions (`grep` for
`"All {judge_errors} judge calls"` in `eval/tests/` finds no hits — the only test touching judge
errors, `test_worksheet_excludes_judge_errored_records`, has zero no-citation records in its fixture
and doesn't assert on `g_dim.status`/`f_dim.status` at all).

Note: this is *not* cleanly framed as a regression versus pre-plan-10 behavior — pre-plan-10,
`judged_sample_count` also incremented for no-citation records that happened to land inside the
sampled slice, so the same equality could fail there too depending on random selection. The bug is
better understood as: `total_sampled`'s two addends have different, mismatched scopes (population vs.
dispatched-subset), and the current sum is only correct for the "no evidence" branch, not the "all
errored" branch.

**Fix:** Do not fix by narrowing `total_sampled` to `judged_sample_count` alone —
`test_zero_citations_record_skipped_from_judged` requires the current sum for the "no evidence"
branch to fire (single record, zero judgeable candidates, `judged_sample_count=0`,
`skipped_no_evidence=1`, `total_sampled=1`, `skipped_no_evidence == total_sampled` must hold).
Instead, correct the "all failed" branch's own comparison to subtract out the no-evidence records
that were never dispatched:

```python
# dimensions.py, both make_groundedness_result and make_faithfulness_result
if judge_errors > 0 and judge_errors == total_sampled - skipped_no_evidence:
    return DimensionResult(
        name=...,
        status="error",
        reason=f"All {judge_errors} judge calls failed with errors",
        detail=err_detail,
        n=0,
    )
```

This is equivalent to `judge_errors == judged_sample_count` (the actually-dispatched population),
while leaving the "no evidence" branch's existing `skipped_no_evidence == total_sampled` comparison
untouched. Verified against the existing suite: `test_zero_citations_record_skipped_from_judged` and
`test_worksheet_excludes_judge_errored_records` both continue to pass under this reasoning (traced by
hand; neither depends on the removed equality path), and it correctly fires on the repro above
(`judge_errors(5) == total_sampled(8) - skipped_no_evidence(3) == 5` → `True`).

## Warnings

### WR-01: `--sample` silently clamps with no disclosure when binding is "data"/"coincident"/"judgeable_count_is_zero"

**File:** `eval/src/lancet_eval/score.py:462-473`

**Issue:** The WR-07 fix scoped the `--sample`-exceeds-bound refusal to `judged_slice_binding ==
"cap"` only:

```python
if sample is not None and sample > derived_slice_size:
    if judged_slice_binding == "cap":
        raise ScoreError(...)
    slice_count = derived_slice_size
elif sample is not None and sample > 0:
    slice_count = sample
else:
    slice_count = derived_slice_size
```

This is deliberate and tested (`test_score_run_sample_exceeds_data_bound_clamps_and_does_not_raise`)
— a user asking for more judged questions than exist in the judgeable population should not be
treated the same as asking for more than the spend cap allows. However, when the clamp fires (e.g.
`--sample 5` against a judgeable population of 2), there is **no** log line, `logger.warning`, or
`RunMetadata.notes` entry recording that the requested sample size was reduced. `judged_slice_state`
resolves to `"completed"` (assuming no cap-stop), which reads as an unremarkable, fully-successful
run. The only way to detect that fewer questions were judged than requested is to compare
`report.metadata.judged_slice_committed` against the `--sample` value passed on the command line —
information that is not itself persisted anywhere in `report.json`.

**Fix:** When the clamp fires (`sample is not None and sample > derived_slice_size and
judged_slice_binding != "cap"`), append a note to `final_notes` (mirroring the pattern already used
for `fallback_note`/`judge_stop_note`/`missing_units_note`), e.g.:

```python
sample_clamp_note: str | None = None
if sample is not None and sample > derived_slice_size and judged_slice_binding != "cap":
    sample_clamp_note = (
        f"--sample {sample} exceeded the judgeable population ({derived_slice_size}); "
        f"judged slice was clamped to {derived_slice_size}."
    )
...
if sample_clamp_note:
    final_notes = f"{final_notes} {sample_clamp_note}".strip() if final_notes else sample_clamp_note
```

### WR-02: Duplicate/redundant fallback-count disclosure when a cap-stopped run also has usage-absent calls

**File:** `eval/src/lancet_eval/score.py:553-564, 1440-1446`

**Issue:** When `cap_stopped` is `True` and `usage_absent_fallback_count > 0`, the cap-stop note
already names the fallback count:

```python
judge_stop_note = (
    f"Judged pass stopped by spend cap "
    f"(${accumulated_judge_spend:.6f} spent >= ${stage_spend_cap:.6f} cap, "
    f"including {usage_absent_fallback_count} call{'s' if usage_absent_fallback_count != 1 else ''} charged at estimated cost)."
)
```

...and then, unconditionally later, `fallback_note` restates the same fact independently:

```python
fallback_note: str | None = None
if usage_absent_fallback_count > 0:
    fallback_note = (
        f"Provider omitted usage for {usage_absent_fallback_count} judged call{'s' if usage_absent_fallback_count != 1 else ''}; "
        f"spend was charged at estimated cost per question."
    )
```

Both are appended to `RunMetadata.notes`, producing text like: *"Judged pass stopped by spend cap
($0.003168 spent >= $0.002772 cap, including 2 calls charged at estimated cost). Provider omitted
usage for 2 judged calls; spend was charged at estimated cost per question."* — the same fact stated
twice in different words. Existing tests only assert substring containment (`"2" in notes`), so this
passes silently. Not incorrect, but degrades the `notes` field as a human-readable audit trail.

**Fix:** Suppress `fallback_note` when `judge_stop_note` already discloses the fallback count (i.e.
when `cap_stopped and usage_absent_fallback_count > 0`), or simplify `judge_stop_note` to omit the
inline fallback clause and rely solely on `fallback_note` for that detail.

### WR-03: `_reusable_verdict_count` does not detect stale cache entries on a corrected re-drive into the same `run_dir`

**File:** `eval/src/lancet_eval/score.py:144-154, 374-378`; `eval/src/lancet_eval/gate.py:398-442`

**Issue:** `_reusable_verdict_count` (the WR-07 fix for the cache-count helper) filters cache entries
by `prompt_version` and `judge_model` matching the currently-configured values:

```python
def _reusable_verdict_count(cache, prompt_version, judge_model):
    return sum(
        1
        for e in cache.entries.values()
        if e.verdict is not None
        and e.prompt_version == prompt_version
        and e.judge_model == judge_model
    )
```

This correctly excludes entries from a superseded prompt version or a different judge model (the
scenario the added test, `test_cached_verdict_count_scoped_by_prompt_version_and_model`, covers).
It does **not**, however, check whether a matching entry actually corresponds to a record that could
be produced again by the *current* primary-arm population — the cache key
(`cache_key(prompt_version, judge_model, question, answer, post_truncation_evidence)`) also embeds
the record's `answer` text and truncated evidence. This phase is explicitly about a **corrected
re-drive**: if the engine fix changes generated answers (or evidence) for previously-judged
questions, the old `judge_cache.json` in the same `run_dir` retains entries whose `prompt_version`/
`judge_model` still match but whose `cache_key` will never be produced again by the corrected drive's
records — they are permanently stale, but `_reusable_verdict_count` still counts them as "reusable."

This inflated `cached_verdict_count` feeds directly into `gate.py::derive_judged_slice_size`:

- `n_cap = cached_verdict_count + int(stage_spend_cap // cost_per_question)` (gate.py:422) —
  over-commits the published slice size relative to what the spend cap can actually fund, since the
  stale "already paid for" verdicts will never actually be hit and will instead consume fresh cap
  headroom when re-dispatched.
- `if n_cap < cached_verdict_count or judgeable_count < cached_verdict_count: raise ValueError(...)`
  (gate.py:424) — can raise a spurious "cannot be below cached verdict count" refusal on a legitimate
  re-drive where the corrected engine run legitimately produces a smaller judgeable population than
  the stale cache count suggests.

Under-counting is not a concern here — cache entries genuinely missing `prompt_version`/`judge_model`
(or from an older schema) are conservatively excluded, which is safe. The gap is specifically
over-counting entries that match on version/model but are stale by answer content, which is the one
combination the new test does not cover.

**Fix:** Score `cached_verdict_count` against reachability from the current population rather than
existence in the cache map, e.g. by recomputing the expected `cache_key` for each currently-judgeable
record and counting only cache hits among those keys (this is naturally available once `distinct_qids`
is computed), rather than iterating `cache.entries.values()` independent of what the current drive
could actually produce.

## Info

### IN-01: Dead branch in calibration-worksheet row emission — `else ""` is unreachable

**File:** `eval/src/lancet_eval/score.py:912-917`

**Issue:** After the WR-07 fix, `selected_records` are filtered through `_is_judgeable(r, gold_map)`
before being added to `selected_records` (line 892), and `_is_judgeable` requires
`bool(rec.structured_citations)` to be `True`. The subsequent per-row emission loop still guards:

```python
ev = (
    truncate_evidence(r.structured_citations)
    if r.structured_citations
    else ""
)
```

Since every `r` in `selected_records` is already guaranteed to have non-empty
`structured_citations`, the `else ""` branch is now dead code.

**Fix:** Simplify to `ev = truncate_evidence(r.structured_citations)`, matching the equivalent call
site in the judge dispatch loop (line 494).

### IN-02: `usage_absent_fallback_count` hardcoded to `0.0` instead of referencing the variable in `no_judge` skip details

**File:** `eval/src/lancet_eval/score.py:1091, 1134`

**Issue:** The `no_judge` skip-path `DimensionResult.detail` for both `answer_faithfulness` and
`answer_groundedness` hardcodes `"usage_absent_fallback_count": 0.0` rather than referencing the
`usage_absent_fallback_count` variable used everywhere else in the function. Functionally equivalent
today (the variable can only be non-zero after the judge dispatch loop runs, which is skipped
entirely when `no_judge=True`), but it's an inconsistent pattern next to the surrounding
`judged_slice_committed`/`verdicts_obtained`/`judged_slice_state` keys, which do reference their
variables, and could silently go stale if the variable's initialization/reset logic ever changes.

**Fix:** Use `float(usage_absent_fallback_count)` for consistency with the other detail keys in the
same dict literal.
