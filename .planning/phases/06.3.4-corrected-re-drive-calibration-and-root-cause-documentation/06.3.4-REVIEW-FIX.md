### WR-03: `_reusable_verdict_count` does not detect stale cache entries on a corrected re-drive into the same `run_dir`

**Files modified:** `eval/src/lancet_eval/score.py`, `eval/tests/test_score_judged.py`
**Commit:** `4ed5829`
**Applied fix:** Changed `_reusable_verdict_count`'s signature and implementation per the
reviewer's suggested approach: rather than iterating `cache.entries.values()` and comparing
stored `prompt_version`/`judge_model` fields, it now takes the current primary-arm `records`
and `gold_map`, filters to currently-judgeable records via the existing `_is_judgeable`
predicate, recomputes each one's real `cache_key` under the *current* `prompt_version`/
`judge_model`, and counts only cache hits (`entry.verdict is not None`) among those
recomputed keys. Since `cache_key` is a SHA-256 hash over
`prompt_version, judge_model, question, answer, post_truncation_evidence`, this preserves the
original WR-07 guarantee (a stored entry from a superseded prompt version or different judge
model naturally fails to match, because those are hash inputs) while additionally excluding
entries that are stale by answer/evidence content — the new WR-03 guarantee for a corrected
re-drive. The single call site (`cached_verdict_count = _reusable_verdict_count(...)`) was
updated to pass `records=p_records, gold_map=gold_map`, both already in scope at that point in
`score_run`. `eval/src/lancet_eval/gate.py` was **not** touched — `derive_judged_slice_size`'s
public signature already accepted `cached_verdict_count: int` as an opaque input, so no
signature change was needed there; only how that integer is computed upstream in `score.py`
changed.

The existing unit test `test_cached_verdict_count_scoped_by_prompt_version_and_model` was
extended (all of its original coverage preserved, none of its assertions removed — the final
`assert reusable == 1` is unchanged) to use real `GoldQuestion`/`RunRecord` fixtures and real
computed `cache_key()` values instead of arbitrary placeholder strings (`"k1"`..`"k4"`), since
the new implementation's reachability check is meaningless against non-hash placeholder keys.
It now separately re-covers: (1) a reachable entry matching current prompt_version/model/
content, (2) an entry stored under a superseded prompt_version (unreachable via hash
mismatch), (3) an entry stored under a different judge_model (unreachable via hash mismatch),
(4) a reachable-by-key entry with no verdict (excluded), and (5, new) a WR-03 case: an entry
stored under a pre-correction answer text that is no longer reachable once the record's answer
changes on a corrected re-drive, even though prompt_version and judge_model both still match.
`uv run --project eval pytest eval/tests -q` was run after this fix: **416/416 passing**
(same count as immediately before this fixer pass — no regressions, and the extended test
replaces rather than adds to the prior test count).
