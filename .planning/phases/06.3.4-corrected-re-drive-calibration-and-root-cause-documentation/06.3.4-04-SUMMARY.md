## 4. Key Findings & Diagnostic Discoveries

### A. Linear Latency Escalation in `RetrieveHybrid`
Analysis of node durations across 100-record slices revealed that `RetrieveHybrid` was not experiencing random latency spikes, but a **monotonic, linear escalation**:
* **Records 0–99**: avg **7,423 ms** (max: 13.7s, high yield)
* **Records 100–199**: avg **15,268 ms** (max: 20.6s)
* **Records 200–299**: avg **23,155 ms** (max: 30.2s)
* **Records 300–399**: avg **28,713 ms** (max: 31.3s)
* **Records 400+**: avg **>30,000 ms** (100% timed out against `retrieve_timeout_ms = 30000`)

This systematic escalation points to resource accumulation in LanceDB table handles, checkout versioning, or index memory over successive queries. Interacting with `--retries 2`, each failing unit took $3 \times ~70\text{s} \approx 210\text{s}$, producing the external OpenRouter request drop to ~50 req/hr documented in `06.3.4-OBSERVATION-THROUGHPUT-PLATEAU.md`.

### B. Unmapped Document Guard Trip (`fa85cb0e-13f9-4909-908c-0dc39d0d40de`)
Offline scoring detected that `RetrieveHybrid` returned chunks belonging to document `fa85cb0e-13f9-4909-908c-0dc39d0d40de` (`Moneyline_Betting...txt`), which is present in PostgreSQL and LanceDB (`data/lancedb-eval/`) but missing from `document_map.json`.
* Cross-audit revealed **367 documents** exist in PostgreSQL `lancet_eval.documents`, whereas `subset_selection.json` and `document_map.json` only map **347 documents**.
* The 20 extraneous documents in the database index leak into search results, tripping the harness's structural integrity check.

### C. Graph Ineffectiveness on Multi-Hop Questions
On the 143 answerable, usable dual-success pairs:
* **Exact Match (EM)**: `graph-on` = 0.0000, `graph-off` = 0.0000 (delta: +0.0000).
* **Token F1**: `graph-on` = 0.0199, `graph-off` = 0.0223 (delta: -0.0024).
* **Recall@4**: `graph-on` = 0.3648, `graph-off` = 0.3613 (delta: +0.0035).
* **Graph Presence Rate**: Only **9.8%** (14 / 143).
* **Notices in `graph-on`**: 89 `GRAPH_TIMEOUT`, 40 `GRAPH_UNAVAILABLE`.
* **Root Cause**: Lancet's graph query mechanism performs a single cosine nearest-neighbor search (`nearest_to(query_embedding).limit(1)`) of the entire complex natural language query against entity `name_vector`s, requiring `score >= 0.5`. Whole multi-hop questions rarely have high cosine similarity to single entity names, resulting in `NoMatchFound` or 40s traversal timeouts.
