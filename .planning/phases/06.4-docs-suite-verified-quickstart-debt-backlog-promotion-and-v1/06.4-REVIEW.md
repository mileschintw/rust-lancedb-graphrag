## Summary

Reviewed the diff `234578f2..HEAD` for the 58 in-scope product files, reading surrounding code where a change depended on it. The wave is largely sound. Points checked and found correct:

- **D-202 startup order.** Every fallible step now precedes the worker spawn and the replay. `TcpIncoming::bind` and `read_staged_jobs` run before `spawn_worker_with_concurrency`. The only fallible step after the spawn is the replay `send`, which fails only if the worker has already exited. The held-port test has positive controls (it asserts `BM25 snapshot built` and `Prompt tokenizer ready` appear) and asserts the absence of `Staged ingestion jobs replayed`.
- **D-207 graph resolution.** It is resolved once at admission. `ctx.disable_graph_context` and `ctx.graph_off_reason` are overwritten after `WorkflowContext::new`, and no other production path reads `req.disable_graph_context`. The `graph_v2` combination check reads the resolved state, and the startup refusal for a `graph_v2` default lever is in `try_from_settings`.
- **Fail-closed env override.** `LANCET_ENGINE__GRAPH__CONTEXT_DEFAULT_ENABLED` accepts only `true`, `1`, `false`, `0`.
- **Wire additivity.** `disable_default_levers = 9` and `NOTICE_CODE_GRAPH_DISABLED_BY_CONFIG = 25` are purely additive. `disable_graph_context` was already `optional`. Code 25 is correctly excluded from `degraded_mode`.
- **A-WR-05 invariant errors.** `rerank_step` and `attach_doc_meta` now fail with an Internal error. The service wires `lever_reranker` and `doc_meta` consistently with admission, so there is no admitted-but-unwired path in production.
- **Secrets.** The `drive_environment` refusal names variables but never values. The rerank span records only the model slug, candidate count, outcome and latency. No key or query text reaches a log or refusal message.
- **Score path.** `explicit_field_failures` is correctly kept out of `provenance_failures` and `score._provenance_scan`, and a test pins that.
- **Request paths.** Every live `/rag/query` caller in `eval/src` now states its graph and lever fields explicitly. The legacy-label refusal covers `run` and `probe`.

No blocking defects were found. The warnings below are a fail-open in the new re-score checker, an override guard weaker than the repo's own sibling guard, and a test that passes vacuously on one of its two halves.

## Warnings

### WR-01: `compare_rescore.py` reports "reproduces" when `dimensions` or `result_hash` is missing from both reports

**File:** `eval/scripts/compare_rescore.py:46-65`
**Issue:** `compare()` decides equality with `committed.get("dimensions") != rescored.get("dimensions")` and `old_meta.get("result_hash") != new_meta.get("result_hash")`. If a key is absent from both reports, both sides evaluate to `None`, the comparison is equal, and the script prints `re-score reproduces the published values` and exits 0.

A report that has no `dimensions` (wrong schema, an aborted `report`, or two unrelated `report.json` files from the wrong directories) therefore passes the D-200/D-201 "published values reproduce" gate. `_load_report` only checks that the file is a JSON object.

Schema checked: the committed run-of-record reports (for example `eval/runs/2026-10-10-levers-heldout-multihop_rag_levers_heldout/report.json`) do use top-level `dimensions` and `metadata.result_hash`, so the keys match and the fail-open is only reachable for malformed or wrong-directory inputs. `eval/runs/smoke_test/report.json` has no `result_hash`, so a pair of such reports already compares equal on that half. `test_compare_rescore.py` has no case for a missing or empty key, so nothing pins the fail-closed behaviour. The same weakness applies when `committed_dir == rescored_dir`, which trivially reproduces.

**Fix:**
```python
dims_old, dims_new = committed.get("dimensions"), rescored.get("dimensions")
if not isinstance(dims_old, (list, dict)) or not dims_old:
    reasons.append("committed report.json has no scored dimensions")
elif dims_old != dims_new:
    reasons.append("scored dimensions differ")
...
for side, meta in (("committed", old_meta), ("re-scored", new_meta)):
    if not isinstance(meta.get("result_hash"), str) or not meta["result_hash"]:
        reasons.append(f"{side} metadata.result_hash is missing")
```
Also refuse when `committed_dir.resolve() == rescored_dir.resolve()`, and add tests for an empty object and for two reports that each lack `dimensions`.

### WR-02: The D-211 `--preregistered-override` matches the spec but is not bound to the corpus and is weaker than the sibling guard in `run`

**File:** `eval/src/lancet_eval/measure.py:618-690` (`_override_problem`, `_enforce_measure_split_role`)
**Issue:** D-211 only asks for "an explicit pre-registered override", so this is not a spec violation; it is a weaker proof than the repo already uses elsewhere. The override unlocks a held-out or split-less corpus when the token (a) starts with `PREREGISTRATION_`, (b) resolves to an object with `reference_arm` in `thresholds`, and (c) has some introducing commit via `git log -S`. Nothing ties the token to the corpus being measured.

The corpus config carries its own `preregistration_token`, and `run._enforce_split_role` uses it. The tests already show the gap: `PREREGISTRATION_06_3_5` unlocks `multihop_rag`, and any committed token unlocks `multihop_rag_levers_heldout`.

The guard also skips the checks `run` applies through `gitcheck.preregistration_problems(..., require_clean_tree=True, unchanged_since_introduction=True)`. It does not check that the introducing commit is an ancestor of HEAD, that the tree is clean, or that the constant is unchanged since introduction.

The effect is that a paid latency pass can spend held-out questions on any committed pre-registration name. This is a typed confirmation, not the proof the docstring implies.

**Fix:** For a `heldout` corpus, require `preregistered_override == config.preregistration_token`. Reuse `gitcheck.preregistration_problems((token,), require_clean_tree=True, unchanged_since_introduction=True)` instead of the bare `introducing_commit` lookup. For a role-less corpus, either keep the "any committed token" rule and say so in the docstring, or bind it to an explicit allowlist.

### WR-03: The Go cross-runtime `d198_opt_out_runs_no_lever` check only discriminates through an uncontrolled real-network call

**File:** `gateway/main_test.go:2832-2870` (with `engineEnv` at `:2625-2634`)
**Issue:** The engine child env sets mock endpoints for embeddings, model metadata and chat, but not `LANCET_OPENROUTER__RERANK_ENDPOINT`. The committed default levers are `["rerank", "evidence_metadata"]`, and `main.rs` always wires the lever reranker. So the baseline request and the two new subtests, `d207_absent_field_runs_graph_off_with_code_25` (new in this wave) and `d198_opt_out_runs_no_lever`, make the engine call the real `https://openrouter.ai/api/v1/rerank` with the literal key `test-key`.

The child env is built by `ragChildEnv`, which keeps only a Windows baseline plus the extras above, and `assertCleanRAGChildEnv` allowlists the same keys. It sets no `LANCET_CONFIG_DIR` and no `LANCET_ENGINE__LEVERS__DEFAULTS`, and the engine runs with `Dir = repoRoot`, so the committed `config/config.toml` defaults apply. The opt-out assertion (`no RERANK_DEGRADED`, empty `levers`) passes only because the real call is *expected to fail* with a degrade notice when the opt-out is absent. The test therefore depends on outbound network behaviour: latency against the 1706 ms rerank timeout, DNS and egress policy. It has no positive control either, such as an assertion that the same body without the opt-out echoes `rerank` or carries code 23.

If the endpoint became reachable and answered the call, or the default set changed, the assertion could pass vacuously.
**Fix:** Point `LANCET_OPENROUTER__RERANK_ENDPOINT` at a mock path on `mock.URL` that returns a deterministic ranking. Add a control request without `disable_default_levers` that asserts `Snapshot.Levers` contains `rerank`, and keep the opt-out request asserting it is empty.

## Info

### IN-01: `explicit_field_failures` "graph ran" evidence is effectively vacuous for `graph_seed_count`

**File:** `eval/src/lancet_eval/arms.py:487-497`
**Issue:** The docstring itself says "the seed count is always on the gateway's wire when metadata exists". So `meta.graph_seed_count is not None` is true for essentially every graph-on record that has workflow metadata. The "graph node ran" branch then reduces to "workflow metadata exists", and the real work is done by the absence of notices 18 and 25.

That is sufficient today, because every off path emits 18 or 25. But when the wire carries the seed count, the `not ran` failure cannot fire, and `test_d199_explicit_field_failures_graph_on_arm_rules` pins a measured zero seed count as proof the node ran. A future off path that emits no notice would slip through.

**Fix:** Count only `graph_node_count > 0` or a graph failure notice as evidence, and treat a bare `graph_seed_count` as insufficient. If seeds are the intended proof, assert `graph_seed_count > 0`.

### IN-02: `load_official` verifies the SHA-256 and then re-opens the path for execution

**File:** `eval/scripts/gen_paper_golden.py:61-79`
**Issue:** `load_official` hashes `path.read_bytes()` and then calls `spec_from_file_location(path)` / `exec_module`, which re-reads the file from disk. The docstring and comment promise that "a swapped or tampered download never runs". Between the hash and the exec, the file can change (TOCTOU). The window is small and the threat is local, but the stated guarantee is stronger than the code.

**Fix:** Execute the bytes that were hashed:
```python
data = path.read_bytes()
if hashlib.sha256(data).hexdigest() != OFFICIAL_FILE_SHA256: raise SystemExit(...)
module = types.ModuleType("official_retrieval_evaluate")
exec(compile(data, str(path), "exec"), module.__dict__)
```
Also catch `OSError` on the read so a missing path gives the same `SystemExit` message style.

### IN-03: The compiled-in `context_default_enabled = true` is the opposite of the shipped default, so a config missing the key silently reverts to graph-on

**File:** `engine/src/config.rs:204-221`, `config/config.toml:137-148`
**Issue:** The owner decision (D-207) is graph default-off. The code default is `true`, and the shipped files carry `false`, pinned by a two-file test. Any engine started without the key, such as an operator's older copy of `config.toml`, a `LANCET_CONFIG_DIR` pointing at a pre-6.4 directory, or no config file, silently runs graph-on and emits neither code 25 nor any startup line.

`LANCET_CONFIG_DIR` is warn-only in D-199, so the harness would not refuse it either. The eval arms are protected by explicit fields. A plain API client is not.

**Fix:** Log the resolved value once at startup, for example `graph_context_default_enabled=false` in the "Rust RAG Engine serving" line. Alternatively, log a WARN when the key is absent from the loaded file and the compiled-in `true` is used.

### IN-04: The port is now bound while the replay can still block

**File:** `engine/src/main.rs:186-229`
**Issue:** `TcpIncoming::bind` moves the listening socket ahead of the replay. The `sender.send(job).await` replay loop awaits when the queue (`QUEUE_CAPACITY`) is full and the worker is draining paid extraction jobs.

For that whole interval the kernel accepts TCP connections that nothing serves. Before, the port was unbound and clients got `connection refused`. A TCP-level readiness probe (a wait-for-port check, or a gateway that dials before the first RPC) now sees the engine as up while the gRPC server is not yet serving. Clients hang until their deadline instead of failing fast.

The tests do not cover this. The bind-first order is the intended D-202 trade-off, so this is a documentation or readiness-contract note rather than a defect.

**Fix:** State in the quickstart that readiness is the `Rust RAG Engine serving` log line or a successful gRPC health RPC, not an open port. Optionally move the replay `send` loop into a spawned task so the serve call is not delayed behind a full queue.
