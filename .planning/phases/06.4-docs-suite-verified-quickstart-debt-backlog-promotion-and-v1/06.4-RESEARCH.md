### A. Lever-free control arm (resolves 06.3.6 D-195)

- **D-198:** **The proto gains an additive opt-out from configured default levers.**
  - **Semantics:** a request field (shape and name at Claude's discretion; e.g. `optional bool use_default_levers`,
    absent = today's behaviour) lets a request say "run exactly the levers I list, even none".
  - **Unchanged behaviour:**
    - a request that names levers still runs exactly those, never the union;
    - an absent field keeps today's behaviour (no levers named → configured defaults);
    - explicitly named levers still fail closed with `lever_unavailable`.
  - **Wiring:** the snapshot echo reports what actually ran. The field is plumbed through the gateway's `/rag/query`.
    It is one additive regeneration, following 06-CONTEXT D-74's single-change discipline.
  - **Harness:** every canonical arm sends it explicitly. The control arms (`dense-only`, `bm25-only`, `hybrid`,
    `hybrid+graph`) send the opt-out with no levers. Legacy labels keep their byte-identical bodies, for re-scoring
    only, never for a new drive.
  - **Docs:** SC-5 documents the field as contract.
  - **Reversibility:** one-way. It is a published gRPC and HTTP request field; removing it breaks any client or harness
    arm that sets it.
- **D-199:** **The env/config refusal lives in committed harness code, not in a launcher script.**
  - **Why:** today's "refusal launchers" are per-session, gitignored `data/oi02-evidence/*/launch.ps1` and
    `env-check.ps1`. There is no committed file to extend.
  - **Refusals:** `lancet-eval preflight` and every gated `run --gate-stage` refuse when:
    1. `LANCET_ENGINE__GRAPH__*` or `LANCET_ENGINE__LEVERS__*` is set in the drive environment;
    2. any arm's echoed lever set or graph state differs from what that arm declares. This is checked per-arm by a
       canary.
  - **Authority:** the echo check is authoritative, because the harness cannot read the engine's own environment.
  - **Tests:** cover both refusals.
- **D-200:** **The quickstart's "run the eval" step is an offline re-score of the 06.3.6 run of record. The live
  check of the new request fields is one `lancet-eval preflight` per platform.** No new paid eval drive runs in this

### C. Graph context default (new finding in this discussion)

- **D-206:** **Finding, recorded as fact.** A plain request today runs hybrid + graph v1 + rerank + evidence_metadata.
  - `disable_graph_context` is an opt-out (`proto/lancet/v1/lancet.proto:93-96`: "`graph-on` is the absent/false
    state").
  - Every 06.3.6 lever arm was measured with the graph off (`eval/src/lancet_eval/arms.py`: the `hybrid+rerank`,
    `hybrid+metadata` and `hybrid+answer-format` arms set `disable_graph_context=True`).
  - The combination a default request receives was therefore never measured. `hybrid+all` does not match it either: it
    carries graph-v2 and answer-format.
  - On the 06.3.6 drive, graph v1 added about 12 ms of RetrieveHybrid time and about 176 prompt tokens, for no
    measured gain (`hybrid+graph` − `hybrid`: `answer_usable` −0.0065, Hits@4 −0.0162).
- **D-207:** **Graph context ships default-off** (owner, 2026-10-11).
  - **Config:** a config default (key at Claude's discretion, e.g. `[engine.graph] context_default = false`; TOML+env
    convention, fail-closed per 06-CONTEXT D-84) sets the graph state for a request that leaves
    `disable_graph_context` absent.
  - **Field semantics:** move to the D-12 pattern already used by `allow_model_only`: absent = configured default,
    `false` = explicitly on, `true` = explicitly off.
  - **The shipped default request becomes `hybrid` + rerank + evidence_metadata.** That is the closest measured shape,
    but the two levers together are still never decisionally tested; the interaction caveat stays.
  - **Interaction rule:** a request that names `graph_v2` while the graph state resolves to off must fail closed
    (the D-165 class), never silently enable or drop.
  - **Commit discipline:** made in the code-first wave in one commit outside any measured system, as an owner decision.
  - **Downstream:** goldens and tests that render the default request are reviewed and moved only with justification.
    The proto comment is updated. The docs describe the graph as built, measured and opt-in (D-216).
  - **Explicit amendment of 06-CONTEXT D-47** (same pattern as D-11 amending Phase 05 D-03). D-47 published
    `disable_graph_context` with absent meaning "graph on". D-207 makes absent mean "the configured default", and that
    default is now off. The proto comment at `lancet.proto:93-96` changes with it.
  - **The harness and the gateway must send the field when they mean it** (scope added after the discussion, verified
    in code):
    - **Harness:** `eval/src/lancet_eval/client.py:271-272` sends `disable_graph_context` only when it is `True`. So
      `hybrid+graph`, `hybrid+graph-v2` and `hybrid+all` currently send no field. Under D-207, `hybrid+graph` would
      silently run graph-off, `hybrid+graph-v2` would be refused by the interaction rule above, and their preflight
      canaries would fail.
    - **Harness fix:** every canonical arm sends the field explicitly, `false` included, alongside D-198's explicit
      lever field. The D-199 canaries assert the effective graph state per arm. Legacy labels keep their recorded
      bodies, for re-scoring only.
    - **Gateway:** it already carries presence (`gateway/main.go:590`, `DisableGraphContext *bool`; forwarded at
      :805). Planning only needs to verify that HTTP absent, `false` and `true` reach the engine distinctly.
  - **A config-off response carries a new informational notice code** (owner, 2026-10-11).
    - `RetrievalSnapshot` has no graph-state echo, so without a notice a default response could not attribute why the
      graph did not run.
    - A response whose graph is off only by configured default carries a new code (name at Claude's discretion, e.g.
      `GRAPH_DISABLED_BY_CONFIG`; INFO severity). Like `GRAPH_ABLATION` (code 18), it is excluded from the
      `degraded_mode` set in `engine/src/workflow/mod.rs`.
    - `GRAPH_ABLATION` stays for an explicit `disable_graph_context = true`, so the eval's ablation arms keep it
      unchanged.
    - Both codes are documented in SC-5. The new code lands in the same additive proto regeneration as D-198.
  - **Reversibility:** one-way. It changes what every client that omits `disable_graph_context` receives (a published
    default behaviour, amending D-47's one-way field) and adds an enum value to the published contract. Undoing the
    default is a config flip, but the field semantics and the new code cannot be withdrawn once clients observe them.
    `gsd-planner` must raise a `checkpoint:decision` before the implementing task.

The most plan-shaping findings, in order of consequence: **(a)** D-217 and ROADMAP SC-1 promise a "rerank node timing and its leaf span" in Jaeger, but the engine has no rerank span at all (`engine/src/rerank/` and `retrieve.rs` contain no `info_span!`/`#[instrument]`), which is also a gap against inherited 06-CONTEXT D-29; this needs an owner decision (add a leaf span in the code-first wave, or amend D-217/SC-1). **(b)** The D-202 bind reorder must call `.with_nodelay(Some(true))` on the incoming stream, because tonic 0.14.6 applies nodelay only in its own `bind_incoming`, which `serve_with_incoming_shutdown` bypasses. **(c)** The Windows cold release build took 20 min 58 s, so every live plan needs the A / orchestrator-wait / B split, and `go run ./gateway` (README, eval/README) does not work from the repo root (the module lives in `gateway/`). **(d)** The compose project name defaults to the clone's directory name, so a fresh clone placed in a folder called `lancet` would share the owner's Postgres volume: the fresh-clone runs must pass an explicit different project name and the owner's dev stack must be stopped (fixed `container_name`s and loopback ports collide regardless). **(e)** The graph "+106 ms / +176 tokens" figures in CONTEXT are unpaired arm-mean differences; the paired readings across the three runs are +1220.6, +356.7 and -18.5 ms of total latency, so the results page must reconcile on the graph node's own timing and the stable +198 prompt tokens.

## Common Pitfalls

### Pitfall 1: shallow clone breaks the re-score
**What goes wrong:** `score` refuses with the D-73 message. **Why:** `git log -S` finds HEAD as the "introducing commit" (`gitcheck.py:108,308`). **How to avoid:** the clone step says full clone; troubleshooting says `git fetch --unshallow`. **Warning signs:** "is not older than the journal header's created_at".

### Pitfall 2: compose project name is the directory name
**What goes wrong:** a clone in a folder called `lancet` reuses `lancet_postgres_data`. **How to avoid:** a different directory name and `-p lancet-qs`; owner checkpoint to `down` the dev stack (no `-v`). **Warning signs:** `docker compose ps` shows containers from the wrong project; the Postgres already holds `lancet_eval`.

### Pitfall 3: Nagle returns with the bind reorder
**What goes wrong:** `TcpIncoming::from(listener)` leaves `nodelay` unset (tonic's own path sets `Some(true)`, `mod.rs:132,653-660`), so SSE streaming latency changes. **How to avoid:** `.with_nodelay(Some(true))`.

### Pitfall 4: `go run ./gateway` from the root
**What goes wrong:** `go: cannot find main module`. **How to avoid:** `cd gateway && go run .`; fix README and `eval/README.md:41`.

### Pitfall 5: CRLF checkouts change the lock hash (not the numbers)
**What goes wrong:** `dependency_lock_hash` differs on a Windows clone. **How to avoid:** the "reproduces" definition allowlists it (Finding 1).

### Pitfall 6: PowerShell `curl` is `Invoke-WebRequest`
**How to avoid:** `curl.exe`, or the `quickstart.py` helper.

### Pitfall 7: Grafana panels empty
**What goes wrong:** "No data" in rate panels. **Why:** no query inside the time window (`rate(...[5m])`). **How to avoid:** capture within minutes of a query burst, `from=now-15m`.

### Pitfall 8: Jaeger trace unreadable
**What goes wrong:** 700+ spans from Lance internals. **How to avoid:** capture from the fresh sample store, immediately.

### Pitfall 9: the rerank leaf span does not exist
**What goes wrong:** the walkthrough promises something Jaeger cannot show. **How to avoid:** resolve O1 before writing the walkthrough.

### Pitfall 10: D-207 breaks `graph_v2` arms and legacy `graph-on`
**What goes wrong:** `hybrid+graph-v2` with no explicit field is refused; `probe --arm graph-on` runs graph-off. **How to avoid:** every canonical arm sends an explicit `disable_graph_context` (Finding 3).

### Pitfall 11: the graph path is not guaranteed on a 5-document store
**What goes wrong:** the opt-in screenshot shows no `graph_traversal` result. **How to avoid:** gate on `graph_path_found` for the example query; adjust the sample text.

### Pitfall 12: executors lose processes
**What goes wrong:** engine and gateway die when the executor exits; a 21-minute build exceeds the Bash cap. **How to avoid:** one start-verify-stop script per platform; orchestrator runs the build.

### Pitfall 13: WSL non-login PATH
**What goes wrong:** `uv: command not found`. **How to avoid:** `export PATH="$HOME/.local/bin:$HOME/.cargo/bin:$PATH"`.

### Pitfall 14: the Go test cache masks config
**How to avoid:** always `go test -count=1 ./...` (memory).

### Pitfall 15: `--locked` and the `sha2` dependency
**What goes wrong:** `cargo test --locked` fails after adding `sha2` to `Cargo.toml` until the lock is updated. **How to avoid:** update and commit `engine/Cargo.lock` in the same commit.

### Pitfall 16: `phase.complete` flips shared requirement IDs
**How to avoid:** diff `REQUIREMENTS.md` afterwards (memory: requirement-revert-shared-id-footgun).

### Pitfall 17: the D-73 gates read the harness source tree
**What goes wrong:** `score` refuses a dirty `eval/src/lancet_eval/`, and a pre-registered token whose assignment changed. **How to avoid:** commit all eval edits before running the re-score; never touch the value of `PREREGISTRATION_06_3_6` or other pre-registered constants (`gitcheck.py:195-262`).

### Pitfall 18: the inherited user-level key masks a broken `.env` flow
**What goes wrong:** `[MEASURED]` the host has `OPENROUTER_API_KEY` set at user level and in this shell, and there is no `.env`, so a "clean" Windows run would silently use the inherited variable and never test the documented `.env` export. **How to avoid:** the verification script clears the variable (`Remove-Item Env:OPENROUTER_API_KEY`), exports from `.env`, and asserts the engine starts; D-220's "only `.env` supplied" is only true if the process environment holds nothing else.
