### Summary

Slice A is mostly sound. The rerank adapter, the lever admission path, the proto wire and the
gateway edge validation all hold up under adversarial reading:

- The rerank reply is parsed under a 1 MiB cap, bounds-checked as a permutation, and checked for
  finite scores. Errors carry the failure class only.
- No key or provider body reaches a log line or notice. `Debug` is hand-written, redirects are off,
  and transport error text is dropped.
- The wire is additive: new field tags 8, 15, 17 and 18, new enum values, and Go and Rust bindings
  agree.
- Timeout nesting is consistent: 2286 + 294 + 500 = 3080 is enforced at startup. The per-call
  allowance is `min(rerank_timeout, node_budget - elapsed - 50ms)`, and the client timeout equals
  the config timeout.
- The test-count scripts add up: gateway 83+7+4+1+17+12 = 124 and engine 813+58+0+18+14+24 = 927.

No Critical finding. The warnings concentrate on how the D-157 default levers behave once they are
in force for every request, not on the adapter itself. The disclosed items (eval arms inheriting the
defaults, and an engine over a store with no metadata refusing to start) are not re-reported.
A-WR-01 and A-WR-04 are interactions with them.

### Warnings

#### A-WR-01: Default-lever fail-closed check runs after side effects, so a refusing start still replays staged ingest jobs

**File:** `engine/src/main.rs:131-165, 195-202`
**Issue:** `validate_default_levers` is called after `spawn_worker_with_concurrency`, after
`spawn_rebuild_debounce_task`, and after `read_staged_jobs` has pushed every staged job into the
worker queue. The worker starts embedding and running LLM extraction as soon as it receives a job.
When the check then fails, `main` returns `Err` and the process exits mid-replay.

The failure case is exactly the disclosed one: committed `defaults` over a store with no metadata.
Under a restart-on-failure supervisor this becomes a crash loop that re-spends OpenRouter
embedding and extraction calls on the same staged jobs each cycle. The "refuses to start" guarantee
is also weaker than documented, because the store has already been written to.

**Fix:** Validate before any task is spawned or any staged job is read. The inputs are all
available right after `initial_snapshot` is built: `effective_settings.default_levers`, the
snapshot, whether a lever reranker exists, and `graph_v2_chunk_precision`. Make
`validate_default_levers` a free function of those, or construct the `LeverResources` before the
spawns, and call it immediately after the snapshot build.

```rust
// after initial_snapshot is built, before spawn_worker_with_concurrency
engine::service::validate_default_levers_for(
    &effective_settings, &initial_snapshot, /* rerank wired */ true,
).map_err(|err| format!("invalid lever defaults: {err}"))?;
```

#### A-WR-02: A configured default lever becomes a hard 400 for every request when the live snapshot loses its metadata

**File:** `engine/src/service.rs:200-210, 1235-1272` (interaction with `engine/src/ingest.rs:1897-1940`)
**Issue:** `evidence_metadata` availability is `!snapshot.doc_meta.is_empty()`, and it is evaluated
per request against the current snapshot. Startup validation only proves it at boot. After a
rebuild, `rebuild_and_swap` swaps in a freshly scanned `DocMetaMap`. If the last metadata-bearing
document is deleted or replaced by documents ingested without the optional `doc_title`, `source`
and `published_date` form fields, the map becomes empty.

From then on every request that names no lever resolves to the defaults, fails the availability
check, and gets `InvalidArgument` / `lever_unavailable`. The gateway maps `InvalidArgument` to
HTTP 400 and echoes the message (`handlePreStreamError`, `gateway/main.go:927`). Consequences:

- The client sent a valid request, and a server-side corpus state is reported as a client error.
- Recovery needs a restart, and the restart itself refuses to start (the disclosed behaviour)
  unless the env override is set.
- Nothing in `/health` signals the state.

**Fix:**
- When the unavailable lever came from the configured defaults rather than from the request, return
  `FailedPrecondition` or `Unavailable`, with a distinct `x-lancet-error-kind` such as
  `default_lever_unavailable`. A client then sees a 5xx.
- Consider degrading with a loud notice and metric instead of failing closed at request time. The
  startup check already provides the strict guarantee.
- Log at WARN when a rebuild swaps in a snapshot that makes a configured default unavailable.

#### A-WR-03: The `evidence_metadata` availability predicate is "any one document has metadata", so the lever can silently no-op for almost every chunk

**File:** `engine/src/service.rs:206`, `engine/src/workflow/nodes/retrieve.rs:199-208`
**Issue:** One metadata-bearing document out of thousands passes both the startup check and the
per-request check. `attach_doc_meta` silently skips every block whose document has no entry.
The snapshot echo still reports `evidence_metadata` as admitted and the prompt still carries the
metadata policy sentence, so the arm is attributed to a lever that did nothing for most blocks.
This is the "lever silently no-op'ing" class the phase wanted to exclude. Startup logs
`doc_meta_documents` and `document_count` side by side but nothing compares them.

**Fix:** Compute coverage (documents with metadata over distinct documents in the snapshot) and
either require a minimum for availability, or record it. Put a per-query `blocks_with_metadata /
blocks` count in the `workflow_completed` metadata or the `retrieve_hybrid_substages` event. At
minimum, log a startup WARN when coverage is below 100%.

#### A-WR-04: There is no way to express a lever-free request once defaults are configured

**File:** `gateway/main.go:596-604, 790-800`, `engine/src/service.rs:1235-1240`, `proto/lancet/v1/lancet.proto:107`
**Issue:** `levers` absent, `null` and `[]` all become an empty `repeated Lever`, which the engine
treats as "use the defaults". A caller who names any lever gets exactly that set, so
`["binary_answer_format"]` drops rerank and metadata. But no request can ask for the empty set.
The only lever-free baseline is restarting the engine with `LANCET_ENGINE__LEVERS__DEFAULTS=`.
This goes beyond the disclosed "arms omitting `levers` now get the defaults": the baseline arm
can no longer be requested at all, so any control or ablation that needs "no levers" must run
against a separately configured engine process, and the echo cannot tell the two apart by
construction.

**Fix:** Add an explicit opt-out the engine can distinguish from absence. For example, a
`bool no_default_levers = 9` on `QueryRAGRequest` (proto3 `optional`) and a gateway field
`"levers": []` handled as explicit-empty only when the key is present (`*[]string` already
distinguishes null from `[]`). Update the contradicted comments (see A-IN-01).

#### A-WR-05: An admitted `rerank` lever falls through to the strict path with no error if the node has no lever reranker

**File:** `engine/src/workflow/nodes/retrieve.rs:215-250`
**Issue:** `rerank_step` takes the lever path only when `self.rerank_lever.is_some()` and
`ctx.levers.contains(Rerank)`. If `ctx.levers` contains `Rerank` but `rerank_lever` is `None`, it
silently falls through to the service reranker. In production that is `NoOpReranker`, which keeps
the fused order. The snapshot echo, built from `ctx.levers.to_wire()`, then claims `rerank` ran,
and `ctx.rerank` stays `None`.

`service.rs` prevents this today by refusing admission when no lever reranker is wired and by
building the node with the reranker only when the lever is present. But the node itself does not
enforce the invariant. Any other constructor (a harness bin, a test double, a later refactor of
`build_production_workflow_with_levers`) turns it into a silent no-op, which is the failure mode
D-136 was written to prevent.

**Fix:** In `rerank_step`, when `ctx.levers.contains(Lever::Rerank)` and `self.rerank_lever` is
`None`, return `NodeError::new(NodeErrorKind::RetrievalFailed, "rerank lever admitted without a
lever reranker")`. Mirror this in `attach_doc_meta`: when the lever is admitted and `self.doc_meta`
is `None`, fail instead of returning silently.

#### A-WR-06: Gateway accepts invalid UTF-8 in `doc_title` and `source`; the failure surfaces as a 502 after staging begins

**File:** `gateway/main.go:384-410`, `gateway/internal/engineclient/engineclient.go:116-125`
**Issue:** `validMetaText` bounds the rune count and rejects control characters, but not invalid
UTF-8. Go's `utf8.RuneCountInString` counts each invalid byte as one rune. A multipart field
carrying invalid bytes passes validation. `stream.Send` then fails in protobuf-go's proto3 string
check on marshal. The caller gets `502 engine ingestion failed` and the compensation path runs
(`compensateFailedIngest`), after the gateway has already inserted the document row. This is a
client error reported as an upstream failure, with write-and-undo churn. The same applies to the
rest of the multipart-derived strings.

**Fix:**
```go
func validMetaText(v string, maxRunes int) bool {
    if !utf8.ValidString(v) || utf8.RuneCountInString(v) > maxRunes {
        return false
    }
    return !strings.ContainsFunc(v, unicode.IsControl)
}
```
The same applies to `published_date`: `time.Parse` already rejects non-ASCII.

#### A-IN-01: Comments and docs now contradict the shipped default behaviour

**File:** `proto/lancet/v1/lancet.proto:107`, `gateway/main.go:596-598`, `gateway/internal/sse/dto.go:73-76`
**Issue:**
- Proto: "empty == absent == today's request".
- Gateway: "Absent or an empty array is today's request".
- DTO: "omitted when no lever was admitted, so a default snapshot keeps exactly its 10 keys".

With `defaults = ["rerank","evidence_metadata"]` an empty request is the defaults run, and a
default snapshot now carries `levers` (11 keys). Downstream consumers that key on the 10-key shape
will see a change. The generated Go and Rust bindings repeat the proto comment.
**Fix:** Reword all three, and regenerate bindings.

#### A-IN-02: `rerank_endpoint` is not scheme- or host-validated, and the generator bearer key is sent to it

**File:** `engine/src/config.rs:1020-1022`, `engine/src/main.rs:94-107`
**Issue:** The lever reuses the generator key (D-131), but the endpoint check is only
non-empty. An `http://` URL, or a host other than the key's issuer, would send the bearer key in
clear text or to a third party. The key reaches the endpoint with no confirmation that it is the
same trust domain as `chat_endpoint`. The file-only (not env-overridable) design limits exposure,
and the other endpoints share the gap.
**Fix:** Require `https` (or loopback for tests) and, ideally, the same host as `chat_endpoint`.

#### A-IN-03: `LeverSet` is a `u8` mask with no guard against a ninth lever, and `DECLARED` is not compiler-checked against the enum

**File:** `engine/src/workflow/levers.rs:17-22, 221-223`
**Issue:** `1_u8 << (lever as i32 - 1)` overflows for enum number 9 and above (a panic in debug,
a wrong bit in release). `DECLARED` is a hand-written array. A lever added to the proto but not to
`DECLARED` would be admitted by `try_from_wire` (it uses `Lever::try_from`) yet dropped by
`to_wire` and `iter`. `wire_name` and `is_available` are exhaustive matches that force an update,
but `DECLARED` is not.
**Fix:** Add a unit test iterating `Lever::iter()` (or `0..=N` through `Lever::try_from`) that
asserts it equals `DECLARED` plus `Unspecified`, and a `const _: () = assert!(DECLARED.len() <= 8);`.

#### A-IN-04: `maxRequestLevers` duplicates `len(leverByName)`

**File:** `gateway/main.go:604-615`
**Issue:** The constant 4 must be bumped by hand with the map.
**Fix:** Use `len(leverByName)` at the comparison.

#### A-IN-05: The backfill `--apply` safeguard accepts any directory that contains a `nodes.lance`, and allows partial sidecar coverage

**File:** `engine/src/bin/backfill_evidence_metadata.rs:243-267, 365-384`
**Issue:**
- `check_snapshot` only checks that `<dir>/nodes.lance` exists and is outside the live store.
  A stale, empty or wrong copy passes. The version-preserving design (no compaction) still allows
  a restore, so this is a weak guard rather than a data-loss path.
- `--apply` proceeds with uncovered documents (null rows), reporting them only in the outcome.
  The eval store then runs `evidence_metadata` with silent gaps (see A-WR-03).
- There is no check that the engine is stopped. `add_columns` with a reader depends on two scans
  of `document_id` matching the scan Lance performs internally. A concurrent writer is caught only
  when the row count changes.

**Fix:** Require the snapshot's `nodes.lance` version and row count to equal the live table. Add
`--require-full-coverage` (default on for `--apply`). Document or enforce that the engine is
stopped.

#### A-IN-06: `inspect_lancedb --graph-dump` can leave a partial dump that blocks a retry

**File:** `engine/src/bin/inspect_lancedb.rs:1643-1668`
**Issue:** The existence check runs before the three writes. If the second or third `fs::write`
fails, the first file remains. A rerun then refuses ("a graph dump is never replaced") until the
operator cleans up by hand. `dump_meta.json` is written last, so completeness is detectable, but
nothing removes a partial dump.
**Fix:** Write to a temporary sibling directory and `rename` it into place, or delete the files
written so far on error.

#### A-IN-07: A pinned `generation_provider_order` with fallbacks off, and a rerank call with no breaker, apply to all production traffic

**File:** `config/config.toml:168-170`, `engine/src/generation/openrouter.rs:352-360`, `engine/src/workflow/nodes/retrieve.rs:257-333`
**Issue:**
- The committed `config.toml` pins generation to `sail-research` with `allow_fallbacks=false`
  (D-191). There is no failover.
- The rerank lever has no circuit breaker. During a provider brownout every default request waits
  the full allowance (up to 2286 ms) before degrading, so latency rises for all traffic. Each
  degrade also marks `degraded_mode=true`.

Both are recorded decisions (D-191, D-192). Neither is a defect on its own, but both are
single-provider availability couplings introduced alongside the default-on change.
**Fix:** Consider a small consecutive-failure breaker around the lever reranker that skips the
call (recording `degraded_timeout` or a new outcome) for a cool-down window, and note the
generation pin as a deliberate SPOF in the runbook.

### Warnings

#### B-WR-01: `compare-levers` takes the provenance block, gates and report on trust, with no binding to the journal

**File:** `eval/src/lancet_eval/lever_comparison.py:1236-1243, 470-479, 1355-1358`
**Issue:**
- `provenance_block_passed` is read from `report.json`: `_provenance_passed` returns True when `arm_provenance_conformance` is `ok` and `records_failing_zero_tolerance == 0.0`.
- That dimension is a constant written by `score.py` (`status="ok"`, `records_failing_zero_tolerance: 0.0`). It is tautological once a report exists.
- Nothing ties `report.json` or `gates-heldout.json` to the journal being read.
  - There is no hash, record count or `partial` check, and no check of the header's `gate_stage` or `split_sha256`.
  - `load_gates` does not check the `stage` key or that the file covers the same arms.
- The populations, p-values and guards are recomputed from the live journal.
- The consequence is that a journal extended or re-driven after `score` (a D-110 re-drive) can show `provenance_block_passed: true` and `gate_reads` from an older run.
- With a `PASS` gate reading and a Holm rejection, `decide_default` can then return `default` for a lever whose journal now holds zero-tolerance failures.
- Unlike `comparison.py`, which refuses stale sidecars, this path has no staleness gate.

**Fix:**
- Recompute the block from the journal records already loaded in `build_lever_comparison`, instead of trusting the report:
```python
counts = Counter()
for r in records:
    for f in provenance.provenance_failures(r):
        if f.code in provenance.ZERO_TOLERANCE_CODES:
            counts[f.code] += 1
prov_ok = not counts
```
- Refuse if `report.metadata.partial` is true or the report's record count differs from `len(records)`.
- Require `gates["stage"] == "heldout"` and `set(gates["arms"]) == set(arms_of(prereg))` before using gate readings.
- Also require the header markers `gate_stage == "heldout"`, `max_retries == 0` and `split_sha256 == split_sha256(split)`.

#### B-WR-02: The O10 rerank tripwire resets on `--resume`, while the spend cap does not

**File:** `eval/src/lancet_eval/run.py:97-99, 677, 735, 775`
**Issue:**
- The docstring says "Counts are per invocation, like the cap's per-drive window". That is wrong. The cap is journal-cumulative: `records = load_records(target_path)` on resume and `compute_spend(records)` for the cap check.
- The tripwire is built fresh (`tripwire = rerank_tripwire_for(config)`) and fed only records produced in this invocation.
- So after a tripwire halt (>20% degrades over at least 50 attempts, or 5 in a row), `drive --resume` starts from zero. It will make at least 5 more degraded paid calls, or 50 more attempts, before it can halt again.
- It ignores the degrade evidence already in the journal.
- A scripted resume loop therefore cannot be stopped by O10.
