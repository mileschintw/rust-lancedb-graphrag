  <behavior>
    - **Failure retention:** a stream containing a `node_failed` frame produces a raw file whose
      lines replay the frames in arrival order with their event names and data payloads.
    - **Baseline retention:** a clean success whose question is in the baseline sample produces
      a raw file; a clean success outside the sample produces none.
    - **Deterministic sample:** the baseline set computed from a given question list is the same
      on every call and is independent of thread scheduling and of the order work units
      complete.
    - **Per-unit cap:** a stream whose frames exceed the byte cap produces a file that stops at
      the cap and ends with a truncation record naming the number of frames not written. No
      frame is dropped without that record.
    - **In-memory bound:** the buffer held during streaming is capped by the same limit, so a
      never-ending stream cannot exhaust memory before the deadline fires.
    - **No secrets:** the written records contain only the event name and its data; no HTTP
      header, no request body, no environment value, no base URL appears in any line.
    - **Off by default:** `run_query` called without the capture option behaves exactly as
      before and returns no raw payload — the preflight canary in task 3 relies on this.
    - **Never raises:** a sink whose directory cannot be created, or whose write fails, records
      the problem and lets the drive continue; `drive_one`'s never-raise contract is preserved
      and a sink failure does not become a fabricated error record.
    - **Concurrency:** two work units driven concurrently write to two distinct paths and
      neither interleaves into the other.
  </behavior>
  <action>
    Create `raw_events.py` with a sink that owns the retention policy and a pure function that
    computes the baseline sample.

    The baseline rule must be reproducible from committed inputs alone: sort the driven question
    identifiers ascending and take the first twenty-five. That set is a function of the question
    list, not of scheduling, so a reader can regenerate exactly which successes were kept. Do not
    use a random sample, a hash bucket, or a running counter — all three make the committed
    artifact unreproducible.

    The sink writes one file per work unit under a `raw_events` directory inside the run
    directory, partitioned by arm and named by question identifier, one JSON object per line
    carrying a sequence ordinal, the event name and the data payload. One file per unit rather
    than one shared file, because the driver runs units concurrently and the existing journal
    append idiom takes no lock — large multi-line payloads appended from several threads to one
    handle would interleave.

    Enforce two bounds. A per-unit byte budget caps what any single unit may write; when it is
    exhausted the sink stops and writes a final record stating that truncation occurred and how
    many frames were not written. Silence here would reproduce, in the forensic artifact, the
    exact class of silent loss this phase exists to remove. The same budget bounds the in-memory
    buffer the client accumulates while streaming, so a pathological stream cannot exhaust
    memory before the wall-clock deadline fires.

    In `client.py`, add an off-by-default capture option to `run_query`. When enabled, append the
    event name and data of each frame to a bounded buffer as it arrives, and return that buffer
    on the `QueryOutcome`. Capture the frame content only: never the response headers, never the
    request body, never the client's configured base URL. The retain decision cannot be made
    until the stream ends, because it depends on whether any node failure appeared, so buffering
    is required — but the buffer is capped, so the cost is bounded whether or not the unit is
    ultimately retained. Every existing caller that does not pass the option must be unaffected.

    In `run.py`, have `drive` compute the baseline set once from the question list it is about to
    drive, construct the sink rooted at the journal path's parent directory, and pass both into
    `drive_one`. `drive_one` enables capture, and after the record is built decides retention:
    keep when the record has any node failure, or when its question is in the baseline set.
    Guard the sink call so a filesystem problem is recorded and swallowed rather than escaping
    into the surrounding blanket handler, where it would be written into the journal as a
    fabricated query error.
  </action>

    Add a canary loader, a live timeout reader and a canary check to `preflight.py`, following the
    file's existing check-function shape: a result carrying a name, a pass flag, an actionable
    message and a diagnostic detail mapping.

    The loader reads the committed canary file, validates each row against the corpus sample's
    text for that identifier, and fails the check loudly on drift rather than probing a question

    The timeout reader parses the engine's live configuration and returns the per-node budgets,
    mapping node names to configuration keys exactly as the engine's own runner does. Read the
    values at check time — do not copy them into the harness, and do not fall back to a default
    when the file is unreadable. A silent default here would let a canary pass against a budget
    nobody configured, which is the opposite of D-12's purpose: this check is what makes the
    budgets 06.3.3 derives actually binding. Read only the workflow timeout keys; the same file
    holds provider configuration, so neither the parsed document nor any part of its contents may
    appear in a message, a detail value or a log line.

    The check drives each canary row through the same client path a real run uses, with the graph

    chunk count, the graph node requirement where present, the completion requirement on the null
    row, the ablation notice on the twin, and for every row each observed node duration against
    that node's configured budget. Accumulate all failures across all rows and report them

    Register the check in `run_preflight_checks` inside the branch that already gates on the
    gateway and engine being reachable, alongside the corpus generation check. Reuse the client
    the aggregator already manages; do not open a second one.
  </action>
