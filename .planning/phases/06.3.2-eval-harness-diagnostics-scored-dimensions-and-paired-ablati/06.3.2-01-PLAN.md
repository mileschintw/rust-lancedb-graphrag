<objective>
Stop the eval harness throwing away the diagnostics the engine already emits, and stop it
writing `success` on a workflow that failed. One wire field is carried the whole way — SSE
frame to journal record to usable-record filter to scored dimension to a row in `report.md` —
and the denominator convention that let infrastructure failure masquerade as a quality score
is made consistent across retrieval and answer dimensions.

This is the tracer slice for Phase 06.3.2. Every later plan in this phase expands sideways
from the path this plan proves end to end.

Purpose: the 2026-09-03 recorded run wrote `outcome: success` on all 1000 records while 966
of them carried a hard node failure and an empty answer (verified directly against
`eval/runs/2026-09-03-multihop_rag/journal.jsonl`: 904 `RetrieveHybrid`, 47 `AssemblePrompt`,
9 `GenerateAnswer` hard failures; 966 empty answers; 34 snapshots). The false green came
entirely from the harness — `run.py:58` hardcodes the outcome and discards the
`QueryOutcome.status` that `client.py:232-242` already computes correctly. Until that is
fixed nothing downstream in this phase can be believed.

Output: wire-diagnostic capture (D-01), the D-27 harness-half outcome fix, the D-34 usable
record predicate and denominator convention, `unusable_record_rate` and `vector_yield` as
scored dimensions, and a report template that shows a failed dimension's diagnostic counts.
</objective>

<open_decision_resolved>
**`DimensionResult._validate_consistency` (`dimensions.py:33-41`) forbids a non-empty `detail`
on `status="error"`, while AI-SPEC section 5 requires `n_pairs=0` to yield `status=error` with
no score *and* requires the report to always print `n_pairs` and `pairing_coverage`. Both the
researcher and the pattern mapper flagged this independently and both recommended option (A).**

**Chosen: (A) — relax the validator to permit `detail` on `status` values `error` and
`skipped`, and nothing else.**

Rationale, checked against the invariant the validator actually protects: Phase 06.3's D-49
made a fabricated number unconstructable by pinning `score is None` on a non-`ok` status (and a
non-blank `reason`). That is the invariant, and it is untouched here — a non-`ok` row still
cannot carry a score. `detail` is `dict[str, float]`: diagnostic counts, never the headline
number. Option (B) would put pairing counts somewhere the report template cannot reach without
a schema change; option (C) would report a dimension that failed to compute as `ok`, which is
the exact class of dishonesty this phase exists to remove.

**Consequence handled in this plan, not deferred:** `report.md.j2:41` currently renders only
`d.reason` for a non-`ok` row and drops `detail` entirely, so relaxing the validator alone
would still leave `n_pairs`/`pairing_coverage` invisible. The template change ships here with
the relaxation so plan 06.3.2-04 cannot pass its own criteria while the requirement is unmet.
</open_decision_resolved>
