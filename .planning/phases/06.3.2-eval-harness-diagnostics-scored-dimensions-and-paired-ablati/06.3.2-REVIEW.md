# Phase 06.3.2: Code Review Report

**Reviewed:** 2026-09-05T00:00:00Z
**Depth:** standard
**Files Reviewed:** 36
**Status:** issues_found

## Summary

Three of this phase's four crux mechanisms were traced end-to-end and hold up
cleanly:

1. **Dedup ordering** — `deduplicate_by_arm` runs once, immediately after
   journal load (`score.py:165`), strictly before arm grouping, judging,
   worksheet selection, and `form_pairs` (`score.py:755`). Keyed on
   `(question_id, graph_arm)`, never on `question_id` alone. Confirmed by
   `test_wr02_journal_wide_placement_behavioral` and the `test_ablation.py`
   end-to-end tests.
2. **Self-contradiction / `error_type` keying** — `error_type` is set only in
   `drive_one`'s harness-exception catch block (`run.py:148`); an honest engine
   failure (`outcome.status == "failed"` returned normally by `run_query`) leaves
   `error_type=None` and hits none of `is_self_contradictory`'s five clauses.
   Directly proven by `test_honesty_edge_and_unparseable_violation` and
   `test_ten_record_journal_with_five_honest_failures_scores_one`.
3. **Report template injection** — `report.md.j2` only interpolates
   `RunMetadata` fields and dimension name/status/score/n/reason/detail; no
   journal-derived question/answer/citation text ever reaches the template.
   `autoescape=False` is correct for Markdown output and introduces no
   injection path here.

The fourth crux — **denominator consistency between retrieval and answer
metrics** — does NOT fully hold. See CR-01 below: there is a reachable, usable
record shape (empty answer + absent snapshot, no hard node failure) where the
retrieval side silently excludes the record from its denominator while the
answer side scores it as a hard 0.0, which is the same structural defect this
phase's D-34/`is_usable()` work was chartered to eliminate, just relocated
inside the usable population instead of across the usable/unusable boundary.
The counter that would have surfaced this discrepancy in the report
(`retrieval_skipped`) is computed but never published.

The judge prompt (`judge.py`) interpolates retrieved-chunk excerpts verbatim
into the LLM-judge user message with no structural defense beyond a
`=== EVIDENCE ===` header — flagged below (IN-02) as a residual
prompt-injection surface worth acknowledging, though it is inherent to any
LLM-as-judge design and the corpus is a fixed, pre-vetted benchmark today.

Test coverage overall is strong and mostly discriminating — `test_ablation.py`,
`test_wire_contract.py`, `test_score_judged.py`, and `test_pairing.py` in
particular use hand-computed expected values and real wire-shaped fixtures
rather than doubles that bypass the code under test. Two test-quality gaps are
noted below (WR-04, IN-04).

## Critical Issues

### CR-01: Empty-answer/absent-snapshot usable records are excluded from retrieval denominators but scored as a hard zero in answer denominators

**File:** `eval/src/lancet_eval/score.py:230-278`
**Issue:** Inside the single `for rec in usable_records:` loop that is supposed
to be the shared, `is_usable()`-filtered population for both retrieval and
answer metrics, the two families diverge on how they handle a record with no
payload:

```python
# Retrieval dimensions strictly read snapshot.retrieved_chunks
if rec.snapshot is None:
    retrieval_skipped_count += 1        # excluded from recall/precision/MRR denominators
else:
    ...

# Answer metrics
if rec.answer is not None and not gold.is_null:
    em_out = squad_em(gold, rec.answer)  # rec.answer == "" is NOT None -> scored
    ...
```

This is reachable without any hard node failure: `client.py`'s third
`success`-path branch (`final_answer_count == 0`, `completion.final_response is
None`, `completion.notices` non-empty) returns `status="degraded", answer=None`
(`client.py:372-390`). `drive_one` then sets `answer_text = ""` (`run.py:62`,
since `outcome.answer` is `None`) and `snapshot =
outcome.partial_snapshot` (`run.py:65-69`), which is also `None` unless the
`workflow_completed` frame separately carried a `partial_snapshot`. The
resulting `RunRecord` has `outcome="success"`, `answer=""`, `snapshot=None`,
`node_failures=[]` — `is_usable()` returns `True` for it (no `outcome=="error"`,
no hard failure of `RetrieveHybrid`/`AssemblePrompt`/`GenerateAnswer`), so it
enters the shared scoring loop as a normal "usable" record.

For this record: `squad_em(gold, "")` and `squad_f1(gold, "")` both return
`status="ok"` with `score=0.0` whenever `gold.gold_answer` is non-blank
(`metrics.py:409-438` has no minimum-length guard, only a blank-gold-answer
skip) — so it is appended to `ems`/`f1s` and drags down `answer_exact_match`
and `answer_f1` as a genuine zero. Meanwhile the exact same record is silently
excluded from `recalls`/`precisions`/`mrrs`/`ndcgs` (not even scored as a zero),
because `rec.snapshot is None` short-circuits before any recall/precision call.

This reproduces the shape of the bug this phase's `is_usable()` work states it
closed ("the prior bug was retrieval excluding failures while answer scored
them as zero") — just relocated from the usable/unusable boundary to inside the
usable population, for records that carry no data at all rather than a node
failure. It also directly contradicts the report's own published caveat:
> "Infrastructure Failure Denominator Exclusion: Infrastructure-failed records
> (unusable records) are excluded from every quality denominator, retrieval and
> answer alike" (`report.md.j2:52`)
— a reader relying on this caveat would not expect retrieval and answer
denominators to disagree on the same record.

Compounding this, `retrieval_skipped_count` (the one signal that would let a
report reader notice this asymmetry) is computed but never surfaced in any
dimension or report detail — `arm_metrics[arm]["retrieval_skipped"]`
(`score.py:284`) has no reader anywhere in the codebase.

No existing test constructs this exact record shape (empty answer + `None`
snapshot + no node failures via the notices-only success branch) and asserts
what happens to `answer_exact_match`/`answer_f1`/`retrieval_evidence_coverage`
denominators for it, so this asymmetry is currently unguarded by tests.
**Fix:** Decide and enforce one consistent policy for records lacking payload
data (either exclude from both families symmetrically, or score both as an
honest zero/miss symmetrically), and publish `retrieval_skipped_count` as a
detail on the affected retrieval dimensions (or as its own diagnostic) so any
future asymmetry is visible in the report rather than silent. Add a test that
builds this exact record shape and asserts the same treatment on both sides.

## Warnings

### WR-01: `single_arm_usable_drops` counter conflates two distinct drop reasons

**File:** `eval/src/lancet_eval/pairing.py:111-117`
**Issue:** `form_pairs` increments the same `single_arm_usable_drops` counter for
two different scenarios:
```python
if on_usable != off_usable:
    single_arm_usable_drops += 1   # genuinely asymmetric: one arm usable, one not
    continue

if not on_usable and not off_usable:
    single_arm_usable_drops += 1   # BOTH arms unusable -- not "single arm"
    continue
```
The field name and its docstring ("Requirements: Both records must satisfy
is_usable (ADJACENCY EDGE)") imply this bucket tracks pairs dropped because only
one arm was usable. It also silently absorbs the "neither arm usable" case,
which is a materially different diagnostic signal (both arms failed vs. an
asymmetric failure that might indicate an arm-specific regression). This bucket
is surfaced directly in the report via `make_paired_ablation_delta`'s
`detail["single_arm_usable_drops"]`, so a report reader diagnosing low pairing
coverage will misattribute "both arms failed" drops as "asymmetric" drops. Given
this phase's entire purpose is making denominators/audit trails trustworthy and
distinguishable, this is a real defect in that same spirit.
No test exercises the "neither arm usable" branch — `test_form_pairs_single_arm_usable_drops`
only covers the asymmetric case (`r_on` usable, `r_off` unusable via
`outcome="error"`), so a regression that further mislabeled or misrouted the
both-unusable case would not be caught.
**Fix:** Split into two counters, e.g. `asymmetric_usable_drops` and
`both_unusable_drops`, update `JoinResult`, `make_paired_ablation_delta`'s detail
keys, and add a test asserting the both-unusable case increments the new,
distinctly-named counter (not `single_arm_usable_drops`).

### WR-02: `check_canary_floors` has no defensive guard against malformed canary rows

**File:** `eval/src/lancet_eval/preflight.py:498-501`
**Issue:** Unlike its sibling `check_canary_manifest` (which wraps its entire body
in `try/except Exception` and returns a clean `PreflightCheckResult(passed=False, ...)`
on any parse/shape problem), `check_canary_floors` indexes required fields
directly with no surrounding guard:
```python
for row in rows:
    qid = row["question_id"]
    arm = row["graph_arm"]
    qtext = row["question"]
    ...
```
A `KeyError` here (e.g. from a future edit to `canary.jsonl` that omits a field,
or from someone passing a custom `canary_path` with a different shape) propagates
out of `check_canary_floors` uncaught, and `run_preflight_checks` has no
try/except around this call either — the whole preflight command crashes with a
raw traceback instead of reporting a named, actionable check failure. This is
inconsistent with the rest of the module's stated intent (every other check
function returns a `PreflightCheckResult(passed=False, ...)` on any internal
error) and with `drive_one`'s explicit "Guaranteed never to raise" contract
pattern used elsewhere in this codebase. Currently benign only because the
committed `canary.jsonl` happens to be well-formed.
**Fix:** Wrap the per-row body (or the whole function) in `try/except Exception`
and append a `PreflightCheckResult(name="canary_floors", passed=False, message=...)`
naming the offending row/field, mirroring `check_canary_manifest`'s pattern.

### WR-03: Raw-event byte-cap truncation in `client.py` can re-admit frames after truncation, producing gapped/renumbered forensic captures

**File:** `eval/src/lancet_eval/client.py:248-259`
**Issue:**
```python
if raw_bytes + approx_bytes <= bytes_per_unit:
    raw_events_list.append(ev_dict)
    raw_bytes += approx_bytes
else:
    raw_truncated = True
    raw_dropped_frames += 1
```
Once a frame is dropped for exceeding `bytes_per_unit`, `raw_truncated` becomes
`True` but collection does not stop — `raw_bytes` is unchanged, so a later,
smaller frame can still satisfy `raw_bytes + approx_bytes <= bytes_per_unit` and
get appended. This produces a `raw_events_list` with a gap in the middle (one or
more frames silently missing) rather than a clean truncated prefix. Downstream,
`RawEventSink.write_events` (`raw_events.py:74-89`) re-enumerates `seq` from the
position in this already-gapped list, so the written `seq` values no longer
correspond to the original wire order, and the `truncation` marker/`unwritten_frames`
count describes only the write-time view, not the true set of frames dropped
during capture. Total byte budget compliance is preserved (each addition is
still gated on cumulative size), so this is a forensic-fidelity issue, not a
resource-exhaustion one. `test_byte_cap_truncation_records_unwritten_count` does
not catch this because its synthetic events are uniform in size, so the "big
frame drops, small later frame re-admitted" path is never exercised.
**Fix:** Once `raw_truncated` is set, stop appending further frames
unconditionally (only continue incrementing `raw_dropped_frames`), so the
captured prefix is always contiguous and `seq` numbering is meaningful.

### WR-04: `test_historical_pre_change_journal_loads` depends on CWD being the repo root, not the `eval/` package root

**File:** `eval/tests/test_wire_capture.py:214-219`
**Issue:**
```python
line = Path("eval/runs/2026-09-03-multihop_rag/journal.jsonl").read_text(
    encoding="utf-8"
).splitlines()[1]
```
This hardcoded relative path only resolves when the test process's working
directory is the repository root. The `eval/` package has its own
`pyproject.toml`/`uv.lock`, and the project's own README documents running
tests as `uv run --project eval pytest` from the repo root — under that
invocation this test passes (verified). However, invoking pytest with `cwd=eval/`
(e.g. `cd eval && uv run pytest`, or many IDE "run test" integrations that cd
into the package directory) makes this path resolve to
`eval/eval/runs/...` and the test fails with `FileNotFoundError` (verified
empirically). Every other path-sensitive module in this codebase
(`preflight.py`, `seed.py`, `score.py`, `config.repo_root()`) resolves paths
via `repo_root()` or `Path(__file__).resolve()...` specifically to avoid this
CWD dependency; this test is the one place that doesn't follow that pattern.
**Fix:** Resolve the fixture path via `repo_root()` (already used elsewhere in
this codebase) instead of a bare relative `Path(...)` literal.

**File:** `eval/src/lancet_eval/score.py:259-261, 287`
**Issue:** `ndcgs` is populated inside the per-record scoring loop
(`n_out = ndcg_at_k(...); if n_out.status == "ok": ndcgs.append(n_out.score)`) and
stored on `arm_metrics[arm]["ndcgs"]`, but no code ever reads
`p_data["ndcgs"]` — `ranking_quality` is built from `p_data["mrrs"]` only. This
predates this phase (present before 06.3.2, confirmed via `git diff`), but the
whole file is in review scope and the dead computation persists. Not incorrect,
just wasted work and a maintenance trap.
**Fix:** Either wire `ndcgs` into a registered dimension or remove the
computation if it's genuinely unused.

### IN-02: LLM-judge prompt has no defense against evidence-borne prompt injection

**File:** `eval/src/lancet_eval/judge.py:282-292`
**Issue:** `truncate_evidence`'s output (raw excerpt text pulled verbatim from
`StructuredCitation.excerpt`, itself sourced from whatever the engine retrieved
from the corpus) is concatenated directly into the judge's user message with only
a `=== EVIDENCE ===` header as a boundary. If a corpus document contained text
designed to look like judge instructions, nothing prevents it from being
interpreted as part of the prompt rather than as evidence to grade. This is a
known, generally-accepted limitation of LLM-as-judge designs and is low risk
against the current fixed/vetted `multihop_rag` benchmark corpus, but is worth
flagging explicitly since this harness makes live calls to an external LLM API.
**Fix:** No change required for the current fixed benchmark corpus; if this
harness is ever pointed at a corpus with untrusted/adversarial content, consider
a stronger structural delimiter or a post-hoc verdict sanity check.

### IN-03: `question_id` used unsanitized as a filename component in raw-event retention

**File:** `eval/src/lancet_eval/raw_events.py:65-67`
**Issue:**
```python
target_dir = self.raw_dir / graph_arm
target_dir.mkdir(parents=True, exist_ok=True)
target_file = target_dir / f"{question_id}.jsonl"
```
`question_id` (and `graph_arm`) flow from `GoldQuestion.id`/corpus config
straight into a filesystem path with no character validation. Today
`question_id` values come from the checked-in, trusted `multihop_rag` corpus
sample files, so this is not currently exploitable, but there is no guard against
a future corpus (or a hand-edited sample file) containing `..`/path-separator
characters in a question ID causing writes outside `raw_dir`.
**Fix:** Sanitize/validate `question_id` before using it to construct a
filesystem path, consistent with the existing `_sanitize_filename` pattern
already used in `seed.py` for a similar purpose.

### IN-04: `test_shared_retrieval_percentile_pair_in_one_place` asserts on source text, not behavior

**File:** `eval/tests/test_path_health.py:39-53`
**Issue:**
```python
source = inspect.getsource(score_module)
assert source.count("percentile(") == 0
```
This checks that the literal substring `"percentile("` does not appear in
`score.py`'s source text, as a proxy for "score.py does not duplicate the
retrieval-latency percentile computation." It is gameable (an aliased import,
e.g. `from lancet_eval.stats import percentile as pctl`, or a differently
formatted call, would satisfy the assertion while reintroducing the duplicate
computation) and fragile (an unrelated comment or docstring containing the
substring `percentile(` would fail the test for no behavioral reason). It does
catch the most likely accidental regression (a direct copy-pasted call), so it
has some value, but it is not a behavioral guarantee.
**Fix:** Prefer a behavioral test (e.g. mock/monkeypatch `stats.percentile` and
assert call count during a `score_run`) over a source-text assertion, or at
least narrow the string match to reduce false positives from comments.
