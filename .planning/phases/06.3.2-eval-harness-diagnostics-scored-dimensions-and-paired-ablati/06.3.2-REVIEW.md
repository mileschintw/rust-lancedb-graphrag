# Phase 06.3.2: Code Review Report

**Reviewed:** 2026-09-06T00:00:00Z
**Depth:** standard
**Files Reviewed:** 34
**Status:** issues_found

## Summary

Reviewed the eval harness files for phase 06.3.2, with special attention (per the scope note) to whether the newly added `has_scorable_payload` predicate is applied consistently everywhere records are scored/excluded, and whether the paired-ablation exclusion (`excluded_unscorable_pairs`) is symmetric across both arms of a pair.

The specific gap this phase closed (SC-7 / prior CR-01: asymmetric exclusion of `answer="" and snapshot=None` records between retrieval denominators and answer metrics) **is fixed correctly and is well tested**. `has_scorable_payload` is applied uniformly in `score.py`'s per-arm accumulation loop and in all five paired-ablation score functions (`_score_evidence_coverage`, `_score_em`, `_score_f1`, `_score_cp`, `_score_mrr`); latency and token deltas correctly skip the payload gate since they don't depend on retrieval/answer payload. `test_paired_ablation_payload_exclusion_across_all_five_metrics` and `test_scorable_payload_exclusion_and_reconciliation` directly verify this symmetry and it holds.

However, the investigation surfaced two correctness bugs specifically in the `abstention_on_unanswerable` dimension that sits directly beside this phase's payload-gate change, plus several quality/maintainability issues elsewhere in the reviewed files.

## Critical Issues

### CR-01: `abstention_rate` is called without `notices`, permanently disabling the documented primary abstention-detection path

**File:** `eval/src/lancet_eval/score.py:282-287`

**Issue:** In the per-record scoring loop, abstention is computed as:
```python
if gold.is_null:
    snap_chunks = rec.snapshot.retrieved_chunks if rec.snapshot else None
    abs_out = abstention_rate(gold, rec.answer or "", snap_chunks)
```
`abstention_rate(question, answer, citations=None, notices=None)` is called with only 3 positional args (`gold`, answer, `snap_chunks` bound to the `citations` parameter) — `notices` is never supplied and defaults to `None` → `[]` inside `abstention_outcome`. But `abstention_outcome`'s own docstring states its **preferred** detection mechanism is:
```python
# 1. Prefer typed notice code NOTICE_CODE_NO_EVIDENCE = 1 or GRAPH_ABLATION = 18
for n in notices:
    typed_code = getattr(n, "typed_code", None)
    if typed_code == 1:
        return "correct_abstention"
```
Because `notices` is always `[]` at this call site, this branch can never fire. The `abstention_on_unanswerable` dimension therefore relies entirely on brittle text-matching (`"insufficient information"` / `"cannot answer"` substrings) to credit correct abstention — any engine that abstains via a structured `NO_EVIDENCE` notice (typed_code 1) rather than one of those two exact phrases is scored as `"other"` (0.0, i.e. an abstention failure) even though the engine behaved correctly. This directly undermines the dimension's validity, and it interacts with this phase's new `has_scorable_payload` gate: a record with `answer=""` plus a `NO_EVIDENCE` notice is *already* excluded by the payload gate (per caveat 6, correctly per design), but a record with a *non-blank* refusal answer that doesn't literally say "insufficient information" or "cannot answer" survives the payload gate yet still gets scored as a wrong abstention because the notice-based signal is unreachable.

**Fix:**
```python
if gold.is_null:
    snap_chunks = rec.snapshot.retrieved_chunks if rec.snapshot else None
    abs_out = abstention_rate(gold, rec.answer or "", snap_chunks, rec.notices)
```
Add a test asserting that a null-gold record with a non-blank answer and a `typed_code=1` (`NOTICE_CODE_NO_EVIDENCE`) notice is scored `correct_abstention` even when the answer text doesn't match either hardcoded refusal phrase.

### CR-02: Misleading skip reason when abstention records exist but are all payload-excluded

**File:** `eval/src/lancet_eval/score.py:979-990`

**Issue:**
```python
else:
    dimensions.append(
        DimensionResult(
            name="abstention_on_unanswerable",
            status="skipped",
            reason="Corpus contains no unanswerable questions",
            detail={
                "excluded_payload_records": unanswerable_payload_excluded,
            },
            n=0,
        )
    )
```
This branch fires whenever `p_data["abstentions"]` is empty — which happens both when the corpus genuinely has zero null-gold questions *and* when the corpus has null-gold questions but every one of their records was excluded by `has_scorable_payload` (i.e. `unanswerable_payload_excluded > 0`). In the second case the `reason` string is factually wrong: the corpus does contain unanswerable questions, they were simply excluded. A reader of `report.md`/`report.json` would conclude the wrong thing about the test corpus's composition. `detail.excluded_payload_records` is present but the human-readable `reason` contradicts it.

**Fix:**
```python
else:
    if unanswerable_payload_excluded > 0:
        reason = (
            "All unanswerable-question records lacked scorable payload "
            "(excluded by the payload rule); none were scored"
        )
    else:
        reason = "Corpus contains no unanswerable questions"
    dimensions.append(
        DimensionResult(
            name="abstention_on_unanswerable",
            status="skipped",
            reason=reason,
            detail={"excluded_payload_records": unanswerable_payload_excluded},
            n=0,
        )
    )
```

## Warnings

### WR-01: Dead code — `_check_provenance` duplicates `has_arm_provenance` and is never called

**File:** `eval/src/lancet_eval/score.py:104-114`

**Issue:** `_check_provenance` is a byte-for-byte reimplementation of `usability.has_arm_provenance` (which is imported at the top of the file and actually used at lines 241 and 304). `_check_provenance` itself has zero call sites in the file. Keeping two independent copies of the same provenance rule risks them silently diverging on a future edit to one but not the other.

**Fix:** Delete `_check_provenance` (lines 104-114) and its now-unnecessary `NOTICE_CODE_GRAPH_ABLATION`/`NOTICE_CODE_GRAPH_UNAVAILABLE` imports if unused elsewhere in the file.

### WR-02: `has_scorable_payload` treats "snapshot present with blank answer" identically to "no payload at all" for null-gold abstention scoring, and this specific combination is untested

**File:** `eval/src/lancet_eval/usability.py:45-65`, consumed at `eval/src/lancet_eval/score.py:246-251`

**Issue:** `has_scorable_payload` requires *both* a non-`None` snapshot *and* a non-blank answer. For answerable questions this is the intended SC-7 fix. For null-gold (unanswerable) questions, however, a present snapshot (even with the NO_EVIDENCE carve-out of empty `retrieved_chunks`) combined with a blank answer is a plausible **correct** abstention behavior — the engine completed retrieval, found nothing, and declined to answer. The current gate excludes this record from the `abstention_on_unanswerable` denominator entirely (same bucket as a record with no snapshot and no answer, which is a genuine harness-capture failure), rather than scoring it.

This is a documented, deliberate design choice for the "no snapshot AND no answer" case (caveat 6 in `report.md.j2`, and covered by `test_abstention_on_unanswerable_payload_exclusion_population_scoped`), but the narrower "snapshot present (with or without NO_EVIDENCE) + blank answer" sub-case has no dedicated test anywhere in the suite (`test_wire_contract.py`'s NO_EVIDENCE carve-out test always uses a non-blank refusal answer, e.g. `"I have no evidence to answer this query."`). Whether a snapshot-present/answer-blank null-gold record should be excluded (current behavior) or scored via the notice-based path (see CR-01) is not analyzed or asserted anywhere.

**Fix:** Add an explicit test pinning the intended behavior for `snapshot present (empty retrieved_chunks) + answer="" + NOTICE_CODE_NO_EVIDENCE notice` on a null-gold question, and confirm with the phase owner whether this should be (a) excluded as payload-less (current behavior, arguably losing a real abstention signal) or (b) scored via CR-01's notice-based path before payload gating is applied to the abstention dimension specifically.

### WR-03: Substantial code duplication across `run_query`'s four `QueryOutcome` return branches

**File:** `eval/src/lancet_eval/client.py:313-389`

**Issue:** The `failed` / `ok` / `degraded (final_response)` / `degraded (notices only)` branches each construct a ~15-field `QueryOutcome(...)` call that is identical except for `status`, `answer`, and `notices`. Any future field addition to `QueryOutcome` (e.g. a new diagnostic counter) has to be replicated correctly across all four call sites; missing one silently produces an incomplete `QueryOutcome` in exactly one code path.

**Fix:** Factor the shared kwargs into a dict/builder, e.g.:
```python
common = dict(
    completion=completion, node_failures=node_failures, session_id=session,
    correlation_id=correlation, duration_ms=completion.total_duration_ms,
    node_timings=node_timings, workflow_meta=workflow_meta,
    partial_snapshot=partial_snapshot, dropped_node_timings=dropped_node_timings,
    raw_events=raw_events_list, raw_events_truncated=raw_truncated,
    raw_events_dropped_frames=raw_dropped_frames,
)
return QueryOutcome(status="failed", answer=completion.final_response, notices=completion.notices, **common)
```

### WR-04: `Journal` docstring claims "thread-safe" but provides no locking

**File:** `eval/src/lancet_eval/journal.py:106-131`

**Issue:** The class docstring states "Append-only thread-safe manager for JSONL evaluation records," but `append()` and `write_header()` simply `open(path, "a")` per call with no `threading.Lock` or other synchronization. Today this is safe only because `run.drive()` happens to route every `journal.append()` call through the single collector thread (`for future in concurrent.futures.as_completed(...)`), never from the worker threads themselves — but that invariant lives in a different file (`run.py`) and isn't enforced or documented by `Journal` itself. Any future caller (e.g. a parallel writer, or a different driver) that calls `Journal.append` concurrently from multiple threads could interleave partial writes, contradicting the class's own contract.

**Fix:** Either add an internal `threading.Lock` around the open/write in `append()`/`write_header()` to make the docstring's claim true, or narrow the docstring to state the actual (single-writer-thread) contract explicitly.

**Fix:** Add `test_has_scorable_payload_*` cases to `test_usability.py` mirroring the existing predicate tests in that file.
