### 2. DimensionResult Validator Forbids Detail on Error Status

**Finding:** `DimensionResult._validate_consistency` [VERIFIED: `dimensions.py:33-41`] enforces:

**Recommendation:** (A) is simplest — `detail` is already `dict[str, float]`, allowing it on error/skipped doesn't break validation. The constraint was written to prevent mis-formatted `skipped` rows; error rows carrying diagnostic counts is different.

**Planner action required:** Decide which resolution, communicate to implementer so they don't ship invalid dimension results.

### 3. Success Predicate Fix Moves Signal, Not Just Adds It

**Finding:** `run.py:58` hardcodes `outcome="success"` [VERIFIED: read lines 54–69]. But `client.py:232–242` [VERIFIED: read lines 232–242] already returns `QueryOutcome(status="failed", ...)` when `completion.success` is false.

**Implication:** The false-green at 966/1000 records in 2026-09-03 run was not a missing field; the field was read and thrown away. The fix is smaller than "read node_failures and infer" — it's "use the existing status field."

### 4. Deduplication Must Be Per-(question_id, arm), Not Per-question_id

**Finding:** WR-02 in 06.3-REVIEW.md [VERIFIED: read lines 161–189] notes that journal de-duplication on resume is per-journal-append, not per-record. Running `lancet-eval run` twice without `--resume` appends duplicates. Review suggests "keep only the last record per `question_id`."

**Pitfall for this phase:** Pairing requires both arms for each question. Deduping per `question_id` (not per `(question_id, arm)`) would delete one arm of every duplicate pair and wreck pairing coverage.

**Correct fix:** De-duplicate by `(question_id, arm)` tuple, keeping the last record. Alternatively, detect duplicates and raise an error (consistent with this module's strict-validation posture).

### Bootstrap Confidence Intervals (Locked)

**Pattern:** [VERIFIED: AI-SPEC lines 865–900, quoted for reference]

```python
import math
import random
from statistics import mean

BOOTSTRAP_B = 10_000
BOOTSTRAP_SEED = 42  # commit this; print bootstrap_seed as float in detail

def bootstrap_mean_ci(diffs: list[float], *, seed: int = BOOTSTRAP_SEED, b: int = BOOTSTRAP_B) -> tuple[float, float, float]:
    n = len(diffs)
    if n == 0:
        raise ValueError("n_pairs=0")  # dimension status=error, no score
    mu = mean(diffs)
    if n == 1:
        return mu, mu, mu  # detail degenerate_ci=1.0
    rng = random.Random(seed)
    means: list[float] = []
    for _ in range(b):
        acc = 0.0
        for _ in range(n):
            acc += diffs[rng.randrange(n)]
        means.append(acc / n)
    means.sort()
    return mu, means[int(0.025 * b)], means[min(b - 1, int(0.975 * b))]


def wilson_ci(k: int, n: int, z: float = 1.96) -> tuple[float, float, float]:
    if n <= 0:
        raise ValueError("n=0")
    p = k / n
    z2 = z * z
    den = 1.0 + z2 / n
    center = (p + z2 / (2 * n)) / den
    half = z * math.sqrt((p * (1 - p) + z2 / (4 * n)) / n) / den
    return p, max(0.0, center - half), min(1.0, center + half)


def percentile(xs: list[float], q: float) -> float:
    ys = sorted(xs)
    n = len(ys)
    if n == 1:
        return ys[0]
    pos = q * (n - 1)
    lo = int(pos)
    hi = min(lo + 1, n - 1)
    frac = pos - lo
    return ys[lo] * (1.0 - frac) + ys[hi] * frac
```

**Runtime:** Measured on 500-pair delta with B=10_000: **0.8955 seconds** [VERIFIED: synthetic benchmark above]. With ~8–9 distinct deltas (recall + 4 deterministic answer metrics × 3 strata + aggregate + latency + tokens = 9 total), total bootstrap time per run ≈ **7–8 seconds** — acceptable for offline scoring.

**Platform determinism:** `random.Random(42)` uses Mersenne Twister, platform-independent for integer operations. **Caveat:** Pair order must be deterministic; sort pairs by `question_id` before bootstrapping or CI will vary run-to-run.

**Seed reuse across dimensions:** Identical seed for all 9 deltas means identical resample index sequence for each, which is defensible (resampling the same pairs consistently). Planner decision: flag this as "shared seed for determinism" or use independent seeds per delta. Either way, seed selection must be documented.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Paired comparison with CIs | Custom delta + pooled variance | Nonparametric bootstrap percentile (AI-SPEC §5) | Bootstrapping handles skewed, non-normal delta distributions; no normality assumption needed. Pooled variance assumes independence (violated here — both arms queried same question). |
| Rate confidence intervals | Wald/normal approximation | Wilson score interval (AI-SPEC §5, z=1.96) | Wilson works near boundaries (0 and 1) where Wald fails; 1927 reference, robust. |
| Detectinginfrastructure failure | Heuristics on notices | Hard node failure predicate on `error_kind` (D-34, AI-SPEC 834–852) | Timeouts can have notices (GRAPH_TIMEOUT, NO_EVIDENCE); failures have explicit error frames. Notices are not sufficient. |

## Common Pitfalls

### Pitfall 1: Using `outcome.status="ok"` vs. Checking `node_failures`

**What goes wrong:** Implementer adds logic like `if record.node_failures: usable=false` but still writes `outcome="success"` to the journal, creating a contradiction. Later dimensions filter on outcome instead of node_failures and miss the unusable record.

**Why it happens:** D-27 says "fix the outcome," but `outcome.status` is *already* set correctly by the client. The harness just throws it away. Engineer might assume they need to read node_failures, when they should use `outcome.status`.

**How to avoid:** Route `outcome.status` directly into the journal record; don't reconstruct it. If outcome already says "failed", don't override it with "success".

**Warning signs:** A D-27 task that creates a new field or adds new logic to run.py when the real fix is just "stop throwing away the existing status."

### Pitfall 2: Null Questions in Pairing Join

**What goes wrong:** Implementer includes null questions in the pairing join, creating asymmetric pair counts across different dimension denominators (retrieval-only null → included; answer-only null → excluded).

**Why it happens:** The pairing join is written as a simple inner join on question_id without filtering `is_null`. Null questions have both arms in the journal, so they join successfully.

**How to avoid:** Filter `where not p[0].gold.is_null and not p[1].gold.is_null` **before** computing paired deltas (but **after** checking for pairing coverage, since null questions still contribute to overall arm completeness).

**Warning signs:** Pairing coverage doesn't match expected number; ablation delta has fewer pairs than expected given usable record counts.

### Pitfall 3: Seed Reuse Across Dimension Calls Without Deterministic Pair Order

**What goes wrong:** Bootstrap CI varies between runs even with identical seed, because pair order to `bootstrap_mean_ci()` differs (journal order is not deterministic across runs if journaling order drifted).

**Why it happens:** `BOOTSTRAP_SEED = 42` is fixed, so the resample index sequence is deterministic. But if the input `diffs` list order changes, the bootstrap operates on a different permutation.

**How to avoid:** Sort pairs by `question_id` before computing deltas, so input list order is deterministic. Consider documenting whether seed is "per-dimension" (independent seed for each delta) or "shared" (same seed for all, resampling same pairs consistently).

**Warning signs:** CI differs on re-run without code changes; bootstrap seed in detail doesn't match expectations.

### Pitfall 4: De-duplication Breaks Pairing

**What goes wrong:** Implementer removes duplicate records by `question_id`, not by `(question_id, arm)`. If both arms of a pair exist twice in the journal, one arm gets deleted, breaking the pair.

**Why it happens:** The suggestion in WR-02 review says "keep only the last record per `question_id`" without noting the pairing context.

**How to avoid:** De-duplicate by `(question_id, arm)` tuple. Alternatively, detect duplicates and raise an error (consistent with score.py's strict-validation posture).

**Warning signs:** Pairing coverage lower than expected; ablation delta has significantly fewer pairs after de-duplication than the usable records would suggest.

### Pitfall 5: Exception in Usability Predicate Silently Becomes outcome="error"

**What goes wrong:** A new predicate function is called inside the try block of `drive_one()` to determine outcome. Any exception (e.g., missing field, type error) is caught by `except Exception` and the record is written as `outcome="error"` instead of "success" or false-green.

**Why it happens:** `drive_one` is designed to "guarantee never to raise" by catching all exceptions. A predicate that raises will silently mask an infrastructure problem as a harness bug.

**How to avoid:** Test the usability predicate thoroughly on all record variants (timeout, no snapshot, empty chunks, hard failures, normal success). Ensure it never raises; return False on malformed input.

**Warning signs:** Sudden spike in `outcome="error"` records after adding D-27/D-34 logic; errors include stack traces that look like missing fields.

### Pitfall 6: Graph Dimensions Computed on graph-off Arm

**What goes wrong:** A graph-health dimension like `graph_presence_rate` is computed over all records, including graph-off early-returns which carry `graph_node_count=0` by design (not because the graph failed).

**Why it happens:** The denominator filter is on "usable records" but not on "graph-on records specifically."

**How to avoid:** Filter denominators to `graph-on` arm: `P(...| usable AND graph_arm == "graph-on")`.

**Warning signs:** Graph presence rate is artificially low or half the expected value (graph-off early-return pulls the mean down by ~50%).

## Code Examples

### Bootstrap Resampling (Verified Pattern)

```python
# Source: AI-SPEC §5 lines 865-889
import random
from statistics import mean

BOOTSTRAP_SEED = 42
BOOTSTRAP_B = 10_000

def bootstrap_mean_ci(
    diffs: list[float],
    *,
    seed: int = BOOTSTRAP_SEED,
    b: int = BOOTSTRAP_B,
) -> tuple[float, float, float]:
    """Compute mean and 95% percentile CI via bootstrap resampling.
    
    Args:
        diffs: List of per-question differences (e.g., graph-on score - graph-off score)
        seed: RNG seed for reproducibility
        b: Number of bootstrap resamples
    
    Returns:
        (point_estimate, ci_low, ci_high)
    
    Raises:
        ValueError: if len(diffs) == 0
    """
    n = len(diffs)
    if n == 0:
        raise ValueError("n_pairs=0")
    mu = mean(diffs)
    if n == 1:
        # Degenerate case: single pair, point estimate is exact
        return mu, mu, mu
    
    rng = random.Random(seed)
    means: list[float] = []
    for _ in range(b):
        # Resample n items with replacement
        acc = 0.0
        for _ in range(n):
            acc += diffs[rng.randrange(n)]
        means.append(acc / n)
    
    means.sort()
    # Percentile CI: 2.5th and 97.5th percentiles
    return mu, means[int(0.025 * b)], means[min(b - 1, int(0.975 * b))]
```

### Pairing Join

```python
# Pseudo-code for pairing
def form_pairs(records: list[RunRecord]) -> list[tuple[RunRecord, RunRecord]]:
    """Join usable records on question_id, both arms required, nulls excluded."""
    by_qid: dict[str, dict[str, RunRecord]] = {}
    
    for record in records:
        if not is_usable(record):
            continue
        if record.question.is_null:  # Exclude null questions from pairing
            continue
        
        qid = record.question_id
        arm = record.graph_arm
        
        if qid not in by_qid:
            by_qid[qid] = {}
        by_qid[qid][arm] = record
    
    # Inner join: both arms required
    pairs = [
        (by_qid[qid]["graph-on"], by_qid[qid]["graph-off"])
        for qid in by_qid
        if "graph-on" in by_qid[qid] and "graph-off" in by_qid[qid]
    ]
    
    return pairs
```

### Hard Failure Detection

```python
# Source: AI-SPEC §5 lines 834-852, D-34
def is_hard_node_failure(node_failures: list[NodeFailed]) -> bool:
    """Check if any failure is infrastructure-grade (non-retryable, critical path)."""
    for failure in node_failures:
        if failure.node_name in ("RetrieveHybrid", "AssemblePrompt", "GenerateAnswer"):
            if not failure.retryable:
                return True
        # error_kind 1=TIMEOUT, 3=LLM_GENERATION, 4=RETRIEVAL, 6=PROMPT_ASSEMBLY, 7=REFORMULATION, 8=INTERNAL, 9=INPUT_VALIDATION
        if failure.error_kind in (1, 3, 4, 6, 7, 8, 9):
            return True
    return False

def is_usable(record: RunRecord, graph_arm_expected: str = "graph-on") -> bool:
    """Apply D-34 usability predicate."""
    # Predicate 1: outcome="error" means hard infrastructure failure
    if record.outcome == "error":
        return False
    
    # Predicate 2: explicit hard node failures
    if is_hard_node_failure(record.node_failures):
        return False
    
    # Predicate 3: eval-scoped success=false (D-29)
    # RetrieveHybrid failed AND no snapshot OR empty snapshot
    has_retrieval_failure = any(
        nf.node_name == "RetrieveHybrid" and not nf.retryable
        for nf in record.node_failures
    )
    if has_retrieval_failure and (record.snapshot is None or not record.snapshot.retrieved_chunks):
        return False
    
    # Predicates that do NOT make a record unusable:
    # - NO_EVIDENCE notice on completed retrieval
    # - GRAPH_TIMEOUT, GRAPH_UNAVAILABLE, NoMatchFound
    # - graph-off early return (GRAPH_ABLATION)
    
    return True
```

### WR-02: Duplicate (question_id, arm) Records Not De-duplicated

**File & Location:** `eval/src/lancet_eval/score.py:318–374` and `466–489` [VERIFIED: 06.3-REVIEW.md lines 161–189]

**Issue:** `Journal.append()` has no uniqueness check. Running `lancet-eval run` twice without `--resume` appends duplicates. Score loop iterates both, double-weighting them in means and worksheet selection.

**Fix:** De-duplicate by `(question_id, arm)` before scoring, keeping last record. **Critical for this phase:** Dedup must be per-arm, not per-question, or pairing breaks.

**Reference:** `06.3-REVIEW.md` lines 161–189.

### WR-03: Primary Arm Fallback Always Resolves to graph-on

**File & Location:** `eval/src/lancet_eval/score.py:274–278` [VERIFIED: 06.3-REVIEW.md lines 191–221]

**Issue:** `arm_metrics` dict is initialized with `{"graph-on": [], "graph-off": []}` so `next(iter(...))` always returns "graph-on", even if only graph-off records exist.

**Fix:** Use `max(arm_metrics, key=lambda a: arm_metrics[a]["total"])` to pick the arm with data.

**Reference:** `06.3-REVIEW.md` lines 191–221.

### WR-04 + IN-02: Silent Config/Cache Failures Fabricate Provenance

**Files & Locations:**
- `eval/src/lancet_eval/score.py:64–74` — `_get_engine_generation_model()` swallows all exceptions, returns `""`
- `eval/src/lancet_eval/score.py:296–300` — Safety guard `gen_model == judge_model` silently skipped if config read fails
- `eval/src/lancet_eval/judge.py:209–222` — `JudgeCache._load()` silently drops corrupted entries

**Issue:** Failures are silent. Report gets `generation_model: "deepseek/deepseek-v4-flash-0731"` (hardcoded fallback) even if config is unreadable. Judge cache corruption loses paid verdicts without warning.

**Fix:**
- Log or re-raise on config parse failure; use `null`/`"unknown"` in metadata if actual value unknown
- Warn when cache entries are dropped during load

**Reference:** `06.3-REVIEW.md` lines 223–289.
