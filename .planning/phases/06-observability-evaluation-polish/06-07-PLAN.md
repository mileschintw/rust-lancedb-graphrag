## Phase User Story

**As a** client of Lancet's `/rag/query` endpoint, **I want to** receive an honest, machine-readable
answer even when the graph is unavailable, one retrieval path fails, evidence is absent, or the
model's citations do not resolve, **so that** I can tell a degraded answer from a healthy one — and a
grounded answer from a model-only one — without parsing prose.

> Planner-derived from the phase's only user-facing outcome (RAG-03 degraded mode). This plan lands
> the vocabulary the story is told in; the behaviors that speak it are plans 06-08 through 06-12.

<objective>
Land the entire Phase 6 wire delta as one additive protobuf change with one regeneration, and make
both sides speak it: a single typed notice constructor on the Rust side, and the request-flag and
notice-field plumbing on the Go side.

Purpose: D-74 exists because Phase 05 paid two repair plans (05-17, 05-23) for incremental proto edits
and generated-field drift. One edit, one `buf generate`, one review, one settled contract — and every
row lands in all three columns (protobuf, Go gateway, a reader) in this plan, because a proto-only
change is an incomplete change: the gateway's strict unknown-field decoder turns a published-but-unwired
request field into a hard HTTP 400.
Output: the extended contract, both regenerated binding trees, the typed notice constructor used at
every emission site, and the gateway carrying both flags and the typed code.
</objective>

<scope_rationale>
Four tasks: one checkpoint and three automated. The checkpoint comes first because the enum values
this plan publishes are one-way (D-76) and two of the choices are genuinely decisions rather than
mechanics. The three automated tasks are the proto edit plus regeneration, the Rust derivation, and
the Go plumbing — split that way because the first must produce a five-path diff a reviewer can read
in one sitting, which it cannot do if it also carries the derivation churn.

This plan exceeds the usual two-to-three-task shape deliberately and by locked decision. AI-SPEC §4.1
states that every row of the delta must land in all three columns *in the same plan* or a consumer
breaks, and research Pitfall H shows the concrete break: the gateway's strict unknown-field decoder
returns HTTP 400 for a request field that has no counterpart in its body type, so a plan ending at
"regenerate bindings" publishes a flag that cannot be used. Splitting the Go column into its own plan
would ship exactly that state at a wave boundary.

Language-guideline routing per CLAUDE.md: `rust-guidelines.md` is loaded by task 2 only,
`go-guidelines.md` (target Go **1.25** per `gateway/go.mod:3`) by task 3 only, and neither by task 1,
which touches only protobuf and generated artifacts.

**Test-count gate protocol.** `scripts/engine-test-targets.sh` and `scripts/gateway-test-targets.sh`
assert *fixed measured* counts, and this plan adds tests, so their current expected values stop
holding the moment it lands. That is the design: the gates exist to make a count change deliberate,
not impossible. For each task that changes a count — run the enumeration, confirm the delta is exactly
the tests the task added, write the newly measured values into the script's assertions **in the same
commit as the tests that moved them**, and record the before and after rows verbatim in the summary.
Never lower an expected value to make a gate pass, and never delete an assertion: the expected value
must equal the measured value and the delta must be explainable test by test. A delta the task cannot
account for is a finding to report, not a number to overwrite. The scripts' *structure* — one row per
target, a named failure message per assertion — is never edited; only the expected values move.

Shell note: every `<automated>` gate in this phase is POSIX shell, matching `.planning/config.json`'s
`test_command`. Run them through the Bash tool, not PowerShell.
</scope_rationale>

<assumption_delta_decision>
**Noun that becomes primary:** the notice code. Until this plan a notice's identity is a bare string
invented at each emission site; after it, the identity is the typed enum value and the string is a
derived projection of it.

**Decision: promote.** The enum is canonical and the string field is demoted to a derived detail —
not added alongside a still-authoritative string. Rationale: adding alongside would leave two
independently-settable representations of the same fact, and the de-duplication key reads the string
one, so a site that set only the typed value would silently change de-duplication behavior. Promotion
with a single constructor makes the two impossible to disagree.

**Invariant test (accepted, landed in task 2):** every emitted notice carries a non-empty string code
whose value equals the derivation of its typed code, and every published enum value has at least one
emission site somewhere in Phase 6 or is explicitly reserved for Phase 6.1.
</assumption_delta_decision>
