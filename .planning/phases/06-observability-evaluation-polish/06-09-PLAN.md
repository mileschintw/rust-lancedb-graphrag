## Phase User Story

**As a** client of Lancet's `/rag/query` endpoint, **I want to** receive an honest, machine-readable
answer even when the graph is unavailable, one retrieval path fails, evidence is absent, or the
model's citations do not resolve, **so that** I can tell a degraded answer from a healthy one — and a
grounded answer from a model-only one — without parsing prose.

> This plan delivers the "one retrieval path failed and I still got an answer, and I can tell which
> path it was" slice.

<objective>
Convert both retrieval paths in the hybrid retrieval node from fail-closed to degrade-and-continue,
each with its own machine-readable notice naming the failed path.

Purpose: research corrected the AI-SPEC on this point and the correction is the whole shape of the
plan. D-13 reads like a notice addition, but both retrieval calls currently return an error, which
fails the node and produces a failed terminal event. The destination is a degrade; the origin is
fail-closed. So this is a behavior change on a fail-closed path — the single most consequential edit
in the phase's behavior work — and its tests must assert the *absence* of a node-failure event, not
merely the presence of a notice.
Output: two converted call sites, per-variant tolerance in the lexical loop, and the three-notice
both-paths-failed shape the model-only opt-in consumes next.
</objective>

<scope_rationale>
Two tasks, one per path, in the order the code runs them. They are separate because the lexical path
sits inside a per-variant loop and the dense path does not: the loop is where the subtle failure lives
(a failure on one variant must not discard the variants already accumulated), and giving it its own
task keeps that reasoning from being buried in a diff that also converts a straight-line call.

This plan continues the tracer-first shape started in 06-08: 06-08 proved the request-to-response
spine end to end, and this plan expands along it. Each task leaves the system able to do something a
user could not do before — answer a query when one half of retrieval is down — rather than laying
foundation for a later task.

Ordering with 06-10 is load-bearing and comes from research: after this change, "both retrieval paths
failed" and "evidence is absent" converge on the same observable state, which is what lets a single
opt-in cover both of the model-only triggers D-10 names. Doing 06-10 first would mean implementing the
opt-in against a state that does not yet exist.

**Explicit leftover (not D-13).** Fusion and rerank still fail the node (`retrieve.rs` fusion error
arm, rerank error arm). A healthy dense/BM25 pair with a fusion error still produces a failed
terminal. D-13 is about the two retrieval paths, not fusion or rerank. Record this leftover in the
SUMMARY as accepted residue, not as a silent "also fixed". Addresses review concern: fusion/rerank
fail-closed unnamed.

**Test-count gate protocol.** `scripts/engine-test-targets.sh` asserts *fixed measured* counts, and
this plan adds tests, so its current expected values stop holding the moment it lands. That is the
design: the gate exists to make a count change deliberate, not impossible. Run the enumeration,
confirm the delta is exactly the tests the task added, write the newly measured values into the
script's assertions **in the same commit as the tests that moved them**, and record the before and
after rows verbatim in the summary. Never lower an expected value to make the gate pass, and never
delete an assertion: the expected value must equal the measured value and the delta must be
explainable test by test. A delta the task cannot account for is a finding to report, not a number to
overwrite. The script's *structure* — one row per target, a named failure message per assertion — is
never edited; only the expected values move. Update it once, at the end of the last task, so this
plan produces one count change rather than two.

Shell note: every `<automated>` gate in this phase is POSIX shell, matching `.planning/config.json`'s
`test_command`. Run them through the Bash tool, not PowerShell.
</scope_rationale>
