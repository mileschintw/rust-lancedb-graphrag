## 1. System Classification

**System Type:** RAG / GraphRAG — **request-path hardening and wire contract**, not a new AI system.

> Classification note, because the template's assumption does not hold here. Phases 1–5 already
> shipped the AI system: a five-node Rust workflow state machine (`ReformulateQuery` →
> `ExtractGraphContext` → `RetrieveHybrid` → `AssemblePrompt` → `GenerateAnswer`) behind a Go
> gateway, streaming `WorkflowEvent`s over gRPC and SSE. **Phase 6 builds no new AI capability.** It
> does three things: (a) restructures the Rust and Go module graphs so five phases of new code land
> on a settled foundation (D-80/D-81/D-82); (b) lands one consolidated additive wire-contract change
> (D-74/D-76); (c) makes the system **honest about its own degradation** — the RAG-03 clauses the
> Phase 03 force-close parked here (D-08, D-10 … D-19). The AI-shaped risk in this phase is
> therefore not "does the model answer well" but **"does the system tell the truth about how it
> answered."**

**Description:**
When retrieval succeeds, Lancet answers from evidence and cites it. Phase 6 specifies what happens
on every other path. A caller may **opt in** — per request, default off (D-10/D-12) — to receiving a
model-only answer when evidence is absent or both retrieval paths fail; that answer carries
`answer_basis = MODEL_ONLY`, an explicit notice and **zero citations**. With the flag off, today's
fail-closed behavior is untouched. One path failing keeps `answer_basis = RETRIEVAL` and names the
failed path in a machine-readable notice (D-13). Citation markers the model emits that do not
resolve get **one local normalize-then-strip pass** with no second provider call, emitting
`CITATION_REPAIRED` / `CITATION_DROPPED` and downgrading the basis if all grounding is lost (D-14).
The two graph paths that degrade **silently** today — empty result and absent `graph_port` — gain a
`GRAPH_UNAVAILABLE` notice without any behavior change (D-08). `MIXED` stops being whatever the
model claims: the model self-reports, the engine validates against observable facts, and on
disagreement the **more conservative basis wins** with a notice recording the reconciliation (D-18).
An enumerated bad-input matrix rejects malformed requests **before** retrieval or provider work with
stable HTTP 400 / gRPC `InvalidArgument` (D-15). All of this is carried by one additive protobuf
change landed **before** any behavior plan starts (D-74), including a typed `NoticeCode` enum that
ends ad-hoc code invention (D-76).

The users are the Go gateway's HTTP/SSE clients, and — first among them, by design — Phase 6.3's
Python evaluation harness, which is a **second independent consumer of this wire contract** (D-65).
"Good" is: every degradation is machine-readable, no answer claims grounding it does not have, and
the contract is complete enough that 6.1–6.4 never need a second protobuf regeneration.

**Critical Failure Modes:**

1. **A model-only answer reaching a caller who did not opt in.** D-10's flag is default-off and the
   hard guard at `engine/src/generation/mod.rs:172-175` is being deliberately lifted. If the lift is
   unconditional rather than gated, every zero-evidence query silently starts answering from model
   priors while looking exactly like a grounded answer. This is the single highest-risk edit in the
   phase — it is a *removal of a safety check*, and the gate that replaces it is new code.
2. **Silent degradation — the defect DEBT-RAG-06 exists to name.** A degraded answer that carries no
   notice is indistinguishable on the wire from a healthy one. Today the empty-graph-result path
   (`graph_context.rs:112-115`) and the absent-`graph_port` path (`:145-148`) do exactly this. Any
   Phase 6 path that degrades without emitting a typed notice reproduces the bug being closed.
3. **Citation repair that manufactures grounding instead of removing it.** D-14 and DEBT-RAG-03's
   own acceptance criteria both say *repair, then remove what is still unresolved, then downgrade
   transparently*. A repair pass that maps a near-miss marker onto the wrong evidence block produces
   a citation that resolves, passes validation, and points at text that does not support the claim —
   wrong in the one direction no downstream check catches.
4. **An incomplete D-74 delta forcing a second regeneration.** D-74 exists because Phase 05 spent
   plans 05-17 and 05-23 repairing generated-field drift. If the enum omits values Phase 6.1 (D-25
   index staleness) or 6.2 (D-41 metadata) will emit, or the Go DTO layer is updated without its
   `ragQueryRequestBody` counterpart, the consolidation has failed on its own terms. Note that
   `gateway/main.go:677` sets `dec.DisallowUnknownFields()` — a proto-only change leaves the new
   request fields **a hard HTTP 400**, which is precisely where 6.3's harness is blocked today.
5. **Evidence losing to model priors.** The load-bearing principle recorded in 06-CONTEXT
   `<specifics>` is that *when retrieved data contradicts model knowledge, our data wins*. D-17 ships
   this as a prompt-contract instruction only, and **D-45 defers the metric that would measure it**.
   v1 therefore ships this behavior unverified — an accepted, recorded gap that D-71 requires the
   README to state plainly. It is listed here so no downstream agent mistakes silence for coverage.

## 1b. Domain Context

**Industry Vertical:** **Developer tooling / infrastructure.** Lancet has no end-user vertical — no
healthcare, legal or financial deployment exists, and PROJECT.md scopes it local-first
(`go run` / `cargo run`). The domain that actually governs Phase 6 is **honest degradation in
retrieval-augmented question answering**: the sub-discipline concerned with what a RAG system does
when retrieval returns nothing, returns the wrong thing, or half-fails, and how it says so on the
wire. Its practitioners are RAG/IR engineers and API contract designers, and the question they ask
is not *"is the answer good?"* but **"can a downstream consumer tell, from the response alone, how
much of this answer is grounded?"**

This deliberately mirrors — and does not duplicate — 06.3 §1b, whose domain is *benchmark evaluation
methodology* ("is this reported number trustworthy?"). The two are complementary halves of the same
honesty property: Phase 6 makes the system say what it did; Phase 6.3 checks whether it said it.

**User Population:** Direct consumers of the gateway's `/rag/query` HTTP/SSE endpoint and the
engine's `QueryRAG` gRPC stream. Three concrete populations exist today:

| Consumer | What it reads | Why it constrains Phase 6 |
|---|---|---|
| **Phase 6.3's Python eval harness** | Every SSE frame, `notices[]`, `structured_citations[]`, `snapshot.index_generation` | The only consumer that *asserts* the contract (D-65). A contract regression surfaces as an eval failure. It is blocked on D-74's request flag. |
| **Phase 6.2's telemetry** | `answer_basis`, notice codes, D-41 metadata | Span attributes and the D-35 metric set are derived from these values. Phase 6 produces what 6.2 measures. |
| **The README / docs suite (6.4)** | The notice table as published API contract (D-76) | The vocabulary becomes client-facing and one-way (D-76 reversibility note). |

**Stakes Level:** **Medium**, argued rather than defaulted — with one **High** sub-case.

There is no patient, financial or safety harm downstream; this is a local-only portfolio system with
no auth, no TLS and no external callers (D-06). What makes the stakes non-trivial is that Phase 6's
entire deliverable *is* a set of truth claims: `answer_basis` is a claim about provenance, a notice
is a claim about health, a citation is a claim about support. A wrong claim here is worse than no
claim, because every downstream phase treats it as ground truth. **The High sub-case is failure mode
#1** — an ungated `MODEL_ONLY` lift. It converts a fail-closed system into one that answers from
priors while presenting as grounded, and it does so *silently*, on the default path, for every
caller. That is the specific outcome D-10's default-off, D-12's opt-in plumbing and D-18's
conservative-wins reconciliation exist to prevent, and it is the sub-case the guardrails in §6 weight.

**Output Consequence:** Every degraded response is consumed three ways within this milestone —
scored by 6.3's Dimensions 5, 8 and 9; turned into span attributes and metric increments by 6.2
(D-31, D-35); and documented as published contract by 6.4 (D-76). A notice code, once emitted, is
**one-way**: D-76 records the enum values as part of the published contract. There is no "we'll
rename it later."

### Known Failure Modes in This Domain

Not generic hallucination — these are how it actually manifests on a degrading RAG request path,
each tied to something observable in this repository.

1. **The unconditional guard lift.** A safety check removed for a legitimate new case, but removed
   for all cases. Concretely: `validate_grounding_with_limits` rejects `AnswerBasis::ModelOnly`
   outright (`engine/src/generation/mod.rs:172-175`). D-10 lifts it. If the lift is not conditioned
   on the opt-in reaching that call site, the default path changes silently. Failure mode #1.
2. **Ad-hoc notice vocabulary.** Codes invented at the emission site rather than drawn from one
   table. Already happening: `GRAPH_TIMEOUT` appears as a bare literal in `graph_context.rs`, and
   `update_from_model_output` (`engine/src/workflow/mod.rs:115-128`) emits notices whose codes are
   the literal strings `"NOTICE"` and `"WARNING"` — **contentless codes already on the published
   wire**. D-76's enum must reckon with them, not pretend they are absent (see §4).
3. **Repair that widens rather than narrows.** Normalization that resolves a marker by *guessing*.
   The debt's criteria say one bounded attempt, then removal. The dangerous variant is a fuzzy match
   that succeeds — producing a resolving citation that points somewhere wrong.
4. **Basis inflation by self-report.** The model declares `answer_basis` in its structured output
   and the engine copies it (`update_from_model_output` today does exactly this). A model that says
   `RETRIEVAL` while citing nothing that resolves inflates the provenance claim. D-18's engine-side
   validation and conservative-wins rule exist for this.
5. **Validation that runs too late.** Input checks placed after embedding or retrieval — the request
   is rejected, but it already cost a provider call and a LanceDB scan. DEBT-RAG-05's criteria say
   *"rejected before retrieval/provider work"*; that ordering is the acceptance criterion, not an
   optimization.
6. **Partial contract propagation.** Proto changed, bindings regenerated, and the Go DTO layer
   missed. Here it is worse than usual: `dec.DisallowUnknownFields()` means a request field added in
   proto but not in `ragQueryRequestBody` is not ignored — it is a **400**. Already-known asymmetry
   of the same kind: `retrievalSnapshotDTO` omits `variant_count` and `variant_identities`, which
   exist on the proto `RetrievalSnapshot` (tags 10/11) and never reach HTTP clients.
7. **Refactor-and-behavior in one commit.** D-80/D-82's restructures touch the module declarations
   of both binaries. Landing behavior changes inside the same plan makes a regression
   unattributable. D-81 front-loads the restructure as a *pure-refactor* plan for exactly this
   reason; the 285-test suite is the safety net.

## 2. Framework Decision

**Selected Framework:** **None added — the shipped in-house stack is the framework.** Concretely:
the Rust engine's hand-rolled workflow state machine (`Node` trait + `WorkflowRunner`, Phase 05) over
`tokio` / `tonic` / `prost`, the OpenRouter structured-output generation client, and the Go gateway
(`chi` + `grpc-go`) translating `WorkflowEvent`s to SSE.

**Version:** Pinned by the existing manifests, not by this document — `engine/Cargo.toml`,
`gateway/go.mod`, and `proto/lancet/v1/lancet.proto` as the contract of record. Phase 6 adds **no
new AI/LLM framework dependency in either language.** Model pins stay as `config/config.toml:41-44`
records them (D-62 documents them; 6.3 reports them per run).

**Rationale:**

This is the correct answer, not an evasion, for four independent reasons:

1. **There is nothing to select.** The system exists and is verified through Phase 05. Phase 6's
   scope is a module-graph restructure, one protobuf change, and behavior on branches of a state
   machine that already runs. Introducing LangGraph or LlamaIndex here would mean *rewriting a
   shipped, tested orchestrator* to close four debt items — squarely 06-CONTEXT `<domain>`'s
   scope discipline, and the anti-pattern the framework reference itself names ("Using LangChain for
   simple chatbots — direct SDK call is less code, faster, and easier to debug").
2. **The decision is already made and recorded.** D-67 lists *"LangGraph/Dify vs a custom state
   machine"* among the alternatives-considered that 6.4's design narrative must document with what
   was rejected and why, linking to the ADR. Re-opening it in Phase 6 would contradict a locked
   Section F decision.
3. **The languages rule it out.** The engine is Rust and the gateway is Go
   (`.discussion/final_implementation_decision_document.md` fixes the split-service boundary). Every
   framework in the reference matrix except AutoGen/Microsoft Agent Framework is Python and/or
   TypeScript. `06-CONTEXT` `<code_context>` records *Go owns PostgreSQL, Rust owns LanceDB* as an
   established, preserved pattern.
4. **PROJECT.md's local-first constraint.** The project must run with plain `go run` / `cargo run`
   (D-38 reiterates this for telemetry). A Python agent framework in the request path would break it.

The **only** place a framework decision is live in this milestone is Phase 6.3's Python harness, and
06.3 §2 already made it — with RAGAS, Arize Phoenix and Promptfoo each explicitly rejected and the
reasoning recorded. Phase 6 does not revisit that.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| **LangGraph** | Closest conceptual fit (stateful graph, checkpointing, audit trails) and genuinely what one would reach for on a greenfield build — which is why D-67 requires 6.4 to document the comparison. Ruled out here: Python/TypeScript only, would replace a shipped Rust state machine with 285 passing tests, and the checkpointing it offers already exists (Phase 05 D-24/D-28, PostgreSQL-backed). |
| **LlamaIndex** | RAG-first, and retrieval quality is genuinely this system's #1 concern — but the retrieval stack (LanceDB dense + BM25 + RRF fusion + graph context) is built, tuned and on the wire via `RetrievalSnapshot`. Adopting it means rewriting Phases 2–4, not hardening Phase 6. Python/TS only. |
| **LangChain** | "Evolving requirements" is the case for it; requirements here are locked in an 86-decision context document. Adds abstraction overhead over a request path whose per-node timeouts are already individually tuned (Phase 05 D-17). |
| **Haystack** | Explicit, auditable pipelines match this project's values well. Same language barrier; same "replace working code" cost. |
| **Claude Agent SDK / OpenAI Agents SDK** | Provider-native, and this system is deliberately provider-pinned to OpenRouter free-tier models (`config.toml:41-44`, D-62). Adopting either would re-open a model-provider decision that D-05/Phase 05 D-14 closed. Neither offers a Rust request path. |
| **A Rust LLM framework (`rig`, `llm-chain`, …)** | The one category without a language barrier. Ruled out on scope: it would replace `engine/src/generation/` — the exact module D-14, D-17 and D-18 modify — during the phase that modifies it. D-81 front-loads a *pure-refactor* plan precisely to avoid mixing structural churn with behavior change. |

**Vendor Lock-In Accepted:** **Partial, and consciously.** Single generation/embedding provider
(OpenRouter) with no multi-provider fallback — descoped by Phase 05 D-14, confirmed closed by D-05,
revisit only if reliability requirements change. Model IDs are pinned in config and overridable by
the existing TOML+env convention, so the lock-in is at the *provider API* level, not the model level.
Not accepted anywhere else: no framework lock-in, no cloud lock-in, no managed-service dependency.

### Entry Point Pattern

Two entry points matter in Phase 6. First, **how a node emits a degraded notice** — the pattern every
D-08/D-13/D-14 change follows:

```rust
// A node degrades by (a) leaving the context usable, (b) adding a TYPED notice,
// (c) returning Ok(()).  Returning Err() is a FAILURE, not a degrade — it produces
// NodeFailed + WorkflowCompleted(failed) and is reserved for fail-closed paths.
impl Node for ExtractGraphContext {
    fn kind(&self) -> NodeKind { NodeKind::ExtractGraphContext }

    fn run<'a>(&'a self, ctx: &'a mut WorkflowContext, cancel: &'a CancellationToken)
        -> BoxFuture<'a, Result<(), NodeError>>
    {
        Box::pin(async move {
            let Some(graph_port) = &self.graph_port else {
                // D-08: the absent-graph_port path — SILENT today (graph_context.rs:145-148).
                ctx.graph_context = String::new();
                ctx.graph_facts   = Vec::new();
                ctx.add_notice(notice(
                    NoticeCode::GraphUnavailable,
                    "Graph context is not configured; answered from source chunks only.",
                    NoticeSeverity::Info,
                ));
                return Ok(());
```

### Common Pitfalls

1. **Lifting the `ModelOnly` guard unconditionally.** `validate_grounding_with_limits`
   (`generation/mod.rs:172-175`) rejects `AnswerBasis::ModelOnly` with a `SchemaValidation` error.
   D-10 lifts it — *conditionally*. The opt-in must reach that call site; today it has no parameter
   through which it could. Threading it there is a design task, not a one-line deletion. Critical
   failure mode #1.
2. **Forgetting `DisallowUnknownFields`.** A proto request field with no `ragQueryRequestBody`
   counterpart is not ignored by the gateway — it is a **400**. This is exactly why 06.3's harness
   currently cannot send the D-47 flag. Any D-74 plan that ends at "regenerate bindings" is incomplete.
3. **Plain `bool` for the opt-ins.** proto3 scalar `bool` has no presence: `false` and *unset* are
   indistinguishable on the wire. D-12 specifies **config default + per-request override**, which is
   three-state. Use `optional bool` (explicit presence → `Option<bool>` in prost, `*bool` in Go).
   With a plain `bool`, a config default of `true` could never be honored — the request would always
   read as an explicit `false`.
4. **Confusing the two new flags.** D-47 is emphatic: *"answer without evidence"* and *"answer
   without graph"* are different concepts and **must not share a field**. Two flags, two names, two
   code paths, and 6.3's Dimension 8 explicitly fails a run that conflates them.
5. **Emitting a notice from a node that then returns `Err`.** The terminal `WorkflowCompletedEvent`
   carries `notices` only when `final_response` is nil (`main.go:864-880`), so a notice added just
   before a failure may or may not reach the client depending on that branch. Decide the emission
   point relative to the failure, deliberately. §4 recommends making `notices` unconditional on the
   terminal payload to remove the ambiguity.
6. **Changing `RetrievalSnapshot`.** Phase 05 D-30 excluded it, D-41 puts the metadata on
   `WorkflowCompletedEvent`, and 6.3's harness parses `RetrievalSnapshot` with three required fields.
   Leave it alone. (Its `variant_count`/`variant_identities` → DTO gap is pre-existing; see §4.)
7. **Mixing the restructure with behavior.** D-80/D-82 touch both binaries' module declarations.
   D-81 makes it the **first, pure-refactor** plan. A restructure commit that also changes a notice
   makes a suite regression unattributable.
8. **Assuming `answer_chunk` text equals the answer.** The scorer (6.3) reads `final_answer.answer`
   and never the concatenation of `answer_chunk.chunk_text`. Phase 6 must keep those consistent, but
   `final_answer` is the contract.
9. **Introducing a threshold for "weak evidence."** D-16 **dropped the concept**. RRF fusion scores
   are not calibrated across queries. Adding a cutoff would be a re-litigation, not an improvement.

### 4.5 Core Pattern — the four behavior changes

**D-10/D-11/D-12 — MODEL_ONLY opt-in.** Resolution order: request field if present, else config,
else `false`. Resolved **once**, at request admission, into `WorkflowContext`, so no downstream site
re-reads config. With it **on**, D-03's zero-evidence short-circuit (`runner.rs:427,481`) no longer
skips `AssemblePrompt`/`GenerateAnswer` — this is an **explicit amendment to Phase 05 D-03** (D-11) —
and the run produces `MODEL_ONLY` + a `MODEL_ONLY` notice + **zero** citations. With it **off**,
D-03's short-circuit is byte-for-byte as shipped. The `generation/mod.rs:172-175` guard becomes
conditional on the resolved flag; it must remain a hard rejection when the flag is off.

**D-13 — one-path degraded.** A single retrieval path failing keeps `answer_basis = RETRIEVAL` and
adds `RETRIEVAL_DEGRADED` whose `message` **names the failed path** (`dense` / `bm25` / `graph`) and
its kind. The basis is not downgraded: it describes provenance, not health.

**D-14 — citation repair, normalize-then-strip.** One *local* pass: whitespace/case/format
normalization and index-vs-id disambiguation against the packed evidence set. **No second provider
call** — the debt's own criterion. Each marker resolved emits `CITATION_REPAIRED` (its `message`
naming the marker); each still unresolved is **removed from the answer text and from
`citations[]`/`structured_citations[]`** and emits `CITATION_DROPPED`. If every citation is dropped,
the basis downgrades — see the flagged interaction in §6.

**D-17/D-18/D-19 — precedence and reconciliation.** D-17 adds a precedence instruction to the
assembled prompt ("when evidence contradicts your prior knowledge, the evidence is authoritative;
say so") — **prompt text only, schema untouched** (D-19). D-18 replaces the basis copy in
`update_from_model_output`: the model self-reports, the engine validates against observable facts
(citations present and resolving, markers stripped by repair, evidence partiality), and on
disagreement the **more conservative basis wins** — conservatism ordered
`RETRIEVAL` (strongest claim) > `MIXED` > `MODEL_ONLY` (weakest) — with `BASIS_RECONCILED` recording
what changed and why. Note the direction this rule implies and accept it deliberately: a model that
self-reports `MODEL_ONLY` while its citations resolve **stays** `MODEL_ONLY`. Reconciliation only
ever weakens a provenance claim; it never strengthens one.

**D-15 — bad-input matrix.** An enumerated, table-driven set applied at admission, before any
retrieval or provider work: empty / whitespace-only / oversized query; malformed session ID;
malformed document ID; unsupported content type; and each filter bound (over-limit, negative,
contradictory, unmatched). One table-driven test per surface (gRPC and HTTP), stable HTTP 400 /
gRPC `InvalidArgument`. The gateway already maps `InvalidArgument` → 400
(`handlePreStreamError`, `main.go:796-799`), so the HTTP status is consistent whether the check fires
gateway-side or engine-side. **The table is the source artifact**; the tests and 6.4's API-contract
documentation are both generated from it (D-15).

## 4b. AI Systems Best Practices

### Structured Outputs with Pydantic

**Template override, declared rather than fabricated.** Phase 6 ships **no Python**. The structured
output contract in this phase is the Rust one, and D-19 is explicit that **the JSON schema is
untouched** — Phase 3 D-28's `response_format` / `json_schema` contract and Phase 05 D-01 both hold
unchanged. Writing a Pydantic model here would invent an artifact this phase does not produce.

The Pydantic layer that genuinely exists in this milestone is **Phase 6.3's** — wire DTOs with
`extra="ignore"` (forward-compatible: a gateway *adding* a field never breaks a run) and result/report
models with `extra="forbid"`. See **06.3 §3 "Entry Point Pattern"** and **06.3 §4b**. That asymmetry
is the reason Phase 6's `typed_code` and `metadata` additions are safe to land: 6.3's existing wire
models ignore them until 6.3 chooses to read them.

What Phase 6 owns on the structured-output side is the **Rust** contract:

```rust
// engine/src/generation — Phase 3 D-28's contract, UNCHANGED by Phase 6 (D-19).
// The model self-reports answer_basis in this existing schema; D-18 validates it
// engine-side rather than trusting it. NO schema field is added, renamed or removed.
pub struct ModelOutput {
    pub answer: String,
    pub cited_evidence_ids: Vec<String>,
    pub answer_basis: AnswerBasis,   // ← self-reported; D-18 reconciles against observable facts
    pub notices: Vec<String>,        // ← today become code "NOTICE"  → NOTICE_CODE_MODEL_NOTICE
    pub warnings: Vec<String>,       // ← today become code "WARNING" → NOTICE_CODE_MODEL_WARNING
}
```

The invariant D-18 adds, stated as code so a reviewer can check it: **`answer_basis` is written to
`WorkflowContext` exactly once**, by the reconciler, after citation repair has run — never by
`update_from_model_output` copying the model's claim. Validation failure handling is unchanged:
`GenerationErrorKind::SchemaValidation` and Phase 05 D-12's single bounded retry.

### Async-First Design

`tokio` throughout the engine; each `Node::run` returns a `BoxFuture` and the runner awaits them in
fixed sequence. Two things to get right in Phase 6:

- **`prepare()` runs outside the node's elapsed-time budget** (`node.rs:122-126`). Any setup a new
  code path needs — loading the repair table, resolving the opt-in — belongs there, not in `run`,
  or it silently eats the node's timeout.
- **Cancellation is cooperative and biased.** The existing pattern is
  `tokio::select! { biased; _ = cancel.cancelled() => return Err(NodeError::cancelled()), res = timeout(...) => ... }`
  (`graph_context.rs:101-108`). Every new awaited operation must sit inside that shape; a bare
  `.await` makes the request uncancellable, breaking Phase 05 D-16's connection-close propagation.
- **Streaming vs awaiting:** the gRPC response is a `stream WorkflowEvent`, and the gateway flushes
  each frame (`rc.Flush()`). Phase 6 adds no new frame type — only fields on existing ones — so no
  new streaming concern arises. The one ordering rule: notices must be in the context **before**
  `to_query_rag_response()` runs, since that is the single serialization point.

### Prompt Engineering Discipline

- **System vs. user separation stays as shipped.** D-17 adds one precedence instruction; it belongs
  with the system-role instructions, not interleaved with evidence.
- **Evidence is untrusted data.** Corpus text is delimited and labelled as material to reason over,
  never interpolated into instruction position. This already holds; D-17's addition must not weaken
  it by placing the precedence sentence after the evidence block.
- **No few-shot examples added.** None exist today; adding them would change output distribution
  during the phase that also changes basis semantics, making a regression unattributable.
- **The instruction ships unmeasured, and that is recorded.** D-45 defers the evidence-vs-priors
  metric with the LLM-generated item set; D-71 requires the README to say so. Any downstream claim
  that D-17 is *verified* is false. See §5's explicitly-not-scoreable row.
- **Prompt edits are contract edits.** A change to the precedence text changes what 6.3's judged
  dimensions are scoring. If it changes after a recorded run, 6.3's `judge_prompt_version` discipline
  (06.3 §5) is the mechanism that keeps two runs from being silently compared.

### Context Window Management

Governed by Phase 3 D-39's evidence token budget, unchanged. The Phase 6 additions that touch prompt
size: the D-17 precedence sentence (a handful of tokens, constant) and the D-11 zero-evidence path
(strictly *smaller* — no evidence blocks at all). Citation repair operates on the **returned answer**,
after generation, and has no context-window effect. No chunking, summarization or compaction strategy
changes in this phase.

### Cost and Latency Budget

| Path | Provider calls | Change from today |
|---|---|---|
| Healthy query | 1 embedding + 1 generation (+1 on retry) | unchanged |
| One path degraded (D-13) | same | unchanged — degrade is not a retry |
| Zero evidence, opt-in **off** | 1 embedding, **0 generation** | unchanged (D-03 short-circuit) |
| Zero evidence, opt-in **on** (D-11) | 1 embedding + 1 generation | **new cost**, only when opted in |
| Citation repair (D-14) | **0 additional** | by construction — no second provider call |
| Bad input (D-15) | **0** | rejected before embedding; currently some cases reach further |

D-15 is a net cost *reduction* on the invalid-input path — rejecting before provider work is its
acceptance criterion, and it happens to save the call. Caching: none added; 6.3 owns the judge cache.
No sub-task model routing — single model per role, pinned (D-62).

records 06.3 §6's reference-set spot-check is weighted toward, and the citation-repair adjudicator's
queue is the `CITATION_REPAIRED` subset — the only control that catches a repair that resolved a
marker to the wrong evidence.
