## Phase User Story

**As a** client of Lancet's `/rag/query` endpoint, **I want to** receive an honest, machine-readable
answer even when the graph is unavailable, one retrieval path fails, evidence is absent, or the
model's citations do not resolve, **so that** I can tell a degraded answer from a healthy one — and a
grounded answer from a model-only one — without parsing prose.

> This plan delivers the first slice of that story end to end: the "graph is unavailable — or was
> deliberately switched off — and I can tell which" half.

<objective>
Make graph absence observable. Land one end-to-end slice — a caller sets the graph-ablation flag and
receives an answer produced without graph context, carrying a notice that says so — then close
DEBT-RAG-06 by giving the two silently-degrading graph paths their own notice.

Purpose: D-08 closes DEBT-RAG-06 by adding the missing notice rather than by changing behavior; the
graph node already emits notices on failure, and what degrades silently is the empty-result path and
the absent-port path. Research open question 4 found that no success criterion in Phase 6, 6.1, 6.2 or
6.3 owned the ablation flag's *behavior* even though Phase 6.3 depends on it, and recommends this plan
own it: the flag is one early return in the same node, landing on the same branch D-08 is
instrumenting, and it must carry a distinct notice or Phase 6.3's graph-off arm becomes
indistinguishable from an outage.
Output: the resolved flag in the workflow context, three instrumented non-failure paths in the graph
node, and the tests that prove a source-chunk query never needs graph data.
</objective>

<scope_rationale>
Tracer-first. Task 1 is one production-quality vertical slice: the request flag crosses admission,
reaches the node, changes what the node does, and shows up in the serialized response. It is not a
prototype and nothing in it is thrown away — it is the ablation feature, complete for its one path.
Tasks 2 and 3 expand horizontally from that proven spine.

**Where the tracer's "end to end" ends, and why.** The engine's single serialization point is the
context-to-response conversion in the workflow module, and the repository has no cross-process test
harness — the only true integration target is a startup test. So the tracer's verification drives the
real gRPC service implementation through its `query_rag` entry point, using the service-construction
helper the existing test root already provides, and asserts on the response the service streams back.
That is genuinely end to end *within the engine process*: request admission, flag resolution, node
dispatch, notice accumulation, serialization. The HTTP hop is not re-proven here because plan 06-07
already proved it — that plan's Go tests assert both flags cross the strict decoder and reach the
generated request. A plan-checker looking for a two-process assertion will not find one, deliberately.

Three tasks rather than two because D-08's two silent paths and DEBT-RAG-06's "never requires graph
data" proof are different kinds of work: the first is an edit to production branches, the second is
purely a test that closes a ROADMAP success criterion the notice alone does not close.

**Test-count gate protocol.** `scripts/engine-test-targets.sh` asserts *fixed measured* counts, and
this plan adds tests, so its current expected values stop holding the moment it lands. That is the
design: the gate exists to make a count change deliberate, not impossible. Run the enumeration,
confirm the delta is exactly the tests the task added, write the newly measured values into the
script's assertions **in the same commit as the tests that moved them**, and record the before and
after rows verbatim in the summary. Never lower an expected value to make the gate pass, and never
delete an assertion: the expected value must equal the measured value and the delta must be
explainable test by test. A delta the task cannot account for is a finding to report, not a number to
overwrite. The script's *structure* — one row per target, a named failure message per assertion — is
never edited; only the expected values move. Update it once, at the end of the last task, so the
plan's three tasks produce one count change rather than three.

Shell note: every `<automated>` gate in this phase is POSIX shell, matching `.planning/config.json`'s
`test_command`. Run them through the Bash tool, not PowerShell.
</scope_rationale>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| gRPC client → engine admission | An untrusted request field now changes which nodes do work; it is resolved once at admission and never re-read. |
