## Phase User Story

**As a** client of Lancet's `/rag/query` endpoint, **I want to** receive an honest, machine-readable
answer even when the graph is unavailable, one retrieval path fails, evidence is absent, or the
model's citations do not resolve, **so that** I can tell a degraded answer from a healthy one — and a
grounded answer from a model-only one — without parsing prose.

> This plan delivers the negative half of that story: when the request itself is bad, the rejection is
> stable, enumerated and identifiable — and it costs nothing, because it happens before any work.

<objective>
Enumerate the bad-input surface as a table and prove it on both surfaces: a table-driven gRPC test
asserting the status code and the stable error-kind string per row, and a table-driven HTTP test
asserting status 400 and the error-kind header per row.

Purpose: D-15 is mostly test work. The nine-variant retrieval error taxonomy, its mapping to status
codes and stable error-kind strings, the identifier format checks, and the gateway's derivation of
HTTP 400 from the gRPC code all already exist and already run before retrieval. What does not exist is
the enumeration — the artifact that says which inputs are rejected, with what identity, and which
inputs deliberately are not. Building a second validation surface here would create two sources of
truth for the same bound and guarantee they drift.
Output: the matrix, the two table-driven tests, and the recorded dispositions for the rows that are
deliberately not rejections.
</objective>

<scope_rationale>
Two tasks, one per surface, gRPC first because the HTTP surface derives its status from it. This plan
is test-and-enumeration work over an existing validation surface, which is why it carries no tracer
task: it adds no new capability path to trace.

**Why this plan runs last despite depending only on 06-07.** Its source files — a new test module
declared from `engine/src/tests.rs`, and `gateway/main_test.go` — collide with nothing in the behavior
plans, so on content alone it could run alongside 06-08. What it does collide with is the two gate
scripts: it adds tests to both suites, so it must update the expected counts in
`scripts/engine-test-targets.sh` and `scripts/gateway-test-targets.sh`, and every behavior plan from
06-08 to 06-11 updates the engine one too. Two plans rewriting the same expected value in the same
wave would produce a merge conflict on the one file whose whole purpose is to be authoritative about
test counts. Serializing after 06-11 costs a wave and removes that class of failure entirely. The
`depends_on` list names 06-11 for that reason, not because this plan needs anything 06-11 builds.

`rust-guidelines.md` governs task 1 and `go-guidelines.md` with target Go **1.25** governs task 2
(`gateway/go.mod:3` declares `go 1.25.0`, the installed toolchain is newer, and Go 1.26 features are
forbidden even though they compile).

Publishing the matrix as documentation is Phase 6.4's work, not this plan's. The table lands here as a
committed test artifact and as a verbatim block in the summary; 6.4 lifts it.

**Test-count gate protocol.** `scripts/engine-test-targets.sh` and `scripts/gateway-test-targets.sh`
assert *fixed measured* counts, and this plan adds tests to both suites, so their current expected
values stop holding the moment it lands. That is the design: the gates exist to make a count change
deliberate, not impossible. For each task — run the enumeration, confirm the delta is exactly the
tests the task added, write the newly measured values into the script's assertions **in the same
commit as the tests that moved them**, and record the before and after rows verbatim in the summary.
Never lower an expected value to make a gate pass, and never delete an assertion: the expected value
must equal the measured value and the delta must be explainable test by test. A delta the task cannot
account for is a finding to report, not a number to overwrite. The scripts' *structure* — one row per
target, a named failure message per assertion — is never edited; only the expected values move.

Shell note: every `<automated>` gate in this phase is POSIX shell, matching `.planning/config.json`'s
`test_command`. Run them through the Bash tool, not PowerShell.
</scope_rationale>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP client → gateway | Untrusted JSON crosses the body bound and the strict decoder; this is the outermost validation boundary and the matrix's HTTP half proves its identity contract. |
| gRPC client → engine admission | Untrusted request fields cross the validation surface; every rejection must occur before any retrieval or provider work so a malformed request cannot consume corpus or provider budget. |
| Engine error → HTTP status | The error-kind string and the status code are the published identity of a rejection; a client's retry and reporting behavior depends on them being stable. |
