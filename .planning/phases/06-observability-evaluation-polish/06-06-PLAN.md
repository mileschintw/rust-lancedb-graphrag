## Phase User Story

**As a** client of Lancet's `/rag/query` endpoint, **I want to** receive an honest, machine-readable
answer even when the graph is unavailable, one retrieval path fails, evidence is absent, or the
model's citations do not resolve, **so that** I can tell a degraded answer from a healthy one — and a
grounded answer from a model-only one — without parsing prose.

> Planner-derived from the phase's only user-facing outcome (RAG-03 degraded mode). This plan builds
> the test surface every later behavior plan asserts against; it delivers no user-visible slice of the
> story itself.

<objective>
Make the D-74 wire-contract change reviewable and the RAG-03 behavior changes testable: one test
constructor module for the two protobuf messages the contract change touches, the four D-83 fake-port
failure modes, and a Go assertion that actually notices a new JSON key.

Purpose: research §3 measured the churn — the request message appears as an exhaustive struct literal
80 times with zero uses of the struct-update shorthand, and the notice message 19 times, so a naive
proto edit produces roughly 101 compile errors in the same diff as a published-contract change and
the review D-74 exists to enable does not happen. On the Go side the opposite problem holds: research
counted zero whole-payload equality assertions, so an added JSON key is invisible to all 67 tests.
This plan closes both, and lands D-83's failure modes so the behavior plans have something to fail
with.
Output: `engine::testkit`, the extended fake seam, and the Go payload-shape tests.
</objective>

<scope_rationale>
Three tasks, one per surface, ordered by what the next plan needs first. Task 1 is the literal
migration that unblocks the proto edit. Task 2 is D-83, which every behavior plan from 06-08 onward
consumes. Task 3 is the Go-side gap: a payload-shape assertion has to exist *before* 06-07 adds keys,
or the keys land under no observation at all.

They are separate tasks rather than one because task 1 is roughly a hundred near-identical edits in
four files and task 2 is a small number of designed additions in two files; interleaving them would
bury the design work in the churn — the same reasoning that separates this plan from 06-07.

`rust-guidelines.md` governs tasks 1 and 2; `go-guidelines.md` with target Go **1.25** governs task 3
(`gateway/go.mod:3` declares `go 1.25.0`, and the installed toolchain is newer — Go 1.26 features are
forbidden even though they compile).

**Test-count gate protocol — applies to every task below, and to every Phase 6 plan from this one
onward.** `scripts/engine-test-targets.sh` and `scripts/gateway-test-targets.sh` assert *fixed
measured* counts, and this plan adds tests, so their current expected values stop holding the moment
it lands. That is the design: the gates exist to make a count change deliberate, not impossible. For
each task that changes a count — run the enumeration, confirm the delta is exactly the tests the task
added, write the newly measured values into the script's assertions **in the same commit as the tests
that moved them**, and record the before and after rows verbatim in the summary. Never lower an
expected value to make a gate pass, and never delete an assertion: the expected value must equal the
measured value and the delta must be explainable test by test. A delta the task cannot account for is
a finding to report, not a number to overwrite. The scripts' *structure* — one row per target, a named
failure message per assertion — is never edited; only the expected values move.

Shell note: every `<automated>` gate in this phase is POSIX shell, matching `.planning/config.json`'s
`test_command`. Run them through the Bash tool, not PowerShell.
</scope_rationale>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Test-only code → production binary | The D-83 fake seam is compile-time gated; a fake that escapes the gate becomes a way to make a running engine return an attacker-chosen empty or malformed result. |
| Wire payload → HTTP client | The Go key-set assertions are the only mechanism that makes a change to that payload visible; without them a field can be added or removed silently. |
