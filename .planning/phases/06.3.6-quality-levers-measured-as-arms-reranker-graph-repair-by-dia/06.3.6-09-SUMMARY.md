# Phase 06.3.6 Plan 09: Rerank lever Summary

**An OpenRouter rerank adapter behind a query-taking Reranker port, selected per request, degrading to the fused order with a class-only notice, nested in the retrieve node budget at a provisional 1706 ms, with every lever-free byte unchanged**

## Accomplishments

- The `Reranker` port takes `RerankRequest { query, candidates }` and returns `RerankOutput { ranked, cost_credits }`. A failing reranker can no longer lose the fused list. `NoOpReranker`, `RecordingReranker`, `FailingReranker` and `FakeReranker` follow, and `reorder()` validates a permutation with finite scores.
- `OpenRouterReranker` makes one POST per query with `bearer_auth` and `provider.allow_fallbacks = false`; no retry, no spawn, no redirect. The reply must be a permutation of the documents with finite scores and a `model` that is the slug or its bare name (D-186). It is ordered by `(score desc, index asc)` and read through a 1 MiB cap. All twelve listed statuses, transport, timeout and malformed replies map to class-only errors. A sentinel key never appears in an error, a captured TRACE log or any `Debug` output.
- `RetrieveHybridNode` runs the lever for a request that names `rerank` and has a lever reranker: one call clamped to the node budget left minus a 50 ms reserve, relevance written over `fused_score` (D-166) so the packer reproduces the reranked order, and on any failure the fused list kept with one `RERANK_DEGRADED` notice, `RerankMetadata.outcome` set to the class, and the `rerank` path-failure metric. The pre-truncation ranking is now captured after the reranker and before the final take (D-133); with no reranker the order is the fused order and the three goldens are unchanged.
- `LeverResources` and `build_production_workflow_with_levers` pick the reranker per request. `rerank` is available only when the lever reranker is wired; `main.rs` builds it from the generator's key. The service-wide NoOp reranker keeps its strict `RetrievalFailed` semantics for lever-free requests.
- `rerank_timeout_ms = 1706` is the 8th workflow budget in `config.toml`, `config.example.toml` and the `config.rs` default (the largest value that nests: 2500 - 294 - 500). Startup refuses a zero value and `retrieve_timeout_ms < rerank_timeout_ms + 294 + 500`. `LANCET_ENGINE__WORKFLOW__RERANK_TIMEOUT_MS` overrides it. `[openrouter]` gains `rerank_endpoint` and `rerank_model` (no environment override for the endpoint).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] RED commits carry the non-test scaffolding they compile against**
- **Found during:** Task 1 and Task 2 (Rust has no failing-test-without-compiling step)
- **Issue:** changing a trait or adding a config field breaks every caller, so a RED commit that is only tests would not compile.
- **Fix:** each `test(...)` commit holds the mechanical port/field changes and a skeleton whose behaviour is wrong (an empty ranking, an unclamped allowance, a node that ignores the lever), so the new tests fail on assertions. The config files were left unedited in the Task 2 RED commit so the agreement tests failed for the right reason.
- **Files modified:** as listed under each commit
- **Committed in:** e65a52f5, 06518fba

**2. [Rule 3 - Blocking] `engine/src/tests/retrieval_mode_pins.rs` edited although the plan does not list it**
- **Found during:** Task 2 (lever pins)
- **Issue:** the byte-identity golden renderer, `Fixture`, `run_chain` and the runner helper are private to that module and cannot take a reranker, lever or admitted `LeverSet`.
- **Fix:** `Fixture`, `run_chain`, `with_ranking`, `stripped` and a new `run_runner` are `pub(super)`; `Fixture` gains `with_reranker` / `with_lever`; `Variation` gains `with_identity_lever`; `run_chain` and `run_runner` apply `LeverSet::try_from_wire(variation.levers)` to the context; `Variation::strip` also clears the `levers` echo. Every existing call passes empty levers, so the recorded goldens are unchanged (all pass).
- **Files modified:** engine/src/tests/retrieval_mode_pins.rs
- **Committed in:** 06518fba

**3. [Rule 3 - Blocking] Admission and node tests live in `levers_pins.rs`, not `bad_input_matrix.rs` and `tests.rs`**
- **Found during:** Task 2
- **Issue:** the plan put the admission rows in `bad_input_matrix.rs` and the node tests in `tests.rs`. The matrix builds one service that must stay unwired for its `lever_unavailable_rerank` row, so it cannot also hold the wired, admitted case; and the node pins need `retrieval_mode_pins`' fixtures, which `levers_pins.rs` already imports.
- **Fix:** the unwired rows stay in the matrix (doc wording updated); the wired availability, the per-request selection through the real service, and every node pin are in `levers_pins.rs`, which reaches `tests.rs`' private fakes through its parent module.
- **Files modified:** engine/src/tests/levers_pins.rs, engine/src/tests/bad_input_matrix.rs
- **Committed in:** 06518fba, 5b306148

**4. [Rule 1 - Bug] Flaky log capture in the sentinel test under parallel execution**
- **Found during:** Task 1
- **Issue:** the test installed one `tracing` subscriber and could miss the `rerank_call` event when another test thread first hit the same callsite while the subscriber was being created.
- **Fix:** two warm-up subscribers, each with one real call, are created before the asserted calls, because creating a subscriber rebuilds the callsite interest cache. The test passed in four consecutive parallel runs and in the full suite.
- **Files modified:** engine/src/rerank/tests.rs
- **Committed in:** 9a79eaf7
