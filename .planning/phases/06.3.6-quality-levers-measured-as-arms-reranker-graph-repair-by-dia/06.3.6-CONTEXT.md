## Phase Boundary

**What this phase delivers:**
- A small set of standard quality levers, each switchable per request through one `levers` list on the
  query contract (D-136):
  - a reranker;
  - a graph repair, chosen by a pre-registered diagnosis rule;
  - evidence metadata (date, source and real title) in the prompt;
  - a yes/no answer-format rule.
- Each lever is developed on the 100 dev questions only.
- Each lever is read **once** on the 06.3.5 held-out split (351 questions) in one interleaved drive. The
  drive includes a same-day `hybrid` reference on one recorded index generation.
- A lever becomes a default only on a pre-registered Holm rejection with a positive delta. A lever that
  does not pay is recorded, not shipped. Results are published in either direction (D-49).

**Amended against the ROADMAP wording (owner, this discussion; ROADMAP edited to match):**
- Lever 3 is **evidence metadata**: date, source and real title, arm `hybrid+metadata`. It was
  `published_at` only, arm `hybrid+temporal` (D-142).
- A descriptive `hybrid+graph` (v1) control arm is added (D-140).
- The Holm family covers the **lever arms only**. `hybrid+all` is descriptive (D-150).
- No judge pass runs (D-153).

**Evidence gathered during this discussion (2026-10-08):**
- **The reranker cannot be scored on the D-100 ranking as it stands.** The D-100 ranking is captured *before*
  the reranker (`engine/src/workflow/nodes/retrieve.rs:369-391`), so a rerank arm read from it would equal
  `hybrid` by construction. D-133 fixes this.
- **Truncation comes after the reranker.** The reranker receives the whole fused list, and `.take(final_limit)`
  happens after it (`retrieve.rs:393-395`). A reranker failure today returns `RetrievalFailed` (`retrieve.rs:378-388`).
- **A full reseed rebuilds the graph.** Re-ingestion re-runs LLM entity extraction
  (`engine/src/ingest.rs:912` `extract_and_persist_entities`), so a reseed would replace `lance-702`'s graph
  and invalidate the lever-2 diagnosis. D-144 avoids that.
- **The metadata is in the corpus but never reaches the prompt.**
  - `eval/corpora/multihop_rag/documents.subset.jsonl` carries `title` (HTML-entity-escaped), `source`
    (the publication), `published_at`, `category` and `url`.
  - The prompt's `<TITLE>` (`engine/src/prompt.rs:41-95`) holds a sanitized filename
    (`Bills_vs._Bengals_live_score__….txt`).
  - Neither source nor date reaches the prompt.
  - Dev questions name publications ("Does the Engadget article claim … while the TechCrunch article …").
- **No query-time question type.** The engine has no `question_type`, and the base system policy already
  asks for `Answer: <yes, no, an entity name, or a short phrase>` (`prompt.rs:212-223`).
- **Where the graph repair lever starts from.** The `Reranker` port (`engine/src/rerank/mod.rs`) has only
  `NoOpReranker`. The `EntityResolver` port (`engine/src/db/mod.rs:336`) has only `ExactMatchResolver`.

**Out of scope (ROADMAP, unchanged):**
- community summaries (999.1/999.5/999.4);
- query reformulation (999.3, v1.1);
- a local inference endpoint (999.11, v1.1);
- deeper traversal (more hops is explicitly not a lever);
- new corpora;
- metadata-aware retrieval (deferred, see `<deferred>`).

### Lever switches on the wire

- **D-136:** **A repeated `levers` enum on the query request.**
  - **Values:** names are Claude's discretion; there is one value each for the reranker, graph v2, evidence
    metadata and binary answer format.
  - **Default:** an empty list is today's behaviour, byte-identical. Proven by goldens: the
    `graph_off_fusion.golden` and the default-request node-chain golden from 06.3.5-01, plus a prompt
    golden.
  - **Fail-closed rules:** an unknown value fails closed at both the gateway and the engine (the D-99
    unknown-mode pattern), and a duplicate value is rejected.
  - **Provenance:** the snapshot echoes the canonical sorted list, so the harness verifies arm provenance
    per record, the way it verifies `retrieval_mode` and `GRAPH_ABLATION`.
  - **Independence:** the list is orthogonal to `retrieval_mode` and `disable_graph_context`.
  - **Wire changes:** the D-52 pattern applies (regenerate both proto trees and the gateway's vendored
    `lancet.pb.go`, and add a gateway pin test).
  - **Reversibility:** costly. It is a new public contract field that every client sees.

### Lever 1: reranker (999.2)

- **D-131:** **The reranker is `voyageai/rerank-2.5-lite` served through OpenRouter** (owner choice), behind
  the `Reranker` trait. `NoOpReranker` stays the default.
  - **Research must verify that OpenRouter actually serves rerank for this model:** the endpoint shape,
    pricing and the auth path.
  - **If it does not, research stops and the owner is asked.** There is no silent fallback to another
    provider or model.
  - Rerank spend reconciles on the OpenRouter account like generation spend.
- **D-132:** **The reranker re-scores the whole fused list**, bounded by `candidate_limit = 32`, and the
  engine keeps `final_limit = 8`. `config/config.toml` `[engine.retrieval]` is unchanged, so only the order
  moves.
- **D-133:** **The D-100 ranking capture moves to after the reranker.** It is still taken before
  truncation, so the field keeps its name and meaning ("pre-truncation ranking").
  - Under `NoOpReranker` the order is identical, so every D-100 golden and every 06.3.5 reading still
    holds. A test proves it.
  - On the rerank arm, Hits@4/@10, MRR@10 and MAP@10 read the reranked order.
  - The "where was gold before rerank" view comes from the same question's `hybrid` record in the
    interleaved drive. Retrieval is deterministic within a run.
  - **Reversibility:** costly. It changes what a contract field means when a reranker is active.
- **D-134:** **A reranker failure degrades with a notice.**
  - **Behaviour:** on a reranker error or timeout, the engine keeps the fused order and emits a
    `RERANK_DEGRADED` notice (the code name is Claude's discretion). This replaces today's `RetrievalFailed`
    on the rerank path only.
  - **In the harness:** such records are **off-arm**. They are excluded as a provenance failure of the
    rerank arm and counted per arm, never silently mixed into it.
- **D-135:** **The rerank timeout is derived, not guessed** (06.3.3 rule, SC-3).
  - Rerank latency is measured on the dev reads, and the budget comes from a censoring-aware high quantile
    plus headroom.
  - The budget is committed before the held-out cap checkpoint.
  - Rerank latency is a wire-visible node timing.

### Lever 2: graph repair chosen by diagnosis (999.6-lite)

- **D-137:** **The pre-registered selection rule**, committed before the diagnosis table is regenerated and
  applied mechanically.
  - **Table:** for each of the 38 drive-2 dev `GRAPH_UNAVAILABLE` questions (on `lance-702`), one class:
    *gold entities absent* / *alias split* / *missing edge* / *other*. SC-1 requires it to be a regenerated
    artifact, not a narrative.
  - **Rule:**
    - Alias split is the strict plurality: **entity resolution**.
    - Missing edge or other is the plurality, or there is any tie: **graph-list precision**.
    - Gold entities absent is the strict plurality: **no lever-2 arm** (D-141).
  - The rule and the resulting selection are recorded before any lever-2 code is committed.
- **D-138:** **If entity resolution is selected, the merged graph lives in side tables.**
  - Alias-merged entity and edge tables are written in the same store, next to the v1 tables, and the
    graph-v2 lever selects them per request.
  - Chunks, embeddings and the v1 graph stay `lance-702`. There is no LLM re-extraction, so v1 and v2
    coexist.
  - The merge goes through `EntityResolver` (normalised name plus name-vector similarity). The similarity
    threshold is set on dev within the D-154 budget.
  - **Reversibility:** costly. It adds new store tables and a per-request table selection.
- **D-139:** **If graph-list precision is selected, the variant is chosen on dev within the 2-read budget.**
  - Read 1 uses the edge-evidence chunk only.
  - If needed, read 2 uses chunks cited by at least 2 path entities.
  - The variant with the better dev `answer_usable` is frozen, and both readings are disclosed.
- **D-140:** **A descriptive `hybrid+graph` (v1) control arm runs in the drive.**
  - It reports paired deltas against `hybrid`, and `graph-v2` against `graph-v1`.
  - It is outside every Holm family and decides nothing.
  - It separates "the repair moved the graph" from "graph on".
- **D-141:** **If the rule says neither repair applies**, the diagnosis table *is* the lever-2 result.
  - There is no `graph-v2` arm, and the reason is recorded for 6.4's limitations.
  - The Holm m and the `hybrid+all` composition shrink accordingly.
  - The v1 control arm is still run as a descriptive arm.

### Lever 3: evidence metadata (amended from "temporal metadata")

- **D-142:** **The lever carries three fields into each evidence block's headers, behind the lever flag
  only:**
  - `published_at` rendered as `YYYY-MM-DD`;
  - `source` (the publication name);
  - the real document **title** (HTML entities unescaped).

  More rules:
  - **Reference arm unchanged:** the reference arm's prompt stays byte-identical, proven by a golden.
  - **Arm name:** `hybrid+metadata`.
  - **Missing fields:** a document without one of the fields omits that header and never fails (SC-4).
  - **Carry-forward #4:** this covers titles **for generation**. The judge-side half is deferred (D-153).
  - **Why source and title are included:** MultiHop-RAG questions name publications, so the source and
    title are likely the larger half of this lever. Attribution stays one lever (owner's choice over
    splitting into two arms).
- **D-143:** **Data plus one policy sentence.** Under the flag only, the system policy gains one sentence
  stating that evidence blocks carry their publication, title and date, and to use them when the question
  refers to a source or a time. The exact wording is set on dev within D-154.
  - The pinned base policy text and its byte-identical prefix tests (`prompt.rs:708-790`) are untouched
    when the flag is off.
- **D-144:** **Storage: ingestion learns the fields, and the eval store gets a backfill (no reseed).**
  - **Ingestion:** the ingestion path persists `published_at`, `source` and the real title as chunk or
    document metadata for new documents.
  - **Backfill:** the eval store gets a one-off column backfill keyed by `document_id` onto `lance-702`.
    Chunks, embeddings and the graph do not change.
  - **Identity:** the post-backfill store is recorded as a new index generation. Every arm of the held-out
    drive runs on it, including the same-day `hybrid`, which satisfies SC-6.
  - **D-61 coverage:** regenerated on it, and expected identical. A diff proves it.
  - **Test:** backfilled values must equal what a fresh ingest of the same document writes.
  - **Reversibility:** costly. It is a schema change on a store table plus a recorded generation bump.
- **D-145:** **The metadata reaches the prompt and nothing else.**
  - Retrieval is untouched (no BM25 or embedding over source or title), so `hybrid+metadata`'s retrieval
    equals `hybrid`'s by construction.
  - Graph-path facts do not carry the metadata.
  - The wire's `StructuredCitation.title` is unchanged (still the stored title), so harness matching and
    06.3.5 comparability hold.

### Lever 4: answer format for binary gold

- **D-146:** **A conditional rule, always present under the flag.** The rule: if the question can be
  answered yes or no, the `Answer:` line must be exactly `Yes` or `No`.
  - There is no question-type classifier in the engine.
  - **`question_type` is never passed from the harness to the system under test.** It is a benchmark label
    that a production client would not have.
- **D-147:** **Format plus an evidence-decides stance.** The rule adds: for a yes/no question, answer from
  the evidence; if the evidence covers both parts and they do not match the claim, answer `No` rather than
  `Insufficient information`.
  - This targets the dev abstention loss (the 26 drive-2 "(c) yes, (e) no" questions).
  - The wording is set on dev within D-154.
- **D-148:** **Two guards, pre-registered before the held-out drive:**
  1. **Null-abstention non-inferiority.**
     - The lever cannot become a default if `null_abstention_correctness` drops by more than a margin
       against the same-day `hybrid` (n = 43, coarse; disclosed).
     - Research proposes the margin, the owner confirms it, and it is committed in `thresholds.py` before
       the drive (D-73).
  2. **A Yes-share disclosure.** On the comparison stratum, the arm's share of `Yes` answers is reported
     beside the gold Yes share and the constant-Yes baseline, so a Yes-bias "win" is visible.
  - Beating the constant-Yes baseline is **not** a default condition (owner).

### Drive and pre-registration

- **D-149:** **The arm set.**

  | Arm | Role | `levers` | Graph |
  |---|---|---|---|
  | `hybrid` | reference, re-run the same day | none | off |
  | `hybrid+rerank` | lever | rerank | off |
  | `hybrid+graph-v2` | lever (only if D-137 keeps it) | graph_v2 | on |

  - `retrieval_mode` is `hybrid` on every arm. The D-101 registry gains these labels.
  - Size: 7 × 351 ≈ **2,457 records** (6 arms if graph-v2 is dropped).
- **D-150:** **Holm families and the default rule.** This supersedes the ROADMAP's "five lever arms" and its
  "CI excludes zero" wording.
  - **The `answer_usable` family decides defaults.**
    - It holds the lever arms against `hybrid`: m = 4, or 3 without graph-v2.
    - The test is D-123's exact two-sided paired sign-flip (exact McNemar), with Holm step-down at FWER 0.05.
    - The population is the all-arms-ok paired set, the D-121 analogue.
    - A lever becomes a default only on a **Holm rejection with a positive delta** that also passes its
      guards (D-148).
  - **The paper `Hits@4` family supports a retrieval claim and does not decide a default.**
    - It holds `hybrid+rerank` and `hybrid+graph-v2` against `hybrid` (m ≤ 2).
    - A rejection supports a retrieval-improvement claim. It cannot make a default on its own.
  - **Descriptive arms:** `hybrid+all` and `hybrid+graph` (v1) are reported with unadjusted paired deltas
    and decide nothing.
  - **Reporting:** bootstrap CIs are reported, labelled "unadjusted, estimation only" (D-123). The report
    states that the FWER across both families can reach 0.10.
  - **Commitment:** committed as `PREREGISTRATION_06_3_6` in `thresholds.py` before the held-out cap
    checkpoint, and never changed after data is seen (D-73).
- **D-151:** **SC-2 error-mode materiality floor** (carry-forward #1).
  - Research proposes a count-or-rate floor, derived the D-89 way, below which the error-mode clause reports
    instead of failing.
  - The owner confirms it, and it is committed before the drive.
  - The drive-1/1b/2 and 06.3.5 gate verdicts must re-read unchanged under the new floor, or the difference
    is shown and explained.
- **D-152:** **Query-embedding resilience: one bounded retry** (carry-forward #2).
  - On a query-embedding timeout, the engine retries once after a short jitter. The per-attempt budget
    stays `query_embedding_timeout_ms = 2000`.
  - Each retry emits an event and a per-record count.
  - It applies to every arm, the reference included. The same-day reference controls for it.
  - **The engine is changed before the drive.** This is not a change after a held-out read: 06.3.6's
    held-out read has not happened yet.
- **D-153:** **No judge pass in 06.3.6.**
  - Judged dimensions are uncalibrated (D-114) and barred from defaults.
  - Carry-forward #5 is fixed: the judge price constants in `eval/src/lancet_eval/measure.py` are

  - Carry-forwards #3 (marker convention in the rubric), #4 (judge-side evidence titles) and #6
    (recalibration) are deferred to v1.1 with this reason recorded.
- **D-154:** **The dev budget and the freeze.**
  - Each lever gets at most **2 paid dev reads**: a first read and at most one revision.
  - One blanket D-86 `checkpoint:decision` pre-authorises every dev read up to one total cap. The planner
    proposes the value; it is cents per read.
  - All lever parameters (prompt sentences, rerank timeout, precision variant, ER threshold) are frozen in
    **one commit before the held-out cap checkpoint**.
  - Dev reads use dev questions only (D-106 discipline; D-124 for canaries).
- **D-155:** **The drive shape follows D-107/D-108.**
  - **Drive:** one interleaved drive, with all arms of a question back to back in a seeded, balanced
    rotation. It runs at `--workers 1`, `--retries 0` and `--gate-stage` under its own D-86 cap, about 6 h,
    detached.
  - **Rehearsal first:** a rehearsal precedes it. It runs canaries under every arm from the rehearsal pool
    only (D-124), plus a cent-level live probe that proves arm provenance and the `levers` echo on the wire.
  - **Where it runs:** sequentially on main (memory `execute-phase-worktree-vs-live-store-lancet`).
- **D-156:** **Gates and misses.**
  - Gates are read per arm plus a pooled line (D-109), with the D-151 floor.
  - A miss follows **D-110 unchanged**: one bounded re-drive for a plumbing or infrastructure fix only, with
    a new cap, then halt-disclose. A quality change is never allowed, and a worse arm is a result.
- **D-157:** **How a win lands.**
  - The run of record states each default decision. **One commit after the run of record** flips the default
    for each winning lever, with goldens updated and the run untouched.
  - That commit is outside the measured system (SC-7), and Phase 6.4 documents the new defaults.
  - Latency and prompt-token cost per arm are **reported only** (D-42) and gate nothing.
- **D-158:** **06.3.5 review debt fixed here.**
  - **WR-02's remainder:** `lancet-eval compare` gets the D-73 git gate on pre-registered values. This is
    mandatory before the held-out compare.
  - **IN-02:** a normalised abstention is no longer flagged `degraded_mode`.
  - **IN-03:** preflight fails closed instead of silently running the legacy canaries when the corpus
    config fails to load. This guards the held-out questions.
  - **IN-04:** provenance clause (a) no longer substring-matches a message. This matters with new notices
    like `RERANK_DEGRADED`.
  - IN-01, IN-05 and IN-06 stay open (deferred).

- **D-159:** **Store mutations land in a fixed order, and the generation is recorded once** (SC-6).
  1. Every store write lands first: the D-144 metadata backfill, plus the D-138 side tables if entity
     resolution is selected.
  2. The index generation is recorded **once** after both.
  3. D-61 coverage is regenerated on that generation.
  4. Every dev read that uses `evidence_metadata` or `graph_v2`, the rehearsal and the held-out drive run on
     that one generation.

  Research confirms how `index_generation` is derived (from Lance table versions or set by hand), and so
  whether the bump is automatic.
- **D-160:** **The population for the decisional family is pre-registered, not defaulted** (the D-148/D-151
  pattern).
  - **Why it matters:** with seven arms, an all-arms-ok population (the plain D-121 analogue) would let
    failures on the descriptive arms remove questions from the decisional tests. D-134's off-arm
    `RERANK_DEGRADED` records would drop questions from *every* lever's test.
  - **The choice:** research proposes complete-case over the reference plus the decisional lever arms only,
    or pairwise per comparison. The proposal comes with a complete-case coverage floor.
  - **Commitment:** the owner confirms, and it is committed in `PREREGISTRATION_06_3_6` before the held-out
    cap checkpoint.

### Owner confirmations from `/gsd-ai-integration-phase 06.3.6` (2026-10-09)

*Proposed in `06.3.6-AI-SPEC.md` §5 "Owner decisions" (O1..O6) and confirmed by the owner. They are committed
in `PREREGISTRATION_06_3_6` / `thresholds.py` before the held-out cap checkpoint (D-73). Derivations: §5 and
`research/d148_null_guard.out`, `research/d151_sc2_floor.out`. No held-out number set any value (D-129).*

- **D-161:** **The D-160 population is pairwise per comparison.** It resolves D-160.
  - **Population:** for each comparison X, P_X = the held-out G questions with `ok(r)` on `hybrid` and on X.
  - **Families:** it applies to both the `answer_usable` and the Hits@4 family.
  - **Coverage floor:** |P_X| / 308 ≥ 0.80 for each comparison, i.e. ≥ 247 pairs. A comparison below the floor
    enters Holm as p = 1, and m stays fixed.
  - **Why:** a rerank degrade (D-134) or a descriptive-arm failure cannot remove questions from another lever's
    test.
  - **Supersedes:** D-150's "the all-arms-ok paired set, the D-121 analogue".
- **D-162:** **The D-148 guard 1 rule is a count rule at 0.10, and it fails closed.**
  - **The rule:** the lever cannot become a default if (b − c) / n_N > 0.10 on the paired null questions against
    the same-day `hybrid`. That is a net null-abstention loss of ≥ 5 of 43.
  - **Fewer than 35 null pairs** (⌈0.80 × 43⌉): the guard fails closed.
  - **Basis:** the 0.10 is the repo's committed material-rate convention (`thresholds.py`). Dev could not set it:
    there were 0 discordant pairs in the dev null pairings.
- **D-163:** **Guard 1 binds `hybrid+answer-format` and `hybrid+metadata`.** This widens D-148's literal text.
  - **Why metadata too:** MultiHop-RAG null queries carry fictional source metadata, and 4 of 10 dev nulls name
    a publication that is in the corpus.
  - **Other arms:** for rerank, graph-v2 and the descriptive arms, null abstention is reported, not decisional.
- **D-164:** **The D-151 SC-2 error-mode floor is a rate.**
  - **The rule:** the error-mode (timeout) clause fails only if timeout is the dominant class **and** timeouts
    divided by records in the reading is ≥ 0.025.
  - **Derivation:** committed constants only, ½ (D-89's half headroom) × the 5% tail left by the p95 budget
    rule.
  - **Effect on past verdicts:** drives 1, 1b and 2 re-read unchanged. The four 06.3.5 SC-2 MISSes (three arms
    plus the pooled line) would re-read as "reported".
  - **How the difference is handled:** it is shown and explained in the run of record, as D-151 permits, and
    the recorded 06.3.5 gate files are never rewritten.
  - **Scope:** the floor applies only to drives committed after it.
