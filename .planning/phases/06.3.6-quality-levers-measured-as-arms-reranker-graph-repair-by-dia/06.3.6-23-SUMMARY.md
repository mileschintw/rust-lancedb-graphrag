# Phase 06.3.6 Plan 23: Degrade an unavailable default lever with a notice, and migrate the legacy dev store Summary

**Notice code 24 (`DEFAULT_LEVER_UNAVAILABLE`) end to end: an unavailable configured default is dropped per request with one WARNING notice and a startup WARN that runs before the ingest worker and the staged-job replay, explicit levers still fail closed, and the legacy `./data/lancedb` store is migrated once and boots under the committed config.**

## Accomplishments

- Task 1: `query_rag` keeps the D-136 order (`invalid_levers`, then `invalid_lever_combination`, then availability). Only the availability slot changed. A request that names levers keeps the `lever_unavailable` refusal byte for byte. A request that names none removes each unavailable configured default with `LeverSet::without` and adds one `DEFAULT_LEVER_UNAVAILABLE` WARNING notice per drop, "configured default lever {wire} was not applied: {reason}". The echo is the filtered set, canonical ascending.
- Task 2: `validate_default_levers` is replaced by the free functions `unavailable_default_levers` and `default_lever_unavailable_warning`. `main.rs` warns once per unavailable default right after the lever reranker exists, before `spawn_worker_with_concurrency`, the rebuild task and `read_staged_jobs`, and never exits over availability. It also warns when metadata coverage (distinct documents with an entry over distinct documents, not chunks) is below 100%, and logs "Staged ingestion jobs replayed" after the replay. A rebuild swap that empties or refills the metadata logs a WARN or INFO. The config prose and the CLOSEOUT item 2 note describe degrade-with-notice.
- Task 3: the legacy dev store was migrated exactly once and booted once (evidence below).

## Effect on the published contract

Notice code 24 joins the `degraded_mode` set (`derive_degraded_mode`), like `GRAPH_UNAVAILABLE` and `RERANK_DEGRADED` and unlike the request-shape `GRAPH_ABLATION`. Every response to a request that names no lever, over a store without document metadata (or on an engine without a lever reranker), now reports `degraded_mode = true` in its workflow metadata. Clients and dashboards that count degraded responses will count these. The same is written in CLOSEOUT item 2's supersession note.
