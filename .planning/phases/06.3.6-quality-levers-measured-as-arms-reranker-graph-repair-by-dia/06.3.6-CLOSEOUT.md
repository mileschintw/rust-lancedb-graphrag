## What the flip commit changed

One commit, `3d765ea3`, after the run-of-record commits (`2f2d4aa5`, `c6dd4cc8`), outside the measured system (SC-7):

- `config/config.toml` and `config/config.example.toml`: a new `[engine.levers]` table, `defaults = ["rerank", "evidence_metadata"]` (canonical order). The compiled-in default in `engine/src/config.rs` stays empty on purpose, so every test fixture and every service built without the file stays lever-free. A unit test pins that the code default is empty and that both files carry the winners and agree.
- `query_rag` admission (`engine/src/service.rs`): a request that names no lever runs the configured defaults and the snapshot echo reports that effective set; a request that names levers runs exactly those, never the union. The effective set goes through the same checks as a named one, so a default whose resource is missing refuses the request with `lever_unavailable` and is never silently dropped.
- Startup validation (`LancetServiceImpl::validate_default_levers`, called from `main.rs` before the server listens): the engine refuses to start when a configured default lever cannot be served. A name that is unknown, repeated or out of canonical order also stops startup (`LeverSet::try_from_names`).
- `LANCET_ENGINE__LEVERS__DEFAULTS` (comma list; an empty value means none) lets a process start lever-free. It is the operator's escape for a store that holds no document metadata yet.
- Tests: ten lib tests, two `config_startup` tests, two post-table checks inside the bad-input matrix test, and the count script (lib 803 to 813, config_startup 22 to 24, total 915 to 927). The `config_startup` fixtures now start lever-free by default, because they boot the real engine with the committed config over an empty store.
- **Goldens: none moved and none was re-recorded.** The three goldens (`retrieve_node_default.golden`, `graph_off_fusion.golden`, `provider_messages_default.golden`) render at node level or with default settings, where the default list is empty; the full engine suite passed against them unchanged. Re-recording would have been a behaviour change to justify, and there was none.
- After the commit the engine was release-rebuilt (`cargo build --release --manifest-path engine/Cargo.toml --locked`, exit 0), so the deployed binary matches the committed source.
- `eval/runs/` was not touched: `git diff --quiet 9583bf80 HEAD -- eval/runs/2026-10-06-drive2-multihop_rag_diag eval/runs/2026-10-07-heldout-multihop_rag_heldout` exits 0 and `git status --porcelain -- eval/runs` is empty. ## Open items (not blockers; the owner decides)

1. **The eval harness sends no `levers` field for four arms, so after the flip they silently run the defaults.** `eval/src/lancet_eval/arms.py` (`request_fields`, "no other arm sends the field") and `client.py` (`if levers:`) omit the field for `dense-only`, `bm25-only`, `hybrid` and `hybrid+graph`, and proto3 `repeated` cannot tell "omitted" from "explicit empty". Any future drive against an engine running the committed config therefore measures those four arms with rerank and metadata on, and provenance clause (h) (`lever_echo_failures`, expected `[]` against the echo `[rerank, evidence_metadata]`) and clause (j) (rerank leak onto a non-rerank arm) will flag their records. The recorded runs are unaffected (they were driven before the flip). No wire opt-out exists, and adding one is a proto change that this plan did not make; the eval code was not changed (no test failed). Choices for a later plan: start the drive engine with `LANCET_ENGINE__LEVERS__DEFAULTS=` (empty), add an `[engine.levers] defaults = []` overlay for the eval environment, or add an explicit opt-out to the proto. The rehearsal and drive launchers refuse `LANCET_ENGINE__GRAPH__*` variables and should be made to refuse `LANCET_ENGINE__LEVERS__*` as well, so a drive cannot be moved by an override it did not pre-register.
2. **An engine over a store that holds no document metadata will not start with the committed config.** The startup check is strict on purpose (no carve-out for an empty store): `evidence_metadata` needs a non-empty `DocMetaMap`. Remedies: run `backfill_evidence_metadata` on the store, or start with `defaults = []` / `LANCET_ENGINE__LEVERS__DEFAULTS=` (needed, for example, to ingest into a fresh store; a fresh store cannot be backfilled before it exists). The in-repo `config_startup` fixtures that boot the real engine over an empty store now set the override, and one test proves the refusal and one the override. Scripts that boot the engine over a fresh or verify store with the committed config (`verify-ingestion.sh`, `verify-live-evidence.sh`, `scripts/oi02-replay.ps1` and similar) were not edited or run here and will need the override too; a store at `./data/lancedb` that was never backfilled is affected the same way.
3. **The measured system changed on purpose, so the freeze is spent.** The rehearsal provenance gate (`git diff --quiet 7d3da37a HEAD -- engine/ config/ ...`) will not pass again without a new freeze. That is D-157's design (the flip is outside the measured system), and no recorded run depends on it. Phase 6.4 documents the new defaults (D-157).
4. **The default is a statement about one corpus.** The held-out population is MultiHop-RAG (351 questions), one generation model from one provider and one seed; the null guard rests on 43 questions. Rerank's latency caveat (D-192) stays attached to the default.
