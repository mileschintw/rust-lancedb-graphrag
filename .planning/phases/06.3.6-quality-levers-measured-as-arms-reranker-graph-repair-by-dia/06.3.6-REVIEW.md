## Warnings

### WR-01: Fallible startup steps still run after the worker is spawned and staged jobs are replayed

**File:** `engine/src/main.rs:161-193, 195-208, 224, 228-230, 245-251`
**Issue:** Plan 23 removed the lever refusal, which was the cause cited in A-WR-01. The ordering hazard
behind that finding is still present. The ingest worker is spawned (161) and every staged job is sent
into its queue (186-192) before these steps, which can each still return `Err` and end the process:

- `from_effective_limits(...)?` (195-205)
- `OpenRouterGenerator::new_with_config(...)?` (206-208)
- `settings.engine.grpc_addr.parse()?` (224)
- the tokenizer warm-up join (228-230)
- the gRPC bind inside `Server::serve_with_shutdown(...).await?` (245-251). A port still held by the previous process is the commonest real-world failure here.

The worker begins embedding and LLM extraction as soon as it receives a job. A supervisor restart loop
re-spends OpenRouter calls on the same staged jobs each cycle. That is the cost A-WR-01 described. The
new ordering test only proves the lever check precedes the spawn, so nothing guards the rest.

**Fix:** Do the infallible-to-the-store setup before the worker spawn: parse `grpc_addr`, build
`generation_config` and `generator`, and run the tokenizer warm-up. Bind a `tokio::net::TcpListener`
first and serve with `serve_with_incoming_shutdown`. Keep the spawn and replay as the last fallible-free
block before serving. Extend `main_runs_the_default_lever_check_before_the_workers_and_the_replay` to
assert that `grpc_addr.parse` and the generator construction also precede `spawn_worker_with_concurrency(`.

### WR-02: Metadata coverage is reported once at boot, so drift after a rebuild is invisible and the echo still claims the lever

**File:** `engine/src/main.rs:80-92`, `engine/src/ingest.rs:1974-1991`
**Issue:** The coverage warning runs on the first snapshot only. The rebuild hook logs only an
empty <-> non-empty transition (`log_doc_meta_availability_change`). The documented reason is that a
partly covered store would warn on every rebuild.

The realistic sequence is a store that starts at 100% coverage and then receives ingests that omit the
optional `doc_title`, `source` and `published_date` fields. Each rebuild swaps in a snapshot with
partial coverage. Nothing logs, `evidence_metadata` stays available, the echo lists it, the prompt
carries the metadata policy sentence, and `attach_doc_meta` skips every block whose document has no
entry. This is the silent per-chunk no-op that A-WR-03 named. Restarting is the only way to see it.

**Fix:** Compute coverage on each swap and log it at INFO. Log at WARN only when the ratio falls
relative to the prior snapshot, so a steady partial store stays quiet:

```rust
let (before, after) = (prior.doc_meta_coverage(), new_snapshot.doc_meta_coverage());
if after.documents > 0 && after.with_metadata < after.documents
    && after.with_metadata * before.documents < before.with_metadata * after.documents
{
    tracing::warn!(/* documents, documents_with_metadata */ "evidence metadata coverage fell");
}
```

Optionally add the per-query `blocks_with_metadata / blocks` count that A-WR-03 suggested.

## Info

### IN-01: Rebuild-swap and coverage log text assert a configured default regardless of configuration

**File:** `engine/src/ingest.rs:1979-1983`, `engine/src/main.rs:83-92`
**Issue:** The swap WARN says "a configured default is dropped with a notice and a request naming it is
refused". That is untrue when `evidence_metadata` is not in `[engine.levers] defaults`, for example with
`defaults = []`. The startup coverage WARN also fires for lever-free engines. The helper has no access to
the configured defaults, so it cannot tell the cases apart.
**Fix:** Pass `settings.default_levers.contains(Lever::EvidenceMetadata)` into the helper and the coverage
block. Use the "dropped from requests that name no lever" wording only when it holds. Otherwise log
"evidence_metadata is unavailable" without the claim.

### IN-02: The startup warning's remedy text is not lever-specific

**File:** `engine/src/service.rs:239-250`
**Issue:** One format string serves every lever. A `rerank` or `graph_v2` warning says "for example
backfill the store, or for a legacy 19-column store run `backfill_evidence_metadata --migrate-only`",
which is irrelevant to those levers. The test only asserts the `evidence_metadata` rendering.
**Fix:** Move the remedy next to `lever_unavailable_reason` (a `lever_unavailable_remedy(lever)`). Keep
only the shared tail, `defaults = []` to start lever-free, in the common string.

### IN-03: The per-request notice exposes server-internal configuration names to every client

**File:** `engine/src/service.rs:198-206, 1392-1401`
**Issue:** `lever_unavailable_reason` text is reused verbatim in the client-visible notice. It includes
"graph_v2_chunk_precision is the no-op `all`", "no lever reranker is wired" and "the corpus snapshot
holds no document metadata". The gateway passes it through in the SSE terminal event. The text is useful
in the log. A client needs only the lever name and "not applied: resource unavailable". The same string
is also a stable machine-readable contract that is not tested for shape.
**Fix:** Keep the detailed reason for the startup log. Send the client a short fixed phrase, such as
`configured default lever {wire} was not applied: unavailable on this engine`.

### IN-04: `NOTICE_CODE_DEFAULT_LEVER_UNAVAILABLE` has no consumer in the eval package

**File:** `eval/src/lancet_eval/dimensions.py:17`
**Issue:** Only the wire-contract test imports the constant. `provenance.py` clause (i), `usability.py`
and `run.py` handle `RERANK_DEGRADED` (23) but nothing recognises code 24. A drive arm that omits
`levers` against a store that lost metadata therefore runs degraded, and nothing in the eval flags it.
That path is the lever-free control arm deferred by D-195 and is not re-reported. The unused constant is
the only new artefact.
**Fix:** Leave it as a pin, or consume it when the D-195 work lands (a provenance clause that treats a
code-24 notice on a control arm as off-arm).

### IN-05: A test pins a 400 for a default that the new semantics would drop

**File:** `engine/src/tests/levers_pins.rs:1658-1678`
**Issue:** `a_request_naming_no_lever_meets_the_combination_check_before_the_availability_filter`
configures `graph_v2` as a default and sets `chunk_precision = all`, so `graph_v2` is unavailable. It
asserts that `disable_graph_context = true` is refused with `invalid_lever_combination`. Under D-194 an
unavailable default is dropped, so this request would be valid without the pre-availability combination
check. It is refused for a lever it never named and cannot run. The ordering is documented, so this is
not a bug. The pin makes the 400 look intended, though, and the same pre-availability ordering applies to
an available `graph_v2` default with a graph-off request (the D-195 area).
**Fix:** Say in the test comment that this is deliberate and tied to D-195. The alternative is to move
the combination check after the default filter for requests that name no lever, and to flip the test
once D-195 is resolved.
