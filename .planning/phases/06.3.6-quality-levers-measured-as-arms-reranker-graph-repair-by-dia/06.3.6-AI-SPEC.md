## 1. System Classification

**System Type:** Hybrid. Inherited from `06.3.4.1-AI-SPEC.md` §1: a multi-hop RAG / GraphRAG system under test
(a Rust engine, LanceDB hybrid retrieval with RRF, an entity/edge graph, and OpenRouter generation) plus its
Python `lancet-eval` harness.

**Description (phase delta only):**

**What it builds.** 06.3.6 adds up to four standard quality levers to the shipped system, each off by default
and switchable per request through one `levers` list (D-136):
1. **A cross-encoder reranker over the fused top-32.** The order changes and the truncation to 8 is
   unchanged (D-131..D-135).
2. **A graph repair chosen by a pre-registered diagnosis rule** over the 38 dev `GRAPH_UNAVAILABLE`
   questions: entity resolution in side tables, or graph-list precision, or no arm (D-137..D-141).
3. **Evidence metadata in the prompt:** publication, real title and date (D-142..D-145).
4. **A conditional yes/no answer-format rule** with an evidence-decides stance (D-146..D-148).

**How it is measured.** Each lever is developed on the 100 dev questions only, within 2 paid reads (D-154). Its
parameters are frozen in one commit. It is then read once on the 06.3.5 held-out split in one interleaved drive,
against a same-day `hybrid` reference on one recorded index generation (D-149, D-155, D-159).

**What "good" means.** A run of record in which:
- every lever's `answer_usable` delta against the same-day reference is paired, Holm-corrected inside a
  pre-registered family, and read on a pre-registered population;
- every record's arm is proven on the wire (the `levers` echo);
- a lever becomes a default only on a Holm rejection with a positive delta that also passes its guards
  (D-150, D-148).

A lever that does not pay is a published result, not a failure (D-49).

**Critical Failure Modes:**
1. **The reference arm is not the reference.** Any of these makes every delta an artefact:
   - with `levers` empty, the prompt, the ranking or the snapshot bytes change;
   - the metadata backfill touches `nodes.title`, which feeds BM25 with `title_boost` 2.0 (verified-facts
     C2), or touches chunks, embeddings or the graph;
   - arms run on different index generations, or the engine is not restarted after the backfill
     (verified-facts D).
2. **Rerank provenance is mixed.** Any of these mislabels or drops records:
   - a reranker error or timeout silently yields the fused order inside the rerank arm, instead of the
     off-arm `RERANK_DEGRADED` (D-134);
   - the rerank call overruns the `RetrieveHybrid` node budget and fails the whole query (`retrieve_timeout_ms`
     2500, verified-facts A5);
   - the D-100 ranking still reads pre-rerank, so Hits@4 on the rerank arm equals `hybrid`'s by construction
     (D-133).
3. **The answer-format lever wins by saying Yes.** On binary gold, a Yes-biased arm can raise `answer_usable`
   while degrading null abstention. The guards (D-148) must be committed before the drive and read
   mechanically.
4. **Forking paths.** Any of these after held-out data is seen invalidates the run:
   - lever parameters, the lever-2 selection rule, the Holm families, the decisional population, margins or
     floors are chosen or changed (D-73, D-129, D-137, D-150, D-160);
   - held-out data motivates a dev revision;
   - a dev read exceeds the 2-read budget (D-154).
5. **The population erodes the decisional test.** With seven arms, an all-arms-ok population lets failures
   on descriptive arms, or off-arm `RERANK_DEGRADED` records, remove questions from every lever's test. D-160
   pre-registers the population and a coverage floor.

  paired result with d discordant questions split evenly, a one-sided 95% Clopper-Pearson upper bound still allows a
  net loss of about 3.2 questions (7.5 points) at d = 4, 4.9 (11.4 points) at d = 8, 6.1 (14.2 points) at d = 12 and
  7.1 (16.5 points) at d = 16. An approximation, conditional on d. So at this n the guard can detect a large drop but
  cannot show "no harm" for a margin under roughly 10 points. The margin itself is for the eval-planner and the
  owner (D-148). It must come from dev or earlier rules, never from the 0.64 / 0.45 quote (D-129).

### Known Failure Modes in This Domain

1. **The rerank "wins" a retrieval metric, not the question.**
   - Any-hit Hits@4 cannot see the second article being demoted (`metrics.py:331-358`).
   - A cross-encoder scores each question-and-chunk pair on its own, so the chunk that matters only after hop 1 can
     rank low. This is the standard mechanism, but a quantified failure on multi-hop QA was **not found** in a source
     opened for this spec.
   - The prompt packer re-sorts blocks 2 to 8 by `fused_score` (`engine/src/prompt.rs:469`, verified-facts I), so a
     reorder-only reranker mostly changes **which 8** survive, not their order in the prompt.
   - A rerank call that outlives `retrieve_timeout_ms` (2500) fails the query as a node timeout, not as a degrade
     (verified-facts A5). A rerank arm can then lose questions for reasons unrelated to relevance.
2. **Graph-repair failures differ by branch, and the table must not pre-judge which applies.**
   - **Under-merge (alias split):** one real entity has two nodes, so a path between two gold entities does not
     exist. DEG-RAG's abstract describes LLM-built graphs with "redundant entities", and common pipelines that
     de-duplicate with "rudimentary string-matching heuristics".
   - **Over-merge:** two real entities collapse into one node and the path is a false one. The model then reasons from
     a wrong link. No peer figure on false-merge rates was **found**, so the owner's audit sample is the only
     evidence.
   - **Degree growth:** a merged node's degree is the sum of its members', so more intermediates exceed
     `DEGREE_CAP = 33` and drop out (AI-SPEC §3 Pitfall 10).
   - **Neither:** if the gold entities were never extracted, no resolver helps. D-141 records that as the result.
   - **No ER-on/off figure on MultiHop-RAG was found.** DEG-RAG's abstract reports improved QA "across several
     popular Graph-based RAG variants" without numbers on this page.
3. **Metadata acts on the null slice, and on dates, in ways the lever name hides.**
   - Null queries are built from entities absent from the corpus plus "fictional news source metadata". Showing the
     source can help the model see that no evidence block comes from the named publication. It can also hurt if the
     model trusts a similar-looking source.
   - MultiHop-RAG temporal answers are about "the temporal ordering of events", while the corpus date is the
     **publication** date (all 346 subset documents are dated 2023-09-26 to 2023-12-25, per the `check_metadata_join.py` output recorded in §3 Entry Point Pattern; not re-run here).
     An article can be published after the event it reports.
   - **No study that isolates publication metadata in the prompt was found.** The rubric row is therefore practitioner
     reasoning, and the dev reads are the evidence.
4. **A format rule that wins by changing the answer mix, or by the scorer.**
   - Direction is contested. Braun (2025) finds LLMs lean to "no". A Cognitive Science Society paper surfaced in
     search (not opened) calls the evidence inconclusive. Guarding only the Yes share misses a lever that converts
     abstentions into "No" (D-147 pushes that way on purpose).
   - Comparison gold is "typically" Yes/No, but temporal gold may be "before", "after" or an indicator word
     (Tang & Yang §3.1). A strict Yes/No rule can break those.
   - RAGU §3.3 shows how a verbose-versus-terse answer protocol moved a published comparison: "largely a format
     artifact". It reports results under **both** protocols. That is the practice to copy: check the answer-line
     parser sees the same thing on every arm.
   - 43 null questions is coarse (see the arithmetic above). Dev has 10 null questions in the seed probe
     (verified-facts F), so dev cannot tune this guard.

## 2. Framework Decision

**Selected Framework:** **Locked existing stack, no new framework.** Inherited unchanged from
`06.3.4.1-AI-SPEC.md` §2 and `06.3.5-AI-SPEC.md` §2: a Rust engine, a Go gateway and `lancet-eval`, with
`uv`-managed Python at `eval/`. The framework selector was not run for this phase (D-128: "the framework stays
locked").

**Version:** As shipped (see `06.3.4.1-AI-SPEC.md` §2).

**New model dependency (not a framework):**
- **What:** `voyageai/rerank-2.5-lite` (canonical slug `voyageai/rerank-2.5-lite-20260727`), served through
  OpenRouter `POST https://openrouter.ai/api/v1/rerank`.
- **Auth:** the same bearer key as generation.
- **Limits:** `context_length` 32000.
- **Called how:** directly over HTTP from the engine, like the existing OpenRouter generator and embedder. No
  SDK.
- **Verification status:** D-131's verification is **partial**. See verified-facts A7. An authenticated 200 and
  the billed price are an open gate that the plan closes before any lever-1 code.

**Rationale:**
- Every lever is a small change inside the existing seams: the `Reranker` port, the `EntityResolver` port,
  `prompt.rs` evidence rendering and policy, the store schema, and the harness registry and pre-registration.
- 06-CONTEXT D-48..D-50/D-54 still apply: no AI framework, no new dependencies beyond what a lever strictly
  needs, no LLM in the metrics layer, and a fail-closed report.
- The reranker is one HTTP call with a small JSON shape (verified-facts A7). An SDK would add a dependency for
  nothing.

**Alternatives Considered:**

| Option | Ruled Out Because |
|-----------|------------------|

### Common Pitfalls

1. **prost drops unknown lever integers.** A `repeated enum` is `Vec<i32>` in the generated request, and the
   generated `levers()` accessor yields only the known values (R9; verify in the regenerated
   `engine/src/pb/lancet/v1/lancet.v1.rs`). Reading the accessor turns `levers: [99]` into an empty list, which
   is a lever-free request, which is the reference arm. Admission must read the raw vector and refuse
   unknown values, `0` (`LEVER_UNSPECIFIED`) as a member, and duplicates.
2. **The prompt packer undoes most of a rerank.** `pack_evidence_and_graph_prompt` keeps block 1 first, then
   sorts the remaining blocks by `block.score` descending (`prompt.rs:443-475`), and `block.score` is
   `fused_score` (`prompt.rs:68`). A reranker that reorders the list but leaves `fused_score` alone changes
   *which* 8 chunks survive `take(8)` and which is first. Blocks 2 to 8 then come back in fused order, with the
   `[n]` ids out of sequence. Under `NoOp` the list is already in score order, so this has never been visible.
   The fix is in §4 item 2. It changes what `StructuredCitation.score` means on the rerank arm, which must be
   disclosed. The D-100 ranking carries no score, so the harness is unaffected.
3. **The generator packs the prompt a second time.** `GenerationRequest::system_policy` ("You are a precise
   technical RAG engine.", `generation/mod.rs:555`) is never read by `execute_one_call`. The real policy is in
   the user message built by `pack_openrouter_messages` (`openrouter.rs:269-299`, called at `:534`). A policy
   sentence added only to `AssemblePromptNode` changes a string nobody sends. `GenerationRequest` is built at
   `nodes/generate.rs:165-166` and `workflow/mod.rs:411-414`. Its `PartialEq` destructures every field
   (`generation/mod.rs:528-549`), so a new field forces that edit.
4. **`rerank()` consumes the list.** `rerank(Vec<FusedCandidate>)` (`rerank/mod.rs:12-15`, `retrieve.rs:379`)
   moves the only copy. On an error D-134's "keep the fused order" has nothing to keep, unless the node cloned
   first or the port returns a permutation instead of owning the list.
5. **Degrade only when the lever is on.** Today a failing reranker on a default request must give
   `RetrievalFailed` (`tests.rs:4164`; `tests/workflow_phase5.rs:1063,1784,7305`), and an injected
   `RecordingReranker` must have its rotation applied (`tests.rs:4041,4070`). Those tests describe the
   lever-free path. Keep that branch as it is, and degrade only under the rerank lever.
6. **Startup schema validation is fail-closed, and ingest is positional.** Appending columns to
   `nodes_schema()` makes every store that lacks them refuse to start (`db/mod.rs:188-201`), including
   `data/lancedb` and test stores. Do not copy the `staged_documents_v2` auto-upgrade branch
   (`db/mod.rs:83-97`) for `nodes`: on the eval store it would pre-empt the backfill (item 4f). Ingest builds the `nodes` batch as a positional vec against the live schema
   (`ingest.rs:685-748`), so a 22-column schema with a 19-element vec fails `RecordBatch::try_new` on the first
   ingest.
7. **`nodes.title` is the sanitized filename and feeds BM25.** Ingest writes `title = job.filename`
   (`ingest.rs:731-734`). BM25 indexes it with `title_boost = 2.0` (`bm25.rs:134`, `config.toml:100`), the dense
   projection reads it (`dense.rs:33,227`), and `<TITLE>` and `StructuredCitation.title` show it
   (`prompt.rs:44-50`, `retrieve.rs:425-428`). The real title goes in a new column. An `update` of `title`
   changes BM25 on every arm, the reference included.
8. **Ingest metadata is not durable.** `persist_raw_with_boundary` writes a staged row from the filename, the
   bytes and the chunk settings only (`ingest.rs:432-465`), and the restart reload rebuilds `metadata` from
   three keys (`ingest.rs:373-377`). A document admitted with metadata and recovered from staging after a crash
   is ingested without it. Also `GRPCEngine.Ingest(ctx, id, filename, strategy, chunkSize, chunkOverlap, src)`
   (`engineclient.go:74`) has no metadata parameter, and `parse_chunk_settings` ignores extra keys
   (`ingest.rs:80-121`), so a typo in a key name is silently dropped.
9. **Side tables must be optional.** `table_schemas()` is a fixed `[_; 7]` that every store must satisfy
   (`db/mod.rs:323-333`). Adding `entities_v2` to it makes every store without it fail `open_and_validate`.
   Graph reads hard-code the v1 accessors in three places: `GraphIndex::build` (`graph/index.rs:137-192`), the
   name-vector search (`graph/seeding.rs:205`) and `scan_seed_edges` (`graph/paths.rs:507`). A per-request
   table choice touches all three, plus a second `GraphIndex` in the snapshot.
10. **Merging inflates degree against a fixed cap.** `DEGREE_CAP = 33` is the p99 of the v1 degree
    distribution (`paths.rs:34-51`). After an alias merge an entity's degree is the sum of its members', more
    intermediates exceed 33, and `degree_capped_count` rises (wire-visible, `workflow/mod.rs:129`). Do not
    re-tune the cap for v2, which would add a second tunable. Report the count per arm.
11. **"The edge-evidence chunk" is not stored.** `entity_edges` has no chunk column (`db/mod.rs:272-283`, written
    at `ingest.rs:1348-1390`), although the chunk is known in memory when the edge is built
    (`ingest.rs:1208-1224`). D-139's read 1 can only be approximated from the index. Re-extraction is barred
    (D-138, D-144).
12. **The D-73 gate false-passes** on the 06.3.5 token (R6), and **`compare` cannot run** on a 06.3.6 run (R7).
    Both are silent until the run of record: the gate passes, and `compare` refuses only after the paid drive.
13. **`is_graph_arm` misreads the new arms** (R8). The graph-yield dimensions (`dimensions.py:597,687`) would
    treat `hybrid+graph-v2` and `hybrid+all` as graph-off and drop them from the graph-on population.
14. **A new wire field has five hops and two of them swallow it silently.** (1) proto and prost; (2) the gateway's
    hand-written map (`sse.go:117-155`, two branches) or DTO (`dto.go:56-73`, `:159-193`); (3) `client.py`
    models, which are `extra="ignore"` and drop what they do not model; (4) `journal.py` `WorkflowWireMeta`,
    which is `extra="forbid"` and needs a default so old journals parse; (5) the copy sites `run.py:271-276`,
    `measure.py:387-392` and `scripts/drive_measurement_pass.py:292`. The default snapshot keeps exactly 10 keys
    through `omitzero` (`dto.go:67-72`, pinned at `sse_test.go:874-920`). A new metadata key written
    unconditionally would change the default bytes. Emit it only when non-zero.
15. **The rerank response echoes the documents.** `results[].document` is required by the schema and holds the
    text. 32 chunks of a few KB each can pass the 256 KiB default of `read_body_limited`
    (`client/mod.rs:16,39`), and a `TooLarge` there would degrade the arm for no provider fault. Use
    `read_body_limited_with_limit` with a larger cap, and deserialise only `index`, `relevance_score` and
    `usage`. `usage` and `usage.cost` are optional in the schema.
16. **The rerank must fit inside a node budget it does not own.** `retrieve_timeout_ms` is enforced by the runner
    around the whole node (`runner.rs:380-390`). A rerank that outlives it fails the query with a node timeout,
    which is a failure, not D-134's degrade. Hand the node its budget and clamp the rerank call to what is
    left.

```rust
// (PROPOSED, illustrative, not compiled)  request / reply shapes. `document` in a result is ignored on purpose.
```

Rules, each with a test row (the harness-side twin of the permutation check is **executed**, §4b.1):
- An empty candidate list returns `Ok` with no call (`documents` has `minItems: 1`; an empty list is a 400).
- Status mapping: 401, 402 (insufficient credits), 429, 5xx and a transport error are `RerankError` classes. The
  message carries the class and status, never the response body (it can echo document text) and never the key.
- Read the body with `read_body_limited_with_limit` at a documented cap (M-DOCUMENTED-MAGIC), not the 256 KiB
  default (Pitfall 15).
- Require `results.len() == n`, indices a permutation of `0..n`, scores finite, and the response `model` to start
  with the requested slug (the reply may carry the dated canonical slug). Anything else is
  `MalformedResponse`, which degrades. Do not repair a bad reply by guessing.
- Sort by `(relevance_score` descending, `index` ascending`)` ourselves, so ties do not depend on the unspecified
  order of `results`.
- `usage.cost` is optional. Carry `None`, and let the harness count "cost not reported". Never substitute a
  constant (the listing shows 0/0 for rerank, and the Voyage-direct price is not verified through OpenRouter).
- No retry: a retry cannot fit the budget below.

**6. D-152: one bounded query-embedding retry, every arm.**

```rust
// workflow/nodes/graph_context.rs, replacing :78-99   (PROPOSED, illustrative, not compiled)
/// One try plus one retry (D-152). The per-attempt budget stays query_embedding_timeout_ms.
const QUERY_EMBEDDING_ATTEMPTS: u32 = 2;
/// Upper bound of the pause before the retry. Small against the 2000 ms attempt; it only spreads concurrent retries.
const RETRY_JITTER_MAX_MS: u64 = 250;
for attempt in 1..=QUERY_EMBEDDING_ATTEMPTS {
    let res = tokio::select! { biased;
        _ = cancel.cancelled() => return Err(NodeError::cancelled()),
        r = timeout(self.embedding_timeout, embedder.embed_variant_zero(variant_zero, cancel)) => match r {
            Ok(inner) => inner,
            Err(_) => Err(NodeError::new(NodeErrorKind::Timeout, "Query embedding timed out")),
        },
    };
    match res {
        Ok(v) => { ctx.query_embedding = Some(v); break; }
        Err(e) if e.kind == NodeErrorKind::Timeout && attempt < QUERY_EMBEDDING_ATTEMPTS => {
            ctx.query_embedding_retries += 1;
            let jitter = jitter_ms(&ctx.trace_id, attempt, RETRY_JITTER_MAX_MS);   // blake3 over the trace id: no `rand`
            tracing::warn!(attempt, jitter_ms = jitter, "query_embedding_retry");   // the event; no query text (M-LOG-STRUCTURED)
            tokio::select! { biased; _ = cancel.cancelled() => return Err(NodeError::cancelled()),
                             _ = tokio::time::sleep(Duration::from_millis(jitter)) => {} }
        }
        Err(e) => return Err(e),                      // second timeout, or any non-timeout error: as today
    }
}
```
- **Retry on `Timeout` only** (Pitfall 17). A permanent provider error returns at once, as now.
- **Nesting.** Worst case `2 x 2000 + jitter + 2424 + 500 = 6924 + jitter`: 7174 ms with 250 ms jitter, inside
  `graph_node_timeout_ms = 12500` with 5326 ms spare (**executed**; the one-attempt value 4924 reproduces
  `config.rs:299-302`). `WorkflowSettings::validate` (`config.rs:498-506`) checks only `graph_node >= q_emb +
  g_op`; extend it and `latency.check_nesting_invariants` (`:466-501`) to `attempts x q_emb + jitter + g_op`, and
  the slack assertion in the test at `config.rs:1156-1162`.
- **Wire.** The count is a per-record `WorkflowMetadata.query_embedding_retries` (PROPOSED tag 18, `uint32`,
  zero omitted), through the four hops. The event is the `tracing` line. No notice is added, so a retried-then-
  successful record is not "degraded".
- **Byte-identity.** A fake embedder that succeeds first time takes one attempt, no sleep, `retries = 0`, no
  new bytes. Tests with `tokio::time::pause()`: times out once then succeeds (`retries = 1`), times out twice (a
  node `Timeout`, as today), a non-timeout error (no retry), a cancel during the pause.
- It applies to every arm including the reference. Change the engine **before** the dev reads and before the
  freeze commit; D-152 notes this is not a change after a held-out read.

### Structured Outputs with Pydantic

**This phase adds no LLM output schema.** The generation schema is unchanged: `answer`, `cited_evidence_ids`,
`answer_basis` and `final_answer` (`generation/openrouter.rs`, schema built in `execute_one_call`), checked by the
engine's grounding validator, with the existing single citation-repair pass and the generator's one retry on a
timeout or provider error (`workflow/mod.rs:422-431`). There is no `instructor` and no new dependency. The
judge, which has a Pydantic schema (`JudgeVerdict`), does not run (D-153).

Two things are new and structured: the **provider JSON** of the rerank call, and the **arm registry row** that
says what a request must carry and what the snapshot must echo. The engine reads the first with `serde` (the
Rust twin of Pydantic here); the harness side below is the same logic, in Pydantic v2, and is what ran. House
style: registry and gate models are `extra="forbid"` and `frozen=True`; wire mirrors are `extra="ignore"`
(`client.py:71-74`); a journal mirror is `extra="forbid"` and needs a default for every new field
(`journal.py:51-54`).

```python
# CONDENSED from research/spec_snippets_06_3_6.py (sections 1 and 2): comments trimmed, docstrings dropped,

            raise ValueError(f"duplicate lever in {self.levers!r}")

            raise ValueError(f"levers must be in canonical order {LEVER_ORDER!r}")
        if "graph_v2" in self.levers and self.disable_graph_context:
            raise ValueError("graph_v2 with the graph switched off would be a silent no-op")

def request_levers(spec: ArmSpec) -> list[str] | None:      # None => the `levers` key is not sent
    return list(spec.levers) if spec.levers else None

def lever_echo_failure(spec: ArmSpec, echoed: list[str]) -> str | None:   # provenance clause (h)
    if echoed != list(spec.levers):
        return f"arm {spec.label!r}: expected levers {list(spec.levers)!r}, echoed {echoed!r}"
    return None

class RerankItem(BaseModel):                 # the 200 body; only what the engine needs (`document` is ignored)
    model_config = ConfigDict(extra="ignore")
    index: Annotated[int, Field(ge=0)]
    relevance_score: float

class RerankUsage(BaseModel):                # `cost` is optional in the OpenAPI schema
    model_config = ConfigDict(extra="ignore")
    cost: float | None = None
    total_tokens: int | None = None
    search_units: int | None = None

class RerankResponse(BaseModel):
    model_config = ConfigDict(extra="ignore")
    model: str
    results: list[RerankItem]
    usage: RerankUsage | None = None

    def order_for(self, n_documents: int, requested_model: str) -> list[int]:
        indices = [item.index for item in self.results]
        if sorted(indices) != list(range(n_documents)):          # fail closed: a full permutation or nothing
            raise ValueError(f"results are not a permutation of 0..{n_documents - 1}: {indices!r}")
        if not self.model.startswith(requested_model.split("-20")[0]):
            raise ValueError(f"response model {self.model!r} != requested {requested_model!r}")
        if any(not math.isfinite(item.relevance_score) for item in self.results):
            raise ValueError("non-finite relevance_score")
        ranked = sorted(self.results, key=lambda item: (-item.relevance_score, item.index))   # our own tie-break
```

### Async-First Design

**Engine (tokio).** The rerank and the embedding retry are both awaits inside nodes that the runner already
wraps in `tokio::select! { biased; cancel, timeout }` (`runner.rs:382-391`). Phase-specific rules:
- **The one common mistake: a detached call.** Do not `tokio::spawn` the rerank request, and do not hand it to
  `spawn_blocking`. `tokio::time::timeout` drops the inner future when it elapses, and dropping a `reqwest` future
  cancels the request. A spawned task would keep running and billing after the record was marked degraded.
- **No blocking sleep.** Use `tokio::time::sleep` inside a `select!` with `cancel.cancelled()` for the retry
  pause. `std::thread::sleep` stalls a runtime worker, and an unselected sleep ignores a client disconnect.
- **Borrow across the await.** `RerankRequest<'a>` borrows `&fused_candidates` while the call is in flight, so
  the list is intact on every error path (§4 item 2). The future must be `Send`: `FusedCandidate` is.
- **Keep futures small** (M-ASYNC-STACK-SIZE). `execute_inner` is already long (`retrieve.rs:145-506`) and
  everything live across an `.await` sits in its future. Put the rerank branch in a helper that returns a small
  enum, and never hold the `substage_report` mutex across an await (`:154-157`, `:488-491` lock briefly).
- **Time is testable.** `tokio` is built with `test-util` (`engine/Cargo.toml:7`), so `tokio::time::pause()` drives the
  timeout, the clamp and the jitter pause with no real waiting. The pattern is `FakeReranker::stall`
  (`workflow/ports.rs:673-681`).
- **Stream versus await.** Nothing in the rerank streams (the endpoint has no streaming). The reply is awaited
  and validated whole before any of it is used. The answer path is unchanged: the SSE stream is drained to
  `workflow_completed` before the harness journals the record.

**Harness.** It stays synchronous (`httpx` plus `connect_sse`); this phase adds no asyncio. Two rules:
- Run the drive at `--workers 1` (D-155) and, **inferred, not stated by a decision**, the dev reads that feed
  the D-135 derivation too. The rerank latency percentile depends on contention, and a derivation made under
  parallel workers would not describe the drive.
- Do not overlap stages. The comparison reads a closed journal; the store writes of item 4g finish, and the
  engine restarts, before the first dev read that uses them.

The Go gateway needs no new concurrency. If a helper fans out, Go 1.25 gives `sync.WaitGroup.Go`
(`go-guidelines.md`, 1.25+), but the lever parser and the metadata validation are plain functions.

### Prompt Engineering Discipline

- **The real system/user split.** The system message is one fixed line, "You are a precise technical RAG
  engine." (`openrouter.rs:296`). The policy, the question and every evidence block are in the **user** message
  (`prompt.rs:380-389`; the template at `:91`). Corpus text, the new metadata headers included, is untrusted
  data inside `<EVIDENCE>` blocks, entity-escaped by the one seam (`encode_evidence_block`). Treat a title, a
  publication name and a date exactly like body text: a `source` of `</EVIDENCE>` must come out as
  `&lt;/EVIDENCE&gt;`. Test it, and test that `suspicious` flips.
- **Append, never edit.** The base policy is pinned by one assertion per sentence and by byte-identical-prefix
  tests (`prompt.rs:704-830`, written at 06.3.4.1-08 and 06.3.4.1-29 on the rule "No existing sentence … may be
  reworded, reordered or removed"). The lever sentences are new constants appended after it. Follow the same
  discipline for them: a verbatim assertion per sentence, and a property that the flag-on policy starts with
  the flag-off policy.
- **One fixed order and one place.** Base, graph sentence, metadata sentence, format rules; inside
  `pack_evidence_and_graph_prompt_with` only (item 4d). Never in `AssemblePromptNode` alone, never in
  `GenerationRequest::system_policy` (vestigial, Pitfall 3).
- **No few-shot.** Do not add dev or held-out questions as examples. They would leak into the measured system
  (D-129). A lever's wording is chosen from at most two paid dev reads (D-154), so there is no search over
  phrasings; every offline variant looked at is disclosed.
- **Do not name the benchmark.** No question types, strata, "comparison", "temporal" or gold-answer vocabulary in
  a sentence (D-146). A production client has no such label.
- **Explicit bounds, never open.** Generation keeps `max_output_tokens = 2048` (`config.toml:138`) and
  `temperature = 0.0`. The rerank has no token parameter, so bound it by what it can be given: at most
  `candidate_limit` = 32 documents, `top_n = n`, a documented response-body cap, and `rerank_timeout_ms`.
- **Versioning.** There is no judge prompt version to bump. The prompt text is code, frozen in the D-154 commit,
  and the report records the commit (`report.json` metadata `commit_sha`). A change after a held-out read is a
  forking path.
- **A guard against the lever's own failure mode.** The evidence-decides sentence can raise Yes-share and cost
  null abstention. That is why D-148's two guards exist; no sentence is allowed to be tuned until it
  "wins" on dev if that tuning moves the guard numbers the wrong way without being disclosed.

### Context Window Management

This is RAG with a fixed window, and the reranker is the phase's answer to "what do we keep when the context is
too small": 32 fused candidates compete for 8 slots (`final_limit`), inside an 8,192-token evidence budget that
already reserves 2,048 tokens for the answer.
- **Where truncation happens, in order:** fusion makes at most 32 (`candidate_limit`); the reranker reorders them;
  `take(8)` cuts (`retrieve.rs:392-395`); the packer then drops, whole-block, any block that does not fit the
  token budget after always keeping block 1 (`prompt.rs:404-420`, `:497-499`). The rerank changes the **set** that
  survives the cut and the first block. It changes the rest of the prompt order only if `fused_score` is
  overwritten (Pitfall 2).
- **Do not "fix" a budget squeeze by moving a shared setting.** If maximal metadata headers evict a typical
  chunk, the answer is to report it (`evidence_block_count` per arm, `prompt_tokens` per arm), not to raise
  `evidence_token_budget` or lower the answer reserve. Both are shared by every arm and would change the
  reference (D-132 keeps `[engine.retrieval]` unchanged).
- **Graph facts compete for the same budget.** They interleave with evidence by normalised score
  (`prompt.rs:443-475`). With rerank scores written into `fused_score` the normalisation is per source, so the
  interleave moves under the lever. That is part of `hybrid+all` and is a reason to read it as descriptive only.
- **The graph chunk list is already bounded** (`max_graph_chunk_candidates = 8`, `config.toml:125`); the precision
  variants only shrink it.
- **The rerank input is the whole fused list, untruncated.** Chunks are at most the ingest chunk size. If the
  provider refuses a pair as too long, the record degrades; the engine does not truncate a document to make it
  fit, because the reranker would then score text the generator never sees.
- **Conversation and agent patterns do not apply.** The engine is stateless per request; there is nothing to
  summarise or compact.

### D-148 guards: the decision procedure

**Guard 1, null abstention (decisional for the O4 arms).**

- **Procedure.** It is a count rule on the observed paired drop. That is D-148's own wording ("drops by more than a
  margin"), and the only procedure that works at this n:

  ```text

  b    = |{q in N_X : is_abstention(hybrid_q) and not is_abstention(X_q)}|
  ```

### D-151: the SC-2 error-mode materiality floor (owner-approved 2026-10-09 as D-164; O6)

**The rule.** The 06.3.4.1 clause, `timeout` not the plurality-or-tied class (`unpark_gates.py:436-445`; dominance rule
`plurality_tie_is_dominant`), now fails only when timeouts are also **material** in that reading:

```text
error-mode clause FAILS  iff  timeout is dominant  and  Fraction(timeouts, n_records_in_reading) >= Fraction(1, 40)
below the floor          ->   "reported: timeout dominant, not material (k of n)"; the clause does not fail
```

- It is applied per arm and to the pooled line, each with its own n. The flatness clause is unchanged (SC-2 = error
  mode AND flatness).
- **Derivation, the D-89 way** (committed constants only; `d151_sc2_floor.py` section 1 fixes it before any gate file
  is read):
  - **The tail.** A node whose latency still matches the distribution its budget came from exceeds its derivation p95
    on at most 1 − `derivation_percentile` = 5% of records (`thresholds.py:95`). It times out on fewer still, because the
    budget is p95 × 1.5 (`:94`). A 5% timeout rate means the budget protects no better than the bare p95: the headroom
    is gone.
  - **The half.** D-89 calls decay material "once it would use half of that headroom". Its committed encoding is
    0.25 / (1.5 − 1) = ½ (`thresholds.py:217`).
  - **So** the floor is ½ × 5% = **2.5%**.
- **Thresholds it implies** [executed]: material at ≥ 3 timeouts of 100, ≥ 5 of 200, ≥ 9 of 351 per arm, ≥ 62 of 2,457
  pooled.
- **The pooled line is lenient by construction.** The per-arm readings are the binding ones (D-109: "a failing arm
  cannot hide").

**D-135 derivation (rerank timeout).** The procedure of §4 item 2, settled here:
1. **Sample.** Dev read 1 of `hybrid+rerank` runs at the provisional 1706 ms, at `--workers 1` (§4b). The latency sample
   is `workflow_meta.rerank.latency_ms` over records that attempted a rerank (n ≈ 100).
   - A degrade by **timeout** is a censored observation at its allowed time.
   - A degrade by **status, malformed or transport** is not a latency observation. It is excluded and counted.
2. **Identification (refines §4 item 2).** Let k be the number of censored observations and n the sample size.
   - If k ≤ n − ⌈0.95 n⌉ (≤ 5 of 100), **and** every censoring time is at or above the 95th order statistic, then that
     order statistic is an uncensored value. The p95 is **exact**, and its CI's upper end is unbounded.
   - The record says `censored_above_p95_rank(k)`.
   - Otherwise the p95 is a lower bound (the 06.3.3 convention, `06.3.3-BUDGETS.md:34`).
3. **Rule.** T = ⌈1.5 × p95⌉ (`derive_budget`, `latency.py:352`, `COMMITTED_THRESHOLDS`). It nests iff
   T + 294 + 500 ≤ `retrieve_timeout_ms` (2500), that is p95 ≤ 1137 ms (§4, executed).
4. **Lower bound only.**
   - If ⌈1.5 × lower bound⌉ already does not nest, "does not fit" is decided.
   - Otherwise read 1 cannot decide. **Read 2 is then the rerank lever's second and last dev read.** It runs with the
     rerank timeout and `retrieve_timeout_ms` raised through the env override (`config.rs:899-916`), on dev only, with
     both values in that read's ledger entry.
   - Because rerank has no other tunable (D-132), this read consumes its whole revision budget.
   - If read 2 is still a lower bound, the owner decides at the freeze. There is no third read.
5. **Does not fit (O11).** The owner decides before the freeze:
   - **(A), recommended:** `retrieve_timeout_ms` = ⌈294 + T + 500⌉ for **every** arm. It moves `config.toml:72`,
     `config.example.toml`, the `config.rs` default and the pin at `config.rs:1131-1144`, in the freeze commit.
   - **(B):** clamp at 1706 ms, with the predicted degrade rate disclosed.
   - **(C):** drop the rerank arm. m becomes 3 or 2, and the Hits@4 family shrinks. This is decided before the freeze.
