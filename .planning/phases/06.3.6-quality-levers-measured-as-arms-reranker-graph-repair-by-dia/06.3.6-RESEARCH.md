## Summary

The AI-SPEC is consistent with the code at HEAD on almost every line it cites; the drift found is small (a table below). Three findings change plan content and are not in the AI-SPEC:

1. **The proposed backfill mechanism does not run.** Lance's SQL planner has no `CASE`. `Table::add_columns(NewColumnTransform::SqlExpressions(... CASE document_id WHEN ...))` is rejected (`lance-datafusion-8.0.0/src/planner.rs:838`). `NewColumnTransform::Reader` (an `arrow` `RecordBatchReader` that yields the three new columns in scan order) works, and it was executed on a throwaway 5-fragment table with deletion vectors: one new version, all 19 old column digests equal, old data files byte-identical, five new column files, the strict 22-column schema equality the engine's `validate_schema` makes holds. [EXECUTED: `research/lance_add_columns_probe.out`]
2. **The `nodes_schema()` commit makes every tool that opens the eval store fail closed until the backfill runs**, not only the engine: `inspect_lancedb`, `diag_probe` and `reconcile_eval_store` use `open_and_validate`, and `lancet-eval run`, preflight and D-61 coverage shell out to `inspect_lancedb`. So the D-137 store read must happen before that commit, and the backfill bin needs its own opener.
3. **The harness has no `dev` split role, and the D-73 gate applies to any `[split]` corpus.** AI-SPEC §5 assumes a dev corpus "with its `[split]` guard"; `_SPLIT_ROLES = frozenset({"heldout", "rehearsal"})`. A dev `[split]` corpus on the 06.3.6 token would be refused before the freeze commit exists.

**Primary recommendation:** plan 18 units in 14 waves (map below). Wave 1 holds the D-131 probe, the D-137 chain and the offline hardening; the wire commit waits for both gates; the engine plans run one at a time because they share `service.rs`, `workflow/mod.rs`, `ports.rs`, `config.rs` and both test-count scripts; every live stage that exceeds one executor (dev sessions, rehearsal, drive) is expressed as prep task, `checkpoint:human-action` (orchestrator launches WMI-detached under a sleep hold), record task.

## Long-Running Live Work Shapes

**What an agent can and cannot do on this host.** A `gsd-executor` has Read, Write, Edit, Bash, Grep, Glob and Skill, no Monitor, and a 10-minute foreground Bash cap. A process started from an agent's shell sits in that agent's Windows job object and dies when the agent exits (`06.3.5-WORKFLOW-MEMO.md` rows 10-11). Any agent CAN start a detached process (`Invoke-CimMethod Win32_Process Create`), but no executor can wait for one. So: an executor prepares and may launch; the **orchestrator owns the wait**.
