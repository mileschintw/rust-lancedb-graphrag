# Purpose

This ADR records locked dispositions for the remaining Phase 03 blockers called out by the 2026-08-05 verification and code-review reports, plus one explicit MVP override. The system is a Go gateway plus Rust engine RAG path over LanceDB-backed staging/retrieval. Decisions optimize for fail-closed correctness, process and data integrity, and Lance-native durability semantics, under MVP pressure that allows limited ops-hygiene debt when it does not falsify durable state or HTTP success semantics.

Decision criteria: (1) preserve or restore phase contract truths required to exit Phase 03, (2) prefer single authority objects and pre-allocation bounds over post-hoc checks, (3) align ingestion mutation with Lance immutability, (4) defer only with tracking and escalation triggers.

# Findings to Ship

## G1: Single GroundingLimits carrier

**Decision:** Ship.

**Problem:**
`EffectiveRagSettings` validates scalar budgets but does not store one `GroundingLimits` value. Query code and startup `OpenRouterGenerationConfig` each reconstruct carriers. `GroundingLimits` fields are public; `with_grounding_limits` can inject values without re-validating service ceilings. Plan 03-16 / verification require one carrier governing packing, max output, derived total usage, shared grounding validation, and OpenRouter usage validation.

**Rationale:**
Two reconstructions drift when fields or total formulas change. Public fields defeat constructor invariants. Phase exit cannot claim G1 while authority is only “logical.”

**Alternatives considered:**
- Scalars plus boundary assert/rebuild — smaller diff; fails literal one-carrier contract; easy to miss call sites.
- Newtype budgets only without cached carrier — improves parse safety; still derived-per-site unless embedded.
- Defer G1 — rejected; verification already FAILED this must-have.
- **Chosen: embed validated carrier on `EffectiveRagSettings`** — true SSOT; matches G1 wording.

**Chosen implementation:**
- In `EffectiveRagSettings::try_from_settings`, after scalar/ceiling validation, construct and store `grounding_limits: GroundingLimits`.
- Make `GroundingLimits` fields private; expose read-only accessors.
- Single constructor path derives **total** as `f(evidence, output)` only — **no config total override**.
- OpenRouter / generation config is **settings-only**: accept `&GroundingLimits` (or settings slice) from effective settings; remove divergent independent budget construction.
- Evidence packing, usage validation, max completion tokens, and `validate_grounding` all borrow the same carrier.
- Close related review WR-10 in the same change (no public bypass of ceilings).

**Estimated effort:** Medium

**Acceptance criteria:**
- `EffectiveRagSettings` holds exactly one `GroundingLimits` instance used on the production query and startup generation paths (inspectable in code; no second `GroundingLimits::new` on those paths with independent scalars).
- Non-default evidence/output budgets pass end-to-end usage and packing validation against that carrier (existing effective-usage tests remain green and assert shared values).
- Illegal direct construction or unvalidated `with_grounding_limits` bypass is impossible or rejects above service ceilings.
- Startup still rejects budgets above service ceilings before readiness.

**Risk if not fixed:**
Configured limits silently disagree across packing vs provider validation; false rejects or accepts under wrong budgets.

**Consequences:**
- Good: one authority object; simpler audits; WR-10 closed.
- Bad: call-site and test construction churn; generation API slightly stricter.

## P24-BODY: Bound provider response bodies before allocation

**Decision:** Ship.

**Problem:**
Chat path materializes `response.bytes()` then checks 256 KiB. Model metadata uses `response.json()` with no body cap. Embedding client has the same class of unbounded deserialize. Limit-after-read allows memory exhaustion before rejection (`engine/src/generation/openrouter.rs`, `engine/src/client/mod.rs`).

**Rationale:**
Process-level DOS on a shared Engine defeats RAG-02 bounded-service assumptions. Post-buffer checks are not fail-closed under hostile or buggy upstreams.

**Alternatives considered:**
- Content-Length only — simple; bypassed by chunked or lying CL.
- Client middleware only — coverage uncertain across call sites.
- Split caps per endpoint — optional later; not required for first ship.
- Status quo or MVP waive — rejected; availability risk is higher severity than log-text debt.
- **Chosen: shared bounded streaming reader on every provider path.**

**Chosen implementation:**
- Add one helper, e.g. `read_body_limited(response, max_bytes) -> Result<Bytes, …>`:
  - If `Content-Length` present and `> max`, error without reading body.
  - Otherwise stream/read with hard stop at `max + 1` observed bytes; error and drop buffer.
  - Success only with `len <= max`.
- Apply to chat, model-metadata, and embeddings.
- Deserialize only via `serde_json::from_slice` (or equivalent) on the limited buffer.
- Single shared ceiling: **256 KiB** (`MAX_RESPONSE_BODY_BYTES`), matching current chat policy.
- Oversized → fail-closed provider/infra mapping; no generation continuation; no partial parse.

**Estimated effort:** Medium

**Acceptance criteria:**
- Body of exactly max bytes can succeed when otherwise valid.
- Body of max+1 is rejected on chat, metadata, and embeddings paths.
- Missing `Content-Length` still cannot allocate unbounded body (streaming cap enforced).
- Focused tests cover all three paths; full locked Rust suite remains green.

**Risk if not fixed:**
Engine OOM or severe memory pressure from a single provider response; silent weakening of P24.

**Consequences:**
- Good: real pre-allocation bound; uniform provider policy.
- Bad: custom body read path to maintain; slight latency/code complexity.

## RAG02-CEIL: Service-safe retrieval and request ceilings

**Decision:** Ship.

**Problem:**
Validation allows candidate/final/query/filter-scale values up to roughly `i32::MAX`. Values flow into LanceDB collect, BM25 structures, and fusion vectors. BM25 may size work from full document count before truncation. Verification treats this as blocking roadmap SC1 / RAG-02 bounded evidence.

**Rationale:**
“Bounded evidence” is a service property before generation. Accepting absurd but “valid” config makes other limits irrelevant under load.

**Alternatives considered:**
- Code-only fixed ceilings with no config tunability — simple; less deploy flexibility.
- Memory-budget-derived caps — hard to estimate Lance/BM25 cost accurately in MVP.
- Warn-only or MVP waive — rejected; leaves SC1 failed.
- BM25-only alloc fix — incomplete; dense/config surface remains unbounded.
- **Chosen: operator-configurable limits with code absolute maximums; reject over-ceiling at startup.**

**Chosen implementation:**
- Introduce absolute service ceilings (constants or `ServiceCeilings`) enforced in `EffectiveRagSettings::try_from_settings` and retrieval `QueryRequest::validate`.
- **No silent clamp** — over-ceiling config fails startup (and request boundary if overrides exist).
- BM25 working set / scoring workspace bounded by effective candidate ceiling, not raw full-corpus size alone.
- Provisional absolute maxima (pin exact integers at plan/implement time against fixture + `config.example.toml`):

```text
per-source candidate_limit  <= 500
final_limit                 <= 100   # and <= candidate_limit
query_bytes                 <= 8192
filter keys                 <= 32
values per filter key       <= 64
RRF weights                 finite and magnitude-capped (align RRF-FINITE)
```

- Example/default toml stays at small happy-path values well under maxima.
- Prefer fixing BM25 missing `QueryRequest::validate` (review WR-05) in the same effort if cheap.

**Estimated effort:** Medium

**Acceptance criteria:**
- Startup rejects configuration with any knob above absolute max (e.g. `candidate_limit = absolute_max + 1` or `i32::MAX`).
- Startup accepts current example/default config.
- BM25 path does not allocate solely from unbounded full document count when candidate limit is smaller (test or structural proof).
- Documented ceilings appear in example config comments or ops docs touched by the change.

**Risk if not fixed:**
Availability collapse under misconfiguration; SC1/RAG-02 remain unverified.

**Consequences:**
- Good: fail-closed resource envelope; tunable within safe band.
- Bad: two-layer docs (operator limit vs absolute max); strawman numbers may need one adjust pass.

## RRF-FINITE: Finite fused scores and safe JSON commit

**Decision:** Ship.

**Problem:**
RRF accumulation in `engine/src/retrieval/fusion.rs` lacks finiteness checks; large weights and duplicate contributions can yield `+Inf`. Gateway `writeJSON` commits HTTP status then encodes and ignores encode errors (`gateway/main.go`). Go `encoding/json` rejects non-finite floats → clients can observe HTTP 200 with empty or malformed body.

**Rationale:**
Malformed success breaks API trust. Rust-only or Go-only fixes leave residual paths. This is user-visible correctness, not polish.

**Alternatives considered:**
- Rust-only finite checks — leaves generic writeJSON hazard.
- Go-only encode-before-header — leaves Inf in proto/metrics.
- Sanitize Inf to 0 / drop candidate as success — hides corruption; weak fail-closed.
- New score type (fixed-point) — out of MVP scope.
- MVP waive — rejected.
- **Chosen: guard both sides.**

**Chosen implementation:**
- Rust: after each RRF contribution and accumulator update, require `is_finite()`; reject non-finite weights/scores at boundary.
- Non-finite → **fail the query** with typed retrieval error and existing fail-closed mapping — do not clamp-as-success.
- Prefer **WR-01** in the same change: dedup per source/chunk before contribute (duplicates amplify overflow).
- Weight magnitude caps from RAG02-CEIL reduce but do not replace runtime finite checks.
- Go: marshal/encode to a buffer first; on success write header + bytes; on failure return **HTTP 500** with existing error envelope — never commit empty 200.

**Estimated effort:** Small–Medium

**Acceptance criteria:**
- Unit test: absurd weight and/or duplicate flood returns error and never emits non-finite `fused_score` in a successful response path.
- `writeJSON` (and twins) encode-before-header; targeted Go test proves encode failure does not yield successful empty body.
- Cross-runtime happy path still passes with normal finite scores.
- Full Go and locked Rust suites green.

**Risk if not fixed:**
Callers treat corrupt payloads as success; ranking and clients diverge silently.

**Consequences:**
- Good: defense in depth; cleaner success semantics for all JSON responses.
- Bad: touches Rust and Go; strict fail on non-finite may surface previously hidden bad configs (desired).

## PERSIST-RAW: Lance-native append-then-delete replace

**Decision:** Ship.

**Problem:**
`persist_raw` deletes the existing staged row before schema lookup, `RecordBatch` build, and add (`engine/src/main.rs`). Failure after delete leaves neither old nor new replay payload — document unrecoverable for startup replay.

**Rationale:**
Staging raw is the durability asset for ingest recovery. Delete-first creates a permanent data-loss window. Must match Lance Format: immutable fragments, versioned writes, deletion via deletion index (not in-place rewrite).

**Alternatives considered:**
- Side-table + pointer swap — clearer atomic pointer; more moving parts for MVP.
- App-level soft-delete + GC parallel to Lance — redundant with deletion index if Lance delete is used correctly.
- Multi-op SQL transaction assumption — may not match Lance version model.
- Keep delete-first or MVP waive — rejected; real data loss.
- **Chosen: write-new then mark-old-deleted, expressed as Lance append + deletion index, with generation latest-wins.**

**Chosen implementation:**
- Follow Lance semantics only:
  - Each successful write creates a new table version (immutable fragments).
  - Removals use Lance delete APIs that mark rows in a **deletion index**, not file rewrites.
- Logical identity: stable `document_id` + monotonic **`generation`** (or equivalent total order). Add column if missing.
- Replace sequence (binding order):
  1. Read latest non-deleted generation `G` for `document_id` (if any).
  2. **Append** successor row with `generation = G+1` (or `1`).
  3. **Verify** append success / readable at current version per Lance API.
  4. Only then **delete** prior generation(s) (`document_id = ? AND generation <= G`) via Lance delete (deletion index).
- Readers and replay: always **latest non-deleted generation wins** for a `document_id`.
- Failure policy:
  - Before append succeeds: old row untouched.
  - After append+verify, if delete of old fails: **keep both rows**; fail or retry job for visibility; **never** delete the new row to “clean up” if that re-opens a zero-row window.
- Do not implement app-level fragment rewrite or delete-first “in-place update” documentation.
- Compaction/GC of old Lance versions is out of band (Lance ops); not a Phase 03 custom rewrite GC.

**Estimated effort:** Medium–Large

**Acceptance criteria:**
- Code path never deletes prior generation before successor append+verify succeeds (enforced by structure and/or ordering test).
- Crash/failure between append and delete: restart/replay still observes the new payload (old may also exist until delete retries).
- No successful replacement path ends with zero rows for that `document_id` after successor append succeeded.
- Replay/startup selection uses latest non-deleted generation consistently with online readers.
- No design dependency on in-place fragment mutation.

**Risk if not fixed:**
Permanent loss of staged documents; ingest cannot heal across process death.

**Consequences:**
- Good: durable replace aligned with Lance; recovery-friendly failure modes.
- Bad: brief dual-generation visibility; schema may gain `generation`; readers must filter latest-wins everywhere staged rows are consumed.

## WR-01: Dedup before RRF contribute

**Decision:** Ship (prefer bundled with RRF-FINITE).

**Problem:**
Fusion adds contribution before checking whether a source rank for the chunk already exists; duplicate rows inflate `fused_score` (`engine/src/retrieval/fusion.rs`). Amplifies non-finite risk and non-deterministic rank quality when fixtures or indexes duplicate.

**Rationale:**
Cheap correctness fix; directly supports RRF-FINITE and deterministic hybrid ranking.

**Alternatives considered:**
- Separate later warning-only fix — acceptable only if same-week follow-up; prefer same PR.
- **Chosen: dedup per source/chunk before contribute in the RRF-FINITE change set when low-cost.**

**Chosen implementation:**
- Skip contribution when source rank already populated for `chunk_id`, or dedup each source list by `chunk_id` before fusion.
- Fixture seeder idempotency (review WR-02) remains optional follow-up unless it blocks tests.

**Estimated effort:** Small

**Acceptance criteria:**
- Duplicate candidates from one source contribute at most once per source to fused score.
- Existing fusion determinism tests pass; add regression with intentional duplicates.

**Risk if not fixed:**
Inflated scores; harder finite-score guarantees; flaky ranks under duplicate data.

**Consequences:**
- Good: stable RRF; less Inf pressure.
- Bad: none material.

## D1-LOG: Identity-only safe structured D1 logs

**Decision:** Accept-as-is (MVP override of plan 03-17 log clause).

**Problem:**
Verification requires D1 infrastructure failures to log only identity-safe structured fields (`session_id`, `correlation_id`, `error_kind`, fixed event name). Current `d1_status` still interpolates full `msg` into tracing. Fail-closed behavior and status-path identity metadata already work (3/4 plan truths).

**Decision rationale:**
Human decider explicitly overrode the prior safe-log requirement for Phase 03 MVP. Ops debuggability outweighs log hygiene at current single-operator / non-production trust assumptions. This is **not** a waiver of D1 fail-closed or status identity.

**Conflict with source material:**
- Source (03-VERIFICATION / plan 03-17): identity-only safe logs are a failed must-have.
- User decision: safe structured log **not required** for Phase 03 MVP; keep full `msg` in logs (option E).

**Minimum guardrail to ship now:**
- Do **not** strip or redact D1 logs in gap-closure implementation.
- **Do** update phase documents so re-verification does not treat D1-LOG as an open code blocker:
  - Record debt in `.planning/.../deferred-items.md` (e.g. `DEBT-D1-SAFE-LOG`) owned by Phase 06 (or hardening milestone).
  - Mark verification truth for identity-only logs as **waived / deferred by human override**, with pointer to this ADR; or rewrite the truth to: “fail-closed + identity on status path; detailed log message allowed in MVP.”
- Preserve fail-closed: no generation / no model-only continuation on D1 infra failure.
- Preserve status/response identity fields already implemented.

**Known risk:**
- Likelihood now: Medium (any provider/transport error path)
- Impact if realized: Medium (sensitive URLs, payload fragments, or PII-adjacent text in log sinks)
- Residual exposure: long-lived log pipelines may retain untrusted upstream free text

**Current operating constraints:**
- Treat log sinks as sensitive; do not ship shared multi-tenant log access without reopening this item.
- Prefer local/single-operator deployments until safe-log ships.

**Tracking:** `DEBT-D1-SAFE-LOG` (create/confirm in deferred-items.md)

**Target:** Phase 06 hardening (or earlier if escalation triggers fire)

**Escalation trigger:**
Any of: multi-tenant deployment; shared log access beyond single operator; compliance/retention requirement on logs; production internet-facing Engine; incident involving secret or PII in logs.

**Future acceptance criteria:**
- D1 warning/error logs include only fixed event name + `session_id` + `correlation_id` + `error_kind` (and optional allowlisted safe codes).
- Regression test with tracing subscriber: required fields present; fixture sensitive substring from error `msg` absent.
- Fail-closed + status identity remain green.
