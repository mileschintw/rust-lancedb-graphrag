`score` and `compare-levers` can now score a run on a dev-role corpus (S1, D-259; S2, D-252). Before this change, both read the split's held-out lists whatever the corpus's `[split] role` said. A dev run, whose question file holds only the dev pool, was refused with "308 held-out G question(s) cannot be scored".

On a corpus whose role is `dev`, both commands now read the dev population, scoped the way `dev_reads.py` does:

- **G:** the dev IDs with gold evidence (90 for MultiHop-RAG).
- **null:** the dev null IDs (10).

Held-out and rehearsal corpora read the split as they did before. One shared helper, `score.scope_split`, does the scoping. `_load_split_inputs` calls it, and so does `lever_comparison._load_inputs`, so every population built downstream reads the dev lists:

- in `score`: P_all, the null dimensions and the judged path;
- in `compare-levers`: the pairwise populations and both null guards, the reader-comparison guards included.

The null guard's floor is therefore `ceil(0.80 × |dev null|)`.

Scoping differs from `dev_reads.py` in one way. A dev ID missing from the corpus's question file stays in G, so `score` and `compare-levers` refuse the run instead of silently dropping that ID. All 100 MultiHop-RAG dev IDs are in `questions.diag.jsonl`, so the real S1 and S2 runs are unaffected.

The journal's split marker (D-107) is still checked against the split as written. The marker hashes the whole file, so checking it against the scoped view would refuse every dev drive that recorded one.
