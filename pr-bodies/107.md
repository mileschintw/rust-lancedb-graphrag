## Summary

`OpenRouterBatchClient.submit` now posts the batch-level `endpoint`, `model` and `provider` fields ahead of
`requests`, as OpenRouter's Batch API reference requires. Before, it sent only `{"requests":[...]}`, so a submit
could be refused, or worse, run unpinned on shared capacity and fail every record's `is_byok` replay clause.

- `eval/src/lancet_eval/batch_client.py`:
  - `_payload` takes an optional ordered `head` of batch-level fields and writes them before `requests`. The
    Anthropic path passes none, so its payload is unchanged.
  - New `_openrouter_head` builds `{endpoint: "/v1/chat/completions", model, provider}`. `model` and the provider
    pin come from the request bodies, which the rewrite (`reader_request.py`) already sets from the reader's
    declaration, so `batch.py` needs no new argument. The batch-level `provider` keeps only `only` and
    `allow_fallbacks`, the two keys the schema allows.
  - It fails closed before anything is sent: a body that is not a JSON object, names no model or pins no
    `provider.only`, bodies that disagree on model or pin, or an empty batch raise `BatchClientError`.
  - Each body is still embedded as the exact text whose hash the manifest records, so `body_sha256` does not change.
- `eval/tests/test_batch.py`: one test pins the payload's top-level keys and their order, the values and the
  byte-for-byte bodies, through a fake `httpx.post` (no network). One parametrised test covers the four refusals
  (two models, no model, two provider pins, no provider).

Field names follow OpenRouter's create-a-batch reference
(https://openrouter.ai/docs/api/api-reference/batch/create-a-batch.md, read 2026-10-31). They match
`experiments/v1.1/PLAN.md:325`.
