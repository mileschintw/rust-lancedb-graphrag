## Summary

`generate_from_context` gets a third mode, `render`. It runs the `generate` tail over reader outputs taken from a results file instead of calling the network.


To keep it to one copy of the logic, the OpenRouter adapter's choice checks moved verbatim from `OpenRouterGenerator::execute_one_call` into `pub OpenRouterGenerationConfig::accept_choice(&GenerationRequest, ProviderChoice)`. The live adapter now calls it, and so does `render`. Error kinds, messages, check order and `generation_output_rejected` events are unchanged. ### For #53: CLI form

```text
generate_from_context render --input <context_export.jsonl> --results <results.jsonl> [--levers <names>]
```

`--results` is required for `render`, and `pack`/`generate` refuse it. `--levers` has the same semantics in all three modes: comma-separated wire names, an empty value is no lever, and without the flag the configured `[engine.levers] defaults` apply. It is parsed once and passed to the same `run_row` tail, so render under the levers a row was packed with (`snapshot.levers`) runs that row's tail exactly as pack/generate did. `parse_args_reads_render_results` pins that render and pack read `--levers` alike.

### For #53: results-file line schema

One JSON object per line (`deny_unknown_fields`):

```json
{"question_id": "q-1", "arm": "graph_on",
 "content": "<raw message content: the JSON text of the engine's ModelOutput>",
 "finish_reason": "stop",
 "usage": {"prompt_tokens": 900, "completion_tokens": 40, "total_tokens": 940}}
```

- `question_id` + `arm` match an export row. A line whose key matches no row is ignored.
- `finish_reason` uses the chat-completions values. `stop` is the only one accepted. Any other value (`refusal`, `length`, …) or `null` becomes an `error` line. #53 maps the Anthropic `stop_reason` (`end_turn` → `stop`).
- `usage` is chat-completions usage and is required. The adapter's budget checks apply to it: `prompt_tokens` ≤ the evidence token budget, `completion_tokens` ≤ max output tokens, and `total_tokens` ≥ their sum and ≤ the ceiling.
- Per row:
  - a row with no result line → `error_type: "MISSING_RESULT"`;
  - a line whose key reads but whose other fields don't → `"INVALID_RESULT"`;
  - a rejected output → the node's error kind (for example `NODE_ERROR_KIND_LLM_GENERATION_FAILED`).

  In each case the run goes on, and every row gets exactly one line.
- A line with no readable key, or a second line for the same key, fails the whole input before any row is written (the same rule as an unreadable export row).

No eval files were added.
