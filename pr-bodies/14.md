## Summary

`lancet-eval run-external` drives an external arm. It answers an arm's context export through the generate-only bin and journals the result beside the Lancet arms.

```text
run-external --corpus C --arm llamaindex --export <dir>/context_export.jsonl
  refuse before any reader call:
    the arm is not an external arm, or not in C's arm list
    the export fails read_export; a row of another corpus, arm or question; evidence != 8
    pipeline_config.json is missing a flat key or index_fingerprint
    the run's export already holds a different row for the same question
    [split] gates (D-73 pre-registration, split inputs, split role) and the split marker
    a gate-stage journal; --no-resume on a journal that holds records
  copy the arm's rows into <run>/context_export.jsonl
  for each batch of 16 rows not yet in the journal (resume key):
    generate_from_context pack      -> generation_model, provider.order from the sent body
    generate_from_context generate  -> answer ending in "Answer:"
    journal one RunRecord per row: success + external block, or an error record
```

```diff
 eval/src/lancet_eval/
+├── external_run.py   # run_external(), the external drive
 ├── run.py            # require_split_gates, resume_state, reconcile_quietly
 │                     #   factored out of drive(); write_context_export keeps
 │                     #   external rows at the end of a drive
 └── cli.py            # + run-external; export-context calls write_context_export
 eval/tests/
+└── test_run_external.py
```

- **External block.** The pipeline and `index_fingerprint` come from `pipeline_config.json`'s flat top-level keys. `generation_model` and `generation_provider_order` come from the request body the bin's `pack` mode builds. The `generate` output line carries neither, and `pack`'s body is the body `generate` posts (the parity check pins this).
- **Reader levers.** The reader runs with `evidence_metadata` only. Document metadata then reaches the reader in the same DocMeta tags as Lancet's metadata lever (D-248).
- **Shared journal.** An S0 journal holds Lancet and external records together. `export_context` joins every success record on its checkpoint, so it failed closed on external records. `run.write_context_export` exports the engine records from their checkpoints, carries the external rows over from the run's export, and fails closed when an external success record has no row. Both `run`'s end-of-drive export and `export-context --run` use it. `context_export.py` is unchanged.
- **Token usage.** Usage goes to `workflow_meta.prompt_tokens`/`completion_tokens`, so spend accounting sees it. `duration_ms` stays 0.0, since external latency is not comparable end to end (#6 story 35).
- **`chunk_index` (lane 11's open point).** Nothing in `eval/` reads `chunk_index`, so nothing scored depends on it and it is left as is. The reader prompt does show `chunk_index=0` in each external evidence block's `<PROVENANCE>`, because the LlamaIndex chunk IDs are `<document_id>#<n>`.

## Review

Three rounds: two-axis review (standards, spec), then two rounds over the fixes.

- **Fixed: whole export in one bin call.** One bin call over the whole export ran under one 1800 s timeout, so a slow reader or a crash lost every paid answer. The drive now answers in batches of 16, journalling each batch, and copies the rows into the run's export first.
- **Fixed: `export-context` on a shared journal.** It still called `export_context` and failed closed on a shared journal. It now calls `run.write_context_export`, with the coordinator's approval to widen that one cli.py call.
- **Fixed: stale docstrings.** Two docstrings described the drive before batching.
- **Note: generation values come from `pack`, not `generate`.** The brief says "from what generate actually sent (its output)", but the generate line carries neither field. Taking them from `pack`'s body keeps the engine unchanged (it is lane 25's). The alternative is to add `model` and `provider_order` to the bin's generate line in a later engine change.
- **Note: header parity with `run`.** run-external writes a v1.1 header without a `max_retries` marker and refuses gate-stage journals; it does not compare `max_retries`. This lets `run --retries 2` and `run-external` share a journal.
- **Note: atomic writes.** Three near-identical atomic export writers now exist: `export_context`, `write_context_export`, and `_write_run_export`. A shared helper in `context_export.py` would remove the copies.
- **Note: dropped fields.** `citations`, `answer_basis` and `final_answer` from the generate line are not kept, because `RunRecord` has no fields for them.
- **Note: pinned export rows.** The run's export pins the arm's rows even for questions that were never answered. A rerun with an export from another index is refused for the whole run directory.
- **Note: naming and seams (judgement calls).** `_require_matching_split_marker` is imported from `run.py` while it is still private. There are two runner seams: the `bin_runner` module global and the `runner=` parameter. Some helper names are thin: `_read`, `_bin`, `_sent`.
