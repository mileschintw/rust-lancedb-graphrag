## Summary

`lancet-eval batch submit` and `batch fetch` read an S2 reader arm (`<arm>@<reader>`) through a batch API. They work on the run directory `replay-init` wrote, and their output journals and scores like any other arm.

```text
eval/src/lancet_eval/batch_client.py  # port + OpenRouter and Anthropic Message Batches clients, response normalisers
eval/src/lancet_eval/batch.py         # submit / fetch, manifest, cost estimate, replay records
eval/src/lancet_eval/parity.py        # run_bin(..., results) for render; check-prompt-parity skips reader rows
eval/src/lancet_eval/cli.py           # the `batch` group only
eval/tests/test_batch.py              # seam S-F with a fake client and a fake bin; one integration test
docs/testing.md                       # the integration command also runs test_batch.py
```

### `batch submit --run <S2 dir> --arm <reader arm> [--limit N] [--retry-errors]`

1. Reads the run's corpus from the journal header (the S2 corpus `replay-init --corpus` wrote) and the reader's declaration from that corpus's pre-registration. The arm must be a reader arm the corpus lists.
2. Refuses while a manifest of the arm is `submitting` or `submitted`.
3. Picks questions in the base arm's journal order:
   - by default, each base success question the arm has no record of. `--limit N` takes the first N, so the pilot and a later full submit read disjoint questions;
   - with `--retry-errors`, each question whose latest record is a request that produced no answer (`batch_errored`, `batch_expired`, `batch_canceled`, `batch_no_result`). A billed answer `render` rejected, or a response that arrived unreadable, is final and is not resubmitted.
   - It refuses when nothing is left. The message counts the questions that already have a success record and the ones that have an error record.
4. Packs each base row with `generate_from_context pack` under the levers its base record echoes (`snapshot.levers`). It refuses before any request if a row's hash differs from the one the header carried, if the packed user message is not the row's `assembled_prompt`, or if the bin fails.
5. Rewrites each body for the reader (#51) and prints the D-258 cost estimate. The estimate never refuses. It is built on `ReaderPrice` × `BATCH_PRICE_FACTOR`: the deepseek record's tokens give the expected cost, and `max_completion_tokens` gives the bound. It also prints the arm's spend so far, from `measure.compute_spend(..., readers=preregistration.readers_of(prereg))`.
6. Writes the manifest `<run>/batches/<arm slug>-<n>.json` with state `submitting` and a null `batch_id`, then submits one batch with `custom_id` = question ID, then records the batch ID as `submitted`. Per request, the manifest keeps the levers, the body hash, the base row hash, the rewritten fields and the `pack` body. If the endpoint refuses the batch, the state becomes `rejected`. A crash between the write and the ID leaves `submitting`, which counts as pending and needs a manual check.
7. Journals one `error_type = "base_error"` reader record for each base error record, once the batch is accepted. If the only thing left is new base errors, it journals them and refuses.

Each body goes out as the exact JSON text the rewrite produced, embedded in the payload without re-serialising. So the manifest hash, the bytes sent and the `body_hash` clause's recomputation are the same value.

### `batch fetch --run <S2 dir> [--arm ...]`

For each `submitted` manifest whose batch has finished:

- Succeeded results go into a results file in #50's schema (`{question_id, arm, content, finish_reason, usage}`; Anthropic `end_turn`→`stop`, `max_tokens`→`length`). That file and the reader rows (the S2 base row under the reader label) go to `render --levers <the request's levers>`.
- A rendered answer becomes a success record. Its export row is appended before the record.
- An answer `render` rejects becomes an error record that keeps its `replay` block and usage, because the call was billed.
- An errored, expired or canceled request, or one missing from the results, becomes an error record with no replay block.
- Each record carries the base record's `correlation_id` and `index_generation`, the S2 corpus and `session_id` = batch ID. Its `workflow_meta` tokens come from the response usage; completion tokens include reasoning tokens.
- A request the journal already holds from the same batch is skipped, and the manifest becomes `fetched`, so a re-run adds nothing.

`ReplayProvenance`, per #80: `model` comes from the response. For OpenRouter, `provider`, `usage.is_byok` and `usage.completion_tokens_details.reasoning_tokens` also come from the response; `content_block_types` is null. For native Anthropic, `provider` is `api.anthropic.com`, `is_byok` is null, `reasoning_tokens` is 0 and `content_block_types` lists the block types in order. If an OpenRouter response has no reasoning count, the record gets `-1`, so the clause fails closed for a reader whose thinking is not `on`.

### Clients

Both clients take their key from the environment (`OPENROUTER_API_KEY` / `ANTHROPIC_API_KEY`) and send nothing until the owner runs a submit.

- OpenRouter: `POST /api/v1/batches` with inline `{custom_id, body}`, then `GET /api/v1/batches/{id}`. The response shape is not documented, so the pilot has to confirm it.
- Anthropic: `POST /v1/messages/batches` with `{custom_id, params}`, then `results_url`, with `anthropic-version: 2023-06-01`.
